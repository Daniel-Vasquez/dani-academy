En B4 viste por qué los índices son la herramienta número uno de rendimiento. Ahora toca aplicarlos en MongoDB: crearlos desde el código, elegir el orden de los campos con la regla **ESR** y comprobar con `explain` que tus consultas los usan de verdad.

## Crear índices

```ts
await entrenos.createIndex({ userId: 1 }); // simple
await entrenos.createIndex({ userId: 1, fecha: -1 }); // compuesto
await usuarios.createIndex({ email: 1 }, { unique: true }); // único
await progreso.createIndex(
  { userId: 1, sectionId: 1 },
  { unique: true, name: "user_section_unique" }, // con nombre propio
);
```

- `1` = ascendente, `-1` = descendente. En un índice simple da igual; en uno compuesto importa para ordenar por varios campos a la vez.
- `createIndex` es **idempotente**: si el índice ya existe con la misma definición, no hace nada.
- `_id` siempre tiene un índice único automático.

```ts
await entrenos.indexes(); // lista los índices de la colección
```

## Dónde crearlos: un script, no en cada petición

Crear índices no es parte de atender una petición. Esta plataforma los define en `scripts/db-setup.ts` y los aplica con un comando:

```bash
npm run db:setup
```

```text
✓ índice section_progress.user_section_unique
✓ índice section_progress.user_course
✓ índice quiz_attempts.user_course_submittedAt
…
```

Así quedan versionados en el repositorio y se pueden aplicar igual en desarrollo, _preview_ y producción.

## Leer un `explain`

`explain("executionStats")` te dice **cómo** ejecutó MongoDB la consulta:

```ts
const plan = await entrenos.find({ userId: "u1" }).sort({ fecha: -1 }).explain("executionStats");
```

Lo que debes mirar:

| Dato                | Dónde                      | Qué te dice                                                       |
| ------------------- | -------------------------- | ----------------------------------------------------------------- |
| Etapas              | `queryPlanner.winningPlan` | `COLLSCAN` (recorre toda la colección) o `IXSCAN` (usa un índice) |
| `totalDocsExamined` | `executionStats`           | Documentos leídos                                                 |
| `totalKeysExamined` | `executionStats`           | Entradas de índice leídas                                         |
| `nReturned`         | `executionStats`           | Documentos devueltos                                              |

Sin índice:

```text
SORT ← COLLSCAN     docsExamined: 4   keysExamined: 0   nReturned: 3
```

Con el índice `{ userId: 1, fecha: -1 }`:

```text
FETCH ← IXSCAN      docsExamined: 3   keysExamined: 3   nReturned: 3
```

El índice resuelve el filtro **y** el orden: desaparece la etapa `SORT` (ordenar en memoria) y solo se leen los documentos que se devuelven. La consulta ideal tiene `totalDocsExamined ≈ nReturned`.

En Compass, la pestaña **Explain Plan** muestra lo mismo de forma visual.

## Índices compuestos: la regla ESR

¿En qué orden pongo los campos? La regla **ESR**:

1. **E**quality: primero los campos que filtras por **igualdad** (`userId: "u1"`).
2. **S**ort: después los campos por los que **ordenas** (`fecha: -1`).
3. **R**ange: al final los campos con **rangos** (`km: { $gte: 5 }`, fechas entre dos valores).

```ts
// Consulta: entrenos de un usuario, de un tipo, con km ≥ 5, del más reciente al más antiguo
entrenos.find({ userId: "u1", tipo: "running", km: { $gte: 5 } }).sort({ fecha: -1 });

// Índice según ESR:  E        E          S            R
entrenos.createIndex({ userId: 1, tipo: 1, fecha: -1, km: 1 });
```

Y recuerda la guía telefónica: un índice compuesto sirve para consultas que usan sus campos **desde la izquierda**. `{ userId: 1, fecha: -1 }` sirve para filtrar por `userId`, pero no para filtrar **solo** por `fecha`:

```text
find({ fecha: { $gte: … } })   →   COLLSCAN
```

## Índices TTL: borrado automático

Un índice TTL (_Time To Live_) sobre un campo de fecha hace que MongoDB **borre solo** los documentos cuando caducan:

```ts
// Borra cada documento cuando llega la fecha de su campo expiresAt
await rateLimits.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });

// O: borra 30 días después de createdAt
await logs.createIndex({ createdAt: 1 }, { expireAfterSeconds: 60 * 60 * 24 * 30 });
```

El proceso de borrado pasa cada minuto aproximadamente: no es exacto al segundo. Es ideal para sesiones, códigos temporales o límites de uso. Esta plataforma lo usará para su _rate limiting_ en la Tanda de calidad.

## Qué indexar en tu app

1. Lista las consultas frecuentes (las de cada página y endpoint).
2. Para cada una, construye el índice con ESR.
3. Si dos consultas comparten el prefijo, un solo índice puede servir a ambas: `{ userId, courseId }` sirve también para filtrar solo por `userId`.
4. Comprueba con `explain` y vigila los índices que nunca se usan (Atlas te lo muestra).

## Errores comunes

- **No tener índices** hasta que la app va lenta.
- **Índices compuestos en el orden equivocado** (el rango antes del orden, por ejemplo).
- **Un índice por cada campo** en lugar de compuestos pensados para las consultas reales.
- **Crear índices en cada petición** en lugar de en un script.
- **Fiarse sin mirar `explain`**.

## Resumen

- `createIndex` crea índices simples, compuestos, únicos y TTL; es idempotente.
- Define los índices en un script versionado, no en cada petición.
- `explain`: busca `IXSCAN` y que `totalDocsExamined` se acerque a `nReturned`.
- ESR: igualdad, luego orden, luego rangos.
- Los índices TTL borran solos los documentos caducados.
