Un test es un programa que comprueba otro: se escribe una vez y se ejecuta miles. Su valor llega meses después, cuando alguien rompe una regla sin darse cuenta y el test lo avisa en un segundo, antes que un usuario. Pero también cuesta escribirlo, mantenerlo y esperarlo. Aquí decides qué merece un test, mides lo que cuesta cada tipo y preparas Vitest para los módulos de Astro.

**Requisitos:** la app de entrenos de I5, con los 13 tests de I3.5. Este curso la usa de principio a fin.

## Paso 1: la pirámide y el trofeo

**Qué es:** tres tipos de test, según cuánto de la app ponen en marcha.

| Tipo                   | Qué prueba                                        | Ejemplo en tu app                                 | Velocidad          | Si falla, el fallo está… |
| ---------------------- | ------------------------------------------------- | ------------------------------------------------- | ------------------ | ------------------------ |
| **Unitario**           | Una función o un módulo, aislado                  | `lunesDe()`, el servicio con un repositorio falso | Milisegundos       | En esa función           |
| **Integración**        | Varias piezas juntas, con sus dependencias reales | El repositorio contra un MongoDB de verdad        | Décimas de segundo | Entre esas piezas        |
| **_End-to-end_** (E2E) | La app entera, desde un navegador                 | Registrarse, crear un entreno y verlo en la lista | Segundos           | En cualquier parte       |

**Cómo se usa:** la **pirámide** pide muchos unitarios, menos de integración y pocos E2E, porque cuanto más arriba, más lentos y difíciles de depurar. El **trofeo** (de Kent C. Dodds) carga la integración: la mayoría de los fallos web están en cómo encajan las piezas, y un unitario con todo simulado no los ve. Coinciden en que **cada capa atrapa fallos distintos** y los E2E son pocos y para lo crítico.

- **Merecen un test:** las **reglas de negocio** ("solo el running lleva km"), los **bugs que ya ocurrieron** (I8.6), los **flujos críticos** (registrarse, entrar, guardar) y los **casos límite** (semana vacía, fin de mes, un id mal formado).
- **No lo merecen:** el código sin lógica, lo que ya comprueba TypeScript ni las librerías ajenas (que Zod valide un correo es cosa de Zod; lo tuyo es **qué** esquema usas).

<Callout type="risk">

- **Un test que nunca puede fallar no prueba nada:** rompe el código a propósito de vez en cuando y comprueba que se pone en rojo.
- **Prueba el comportamiento, no la implementación:** "devuelve `cumplido: true` con 150 minutos" sobrevive a una reescritura; "llama a `reduce` dos veces", no.

</Callout>

## Paso 2: Vitest con la configuración de Astro

**Qué es:** `astro:env/server` no es un paquete de npm: es un **módulo virtual** que Astro genera desde `astro.config.mjs`, y Vitest no sabe crearlo sin esa configuración. **`getViteConfig`** le pasa la misma configuración de Vite que usa Astro.

**Cómo se usa:** un test que importa los servicios reales, `tests/unit/servicios.test.ts`:

```ts
// Archivo: tests/unit/servicios.test.ts
// Un test que importa los servicios reales: pasan por src/lib/mongo.ts, que usa astro:env
import { describe, expect, it } from "vitest";
import { servicios } from "../../src/services";

describe("servicios", () => {
  it("expone el servicio de entrenos y el de resumen", () => {
    expect(Object.keys(servicios)).toEqual(["entrenos", "resumen"]);
  });
});
```

Con la configuración "a secas" de I3.5:

```text

Error: Cannot find package 'astro:env/server' imported from /mi-entreno/src/services/index.ts
```

Ordena los tests por capas:

```bash
mkdir -p tests/unit tests/integration
git mv tests/entrenos.repo.test.ts tests/integration/
git mv tests/entrenos.service.test.ts tests/resumen.service.test.ts tests/unit/
```

Cambia los _imports_ de los tres archivos movidos de `"../src/…"` a `"../../src/…"`, y sustituye `vitest.config.ts`:

```ts
// Archivo: vitest.config.ts
// getViteConfig: Vitest usa la configuración de Astro (astro:env, astro:actions, alias…)
/// <reference types="vitest/config" />
import { getViteConfig } from "astro/config";

export default getViteConfig({
  test: {
    include: ["tests/{unit,integration}/**/*.test.ts"],
    hookTimeout: 120_000, // la primera vez, mongodb-memory-server descarga MongoDB
  },
});
```

- **El test de los servicios ya pasa;** bórralo tras el ejercicio (`rm tests/unit/servicios.test.ts`), el riesgo de abajo explica por qué.
- **`/// <reference types="vitest/config" />`** hace que TypeScript acepte la clave `test`, y **`include` con dos carpetas** deja fuera los E2E de I8.5, que ejecuta Playwright.
- **`getViteConfig` lee tu `.env` y valida `astro:env`:** con un `BETTER_AUTH_SECRET` de menos de 32 caracteres, lo que importa los servicios falla al cargar; lo que no importa nada de Astro sigue pasando.

<Callout type="risk">

- **Poder importar la base de datos real no significa deber:** `servicios.test.ts` crea un `MongoClient` con tu `MONGODB_URI`; uno que llamara a `servicios.entrenos.crear()` escribiría en tu base. Unitarios con repositorios falsos (I3.5); integración, con un MongoDB en memoria (I8.4).
- **Al actualizar Astro, comprueba que los tests arrancan:** `getViteConfig` depende de que su Vite sea compatible con tu Vitest.

</Callout>

## Paso 3: la estructura AAA

**Qué es:** cada test en tres partes. **_Arrange_** prepara los datos y el estado, **_Act_** hace **una** llamada a lo que se prueba y **_Assert_** comprueba lo que salió.

**Cómo se usa:** la app no muestra el **ritmo**, lo que más mira quien corre (minutos por km). Crea `src/lib/ritmo.ts`:

```ts
// Archivo: src/lib/ritmo.ts
// El ritmo medio de un entreno de running: cuánto se tarda en cada km

/** "m:ss min/km", o null si no hay km (no se puede dividir entre 0) */
export function ritmo(minutos: number, km: number | undefined): string | null {
  if (!km || km <= 0) return null;
  const minutosPorKm = minutos / km;
  const min = Math.floor(minutosPorKm);
  const seg = Math.round((minutosPorKm - min) * 60);
  return `${min}:${String(seg).padStart(2, "0")} min/km`;
}
```

En `src/components/Entrenos.tsx`, importa la función:

```tsx
import { ritmo } from "../lib/ritmo";
```

Y añade una línea bajo la de los km, dentro del `<li>`:

```tsx
            {e.km !== undefined && ` · ${e.km} km`}
            {e.tipo === "running" && e.km !== undefined && ` · ${ritmo(e.minutos, e.km)}`}
```

Sus tests, `tests/unit/ritmo.test.ts`; el primero marca las tres partes con comentarios:

```ts
// Archivo: tests/unit/ritmo.test.ts
import { describe, expect, it } from "vitest";
import { ritmo } from "../../src/lib/ritmo";

describe("ritmo", () => {
  it("45 minutos en 9 km son 5:00 min/km", () => {
    // Arrange: los datos de entrada
    const minutos = 45;
    const km = 9;
    // Act: UNA llamada a lo que se prueba
    const resultado = ritmo(minutos, km);
    // Assert: lo que tiene que salir
    expect(resultado).toBe("5:00 min/km");
  });

  it("convierte la fracción de minuto en segundos", () => {
    expect(ritmo(50, 8)).toBe("6:15 min/km"); // 6,25 min = 6 min 15 s
  });

  it("redondea al segundo más cercano", () => {
    expect(ritmo(25, 5.5)).toBe("4:33 min/km"); // 4,5454… min = 4 min 32,7 s
  });

  it("los segundos de una cifra llevan un cero delante", () => {
    expect(ritmo(61, 10)).toBe("6:06 min/km");
  });

  it("sin km no hay ritmo", () => {
    expect(ritmo(30, undefined)).toBeNull();
    expect(ritmo(30, 0)).toBeNull();
  });
});
```

- **Un comportamiento por test, y el nombre lo dice:** si falla "los segundos de una cifra llevan un cero delante", sabes qué se rompió sin abrir el archivo.
- **Un comentario con la cuenta** (`6,25 min = 6 min 15 s`) dice de dónde sale el esperado.
- **Los casos límite, en su test:** "sin km no hay ritmo" cubre `undefined` y `0`.

<Callout type="risk">

- **El valor esperado se calcula a mano:** pegar lo que devuelve `ritmo(25, 5.5)` solo comprueba que la función hace lo que ya hacía, aunque esté mal.
- **Un solo _Act_:** si un test crea, edita y borra y falla, no sabes cuál de las tres. Lo previo va en el _Arrange_.

</Callout>

<Callout type="risk">

- **Cinco tests en verde no hacen correcta la función:** `ritmo()` tiene un bug que ninguno encuentra (I8.6). Los casos límite se buscan a propósito.

</Callout>

<Callout type="mastery">

Sabes justificar por qué algo merece (o no) un test: es una regla de negocio, un bug que ya ocurrió, un flujo crítico o un caso límite; no lo es lo que ya comprueba TypeScript o una librería. Sabes qué cubre y cuánto cuesta cada capa (unitario, integración y E2E), configuras Vitest con `getViteConfig` para que entienda los módulos de Astro y escribes cada test con la estructura AAA.

</Callout>

## Resumen

- Unitario (milisegundos), integración (décimas) y E2E (segundos).
- Muchos unitarios y de integración; pocos E2E, solo para lo crítico.
- Reglas de negocio, bugs pasados, flujos críticos y casos límite.
- `getViteConfig` hace que Vitest entienda `astro:env` y compañía.
- AAA: preparar, **una** acción y comprobar, con el esperado calculado a mano.
