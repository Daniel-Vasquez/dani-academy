Esta plataforma vive en Vercel: `git push` y, un minuto después, está en internet con HTTPS. Este curso trata de hacer tú ese trabajo en un servidor propio. Aquí mides qué hace Vercel por ti, ejecutas tu app compilada como en producción en el Mac y en Ubuntu, y comparas Vercel, un VPS, un PaaS y Coolify con precios reales.

**Requisitos:** `entrenos-app` como quedó en I8, con su `.env`, y el Ubuntu de I6 (máquina virtual o VPS) con acceso por SSH.

## Paso 1: lo que Vercel hace por ti, medido

**Qué es:** los servicios que Vercel añade sin que los configures, vistos en las cabeceras de esta plataforma.

**Cómo se usa:** `curl` enseña las cabeceras (`-D -`) sin guardar el cuerpo (`-o /dev/null`). Primero, con `http://`:

```bash
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://academy.danielvasquez.lat/
```

```text
308 https://academy.danielvasquez.lat/
```

Un JavaScript de la página de entrada, diciendo que el cliente entiende Brotli (`-H "Accept-Encoding: br"`), el formato de los navegadores:

```bash
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip, br" https://academy.danielvasquez.lat/_astro/client.Dda4loRL.js
```

```text
HTTP/2 200
age: 7
cache-control: public, max-age=31536000, immutable
content-encoding: br
strict-transport-security: max-age=63072000; includeSubDomains
x-vercel-cache: HIT
```

El mismo archivo con y sin compresión:

```text
con Accept-Encoding: br → 66 730 bytes descargados
sin comprimir           → 209 191 bytes
```

- **`308` hacia `https://`,** con el certificado TLS emitido y renovado por Vercel.
- **`strict-transport-security` (HSTS):** el navegador no vuelve a intentar `http://` en dos años (63 072 000 s), ni la primera petición.
- **`content-encoding: br`:** viaja al 32 % de su tamaño.
- **`x-vercel-cache: HIT` y `age: 7`:** salió de la **CDN**, un servidor de Vercel cercano que lo guardó hace 7 s; ni llegó a tu app. **`HTTP/2`** lleva varias peticiones por una conexión.
- **`cache-control: … immutable`:** un año en el navegador. Esta la pone Astro, y tu servidor Node también la envía (Paso 4).
- **Fuera de las cabeceras:** el _build_ en cada `push` con las variables de cada entorno (I3.6), un _preview_ por rama y PR, funciones _serverless_ que arrancan solas con el tráfico y _rollback_ con un clic.

<Callout type="risk">

- **El 32 % depende del archivo:** JavaScript y HTML se comprimen muy bien; JPEG o WebP, casi nada.
- **HSTS es difícil de deshacer:** el navegador lo recuerda todo el `max-age`. En A4.4 empezarás con uno corto.
- **`x-vercel-cache: MISS` la primera vez es normal:** repite la petición antes de concluir.

</Callout>

## Paso 2: el adaptador de Node en modo `standalone`

**Qué es:** fuera de Vercel (`@astrojs/vercel`), el adaptador es **`@astrojs/node`**, que convierte la app en un servidor Node: un proceso escuchando en un puerto. `standalone` incluye el servidor HTTP; `middleware` exporta un manejador para tu propio Express o Fastify.

**Cómo se usa:** tu `astro.config.mjs` ya lo usa desde I3.1:

```js
// Archivo: astro.config.mjs (el de I5.2, sin cambios)
// @ts-check
import { defineConfig, envField } from "astro/config";
import react from "@astrojs/react";

import node from "@astrojs/node";

export default defineConfig({
  integrations: [react()],

  env: {
    schema: {
      // Secretas del servidor: nunca llegan al navegador ni al HTML
      MONGODB_URI: envField.string({ context: "server", access: "secret", startsWith: "mongodb" }),
      MONGODB_DB: envField.string({ context: "server", access: "secret", default: "entrenos_lab" }),
      // Better Auth: el secreto firma las cookies de sesión (mínimo 32 caracteres) y la URL base de la app
      BETTER_AUTH_SECRET: envField.string({ context: "server", access: "secret", min: 32 }),
      BETTER_AUTH_URL: envField.string({ context: "server", access: "secret", url: true }),
      // Públicas del servidor: configuración que no es secreta (se puede incrustar en el build)
      OBJETIVO_SEMANAL_MINUTOS: envField.number({ context: "server", access: "public", int: true, gt: 0, default: 150 }),
      // Públicas del cliente: las pueden leer los componentes de React. NUNCA un secreto.
      PUBLIC_NOMBRE_APP: envField.string({ context: "client", access: "public", default: "Mi entreno" }),
    },
    // Comprueba también las secretas al arrancar `astro dev` y `astro build`
    validateSecrets: true,
  },

  adapter: node({
    mode: "standalone",
  }),
});
```

No hace falta `output: "server"`: con `"static"`, Astro prerenderiza lo que puede y ejecuta en el servidor las páginas con `prerender = false` (I3.1). Compila:

```bash
npm run build
```

```text
23:38:52 [build] output: "static"
23:38:52 [build] mode: "server"
23:38:52 [build] adapter: @astrojs/node
…
23:38:52 [build] Complete!
```

```bash
du -sh dist/client dist/server
ls dist/client dist/server
```

```text
460K	dist/client
696K	dist/server
dist/client:
_astro		acerca		favicon.ico	favicon.svg	index.html

dist/server:
chunks		entry.mjs	virtual_astro_middleware.mjs
```

- **`dist/client`:** lo que el navegador descarga tal cual: páginas prerenderizadas y `_astro/` con _hash_ en el nombre, que cambia con el contenido.
- **`dist/server`:** `entry.mjs` arranca el servidor; `chunks/` tiene páginas SSR, _endpoints_, _middleware_ y Actions.
- **Las dependencias no están en `dist`:** se importan de `node_modules` (lo comprobarás en el Paso 5):

```bash
grep -rhoE "from \"[^./][^\"]*\"" dist/server | sort | uniq -c | sort -rn | head -n 8
```

```text
   7 from "react"
   6 from "react/jsx-runtime"
   5 from "zod"
   3 from "piccolore"
   3 from "mongodb"
   3 from "astro:middleware"
   2 from "zod/v4"
   2 from "unstorage/drivers/fs-lite"
```

<Callout type="risk">

- **Sin adaptador, el _build_ falla** con rutas de servidor (`NoAdapterInstalled`), y solo puede haber uno: para Vercel y VPS desde el mismo código, elígelo con una variable de entorno en `astro.config.mjs`.
- **`dist/` se regenera en cada _build_:** un arreglo a mano desaparece, y no va a Git.

</Callout>

## Paso 3: ejecutarla como en producción

**Qué es:** sin Vite, sin recarga ni errores detallados: un proceso Node con `dist/server/entry.mjs`.

**Cómo se usa:** en tu Mac:

```bash
node dist/server/entry.mjs
```

```text
23:40:27 [@astrojs/node] Server listening on http://localhost:4321
```

En otra terminal:

```bash
curl -s -o /dev/null -w "GET / -> %{http_code}\n" http://localhost:4321/
curl -s -o /dev/null -w "GET /api/resumen -> %{http_code}\n" http://localhost:4321/api/resumen
curl -s -o /dev/null -w "GET /estadisticas -> %{http_code}\n" http://localhost:4321/estadisticas
```

```text
GET / -> 200
GET /api/resumen -> 500
GET /estadisticas -> 500
```

La terminal del servidor:

```text
23:40:30 [ERROR] EnvInvalidVariables: The following environment variables defined in `env.schema` are invalid:

- MONGODB_URI is missing
```

- **El servidor compilado no lee `.env`:** `astro dev` y `astro build` sí; Node solo ve las variables del proceso. La portada funcionó porque es un archivo prerenderizado.
- **El error llega en la primera petición que necesita un secreto,** no al arrancar: un servidor puede pasar días «en marcha» y roto.

Node lo arregla con `--env-file` (desde 20.6). Para con Ctrl+C y vuelve a arrancar:

```bash
node --env-file=.env dist/server/entry.mjs
```

```text
23:40:48 [@astrojs/node] Server listening on http://localhost:4321
```

```text
GET / -> 200
GET /estadisticas -> 302 http://localhost:4321/entrar?volver=%2Festadisticas
GET /api/resumen -> 401
GET /entrar -> 200
```

- **La página privada redirige a `/entrar`** (_middleware_ de I5.3) y la API sin sesión da 401. En el Mac, **0,15 s** hasta la primera respuesta y **149 MB** de RSS.

### `HOST` y `PORT`: dónde escucha

`lsof` lista quién escucha en cada puerto:

```bash
lsof -nP -iTCP:4321 -sTCP:LISTEN
```

```text
COMMAND   PID USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
node    27363 tú     14u  IPv6 0x601dedf48e2b9866      0t0  TCP [::1]:4321 (LISTEN)
```

```bash
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4321/
```

```text
000
```

- **En el Mac, `localhost` es `::1`** (IPv6) y no responde en `127.0.0.1` ni desde la red. Escuchar solo en la propia máquina es un buen valor por defecto.

`HOST` y `PORT` lo eligen:

```bash
HOST=0.0.0.0 PORT=4322 node --env-file=.env dist/server/entry.mjs
```

```text
23:41:04 [@astrojs/node] Server listening on
  local: http://localhost:4322
  network: http://192.168.1.50:4322
```

```text
node    27386 tú     12u  IPv4 0x739a751ed71e5868      0t0  TCP *:4322 (LISTEN)
127.0.0.1 -> 200
localhost -> 200
IP-de-la-red -> 200
```

- **`0.0.0.0` es «todas las interfaces»:** `127.0.0.1`, `localhost` y la red (aquí, `192.168.1.50`). Con el puerto ocupado:

```text
Error: listen EADDRINUSE: address already in use 0.0.0.0:4322
```

- **Termina con código 1:** un servidor que no puede escuchar debe morir y avisar.

<Callout type="risk">

- **`Server listening` no significa que funcione:** comprueba una ruta con base de datos; en A4.5, `/api/health`.
- **`--env-file` sin el archivo termina** con `node: .env: not found` (código 9). Con `systemd`, Docker o un PaaS, las variables vienen de otro sitio.
- **Fija siempre `HOST` en un servidor:** `localhost` es `::1` en el Mac y `127.0.0.1` en Ubuntu, y Nginx (A4.3) fallaría si no coincide. `127.0.0.1` detrás de Nginx, `0.0.0.0` en un contenedor (A4.2); y nunca `0.0.0.0` en el portátil en una red ajena.

</Callout>

## Paso 4: lo que el servidor de Node no hace

**Qué es:** las mismas peticiones del Paso 1, ahora a tu servidor.

**Cómo se usa:** con `HOST=127.0.0.1` para usar siempre la misma dirección:

```bash
HOST=127.0.0.1 node --env-file=.env dist/server/entry.mjs
```

```bash
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip, br" http://127.0.0.1:4321/_astro/react.CmU_e8vp.js
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip, br" http://127.0.0.1:4321/
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip, br" http://127.0.0.1:4321/entrar
```

```text
== /_astro/react.CmU_e8vp.js
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
ETag: W/"1ec4-1a18b517098"
Content-Type: text/javascript; charset=utf-8
Content-Length: 7876
== /
HTTP/1.1 200 OK
Cache-Control: public, max-age=0
ETag: W/"2129-1a18b517166"
Content-Type: text/html; charset=utf-8
Content-Length: 8489
== /entrar
HTTP/1.1 200 OK
content-type: text/html
Transfer-Encoding: chunked
```

- **Sin compresión:** el JavaScript llega con sus 7876 bytes. Todo el del cliente suma **398 661 bytes**, que con gzip serían **128 569** (un 32 %): el triple de lo necesario.
- **La caché del navegador, igual que Vercel:** `immutable` en `_astro/`, y `max-age=0` con `ETag` en las prerenderizadas (un 304 vacío si no cambiaron). Lo decide Astro.
- **Las SSR, sin `Cache-Control`,** en trozos (`chunked`). **Y sin HTTPS, HTTP/2 ni CDN:** `HTTP/1.1` en claro, un proceso, una máquina.
- **Fuera de las cabeceras:** nadie lo reinicia si muere (I6.4, `systemd`), usa un solo núcleo y nadie compila al hacer `git push`.

<Callout type="risk">

- **No comprimas dentro de Node:** gasta CPU en el hilo que atiende peticiones. Lo hace Nginx o Caddy (A4.3).
- **`immutable` solo con _hash_ en el nombre:** servir `public/` así dejaría un `logo.svg` cambiado un año en caché.

</Callout>

## Paso 5: llevarla a un servidor Linux

**Qué es:** copiar la app compilada al Ubuntu de I6, instalar Node y sus dependencias, y arrancarla.

**Cómo se usa:** en el Mac, empaqueta `dist`, `package.json`, `package-lock.json` y `.env`:

```bash
tar -czf paquete.tgz dist package.json package-lock.json .env
```

Al descomprimir en Ubuntu salen avisos y archivos de más:

```text
tar: Ignoring unknown extended header keyword 'LIBARCHIVE.xattr.com.apple.provenance'
…
._.env  ._dist  ._package-lock.json  ._package.json  .env  dist  package-lock.json  package.json
```

- **El `tar` de macOS guarda atributos extendidos** y crea archivos `._*` que Linux no entiende. Sin ellos:

```bash
COPYFILE_DISABLE=1 tar --no-xattrs -czf paquete.tgz dist package.json package-lock.json .env
scp paquete.tgz deploy@tu-servidor:/tmp/
```

En el servidor, como `deploy`, en `/opt/entrenos` (I6.4):

```bash
cd /opt/entrenos
tar xzf /tmp/paquete.tgz && rm /tmp/paquete.tgz
node --env-file=.env dist/server/entry.mjs
```

Faltan las dependencias (Paso 2), solo las de producción:

</Callout>

## Paso 6: VPS, PaaS, Coolify o Vercel

**Qué es:** quién monta todo lo anterior, de más a menos trabajo para ti:

- **VPS** (Hetzner, DigitalOcean): Ubuntu y una IP; tú instalas Node, Nginx, el certificado, `systemd`, las actualizaciones y las copias. Es este curso.
- **VPS con Coolify:** un panel de código abierto en tu VPS que construye la imagen de Docker, pone el proxy con HTTPS y despliega en cada `push`.
- **PaaS** (Railway, Render, Fly.io): les das el repositorio o una imagen y se ocupan de máquina, HTTPS y reinicios. Tu app sigue siendo un servidor Node de larga duración.
- **Vercel:** todo lo del Paso 1, sin servidor.

**Cómo se usa:** con precios oficiales consultados el 29 de octubre de 2026, sin impuestos (cambian a menudo):

| Opción               | Lo más pequeño                                                                    | Precio al mes                     |
| -------------------- | --------------------------------------------------------------------------------- | --------------------------------- |
| Vercel Hobby         | Uso personal, **no comercial**; 100 GB de transferencia                           | 0 $                               |
| Vercel Pro           | Por miembro del equipo; 1 TB de transferencia y 20 $ de crédito incluidos         | 20 $                              |
| Hetzner CX23         | 2 vCPU, 4 GB, 40 GB NVMe, 20 TB de tráfico, IPv4 incluida                         | 5,99 € (ese día, «no disponible») |
| Hetzner CPX12        | 1 vCPU, 2 GB, 40 GB NVMe                                                          | 11,99 €                           |
| DigitalOcean Basic   | 1 vCPU, 512 MiB, 10 GiB; o 1 vCPU, 1 GiB, 25 GiB                                  | 4 $ · 6 $                         |
| Railway Hobby        | 5 $ de uso incluidos; después, unos 10 $ por GB de RAM y 20 $ por vCPU al mes     | desde 5 $                         |
| Render Free          | 0,1 CPU, 512 MB; **se apaga tras 15 min** sin tráfico y tarda ~1 min en volver    | 0 $                               |
| Fly.io shared-cpu-1x | 256 MB · 512 MB · 1 GB, sin capa gratuita                                         | 2,19 $ · 3,69 $ · 6,70 $          |
| Coolify              | Autoalojado: gratis y de código abierto. En su nube: el panel, con tus servidores | 0 · 5 $ (2 servidores)            |

- **La memoria decide:** tu app ocupó 101–173 MB y MongoDB en la misma máquina necesita bastante más. 512 MB no dan; con 2–4 GB vas holgado.
- **Los límites de Vercel** (funciones con _Fluid compute_): **300 s** por petición en Hobby (800 en Pro), **4,5 MB** de cuerpo (si no, `413`), 2 GB de memoria (4 en Pro), _cold starts_ tras un rato sin tráfico y nada en marcha entre peticiones (un _cron_ de la plataforma, no `setInterval`).
- **En tu VPS no existen:** el proceso siempre está en marcha y una petición dura lo que quieras. A cambio, si la máquina cae, cae la app.
- **Vercel** si la app cabe en sus límites (como esta plataforma) y no quieres administrar; Pro si es comercial. **PaaS** para un servidor siempre en marcha (WebSockets, colas) sin Linux. **VPS** para control total, coste bajo y predecible con tráfico alto, o aprender, sin contar tu tiempo. **Coolify** para precio de VPS con experiencia de PaaS, manteniendo también Coolify.

<Callout type="risk">

- **Vercel Hobby no permite uso comercial:** es una condición de uso y nada avisa al desplegar.
- **La transferencia se paga aparte:** Vercel desde 0,15 $/GB por encima de lo incluido, Railway 0,05 $; Hetzner incluye 20 TB. Elige también pensando en el plan siguiente: el más barato de Hetzner salía «no disponible».
- **Gratis suele significar «se duerme»:** el Render gratuito tarda un minuto en despertar. Vale para una demo, no con usuarios.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Compila tu app de entrenamiento con el adaptador de Node y ejecútala en local como en producción: con las variables de `.env`, `NODE_ENV=production` y `HOST` y `PORT` explícitos.
2. Escribe un _script_ `scripts/produccion.sh` que lo haga todo de una vez: compilar, arrancar, esperar a que responda, comprobar que cada tipo de ruta responde con su código (prerenderizada, SSR, privada, API sin sesión, inexistente), enseñar las cabeceras de un recurso de `_astro/` y la memoria del proceso, y parar el servidor al terminar, también si algo falla.
3. Añade a `package.json` un _script_ `start` para arrancar la app compilada.

</Callout>

Solución. `scripts/produccion.sh`:

```bash
#!/usr/bin/env bash
# Archivo: scripts/produccion.sh
# Compila la app y la ejecuta como en producción; comprueba rutas y cabeceras, y la para al terminar.
# Uso: bash scripts/produccion.sh   (desde la raíz del proyecto, con .env relleno)
set -euo pipefail

PUERTO="${PORT:-4330}"
BASE="http://127.0.0.1:$PUERTO"

[ -f .env ] || { echo "Falta .env (cp .env.example .env)"; exit 1; }
if lsof -nP -iTCP:"$PUERTO" -sTCP:LISTEN >/dev/null 2>&1; then
  echo "El puerto $PUERTO está ocupado: elige otro con PORT=4331 bash scripts/produccion.sh"; exit 1
fi

echo "== 1. Build"
npm run build > /tmp/entrenos-build.log 2>&1 || { tail -n 20 /tmp/entrenos-build.log; exit 1; }
du -sh dist/client dist/server

echo "== 2. Arranque, como en producción"
NODE_ENV=production HOST=127.0.0.1 PORT="$PUERTO" node --env-file=.env dist/server/entry.mjs > /tmp/entrenos-server.log 2>&1 &
PID=$!
trap 'kill "$PID" 2>/dev/null || true' EXIT # pase lo que pase, el servidor se para al salir

for _ in $(seq 1 50); do
  curl -s -o /dev/null "$BASE/" && break
  kill -0 "$PID" 2>/dev/null || { echo "El servidor ha terminado:"; cat /tmp/entrenos-server.log; exit 1; }
  sleep 0.1
done

echo "== 3. Rutas"
comprobar() { # ruta, código esperado
  local codigo
  codigo=$(curl -s -o /dev/null -w "%{http_code}" "$BASE$1")
  if [ "$codigo" = "$2" ]; then echo "  ok   $1 -> $codigo"; else echo "  FALLO $1 -> $codigo (esperaba $2)"; FALLOS=1; fi
}
FALLOS=0
comprobar /             200 # prerenderizada: un archivo de dist/client
comprobar /entrar       200 # SSR: la renderiza Node en cada petición
comprobar /estadisticas 302 # privada: el middleware redirige a /entrar
comprobar /api/resumen  401 # API privada sin sesión
comprobar /no-existe    404

echo "== 4. Cabeceras (lo que Vercel añade y aquí no hay)"
JS=$(ls dist/client/_astro/*.js | head -n 1)
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip, br" "$BASE/_astro/$(basename "$JS")" |
  grep -iE "^(cache-control|content-encoding|content-length)" | sed 's/^/  /'
grep -iE "error" /tmp/entrenos-server.log && FALLOS=1

echo "== 5. Memoria del proceso"
ps -o rss= -p "$PID" | awk '{printf "  %.0f MB\n", $1/1024}'

exit "$FALLOS"
```

## Resumen

- Vercel da `308` a HTTPS, HSTS de dos años, Brotli (209 191 → 66 730 bytes), CDN, HTTP/2, _build_ por `push`, _previews_, reinicios y _rollback_.
- `@astrojs/node` `standalone`: `dist/client` y `dist/server/entry.mjs`, con dependencias de `node_modules`.
- El servidor compilado **no lee `.env`**: falla en la primera ruta con secretos. `node --env-file=.env`.
- `localhost` fue `::1` en el Mac y `127.0.0.1` en Ubuntu: fija `HOST` y `PORT`.
- Node no comprime, no da HTTPS y nadie lo reinicia.
- En Ubuntu: Node de NodeSource, `npm ci --omit=dev` y `tar` sin metadatos del Mac; 101–173 MB.
- VPS, PaaS, Coolify o Vercel: control y coste frente a trabajo. Hobby no admite uso comercial.
