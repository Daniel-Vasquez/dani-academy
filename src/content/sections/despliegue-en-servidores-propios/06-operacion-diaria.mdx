Vercel daba registros, avisos y parches sin pedirlos. En tu servidor, si nadie mira, el disco se llena, una copia deja de hacerse y la web cae un sábado de noche. El objetivo aquí es **enterarte de una caída antes que tus usuarios**: registros que sobreviven, copias restauradas, parches, vigilancia interna y externa y un _runbook_ probado.

**Requisitos:** el montaje _blue-green_ de A4.5, en un servidor con dominio y HTTPS.

<Callout type="note" title="Qué se ha ejecutado y qué no">

Registros, copias, actualizaciones, el vigilante y todas las averías se midieron en el servidor de pruebas. No se ejecutaron:

- **Telegram:** los avisos se probaron contra un servidor local que imita su API, sin mensajes reales.
- **Uptime Kuma:** se comprobó que arranca y cuánto ocupa, pero no se configuró (exige crear una cuenta). Sus pasos salen de su documentación y de la de Telegram.

</Callout>

## Paso 1: registros que sobreviven

**Qué es:** cada petición escribe una línea (_middleware_ de I3.4) que Docker guarda en un JSON: **98 bytes por petición**, medido con 20 000.

**Cómo se usa:**

```bash
docker compose logs --tail 100 blue
docker compose logs --since 10m blue
```

En `blue`, antes y después de desplegar otra versión en ella:

```text
blue con registros:                     20000 líneas GET /entrar
blue tras recrearse con otra versión:   0
```

- **Cada despliegue borra los registros de esa instancia:** el archivo se va con el contenedor, justo cuando quieres comparar. Y vivo, crece sin límite (A4.2).

Docker puede enviarlos al **diario de `systemd`** (`journald`, I6.4). En el bloque `x-app` de `compose.yaml`:

```yaml
  restart: unless-stopped
  logging:
    driver: journald # en el diario del servidor: sobreviven a cada despliegue (A4.6)
    options:
      tag: entrenos
```

Tras recrear la instancia (en tu siguiente despliegue):

```text
tras recrear green, diario:   20000
```

- **Las dos instancias, en un sitio:** `docker compose logs` sigue funcionando y `journalctl` añade búsquedas:

```bash
sudo journalctl -t entrenos -n 50                          # las últimas 50 líneas
sudo journalctl -t entrenos -f                             # en directo
sudo journalctl -t entrenos --since "1 hour ago" | grep "→ 5"   # errores 5xx de la última hora
```

- **Cuesta 1258 bytes por petición** frente a 98, por los metadatos. Límite en `/etc/systemd/journald.conf.d/limite.conf`:

```ini
[Journal]
SystemMaxUse=500M
MaxRetentionSec=30day
```

```bash
sudo systemctl restart systemd-journald
sudo journalctl --disk-usage
```

```text
Archived and active journals take up 178.4M in the file system.
```

- **Caben unos 400 000 registros de petición:** con mucho tráfico, días, no un mes. Los de Nginx ya los rota `/etc/logrotate.d/nginx` (diario, comprimidos, 14).

<Callout type="risk">

- **En el servidor mueren con él** y un intruso puede borrarlos: con usuarios reales, valora enviarlos fuera (Better Stack Logs, Grafana Loki).
- **Sin datos personales:** nada de contraseñas, _tokens_ ni cuerpos; método, ruta y código. Cuidado con los parámetros de la URL.
- **Con el diario, `journalctl -t entrenos`** ve todo; `docker compose logs` solo lo que existe. Los 1258 bytes son aproximados (bloques): importa que el límite se cumple.

</Callout>

## Paso 2: copias que has restaurado

**Qué es:** el MongoDB de Compose no tiene copias automáticas (Atlas sí, I4.5). **Una copia que nunca has restaurado es una esperanza.** `scripts/copia-mongo.sh` guarda, restaura en una base aparte y compara.

**Cómo se usa:**

```bash
#!/usr/bin/env bash
# Archivo: scripts/copia-mongo.sh
# Copia de MongoDB comprobada: la restaura en una base aparte y compara los documentos.
# Uso, en el servidor, desde la carpeta del proyecto: bash scripts/copia-mongo.sh
set -euo pipefail

BASE=entrenos
DESTINO=/var/backups/entrenos
CONSERVAR_DIAS=14
ARCHIVO="$DESTINO/$BASE-$(date +%Y%m%d-%H%M).archive.gz"

mongo() { docker compose exec -T mongo "$@"; }
contar() { # documentos por colección de una base, en orden
  mongo mongosh --quiet "$1" --eval \
    'db.getCollectionNames().sort().forEach((c) => print(c, db[c].countDocuments()))'
}

# Primero a .parcial: un corte a medias no debe parecer una copia buena
mongo mongodump --quiet --archive --gzip --db "$BASE" > "$ARCHIVO.parcial"
mv "$ARCHIVO.parcial" "$ARCHIVO"

# Una copia que no se ha restaurado no es una copia
mongo mongorestore --quiet --archive --gzip --drop \
  --nsFrom "$BASE.*" --nsTo "verificacion.*" < "$ARCHIVO"
ORIGINAL="$(contar "$BASE")"
RESTAURADA="$(contar verificacion)"
mongo mongosh --quiet verificacion --eval 'db.dropDatabase()' >/dev/null

if [ "$ORIGINAL" != "$RESTAURADA" ]; then
  echo "✗ La copia no coincide con la base de datos" >&2
  diff <(echo "$ORIGINAL") <(echo "$RESTAURADA") >&2 || true
  rm -f "$ARCHIVO"
  exit 1
fi

find "$DESTINO" -name '*.archive.gz' -mtime +"$CONSERVAR_DIAS" -delete
echo "✓ $ARCHIVO ($(du -h "$ARCHIVO" | cut -f1)), $(echo "$ORIGINAL" | wc -l | tr -d ' ') colecciones comprobadas"
```

```bash
sudo install -d -o deploy -g deploy -m 700 /var/backups/entrenos
bash scripts/copia-mongo.sh
```

```text
✓ /var/backups/entrenos/entrenos-20261105-2131.archive.gz (8.0K), 5 colecciones comprobadas
```

- **`--archive --gzip`** saca un flujo comprimido del contenedor a un archivo; **`.parcial`** evita que un corte parezca una copia buena.
- **`--nsFrom` y `--nsTo`** restauran `entrenos.*` como `verificacion.*`, y **`-mtime +14`** borra solo tras comprobar la nueva.

Simulacro: una copia, la base borrada entera y restaurada:

```bash
docker compose exec -T mongo mongosh --quiet entrenos --eval "db.dropDatabase().ok"
curl -s -b sesion.txt https://academy.tudominio.com/api/entrenos
curl -s https://academy.tudominio.com/api/health
```

```text
1
{"entrenos":[]}
{"ok":true,"version":"v2"}
```

- **Con todos los datos borrados, `/api/health` dice que todo va bien** y la app responde 200 con una lista vacía. Ningún monitor te avisará.

```bash
docker compose exec -T mongo mongorestore --archive --gzip --drop < /var/backups/entrenos/entrenos-20261105-2131.archive.gz
```

```text
48 document(s) restored successfully. 0 document(s) failed to restore.
```

- **El entreno volvió,** con la misma sesión.

Cada noche, con un temporizador de `systemd` (I6.4):

```ini
# Archivo: /etc/systemd/system/entrenos-copia.service
[Unit]
Description=Copia comprobada de MongoDB
After=docker.service

[Service]
Type=oneshot
User=deploy
WorkingDirectory=/opt/entrenos
ExecStart=/usr/bin/bash scripts/copia-mongo.sh
```

```ini
# Archivo: /etc/systemd/system/entrenos-copia.timer
[Unit]
Description=Copia de MongoDB cada noche

[Timer]
OnCalendar=*-*-* 03:30:00
RandomizedDelaySec=15m
# Si el servidor estaba apagado a esa hora, se hace al arrancar
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now entrenos-copia.timer
sudo systemctl start entrenos-copia.service   # pruébalo ya: no esperes a las 3:30
systemctl list-timers "entrenos-*"
```

- **`deploy` en el grupo `docker`** y dueño de `/var/backups/entrenos`; **`Persistent=true`** hace la copia al arrancar si estaba apagado.

<Callout type="risk">

- **Una copia en el mismo servidor no te salva del servidor:** cada día, fuera (`scp` a otro servidor, o Backblaze B2 o S3 con `rclone`). Lo único que no puede faltar.
- **Llevan _hashes_, sesiones y datos personales:** `chmod 700`, y cifradas fuera.
- **`systemd` ignora comentarios al final de línea** (`Persistent=true # …`): `systemd-analyze verify` lo detectó. Y `mongorestore --drop` borra lo que haya: guarda antes el estado actual.

</Callout>

## Paso 3: actualizaciones de seguridad

**Qué es:** **`unattended-upgrades`**, activo en Ubuntu, instala cada día los parches de seguridad.

**Cómo se usa:**

```bash
cat /etc/apt/apt.conf.d/20auto-upgrades
sudo unattended-upgrade --dry-run -d 2>&1 | grep -E "Allowed origins"
```

```text
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
Allowed origins are: o=Ubuntu,a=resolute, o=Ubuntu,a=resolute-security, o=UbuntuESM…
```

- **Lo importante es lo que no cubre:** con actualizaciones pendientes de Docker y del núcleo, el ensayo incluía `linux-image-virtual` y nada de Docker:

```text
docker-ce/resolute 5:29.9.3-1~ubuntu.26.04~resolute arm64 [upgradable from: 5:29.9.2-1…
linux-image-virtual/resolute-updates 7.0.0-43.43 arm64 [upgradable from: 7.0.0-38.38]
```

| Componente                            | Quién lo actualiza                                 |
| ------------------------------------- | -------------------------------------------------- |
| Ubuntu, núcleo, Nginx, OpenSSL        | `unattended-upgrades`, solo                        |
| Docker y Node (repositorios externos) | Tú: `sudo apt update && sudo apt upgrade` cada mes |
| `node:26-alpine` dentro de tu imagen  | Tú: reconstruir sin caché (`docker build --pull`)  |
| `mongo:8.2`                           | Tú: leer las notas de versión y probar (A4.2)      |
| Dependencias de npm                   | Tú: `npm audit`, y desplegar                       |

- **El núcleo pide reinicio y Ubuntu no lo hace** (`Automatic-Reboot` viene comentado): aparece `/var/run/reboot-required` y el vigilante (Paso 4) lo dice. Desde `sudo reboot`, `/api/health` volvió a 200 en **7,4 s**:

```text
t=5.1 s -> 000
t=6.1 s -> 502
t=7.4 s -> 200
```

```text
blue entrenos:v1 Exited (143) 4 minutes ago
green entrenos:v2 Up 4 seconds (healthy)
mongo mongo:8.2 Up 4 seconds (health: starting)
```

- **`restart: unless-stopped` levanta lo que estaba en marcha y respeta lo parado,** así que `volver.sh` conserva su instancia, y el diario guardó el arranque anterior. Un VPS real tardará más.

<Callout type="risk">

- **Un parche puede romper algo,** raramente: `/var/log/unattended-upgrades/` dice qué se instaló. No parchear un servidor expuesto es peor.
- **No actives `Automatic-Reboot` sin pensarlo:** un núcleo nuevo puede cambiar cosas (MongoDB en A4.2). Reinicia tú, mirando.
- **Tu imagen no se parchea sola:** despliega al menos una vez al mes aunque no cambies nada.

</Callout>

## Paso 4: vigilar desde dentro

**Qué es:** `scripts/vigilar.sh` comprueba cada 5 minutos lo que no se ve desde fuera (disco, copia, certificado, reinicio pendiente) y avisa por Telegram **solo cuando algo cambia**.

**Cómo se usa:**

```bash
#!/usr/bin/env bash
# Archivo: scripts/vigilar.sh
# Lo que un monitor externo no ve desde fuera. Avisa por Telegram solo cuando algo cambia.
# Lo ejecuta un temporizador de systemd cada 5 minutos, con las variables de /etc/entrenos/avisos.env
set -uo pipefail

: "${DOMINIO:?}" "${TELEGRAM_TOKEN:?}" "${TELEGRAM_CHAT:?}"
TELEGRAM_API="${TELEGRAM_API:-https://api.telegram.org}"
COPIAS="${COPIAS:-/var/backups/entrenos}"
ESTADO=/var/tmp/entrenos-vigilar.estado
DISCO_MAX=85
COPIA_MAX_HORAS=26
CERT_MIN_DIAS=14

problemas=()

salud="$(curl -s -m 8 -o /dev/null -w '%{http_code}' "https://$DOMINIO/api/health")"
[ "$salud" = 200 ] || problemas+=("La app no está sana: /api/health responde $salud")

disco="$(df --output=pcent / | tail -n 1 | tr -dc 0-9)"
[ "$disco" -lt "$DISCO_MAX" ] || problemas+=("Disco al $disco %")

reciente="$(find "$COPIAS" -name '*.archive.gz' -mmin -$((COPIA_MAX_HORAS * 60)) | head -n 1)"
[ -n "$reciente" ] || problemas+=("Ninguna copia de MongoDB en las últimas $COPIA_MAX_HORAS horas")

if ! echo | openssl s_client -connect "$DOMINIO:443" -servername "$DOMINIO" 2>/dev/null |
  openssl x509 -noout -checkend $((CERT_MIN_DIAS * 86400)) >/dev/null; then
  problemas+=("El certificado caduca en menos de $CERT_MIN_DIAS días")
fi

[ -f /var/run/reboot-required ] && problemas+=("El servidor necesita reiniciarse (actualizaciones)")

avisar() {
  curl -s -m 10 -o /dev/null --fail "$TELEGRAM_API/bot$TELEGRAM_TOKEN/sendMessage" \
    --data-urlencode "chat_id=$TELEGRAM_CHAT" --data-urlencode "text=$1"
}

actual="$(printf '%s\n' "${problemas[@]:-}")"
anterior="$(cat "$ESTADO" 2>/dev/null || true)"
[ "$actual" = "$anterior" ] && exit 0 # sin cambios: no repitas el aviso cada 5 minutos

if [ -n "$actual" ]; then
  avisar "⚠️ $DOMINIO
$actual" || exit 1
else
  avisar "✅ $DOMINIO: todo resuelto" || exit 1
fi
echo "$actual" > "$ESTADO" # solo si el aviso ha salido: si falla, se reintenta en la próxima pasada
```

Las variables, en `/etc/entrenos/avisos.env` con `chmod 600` (el _token_ es una contraseña):

```bash
DOMINIO=academy.tudominio.com
TELEGRAM_TOKEN=123456:ABC-tu-token
TELEGRAM_CHAT=tu-chat-id
```

Su temporizador, como el de las copias:

```ini
# Archivo: /etc/systemd/system/entrenos-vigilar.service
[Unit]
Description=Comprobaciones internas del servidor

[Service]
Type=oneshot
User=deploy
EnvironmentFile=/etc/entrenos/avisos.env
ExecStart=/usr/bin/bash /opt/entrenos/scripts/vigilar.sh
```

```ini
# Archivo: /etc/systemd/system/entrenos-vigilar.timer
[Unit]
Description=Comprobaciones internas cada 5 minutos

[Timer]
OnBootSec=2m
OnUnitActiveSec=5m

[Install]
WantedBy=timers.target
```

Escenario por escenario, contando los mensajes:

```text
[todo bien]                     mensajes: 0
[mongo parado]                  mensajes: 1
[mongo parado, segunda pasada]  mensajes: 1
[mongo de vuelta]               mensajes: 2
[sin copia]                     mensajes: 3
[reinicio pendiente]            mensajes: 4
[resuelto]                      mensajes: 5
```

```text
⚠️ academy.entrenos.test / La app no está sana: /api/health responde 503
✅ academy.entrenos.test: todo resuelto
⚠️ academy.entrenos.test / Ninguna copia de MongoDB en las últimas 26 horas
⚠️ academy.entrenos.test / El servidor necesita reiniciarse (actualizaciones)
✅ academy.entrenos.test: todo resuelto
```

Con un archivo de 6 GB que llena el disco:

```text
⚠️ academy.entrenos.test / Disco al 88 %
```

- **No repite el aviso** en la segunda pasada con MongoDB parado: un aviso cada 5 minutos acaba silenciado.
- **`|| exit 1` antes de guardar el estado:** con Telegram inaccesible, termina con error sin anotar nada y reintenta en la siguiente pasada (medido).

<Callout type="risk">

- **Muere con el servidor:** si la máquina se apaga no avisa. Por eso también el Paso 5.
- **Lo que más llena el disco son las imágenes:** 9,3 GB, 7 recuperables (`docker system df`). `docker image prune -a --filter "until=720h"`, dejando las recientes para volver.
- **Pruébalo con el mismo usuario:** con `sudo`, el estado en `/var/tmp` queda de `root` y `deploy` no lo actualiza.

</Callout>

## Paso 5: vigilar desde fuera

**Qué es:** un monitor que pregunta a tu web cada minuto desde otra máquina.

- **Uptime Kuma,** autoalojado y libre: `louislam/uptime-kuma:2` (2.5.9) ocupa **2,56 GB** y unos 126 MB de memoria, arranca en 2 s en `/setup-database` y admite Telegram y comprobar JSON o palabras clave.
- **Better Stack,** un servicio: gratis para proyectos personales con 10 monitores y avisos por correo y Slack (Telegram no aparece).

**Cómo se usa:** qué URL vigilar, provocando cada avería:

| Avería         | `/`          | `/entrar`    | `/api/health` |
| -------------- | ------------ | ------------ | ------------- |
| Todo bien      | 200          | 200          | 200           |
| App parada     | 502          | 502          | 502           |
| MongoDB parado | **200**      | **200**      | **503**       |
| Nginx parado   | sin conexión | sin conexión | sin conexión  |

- **Con MongoDB caído, la portada y `/entrar` siguen en 200:** vigila `/api/health` y que el cuerpo contenga `"ok":true`.

<Callout type="risk">

- **En otra máquina:** un Kuma en el mismo servidor cae con él. Un monitor gratuito externo es mejor que uno propio al lado.
- **Prueba el aviso, no solo el monitor:** para la app una vez. Y 1 o 2 reintentos contra cortes de red (Kuma 2 trae 0).
- **No ve errores de lógica:** ni los datos borrados del Paso 2 ni una página concreta que falla.

</Callout>

## Paso 6: el _runbook_

**Qué es:** lo que escribes hoy, con la cabeza despejada, para ti mismo a las tres de la mañana. Cada orden de este se ejecutó provocando su avería.

**Cómo se usa:** en el repositorio, como `docs/runbook.md`:

````markdown
# Runbook · Dani Academy autoalojada

Servidor: `ssh deploy@academy.tudominio.com` · Proyecto: `/opt/entrenos`

## La web no responde

1. Desde tu equipo, sin entrar al servidor:

   ```bash
   curl -s -m 8 -w " -> %{http_code}\n" https://academy.tudominio.com/api/health
   ```

2. Busca el síntoma en la tabla y ve a su sección.

| `/api/health`            | Portada | Qué pasa              | Sección     |
| ------------------------ | ------- | --------------------- | ----------- |
| `{"ok":true,…}` 200      | 200     | La app está bien      | Otro fallo  |
| `{"ok":false,…}` 503     | 200     | MongoDB               | MongoDB     |
| 502                      | 502     | La app no responde    | La app      |
| Sin conexión (`000`)     | Igual   | Nginx o el servidor   | Nginx       |

## La app (502)

```bash
cd /opt/entrenos
cat /etc/nginx/entrenos-activo.conf          # 4321 = blue, 4322 = green
docker compose ps
sudo tail -n 5 /var/log/nginx/error.log      # connect() failed: Node no escucha
docker compose logs --tail 100 green         # o blue: la instancia activa
docker compose start green                   # si está parada
```

Si empezó tras un despliegue, vuelve atrás: `bash scripts/volver.sh`

## MongoDB (503)

```bash
docker compose ps mongo
docker compose exec -T mongo mongosh --quiet --eval 'db.adminCommand({ ping: 1 }).ok'
docker compose logs --tail 50 mongo
docker compose start mongo
```

La portada y `/entrar` siguen dando 200: no te fíes de ellas.

## Nginx o el servidor (sin conexión)

```bash
ssh deploy@academy.tudominio.com             # ¿No entra? Panel del proveedor: ¿servidor encendido?
systemctl is-active nginx docker
sudo nginx -t
sudo systemctl start nginx
sudo tail -n 20 /var/log/nginx/error.log
```

## Disco lleno

```bash
df -h /
docker system df
docker image ls entrenos                     # conserva las últimas versiones
docker image prune -a --filter "until=720h"  # imágenes sin usar de hace más de 30 días
sudo journalctl --disk-usage
```

## Datos borrados o dañados

`/api/health` seguirá en 200: la app funciona, pero sin tus datos. Avisa antes de tocar nada.

```bash
ls -lt /var/backups/entrenos | head
docker compose exec -T mongo mongorestore --archive --gzip --drop < /var/backups/entrenos/ARCHIVO
```

## Después de cada incidente

Apunta aquí qué pasó, cómo lo notaste y qué vas a cambiar. Si este documento no te sirvió, corrígelo.
````

- **Lo más útil es la tabla inicial:** el código de `/api/health` dice dónde mirar antes de entrar. Y los mensajes de los simulacros:

```text
App parada, /var/log/nginx/error.log:
  connect() failed (111: Connection refused) while connecting to upstream

MongoDB parado, docker compose logs:
  GET /api/health → 503 (2009.0 ms)
  docker compose exec … mongosh → service "mongo" is not running

Nginx parado:
  systemctl is-active nginx → inactive
```

<Callout type="risk">

- **Un _runbook_ sin probar miente:** vive en el repositorio y cada incidente lo corrige. Donde dice `app`, ahora son `blue` y `green`: mira cuál está activa.
- **Una copia fuera del servidor:** si no puedes entrar, el archivo de dentro no sirve.
- **Primero recupera, luego investiga:** `volver.sh` antes que entender el fallo; los registros siguen en el diario.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Monta Uptime Kuma en Docker, en una máquina que no sea tu servidor, para que vigile `/api/health` y te avise por Telegram.
2. Para la app a propósito y comprueba cuánto tardas en enterarte. Después, vuelve a arrancarla y comprueba que llega el aviso de recuperación.
3. Haz un simulacro completo con tu _runbook_: pide a alguien que pare un servicio sin decirte cuál, o hazlo tú con un `sleep` aleatorio, y arréglalo siguiendo solo lo que está escrito. Corrige lo que te falte.

</Callout>

**Kuma,** en otra máquina:

```bash
docker run -d --restart=always -p 127.0.0.1:3001:3001 -v uptime-kuma:/app/data --name uptime-kuma louislam/uptime-kuma:2
```

- **El volumen `uptime-kuma` conserva sus datos,** y `127.0.0.1` no abre el puerto (A4.2). Para entrar, un túnel SSH (I6.3):

```bash
ssh -L 3001:127.0.0.1:3001 usuario@maquina-del-monitor
```

1. _Settings_ → _Notifications_ → una de tipo **Telegram**, con tu _token_ y tu chat, y envía la prueba.
2. _Add New Monitor_ → **HTTP(s) - Keyword**, URL `https://academy.tudominio.com/api/health`, palabra clave `"ok":true`, 60 s y 1 o 2 reintentos, con la notificación marcada.

Los simulacros del punto 2, en tu servidor:

```bash
docker compose stop green     # o blue: la instancia activa
docker compose start green
```

- **Con 60 s y un reintento, el aviso llega en un par de minutos.** Mide el tuyo: es lo que tu web puede estar caída sin que lo sepas.

<Callout type="risk">

- **No publiques Kuma tal cual:** guarda tus avisos y _tokens_. Túnel SSH o Nginx con HTTPS (A4.3, A4.4).
