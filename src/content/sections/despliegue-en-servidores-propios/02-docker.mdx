En A4.1 llevaste la app a Ubuntu a mano, y en otro servidor tendrías que repetir cada paso. **Docker** empaqueta la app con todo lo que necesita (sistema base, Node 26, `node_modules`, `dist`) en una **imagen** que se ejecuta igual en cualquier máquina con Docker. Aquí construyes una imagen de 562 MB sin secretos ni `root`, y la levantas con MongoDB usando Compose.

**Requisitos:** `entrenos-app` de A4.1 y el Ubuntu de I6. Las salidas se midieron en ese servidor (Ubuntu 26.04, arm64) con Docker Engine; en el Mac, las mismas órdenes con Docker Desktop, OrbStack o Colima.

## Paso 1: Docker en el servidor, imágenes y contenedores

**Qué es:** una **imagen** es un conjunto de **capas** de solo lectura; un **contenedor** es una imagen en marcha, con una capa propia en la que escribe y que desaparece al borrarlo.

**Cómo se usa:** instala Docker Engine desde su repositorio oficial, con la clave y el repositorio a mano (deb822), como NodeSource en A4.1:

```bash
# La clave con la que Docker firma sus paquetes
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# El repositorio, para tu versión de Ubuntu y tu arquitectura
. /etc/os-release
printf "Types: deb\nURIs: https://download.docker.com/linux/ubuntu\nSuites: %s\nComponents: stable\nArchitectures: %s\nSigned-By: /etc/apt/keyrings/docker.asc\n" \
  "$VERSION_CODENAME" "$(dpkg --print-architecture)" | sudo tee /etc/apt/sources.list.d/docker.sources

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker version --format "Engine {{.Server.Version}}, cliente {{.Client.Version}}"
docker compose version
```

```text
Engine 29.9.2, cliente 29.9.2
Docker Compose version v5.6.1
```

- **Cinco paquetes:** el motor (`docker-ce`), el cliente (`docker-ce-cli`), `containerd.io` debajo, **Buildx** para construir y **Compose** para varios contenedores (Paso 6).

Para no escribir `sudo`, `deploy` al grupo `docker`, y vuelve a entrar (los grupos se leen al iniciar sesión):

```bash
sudo usermod -aG docker deploy
exit # y vuelve a entrar: ssh deploy@tu-servidor
```

**`docker pull`** descarga de Docker Hub. Las variantes de Node:

```bash
docker pull node:26-alpine
docker pull node:26-slim
docker pull node:26
docker image ls --format "{{.Repository}}:{{.Tag}} {{.Size}}"
```

```text
node:26-alpine 258MB
node:26 1.8GB
node:26-slim 377MB
```

- **`node:26`** es Debian completo (1,8 GB); **`node:26-slim`**, sin compiladores (377 MB); **`node:26-alpine`**, Alpine Linux mínimo (258 MB), el de esta sección.

**`docker run`** crea un contenedor y ejecuta una orden; `--rm` lo borra al terminar:

```bash
docker run --rm node:26-alpine node -v
docker run --rm node:26-alpine sh -c "head -n 2 /etc/os-release; whoami; pwd"
```

```text
v26.13.0
NAME="Alpine Linux"
ID=alpine
root
/
```

- **Node 26.13.0 sobre Alpine,** no el sistema del servidor, y como `root` por defecto (Paso 4).

`docker history` enseña las capas, de la más reciente a la más antigua:

```bash
docker history node:26-alpine --format "{{.Size}}\t{{.CreatedBy}}"
```

```text
0B	CMD ["node"]
0B	ENTRYPOINT ["docker-entrypoint.sh"]
20.5kB	COPY docker-entrypoint.sh /usr/local/bin/ # …
180MB	RUN /bin/sh -c addgroup -g 1000 node     && …
0B	ENV NODE_VERSION=26.13.0
0B	CMD ["/bin/sh"]
9.31MB	ADD alpine-minirootfs-3.24.3-aarch64.tar.gz …
```

- **Alpine (9,31 MB) abajo y Node (180 MB) encima.** Las capas se comparten: diez imágenes sobre `node:26-alpine` ocupan esos 258 MB una vez.

<Callout type="risk">

- **El grupo `docker` equivale a `root`:** puede montar `/` del servidor en un contenedor. Solo para quien sería administrador; `deploy` ya tenía `sudo` (I6.2).
- **Una etiqueta no es una versión fija:** `node:26-alpine` cambiará. Para fijarla, el _digest_ (`node:26-alpine@sha256:…`).
- **Alpine usa musl, no glibc:** algunos binarios de npm fallan. Si te pasa, `node:26-slim`.

</Callout>

## Paso 2: el primer `Dockerfile`, y por qué está mal

**Qué es:** un **`Dockerfile`** es la receta de una imagen. `FROM` es la imagen de partida, `WORKDIR` la carpeta de trabajo, `COPY` copia del **contexto** (la carpeta del proyecto), `RUN` ejecuta una orden y guarda una capa, y `CMD` es lo que arranca el contenedor.

**Cómo se usa:** la primera idea de casi todo el mundo:

```dockerfile
# Archivo: Dockerfile.ingenuo — la primera idea, con todos sus problemas
FROM node:26-alpine
WORKDIR /app
COPY . .
RUN npm ci
RUN npm run build
CMD ["node", "dist/server/entry.mjs"]
```

`-f` elige el archivo, `-t` le pone nombre y `.` es el contexto:

```bash
docker build --progress=plain -f Dockerfile.ingenuo -t entrenos:ingenuo .
docker image ls entrenos --format "{{.Tag}} {{.Size}}"
```

```text
#5 transferring context: 273.93MB 2.5s done
…
ingenuo 1.24GB
```

Funciona en 26 s y pesa **1,24 GB**. Lo que contiene, sin enseñar secretos (solo cuenta líneas):

```bash
docker run --rm entrenos:ingenuo sh -c 'ls -A /app | tr "\n" " "; echo; grep -c "^BETTER_AUTH_SECRET=." .env; whoami'
docker history entrenos:ingenuo --format "{{.Size}}\t{{.CreatedBy}}" | head -n 5
```

```text
.astro .env .env.example .gitignore .vscode AGENTS.md Dockerfile.ingenuo README.md astro.config.mjs dist node_modules package-lock.json package.json playwright.config.ts public scripts src tests tsconfig.json vitest.config.ts
1
root
0B	CMD ["node" "dist/server/entry.mjs"]
15.9MB	RUN /bin/sh -c npm run build # buildkit
413MB	RUN /bin/sh -c npm ci # buildkit
340MB	COPY . . # buildkit
8.19kB	WORKDIR /app
```

- **Tu `.env` está dentro:** cualquiera con la imagen lee el secreto de Better Auth y la contraseña de MongoDB.
- **274 MB de contexto,** casi todo tu `node_modules` del Mac (340 MB en la capa `COPY`), que `npm ci` sustituye (413 MB más) sin quitar la capa anterior: las capas solo se añaden.
- **Todo va dentro** (TypeScript, Vitest, Playwright, tests, código fuente), **y se ejecuta como `root`.**

Cambia una línea y reconstruye:

```bash
echo "// cambio" >> src/lib/ritmo.ts
docker build --progress=plain -f Dockerfile.ingenuo -t entrenos:ingenuo .
```

```text
#6 [2/5] WORKDIR /app
#6 CACHED
#7 [3/5] COPY . .
#8 [4/5] RUN npm ci
#9 [5/5] RUN npm run build
```

- **Otros 23 s y otra vez `npm ci`:** Docker reutiliza una capa (`CACHED`) solo si ella y las anteriores no cambian, y `COPY . .` incluye `ritmo.ts`. (Quita esa línea antes de seguir).

<Callout type="risk">

- **`RUN rm .env` no lo quita:** la capa del `COPY` sigue en la imagen y `docker save` la exporta. Un secreto que entra en una capa ya está filtrado.
- **Si ya subiste una imagen con secretos, cámbialos:** el de Better Auth cierra todas las sesiones (I5.3); la contraseña de MongoDB, en Atlas.

</Callout>

## Paso 3: `.dockerignore` y el orden de las capas

**Qué es:** **`.dockerignore`** es el `.gitignore` del contexto. Y copiar **primero** `package.json` y `package-lock.json`, después `npm ci` y luego el resto, hace que `npm ci` solo se repita al cambiar las dependencias.

**Cómo se usa:** en la raíz del proyecto:

```text
# Archivo: .dockerignore
node_modules
dist
.astro
.env
.env.*
!.env.example
.git
.vscode
coverage
playwright-report
test-results
logs
Dockerfile*
compose*.yaml
.dockerignore
*.log
.DS_Store
```

- **`node_modules`, `dist`, `.astro`** se generan dentro (y los del Mac traen binarios de macOS); **`.env` y `.env.*`** nunca entran, salvo `!.env.example`; **`Dockerfile*`, `compose*.yaml`** no deben invalidar la caché del código.

El paso intermedio, solo con esos dos cambios:

```dockerfile
FROM node:26-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
CMD ["node", "dist/server/entry.mjs"]
```

```bash
docker build --progress=plain -f Dockerfile.capas -t entrenos:capas .
```

```text
#10 0.836 06:21:27 [ERROR] [vite] ✗ Build failed in 62ms
#10 0.899 [EnvInvalidVariables] The following environment variables defined in `env.schema` are invalid:
#10 0.899 - MONGODB_URI is missing
#10 0.899 - BETTER_AUTH_SECRET is missing
#10 0.899 - BETTER_AUTH_URL is missing
#10 ERROR: process "/bin/sh -c npm run build" did not complete successfully: exit code: 1
```

- **Sin `.env`, `validateSecrets: true` (I3.6) para el _build_,** y con `false` falla igual, más tarde:

```text
#13 1.875 06:23:11 [ERROR] [build] Caught error rendering /acerca: EnvInvalidVariables: The following environment variables defined in `env.schema` are invalid:
#13 1.875 - MONGODB_URI is missing
```

- **Para prerenderizar `/acerca`, Astro ejecuta el _middleware_** (I3.4), que importa `auth.ts` y este `mongo.ts`, que lee `MONGODB_URI` de `astro:env/server` al cargarse.
- **La solución (Paso 4): valores de relleno solo para el _build_.** `new MongoClient(...)` no conecta hasta la primera consulta, así que basta con que pasen la validación.

<Callout type="risk">

- **Ni `.env` ni `ARG`/`ENV` con secretos:** con `--build-arg BETTER_AUTH_SECRET=…`, `docker history --no-trunc` lo enseña, y `docker build --check` avisa con `SecretsUsedInArgOrEnv`.
- **Las secretas no se incrustan en `dist`** (`_internalGetSecret("MONGODB_URI")`), **las públicas sí:** `var PUBLIC_NOMBRE_APP = "Mi entreno"`. Unas van al arrancar y otras al compilar.

</Callout>

## Paso 4: el `Dockerfile` _multi-stage_

**Qué es:** un `Dockerfile` con varios `FROM`, cada uno una etapa con su sistema de archivos. Se compila en las primeras y la imagen final, la última, recibe solo el resultado.

**Cómo se usa:** sustituye el `Dockerfile` de la raíz:

```dockerfile
# syntax=docker/dockerfile:1
# Archivo: Dockerfile

# ─── Etapa 1: compilar ───────────────────────────────────────
FROM node:26-alpine AS build
WORKDIR /app
# Primero solo las dependencias: esta capa se reutiliza mientras package-lock.json no cambie
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
# Las públicas se fijan en el build (I3.6): se pasan con --build-arg, no al arrancar
ARG PUBLIC_NOMBRE_APP="Mi entreno"
ARG OBJETIVO_SEMANAL_MINUTOS=150
# El build carga el middleware, que importa src/lib/mongo.ts y src/lib/auth.ts, y astro:env exige sus
# secretas al cargarlos. Estos valores de relleno solo pasan la validación: el build nunca conecta con
# ellos y no quedan en dist (los secretos se leen al arrancar). Los de verdad llegan con `docker run`.
RUN MONGODB_URI="mongodb://relleno-del-build.invalid" \
    BETTER_AUTH_SECRET="relleno-del-build-no-es-un-secreto-real" \
    BETTER_AUTH_URL="http://localhost:4321" \
    npm run build

# ─── Etapa 2: solo las dependencias de producción ───────────
FROM node:26-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

# ─── Etapa 3: la imagen final ────────────────────────────────
FROM node:26-alpine
WORKDIR /app
ENV NODE_ENV=production HOST=0.0.0.0 PORT=4321
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
COPY scripts ./scripts
# Los archivos son de root y el proceso es de node: la app puede leerlos, pero no cambiarlos
USER node
EXPOSE 4321
CMD ["node", "scripts/arrancar.mjs"]
```

- **`build`** instala todo y ejecuta `npm run build`; **`deps`**, desde cero, solo `npm ci --omit=dev`; **la final** es `node:26-alpine` con `dist`, ese `node_modules`, `package.json` y `scripts`.
- **`# syntax=docker/dockerfile:1`** permite `RUN --mount=type=cache,target=/root/.npm`: la caché de npm vive fuera de la imagen y un `npm ci` repetido solo descarga lo nuevo.
- **`ARG`** fija las variables públicas al compilar (I3.6), cambiables con `--build-arg`.
- **`ENV … HOST=0.0.0.0`:** en un contenedor, `127.0.0.1` sería el propio contenedor y Docker no podría hacerle llegar peticiones (A4.1).
- **`USER node`:** los archivos son de `root`; la app los lee, no los cambia. **`EXPOSE 4321`** solo documenta; publica `docker run -p`.
- **`CMD ["node", "scripts/arrancar.mjs"]`:** primero valida las variables.

Sin variables, el servidor arranca y falla con la primera petición (A4.1), y Docker lo da por bueno. `scripts/arrancar.mjs` valida las secretas con Zod y solo entonces importa el servidor:

```js
// Archivo: scripts/arrancar.mjs
// Punto de entrada del contenedor: valida las variables secretas y, si están bien, arranca Astro.
// astro:env las comprueba en `astro dev` y `astro build`, pero el servidor compilado no lo hace al
// arrancar: fallaría en la primera petición que las use (A4.1). Así, el contenedor no llega a arrancar.
import { z } from "zod";

const EnvArranqueSchema = z.object({
  MONGODB_URI: z
    .string({ error: "falta" })
    .refine((v) => v.startsWith("mongodb://") || v.startsWith("mongodb+srv://"), "debe empezar por mongodb:// o mongodb+srv://"),
  MONGODB_DB: z.string().min(1).optional(),
  BETTER_AUTH_SECRET: z.string({ error: "falta" }).min(32, "debe tener al menos 32 caracteres"),
  BETTER_AUTH_URL: z.url({ error: "falta o no es una URL" }),
});

const resultado = EnvArranqueSchema.safeParse(process.env);
if (!resultado.success) {
  console.error("✗ No arranco: variables de entorno no válidas");
  for (const issue of resultado.error.issues) console.error(`  - ${issue.path.join(".")}: ${issue.message}`);
  process.exit(1);
}

await import("../dist/server/entry.mjs");
```

```bash

docker image ls entrenos --format "{{.Tag}} {{.Size}}"
docker history entrenos:1 --format "{{.Size}}\t{{.CreatedBy}}" | head -n 9
```

- **El relleno debe pasar el esquema** (`min: 32` en `BETTER_AUTH_SECRET`, `startsWith` en `MONGODB_URI`) y no servir de nada si se cuela: `.invalid` es un dominio que nunca existe. Una secreta nueva va en tres sitios: `astro.config.mjs`, el `Dockerfile` y `arrancar.mjs`.
- **`--omit=dev` sigue instalando `vitest`** (A4.1): unos 40 de los 250 MB.
- **Una imagen por arquitectura:** esta es arm64 y no corre en un VPS `amd64`. En A4.5 construirás en el servidor; si no, `docker buildx build --platform linux/amd64`.

</Callout>

## Paso 5: ejecutar el contenedor

**Qué es:** arrancar la imagen con sus variables, publicar el puerto y pararla bien.

**Cómo se usa:** sin variables, `arrancar.mjs` no deja arrancar:

```bash
docker run --rm entrenos:1; echo "exit $?"
docker run --rm -e MONGODB_URI=mongodb://x -e BETTER_AUTH_SECRET=corto -e BETTER_AUTH_URL=http://localhost:4321 entrenos:1; echo "exit $?"
```

```text
✗ No arranco: variables de entorno no válidas
  - MONGODB_URI: falta
  - BETTER_AUTH_SECRET: falta
  - BETTER_AUTH_URL: falta o no es una URL
exit 1
✗ No arranco: variables de entorno no válidas
  - BETTER_AUTH_SECRET: debe tener al menos 32 caracteres
exit 1
```

Con tu `.env` (MongoDB en `127.0.0.1`); `-d` en segundo plano y `-p 127.0.0.1:4321:4321` publica solo en `127.0.0.1`:

```bash
docker run -d --name e1 --env-file .env -p 127.0.0.1:4321:4321 entrenos:1
for p in / /entrar /estadisticas; do curl -s -o /dev/null -w "GET $p -> %{http_code}\n" http://127.0.0.1:4321$p; done
```

```text
GET / -> 200
GET /entrar -> 200
GET /estadisticas -> 302
```

Ninguna ruta tocó la base. Un registro, sí:

```bash
curl -s -o /dev/null -w "POST registro -> %{http_code} en %{time_total}s\n" \
  -H "content-type: application/json" -H "origin: http://localhost:4321" \
  -d '{"email":"prueba@prueba.test","password":"una-clave-de-prueba-larga","name":"Prueba"}' \
  http://127.0.0.1:4321/api/auth/sign-up/email
docker logs e1 2>&1 | grep -oE "ECONNREFUSED [0-9.:]+" | sort -u
```

```text
POST registro -> 500 en 5.132106s
ECONNREFUSED 127.0.0.1:27017
```

- **500 tras 5 s** (`serverSelectionTimeoutMS`, B5.2): **dentro de un contenedor, `127.0.0.1` es el contenedor.** MongoDB irá en otro contenedor de la misma red (Paso 6).

Para el contenedor:

```bash
inicio=$(date +%s.%N); docker stop e1 > /dev/null; echo "docker stop tardó $(echo "$(date +%s.%N) - $inicio" | bc) s"
docker inspect e1 --format "exit {{.State.ExitCode}}"
```

```text
docker stop tardó 10.012706824 s
exit 137
```

- **10 s y código 137** (`SIGKILL`): `docker stop` manda `SIGTERM` (I6.4) y mata a los 10 s. Node es el **PID 1**, al que Linux no aplica la acción por defecto de las señales, y no atiende `SIGTERM` por sí solo. **`--init`** pone delante un proceso mínimo que las reenvía:

```bash
docker rm e1
docker run -d --init --name e1 --env-file .env -p 127.0.0.1:4321:4321 entrenos:1
docker exec e1 ps -o pid,user,args
inicio=$(date +%s.%N); docker stop e1 > /dev/null; echo "docker stop con --init: $(echo "$(date +%s.%N) - $inicio" | bc) s"
docker inspect e1 --format "exit {{.State.ExitCode}}"
```

```text
PID   USER     COMMAND
    1 node     /sbin/docker-init -- docker-entrypoint.sh node scripts/arrancar.mjs
    7 node     {node-MainThread} node scripts/arrancar.mjs
   16 node     ps -o pid,user,args
docker stop con --init: .077704994 s
exit 143
```

- **0,08 s y código 143** (`SIGTERM`): 10 s menos en cada despliegue (A4.5).

Con `ufw` rechazando todo salvo SSH (I6.5), desde otro equipo, frente a un Python fuera de Docker en el 5556 y un contenedor con `-p 5555:80`:

```text
Default: deny (incoming), allow (outgoing), deny (routed)
otro equipo -> servidor:5556 (Python, fuera de Docker) -> sin conexión
otro equipo -> servidor:5555 (contenedor, -p 5555:80) -> 200
otro equipo -> servidor:5555 (contenedor, -p 127.0.0.1:5555:80) -> sin conexión
```

- **Docker se salta `ufw`:** escribe sus reglas en `iptables` y el tráfico hacia contenedores no pasa por `ufw`. `-p 5555:80` queda abierto a internet; con `127.0.0.1:` delante, solo existe dentro del servidor.

<Callout type="risk">

- **Publica siempre en `127.0.0.1`:** en A4.3, Nginx recibe el 80 y el 443 y pasa a `127.0.0.1:4321`.
- **`docker run --env-file` no quita comillas** (`"valor"` llega con ellas); el `env_file` de Compose sí. Escribe los valores sin comillas.
- **`docker logs` guarda en disco sin límite** (`json-file`): puede llenarlo. Rotación en A4.6.

</Callout>

## Paso 6: la app y MongoDB con `docker compose`

**Qué es:** **Docker Compose** describe varios contenedores (red, orden, variables, volúmenes) en `compose.yaml` y los levanta con una orden.

**Cómo se usa:**

```yaml
# Archivo: compose.yaml
# La app y un MongoDB local, cada uno en su contenedor: docker compose up --build
services:
  app:
    build:
      context: .
      args:
        PUBLIC_NOMBRE_APP: "Mi entreno"
    image: entrenos:local
    init: true # un init como PID 1: reenvía SIGTERM a Node y docker stop tarda milisegundos, no 10 s
    env_file: .env # BETTER_AUTH_SECRET y BETTER_AUTH_URL, de tu .env
    environment:
      # Dentro de un contenedor, 127.0.0.1 es el propio contenedor: MongoDB está en el servicio «mongo»
      MONGODB_URI: mongodb://mongo:27017/?replicaSet=rs0
      MONGODB_DB: entrenos
    ports:
      - "127.0.0.1:4321:4321" # solo desde tu equipo; sin 127.0.0.1, desde toda tu red
    depends_on:
      mongo:
        condition: service_healthy # no arranca hasta que MongoDB sea el primario del replica set
    restart: unless-stopped

  mongo:
    image: mongo:8.2 # una versión fijada y probada (ver los riesgos de este paso)
    # Un replica set de un nodo: Better Auth usa transacciones, y un servidor suelto no las admite (I5.2)
    command: ["--replSet", "rs0", "--bind_ip_all"]
    volumes:
      - mongo-datos:/data/db # los datos sobreviven a docker compose down
    healthcheck:
      # La primera vez, inicia el replica set; después, solo comprueba que responde y que es el primario
      test:
        - CMD
        - mongosh
        - --quiet
        - --eval
        - "try { rs.status().ok } catch { rs.initiate({ _id: 'rs0', members: [{ _id: 0, host: 'mongo:27017' }] }).ok }; db.hello().isWritablePrimary || quit(1)"
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 10s
    restart: unless-stopped
    # Sin «ports»: MongoDB solo es accesible para los otros servicios de este compose

volumes:
  mongo-datos:
```

- **`app` y `mongo` comparten una red** en la que cada servicio se llama por su nombre: MongoDB está en `mongo:27017`.
- **`env_file` aporta los secretos y `environment`** sustituye `MONGODB_URI` y `MONGODB_DB`.
- **`depends_on` con `service_healthy`:** la app espera al `healthcheck`, que la primera vez crea el _replica set_ (`rs.initiate`) y después exige `isWritablePrimary`.
- **`--replSet rs0 --bind_ip_all`:** _replica set_ de un nodo que escucha en su contenedor. **`mongo-datos`** es un **volumen**, disco de Docker que sobrevive al contenedor. **`restart: unless-stopped`** lo rearranca si muere.

Con un `mongo:8.2` suelto, todo arrancaba y el registro daba 500:

```text
app-1  | 2026-10-30T06:29:50.908Z ERROR [Better Auth]: MongoServerError MongoServerError: Transaction numbers are only allowed on a replica set member or mongos
```

- **Better Auth usa transacciones al crear una cuenta,** y MongoDB solo las admite en un _replica set_ (I5.2, I7.5): Atlas siempre lo es; uno local, si lo arrancas así.

## Ejercicio práctico

<Callout type="exercise">

1. Crea el `Dockerfile` y un `compose.yaml` con tu app y un MongoDB local, y levanta todo con `docker compose up`.
2. Escribe `scripts/compose-prueba.sh`, que compruebe de principio a fin que la imagen funciona: construir y levantar desde cero, crear los índices, registrarse, guardar un entreno, comprobar que sigue ahí después de `down` y `up` (y que la sesión sigue valiendo), y que `docker compose stop` tarda menos de 5 s. Al terminar, bien o mal, que no quede nada: ni contenedores ni volúmenes.
3. Comprueba que el _script_ detecta un fallo: quita `init: true` del `compose.yaml` y ejecútalo.

</Callout>

Solución. Los archivos del primer punto son los de los Pasos 4 y 6. `scripts/compose-prueba.sh`:

```bash
#!/usr/bin/env bash
# Archivo: scripts/compose-prueba.sh
# Levanta la app y MongoDB con docker compose desde cero, prueba el flujo real y lo borra todo al terminar.
# Uso: bash scripts/compose-prueba.sh   (desde la raíz del proyecto, con .env relleno)
set -euo pipefail

BASE="http://127.0.0.1:4321"
ORIGEN="origin: http://localhost:4321" # Better Auth comprueba el origen (I5.2)
COOKIES="$(mktemp)"
trap 'docker compose down -v >/dev/null 2>&1; rm -f "$COOKIES"' EXIT # pase lo que pase, no deja nada

paso() { printf "== %s\n" "$1"; }
falla() { echo "  FALLO: $1"; docker compose logs --tail 20 app; exit 1; }
esperar_app() {
  for _ in $(seq 1 60); do
    curl -s -o /dev/null "$BASE/" && return 0
    sleep 0.5
  done
  falla "la app no responde en $BASE"
}
contar_entrenos() { docker compose exec -T mongo mongosh --quiet entrenos --eval "db.entrenos.countDocuments()"; }

paso "1. Build y arranque desde cero"
docker compose down -v >/dev/null 2>&1
docker compose up -d --build --wait mongo >/dev/null 2>&1 || falla "MongoDB no llega a estar healthy"
docker compose up -d app >/dev/null 2>&1
esperar_app
docker compose ps --format "  {{.Service}}: {{.Status}}"

paso "2. Índices"
docker compose run --rm -T app node scripts/crear-indices.mjs 2>/dev/null | sed 's/^/  /'

paso "3. Registro y un entreno"
EMAIL="compose-$(date +%s)@prueba.test"
CLAVE="$(openssl rand -base64 18)"
codigo=$(curl -s -c "$COOKIES" -o /dev/null -w "%{http_code}" -H "content-type: application/json" -H "$ORIGEN" \
  -d "{\"email\":\"$EMAIL\",\"password\":\"$CLAVE\",\"name\":\"Prueba\"}" "$BASE/api/auth/sign-up/email")
[ "$codigo" = "200" ] || falla "registro: $codigo"
echo "  registro: $codigo"
codigo=$(curl -s -b "$COOKIES" -o /dev/null -w "%{http_code}" -H "content-type: application/json" -H "$ORIGEN" \
  -d '{"tipo":"running","minutos":45,"km":8.5,"fecha":"2026-10-29","sensacion":4}' "$BASE/api/entrenos")
[ "$codigo" = "201" ] || falla "nuevo entreno: $codigo"
echo "  nuevo entreno: $codigo"
[ "$(contar_entrenos)" = "1" ] || falla "MongoDB no tiene el entreno"
echo "  entrenos en MongoDB: 1"

paso "4. Los datos sobreviven a down y up"
docker compose down >/dev/null 2>&1
docker compose up -d --wait mongo >/dev/null 2>&1
docker compose up -d app >/dev/null 2>&1
esperar_app
[ "$(contar_entrenos)" = "1" ] || falla "el entreno no ha sobrevivido"
codigo=$(curl -s -b "$COOKIES" -o /dev/null -w "%{http_code}" "$BASE/api/entrenos")
[ "$codigo" = "200" ] || falla "la sesión no ha sobrevivido: $codigo"
echo "  entrenos tras down y up: 1; la sesión sigue valiendo: $codigo"

paso "5. Se para rápido"
inicio=$(date +%s)
docker compose stop app >/dev/null 2>&1
segundos=$(( $(date +%s) - inicio ))
[ "$segundos" -lt 5 ] || falla "docker compose stop ha tardado ${segundos} s (¿falta init: true?)"
echo "  docker compose stop: ${segundos} s"

echo "Todo correcto"
```


- **22 s, y después `docker compose ps -a` y `docker volume ls` no muestran nada.** Sin `init: true`:

```text
== 5. Se para rápido
  FALLO: docker compose stop ha tardado 10 s (¿falta init: true?)
```

- **`trap … EXIT` con `down -v`** empieza y termina desde cero: sin datos de prueba ni puerto ocupado.
- **`up --wait mongo` y luego `up app`:** `--wait` falla si no llega a _healthy_; la app aún no tiene `healthcheck` (A4.5), así que `esperar_app` pregunta con `curl`. **`exec -T` y `run -T`** no piden terminal, que en `cron` o CI no hay.
- **La sesión sobrevive a `down` y `up`:** está en MongoDB, en el volumen, con el mismo secreto. Lo que verá un usuario tras un despliegue.
- **El correo usa `.test`,** un dominio reservado que nunca recibe correo.

<Callout type="risk">

- **El _script_ borra el volumen del proyecto de la carpeta:** si tienes datos en ese Compose, usa `COMPOSE_PROJECT_NAME=prueba` y otro puerto.
- **Con `set -e`, un `$(…)` que falla da texto vacío:** el mensaje será el del _script_. `falla` enseña 20 líneas del registro de la app; el de MongoDB, con `docker compose logs mongo`.

</Callout>

<Callout type="mastery">

Tu app arranca igual en cualquier máquina con Docker: una imagen _multi-stage_ de 562 MB que no contiene secretos (los recibe al arrancar, y se niega a arrancar si faltan), ni herramientas de compilación, ni se ejecuta como `root`; con las capas en el orden que aprovecha la caché (3 s al cambiar código); que se para en milisegundos con `init`; y que con `docker compose` levanta junto a un MongoDB _replica set_ con sus datos en un volumen, publicada solo en `127.0.0.1`.

</Callout>

## Resumen

- Imagen: capas de solo lectura; contenedor: una imagen en marcha. `node:26-alpine`, 258 MB; `node:26`, 1,8 GB.
- El `Dockerfile` ingenuo metió el `.env`, copió 274 MB, pesó 1,24 GB, corría como `root` y repetía `npm ci`.
- `.dockerignore` y copiar primero `package*.json`: 3 s al cambiar código.
- Secretas de relleno para el _build_ (no quedan en `dist`); públicas con `--build-arg`.
- _Multi-stage_ con `USER node`: 562 MB. `arrancar.mjs` valida, `--init` para en 0,08 s y Docker se salta `ufw`: publica en `127.0.0.1`.
- Compose: nombres de servicio, `service_healthy`, _replica set_ y un volumen que solo borra `down -v`.
