Los avisos de tu Planificador funcionan por **sondeo** (_polling_): cada cierto tiempo, una tarea pregunta a la base de datos "¿hay algo nuevo?". Casi siempre la respuesta es "no", y cada pregunta es una consulta. Y cuando hay algo nuevo, se entera tarde: hasta el siguiente sondeo. Los **_change streams_** le dan la vuelta: la aplicación abre un canal con MongoDB, y MongoDB le **avisa** de cada cambio en cuanto ocurre. En esta sección vas a ver qué entregan, a medir la diferencia con el sondeo, a no perder eventos cuando el proceso se cae y a rehacer los avisos del Planificador con todo eso.

**Lo que tendrás al terminar:** un proceso de avisos que escucha las tareas del Planificador, avisa por Telegram de las urgentes y de las terminadas, sigue donde lo dejó tras un reinicio y no repite ningún aviso.

**Requisitos:** el proyecto `mongo-academy` con `src/a2/`, conectado a un _replica set_ (como en A2.1). En un MongoDB suelto, `watch()` no funciona:

```text
Location40573: The $changeStream stage is only supported on replica sets
```

Dos cosas de esta sección **no se han ejecutado contra servicios reales:** los avisos van a un servidor local que imita la API de Telegram (el código es el mismo; solo cambia la dirección), y los Atlas Triggers (Paso 4) solo existen en Atlas, así que se explican sin ejecutarlos.

## Paso 1: `watch()`

`src/a2/16-watch.ts`:

```ts
// Archivo: src/a2/16-watch.ts
// watch(): MongoDB avisa de cada cambio en la colección, en el momento en que ocurre
import { cliente, db } from "../db";

interface Intento {
  userId: string;
  cursoId: string;
  puntuacion: number;
}
const intentos = db.collection<Intento>("a2_intentos_eventos");
await intentos.deleteMany({});

// fullDocument: "updateLookup": en las actualizaciones, trae también el documento entero tal como quedó
const stream = intentos.watch([], { fullDocument: "updateLookup" });

// Escuchar en segundo plano: un bucle que recibe los eventos según llegan
const recibidos = (async () => {
  try {
    for await (const cambio of stream) {
      const resumen =
        cambio.operationType === "insert"
          ? `fullDocument=${JSON.stringify(cambio.fullDocument)}`
          : cambio.operationType === "update"
            ? `cambios=${JSON.stringify(cambio.updateDescription.updatedFields)} · fullDocument=${JSON.stringify(cambio.fullDocument)}`
            : cambio.operationType === "delete"
              ? `documentKey=${JSON.stringify(cambio.documentKey)}`
              : "";
      console.log(`${cambio.operationType.padEnd(7)} ${resumen}`);
    }
  } catch (e) {
    if (!stream.closed) throw e; // cerrarlo a propósito interrumpe el for await con "ChangeStream is closed"
  }
})();

await new Promise((r) => setTimeout(r, 300)); // el stream ya está abierto
const { insertedId } = await intentos.insertOne({
  userId: "ana",
  cursoId: "A2",
  puntuacion: 4,
});
await intentos.updateOne({ _id: insertedId }, { $set: { puntuacion: 5 } });
await intentos.deleteOne({ _id: insertedId });

await new Promise((r) => setTimeout(r, 500)); // tiempo para que lleguen los eventos
await stream.close();
await recibidos;
await cliente.close();
```

```bash
npm start -- src/a2/16-watch.ts
```

```text
insert  fullDocument={"_id":"…","userId":"ana","cursoId":"A2","puntuacion":4}
update  cambios={"puntuacion":5} · fullDocument={"_id":"…","userId":"ana","cursoId":"A2","puntuacion":5}
delete  documentKey={"_id":"…"}
```

- **Cada cambio llega como un evento**, con su `operationType` (`insert`, `update`, `delete`, `replace`…), la clave del documento (`documentKey`) y lo que cambió.
- **En un `insert`, `fullDocument` es el documento nuevo.** En un `update`, `updateDescription.updatedFields` dice qué campos cambiaron; con `fullDocument: "updateLookup"`, el evento trae además el documento entero tal como quedó.
- **En un `delete`, solo llega la clave:** el documento ya no existe. Si necesitas saber qué había, MongoDB puede guardar la versión anterior (`changeStreamPreAndPostImages` en la colección), a cambio de más espacio.
- **Por dentro, MongoDB lee el _oplog_:** el registro de operaciones que el _replica set_ usa para copiar los cambios entre nodos. Por eso hace falta un _replica set_.

<Callout type="risk">

- **Cerrar el _stream_ interrumpe el `for await` con un error:** la primera versión de este _script_ terminaba con `MongoAPIError: ChangeStream is closed` al llamar a `stream.close()`. El `try`/`catch` que comprueba `stream.closed` distingue el cierre a propósito de un fallo de verdad.
- **`updateLookup` busca el documento después del cambio:** si entre el cambio y la búsqueda hay otro, el `fullDocument` que llega ya incluye ese segundo cambio. Para saber exactamente qué cambió en cada evento, usa `updatedFields`.

</Callout>

## Paso 2: sondeo frente a _change stream_

Lo mismo de las dos formas, a la vez: diez intentos a intervalos irregulares, y dos procesos que se enteran de cada uno. `src/a2/18-sondeo.ts`:

```ts
// Archivo: src/a2/18-sondeo.ts
// Sondeo (preguntar cada segundo "¿hay algo nuevo?") frente a change stream (MongoDB avisa)
import { ObjectId } from "mongodb";
import { cliente, db } from "../db";

interface Intento { userId: string; cursoId: string; puntuacion: number; escritoEn: number }
const intentos = db.collection<Intento>("a2_intentos_eventos");
await intentos.deleteMany({});

const EVENTOS = 10;
const retrasosSondeo: number[] = [];
const retrasosStream: number[] = [];
let consultas = 0;

// 1. Sondeo: cada 1000 ms, busca los intentos con _id mayor que el último visto
let ultimo = new ObjectId();
const sondeo = setInterval(async () => {
  consultas++;
  const nuevos = await intentos.find({ _id: { $gt: ultimo } }).sort({ _id: 1 }).toArray();
  for (const n of nuevos) {
    retrasosSondeo.push(Date.now() - n.escritoEn);
    ultimo = n._id;
  }
}, 1000);

// 2. Change stream: MongoDB entrega cada insert en cuanto ocurre
const stream = intentos.watch([{ $match: { operationType: "insert" } }]);
const bucle = (async () => {
  try {
    for await (const c of stream) if (c.operationType === "insert") retrasosStream.push(Date.now() - c.fullDocument.escritoEn);
  } catch (e) {
    if (!stream.closed) throw e;
  }
})();

// Diez intentos, a intervalos irregulares, durante unos 10 segundos
await new Promise((r) => setTimeout(r, 300));
const inicio = Date.now();
for (let i = 0; i < EVENTOS; i++) {
  await new Promise((r) => setTimeout(r, 400 + ((i * 397) % 1300)));
  await intentos.insertOne({ userId: "ana", cursoId: "A2", puntuacion: 5, escritoEn: Date.now() });
}
await new Promise((r) => setTimeout(r, 1200)); // que el último sondeo lo recoja
clearInterval(sondeo);
await stream.close();
await bucle;

const media = (l: number[]) => (l.reduce((a, b) => a + b, 0) / l.length).toFixed(0);
const segundos = (Date.now() - inicio) / 1000;
console.log(`${EVENTOS} intentos en ${segundos.toFixed(1)} s`);
console.log(`sondeo:        ${retrasosSondeo.length} avisos · retraso medio ${media(retrasosSondeo)} ms (máx. ${Math.max(...retrasosSondeo)}) · ${consultas} consultas a la base`);
console.log(`change stream: ${retrasosStream.length} avisos · retraso medio ${media(retrasosStream)} ms (máx. ${Math.max(...retrasosStream)}) · 1 stream abierto`);
console.log(`a este ritmo, el sondeo hace ${Math.round((consultas / segundos) * 3600)} consultas por hora, haya novedades o no`);

await cliente.close();
```

Dos ejecuciones:

```text

sondeo:        10 avisos · retraso medio 618 ms (máx. 992) · 11 consultas a la base
change stream: 10 avisos · retraso medio 10 ms (máx. 13) · 1 stream abierto
a este ritmo, el sondeo hace 3451 consultas por hora, haya novedades o no
10 intentos en 11.5 s
sondeo:        10 avisos · retraso medio 618 ms (máx. 991) · 11 consultas a la base
change stream: 10 avisos · retraso medio 10 ms (máx. 16) · 1 stream abierto
a este ritmo, el sondeo hace 3452 consultas por hora, haya novedades o no
```

- **Con sondeo cada segundo, cada aviso llega unos 618 ms tarde de media** (hasta casi un segundo): lo que falte para el siguiente sondeo. Para reducirlo, hay que preguntar más a menudo, y entonces hay más consultas.
- **Con el _change stream_, unos 10 ms:** lo que tarda MongoDB en entregar el evento.
- **El sondeo hizo 11 consultas en 11,5 segundos, y casi todas sin novedades.** A ese ritmo, unas 3 450 consultas por hora, por cada proceso que sondea, haya o no haya cambios. El _change stream_ es una sola conexión abierta.

<Callout type="risk">

- **Un _stream_ abierto ocupa una conexión todo el tiempo:** no lo abras por cada petición web. Va en un proceso de larga duración (un _worker_, como el del ejercicio), no en un _endpoint_ ni en una función _serverless_ que termina en segundos.
- **Filtra en el _pipeline_ del _stream_,** no en tu código: con `$match`, MongoDB solo te envía los eventos que te interesan (el Paso 3 lo hace con los 5/5).

</Callout>

## Paso 3: no perder eventos, con _resume tokens_

Cada evento trae en su `_id` un **_resume token_**: un marcador de su posición en el _oplog_. Si el proceso guarda el token del último evento que procesó, al reiniciar puede pedir "todo lo que pasó **después** de este" (`resumeAfter`). `src/a2/17-reanudar.ts`:

```ts
// Archivo: src/a2/17-reanudar.ts
// Si el proceso que escucha se cae, ¿qué pasa con los cambios de mientras? El resume token los recupera
import type { ChangeStreamDocument, ResumeToken } from "mongodb";
import { cliente, db } from "../db";

interface Intento { userId: string; cursoId: string; puntuacion: number }
const intentos = db.collection<Intento>("a2_intentos_eventos");
await intentos.deleteMany({});
const soloCincos = [{ $match: { operationType: "insert", "fullDocument.puntuacion": 5 } }];

/** Escucha durante `ms` y devuelve los eventos recibidos y el token del último */
async function escuchar(ms: number, opciones: { resumeAfter?: ResumeToken } = {}, mientras?: () => Promise<void>) {
  const stream = intentos.watch<Intento, ChangeStreamDocument<Intento>>(soloCincos, opciones);
  const recibidos: string[] = [];
  let token: ResumeToken | undefined;
  const bucle = (async () => {
    try {
      for await (const c of stream) {
        if (c.operationType === "insert") recibidos.push(`${c.fullDocument.userId} ${c.fullDocument.cursoId}`);
        token = c._id; // el resume token de ESTE evento: guárdalo después de procesarlo
      }
    } catch (e) {
      if (!stream.closed) throw e;
    }
  })();
  await new Promise((r) => setTimeout(r, 300));
  await mientras?.();
  await new Promise((r) => setTimeout(r, ms));
  await stream.close();
  await bucle;
  return { recibidos, token };
}

const insertar = (userId: string, cursoId: string, puntuacion: number) => intentos.insertOne({ userId, cursoId, puntuacion });

// 1. El proceso funciona: recibe dos 5/5 (y no el 3/5, que el $match filtra)
const primera = await escuchar(500, {}, async () => {
  await insertar("ana", "A1", 5);
  await insertar("dani", "A1", 3);
  await insertar("dani", "A2", 5);
});
console.log(`1. funcionando:        ${primera.recibidos.join(" · ")}`);

// 2. El proceso está caído (nadie escucha) mientras llegan dos 5/5 más
await insertar("eva", "B1", 5);
await insertar("ana", "A2", 5);

// 3a. Vuelve a arrancar SIN el token: solo ve lo que pasa a partir de ahora
const sinToken = await escuchar(500, {}, async () => {
  await insertar("luis", "I1", 5);
});
console.log(`2. reinicio sin token: ${sinToken.recibidos.join(" · ")}`);

// 3b. Vuelve a arrancar CON el token guardado en el paso 1: recibe lo que se perdió, y lo nuevo
const conToken = await escuchar(500, { resumeAfter: primera.token });
console.log(`3. reinicio con token: ${conToken.recibidos.join(" · ")}`);

// ¿Hasta cuándo se puede reanudar? Mientras el evento siga en el oplog del replica set
const oplog = db.client.db("local").collection("oplog.rs");
const [primero] = await oplog.find().sort({ $natural: 1 }).limit(1).toArray();
const [ultimo] = await oplog.find().sort({ $natural: -1 }).limit(1).toArray();
const [stats] = await oplog.aggregate<{ storageStats: { maxSize: number; size: number } }>([{ $collStats: { storageStats: {} } }]).toArray();
const horas = (ultimo!.ts.getHighBits() - primero!.ts.getHighBits()) / 3600;
console.log(
  `oplog: tamaño máximo ${(stats!.storageStats.maxSize / 1024 ** 3).toFixed(1)} GB · ocupado ${(stats!.storageStats.size / 1024 ** 2).toFixed(0)} MB · cubre ${horas.toFixed(1)} horas`,
);

await cliente.close();
```

```text
1. funcionando:        ana A1 · dani A2
2. reinicio sin token: luis I1
3. reinicio con token: eva B1 · ana A2 · luis I1
oplog: tamaño máximo 0.2 GB · ocupado 177 MB · cubre 0.4 horas
```

1. **Funcionando, el `$match` deja pasar solo los 5/5:** el 3/5 de Dani no llega.
2. **Sin el token, el reinicio pierde lo de mientras:** las dos evaluaciones de 5/5 que llegaron con el proceso caído no se avisan nunca.
3. **Con el token, el reinicio recupera las dos** y sigue con la nueva.

¿Y si el proceso está caído mucho tiempo? Solo se puede reanudar mientras el evento siga en el _oplog_, que tiene un tamaño fijo y descarta lo más antiguo. La última línea lo mide en este laboratorio: un _oplog_ de 0,2 GB que **solo cubre 0,4 horas**, porque los millones de documentos de A2.2 lo llenaron. En un clúster de producción, con escrituras normales, suele cubrir horas o días; míralo en el tuyo antes de decidir cuánto tiempo puede estar caído el proceso. (En este laboratorio no conseguí provocar el caso de un token ya descartado: tras unos 240 MB de escrituras más, el _oplog_ seguía conservando el evento, por encima de su tamaño nominal).

<Callout type="risk">

- **Guarda el token después de procesar el evento, no antes:** si lo guardas antes y el proceso se cae a mitad, al reiniciar ese evento se da por hecho y se pierde. Guardándolo después, en el peor caso se repite (y el ejercicio evita que el aviso se repita).
- **Si el token ya no está en el _oplog_, el _stream_ no se puede reanudar:** el proceso tiene que darse cuenta y recuperarse por otro camino (por ejemplo, una consulta de lo que cambió desde la última fecha conocida). No lo ignores en silencio.

</Callout>

## Paso 4: Atlas Triggers, la alternativa sin servidor

Un _change stream_ necesita un proceso que esté siempre en marcha. Si tu app vive en Vercel, con funciones que duran segundos, no tienes dónde ponerlo. **Atlas Triggers** resuelve eso: en Atlas, un _Database Trigger_ se configura sobre una colección, con los tipos de operación y un filtro, y ejecuta una función de JavaScript alojada en el propio Atlas con cada evento. Por dentro es un _change stream_ que gestiona Atlas, incluido guardar dónde se quedó.

|                           | _Change stream_ propio                  | Atlas Trigger                       |
| ------------------------- | --------------------------------------- | ----------------------------------- |
| Dónde se ejecuta          | Tu proceso (un _worker_ en un servidor) | Atlas                               |
| Guardar el _resume token_ | Tú (el ejercicio)                       | Atlas                               |
| Funciona con              | Cualquier _replica set_                 | Solo Atlas                          |
| Tu código                 | Tu lenguaje, tus dependencias           | Una función con el entorno de Atlas |

Los Triggers **no se han ejecutado en este laboratorio**, porque solo existen en Atlas. Consulta la documentación de Atlas Triggers para configurarlos en tu clúster: la lógica de la función es la misma que `textoDelAviso` del ejercicio.

<Callout type="risk">

- **Atlas puede suspender un Trigger:** por ejemplo, si no puede reanudarlo porque el evento ya salió del _oplog_. Revisa su estado en Atlas de vez en cuando, o un sistema de avisos puede dejar de avisar sin que nadie se entere.
- **No hagas lo mismo con un Trigger y con tu _worker_ a la vez:** los avisos llegarían dos veces.

</Callout>

Solución. El proceso de avisos, `src/a2/avisos.ts`:

```ts
// Archivo: src/a2/avisos.ts
// El proceso de avisos del Planificador: escucha las tareas y avisa por Telegram, sin consultar nada periódicamente
import type { ChangeStream, ChangeStreamDocument, ResumeToken } from "mongodb";
import { db } from "../db";

export interface Tarea {
  titulo: string;
  prioridad: "alta" | "normal";
  hecha: boolean;
}
export const tareas = db.collection<Tarea>("a2_tareas");
const cursores = db.collection<{ _id: string; token: ResumeToken }>("a2_cursores"); // dónde se quedó cada proceso
const avisados = db.collection<{ _id: string; enviado: Date }>("a2_avisados"); // qué eventos ya se avisaron

/** Para comprobar qué hace el proceso: eventos recibidos, avisos enviados y avisos que ya estaban enviados */
export const cuenta = { eventos: 0, avisos: 0, repetidos: 0 };

/** La API de Telegram: sendMessage. En producción, TELEGRAM_API = "https://api.telegram.org" */
async function enviarTelegram(texto: string) {
  const res = await fetch(`${process.env.TELEGRAM_API}/bot${process.env.TELEGRAM_TOKEN}/sendMessage`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ chat_id: process.env.TELEGRAM_CHAT_ID, text: texto }),
  });
  if (!res.ok) throw new Error(`Telegram respondió ${res.status}`);
}

/** El texto del aviso para cada cambio que interesa (o null si no hay que avisar) */
function textoDelAviso(c: ChangeStreamDocument<Tarea>): string | null {
  if (c.operationType === "insert" && c.fullDocument.prioridad === "alta") return `🔴 Nueva tarea urgente: ${c.fullDocument.titulo}`;
  if (c.operationType === "update" && c.updateDescription.updatedFields?.hecha === true && c.fullDocument) return `✅ Hecha: ${c.fullDocument.titulo}`;
  return null;
}

/** Arranca el proceso: sigue donde lo dejó la última vez (o desde ahora, si es la primera) */
export async function arrancarAvisos(nombre: string): Promise<ChangeStream<Tarea, ChangeStreamDocument<Tarea>>> {
  const guardado = await cursores.findOne({ _id: nombre });
  const stream = tareas.watch<Tarea, ChangeStreamDocument<Tarea>>(
    [{ $match: { operationType: { $in: ["insert", "update"] } } }],
    { fullDocument: "updateLookup", ...(guardado && { resumeAfter: guardado.token }) },
  );
  (async () => {
    try {
      for await (const cambio of stream) {
        cuenta.eventos++;
        const texto = textoDelAviso(cambio);
        const clave = JSON.stringify(cambio._id); // el token identifica el evento
        if (texto && (await avisados.findOne({ _id: clave }))) {
          cuenta.repetidos++; // ya se avisó (el proceso se cayó antes de guardar el token): no repetir
        } else if (texto) {
          await enviarTelegram(texto);
          await avisados.insertOne({ _id: clave, enviado: new Date() });
          cuenta.avisos++;
        }
        await cursores.updateOne({ _id: nombre }, { $set: { token: cambio._id } }, { upsert: true }); // procesado: avanzar
      }
    } catch (e) {
      if (!stream.closed) console.error("[avisos] el stream se cortó:", e);
    }
  })();
  return stream;
}
```

```ts
await cliente.close();
```

```text
   /bot***/sendMessage ✅ Hecha: Entregar el informe
2. Proceso caído: una tarea urgente creada y terminada mientras tanto
3. Reiniciado: 2 mensajes · eventos 2, avisos 2, repetidos descartados 0
   /bot***/sendMessage 🔴 Nueva tarea urgente: Cita con el médico
   /bot***/sendMessage ✅ Hecha: Cita con el médico
4. Reiniciado desde un token viejo: 0 mensajes · eventos 4, avisos 0, repetidos descartados 3
```

1. **Funcionando:** tres eventos (dos tareas nuevas y una terminada), dos avisos. La tarea de prioridad normal no avisa.
2. **Caído:** se crea y se termina una tarea urgente sin nadie escuchando.
3. **Reiniciado:** sigue desde el token guardado en `a2_cursores` y avisa de las dos cosas que pasaron mientras tanto.
4. **Reiniciado desde un token viejo** (como si se hubiera caído justo antes de guardarlo): recibe otra vez cuatro eventos, pero los tres que ya se avisaron están en `a2_avisados` y se descartan. Ningún mensaje repetido.

- **El token se guarda en MongoDB,** en la colección `a2_cursores`, con un nombre por proceso: así sobrevive a reinicios y despliegues.
- **`a2_avisados` es la memoria de lo enviado,** con el propio token del evento como clave. Comprobarla antes de enviar hace que repetir un evento no repita el aviso.
- **El orden importa:** enviar, apuntar el aviso y, al final, avanzar el token. Si el proceso se cae entre enviar y apuntar, ese aviso podría salir dos veces; es el caso más improbable, y es mejor que perder un aviso.

<Callout type="risk">

- **El _token_ de Telegram es un secreto:** va en una variable de entorno, nunca en el código ni en los registros (el Telegram falso lo oculta al mostrar la URL).
- **Un proceso de avisos necesita vigilancia:** si se para, nadie recibe avisos y nadie se entera. Que registre cuándo procesó el último evento y que algo te avise si lleva demasiado tiempo sin hacerlo.

</Callout>

<Callout type="mastery">

Reaccionas a cambios de la base de datos sin consultas periódicas: abres un _change stream_ con `watch()` y un `$match`, sabes que entrega cada cambio en milisegundos frente a los cientos del sondeo, guardas el _resume token_ después de procesar cada evento para seguir donde lo dejaste, evitas avisos repetidos con un registro de lo enviado, y sabes cuándo cambiar tu _worker_ por un Atlas Trigger.

</Callout>

## Resumen

- `collection.watch(pipeline, { fullDocument: "updateLookup" })`: un evento por cada cambio, con `operationType`, `documentKey` y lo que cambió. Necesita un _replica set_.
- Sondeo cada segundo: unos 618 ms de retraso y unas 3 450 consultas por hora. _Change stream_: unos 10 ms y una conexión.
- _Resume token_ (`cambio._id`): guárdalo después de procesar; `resumeAfter` recupera lo perdido mientras siga en el _oplog_.
- Idempotencia: un registro de avisos enviados, con el token como clave.
- Atlas Triggers: el mismo mecanismo, gestionado por Atlas, para apps sin procesos permanentes.
