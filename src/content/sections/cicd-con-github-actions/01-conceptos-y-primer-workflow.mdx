«En mi equipo funciona» es la frase más cara del oficio: olvidaste los tests, o el último cambio, o tu equipo tiene algo que el servidor no. **Integración continua** es que una máquina limpia compruebe cada cambio, siempre igual, sin depender de tu memoria. Aquí escribes un _workflow_ que comprueba tipos, tests y _build_ en cada PR, y lo pruebas sin subir nada.

**Requisitos:** Git (B2) y los tests de tu app (I8).

## Paso 1: las piezas

**Qué es:** **CI** (_integración continua_) comprueba cada cambio; **CD** (_entrega o despliegue continuo_) lleva a producción el que pasa. Primero uno y luego el otro: desplegar sin comprobar es automatizar los errores. Esta sección es solo CI.

**Cómo se usa:**

| Pieza      | Qué es                                    | En nuestro archivo         |
| ---------- | ----------------------------------------- | -------------------------- |
| _Workflow_ | Un proceso automático, en un archivo YAML | `.github/workflows/ci.yml` |
| Evento     | Lo que lo dispara                         | `pull_request`, `push`     |
| _Job_      | Un grupo de pasos en una máquina limpia   | `verificar`                |
| _Step_     | Un comando o una acción                   | `npm run check`            |
| _Runner_   | La máquina que lo ejecuta                 | `ubuntu-latest`            |
| Acción     | Un paso reutilizable, escrito por otros   | `actions/checkout@v7`      |

- **Los _jobs_ van en paralelo y en máquinas distintas,** salvo que `needs` diga otra cosa. Los _steps_ de un _job_ van en orden, y si uno falla los siguientes no se ejecutan.

## Paso 2: tu primer workflow

**Qué es:** un archivo YAML en `.github/workflows/` que GitHub ejecuta con cada evento.

**Cómo se usa:** `.github/workflows/ci.yml`:

```yaml
# Archivo: .github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read # este workflow solo lee el código

jobs:
  verificar:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    # Valores de relleno: el build los exige, pero no los usa ni los guarda
    env:
      MONGODB_URI: mongodb://relleno-del-ci.invalid
      BETTER_AUTH_SECRET: relleno-del-ci-no-es-un-secreto-real
      BETTER_AUTH_URL: http://localhost:4321
      OBJETIVO_SEMANAL_MINUTOS: 150
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 26
          cache: npm
      - run: npm ci
      - run: npm run check
      - run: npm run test:run
      - run: npm run build
```

- **`on`:** cada PR y cada `push` a `main`, por si algo llega sin PR.
- **`permissions`:** el mínimo; un _workflow_ comprometido no podrá escribir en tu repositorio. **`timeout-minutes`:** sin él, un _job_ colgado puede gastar 6 horas.
- **`env`:** valores de relleno que el _build_ exige, como en el `Dockerfile` de A4. **Nunca un secreto real aquí:** el repositorio lo guarda para siempre.
- **`actions/checkout`** baja tu código al _runner_ vacío, **`setup-node`** instala la misma versión que tu `Dockerfile` y **`npm ci`** instala exactamente `package-lock.json`. `lint` y `format` llegan en A7.2.

<Callout type="risk">

- **El YAML es sensible a los espacios:** `runs-on` desplazado dio `mapping values are not allowed in this context` y no se ejecutó nada. Espacios, nunca tabuladores, y el archivo exactamente en `.github/workflows/` (si no, GitHub ni avisa).
- **Una acción es código ajeno con acceso a tu repositorio:** `@v7` es una etiqueta que puede cambiar (GitHub recomienda fijar el SHA), y versiones antiguas como `@v4` dejan de funcionar.
- **Nunca `pull_request_target` sin saber qué hace:** puede dar escritura y secretos al código de una PR ajena.

</Callout>

## Paso 3: lo que encontró la primera vez

**Qué es:** **`act`** ejecuta tu _workflow_ en local, en contenedores de Docker, sin subir nada. Se descarga de `nektos/act`, comprobando la suma de verificación.

**Cómo se usa:**

```bash
act push -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-latest
```

- **La imagen ocupa 2,26 GB.** Con la app tal como quedó tras A6.4, tests y despliegues aparentemente en orden:

```text
✅  Success - Main npm ci [23.4s]
❌  Failure - Main npm run check [5.1s]
🏁  Job failed
```

```text
tests/entrenos.service.test.ts:43:44 - error ts(2345): Argument of type '{ entrenos: Pick<…
tests/entrenos.service.test.ts:48:44 - error ts(2345): Argument of type '{ entrenos: Pick<…
tests/entrenos.service.test.ts:55:44 - error ts(2345): Argument of type '{ entrenos: Pick<…
- 3 errors
```

- **Tres errores de tipos reales:** en A5.4 `crearServicioEntrenos` pasó a pedir `limites` y estos tests no se actualizaron. Nadie lo vio porque el `Dockerfile` ejecuta `astro build`, que no comprueba los tipos de los tests. En `tests/entrenos.service.test.ts`:

```ts
/** Estos tests no prueban el límite de A5.4: siempre deja pasar */
const sinLimites = { contar: async () => ({ permitido: true, reintentarEn: 0 }) };

const servicio = crearServicioEntrenos({ entrenos: repoEnMemoria([running]), limites: sinLimites });
```

El paso siguiente encontró dos cosas más:

```text
FAIL  tests/unit/reloj.test.ts > con el reloj falso completo, la espera no termina sola
FAIL  tests/unit/api-resumen.test.ts > GET /api/resumen > un fallo inesperado del servicio es un 500 que no cuenta el detalle
```

- **`reloj.test.ts`** era la demostración de I8.2, un test que falla a propósito: bórralo si lo conservas.
- **`api-resumen.test.ts`** esperaba el `console.error` que A6.4 cambió por `log.error`: una lección rompió el test de otra, justo lo que debe detectar un CI. La solución está en A6.4.
- **El último fallo era del laboratorio:** los 71 tests pasaban, pero el _job_ fallaba al cerrar la base de prueba con `EACCES`:

```text
apparmor="DENIED" operation="signal" profile="docker-default"
```

- **La política de Docker de esa VM impedía a Vitest parar `mongod`,** sin relación con GitHub; se resolvió con `--container-options "--security-opt apparmor=unconfined"`. Verde:

```text
✅  Success - Main actions/setup-node@v7 [0.6s]
✅  Success - Main npm ci [23.5s]
✅  Success - Main npm run check [5.4s]
✅  Success - Main npm run test:run [7.8s]
✅  Success - Main npm run build [1.5s]
🏁  Job succeeded
```

<Callout type="risk">

- **`act` no es GitHub:** ignora `concurrency`, `permissions`, `timeout-minutes` y `continue-on-error`, y **toda esta sección se midió con `act` en ARM**, no en un _runner_ de GitHub. El resultado definitivo es el de GitHub.
- **Sin memoria, el proceso muere:** en una VM de 2 GB con la app en marcha, código 137. Para otro servicio o añade _swap_.
- **Lee la salida, no solo el color:** un _build_ de 1,5 s pareció sospechoso y era bueno. Y un test que falla a propósito estropea el CI: `it.fails` lo documenta.

</Callout>

## Paso 4: caché de dependencias

**Qué es:** `cache: npm` guarda los paquetes descargados entre ejecuciones, porque cada _job_ empieza vacío.

**Cómo se usa:** dos ejecuciones seguidas:

```text
                 Caché vacía    Caché llena
npm ci           23,5 s         17,5 s
Total del job    41 s           34 s
```

```text
Cache Size: ~80 MB (83384656 B)
Cache restored successfully
Cache restored from key: node-cache-linux-arm64-npm-0407d64b…
```

- **Un 26 % menos en `npm ci`,** menos de lo que suele prometerse: no guarda `node_modules`, sino la caché global de npm, y `npm ci` sigue instalando.
- **La clave lleva el _hash_ de `package-lock.json`:** si cambia una dependencia, se reconstruye sola (A6.3).

<Callout type="risk">

- **Un CI debe funcionar igual sin caché:** si falla al vaciarla, había un problema escondido. Y no guardes `node_modules` a mano (binarios de otro sistema).
- **Dura poco y se comparte:** se borra lo que no se usa en 7 días, 10 GB por repositorio, y una PR lee la caché de su rama y de la base.
- **Nunca secretos en la caché:** quien la lea, los verá.

</Callout>

## Paso 5: las trampas que dejan un verde falso

**Qué es:** un rojo es útil; lo peligroso es un **verde que no significa nada**.

**Cómo se usa:** **una tubería oculta el fallo.** El mismo comando con y sin una línea:

```yaml
- run: false | tee salida.txt # sin shell

- run: false | tee salida.txt
  shell: bash
```

```text
Sin shell:    ✅ Success · 🏁 Job succeeded
shell: bash:  ❌ Failure · 🏁 Job failed
```

- **Sin `shell`, GitHub usa `bash -e`;** con `shell: bash`, añade `-o pipefail`. Sin él, la tubería devuelve lo de `tee`, y el paso sale verde con los tests fallando.

**Una etiqueta flotante cambia sola:** `mongo:8` es «la última 8.x». En el kernel 7.0 de la VM:

```text
mongo:8    8.3.13   exited    MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility…
mongo:8.0  8.0.34   exited    (el mismo mensaje)
mongo:8.2  8.2.12   running
mongo:7.0  7.0.45   running
```

- **Fija las versiones de CI** como en `compose.yaml` (A4.2); `ubuntu-latest` también cambia.
- **Un rojo que nadie mira no existe:** un CI puede fallar semanas si no bloquea nada. En A7.2 será obligatorio.

`npm ci` protege de otra forma: con `package.json` cambiado sin actualizar el _lockfile_, falló en 0,6 s:

```text
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync
npm error Missing: left-pad@1.3.0 from lock file
```

<Callout type="risk">

- **`continue-on-error: true` y `|| true` convierten un fallo en verde:** búscalos en los _workflows_ que heredes.
- **Sin tests, todo pasa:** mira cuántos se ejecutan (aquí, 71).
- **Este `push` solo reacciona en `main`:** el resto, por `pull_request`.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

Añade este _workflow_ a tu app de entrenamiento y abre una PR con un error de tipos a propósito para verlo fallar.

</Callout>

Solución:

```bash
git switch -c prueba/error-de-tipos
echo 'export const minutosPorDefecto: number = "treinta"; // ERROR A PROPÓSITO' >> src/lib/ritmo.ts
git add -A
git commit -m "prueba: error de tipos a propósito"
git push -u origin prueba/error-de-tipos
```

Abre la PR y mira la pestaña **Checks**. Para probarlo antes en local, `evento.json`:

```json
{ "pull_request": { "number": 7, "head": { "ref": "prueba/error-de-tipos" }, "base": { "ref": "main" } } }
```

```bash
act pull_request -e evento.json -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-latest
```

```text
✅  Success - Main npm ci [23.0s]
❌  Failure - Main npm run check [4.8s]
🏁  Job failed
```

```text
src/lib/ritmo.ts:14:14 - error ts(2322): Type 'string' is not assignable to type 'number'.
- 1 error
```

- **Falló en 32 s, sin llegar a los tests ni al _build_.** Borra el error y haz otro _commit_: el _workflow_ se repite.
- **Probado con `act`, sin PR real:** compruébalo tú en la página de la PR. Y la PR en rojo aún se puede fusionar: bloquearlo es A7.2.
- **Coste:** gratis en repositorios públicos; en privados, el plan Free incluye 12 USD de cómputo al mes, y Linux cuesta 0,006 USD por minuto.

<Callout type="mastery">

Sabes distinguir CI de CD, y leer un _workflow_ por sus piezas. Tu app ya tiene una máquina limpia que comprueba tipos, tests y _build_ en cada PR, y que encontró errores que tus despliegues no veían. Sabes que un verde puede ser falso, y por qué. Falta el último paso: que ninguna PR con errores pueda mezclarse, en A7.2.

</Callout>

## Resumen

- **CI** comprueba cada cambio en una máquina limpia; **CD** lleva lo aprobado a producción.
- _Workflow_, evento, _job_, _step_, _runner_ y acción.
- La primera ejecución encontró **3 errores de tipos** y 2 tests rotos que el _build_ no veía.
- **`act`** ejecuta en local, pero no es GitHub.
- **`cache: npm`:** de 23,5 a 17,5 s; guarda la caché de npm, no `node_modules`.
- **`false | tee` sale verde** sin `shell: bash`, y las etiquetas flotantes cambian solas.
- Una PR con error de tipos falló en 32 s; en A7.2, bloqueará.
