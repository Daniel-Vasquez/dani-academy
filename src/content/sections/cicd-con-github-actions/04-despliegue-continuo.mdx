Hasta ahora, desplegar en tu servidor (A4) era entrar por SSH y lanzar un _script_, y dependía de que te acordaras y lo hicieras siempre igual. **Despliegue continuo** es que lo que pasa el CI llegue solo a producción: mezclas una PR y ya está. Aquí lo montas sin cortes, con una clave que solo sirve para desplegar, una forma de volver atrás y versiones con significado.

**Requisitos:** el CI de A7.3 y el despliegue _blue-green_ de A4.

## Paso 1: en Vercel ya lo tienes

**Qué es:** la plataforma de este curso se despliega así. Según la documentación de Vercel, al conectar el repositorio, **cada PR o rama** crea una **vista previa** con su URL y **cada _merge_ a `main`**, un despliegue de **producción**.

**Cómo se usa:**

- **No hay _workflow_ que escribir,** pero Vercel despliega al recibir el cambio, sin esperar a tu CI: para que nada llegue sin pasar los tests, la regla de protección de A7.2. No se ha medido aquí (no se tocó ningún despliegue real).
- **Lo que sigue es para tu propio servidor,** donde todo eso hay que construirlo.

## Paso 2: una clave que solo puede desplegar

**Qué es:** el CI necesita entrar en tu servidor, y con tu clave, quien comprometa el CI tiene el servidor. La regla: **que la clave solo pueda hacer una cosa**.

**Cómo se usa:** un usuario propio en el servidor:

```bash
sudo useradd -m -s /bin/bash deploy
sudo usermod -aG docker deploy
ssh-keygen -t ed25519 -N '' -C 'ci-despliegue' -f deploy_ci # en tu equipo
```

Lo único que la clave podrá ejecutar, validando la orden que llega como texto, `scripts/despliegue-remoto.sh`:

```bash
#!/usr/bin/env bash
# Archivo: scripts/despliegue-remoto.sh
# Lo único que puede ejecutar la clave SSH del CI. La versión llega como texto: se valida
set -euo pipefail

VERSION="${SSH_ORIGINAL_COMMAND:-}"
IMAGEN="${IMAGEN_REGISTRO:?Falta IMAGEN_REGISTRO}"

if [[ ! "$VERSION" =~ ^[0-9a-f]{7,40}$ ]]; then
  echo "✗ Versión no válida" >&2
  exit 1
fi

cd /opt/lab/entrenos-app
docker pull -q "$IMAGEN:$VERSION"
docker tag "$IMAGEN:$VERSION" "entrenos:$VERSION" # con esta etiqueta, desplegar.sh no reconstruye
bash scripts/desplegar.sh "$VERSION"
```

En `/home/deploy/.ssh/authorized_keys`, la clave pública con la orden forzada y `restrict`:

```text
command="IMAGEN_REGISTRO=ghcr.io/tu-usuario/entrenos /opt/entrenos-app/scripts/despliegue-remoto.sh",restrict ssh-ed25519 AAAA… ci-despliegue
```

`desplegar.sh` usa `sudo` para Nginx; solo eso, en `/etc/sudoers.d/deploy-entrenos`:

```text
deploy ALL=(root) NOPASSWD: /usr/bin/tee /etc/nginx/entrenos-activo.conf, /usr/sbin/nginx -t -q, /usr/bin/systemctl reload nginx
```

- **`publicar-estaticos.sh` usaba `sudo cp -r`,** que equivale a escribir en todo el disco: haz a `deploy` dueño de `/var/www/entrenos` y quita esos `sudo`.

Intentando abusar de la clave:

```text
cat /opt/lab/entrenos-app/.env       ✗ Versión no válida
id                                   ✗ Versión no válida
abc1234; id                          ✗ Versión no válida
abc1234 && cat /etc/passwd           ✗ Versión no válida
$(id)                                ✗ Versión no válida
../../etc/passwd                     ✗ Versión no válida
sesión sin orden                     ✗ Versión no válida
reenvío de puerto a MongoDB          open failed: administratively prohibited
```

También hay que comprobar **a quién** te conectas: guarda la huella y deja activa la comprobación:

```bash
ssh-keyscan -t ed25519 tu-servidor.com # compárala con la del propio servidor antes de confiar
```

Con una huella que no coincide, se cortó antes de enviar nada:

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
Host key verification failed.
```

<Callout type="risk">

- **El grupo `docker` equivale casi a `root`:** solo lo impide aquí la orden forzada, por eso `restrict` y un `deploy` que no es tu usuario. Valida la versión (`SSH_ORIGINAL_COMMAND` lo escribe quien se conecta; la _regex_ rechazó `abc1234; id`) y nunca `eval`.
- **Nunca `StrictHostKeyChecking=no`:** desactiva justo la protección que acabas de ver. Y rota la clave si dudas: el CI es otro sitio donde vive.
- **El puerto SSH queda abierto** (los _runners_ no tienen IP fija): solo claves (A4). En una nube, OIDC con _tokens_ de un _job_.

</Callout>

## Paso 3: el job de despliegue

**Qué es:** **una imagen por _commit_** que se publica en GHCR, y el servidor solo la descarga.

**Cómo se usa:** en `.github/workflows/ci.yml`:

```yaml
  desplegar:
    needs: [verificar, e2e] # solo lo que ha pasado todo
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    concurrency:
      group: produccion # de uno en uno, sin cancelar uno a medias
    environment: produccion
    permissions:
      contents: read
      packages: write # publicar la imagen en GHCR
    env:
      IMAGEN: ghcr.io/${{ github.repository_owner }}/entrenos
      VERSION: ${{ github.sha }}
      APP_HOSTNAME: ${{ vars.APP_HOSTNAME }}
      VPS_HOST: ${{ vars.VPS_HOST }}
    steps:
      - uses: actions/checkout@v7
      - name: Entrar en GHCR
        run: printf '%s' "$TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
        env:
          TOKEN: ${{ secrets.GITHUB_TOKEN }}
      - name: Construir y publicar la imagen
        run: |
          docker build -q -t "$IMAGEN:$VERSION" \
            --build-arg APP_VERSION="$VERSION" --build-arg APP_HOSTNAME="$APP_HOSTNAME" .
          docker push -q "$IMAGEN:$VERSION"
      - name: Preparar SSH
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$CLAVE" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          printf '%s\n' "$HUELLA" > ~/.ssh/known_hosts
        env:
          CLAVE: ${{ secrets.VPS_SSH_KEY }}
          HUELLA: ${{ secrets.VPS_KNOWN_HOSTS }}
      - name: Desplegar
        run: ssh "deploy@$VPS_HOST" "$VERSION"
```

- **`needs`:** solo se despliega lo que pasó `verificar` y `e2e`. **`if`:** solo en `push` a `main` (en una rama y en una PR no se ejecutó).
- **`$VERSION`, no `latest`:** sabes qué hay en producción y puedes volver a cualquiera; una etiqueta reutilizada desplegó una imagen vieja en A6.3.
- **`concurrency`** despliega dos _merges_ en orden, sin `cancel-in-progress`, que cortaría uno a medias. Las variables van por `env`, nunca `${{ }}` dentro de un `run`.

En GitHub, los secretos `VPS_SSH_KEY` (la clave privada) y `VPS_KNOWN_HOSTS` (la huella), y las variables `VPS_HOST` y `APP_HOSTNAME`.

**La primera vez rompió el _build_,** por el `prepare` de A7.2:

```text
RUN npm ci --omit=dev
process "/bin/sh -c npm ci --omit=dev" did not complete successfully: exit code: 127
```

- **`npm ci` ejecuta `prepare`, que llama a `lefthook`,** una dependencia de desarrollo que `--omit=dev` no instala; `--ignore-scripts` solo trasladó el fallo a la etapa sin `.git`. El _hook_, opcional:

```json
"prepare": "lefthook install || true"
```

El canal completo:

```text
✅  Success - Main Construir y publicar la imagen [29.1s]
✅  Success - Main Preparar SSH [0.1s]
== 1. Imagen entrenos:3de70a6cd0c47fb1eefa85544ba9eab3a427f1f3
== 2. Levantar blue junto a green, que sigue atendiendo
== 3. Publicar los estáticos, antes de que un HTML nuevo los pida
✓ 39 archivos en /var/www/entrenos/_astro
== 4. Cambiar Nginx a blue
== 5. Drenar green y dejarla parada para volver atrás
✓ 3de70a6… en producción (blue). Para volver atrás: bash scripts/volver.sh
✅  Success - Main Desplegar [19.0s]
🏁  Job succeeded
```

<Callout type="risk">

- **Probado con `act` y un registro local,** sin `docker login`: **GHCR, `packages: write`, `environment` y `concurrency` no se han probado** (`act` ignora los dos últimos). Con imagen privada, el servidor necesita su `docker login` de solo lectura.
- **`docker/login-action` y `docker/build-push-action`** hacen lo mismo con caché; aquí, comandos directos porque se pudieron probar. Los 29 s eran con capas ya creadas, y el registro crece: limpia.
- **Durante el cambio conviven dos versiones:** un cambio de esquema debe ser compatible con ambas (A4).

</Callout>

## Paso 4: lo que importa, los fallos

**Qué es:** comprobar que ningún despliegue, bueno o malo, deja a nadie sin servicio.

**Cómo se usa:** una sonda a `/api/health` cada 0,2 s durante cuatro despliegues:

```text
Despliegue bueno      22 s   99 sondas    todas 200   a64h → 3de70a6…
Despliegue roto       34 s   145 sondas   todas 200   siguió 3de70a6…
Versión siguiente     21 s   94 sondas    todas 200   3de70a6… → 305652e…
Vuelta atrás          19 s   85 sondas    todas 200   305652e… → 3de70a6…
```

- **423 sondas, ninguna fallida.** Con una versión cuyo `/api/health` daba 503:

```text
== 2. Levantar green junto a blue, que sigue atendiendo
✗ green no está sana. blue sigue atendiendo: nadie ha notado nada
❌  Failure - Main Desplegar [32.9s]
🏁  Job failed
```

- **La versión rota nunca recibió tráfico** y el CI se puso en rojo para avisarte: el trabajo de A4 dando fruto.
- **Otra prueba, sin querer:** `deploy` no confiaba en el certificado del laboratorio y la comprobación final falló **tras** cambiar Nginx:

```text
== 4. Cambiar Nginx a blue
✗ https://academy.entrenos.test no sirve 3de70a6…: vuelvo a green
```

- **Volvió solo a la anterior,** con las 189 sondas en 200.

**Volver atrás** es desplegar el _commit_ anterior:

```bash
ssh -i deploy_ci deploy@tu-servidor.com 3de70a6cd0c47fb1eefa85544ba9eab3a427f1f3
```

- **19,1 s, sin reconstruir.** O revierte el _commit_ en Git para que el CI lo despliegue y `main` quede bien; si no, el siguiente _merge_ traerá lo que retiraste.

<Callout type="risk">

- **Un `/api/health` que siempre da 200 no protege nada,** y uno que comprueba MongoDB tampoco ve un error en `/estadisticas`: E2E y las alertas de A6.4.
- **Un _job_ en rojo tras desplegar** puede haber cambiado algo: mira la versión activa antes de actuar.
- **15 de los 19 s son drenaje:** con peticiones largas, más. Y practica la vuelta atrás antes de un incidente.

</Callout>

## Paso 5: entornos y aprobaciones

**Qué es:** un **entorno** es un destino con sus reglas, usado con `environment: produccion` y configurado en **Settings → Environments**.

**Cómo se usa:**

- **Revisores obligatorios** (el _job_ espera la aprobación, sin recibir antes los secretos), **temporizador**, **ramas permitidas** (solo `main`) y **secretos del entorno**, visibles solo para sus _jobs_: la clave del servidor va aquí.
- **Depende del plan:** en Free, revisores y secretos de entorno solo en repositorios públicos. Nada de esto se ha probado aquí.
- **Aprobar a mano,** para un equipo de una persona con buenos tests, casi nunca compensa: se aprueba sin mirar. Sirve donde un error es muy caro.

## Paso 6: versiones con significado

**Qué es:** el **versionado semántico** (`MAYOR.MENOR.PARCHE`) comunica qué cambió, que un _hash_ no dice.

| Cambio                       | Sube   | Ejemplo           |
| ---------------------------- | ------ | ----------------- |
| Corrige un error, compatible | PARCHE | `0.0.1` → `0.0.2` |
| Añade algo, compatible       | MENOR  | `0.0.2` → `0.1.0` |
| Rompe algo que funcionaba    | MAYOR  | `0.1.0` → `1.0.0` |

**Cómo se usa:** en `0.y.z` todo puede cambiar; `1.0.0` promete estabilidad. Con npm:

```bash
npm version patch -m "version: %s"
npm version minor -m "version: %s"
```

```text
v0.0.2
v0.1.0
```

- **Cada orden actualiza `package.json`,** crea un _commit_ y la etiqueta.

Para automatizarlo, los _commits_ siguen **Conventional Commits**:

```text
fix: los minutos negativos ya no se aceptan        → PARCHE
feat: exportar entrenos a CSV                      → MENOR
feat!: la API pasa a devolver fechas en UTC        → MAYOR
docs: corregir el README                           → nada
```

**release-please** lee esos _commits_ y mantiene una PR con la siguiente versión y el `CHANGELOG`; al mezclarla, crea la etiqueta y la _release_. Necesita `contents: write` y `pull-requests: write`:

```yaml
- uses: googleapis/release-please-action@v4
  with:
    release-type: node
```

- **No se ha podido probar** (necesita la API de GitHub), y lo que crea con `GITHUB_TOKEN` no dispara otros _workflows_: para que su PR pase tu CI, otro _token_.

<Callout type="risk">

- **Una app no siempre necesita versiones semánticas:** son una promesa a quien te usa; si nadie depende de ti, el _commit_ basta.
- **Exige disciplina:** sin el formato, release-please no encuentra nada (`chore` y `docs` no cuentan), y `feat!` en `0.y.z` empuja a `1.0.0`.
- **Una etiqueta publicada no se reescribe:** si te equivocas, publica la siguiente.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

Automatiza el despliegue de A4 para que cada _merge_ a `main` despliegue en tu VPS tras pasar CI.

</Callout>

Solución, con los Pasos 2 y 3:

1. Usuario `deploy`, `despliegue-remoto.sh`, `authorized_keys`, `sudoers`, y `publicar-estaticos.sh` sin `sudo`.
2. `"prepare": "lefthook install || true"`.
3. El _job_ `desplegar` en `ci.yml`.
4. Los secretos y las variables en GitHub.
5. Una PR con un cambio visible. Mézclala, y comprueba la versión:

```bash
curl -s https://academy.tudominio.com/api/health
```

```json
{ "ok": true, "version": "3de70a6cd0c47fb1eefa85544ba9eab3a427f1f3" }
```

6. Prueba la clave: `ssh -i deploy_ci deploy@tu-servidor.com 'cat .env'` debe responder `✗ Versión no válida`.
7. Provoca un fallo: una versión con `/api/health` en 503 debe poner el _job_ en rojo, sin que cambie la versión activa.

- **El canal entero se ejecutó con `act`** (148 s de `verificar` y `e2e`, unos 20 de despliegue). El primer intento real en GitHub es parte del ejercicio: GHCR, `environment` y `concurrency` están sin probar.
- **Empieza por un entorno que no sea importante,** si lo tienes.

<Callout type="mastery">

Desplegar es mezclar una PR, nada más: lo que pasa el CI llega solo, con una imagen por _commit_ y una clave que no sirve para otra cosa. Si la versión está rota, no recibe tráfico, y volver atrás son 19 s. Sabes qué decidir a mano y qué no, y qué significa cada número de una versión.

</Callout>

## Resumen

- **Vercel** da vistas previas y producción desde `main`, sin esperar a tu CI: regla de A7.2.
- **Clave restringida:** orden forzada, `restrict` y versión validada; `abc1234; id` y `cat .env` fallaron.
- **`known_hosts`:** una huella falsa cortó la conexión. Nunca `StrictHostKeyChecking=no`.
- **Imagen por _commit_, no `latest`;** `prepare` con `|| true` o `docker build` falla (127).
- **423 sondas sin fallos;** una versión rota no recibió tráfico y el CI se puso en rojo.
- **Volver atrás:** 19 s sin reconstruir.
- **Entornos** según tu plan; **`MAYOR.MENOR.PARCHE`**, Conventional Commits y release-please (sin probar).
