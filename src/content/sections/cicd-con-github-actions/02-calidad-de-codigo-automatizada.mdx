Sin herramientas, una revisión de código acaba hablando de comillas y variables sin usar en vez de lógica. Lo que una máquina puede comprobar, que lo compruebe una máquina. Aquí pones formato y _lint_ automáticos en cada _commit_, los compruebas otra vez en CI y proteges `main` para que no entre nada que no haya pasado.

**Requisitos:** el _workflow_ de A7.1.

## Paso 1: Prettier se encarga del estilo

**Qué es:** dos herramientas, dos trabajos: **Prettier** decide cómo se ve el código y **ESLint** busca errores. La documentación de Prettier aconseja no mezclarlos.

**Cómo se usa:**

```bash
npm install -D prettier prettier-plugin-astro
```

`.prettierrc`:

```json
{
  "printWidth": 100,
  "plugins": ["prettier-plugin-astro"],
  "overrides": [{ "files": "*.astro", "options": { "parser": "astro" } }]
}
```

`.prettierignore`:

```text
dist
.astro
node_modules
coverage
package-lock.json
```

En `scripts` de `package.json`:

```json
"format": "prettier --write .",
"format:check": "prettier --check .",
```

- **`--write` cambia los archivos; `--check` solo avisa,** lo que necesita un CI.

```bash
npm run format:check
```

```text
[warn] Code style issues found in 67 files. Run Prettier with --write to fix.
```

- **67 archivos, que `npm run format` arregla en segundos.** En un _commit_ propio: tocó 95 archivos y sería imposible revisarlo junto a otra cosa.

<Callout type="risk">

- **Una versión nueva de Prettier puede reformatearlo todo:** `package-lock.json` la fija, siempre que se instale con `npm ci`.
- **Sin `.prettierignore`,** reformatearía `dist`, `.astro` o `node_modules`.

</Callout>

## Paso 2: ESLint busca errores

**Qué es:** reglas que señalan código probablemente erróneo, más allá del estilo.

**Cómo se usa:**

```bash
npm install -D eslint @eslint/js typescript-eslint eslint-plugin-astro eslint-plugin-react-hooks globals eslint-config-prettier
```

`eslint.config.js`:

```js
// Archivo: eslint.config.js
import js from "@eslint/js";
import prettier from "eslint-config-prettier/flat";
import astro from "eslint-plugin-astro";
import reactHooks from "eslint-plugin-react-hooks";
import { defineConfig } from "eslint/config";
import globals from "globals";
import tseslint from "typescript-eslint";

export default defineConfig(
  { ignores: ["dist", ".astro", "node_modules", "coverage"] },
  js.configs.recommended,
  tseslint.configs.recommended,
  astro.configs.recommended,
  {
    files: ["**/*.tsx"],
    plugins: { "react-hooks": reactHooks },
    rules: reactHooks.configs.recommended.rules,
  },
  { languageOptions: { globals: { ...globals.browser, ...globals.node } } },
  prettier, // el último: apaga las reglas de estilo que chocarían con Prettier
);
```

- **`"lint": "eslint ."` en `scripts`.** `eslint-config-prettier` solo apaga las reglas que chocan con Prettier, por eso va la última. Para comprobarlo:

```bash
npx eslint-config-prettier src/lib/ritmo.ts
```

```text
No rules that are unnecessary or conflict with Prettier were found.
```

En 1,6 s, un error real:

```text
src/components/Entrenos.tsx
  34:5  error  Error: Calling setState synchronously within an effect can trigger cascading renders
```

- **La regla acierta en general,** pero aquí es deliberado: la fecha solo existe en el navegador. Si discrepas, por escrito y con motivo:

```tsx
// eslint-disable-next-line react-hooks/set-state-in-effect -- la fecha solo existe en el navegador
setFormulario((f) => ({ ...f, fecha: f.fecha || hoy() }));
```

El _lint_ con tipos de `typescript-eslint` (`recommendedTypeChecked`) encuentra, por ejemplo, promesas sin esperar:

```text
                  Tiempo    Memoria    Problemas
Sin tipos         1,6 s     378 MB     1
Con tipos         10,2 s    1169 MB    unos 200
```

- **Seis veces más lento,** con 173 `no-unsafe-*` y 7 `no-misused-promises` por funciones `async` en eventos, normal en React. No compensa entero; una regla concreta como `no-floating-promises` (aquí, nada) puede ir en CI.

<Callout type="risk">

- **Un `eslint-disable` sin motivo es una deuda:** `-next-line`, con la regla y el porqué, nunca en todo el archivo.
- **Con cientos de avisos nadie los lee:** en un proyecto grande, por partes o en `warn`. Y `--fix` cambia tu código: revísalo.
- **ESLint no sustituye a `astro check`:** uno ve `sinUsar`, el otro un tipo incorrecto. Biome hace los dos trabajos (no medido).

</Callout>

## Paso 3: un hook antes de cada commit

**Qué es:** un **_hook_** es un programa que Git ejecuta en un momento concreto. `pre-commit` corre antes de guardar y, si falla, cancela el _commit_. **lefthook** lo define en un archivo compartido.

**Cómo se usa:**

```bash
npm install -D lefthook
```

`lefthook.yml`:

```yaml
# Archivo: lefthook.yml
pre-commit:
  piped: true # uno detrás de otro: los dos pueden escribir en el mismo archivo
  jobs:
    - name: eslint
      glob: "*.{js,mjs,ts,tsx,astro}"
      run: npx eslint --fix {staged_files}
      stage_fixed: true
    - name: prettier
      glob: "*.{js,mjs,ts,tsx,astro,css,md,json,yml}"
      run: npx prettier --write --ignore-unknown {staged_files}
      stage_fixed: true
```

- **`"prepare": "lefthook install || true"`** lo instala con `npm install`; sin `|| true`, `docker build` falla porque la imagen no tiene `.git` ni dependencias de desarrollo (A7.4).
- **`{staged_files}`** procesa solo lo que guardas (0,84 s frente a 1,83 del proyecto), **`stage_fixed`** añade lo corregido y **`piped`** los ejecuta en orden, porque los dos escriben en el mismo archivo.

Con código feo, el _hook_ lo corrigió:

```text
En el archivo:  export   const   doble=(n:number)=>{return n*2}

En el commit:   export const doble = (n: number) => {
                  return n * 2;
                };
```

Con un error que no se corrige solo, lo paró:

```text
  1:29  error  'sinUsar' is assigned a value but never used  @typescript-eslint/no-unused-vars
✖ 1 problem (1 error, 0 warnings)
```

Los casos difíciles:

| Caso                           | Resultado                                           |
| ------------------------------ | --------------------------------------------------- |
| Parte del archivo sin preparar | No entró en el _commit_, y siguió en tu disco       |
| Borrar un archivo              | Se omitió la herramienta: «no files for inspection» |
| Nombre con espacios            | Funcionó                                            |
| `npm ci` en un clon nuevo      | Instaló el _hook_                                   |

- **El primero importa:** un cambio sin preparar (`b = 999`) no se coló aunque el archivo se corrigió.

<Callout type="risk">

- **Un _hook_ es opcional:** `git commit --no-verify` y `LEFTHOOK=0 git commit` lo saltan, y sin `npm install` (o con `--ignore-scripts`) no hay _hook_. Comodidad, no garantía.
- **Un _hook_ lento se salta:** por eso los tests y `astro check` quedan para CI.
- **`src/**/_.js`no incluye`src/file.js`** (`\*\*`exige una carpeta);`_.ts`funcionó en subcarpetas.`lint-staged`y`husky` son la alternativa: elige una.

</Callout>

## Paso 4: el CI vuelve a comprobarlo

**Qué es:** lo que el _hook_ no garantiza, lo garantiza el CI.

**Cómo se usa:** en `.github/workflows/ci.yml`, tras `npm ci`, **primero lo más rápido**:

```yaml
- run: npm ci
- run: npm run format:check
- run: npm run lint
- run: npm run check
- run: npm run test:run
- run: npm run build
```

```text
✅  Success - Main npm ci [34.2s]
✅  Success - Main npm run format:check [0.8s]
✅  Success - Main npm run lint [1.4s]
✅  Success - Main npm run check [4.6s]
✅  Success - Main npm run test:run [7.6s]
✅  Success - Main npm run build [1.6s]
🏁  Job succeeded
```

Saltándose el _hook_ con `--no-verify`, en dos ramas:

```text
Formato feo:      ❌ Failure - npm run format:check [0.9s] · 22 s en total
Variable sin uso: ✅ format:check · ❌ Failure - npm run lint [1.5s] · 23 s en total
```

- **El CI atrapó los dos en unos 20 s:** el _hook_ ahorra el viaje y el CI no se salta.

<Callout type="risk">

- **En CI, `--check`, nunca `--write`:** corregiría en la máquina del CI y saldría verde sin cambiar tu repositorio.
- **`prepare` también corre en CI** (`lefthook install`, sin problema); si un día falla, `LEFTHOOK=0`.
- **Las versiones que cambian el resultado,** fijadas por `package-lock.json` con `npm ci`.

</Callout>

## Paso 5: main no acepta lo que no pasa

**Qué es:** una regla de GitHub que impide fusionar una PR en rojo. **No se ha podido probar** (requiere un repositorio real): sale de su documentación, y debes comprobarlo en el tuyo. Hay **reglas de protección de rama** (una por rama) y **rulesets** (varios a la vez, más recientes): usa _rulesets_.

**Cómo se usa:** **Settings → Rules → Rulesets → New ruleset → New branch ruleset**:

1. **Enforcement status:** _Active_.
2. **Target branches:** la rama por defecto.
3. **Require a pull request before merging.**
4. **Require status checks to pass:** añade `verificar`, el nombre del _job_ de tu _workflow_.
5. **Block force pushes.**

- **_Require branches to be up to date before merging_** exige lo último de `main`: más actualizaciones, pero dos PR correctas por separado no rompen `main` al unirse.

<Callout type="risk">

- **Un administrador puede saltárselo:** en las reglas clásicas, salvo _Do not allow bypassing the above settings_; en _rulesets_, deja vacía la _bypass list_.
- **Una comprobación obligatoria que nunca llega bloquea para siempre:** con filtros de `paths`, la PR queda en _Pending_. Nombres de _job_ únicos, y pruébala con una PR tranquila antes de una urgencia.
- **Depende del plan:** no se ha podido confirmar para repositorios privados del plan Free.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

Configura ESLint, Prettier y un _hook_ de _pre-commit_; protege `main` para exigir CI verde.

</Callout>

Solución, con los Pasos 1 a 5:

1. `npm run format` en un _commit_ propio.
2. `npm run lint` hasta llegar a 0 errores, y cada `eslint-disable` con su motivo.
3. `lefthook.yml` y `prepare`.
4. Los dos pasos en `ci.yml`, antes que `check`.
5. El _ruleset_ de `main` con `verificar`.

Las tres pruebas:

```bash
# 1. El hook corrige
echo 'export   const c=1' > src/lib/prueba.ts
git add src/lib/prueba.ts && git commit -m "prueba"

# 2. El hook frena
echo 'export function f() { const sinUsar = 1; return 2; }' > src/lib/prueba.ts
git add src/lib/prueba.ts && git commit -m "prueba"

# 3. El CI frena lo que se salta el hook
git switch -c prueba/sin-hook
git add -A && git commit -m "sin hook" --no-verify
git push -u origin prueba/sin-hook
```

- **La última PR debe quedar en rojo y con el botón de fusionar bloqueado.** Las dos primeras se midieron aquí y el CI de la tercera con `act`; el botón bloqueado, **no**: compruébalo tú, es lo que demuestra la regla. Después, borra la rama y `src/lib/prueba.ts`.

<Callout type="mastery">

El formato y el _lint_ nunca se discuten en una revisión: el _hook_ corrige antes de guardar, el CI lo comprueba otra vez, y la protección de rama impide fusionar lo que no ha pasado. Sabes que cada barrera falla de forma distinta, que `--no-verify` existe, y por qué lo que garantiza algo es el servidor y no tu equipo.

</Callout>

## Resumen

- **Prettier** da el formato (67 archivos, en un _commit_ propio); **ESLint** busca errores.
- **`eslint-config-prettier`,** la última.
- **Sin tipos:** 1,6 s y 378 MB; **con tipos:** 10,2 s, 1169 MB y unos 200 problemas, casi todo ruido aquí.
- **`lefthook`** corrige lo preparado en 0,84 s sin colar lo no preparado.
- **`--no-verify` y `LEFTHOOK=0`** lo saltan: comodidad, no garantía.
- **El CI atrapó** formato y _lint_ saltados en unos 20 s.
- **`verificar` obligatorio en un _ruleset_:** compruébalo con una PR real.
