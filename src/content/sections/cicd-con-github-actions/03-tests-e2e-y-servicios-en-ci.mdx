Los **E2E** comprueban lo que hace un usuario: registrarse, guardar un entreno y verlo al recargar (I8). Son los más parecidos a la realidad y los más caros, porque necesitan navegador, servidor y base de datos a la vez. Aquí los llevas al CI con MongoDB real, guardas un informe para investigar fallos, usas bien los secretos y pruebas una matriz con dos versiones de Node.

**Requisitos:** el CI de A7.2 y los tests E2E de I8.

## Paso 1: MongoDB como servicio

**Qué es:** un **servicio** es un contenedor que GitHub arranca junto a tu _job_ y destruye al terminar. Better Auth usa transacciones, así que MongoDB debe ser un _replica set_: arrancar con `--replSet` e iniciarlo después.

**Cómo se usa:** `scripts/esperar-mongo.mjs` lo inicia y no continúa hasta que acepte escrituras:

```js
// Archivo: scripts/esperar-mongo.mjs
// Convierte el MongoDB del CI en un replica set de un nodo y espera a que acepte escrituras.
// Better Auth usa transacciones, y un servidor suelto no las admite
import { MongoClient } from "mongodb";

const URI = "mongodb://127.0.0.1:27017/?directConnection=true";
const LIMITE_SEGUNDOS = 60;

for (let segundos = 1; segundos <= LIMITE_SEGUNDOS; segundos++) {
  const cliente = new MongoClient(URI, { serverSelectionTimeoutMS: 1_000 });
  try {
    const admin = cliente.db("admin");
    await admin
      .command({ replSetInitiate: { _id: "rs0", members: [{ _id: 0, host: "127.0.0.1:27017" }] } })
      .catch(() => {}); // ya iniciado: da error y no importa

    const { isWritablePrimary } = await admin.command({ hello: 1 });
    if (isWritablePrimary) {
      console.log(`MongoDB listo como primario tras ${segundos} s`);
      process.exit(0);
    }
  } catch {
    // Todavía no acepta conexiones: se reintenta
  } finally {
    await cliente.close();
  }
  await new Promise((resolver) => setTimeout(resolver, 1_000));
}

console.error(`MongoDB no llegó a primario en ${LIMITE_SEGUNDOS} s`);
process.exit(1);
```

Bajo `verificar`, en `.github/workflows/ci.yml`:

```yaml
  e2e:
    needs: verificar # sin tipos ni tests correctos, no merece la pena abrir un navegador
    runs-on: ubuntu-latest
    timeout-minutes: 20
    services:
      mongo:
        image: mongo:8.2 # una versión fijada: mongo:8 no arranca en kernels recientes
        ports:
          - 27017:27017
        command: --replSet rs0 --bind_ip_all
    env:
      MONGODB_URI: mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true
      MONGODB_DB: entrenos_ci
      BETTER_AUTH_SECRET: ${{ secrets.BETTER_AUTH_SECRET_E2E }}
      BETTER_AUTH_URL: http://localhost:4330
      OBJETIVO_SEMANAL_MINUTOS: 150
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 26
          cache: npm
      - run: npm ci
      - run: node scripts/esperar-mongo.mjs
      - run: node scripts/crear-indices.mjs
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
      - uses: actions/upload-artifact@v7
        if: failure() # solo hace falta para investigar un fallo
        with:
          name: informe-playwright
          path: |
            playwright-report
            test-results
          retention-days: 7
```

- **`needs: verificar`:** solo si los tipos y tests pasan; no merece la pena abrir un navegador antes.
- **`image: mongo:8.2`** es una versión exacta (A7.1) y **`command`** pasa los argumentos a `mongod`.
- **`ports`:** el _job_ corre en el _runner_, así que llega por `127.0.0.1`; **`directConnection=true`** habla con ese nodo sin descubrir el resto.

En `playwright.config.ts`, un informe para abrir después:

```ts
reporter: [["list"], ["html", { open: "never" }]],
forbidOnly: !!process.env.CI, // un test.only olvidado no pasa en CI
failOnFlakyTests: !!process.env.CI, // un test inestable no pasa como bueno
```

Añade `playwright-report` y `test-results` a `.gitignore`. El resultado:

```text
✅  Success - Main npm ci [21.0s]
MongoDB listo como primario tras 2 s
✅  Success - Main node scripts/esperar-mongo.mjs [1.6s]
✅  Success - Main node scripts/crear-indices.mjs [0.2s]
✅  Success - Main npx playwright install --with-deps chromium [55.9s]
4 passed (6.8s)
✅  Success - Main npx playwright test [7.4s]
🏁  Job succeeded
```

- **148 s en total,** con `verificar` primero. Instalar el navegador costó **casi ocho veces** más que los tests.

<Callout type="risk">

- **No se ejecutó exactamente así:** `act` rechaza `command` en `services` (`Unknown Property command`), y se usó una imagen derivada con el comando incorporado. Comprueba `command` en tu primera ejecución real. Y solo hay servicios en _runners_ Linux.
- **El _replica set_ debe iniciarse,** y arrancado no es preparado: sin ese paso, `MongoServerError: not primary` en 24 s; por eso el _script_ reintenta 60 s.
- **Nunca E2E contra una base real:** `playwright.config.ts` rechaza cualquier URI no local.

</Callout>

## Paso 2: investigar un fallo que no ves

**Qué es:** en CI no puedes mirar el navegador, y lo que no guardes se pierde con la máquina. El último paso sube un **artefacto** si algo falla, y `trace: "retain-on-failure"` (I8) guarda la traza.

**Cómo se usa:** con un fallo provocado, la salida:

```text
Error: fallo a propósito
Expected: 3
Received: 2
> 6 |   expect(1 + 1, "fallo a propósito").toBe(3);
```

Lo que quedó en el _runner_:

```text
2.0M  playwright-report
40K   test-results
playwright-report/index.html
playwright-report/data/….zip    ← la traza
playwright-report/data/….md     ← el contexto del error
playwright-report/trace/…
```

Con el artefacto descargado de la pestaña de la ejecución:

```bash
npx playwright show-report playwright-report
```

- **El informe muestra la traza paso a paso:** capturas, red y consola. Solo con el archivo:

```bash
npx playwright show-trace trace.zip
```

<Callout type="risk">

- **La subida no se ha comprobado:** se generaron los archivos y `upload-artifact` los encontró, pero con `act` falló (`Unexpected end of JSON input`) tras 80 s de reintentos. Verifícalo en tu primer fallo real.
- **Las trazas pueden llevar datos** (capturas, peticiones): por eso `retention-days: 7` en vez de 90.
- **`if: failure()` no corre si se cancela** (`if: ${{ !cancelled() }}` para siempre), y en una matriz cada artefacto necesita su nombre.

</Callout>

## Paso 3: secretos y variables

**Qué es:** los **secretos** se crean en **Settings → Secrets and variables → Actions → New repository secret** y se usan como `${{ secrets.BETTER_AUTH_SECRET_E2E }}`; las **variables** (`${{ vars.ENTORNO }}`), en la pestaña de al lado, son para lo que no es secreto.

**Cómo se usa:** un valor solo para pruebas, nunca el de producción. O generado en cada ejecución, sin guardarlo (no medido):

```yaml
- run: echo "BETTER_AUTH_SECRET=$(openssl rand -base64 32)" >> "$GITHUB_ENV"
```

Un secreto de prueba en los registros:

```yaml
- run: echo "directo $SECRETO"
- run: echo "en base64 $(printf %s "$SECRETO" | base64)"
- run: echo "invertido $(printf %s "$SECRETO" | rev)"
```

```text
directo ***
en base64 c2VjcmV0by1kZS1wcnVlYmEtMTIz
invertido 321-abeurp-ed-oterces
```

- **El enmascarado solo busca el texto exacto:** cualquier transformación (base64, un `console.log`, un error) lo deja al descubierto.
- **Un secreto que no existe es texto vacío, sin aviso:**

```text
[WebServer] - BETTER_AUTH_SECRET is missing
Error: Timed out waiting 120000ms from config.webServer.
```

- **El servidor no arrancó y el _job_ esperó 2 minutos.**

<Callout type="risk">

- **Las PR de un _fork_ y Dependabot no reciben secretos** (salvo `GITHUB_TOKEN`; Dependabot tiene su almacén): otro motivo para generarlo en cada ejecución. Y nunca `pull_request_target` para dárselos a una PR ajena.
- **Si se filtra, cámbialo:** borrar el registro no basta (A5.5).
- **Pásalos por `env`,** como recomienda GitHub, no dentro del comando.

</Callout>

## Paso 4: matrices

**Qué es:** una **matriz** repite un _job_ con distintos valores, por ejemplo la versión de Node de hoy y la siguiente, antes de actualizar.

**Cómo se usa:**

```yaml
verificar:
  strategy:
    fail-fast: false
    matrix:
      node: [24, 26]
  steps:
    - uses: actions/setup-node@v7
      with:
        node-version: ${{ matrix.node }}
        cache: npm
```

```text
probar-1: v24.22.2 · Tests 71 passed (71) · Job succeeded
probar-2: v26.13.0 · Tests 71 passed (71) · Job succeeded
```

- **Los dos en paralelo, en 56 s.** `fail-fast: false` evita que un fallo cancele al otro, y así sabes si fallan los dos.

<Callout type="risk">

- **Multiplica el coste:** no para E2E, y con una sola versión de producción no hace falta. Manda la del `Dockerfile`.
- **La comprobación obligatoria cambia de nombre por cada valor:** revisa el _ruleset_ de A7.2 (no comprobado en GitHub).
- **Dos _jobs_ en la misma VM compiten por memoria** (A7.1); en GitHub, cada _job_ tiene su máquina.

</Callout>

## Paso 5: cuatro resultados engañosos

**Qué es:** un _job_ de E2E puede mentir en las dos direcciones.

**Cómo se usa:** **verde sin comprobar,** con un `test.only` olvidado:

```text
Sin forbidOnly:  2 passed, en lugar de 4 · Job succeeded
Con forbidOnly:  Error: item focused with '.only' is not allowed · Job failed
```

- **Sin `forbidOnly`, la mitad de los tests no corrió** y nadie se enteró. Mira el número, no el color.

**Verde con un fallo:** con `retries: 1`, un test inestable que pasa a la segunda:

```text
Sin failOnFlakyTests:  1 flaky · 3 passed · Job succeeded
Con failOnFlakyTests:  1 flaky · 3 passed · Failure · Job failed
```

- **No es teórico:** con la máquina cargada, `guardar un entreno` agotó sus 5 s y pasó al reintentar. Un test inestable es un error que aún no entiendes, quizá una carrera que tus usuarios sufren. `failOnFlakyTests` lo convierte en fallo; si es demasiado estricto, apágalo y revisa los `flaky` cada semana, pero míralos.
- **Rojo por algo ajeno:** `mongo:8` (8.3.13) no arranca en un kernel 7.0 (`MongoDB cannot start`). Si tu código no cambió, mira qué cambió alrededor; por eso `mongo:8.2`.
- **Rojo por el secreto:** los 2 minutos del Paso 3. Lee siempre el primer error, no el último.

<Callout type="risk">

- **Más `retries` no arregla nada:** convierte un fallo intermitente en lentitud. `workers: 1` en CI por estabilidad, y `--shard=1/4` en una matriz si hay muchos tests.
- **`astro dev` no es producción:** estos E2E no prueban tu _build_ final.
- **`timeout-minutes`** evita que un _job_ colgado gaste minutos.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

Añade el _job_ E2E a tu CI con MongoDB como servicio.

</Callout>

Solución, con el Paso 1:

1. `scripts/esperar-mongo.mjs`.
2. El _job_ `e2e` en `ci.yml`.
3. `forbidOnly`, `failOnFlakyTests` y el _reporter_ HTML en `playwright.config.ts`.
4. El secreto `BETTER_AUTH_SECRET_E2E` en GitHub.
5. Una PR, y comprueba estas tres cosas, que aquí **no se han podido medir**: que el servicio arranca con `command`, que el _job_ pasa en un _runner_ real, y que un test que falla deja el artefacto.

Para la última, en un test de una rama de prueba:

```ts
expect(1 + 1, "fallo a propósito").toBe(3);
```

- **Descarga el artefacto, abre el informe y borra la línea.** Después, añade `e2e` a las comprobaciones obligatorias del _ruleset_ de A7.2.

En este laboratorio, con `act`:

```text
Verde:             verificar y e2e, 148 s, 4 tests en Chromium
Fallo provocado:   1 failed, 3 passed · informe de 2 MB con su traza
```

<Callout type="mastery">

Tu CI monta una base de datos y un navegador reales para comprobar lo que hace un usuario. Si falla, tienes un informe que investigar. Sabes que el enmascarado solo busca el texto exacto, que un secreto ausente es texto vacío, y que `test.only` y los reintentos pueden dejar un verde falso. Lees el número de tests, no solo el color.

</Callout>

## Resumen

- **`services`** arranca MongoDB con versión fijada; el _replica set_ se inicia con un _script_ (sin él, `not primary`).
- **`needs`:** E2E tras `verificar`. Chromium costó 56 s y los tests 7.
- **Artefactos si falla:** informe de 2 MB con traza; su subida no se probó con `act`.
- **`\***` solo tapa el texto exacto\*\* (en base64 salió en claro); un secreto ausente es vacío.
- **Forks y Dependabot** no reciben secretos.
- **Matriz:** Node 24 y 26, 71 tests cada una, con `fail-fast: false`.
- **`forbidOnly`** y **`failOnFlakyTests`** evitan verdes falsos.
