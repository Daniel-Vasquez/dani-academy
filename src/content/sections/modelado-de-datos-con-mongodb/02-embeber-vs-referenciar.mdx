Cada relación se guarda **embebida** (los datos relacionados dentro del mismo documento) o **referenciada** (en documentos aparte, con un campo que apunta al otro, sin que MongoDB lo compruebe). La buena es la que sirve a tus patrones de acceso (I4.1) sin documentos que crecen sin límite. Aquí mides las dos, el coste de un array sin límite y el de un `$lookup`.

**Requisitos:** el proyecto `mongo-academy` con `src/i4/catalogo.ts` (I4.1).

## Paso 1: el mismo progreso, embebido y referenciado

**Qué es:** dos formas de guardar lo leído. **A, embeber:** un documento por usuario y curso con las secciones en un array (B5.4). **B, referenciar:** un documento por sección leída, con `userId`, `cursoId` y `seccionId`, como `section_progress` en esta plataforma.

**Cómo se usa:** los modelos y sus índices, en `src/i4/02-modelos.ts`:

```ts
// Archivo: src/i4/02-modelos.ts
// Los dos diseños del progreso de lectura, con sus colecciones e índices
import type { ObjectId } from "mongodb";
import { db } from "../db";

/** Opción A (embeber): un documento por usuario y curso, con las secciones leídas dentro */
export interface ProgresoCurso {
  _id?: ObjectId;
  userId: string;
  cursoId: string;
  seccionesLeidas: string[]; // acotado: como mucho, las secciones del curso (≤ 8)
  actualizado: Date;
}

/** Opción B (referenciar): un documento por sección leída (lo que hace la plataforma) */
export interface Lectura {
  _id?: ObjectId;
  userId: string;
  cursoId: string;
  seccionId: string;
  leidaEn: Date;
}

export const progresoA = db.collection<ProgresoCurso>("i4_progreso_a");
export const lecturasB = db.collection<Lectura>("i4_lecturas_b");

export async function crearIndices() {
  await progresoA.createIndex({ userId: 1, cursoId: 1 }, { unique: true });
  await lecturasB.createIndex({ userId: 1, cursoId: 1, seccionId: 1 }, { unique: true });
  await lecturasB.createIndex({ userId: 1, leidaEn: -1 }); // "continuar donde lo dejaste"
}
```

`src/i4/02-sembrar.ts` llena las dos con **los mismos datos**, 2000 usuarios con un tercio de los cursos empezados al azar:

```ts
// Archivo: src/i4/02-sembrar.ts

import { cliente } from "../db";
import { CATALOGO, seccionesDe } from "./catalogo";
import { crearIndices, lecturasB, progresoA, type Lectura, type ProgresoCurso } from "./02-modelos";

const USUARIOS = 2000;

// Generador pseudoaleatorio con semilla: los mismos datos en cada ejecución
let semilla = 42;
const azar = () => ((semilla = (semilla * 1_103_515_245 + 12_345) % 2 ** 31) / 2 ** 31);

await Promise.all([progresoA.drop().catch(() => {}), lecturasB.drop().catch(() => {})]);
await crearIndices();

const docsA: ProgresoCurso[] = [];
const docsB: Lectura[] = [];
const inicio = Date.UTC(2026, 0, 1);

for (let u = 1; u <= USUARIOS; u++) {
  const userId = `u_${String(u).padStart(5, "0")}`;
  for (const curso of CATALOGO) {
    if (azar() > 0.35) continue; // cada usuario empieza un 35 % de los cursos

    if (leidas.length === 0) continue;

    leidas.forEach((seccionId, i) => docsB.push({ userId, cursoId: curso.id, seccionId, leidaEn: fechas[i]! }));
  }
}

await progresoA.insertMany(docsA);
await lecturasB.insertMany(docsB);
console.log(`Sembrado: ${USUARIOS} usuarios · A: ${docsA.length} documentos · B: ${docsB.length} documentos`);
await cliente.close();
```

Compara espacio y patrones en `src/i4/02-comparar.ts`:

```ts
// Archivo: src/i4/02-comparar.ts
// Opción A (embeber) frente a opción B (referenciar): espacio y tiempo de cada patrón de acceso
import type { Collection, Document } from "mongodb";
import { cliente, db } from "../db";
import { CATALOGO, seccionesDe } from "./catalogo";
import { lecturasB, progresoA } from "./02-modelos";

const N = 500;
const kb = (bytes: number) => `${(bytes / 1024).toFixed(0)} KB`;

async function espacio(col: Collection<Document>) {
  const [s] = await col
    .aggregate<{ storageStats: { count: number; size: number; storageSize: number; totalIndexSize: number } }>([
      { $collStats: { storageStats: {} } },
    ])
    .toArray();
  return s!.storageStats;
}

/** Ejecuta `fn` N veces con usuarios y cursos al azar y devuelve la media en ms */
async function medir(fn: (userId: string, cursoId: string, seccionId: string) => Promise<unknown>) {
  const casos = Array.from({ length: N }, (_, i) => {
    const curso = CATALOGO[(i * 7) % CATALOGO.length]!;
    const secciones = seccionesDe(curso);
    return [`u_${String(((i * 37) % 2000) + 1).padStart(5, "0")}`, curso.id, secciones[i % secciones.length]!] as const;
  });
  for (const c of casos.slice(0, 20)) await fn(...c); // calentamiento
  const t = performance.now();
  for (const c of casos) await fn(...c);
  return ((performance.now() - t) / N).toFixed(2).padStart(5);
}

// WiredTiger escribe en disco cada 60 s; fsync fuerza ese punto de control para medir el espacio real
await db.admin().command({ fsync: 1 });
const [a, b] = await Promise.all([espacio(progresoA as never), espacio(lecturasB as never)]);
console.log("Espacio            A (embeber)      B (referenciar)");
console.log(`  documentos       ${String(a.count).padEnd(16)} ${b.count}`);
console.log(`  datos (BSON)     ${kb(a.size).padEnd(16)} ${kb(b.size)}`);
console.log(`  en disco         ${kb(a.storageSize).padEnd(16)} ${kb(b.storageSize)}`);
console.log(`  índices          ${kb(a.totalIndexSize).padEnd(16)} ${kb(b.totalIndexSize)}`);

const ahora = new Date();
const patrones: [string, () => Promise<string>, () => Promise<string>][] = [
  [
    "#1 leídas de un curso",
    () => medir((userId, cursoId) => progresoA.findOne({ userId, cursoId }, { projection: { _id: 0, seccionesLeidas: 1 } })),
    () => medir((userId, cursoId) => lecturasB.find({ userId, cursoId }, { projection: { _id: 0, seccionId: 1 } }).toArray()),
  ],
  [
    "#2 temario (todos los cursos)",
    () => medir((userId) => progresoA.find({ userId }, { projection: { _id: 0, cursoId: 1, seccionesLeidas: 1 } }).toArray()),
    () => medir((userId) => lecturasB.find({ userId }, { projection: { _id: 0, seccionId: 1 } }).toArray()),
  ],
  [
    "#3 marcar como leída",
    () =>
      medir((userId, cursoId, seccionId) =>
        progresoA.updateOne(
          { userId, cursoId },
          { $addToSet: { seccionesLeidas: seccionId }, $set: { actualizado: ahora } },
          { upsert: true },
        ),
      ),
    () =>
      medir((userId, cursoId, seccionId) =>
        lecturasB.updateOne({ userId, cursoId, seccionId }, { $setOnInsert: { leidaEn: ahora } }, { upsert: true }),
      ),
  ],
  [
    "#3 desmarcar",
    () => medir((userId, cursoId, seccionId) => progresoA.updateOne({ userId, cursoId }, { $pull: { seccionesLeidas: seccionId } })),
    () => medir((userId, cursoId, seccionId) => lecturasB.deleteOne({ userId, cursoId, seccionId })),
  ],
];

console.log(`\nTiempo medio (ms, ${N} operaciones)   A        B`);
for (const [nombre, fa, fb] of patrones) {
  console.log(`  ${nombre.padEnd(32)} ${await fa()}    ${await fb()}`);
}

// Un patrón que solo permite B: cada lectura tiene su fecha
const continuar = await medir((userId) => lecturasB.find({ userId }).sort({ leidaEn: -1 }).limit(1).next());
console.log(`  ${"continuar donde lo dejaste".padEnd(32)}   —    ${continuar}`);
await cliente.close();
```

- **En tiempo, empate:** menos de 1 ms al leer y unos 5 ms al escribir (se espera al diario de MongoDB). Con índice, 1 documento o 4 cuestan igual.
- **En espacio, gana A:** B tiene cuatro veces más documentos que repiten `userId` y `cursoId`, e índices de 7,9 MB frente a 1,5 MB.
- **En posibilidades, gana B:** cada lectura tiene fecha, y "continuar donde lo dejaste" tarda 0,14 ms. A solo sabe la fecha del curso entero.
- **Las dos valen porque el array de A está acotado** (8 secciones). La plataforma eligió B por la fecha de cada lectura; si bastara saber qué está leído, A sería más barata.

<Callout type="risk">

- **Un empate con 2000 usuarios no lo es con 2 millones:** los tiempos aguantan mientras los índices quepan en memoria. Por eso se mide el espacio.
- **`$addToSet` en A y el índice único en B** evitan lo mismo: duplicar una lectura (B5.4). Sin el índice, B acumularía duplicados.
- **`$collStats` mide tras el punto de control** (cada 60 s): sin el `fsync` del _script_, una colección nueva sale en 4 KB.

</Callout>

## Paso 2: el antipatrón, un array sin límite

**Qué es:** antes de embeber, la pregunta clave es **¿este array tiene un máximo?** Las secciones de un curso, sí (8); los cursos de un usuario, sí (24); los alumnos de un curso, **no**. El mismo dato se puede guardar en los dos lados, y solo uno es seguro.

**Cómo se usa:** crea `src/i4/02-sin-limite.ts`.

```ts
// Archivo: src/i4/02-sin-limite.ts
// El mismo dato ("quién estudia qué curso") en el lado que crece sin límite y en el lado acotado
import { BSON } from "mongodb";
import { cliente, db } from "../db";

interface CursoConAlumnos {
  _id: string;
  titulo: string;
  alumnos: string[]; // ✗ crece con cada usuario de la plataforma
}
interface UsuarioConCursos {
  _id: string;
  nombre: string;
  cursos: string[]; // ✓ acotado: como mucho, los 24 cursos del catálogo
}

const cursos = db.collection<CursoConAlumnos>("i4_cursos_alumnos");
const usuarios = db.collection<UsuarioConCursos>("i4_usuarios_cursos");
await Promise.all([cursos.drop().catch(() => {}), usuarios.drop().catch(() => {})]);
await cursos.insertOne({ _id: "B5", titulo: "MongoDB esencial", alumnos: [] });

const id = (n: number) => `u_${String(n).padStart(7, "0")}`;
const ms = (t: number, veces: number) => ((performance.now() - t) / veces).toFixed(2).padStart(6);

console.log("✗ curso.alumnos (crece con los usuarios)");
let n = 0;
for (const objetivo of [1_000, 10_000, 50_000, 100_000, 200_000]) {
  // Crece hasta el tamaño objetivo en lotes
  while (n < objetivo) {
    const lote = Array.from({ length: Math.min(10_000, objetivo - n) }, (_, i) => id(n + i));
    await cursos.updateOne({ _id: "B5" }, { $push: { alumnos: { $each: lote } } });
    n += lote.length;
  }

  // $addToSet tiene que comprobar que el valor no está: recorre el array entero
  let t = performance.now();
  for (let i = 0; i < 20; i++) await cursos.updateOne({ _id: "B5" }, { $addToSet: { alumnos: id(5_000_000 + n + i) } });
  const nuevo = ms(t, 20);
  n += 20;

  t = performance.now();
  for (let i = 0; i < 20; i++) await cursos.findOne({ _id: "B5" }, { projection: { titulo: 1 } });
  const titulo = ms(t, 20);

  const doc = await cursos.findOne({ _id: "B5" });
  const mb = (BSON.calculateObjectSize(doc!) / 1024 / 1024).toFixed(2);
  console.log(`  ${String(n).padStart(7)} alumnos · ${mb.padStart(5)} MB · $addToSet: ${nuevo} ms · leer el título: ${titulo} ms`);
}

console.log("\n✓ usuario.cursos (como mucho, 24)");
await usuarios.insertOne({ _id: "u_ana", nombre: "Ana", cursos: [] });
const catalogo = ["B1", "B2", "B3", "B4", "B5", "B6", "B7", "I1", "I2", "I3", "I4", "I5", "I6", "I7", "I8", "A1", "A2", "A3", "A4", "A5", "A6", "A7", "A8", "P1"];
const t = performance.now();
for (const c of catalogo) await usuarios.updateOne({ _id: "u_ana" }, { $addToSet: { cursos: c } });
const doc = await usuarios.findOne({ _id: "u_ana" });
console.log(`  ${doc!.cursos.length} cursos · ${BSON.calculateObjectSize(doc!)} bytes · $addToSet: ${ms(t, catalogo.length)} ms`);

// 200 matrículas a la vez: todas sobre el MISMO documento del curso, o cada una sobre su usuario
console.log("\n200 matrículas simultáneas");
await usuarios.insertMany(Array.from({ length: 200 }, (_, i) => ({ _id: id(9_000_000 + i), nombre: `U${i}`, cursos: [] })));
let t2 = performance.now();
await Promise.all(Array.from({ length: 200 }, (_, i) => cursos.updateOne({ _id: "B5" }, { $addToSet: { alumnos: id(8_000_000 + i) } })));
console.log(`  ✗ en curso.alumnos (un documento):   ${(performance.now() - t2).toFixed(0).padStart(5)} ms en total`);
t2 = performance.now();
await Promise.all(Array.from({ length: 200 }, (_, i) => usuarios.updateOne({ _id: id(9_000_000 + i) }, { $addToSet: { cursos: "B5" } })));
console.log(`  ✓ en usuario.cursos (200 documentos): ${(performance.now() - t2).toFixed(0).padStart(5)} ms en total`);

await Promise.all([cursos.drop(), usuarios.drop()]);
await cliente.close();
```

- **`$addToSet` recorre el array entero:** con 200 000 alumnos tarda el triple que con 1000 (14 frente a 4,9 ms). A unos 21 bytes por `userId`, el curso llega a 16 MB con unos 780 000, y nadie más podrá matricularse.
- **Leer el título no empeora** porque la proyección no envía el array, pero el servidor carga 4 MB en cada lectura.
- **Lo que más duele es la concurrencia:** 200 matrículas a la vez tardan 3,3 s en un mismo documento y 0,15 s en documentos distintos. MongoDB pone en fila las escrituras de un documento: es un **punto caliente**.
- **Embebe en el lado acotado:** la lista de alumnos se busca con una consulta sobre usuarios o lecturas, indexada por `cursoId`.

<Callout type="risk">

- **"Pocos" tiene que ser un máximo:** "pocas notificaciones" no lo es; "5 respuestas por intento", sí. Sin número máximo, no embebas.
- **Los arrays sin límite no avisan:** fallan meses después, primero en lo más popular.
- **Los índices sobre arrays multiplican:** uno sobre `alumnos` tendría 200 000 entradas para este curso, y un índice compuesto no admite dos campos de array.

</Callout>

## Paso 3: el coste de referenciar, `$lookup`

**Qué es:** con datos en dos colecciones hay que unirlas. **`$lookup`** busca, para cada documento, los relacionados en otra colección (como un `LEFT JOIN`); la alternativa es unir en la aplicación con dos consultas.

**Cómo se usa:** un informe de intentos de la última semana con el nombre de cada alumno, en `src/i4/02-lookup.ts`:

```ts
// Archivo: src/i4/02-lookup.ts
// Referenciar tiene un coste al leer: $lookup con y sin índice, frente a unir en la aplicación
import type { Document } from "mongodb";
import { cliente, db } from "../db";
import { CATALOGO } from "./catalogo";

interface Alumno {
  userId: string; // referencia "natural" (no es el _id)
  nombre: string;
}
interface Intento {
  userId: string;
  cursoId: string;
  puntuacion: number;
  fecha: Date;
}

const alumnos = db.collection<Alumno>("i4_alumnos");
const intentos = db.collection<Intento>("i4_intentos");
const id = (n: number) => `u_${String(n).padStart(5, "0")}`;
const inicio = Date.UTC(2026, 9, 1);
const desde = new Date(inicio + 7 * 86_400_000);

// El informe: intentos de la última semana con el nombre de cada alumno
const informe: Document[] = [
  { $match: { fecha: { $gte: desde } } },
  { $lookup: { from: "i4_alumnos", localField: "userId", foreignField: "userId", as: "alumno" } },
  { $project: { _id: 0, cursoId: 1, puntuacion: 1, nombre: { $first: "$alumno.nombre" } } },
];

/** Busca la estrategia del $lookup dentro del explain (el plan es un árbol de etapas) */
function estrategia(nodo: unknown): string | undefined {
  if (!nodo || typeof nodo !== "object") return undefined;
  const n = nodo as Document;
  if (n.stage === "EQ_LOOKUP") return n.strategy as string;
  for (const v of Object.values(n)) {
    const s = estrategia(v);
    if (s) return s;
  }
  return undefined;
}

async function medir(nombre: string, fn: () => Promise<unknown[]>) {
  const t = performance.now();
  const filas = await fn();
  const ms = (performance.now() - t).toFixed(0).padStart(6);
  const plan = nombre.startsWith("$lookup") ? estrategia(await intentos.aggregate(informe).explain("queryPlanner")) : "—";
  console.log(`  ${nombre.padEnd(38)} ${String(filas.length).padStart(6)} filas · ${ms} ms · estrategia: ${plan}`);
}

for (const usuarios of [2_000, 20_000]) {
  await Promise.all([alumnos.drop().catch(() => {}), intentos.drop().catch(() => {})]);
  await alumnos.insertMany(Array.from({ length: usuarios }, (_, i) => ({ userId: id(i + 1), nombre: `Alumno ${i + 1}` })));
  await intentos.insertMany(
    Array.from({ length: 20_000 }, (_, i) => ({
      userId: id((i % usuarios) + 1),
      cursoId: CATALOGO[i % CATALOGO.length]!.id,
      puntuacion: i % 6,
      fecha: new Date(inicio + (i % 14) * 86_400_000),
    })),
  );
  await intentos.createIndex({ fecha: -1 });

  console.log(`\nInforme de la última semana con ${usuarios} alumnos`);
  await medir("$lookup SIN índice en alumnos.userId", () => intentos.aggregate(informe).toArray());
  await alumnos.createIndex({ userId: 1 }, { unique: true });
  await medir("$lookup CON índice en alumnos.userId", () => intentos.aggregate(informe).toArray());
  await medir("unir en la aplicación (2 consultas)", async () => {
    const filas = await intentos
      .find({ fecha: { $gte: desde } }, { projection: { _id: 0, userId: 1, cursoId: 1, puntuacion: 1 } })
      .toArray();
    const ids = [...new Set(filas.map((f) => f.userId))];
    const nombres = new Map((await alumnos.find({ userId: { $in: ids } }).toArray()).map((a) => [a.userId, a.nombre]));
    return filas.map((f) => ({ cursoId: f.cursoId, puntuacion: f.puntuacion, nombre: nombres.get(f.userId) }));
  });
}

await Promise.all([alumnos.drop(), intentos.drop()]);
await cliente.close();
```

- **Con 2000 alumnos, el índice parece no importar:** MongoDB 8 usa `HashJoin`, una tabla en memoria. Rápido, y engañoso.
- **Con 20 000, se derrumba:** pasado un umbral (unos 10 000 documentos unidos), usa `NestedLoopJoin` y recorre los 20 000 alumnos por cada uno de los 9997 intentos: 16,3 s frente a 38 ms con índice (`IndexedLoopJoin`), 430 veces más lento.
- **Unir en la aplicación fue lo más rápido** (19 y 23 ms): `$in` trae los alumnos y un `Map` une. Son dos viajes, que en Atlas pesan más, pero es válido.

<Callout type="risk">

- **Indexa siempre el `foreignField` de un `$lookup`:** `_id` ya lo tiene; `userId`, `slug` o `email`, no. Sin él, funciona en desarrollo y se cae al crecer.
- **Mira la estrategia con `explain`:** `HashJoin` o `IndexedLoopJoin` valen; `NestedLoopJoin` en una colección que crece, no. Atlas M0 usa MongoDB 8.0, con las mismas tres.
- **Un `$lookup` en el patrón más frecuente es una señal:** ese dato quizá debería ir embebido o copiado (_Extended Reference_, I4.3).

</Callout>

## Paso 4: la decisión, en una tabla

**Qué es:** el resumen de qué hacer con cada tipo de relación.

**Cómo se usa:**

| Relación                               | Ejemplo                                                 | Decisión                                    | Por qué                                                        |
| -------------------------------------- | ------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------- |
| 1:1                                    | Usuario y sus preferencias                              | Embeber                                     | Se leen siempre juntos y no crecen                             |
| 1:pocos (acotado)                      | Intento y sus 5 respuestas                              | Embeber                                     | Hay un máximo y se leen juntos                                 |
| 1:pocos, pero con datos propios        | Lecturas de un usuario en un curso (con fecha cada una) | Depende del patrón                          | A ocupa menos; B permite consultar por fecha (Paso 1)          |
| 1:muchos (sin límite)                  | Intentos de un usuario a lo largo de los años           | Referenciar                                 | Crece sin máximo                                               |
| Muchos:1 desde el lado "muchos"        | Alumnos de un curso                                     | Referenciar (o embeber en el lado acotado)  | El lado del curso crece sin límite (Paso 2)                    |
| N:M                                    | Usuarios y cursos                                       | Referenciar, con un documento intermedio    | Los dos lados crecen; las lecturas son el documento intermedio |
| Dato que casi no cambia y se lee mucho | Catálogo de cursos                                      | Fuera de la base de datos, o copiado (I4.3) | Lo publica el autor y se lee en cada página                    |

<Callout type="risk">

- **Referenciar no garantiza integridad:** sin claves foráneas, borrar un curso no borra sus lecturas. Lo hace la aplicación o un _script_; `$jsonSchema` (I4.6) comprueba la forma, no que la referencia exista.
- **Cambiar de opinión cuesta una migración** (I4.6): decide con la lista de patrones y volumen de prueba.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Toma el diagrama entidad-relación de B4.2 (usuario, curso, sección, lectura e intento de evaluación) y decide, para cada relación, si embebes o referencias. Justifica cada decisión con los patrones de I4.1.
2. Escribe los tipos de TypeScript de las colecciones resultantes, crea un índice por patrón de acceso y comprueba con `explain` que cada patrón lo usa.

</Callout>

Solución. Las decisiones:

| Relación de B4.2              | Decisión                                      | Justificación                                                                              |
| ----------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------ |
| CURSO tiene SECCION           | Ninguna de las dos: fuera de la base de datos | Lo cambia el autor al publicar y se lee en todas las páginas (I4.1, Paso 1)                |
| USUARIO lee SECCION (LECTURA) | Referenciar: un documento por lectura         | Patrón "continuar donde lo dejaste" y estadísticas por día: cada lectura necesita su fecha |
| USUARIO hace INTENTO          | Referenciar                                   | Los intentos crecen con el tiempo y se consultan por curso y por fecha                     |
| INTENTO tiene respuestas      | Embeber                                       | Siempre 5 y siempre se leen con el intento                                                 |
| CURSO se evalúa en INTENTO    | Referenciar (`cursoId`)                       | El curso está en el catálogo; el intento solo guarda su identificador                      |

`src/i4/02-ejercicio.ts`:

```ts
// Archivo: src/i4/02-ejercicio.ts
// Ejercicio I4.2: el diagrama de B4.2 llevado a MongoDB, y cada patrón de I4.1 comprobado con explain
import type { Document, ObjectId } from "mongodb";
import { cliente, db } from "../db";

// CURSO y SECCION: no van a la base de datos (catálogo en archivos, src/i4/catalogo.ts)

/** LECTURA: referenciada (un documento por sección leída). Crece con usuarios × secciones */
interface Lectura {
  _id?: ObjectId;
  userId: string; // referencia a USUARIO
  cursoId: string; // referencia a CURSO (del catálogo)
  seccionId: string; // referencia a SECCION (del catálogo)
  leidaEn: Date;
}

/** INTENTO_EVALUACION: referenciado. Las respuestas sí van embebidas: 5 por intento, siempre */
interface Intento {
  _id?: ObjectId;
  userId: string;
  cursoId: string;
  respuestas: number[]; // embebido y acotado (5)
  puntuacion: number;
  total: number;
  aprobado: boolean;
  fecha: Date;
}

const lecturas = db.collection<Lectura>("i4m_lecturas");
const intentos = db.collection<Intento>("i4m_intentos");
await Promise.all([lecturas.drop().catch(() => {}), intentos.drop().catch(() => {})]);

// Un índice por patrón de acceso (y no más: cada índice encarece las escrituras)
await lecturas.createIndex({ userId: 1, cursoId: 1, seccionId: 1 }, { unique: true }); // #1, #2 y #3
await lecturas.createIndex({ userId: 1, leidaEn: -1 }); // continuar donde lo dejaste
await intentos.createIndex({ userId: 1, cursoId: 1, fecha: -1 }); // #7 últimos intentos del curso

// Datos de prueba
const ahora = Date.now();
await lecturas.insertMany(
  ["B5.1", "B5.2", "B5.3", "B1.1"].map((seccionId, i) => ({
    userId: "u_ana",
    cursoId: seccionId.split(".")[0]!,
    seccionId,
    leidaEn: new Date(ahora - i * 3_600_000),
  })),
);
await intentos.insertOne({ userId: "u_ana", cursoId: "B5", respuestas: [1, 0, 3, 2, 1], puntuacion: 4, total: 5, aprobado: true, fecha: new Date() });

/** Resumen del plan: la cadena de etapas y lo examinado frente a lo devuelto */
function resumen(e: Document) {
  const etapas: string[] = [];
  let n: Document | undefined = e.queryPlanner.winningPlan;
  while (n) {
    etapas.push(n.indexName ? `${n.stage}(${n.indexName})` : n.stage);
    n = n.inputStage;
  }
  const s = e.executionStats;
  return `${etapas.join(" ← ")} · ${s.nReturned} devueltos / ${s.totalDocsExamined} documentos examinados`;
}

const patrones: [string, () => Promise<Document>][] = [
  ["#1 leídas de un curso", () => lecturas.find({ userId: "u_ana", cursoId: "B5" }, { projection: { _id: 0, seccionId: 1 } }).explain("executionStats")],
  ["#2 temario", () => lecturas.find({ userId: "u_ana" }, { projection: { _id: 0, seccionId: 1 } }).explain("executionStats")],
  ["continuar donde lo dejaste", () => lecturas.find({ userId: "u_ana" }).sort({ leidaEn: -1 }).limit(1).explain("executionStats")],
  ["#7 últimos intentos del curso", () => intentos.find({ userId: "u_ana", cursoId: "B5" }).sort({ fecha: -1 }).limit(5).explain("executionStats")],
];
for (const [nombre, fn] of patrones) console.log(`${nombre.padEnd(30)} ${resumen(await fn())}`);

await Promise.all([lecturas.drop(), intentos.drop()]);
await cliente.close();
```

```text
#1 leídas de un curso          PROJECTION_COVERED ← IXSCAN(userId_1_cursoId_1_seccionId_1) · 3 devueltos / 0 documentos examinados
#2 temario                     PROJECTION_COVERED ← IXSCAN(userId_1_cursoId_1_seccionId_1) · 4 devueltos / 0 documentos examinados
continuar donde lo dejaste     LIMIT ← FETCH ← IXSCAN(userId_1_leidaEn_-1) · 1 devueltos / 1 documentos examinados
#7 últimos intentos del curso  LIMIT ← FETCH ← IXSCAN(userId_1_cursoId_1_fecha_-1) · 1 devueltos / 1 documentos examinados
```

- **`PROJECTION_COVERED` con 0 documentos examinados:** el índice `{ userId, cursoId, seccionId }` contiene todo lo que piden #1 y #2, y MongoDB responde **solo con el índice**: una consulta cubierta, la más barata.
- **Un índice por patrón, y no más:** tres para cuatro patrones. Cada índice de más encarece las escrituras, y aquí lo más frecuente es escribir.
- **Es el modelo de la plataforma** (`section_progress` y `quiz_attempts` en `src/server/db-types.ts`), en español. Las sesiones de estudio llegan en I4.3.

<Callout type="risk">

- **Un campo de más rompe la cobertura:** con `leidaEn` en la proyección de #1, hay que leer documentos (`FETCH`). Pide solo lo necesario.
- **`_id` también la rompe:** se devuelve siempre salvo `_id: 0`, como en las proyecciones del ejercicio.

</Callout>

<Callout type="mastery">

Antes de embeber, preguntas cuál es el máximo del array: embebes lo acotado que se lee junto (las respuestas de un intento), referencias lo que crece sin límite (lecturas, intentos), identificas el lado acotado de cada relación, indexas el campo por el que une cada `$lookup` y compruebas con `explain` y con volumen real que el diseño aguanta.

</Callout>

## Resumen

- Embeber da lecturas de un documento y ocupa menos; referenciar crece sin límite y consulta cada elemento.
- Con un array acotado, empate en tiempo: deciden el espacio y los patrones.
- Un array sin límite encarece `$addToSet`, acaba en 16 MB y crea un punto caliente (22 veces más lento con 200 escrituras a la vez).
- `$lookup` sin índice en `foreignField` pasa de `HashJoin` a `NestedLoopJoin` (de 38 ms a 16 s).
- Unir en la aplicación con `$in` y un `Map` es una alternativa válida.
