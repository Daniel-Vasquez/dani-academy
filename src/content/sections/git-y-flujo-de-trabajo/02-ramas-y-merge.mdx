Trabajando en `main`, un arreglo urgente te pilla con una funcionalidad a medias que no puedes desplegar. Las **ramas** aíslan cada cambio hasta que está terminado. Aquí añades tres funcionalidades a `planificador`, cada una en su rama.

**Requisitos:** el repositorio `planificador` de B2.1, con `git status` limpio (`nothing to commit, working tree clean`).

## Paso 1: una rama es solo un puntero

**Qué es:** una rama es **un nombre que apunta a un _commit_**, guardado en un archivo de 41 bytes. No copia archivos: por eso crearla es instantáneo.

**Cómo se usa:** mira dónde están las ramas.

```bash
git branch
ls .git/refs/heads
```

```text
* main
main
```

El `*` marca la rama actual, y `main` es literalmente un archivo en `.git/refs/heads/`. Crea otra y compáralas:

```bash
git branch experimento
cat .git/refs/heads/main .git/refs/heads/experimento
git log --oneline -1 --decorate
```

```text
060ecdbee836af6b9ad9b75a5cf22ff7c879dd7d
060ecdbee836af6b9ad9b75a5cf22ff7c879dd7d
060ecdb (HEAD -> main, experimento) docs: explica cómo ejecutar el proyecto
```

- **Los dos archivos tienen el mismo identificador:** dos nombres sobre el mismo _commit_. `--decorate` los muestra: `HEAD -> main` (estás en `main`) y `experimento`.

Borra la rama de prueba:

```bash
git branch -d experimento
```

```text
Deleted branch experimento (was 060ecdb).
```

<Callout type="risk">

- **Borrar una rama no borra _commits_:** si no están en otra rama, quedan sueltos y Git los elimina en unas semanas. Hasta entonces, se recuperan con `git reflog` (B2.3).
- **`Feat/Agua` y `feat/agua` pueden chocar en macOS,** que no distingue mayúsculas en los nombres de archivo. Usa minúsculas, sin espacios ni acentos: `feat/modo-oscuro`.

</Callout>

## Paso 2: crear una rama y trabajar en ella

**Qué es:** `git switch -c` crea la rama en el _commit_ actual y mueve `HEAD` a ella. Al hacer _commit_, **solo avanza la rama actual**.

**Cómo se usa:** un cambio de tema claro/oscuro.

```bash
git switch -c feat/modo-oscuro
cat .git/HEAD
```

```text
Switched to a new branch 'feat/modo-oscuro'
ref: refs/heads/feat/modo-oscuro
```

Crea `src/tema.js`:

```js
// Tema de color del Planificador: claro u oscuro
const TEMAS = ["light", "dark"];

function siguienteTema(actual) {
  return actual === "light" ? "dark" : "light";
}

function esTemaValido(valor) {
  return TEMAS.includes(valor);
}

console.log(`Tema inicial: light → tras pulsar el botón: ${siguienteTema("light")}`);
console.log(`¿"sepia" es un tema válido? ${esTemaValido("sepia")}`);
```

```bash
node src/tema.js
git add src/tema.js
git commit -m "feat: alterna entre tema claro y oscuro"
git log --oneline --graph --all --decorate -3
```

```text
Tema inicial: light → tras pulsar el botón: dark
¿"sepia" es un tema válido? false
* ec87e67 (HEAD -> feat/modo-oscuro) feat: alterna entre tema claro y oscuro
* 060ecdb (main) docs: explica cómo ejecutar el proyecto
* eddf840 feat: muestra el número de tareas completadas
```

- **`feat/modo-oscuro` está en el _commit_ nuevo y `main`, uno atrás.** Compruébalo:

```bash
git switch main
ls src
```

```text
Switched to branch 'main'
tareas.js
```

- **`src/tema.js` ha desaparecido de tu carpeta,** pero no se ha perdido: al cambiar de rama, Git pone en el _working directory_ la foto del _commit_ de esa rama.

<Callout type="risk">

- **`git switch`, no `git checkout`:** `checkout` también descarta archivos y es fácil confundirse. Desde Git 2.23 existen `switch` (ramas) y `restore` (archivos).
- **Cambios sin confirmar en un archivo que difiere entre ramas:** Git se niega a cambiar (`error: Your local changes to the following files would be overwritten by checkout`). Haz _commit_ o usa `git stash` (B2.3).
- **Si el archivo es igual en las dos ramas, el cambio viaja contigo,** y es fácil guardarlo en la rama equivocada. Mira `git status` antes de cambiar.

</Callout>

## Paso 3: el _merge_ más simple, el _fast-forward_

**Qué es:** si `main` no ha avanzado desde que creaste la rama, mezclar es solo **mover el puntero** de `main` hasta el _commit_ de la rama. No se crea ningún _commit_ nuevo.

**Cómo se usa:** desde `main`, trae la rama.

```bash
git merge feat/modo-oscuro
```

```text
Updating 060ecdb..ec87e67
Fast-forward
 src/tema.js | 13 +++++++++++++
 1 file changed, 13 insertions(+)
 create mode 100644 src/tema.js
```

La rama ya no hace falta:

```bash
git branch -d feat/modo-oscuro
```

```text
Deleted branch feat/modo-oscuro (was ec87e67).
```

<Callout type="risk">

- **`merge` trae la otra rama a la rama en la que estás.** El error clásico es `git merge main` desde la funcionalidad. Mira antes `git branch`.
- **Un _fast-forward_ no deja rastro de la rama:** el historial queda recto. Para que quede constancia, `--no-ff` (Paso 5).

</Callout>

## Paso 4: ramas que divergen y el _merge commit_

**Qué es:** cuando `main` también ha avanzado, Git no puede mover el puntero: **combina** las dos líneas en un **_merge commit_**, un _commit_ con **dos padres**.

**Cómo se usa:** provócalo con dos ramas que parten del mismo punto. La primera, el registro de agua:

```bash
git switch -c feat/agua
```

Crea `src/agua.js`:

```js
// Registro de hidratación: vasos de 250 ml
const ML_POR_VASO = 250;
const OBJETIVO_ML = 2000;

function progresoAgua(vasos) {
  const ml = vasos * ML_POR_VASO;
  const porcentaje = Math.min(100, Math.round((ml / OBJETIVO_ML) * 100));
  return `${ml} ml de ${OBJETIVO_ML} ml (${porcentaje} %)`;
}

console.log(`Hoy: ${progresoAgua(5)}`);
```

```bash
node src/agua.js
git add src/agua.js
git commit -m "feat: registra los vasos de agua del día"
```

```text
Hoy: 1250 ml de 2000 ml (63 %)
```

La segunda, **desde `main`**:

```bash
git switch main
git switch -c docs/readme-tema
```

Sustituye `README.md` por:

```markdown
# Planificador 2026

Organizador de tareas por categorías: trabajo, personal, salud y estudio.

Ejecútalo con `node src/tareas.js`.

## Tema de color

`node src/tema.js` muestra cómo se alterna entre el tema claro y el oscuro.
```

```bash
git commit -am "docs: documenta el cambio de tema"
git log --oneline --graph --all --decorate -5
```

```text
* 6e5e8a7 (HEAD -> docs/readme-tema) docs: documenta el cambio de tema
| * 5ff4696 (feat/agua) feat: registra los vasos de agua del día
|/
* ec87e67 (main) feat: alterna entre tema claro y oscuro
* 060ecdb docs: explica cómo ejecutar el proyecto
* eddf840 feat: muestra el número de tareas completadas
```

- **El historial se ha bifurcado:** las dos ramas salen de `ec87e67`, y cada una tiene un _commit_ que la otra no.

Mézclalas en `main`, una tras otra:

```bash
git switch main
git merge feat/agua
git merge docs/readme-tema
```

- **La primera es un _fast-forward_.** En la segunda, `main` ya incluye el agua, así que Git crea un _merge commit_ y abre VS Code con el mensaje `Merge branch 'docs/readme-tema'`: cierra la pestaña para aceptarlo.

```text
Merge made by the 'ort' strategy.
 README.md | 4 ++++
 1 file changed, 4 insertions(+)
```

```bash
git log --oneline --graph --all --decorate -6
```

```text
*   38cc512 (HEAD -> main) Merge branch 'docs/readme-tema'
|\
| * 6e5e8a7 (docs/readme-tema) docs: documenta el cambio de tema
* | 5ff4696 (feat/agua) feat: registra los vasos de agua del día
|/
* ec87e67 feat: alterna entre tema claro y oscuro
* 060ecdb docs: explica cómo ejecutar el proyecto
* eddf840 feat: muestra el número de tareas completadas
```

Ábrelo por dentro, como en B2.1:

```bash
git cat-file -p HEAD
```

```text
tree f788b421e1e6d1fa17e0956f244d2b83f1aad8a9
parent 5ff4696ea077607b8c385f5d43c8e3aa1ba4b50f
parent 6e5e8a79a01b8ad1a5ad4effd4dac0037982a539
author Dani <dani@example.com> 1791565200 -0600
```

- **Dos `parent`:** es la única diferencia con un _commit_ normal. Su foto combina el `agua.js` de una línea y el `README.md` de la otra. `'ort'` es el algoritmo de mezcla por defecto.

Borra las dos ramas, ya integradas:

```bash
git branch -d feat/agua docs/readme-tema
```

<Callout type="risk">

- **`--no-edit`** acepta el mensaje por defecto sin abrir el editor.
- **Si las dos ramas cambian las mismas líneas,** Git se detiene con un **conflicto** (B2.3). Aquí no pasa porque tocan archivos distintos.
- **Sin conflictos no significa que funcione:** si una rama renombra una función y la otra la usa con el nombre viejo, la mezcla sale limpia y el código se rompe. Ejecuta el proyecto y los tests tras cada _merge_.

</Callout>

## Paso 5: borrar ramas sin perder trabajo, y `--no-ff`

**Qué es:** `git branch -d` solo borra ramas **ya mezcladas**; `-D` fuerza el borrado. `--no-ff` **obliga** a crear un _merge commit_ aunque fuera posible un _fast-forward_.

**Cómo se usa:** con una rama abandonada.

```bash
git switch -c feat/abandonada
echo "// borrador" >> src/agua.js
git commit -am "wip: borrador"
git switch main
git branch -d feat/abandonada
```

```text
error: the branch 'feat/abandonada' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feat/abandonada'
```

- **Git te protege:** esa rama tiene un _commit_ que no está en ninguna otra. Para descartarla:

```bash
git branch -D feat/abandonada
```

Ahora la racha, mezclada con `--no-ff`:

```bash
git switch -c feat/racha
```

Crea `src/racha.js`:

```js
// Racha de días con entreno
function racha(dias) {
  let n = 0;
  for (const hecho of dias.toReversed()) {
    if (!hecho) break;
    n += 1;
  }
  return n;
}

console.log(`Racha actual: ${racha([true, false, true, true, true])} días`);
```

```bash
node src/racha.js
git add src/racha.js
git commit -m "feat: calcula la racha de días con entreno"
git switch main
git merge --no-ff feat/racha --no-edit
git log --oneline --graph --decorate -4
git branch -d feat/racha
```

```text
Racha actual: 3 días
Merge made by the 'ort' strategy.
 src/racha.js | 11 +++++++++++
 1 file changed, 11 insertions(+)
 create mode 100644 src/racha.js
*   eaf25e7 (HEAD -> main) Merge branch 'feat/racha'
|\
| * 5ac3f2c (feat/racha) feat: calcula la racha de días con entreno
|/
*   38cc512 Merge branch 'docs/readme-tema'
|\
| * 6e5e8a7 docs: documenta el cambio de tema
```

- **La "burbuja" del historial** deja constancia de que esos _commits_ son una unidad: revertir el _merge commit_ deshace la funcionalidad entera (B2.3).

<Callout type="risk">

- **`-D` no pide confirmación.** Un error se recupera con `git reflog` durante unos días, pero no lo conviertas en costumbre.
- **¿_Fast-forward_ o `--no-ff`?** Es una decisión de equipo; en GitHub, la toman las Pull Requests (B2.4). Lo importante es reconocer los dos.
- **`toReversed()`** devuelve una copia invertida sin tocar el original, a diferencia de `reverse()`. Necesita Node 20 o superior.

</Callout>

## Paso 6: un flujo de trabajo por ramas

**Qué es:** la regla de casi todos los equipos pequeños: **`main` siempre se puede desplegar**.

1. **Desde `main` actualizado,** `git switch -c tipo/descripcion-corta`.
2. **Trabaja en la rama** con _commits_ pequeños (B2.1).
3. **Comprueba que funciona** en la rama: arranca y `npm run check` pasa.
4. **Mezcla en `main`** (en B2.4, con una Pull Request) y **borra la rama**.

Los prefijos de rama son los de los _commits_: `feat/modo-oscuro`, `fix/total-agua`, `docs/readme`. Así `git branch` se lee como una lista de tareas.

**Ramas y Vercel:** con el proyecto conectado desde GitHub, cada rama subida recibe un **despliegue de _preview_** con su propia URL (`planificador-git-feat-modo-oscuro-tuusuario.vercel.app`). Producción solo cambia con `main`. Lo practicarás en B2.4.

<Callout type="risk">

- **Las _previews_ comparten base de datos** si usan las mismas variables que producción: una rama con un error puede borrar datos reales. En Vercel, configura variables distintas para _Preview_.
- **El login puede fallar en una _preview_:** Better Auth solo acepta el dominio de `BETTER_AUTH_URL`. Esta plataforma también lo hace; se resuelve con los orígenes de confianza (I5).
- **Las ramas que viven semanas** acaban en conflictos enormes. Mantenlas en horas o pocos días.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Desde `main`, crea la rama `feat/colores` y en ella un archivo `src/colores.js` que asocie cada categoría del Planificador con un color (trabajo `#0284c7`, personal `#d97706`, salud `#0d9488`, estudio `#f25c76`) e imprima la lista. Haz commit.
2. Vuelve a `main`, crea la rama `docs/categorias` y añade al `README.md` una sección "Categorías" con las cuatro categorías. Haz commit.
3. Antes de mezclar, predice: ¿qué merge será _fast-forward_ y cuál creará un merge commit? Mezcla las dos ramas en `main` y comprueba tu predicción con `git log --oneline --graph --decorate`.
4. Borra las ramas y comprueba con `git branch` que solo queda `main`.

</Callout>

Solución. Primera rama:

```bash
git switch main
git switch -c feat/colores
```

`src/colores.js`:

```js
// Color asociado a cada categoría del Planificador 2026
const COLORES = {
  trabajo: "#0284c7",
  personal: "#d97706",
  salud: "#0d9488",
  estudio: "#f25c76",
};

for (const [categoria, color] of Object.entries(COLORES)) {
  console.log(`${categoria.padEnd(9)} ${color}`);
}
```

```bash
node src/colores.js
git add src/colores.js
git commit -m "feat: asigna un color a cada categoría"
```

```text
trabajo   #0284c7
personal  #d97706
salud     #0d9488
estudio   #f25c76
```

Segunda rama, desde `main`:

```bash
git switch main
git switch -c docs/categorias
```

`README.md` completo:

```markdown
# Planificador 2026

Organizador de tareas por categorías: trabajo, personal, salud y estudio.

Ejecútalo con `node src/tareas.js`.

## Tema de color

`node src/tema.js` muestra cómo se alterna entre el tema claro y el oscuro.

## Categorías

- Trabajo
- Personal
- Salud
- Estudio
```

```bash
git commit -am "docs: documenta las categorías"
git switch main
git merge feat/colores
git merge docs/categorias --no-edit
git log --oneline --graph --decorate -4
git branch -d feat/colores docs/categorias
git branch
```

```text
*   d387499 (HEAD -> main) Merge branch 'docs/categorias'
|\
| * 8016015 (docs/categorias) docs: documenta las categorías
* | 6b539d0 (feat/colores) feat: asigna un color a cada categoría
|/
*   eaf25e7 Merge branch 'feat/racha'
|\
Deleted branch feat/colores (was 6b539d0).
Deleted branch docs/categorias (was 8016015).
* main
```

- **`feat/colores` es _fast-forward_:** `main` no había avanzado. **`docs/categorias` crea un _merge commit_:** al mezclarla, `main` ya tiene los colores. Tus identificadores serán distintos.

<Callout type="risk">

- **Si `docs/categorias` sale de `feat/colores`,** por olvidar `git switch main`, los dos _merges_ son _fast-forward_ y la documentación arrastra código ajeno. Mira en qué rama estás antes de `git switch -c`.
- **`padEnd(9)`** alinea las columnas, pero no recorta: un texto más largo descuadra la salida.

</Callout>

<Callout type="mastery">

Trabajas cada cambio en una rama propia sin pensarlo, sabes que una rama es un puntero a un commit, predices si un merge será _fast-forward_ o creará un merge commit, y `main` en tus proyectos siempre se puede desplegar.

</Callout>

## Resumen

- Una rama es un archivo con el identificador de un _commit_: crearla es instantáneo.
- `git switch -c` crea y cambia; con cada _commit_ solo avanza la rama actual.
- _Fast-forward_: se mueve el puntero. _Merge commit_: dos padres.
- `-d` solo borra ramas mezcladas; `-D` fuerza.
- `main` siempre desplegable, ramas cortas y una _preview_ de Vercel por rama.
