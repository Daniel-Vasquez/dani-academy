Casi todos los sustos con Git (un archivo que "no se sube", un `.env` en GitHub, un _commit_ que mezcla tres cosas) vienen de no saber **dónde está cada cambio**. Aquí lo ves con un repositorio de práctica, `planificador`, que usarás en todo el curso.

**Requisitos:** Git 2.23 o superior (`git --version`) y Node.js.

## Paso 1: configurar Git una sola vez

**Qué es:** la configuración global de Git: quién eres (cada _commit_ lleva autor) y cómo quieres trabajar. Se guarda en `~/.gitconfig` y vale para todos tus repositorios.

**Cómo se usa:** ejecútalo una sola vez en tu Mac.

```bash
git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo@ejemplo.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --global --list
```

- **`user.email`:** usa el mismo correo que en GitHub, para que asocie los _commits_ a tu cuenta.
- **`init.defaultBranch main`:** los repositorios nuevos empiezan en `main`, el nombre que espera GitHub.
- **`core.editor "code --wait"`:** para los textos largos (un mensaje sin `-m`, un _merge_), Git abre VS Code y espera a que cierres la pestaña.

<Callout type="risk">

- **El correo es público** en cada _commit_ de un repositorio público. GitHub te da uno anónimo en _Settings_ → _Emails_ (`12345+usuario@users.noreply.github.com`).
- **`code: command not found` al hacer _commit_:** instala el comando desde VS Code con `Cmd` + `Shift` + `P` → _Shell Command: Install 'code' command in PATH_.
- **Las salidas de este curso están en inglés,** lo habitual en macOS. Si tu Git está en español, los mensajes son equivalentes.

</Callout>

## Paso 2: las tres zonas de Git

**Qué es:** Git trabaja con tres zonas, y tres comandos para moverse entre ellas.

| Zona                                              | Qué es                                   |
| ------------------------------------------------- | ---------------------------------------- |
| **Working directory** (directorio de trabajo)     | Los archivos que ves y editas en VS Code |
| **Staging area** (área de preparación, o _index_) | Lo que irá en el próximo _commit_        |
| **Repositorio** (`.git`)                          | Los _commits_ guardados para siempre     |

**`git add`** pasa cambios del _working directory_ a _staging_, **`git commit`** los guarda en el repositorio y **`git status`** dice qué hay en cada zona.

**Cómo se usa:** crea el proyecto y conviértelo en repositorio.

```bash
mkdir planificador
cd planificador
git init
git status
```

```text
Initialized empty Git repository in /Users/tu-usuario/planificador/.git/

On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

`git init` crea la carpeta oculta **`.git`**, donde vive todo el historial. Crea `README.md`:

```markdown
# Planificador 2026

Organizador de tareas por categorías: trabajo, personal, salud y estudio.
```

Y `src/tareas.js` (crea la carpeta `src`):

```js
// Lista de tareas del Planificador 2026
const tareas = [
  { titulo: "Revisar pull request", categoria: "trabajo", hecha: false },
  { titulo: "Correr 5 km", categoria: "salud", hecha: true },
  { titulo: "Leer sección B2.1", categoria: "estudio", hecha: false },
];

function pendientes(lista) {
  return lista.filter((t) => !t.hecha);
}

console.log(`Tareas pendientes: ${pendientes(tareas).length}`);
```

`node src/tareas.js` muestra `Tareas pendientes: 2`. Pregunta a Git:

```bash
git status
```

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	src/

nothing added to commit but untracked files present (use "git add" to track)
```

**Untracked** significa que Git todavía no vigila esos archivos. Añade **solo** el README:

```bash
git add README.md
git status
```

```text
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	src/
```

Ahora hay un archivo en cada zona: `README.md` en _staging_ ("Changes to be committed") y `src/` solo en el _working directory_. Guárdalo:

```bash
git commit -m "docs: añade README del proyecto"
```

```text
[main (root-commit) 78d8778] docs: añade README del proyecto
 1 file changed, 3 insertions(+)
 create mode 100644 README.md
```

Lo mismo con `src/tareas.js`:

```bash
git add src/tareas.js
git commit -m "feat: lista de tareas pendientes"
git log --oneline
```

```text
c612e72 feat: lista de tareas pendientes
78d8778 docs: añade README del proyecto
```

- **`c612e72` es el identificador del _commit_.** El tuyo será distinto: se calcula con el contenido, el autor y la fecha.

<Callout type="risk">

- **`git add .` lo mete todo,** también un `.env` o un archivo de prueba. Mira `git status` antes de cada _commit_, o añade los archivos por nombre.
- **No inicies un repositorio dentro de otro:** tendrías dos historiales. Antes de `git init`, `git status` debe decir `not a git repository`.
- **Nunca edites a mano dentro de `.git`:** es la base de datos de Git, y puedes corromper el historial.

</Callout>

## Paso 3: qué guarda un _commit_

**Qué es:** un _commit_ guarda **una foto completa del proyecto**, no los cambios. Los _diffs_ se calculan comparando dos fotos.

**Cómo se usa:** `git cat-file` muestra los objetos internos de Git.

```bash
git cat-file -p HEAD
```

```text
tree 15c60bec11c24732963b6109f6f85b0ed85a1099
parent 78d8778efa8c509c9070c75ad67b7e7435b4a51c
author Dani <dani@example.com> 1791561600 -0600
committer Dani <dani@example.com> 1791561600 -0600

feat: lista de tareas pendientes
```

- **`tree`** es la foto; **`parent`**, el _commit_ anterior (así se encadena el historial); **`author`** y **`committer`**, quién y cuándo.

Abre la foto:

```bash
git cat-file -p "HEAD^{tree}"
git cat-file -p HEAD:src
```

```text
100644 blob 015d6f7a06f442c6fda086540d90a3759db2686c	README.md
040000 tree 1d16301cdeae0f8b841a12a0725de7af890b5a70	src
100644 blob 949ff6272e0290077b2b96fa9a3d1941bb490b69	tareas.js
```

- **Es la foto completa:** `README.md` (un _blob_) y `src` (otro _tree_), aunque este _commit_ solo añadió `tareas.js`. Si un archivo no cambia, la foto nueva reutiliza el mismo _blob_.

**`HEAD`** es el puntero que indica dónde estás:

```bash
cat .git/HEAD
cat .git/refs/heads/main
```

```text
ref: refs/heads/main
c612e725948400d140e04abab2dcbdf341d29233
```

- **`HEAD` apunta a `main`, y `main` al último _commit_.** Con cada _commit_, `main` avanza y `HEAD` la sigue: es la base de las ramas (B2.2).

<Callout type="risk">

- **Los archivos grandes se quedan para siempre:** un vídeo de 200 MB que subes y borras sigue en una foto anterior, y todo el que clone lo descarga. Nada de binarios pesados (para eso, Git LFS).
- **Borrar un archivo no lo borra del historial:** un secreto sigue en la foto anterior (Paso 6).

</Callout>

## Paso 4: ver qué ha cambiado con `git diff`

**Qué es:** `git diff` compara el _working directory_ con _staging_: lo que **todavía no** has añadido. `git diff --staged` compara _staging_ con el último _commit_: lo que **va a entrar**.

**Cómo se usa:** en `src/tareas.js`, cambia `"Correr 5 km"` por `"Correr 10 km"`.

```bash
git diff
```

```text
diff --git a/src/tareas.js b/src/tareas.js
index 949ff62..c0322fd 100644
--- a/src/tareas.js
+++ b/src/tareas.js
@@ -1,7 +1,7 @@
 // Lista de tareas del Planificador 2026
 const tareas = [
   { titulo: "Revisar pull request", categoria: "trabajo", hecha: false },
-  { titulo: "Correr 5 km", categoria: "salud", hecha: true },
+  { titulo: "Correr 10 km", categoria: "salud", hecha: true },
   { titulo: "Leer sección B2.1", categoria: "estudio", hecha: false },
 ];
```

- **`---` y `+++`:** la versión antigua (`a/`) y la nueva (`b/`). **`@@ -1,7 +1,7 @@`:** el fragmento empieza en la línea 1 y abarca 7. Las líneas con `-` se quitan y las de `+` se añaden.

Ahora pásalo a _staging_ y repite:

```bash
git add src/tareas.js
git diff
git diff --staged
```

- **`git diff` ya no muestra nada** y `git diff --staged` muestra el mismo cambio. Antes de cada _commit_, `git diff --staged` es la mejor revisión.

```bash
git commit -m "fix: corrige la distancia del entreno"
```

<Callout type="risk">

- **"`git diff` no muestra nada":** casi siempre, porque ya hiciste `git add`. Usa `git diff --staged`.
- **Los archivos nuevos no salen en `git diff`:** no tienen versión anterior. Aparecen en `--staged` al añadirlos.
- **Un editor que reformatea todo** esconde el cambio real entre cientos de líneas. El formato, en un _commit_ aparte (`style: formatea con Prettier`).

</Callout>

## Paso 5: _commits_ pequeños con `git add -p`

**Qué es:** `git add -p` (de _patch_) te deja elegir **qué trozos** de un archivo pasan a _staging_. Sirve para hacer un _commit_ por idea aunque hayas cambiado varias cosas en el mismo archivo.

**Cómo se usa:** sustituye `src/tareas.js` por esta versión, con dos cambios distintos: una tarea nueva y una función para contar por categoría.

```js
// Lista de tareas del Planificador 2026
const tareas = [
  { titulo: "Revisar pull request", categoria: "trabajo", hecha: false },
  { titulo: "Correr 10 km", categoria: "salud", hecha: true },
  { titulo: "Leer sección B2.1", categoria: "estudio", hecha: false },
  { titulo: "Llamar a mamá", categoria: "personal", hecha: false },
];

function pendientes(lista) {
  return lista.filter((t) => !t.hecha);
}

function contarPorCategoria(lista) {
  const conteo = { trabajo: 0, personal: 0, salud: 0, estudio: 0 };
  for (const tarea of lista) {
    conteo[tarea.categoria] += 1;
  }
  return conteo;
}

console.log(`Tareas pendientes: ${pendientes(tareas).length}`);
console.log(contarPorCategoria(tareas));
```

```bash
git add -p
```

```text
diff --git a/src/tareas.js b/src/tareas.js
index c0322fd..5fc0380 100644
--- a/src/tareas.js
+++ b/src/tareas.js
@@ -3,10 +3,20 @@ const tareas = [
   { titulo: "Revisar pull request", categoria: "trabajo", hecha: false },
   { titulo: "Correr 10 km", categoria: "salud", hecha: true },
   { titulo: "Leer sección B2.1", categoria: "estudio", hecha: false },
+  { titulo: "Llamar a mamá", categoria: "personal", hecha: false },
 ];

 function pendientes(lista) {
   return lista.filter((t) => !t.hecha);
 }

+function contarPorCategoria(lista) {
+  const conteo = { trabajo: 0, personal: 0, salud: 0, estudio: 0 };
+  for (const tarea of lista) {
+    conteo[tarea.categoria] += 1;
+  }
+  return conteo;
+}
+
 console.log(`Tareas pendientes: ${pendientes(tareas).length}`);
+console.log(contarPorCategoria(tareas));
(1/1) Stage this hunk [y,n,q,a,d,s,e,p,P,?]?
```

Git agrupó los dos cambios en un trozo. Responde:

1. **`s`** (_split_): Git lo divide en 3 trozos y pregunta por cada uno (`(1/3) Stage this hunk…?`).
2. **`n`** al primero, la tarea "Llamar a mamá": irá en otro _commit_.
3. **`y`** al segundo, la función `contarPorCategoria`, y **`y`** al tercero, su `console.log`.

Las otras respuestas: `y` (sí), `n` (no), `q` (salir) y `?` (ayuda).

```bash
git status --short
git diff --staged
```

```text
MM src/tareas.js
```

- **La doble `M`:** el archivo está **en dos zonas a la vez**. La primera columna son cambios en _staging_; la segunda, los que quedan fuera.

```bash
git commit -m "feat: cuenta las tareas por categoría"
git add src/tareas.js
git commit -m "feat: añade tarea personal de ejemplo"
node src/tareas.js
```

```text
Tareas pendientes: 3
{ trabajo: 1, personal: 1, salud: 1, estudio: 1 }
```

<Callout type="risk">

- **_Commits_ que no funcionan solos:** con `add -p` es fácil guardar una función sin la línea que la usa. Revisa `git diff --staged`; aquí la función y su `console.log` van juntos por eso.
- **`s` no siempre aparece:** con cambios en líneas consecutivas, Git no puede separarlos. Usa `e` para editar el trozo, o haz los cambios en dos momentos.
- **VS Code lo hace con el ratón:** en _Source Control_, selecciona líneas del _diff_ y usa _Stage Selected Ranges_.

</Callout>

## Paso 6: proteger el repositorio con `.gitignore`

**Qué es:** la lista de archivos que Git debe ignorar: dependencias (`node_modules/`), compilados (`dist/`), archivos del sistema (`.DS_Store`) y, sobre todo, **secretos** (`.env`).

**Cómo se usa:** simula un proyecto real con esos archivos.

```bash
printf 'API_TOKEN="token-secreto-1234567890"\n' > .env
mkdir -p node_modules/fake dist
echo "x" > node_modules/fake/index.js
echo "x" > dist/a.js
touch .DS_Store
git status --short
```

```text
?? .DS_Store
?? .env
?? dist/
?? node_modules/
```

Un `git add .` ahora subiría tu token. Crea `.gitignore` en la raíz:

```gitignore
# Dependencias: se reinstalan con npm install
node_modules/

# Resultado de compilar: se regenera con npm run build
dist/
.astro/

# Secretos y configuración local: NUNCA se suben
.env
.env.*
!.env.example

# Archivos del sistema y del editor
.DS_Store
.vscode/*
!.vscode/extensions.json
```

Y `.env.example`, la plantilla que **sí** se sube, con los valores vacíos:

```bash
printf 'API_TOKEN=""\n' > .env.example
git status --short
```

```text
?? .env.example
?? .gitignore
```

- **`node_modules/`,** con `/` al final: la carpeta y todo su contenido. **`.env.*`:** cualquier archivo que empiece por `.env.`.
- **`!.env.example`:** el `!` es una excepción a una regla anterior. Va después de ella.

Si no sabes por qué Git ignora un archivo, pregúntaselo:

```bash
git check-ignore -v .env node_modules/fake/index.js .DS_Store
```

```text
.gitignore:9:.env	.env
.gitignore:2:node_modules/	node_modules/fake/index.js
.gitignore:14:.DS_Store	.DS_Store
```

- **Cada línea dice qué regla** (archivo y número de línea) ignora cada ruta.

```bash
git add .gitignore .env.example
git commit -m "chore: añade .gitignore y .env.example"
```

<Callout type="risk">

- **`.gitignore` no afecta a archivos que Git ya vigila:** si `.env` se subió antes de la regla, sigue versionado. Sácalo sin borrarlo con `git rm --cached .env` y un _commit_, y comprueba con `git ls-files | grep env` que solo sale `.env.example`.
- **Un secreto que llegó a GitHub está comprometido:** sigue en los _commits_ anteriores. Lo primero es **generar uno nuevo** e invalidar el viejo; reescribir el historial es secundario.
- **`git add -f` fuerza a añadir un archivo ignorado.** Si un tutorial lo usa para "arreglar" algo, desconfía.

</Callout>

## Paso 7: buenos mensajes y leer el historial

**Qué es:** **Conventional Commits**, una convención muy extendida para los mensajes: `tipo: descripción`. Hace el historial legible y buscable.

**Cómo se usa:** mira el historial con la vista de cada día.

```bash
git log --oneline --graph --all
```

```text
* f698b16 chore: añade .gitignore y .env.example
* 43489f6 feat: añade tarea personal de ejemplo
* 6b29e14 feat: cuenta las tareas por categoría
* 5a96b7d fix: corrige la distancia del entreno
* c612e72 feat: lista de tareas pendientes
* 78d8778 docs: añade README del proyecto
```

- **`--oneline`:** un _commit_ por línea. **`--graph`:** dibuja las ramas (en B2.2 verás bifurcaciones). **`--all`:** todas las ramas.

| Tipo       | Cuándo usarlo                               | Ejemplo                                           |
| ---------- | ------------------------------------------- | ------------------------------------------------- |
| `feat`     | Funcionalidad nueva para el usuario         | `feat: añade gráfica de peso semanal`             |
| `fix`      | Corrección de un error                      | `fix: corrige el total de agua al cambiar de día` |
| `docs`     | Solo documentación                          | `docs: explica las variables de entorno`          |
| `style`    | Formato, sin cambiar el comportamiento      | `style: formatea con Prettier`                    |
| `refactor` | Reorganizar código sin cambiar qué hace     | `refactor: extrae el cálculo de rachas`           |
| `test`     | Añadir o corregir tests                     | `test: cubre el caso de semana vacía`             |
| `chore`    | Mantenimiento (dependencias, configuración) | `chore: actualiza Astro a la 7.3`                 |

- **Qué, en presente y en una línea** de unos 50–70 caracteres. **Un _commit_, una idea:** si necesitas una "y", probablemente son dos.
- **El porqué va en el cuerpo:** `git commit` sin `-m` abre VS Code. Título, línea en blanco y el motivo.

<Callout type="risk">

- **`wip`, `cambios` o `.` no dicen nada:** dentro de tres meses no encontrarás cuándo entró un error. `git log --oneline --grep "agua"` solo sirve con mensajes descriptivos.
- **Un _commit_ gigante al final del día** es imposible de revisar o deshacer por partes. Haz _commit_ cada vez que algo pequeño funcione.
- **Conventional Commits no es obligatorio,** pero algunas herramientas generan _changelogs_ y versiones con él. Lo importante es usar siempre la misma convención.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. En `planificador`, edita `src/tareas.js` para hacer **a la vez** estos cambios: marca "Leer sección B2.1" como hecha, añade una función `completadas(lista)` y muestra su resultado con `console.log`, y añade una línea al `README.md` explicando cómo ejecutar el proyecto.
2. Con `git add -p` (y `git add` para el README), conviértelos en **tres commits** con mensajes Conventional Commits.
3. Revisa cada commit antes de hacerlo con `git diff --staged`.
4. Comprueba con `git ls-files | grep env` que el único archivo de entorno versionado es `.env.example`.
5. Dibuja en papel las tres zonas y escribe dónde está cada archivo de `planificador` ahora mismo (incluidos `.env` y `node_modules/`).

</Callout>

Solución. `src/tareas.js` con todos los cambios:

```js
// Lista de tareas del Planificador 2026
const tareas = [
  { titulo: "Revisar pull request", categoria: "trabajo", hecha: false },
  { titulo: "Correr 10 km", categoria: "salud", hecha: true },
  { titulo: "Leer sección B2.1", categoria: "estudio", hecha: true },
  { titulo: "Llamar a mamá", categoria: "personal", hecha: false },
];

function pendientes(lista) {
  return lista.filter((t) => !t.hecha);
}

function completadas(lista) {
  return lista.filter((t) => t.hecha);
}

function contarPorCategoria(lista) {
  const conteo = { trabajo: 0, personal: 0, salud: 0, estudio: 0 };
  for (const tarea of lista) {
    conteo[tarea.categoria] += 1;
  }
  return conteo;
}

console.log(`Tareas pendientes: ${pendientes(tareas).length}`);
console.log(`Tareas completadas: ${completadas(tareas).length}`);
console.log(contarPorCategoria(tareas));
```

`README.md`:

```markdown
# Planificador 2026

Organizador de tareas por categorías: trabajo, personal, salud y estudio.

Ejecútalo con `node src/tareas.js`.
```

Los comandos. En `git add -p`, responde `y` a lo que pertenece a ese _commit_ y `n` al resto, con `s` si un trozo mezcla dos cambios:

```bash
git add -p src/tareas.js          # y solo al trozo de "hecha: true"
git diff --staged
git commit -m "feat: marca como leída la sección B2.1"

git add -p src/tareas.js          # y a los trozos de completadas()
git diff --staged
git commit -m "feat: muestra el número de tareas completadas"

git add README.md
git diff --staged
git commit -m "docs: explica cómo ejecutar el proyecto"

git ls-files | grep env
git log --oneline
node src/tareas.js
```

```text
.env.example
```

```text
Tareas pendientes: 2
Tareas completadas: 2
{ trabajo: 1, personal: 1, salud: 1, estudio: 1 }
```

Las tres zonas: el **_working directory_** tiene todos los archivos, incluidos `.env`, `node_modules/`, `dist/` y `.DS_Store`. **_Staging_** coincide con el último _commit_. El **repositorio** tiene `README.md`, `src/tareas.js`, `.gitignore` y `.env.example`, en nueve _commits_. Los ignorados viven **solo** en el _working directory_.

<Callout type="risk">

- **Dos cambios pegados son un solo trozo, sin opción `s`:** deshaz uno, haz el primer _commit_ y vuelve a aplicarlo.
- **`git commit -am`** añade **todos** los archivos modificados que Git vigila, sin preguntar. Úsalo solo si `git status` muestra exactamente lo que quieres.

</Callout>

<Callout type="mastery">

Puedes dibujar en papel las tres zonas de Git y decir en qué zona está cada archivo de tu proyecto, sabes qué muestran `git diff` y `git diff --staged`, separas cambios con `git add -p` y compruebas con `git ls-files` que ningún secreto está versionado.

</Callout>

## Resumen

- Tres zonas: _working directory_, _staging_ y repositorio. `add` prepara; `commit` guarda.
- Un _commit_ es una **foto completa** con su padre; el _diff_ se calcula.
- `HEAD` apunta a la rama, y la rama, a un _commit_.
- `git diff` muestra lo no añadido; `git diff --staged`, lo que entrará.
- `git add -p` separa cambios; `.gitignore` no afecta a lo ya versionado.
