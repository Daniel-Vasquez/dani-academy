Usas Git a diario con cuatro comandos: `add`, `commit`, `push` y, cuando algo sale mal, buscar en internet. Funciona hasta que aparece un conflicto o un "detached HEAD" y no sabes qué está pasando. La causa casi siempre es la misma: falta el **modelo mental**. En esta sección vas a construirlo; el resto del curso se apoya en él.

## Las tres zonas

Git trabaja con tres lugares distintos. Entenderlos es entender Git:

```text
 Working directory        Staging area           Repositorio (.git)
 (tus archivos)    ──add──▶ (lo que irá en   ──commit──▶ (historial de
                            el próximo commit)            commits)
        ◀──────────── restore ────────────────────────────
```

1. **Working directory**: los archivos que ves y editas en VS Code.
2. **Staging area** (o _index_): una zona intermedia donde preparas **exactamente** lo que entrará en el próximo commit.
3. **Repositorio**: la carpeta oculta `.git`, donde se guardan todos los commits.

`git add` copia cambios del _working directory_ al _staging_. `git commit` convierte el _staging_ en un commit nuevo. Nada más.

```bash
git status
```

```text
On branch main
Changes to be committed:        ← staging
        modified:   src/lib/auth.ts
Changes not staged for commit:  ← working directory
        modified:   src/pages/login.astro
Untracked files:                ← archivos que Git aún no conoce
        notas.txt
```

`git status` te dice en qué zona está cada archivo. Úsalo antes y después de cada operación: es tu mapa.

## Elegir qué entra en un commit

La _staging area_ existe para que tus commits sean **pequeños y con un solo propósito**, aunque hayas tocado muchas cosas a la vez:

```bash
git add src/lib/auth.ts       # un archivo concreto
git add -p                    # elegir trozo a trozo (y = sí, n = no, s = dividir)
git diff                      # qué has cambiado y NO está en staging
git diff --staged             # qué entrará en el próximo commit
```

`git add -p` es probablemente el comando que más mejorará tus commits: te enseña cada bloque de cambios y te pregunta si lo incluyes.

<Callout type="tip">
  Antes de cada `git commit`, ejecuta `git diff --staged`. Es tu última revisión: si ves algo que no
  debería ir (un `console.log`, una contraseña), todavía estás a tiempo.
</Callout>

## Qué es un commit

Un commit **no** es una lista de cambios. Es una **foto completa** del proyecto en un momento, más unos metadatos:

```text
commit 81544ef
├─ árbol: foto de todos los archivos
├─ padre: c954b51        ← el commit anterior
├─ autor y fecha
└─ mensaje: "feat: conexión a MongoDB…"
```

Cada commit apunta a su **padre**, y así se forma el historial: una cadena que va hacia atrás. El identificador (`81544ef…`) es un _hash_ calculado a partir del contenido: si cambiara una sola letra, el hash sería otro. Por eso el historial de Git es tan fiable.

`git diff` calcula las diferencias **comparando dos fotos**; no están guardadas como tales.

## HEAD: "dónde estás"

`HEAD` es un puntero que indica **en qué commit estás ahora**. Normalmente apunta a una rama (por ejemplo, `main`), y la rama apunta al último commit:

```text
HEAD → main → 81544ef → c954b51 → 496304c → 07f2014
```

Cuando haces un commit, se crea uno nuevo cuyo padre es el actual, y la rama avanza para apuntar a él. `HEAD` la sigue.

## Leer el historial

```bash
git log --oneline --graph --all
```

```text
* 53a7165 (HEAD -> main, origin/main) feat: página de progreso…
* 461d2f9 chore: zona horaria por defecto America/Mexico_City
* 1c0afa8 feat: índice del temario…
```

- `--oneline`: un commit por línea.
- `--graph`: dibuja las ramas y sus uniones.
- `--all`: muestra todas las ramas, no solo la actual.

Créate un alias para no escribirlo cada vez:

```bash
git config --global alias.lg "log --oneline --graph --all"
git lg
```

## Buenos mensajes de commit

Un mensaje responde a "¿qué hace este commit?" en una línea. La convención más extendida, **Conventional Commits**, añade un prefijo de tipo:

| Prefijo     | Para…                                                 |
| ----------- | ----------------------------------------------------- |
| `feat:`     | una funcionalidad nueva                               |
| `fix:`      | corregir un error                                     |
| `docs:`     | documentación                                         |
| `refactor:` | reorganizar código sin cambiar su comportamiento      |
| `chore:`    | tareas de mantenimiento (dependencias, configuración) |
| `test:`     | añadir o cambiar tests                                |

```bash
git commit -m "fix: el contador del índice no se actualizaba al desmarcar"
```

Este mismo proyecto, Dani Academy, usa esta convención en todos sus commits: revísalos con `git lg` para ver ejemplos reales.

## `.gitignore`: lo que nunca se sube

Algunos archivos no deben entrar jamás en el repositorio:

```gitignore
node_modules/   # se reinstala con npm install; pesa cientos de MB
dist/           # se genera al compilar
.env            # contiene secretos: URI de MongoDB, BETTER_AUTH_SECRET…
.env.*
!.env.example   # la plantilla sí, sin valores reales
.DS_Store
```

`.gitignore` solo afecta a archivos **no rastreados**. Si ya subiste un `.env` por error, añadirlo al `.gitignore` no lo borra del historial: tendrás que dejar de rastrearlo y, sobre todo, **cambiar los secretos** (lo verás en el curso de seguridad).

```bash
git rm --cached .env   # deja de rastrearlo, pero conserva el archivo en tu disco
```

## Errores comunes

- **`git add .` por costumbre.** Mete todo, incluidos cambios a medias y archivos temporales. Revisa con `git status` y usa `git add -p`.
- **Commits gigantes** con mensajes como "cambios" o "arreglos". Imposibles de revisar y de deshacer por partes.
- **Creer que `.gitignore` borra archivos ya subidos.** Solo evita añadir nuevos.
- **Trabajar sin mirar `git status`.** La mayoría de los sustos de Git vienen de no saber en qué zona está cada cosa.

<Callout type="exercise">
  1. Crea un repositorio de práctica (`git init`) y haz 5 commits pequeños usando `git add -p` y
  mensajes con Conventional Commits. 2. En uno de ellos, modifica dos cosas no relacionadas en el
  mismo archivo y usa `git add -p` para separarlas en dos commits. 3. Configura el alias `git lg` y
  revisa el historial resultante. 4. En tus proyectos reales, ejecuta `git ls-files | grep -i env` y
  comprueba que no hay ningún `.env` versionado.
</Callout>

  Puedes dibujar en papel las tres zonas de Git, indicar en cuál está cada archivo según `git
  status` y explicar qué es `HEAD`.
</Callout>

## Resumen

- Git tiene tres zonas: _working directory_, _staging area_ y repositorio.
- `add` prepara, `commit` guarda una foto completa enlazada con su padre.
- `HEAD` indica dónde estás; normalmente apunta a una rama.
- `git add -p` y `git diff --staged` hacen commits pequeños y revisados.
- Conventional Commits da mensajes claros y consistentes.
- `.gitignore` evita subir `node_modules`, compilados y secretos.
