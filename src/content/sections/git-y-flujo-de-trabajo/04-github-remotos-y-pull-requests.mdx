Tu historial vive solo en tu Mac. Un **remoto** es otra copia en GitHub: tu copia de seguridad, el punto de encuentro con otras personas y lo que dispara los despliegues de Vercel. Aquí subes `planificador` y completas el ciclo de una **Pull Request**.

**Requisitos:** el repositorio `planificador` de B2.3, una cuenta de GitHub y tu clave SSH configurada (si `ssh -T git@github.com` responde `Hi tu-usuario!`, está lista).

## Paso 1: crear el repositorio en GitHub

**Qué es:** `gh` es la herramienta oficial de GitHub para la terminal. Con ella, crear el repositorio, conectarlo y subirlo es un solo comando.

**Cómo se usa:** instálala con Homebrew e inicia sesión.

```bash
brew install gh
gh auth login
```

En `gh auth login` elige **GitHub.com**, **SSH**, **Skip** al subir clave (la tuya ya está) y **Login with a web browser**. Después, desde `planificador`:

```bash
gh repo create planificador --private --source=. --remote=origin --push
```

- **`--private`:** solo tú lo ves (`--public` para un portfolio). **`--source=.`:** la carpeta actual. **`--remote=origin`:** el nombre del remoto. **`--push`:** sube la rama actual.

Sin `gh`: crea el repositorio vacío en github.com (**sin** README ni `.gitignore`) y conéctalo a mano.

```bash
git remote add origin git@github.com:tu-usuario/planificador.git
git push -u origin main
```

```text
To github.com:tu-usuario/planificador.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

Comprueba la conexión:

```bash
git remote -v
git branch -vv
```

```text
origin	git@github.com:tu-usuario/planificador.git (fetch)
origin	git@github.com:tu-usuario/planificador.git (push)
  feat/peso-objetivo 27b5ff5 wip: peso objetivo
* main               fcd822e [origin/main] Merge branch 'feat/tema-sepia'
```

- **`origin` es un apodo** para la URL del remoto, por convención.
- **`[origin/main]`:** tu `main` **rastrea** el de GitHub. Lo hizo `-u`, y desde ahora `git push` y `git pull` sin argumentos saben con qué rama sincronizar.

<Callout type="risk">

- **URL SSH, no HTTPS:** con HTTPS, GitHub rechaza la contraseña (`Password authentication is not supported for Git operations`). Cámbiala con `git remote set-url origin git@github.com:tu-usuario/planificador.git`.
- **`git push` sube todo el historial:** un `.env` confirmado alguna vez llega a GitHub. Antes del primer _push_ de un proyecto antiguo, `git log --all --oneline -- .env`, y si sale algo, cambia esos secretos.
- **Un repositorio creado con README** tiene un _commit_ que tú no, y tu primer _push_ se rechaza. Arréglalo con `git pull --rebase origin main`.

</Callout>

## Paso 2: `fetch`, `pull` y `push`

**Qué es:** tu repositorio guarda **una copia de cómo estaba GitHub la última vez que preguntaste**: las ramas `origin/main`, `origin/feat/...`. Estos comandos la sincronizan.

| Comando     | Qué hace                                                        | Toca tus archivos |
| ----------- | --------------------------------------------------------------- | ----------------- |
| `git fetch` | Descarga los commits nuevos de GitHub y actualiza `origin/main` | No                |
| `git pull`  | `fetch` + mezcla `origin/main` en tu rama actual                | Sí                |
| `git push`  | Sube tus commits y mueve la rama en GitHub                      | No                |

**Cómo se usa:** en github.com, edita `README.md` con el lápiz, añade al final una sección "Licencia" con `Uso personal.` y pulsa **Commit changes**. En tu terminal:

```bash
git status
```

```text
On branch main
Your branch is up to date with 'origin/main'.
```

- **"Up to date" es con tu copia de `origin/main`,** que es anterior a la edición. Git no consulta GitHub hasta que se lo pides:

```bash
git fetch
git status
git log --oneline --graph --all --decorate -3
```

```text
From github.com:tu-usuario/planificador
   fcd822e..294df31  main       -> origin/main
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)
* 294df31 (origin/main, origin/HEAD) docs: añade la licencia
*   fcd822e (HEAD -> main) Merge branch 'feat/tema-sepia'
```

- **`fetch` no tocó tus archivos:** solo actualizó tu copia. Revisa antes de traerlo con `git diff main origin/main`.

```bash
git pull
```

```text
Updating fcd822e..294df31
Fast-forward
 README.md | 4 ++++
 1 file changed, 4 insertions(+)
```

<Callout type="risk">

- **`git status` no sabe nada de GitHub hasta el `fetch`.** VS Code lo hace solo con `git.autofetch`; en la terminal, empieza el día con `git switch main` y `git pull`.
- **`pull` trae la rama que rastrea la rama actual:** en la rama equivocada, mezcla cosas inesperadas.
- **Con más gente, no trabajes en `main`:** cada `pull` con líneas divergentes crea _merges_ inútiles (Paso 3).

</Callout>

## Paso 3: cuando tu `main` y el de GitHub divergen

**Qué es:** con un _commit_ local y otro en GitHub, las dos líneas divergen, como dos ramas. `pull --rebase` **reaplica tus _commits_ locales encima** de los que llegaron, en línea recta.

**Cómo se usa:** añade una sección "Autora" al README desde la web y, **sin `pull`**, cambia algo en local:

```bash
sed -i '' 's/vasos de 250 ml/vasos de 250 ml (un vaso estándar)/' src/agua.js
git commit -am "docs: aclara el tamaño del vaso"
git pull
```

```text
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.
```

- **Con _merge_** (`pull.rebase false`), cada vez se crea un _commit_ `Merge branch 'main' of github.com:…` que no aporta nada. **Con _rebase_**, el historial queda recto. Hazlo y déjalo configurado:

```bash
git pull --rebase
git config --global pull.rebase true
git log --oneline --graph -3
git push
```

```text
Successfully rebased and updated refs/heads/main.
* b3b639b docs: aclara el tamaño del vaso
* 1acc118 docs: añade la autoría
* 294df31 docs: añade la licencia
```

- **Tu _commit_ tiene un identificador nuevo:** el _rebase_ crea copias con otro padre.

<Callout type="risk">

- **Un _rebase_ puede dar un conflicto por cada _commit_.** Se resuelve como en B2.3, pero se sigue con `git rebase --continue`, y se cancela con `git rebase --abort`.
- **Nunca rebases _commits_ que otros ya tienen:** sus copias quedarían huérfanas. Tus _commits_ locales o tu propia rama, sí.

</Callout>

## Paso 4: una rama, un _push_ y una Pull Request

**Qué es:** una **Pull Request** (PR) propone mezclar una rama en `main`, con un espacio para revisar el _diff_, comentar y ejecutar comprobaciones automáticas antes.

**Cómo se usa:** crea la rama y `src/resumen.js`.

```bash
git switch -c feat/resumen-diario
```

```js
// Resumen del día: tareas pendientes y agua
const tareasPendientes = 2;
const vasos = 5;

function resumenDiario(pendientes, vasosDeAgua) {
  const tareas = pendientes === 1 ? "1 tarea pendiente" : `${pendientes} tareas pendientes`;
  return `Hoy: ${tareas} y ${vasosDeAgua * 250} ml de agua`;
}

console.log(resumenDiario(tareasPendientes, vasos));
```

```bash
node src/resumen.js
git add src/resumen.js
git commit -m "feat: resumen diario de tareas y agua"
git push -u origin feat/resumen-diario
```

```text
Hoy: 2 tareas pendientes y 1250 ml de agua
To github.com:tu-usuario/planificador.git
 * [new branch]      feat/resumen-diario -> feat/resumen-diario
branch 'feat/resumen-diario' set up to track 'origin/feat/resumen-diario'.
```

Crea la PR desde la terminal:

```bash
gh pr create --base main --title "feat: resumen diario de tareas y agua" --body "## Qué cambia
- Nuevo src/resumen.js con un resumen del día (tareas pendientes y agua).

## Cómo probarlo
node src/resumen.js

Debe mostrar: Hoy: 2 tareas pendientes y 1250 ml de agua"
```

`gh` responde con su URL (`https://github.com/tu-usuario/planificador/pull/1`). Ábrela:

```bash
gh pr view --web
```

- **Tres pestañas:** _Conversation_ (descripción y comentarios), _Commits_ y _Files changed_ (el _diff_, comentable línea a línea). Con Vercel, su bot añade la URL de _preview_ de la rama.
- **Una buena descripción dice qué cambia, por qué y cómo probarlo.** Tú dentro de seis meses eres otra persona.

Cada _push_ actualiza la PR. Gracias al `-u`, ya no hace falta indicar la rama:

```bash
printf '\n// Mostrar el resumen también los domingos\n' >> src/resumen.js
git commit -am "feat: nota sobre el domingo"
git push
```

```text
To github.com:tu-usuario/planificador.git
   28307f4..3ff385c  feat/resumen-diario -> feat/resumen-diario
```

<Callout type="risk">

- **Revisa tu propia PR antes de pedir revisión:** en _Files changed_ se ven el `console.log` olvidado o el archivo que no debía ir.
- **Las PR gigantes se aprueban a ciegas:** 2000 líneas reciben "LGTM"; 150 reciben comentarios útiles. Divídelas.
- **Comillas en `--body`:** la terminal las interpreta. Para textos largos, `gh pr create --fill` o `--web`.

</Callout>

## Paso 5: actualizar tu rama con `rebase`

**Qué es:** mientras tu PR espera, `main` avanza. **Rebasar tu rama sobre `origin/main`** pone tus _commits_ encima del último `main`.

**Cómo se usa:** edita otra vez el README en la web, en `main`.

```bash
git fetch
git log --oneline --graph --all --decorate -6
```

```text
* 3506c10 (origin/main, origin/HEAD) docs: matiza la licencia
| * 3ff385c (HEAD -> feat/resumen-diario, origin/feat/resumen-diario) feat: nota sobre el domingo
| * 28307f4 feat: resumen diario de tareas y agua
|/
* b3b639b (main) docs: aclara el tamaño del vaso
* 1acc118 docs: añade la autoría
* 294df31 docs: añade la licencia
```

```bash
git rebase origin/main
git log --oneline --graph --decorate -4
```

```text
Successfully rebased and updated refs/heads/feat/resumen-diario.
* 5b5bba6 (HEAD -> feat/resumen-diario) feat: nota sobre el domingo
* ae286dd feat: resumen diario de tareas y agua
* 3506c10 (origin/main, origin/HEAD) docs: matiza la licencia
* b3b639b (main) docs: aclara el tamaño del vaso
```

Tus dos _commits_ están encima, con identificadores nuevos. Al subirlos:

```bash
git push
```

```text
 ! [rejected]        feat/resumen-diario -> feat/resumen-diario (non-fast-forward)
error: failed to push some refs to 'github.com:tu-usuario/planificador.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
```

- **GitHub rechaza el _push_:** su rama tiene `28307f4` y `3ff385c`, que el _rebase_ sustituyó por copias. Aquí **sí** quieres reemplazarla, porque es tuya:

```bash
git push --force-with-lease
```

```text
 + 3ff385c...5b5bba6 feat/resumen-diario -> feat/resumen-diario (forced update)
```

<Callout type="risk">

- **No hagas `git pull` tras un _rebase_,** aunque lo sugiera el mensaje: duplicaría cada cambio. Usa `--force-with-lease`.
- **`--force-with-lease`, no `--force`:** se niega si alguien subió _commits_ desde tu último `fetch`. Y **nunca** fuerces `main`.
- **`git merge origin/main` también vale:** no reescribe ni obliga a forzar, mejor si alguien más trabaja en la rama. Con _squash merge_ (Paso 6), la diferencia en `main` desaparece.

</Callout>

## Paso 6: mezclar con _squash merge_ y limpiar

**Qué es:** **Squash and merge** junta todos los _commits_ de la PR en **uno solo** en `main`, con el título de la PR. Así `main` tiene un _commit_ por funcionalidad, aunque la rama tuviera veinte "wip".

**Cómo se usa:** desde la terminal.

```bash
gh pr checks
gh pr merge --squash --delete-branch
```

- **`gh pr checks`** muestra las comprobaciones (Vercel, tests). **`gh pr merge --squash --delete-branch`** mezcla, borra la rama remota y te deja en `main` actualizado, sin la rama local.

Si mezclas desde la web, limpia tú:

```bash
git switch main
git pull --prune
git log --oneline -3
```

```text
Updating b3b639b..7c19077
Fast-forward
 README.md      |  2 +-
 src/resumen.js | 12 ++++++++++++
 2 files changed, 13 insertions(+), 1 deletion(-)
 create mode 100644 src/resumen.js
7c19077 feat: resumen diario de tareas y agua (#1)
3506c10 docs: matiza la licencia
b3b639b docs: aclara el tamaño del vaso
```

- **Un _commit_ con el número de la PR (`#1`),** que en GitHub enlaza a la discusión. `--prune` borra tus copias de ramas remotas que ya no existen.

```bash
git branch -vv
git branch -d feat/resumen-diario
```

```text
  feat/resumen-diario 5b5bba6 [origin/feat/resumen-diario: gone] feat: nota sobre el domingo
* main                7c19077 [origin/main] feat: resumen diario de tareas y agua (#1)
error: the branch 'feat/resumen-diario' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feat/resumen-diario'
```

- **`gone`:** la rama ya no existe en GitHub. **`-d` se niega** porque, con _squash_, sus _commits_ no están en `main`: hay uno nuevo con el mismo contenido y otro identificador. Con la PR mezclada, es seguro forzar:

```bash
git branch -D feat/resumen-diario
```

<Callout type="risk">

- **No sigas trabajando en una rama tras su _squash_:** sus _commits_ viejos chocarían con los de `main`. Crea una rama nueva desde `main` actualizado.
- **`-D` solo con `gone` o con la PR mezclada:** si no, pierdes ese trabajo (salvo por `reflog`).
- **El título de la PR queda en `main` para siempre:** escríbelo como un buen mensaje de _commit_. En _Settings_ → _General_, deja solo **Allow squash merging** y activa **Automatically delete head branches**.

</Callout>

## Paso 7: proteger `main`

**Qué es:** una regla de protección hace que `main` **solo** cambie mediante PR, no por un `git push` despistado.

**Cómo se usa:** en el repositorio, _Settings_ → _Rules_ → _Rulesets_ → _New ruleset_ → _New branch ruleset_:

1. **Ruleset name:** `main protegido`. **Enforcement status:** _Active_.
2. **Target branches:** _Add target_ → _Include default branch_.
3. Marca **Restrict deletions** y **Block force pushes**.
4. Marca **Require a pull request before merging**. Si trabajas solo, deja **Required approvals** en 0 (GitHub no te deja aprobar tus propias PR).
5. Si tienes comprobaciones automáticas (Vercel o, más adelante, tests en CI), marca **Require status checks to pass** y añádelas.
6. Pulsa **Create**.

Desde entonces, un `git push` directo a `main` se rechaza.

<Callout type="risk">

- **En repositorios privados del plan gratuito, las reglas no se aplican:** GitHub solo las hace cumplir en repositorios públicos o con un plan de pago. Ahí, la protección es tu disciplina.
- **No te bloquees:** una comprobación obligatoria que nunca se ejecuta (un nombre mal escrito) impide mezclar cualquier PR. Añádelas tras verlas funcionar.
- **No te pongas en la _Bypass list_ "por si acaso":** la regla existe para los días con prisa.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Sube uno de tus proyectos reales (el Planificador 2026 o tu app de entrenamiento) a GitHub con `gh repo create`, si aún no está, y conéctalo a Vercel.
2. Configura el repositorio: solo _squash merging_, borrado automático de ramas y la regla de protección de `main`.
3. Haz el próximo cambio real del proyecto mediante una PR: rama, commits, `push -u`, `gh pr create` con qué/por qué/cómo probarlo, revisión de _Files changed_ y de la _preview_ de Vercel, y `gh pr merge --squash --delete-branch`.
4. Comprueba con `git log --oneline` que `main` termina con un commit `(#1)` y que la rama ya no existe ni en local ni en GitHub (`git branch -a`).

</Callout>

Solución: la secuencia completa. Sustituye `mi-proyecto` y la rama por los tuyos.

```bash
# 1. Subir el proyecto (solo la primera vez)
cd ~/proyectos/mi-proyecto
git status
git log --all --oneline -- .env
gh repo create mi-proyecto --private --source=. --remote=origin --push

# 2. Configurar el repositorio: solo squash y borrado automático de ramas
gh repo edit --enable-squash-merge --enable-merge-commit=false --enable-rebase-merge=false --delete-branch-on-merge

# 3. El ciclo de una PR
git switch main
git pull
git switch -c feat/mi-cambio
# Aquí editas, pruebas y haces commits pequeños, con git add y git commit (B2.1)
git push -u origin feat/mi-cambio
gh pr create --base main --fill
gh pr view --web
gh pr checks
gh pr merge --squash --delete-branch

# 4. Comprobar
git log --oneline -3
git branch -a
```

- **La regla de protección se crea en la web,** como en el Paso 7: `gh` no tiene un comando sencillo para ello.
- **Vercel:** en vercel.com → _Add New_ → _Project_, importa el repositorio. Desde entonces, cada rama tiene su _preview_ y cada cambio en `main` despliega producción.

<Callout type="risk">

- **`git log --all --oneline -- .env` antes del primer _push_:** si devuelve algo, cambia esos secretos **antes** de subir.
- **`gh pr create --fill`** toma el título y la descripción de tus _commits_. Complétala en la web con el porqué y el cómo probarlo.
- **Si la _preview_ falla y producción no,** revisa las variables del entorno _Preview_ en Vercel. Es el motivo más habitual.

</Callout>

<Callout type="mastery">

Tu historial de `main` se compone solo de PRs mezcladas, sabes que `git status` no ve GitHub hasta que haces `fetch`, actualizas tu rama con `rebase` y `--force-with-lease` sin miedo, y nunca fuerzas un _push_ a `main`.

</Callout>

## Resumen

- `origin` es un apodo; `push -u` conecta tu rama con la de GitHub.
- `fetch` actualiza tu copia sin tocar archivos; `pull` = `fetch` + mezcla, con `pull.rebase true`.
- Tras rebasar una rama ya subida: `--force-with-lease`, nunca en `main`.
- Una PR propone una mezcla revisada; con _squash_, un _commit_ por PR.
- Tras el _squash_, `-D` a la rama (`gone`) y una rama nueva para lo siguiente.
