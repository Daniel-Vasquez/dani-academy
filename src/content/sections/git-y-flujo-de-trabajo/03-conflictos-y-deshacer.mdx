Los conflictos y los "¿cómo deshago esto?" dan miedo cuando no sabes qué hace cada comando ni qué se puede recuperar. Aquí provocas cada situación a propósito en `planificador` y terminas recuperando un _commit_ "borrado".

**Requisitos:** el repositorio `planificador` de B2.2, en `main` y con `git status` limpio.

## Paso 1: provocar un conflicto

**Qué es:** un conflicto aparece cuando **dos ramas cambian las mismas líneas** de forma distinta. Git mezcla solo las líneas distintas; si chocan, te pregunta.

**Cómo se usa:** dos ideas sobre el objetivo de agua, cada una en su rama.

```bash
git switch -c feat/objetivo-nutriologa
```

En `src/agua.js`, cambia `const OBJETIVO_ML = 2000;` por:

```js
const OBJETIVO_ML = 2500; // recomendación de la nutrióloga
```

```bash
git commit -am "feat: sube el objetivo de agua a 2,5 L"
git switch main
git switch -c feat/objetivo-verano
```

En esta otra rama, cambia **la misma línea** por:

```js
const OBJETIVO_ML = 3000; // en verano se suda más
```

```bash
git commit -am "feat: objetivo de agua de verano"
git switch main
git merge feat/objetivo-nutriologa
git merge feat/objetivo-verano
```

El primer _merge_ es un _fast-forward_. El segundo se detiene:

```text
Auto-merging src/agua.js
CONFLICT (content): Merge conflict in src/agua.js
Automatic merge failed; fix conflicts and then commit the result.
```

<Callout type="risk">

- **Un conflicto no rompe nada:** el _merge_ está **en pausa**, esperando tu decisión, y puedes cancelarlo (Paso 2).
- **Cuanto más vive una rama, más conflictos:** `main` cambia mientras tanto. Ramas cortas.
- **Los formateadores provocan conflictos falsos:** una rama que reformatea un archivo entero choca con cualquier cambio en él. Misma configuración de Prettier en todo el equipo.

</Callout>

## Paso 2: leer el conflicto

**Qué es:** Git escribe **las dos versiones** en el archivo, entre marcadores. Lo que queda fuera de ellos ya se mezcló.

**Cómo se usa:** mira el estado y abre el archivo.

```bash
git status
```

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   src/agua.js
```

```text
// Registro de hidratación: vasos de 250 ml
const ML_POR_VASO = 250;
<<<<<<< HEAD
const OBJETIVO_ML = 2500; // recomendación de la nutrióloga
=======
const OBJETIVO_ML = 3000; // en verano se suda más
>>>>>>> feat/objetivo-verano

function progresoAgua(vasos) {
```

- **`both modified`:** las dos ramas cambiaron el archivo.
- **Entre `<<<<<<< HEAD` y `=======`:** tu versión, la de la rama actual (_Current Change_ en VS Code). **Entre `=======` y `>>>>>>>`:** la de la rama que mezclas (_Incoming Change_).

Para echarte atrás, en cualquier momento antes del _commit_:

```bash
git merge --abort
```

Hazlo, activa esta configuración y repite el _merge_:

```bash
git config --global merge.conflictStyle zdiff3
git merge feat/objetivo-verano
```

```text
<<<<<<< HEAD
const OBJETIVO_ML = 2500; // recomendación de la nutrióloga
||||||| d387499
const OBJETIVO_ML = 2000;
=======
const OBJETIVO_ML = 3000; // en verano se suda más
>>>>>>> feat/objetivo-verano
```

- **La sección `|||||||` muestra el original,** `2000`: cada rama lo cambió por un motivo. A menudo, la solución es **combinar las dos intenciones**, no elegir una.

<Callout type="risk">

- **Aceptar un lado sin entender el otro** descarta en silencio el trabajo de alguien, o el tuyo de hace dos días. Pregúntate qué quería cada rama.
- **Un archivo puede tener varios conflictos:** busca `<<<<<<<` en todo el archivo.

</Callout>

## Paso 3: resolver el conflicto

**Qué es:** resolver es **editar el archivo hasta dejarlo como debe quedar**, sin marcadores. Después, `git add` lo marca como resuelto y `git commit` termina el _merge_.

**Cómo se usa:** aquí las dos ideas son compatibles: 2,5 L de base y un extra en verano. Sustituye `src/agua.js`:

```js
// Registro de hidratación: vasos de 250 ml
const ML_POR_VASO = 250;
const OBJETIVO_ML = 2500; // recomendación de la nutrióloga
const EXTRA_VERANO_ML = 500; // en verano se suda más

function progresoAgua(vasos, esVerano = false) {
  const objetivo = OBJETIVO_ML + (esVerano ? EXTRA_VERANO_ML : 0);
  const ml = vasos * ML_POR_VASO;
  const porcentaje = Math.min(100, Math.round((ml / objetivo) * 100));
  return `${ml} ml de ${objetivo} ml (${porcentaje} %)`;
}

console.log(`Hoy: ${progresoAgua(5)}`);
console.log(`Hoy en verano: ${progresoAgua(5, true)}`);
```

```bash
node src/agua.js
git add src/agua.js
git commit --no-edit
git log --oneline --graph -4
git branch -d feat/objetivo-nutriologa feat/objetivo-verano
```

```text
Hoy: 1250 ml de 2500 ml (50 %)
Hoy en verano: 1250 ml de 3000 ml (42 %)
[main dab9f79] Merge branch 'feat/objetivo-verano'
*   dab9f79 Merge branch 'feat/objetivo-verano'
|\
| * 1dcd2fa feat: objetivo de agua de verano
* | 5704c16 feat: sube el objetivo de agua a 2,5 L
|/
```

- **En VS Code,** cada bloque tiene _Accept Current Change_, _Accept Incoming Change_, _Accept Both Changes_ y _Compare Changes_. _Resolve in Merge Editor_ abre un editor de tres paneles. Al guardar, `+` en _Source Control_ equivale a `git add`.

<Callout type="risk">

- **Git deja confirmar con los marcadores dentro:** acabarían en producción como un `SyntaxError`. Antes del _commit_:

  ```bash
    git diff --cached --check
  ```

  Si quedan marcadores, verás `src/agua.js:3: leftover conflict marker` y un código de error.

- **"Accept Both Changes" casi nunca es la respuesta:** aquí dejaría dos `const OBJETIVO_ML`, un `SyntaxError`. Sirve en listas, donde las dos líneas conviven.
- **Sin marcadores no significa correcto:** ejecuta el proyecto. En Astro, `npm run check` y `npm run build`.

</Callout>

## Paso 4: descartar cambios sin confirmar (`restore`)

**Qué es:** `git restore archivo` devuelve el archivo a como estaba en _staging_ o en el último _commit_. `git restore --staged archivo` lo saca de _staging_ sin perder el cambio.

**Cómo se usa:** una prueba que no quieres conservar.

```bash
echo 'console.log("prueba que no quiero");' >> src/tareas.js
git status --short
git restore src/tareas.js
git status --short
```

```text
 M src/tareas.js
```

La segunda vez, `git status --short` no muestra nada. Ahora, algo añadido a _staging_ por error:

```bash
echo "## Notas" >> README.md
git add README.md
git status --short
git restore --staged README.md
git status --short
git restore README.md
```

```text
M  README.md
 M README.md
```

- **La `M` cambia de columna:** a la izquierda está en _staging_; tras `restore --staged`, a la derecha. El último `git restore` lo descarta del todo.

<Callout type="risk">

- **`git restore archivo` no tiene vuelta atrás:** el cambio nunca fue un _commit_, y ni `reflog` lo recupera. Mira antes `git diff archivo`; el _Timeline_ de VS Code a veces lo salva.
- **`git restore .`** descarta **todos** los archivos. Solo tras revisar `git status`.
- **Los archivos nuevos no se tocan:** para borrarlos, `git clean -n` (muestra qué borraría) y después `git clean -f`.

</Callout>

## Paso 5: corregir el último _commit_ (`commit --amend`)

**Qué es:** `--amend` **sustituye** el último _commit_ por uno nuevo, para corregir el mensaje o añadir algo olvidado.

**Cómo se usa:** un _commit_ con erratas. Crea `src/semana.js`:

```js
// Días de la semana en orden, empezando en lunes
const DIAS = ["lunes", "martes", "miércoles", "jueves", "viernes", "sábado", "domingo"];

console.log(`La semana tiene ${DIAS.length} días y empieza en ${DIAS[0]}`);
```

```bash
git add src/semana.js
git commit -m "feat: dias de la semna"
git log --oneline -1
git commit --amend -m "feat: lista los días de la semana"
git log --oneline -2
```

```text
cf82712 feat: dias de la semna
[main b411f4b] feat: lista los días de la semana
 Date: Fri Oct 9 13:20:00 2026 -0600
 1 file changed, 4 insertions(+)
 create mode 100644 src/semana.js
b411f4b feat: lista los días de la semana
dab9f79 Merge branch 'feat/objetivo-verano'
```

Añade algo olvidado: documenta el archivo al final de `README.md`.

```markdown

## Semana

`node src/semana.js` lista los días de la semana.
```

```bash
git add README.md
git commit --amend --no-edit
git show --stat --oneline HEAD
```

```text
[main eaaa7ed] feat: lista los días de la semana
 Date: Fri Oct 9 13:20:00 2026 -0600
 2 files changed, 8 insertions(+)
 create mode 100644 src/semana.js
eaaa7ed feat: lista los días de la semana
 README.md     | 4 ++++
 src/semana.js | 4 ++++
 2 files changed, 8 insertions(+)
```

- **`--no-edit`** conserva el mensaje. El _commit_ incluye los dos archivos, como si lo hubieras hecho bien a la primera.

<Callout type="risk">

- **`--amend` crea otro _commit_:** `cf82712` → `b411f4b` → `eaaa7ed`. Si el original ya estaba en GitHub, `git push` se rechaza. **Solo con _commits_ que no has subido.**
- **Solo afecta al último _commit_.** Para uno anterior, `git rebase -i`; para uno compartido, `revert` (Paso 6).

</Callout>

## Paso 6: deshacer un _commit_ ya compartido (`revert`)

**Qué es:** `git revert` crea un _commit_ **nuevo** que hace lo contrario de otro. El historial solo crece, así que es la forma segura de deshacer en ramas compartidas.

**Cómo se usa:** quita los colores de B2.2. Búscalos por su mensaje y revierte el identificador que te salga:

```bash
git log --oneline --grep "color"
git revert --no-edit 6b539d0
git log --oneline -2
git show --stat HEAD
```

```text
6b539d0 feat: asigna un color a cada categoría
[main 830e591] Revert "feat: asigna un color a cada categoría"
 1 file changed, 11 deletions(-)
 delete mode 100644 src/colores.js
830e591 Revert "feat: asigna un color a cada categoría"
eaaa7ed feat: lista los días de la semana
```

- **El original sigue ahí,** y el mensaje nuevo dice cuál deshizo (`This reverts commit 6b539d0…`).

Para deshacer una funcionalidad entera, revierte su _merge commit_ (la racha, mezclada con `--no-ff`). Pero tiene dos padres:

```bash
git revert --no-edit eaf25e7
```

```text
error: commit eaf25e7e2ce92e33a0f4af4ebec17353024bc433 is a merge but no -m option was given.
fatal: revert failed
```

```bash
git revert --no-edit -m 1 eaf25e7
ls src
```

```text
[main e11b414] Revert "Merge branch 'feat/racha'"
 1 file changed, 11 deletions(-)
 delete mode 100644 src/racha.js
agua.js
semana.js
tareas.js
tema.js
```

- **`-m 1`:** el padre 1 es la línea principal (`main`), y se deshace lo que aportó la rama. Casi siempre es `-m 1`.

<Callout type="risk">

- **Revertir un _merge_ tiene trampa:** Git recuerda que esos _commits_ ya se mezclaron, y volver a mezclar la rama solo trae lo nuevo. Para reintroducirla, revierte el _revert_.
- **Un _revert_ también puede dar conflictos,** si _commits_ posteriores tocaron las mismas líneas. Se resuelven como en el Paso 3, o se cancela con `git revert --abort`.

</Callout>

## Paso 7: mover la rama hacia atrás (`reset`)

**Qué es:** `git reset` mueve el puntero de la rama actual a otro _commit_. Sus tres modos deciden qué pasa con los cambios de los _commits_ que quitas. `HEAD~1` es "el _commit_ anterior a `HEAD`".

| Modo      | El commit           | Los cambios quedan en             |
| --------- | ------------------- | --------------------------------- |
| `--soft`  | Se quita de la rama | _Staging_                         |
| `--mixed` | Se quita de la rama | Tu mesa (_working directory_)     |
| `--hard`  | Se quita de la rama | **En ningún sitio** (descartados) |

**Cómo se usa:** practica con `src/peso.js`.

```js
// Registro de peso semanal (kg)
const pesos = [80.5, 79.8, 79.2, 78.9];

const cambio = pesos[pesos.length - 1] - pesos[0];
console.log(`Cambio en ${pesos.length} semanas: ${cambio.toFixed(1)} kg`);
```

```bash
git add src/peso.js
git commit -m "feat: registro de peso semanal"
git reset --soft HEAD~1
git status --short
```

```text
A  src/peso.js
```

- **`--soft`:** los cambios quedan en _staging_. Sirve para rehacer el mensaje o juntar varios _commits_.

```bash
git commit -m "feat: registro de peso semanal"
git reset HEAD~1
git status --short
```

```text
?? src/peso.js
```

- **`--mixed`** (el modo por defecto): los cambios quedan en el _working directory_. Sirve para dividir el _commit_ con `git add -p`.

```bash
git add src/peso.js
git commit -m "feat: registro de peso semanal"
git reset --hard HEAD~1
ls src
```

```text
HEAD is now at e11b414 Revert "Merge branch 'feat/racha'"
agua.js
semana.js
tareas.js
tema.js
```

- **`--hard`:** el _commit_ y sus cambios desaparecen. `peso.js` ya no está, pero no está perdido (Paso 9).

<Callout type="risk">

- **`reset` reescribe el historial,** como `--amend`. Con _commits_ subidos, tendrías que forzar el _push_ y borrar el trabajo de otros. **`revert` para lo compartido, `reset` solo para lo local.**
- **`reset --hard` destruye también los cambios sin confirmar,** y esos no los recupera nada. Antes, `git status`, y _commit_ o `stash` si hay algo que conservar.

</Callout>

## Paso 8: guardar trabajo a medias (`stash`)

**Qué es:** `git stash` guarda tus cambios sin confirmar en un cajón aparte y deja el _working directory_ limpio. Sirve cuando llega algo urgente a mitad de una funcionalidad.

**Cómo se usa:** recupera `peso.js` (lo entenderás en el Paso 9) y crea una rama de trabajo.

```bash
git reset --hard HEAD@{1}
git switch -c feat/peso-objetivo
```

En `src/peso.js`, añade `const OBJETIVO_KG = 75;` justo antes de `const cambio`, y crea unas notas:

```bash
printf '// Notas sueltas, sin terminar\n' > src/notas.js
git status --short
```

```text
 M src/peso.js
?? src/notas.js
```

Guárdalo todo, **incluidos los archivos nuevos** (`-u`), con un nombre:

```bash
git stash push -u -m "peso objetivo a medias"
git status --short
git stash list
```

```text
Saved working directory and index state On feat/peso-objetivo: peso objetivo a medias
stash@{0}: On feat/peso-objetivo: peso objetivo a medias
```

Haz el arreglo urgente en su rama desde `main`:

```bash
git switch main
git switch -c fix/semana-domingo
```

Sustituye `src/semana.js`:

```js
// Días de la semana en orden, empezando en lunes
const DIAS = ["lunes", "martes", "miércoles", "jueves", "viernes", "sábado", "domingo"];

console.log(`La semana tiene ${DIAS.length} días y empieza en ${DIAS[0]} y termina en ${DIAS.at(-1)}`);
```

```bash
node src/semana.js
git commit -am "fix: muestra también el último día de la semana"
git switch main
git merge fix/semana-domingo
git branch -d fix/semana-domingo
```

```text
La semana tiene 7 días y empieza en lunes y termina en domingo
```

Vuelve a tu trabajo y saca los cambios del cajón:

```bash
git switch feat/peso-objetivo
git stash pop
git status --short
```

```text
 M src/peso.js
?? src/notas.js
```

- **`pop` aplica el último _stash_ y lo borra** del cajón (`Dropped refs/stash@{0}`).

<Callout type="risk">

- **Sin `-u`, los archivos nuevos no entran** y viajan a la otra rama. Usa `git stash push -u` siempre.
- **Los _stash_ olvidados se acumulan** y, sin nombre, no sabes qué contienen. Usa `-m`, y si el cambio va a vivir más de un día, mejor un _commit_ en su rama.
- **`stash pop` puede dar conflictos:** se resuelven como en el Paso 3, y si falla, el _stash_ **no** se borra.

</Callout>

## Paso 9: tu red de seguridad, `git reflog`

**Qué es:** un diario local de **cada sitio por el que ha pasado `HEAD`**: _commits_, cambios de rama, _resets_, _merges_. Un _commit_ "borrado" sigue existiendo; solo ninguna rama apunta a él.

**Cómo se usa:** así se veía justo después del `reset --hard` del Paso 7.

```bash
git reflog -6
```

```text
e11b414 HEAD@{0}: reset: moving to HEAD~1
8ca64f9 HEAD@{1}: commit: feat: registro de peso semanal
e11b414 HEAD@{2}: reset: moving to HEAD~1
799fdb8 HEAD@{3}: commit: feat: registro de peso semanal
e11b414 HEAD@{4}: reset: moving to HEAD~1
7a445d6 HEAD@{5}: commit: feat: registro de peso semanal
```

- **`HEAD@{0}` es ahora; `HEAD@{1}`, un movimiento antes:** el _commit_ que acababas de quitar. Para recuperarlo, mueve la rama de vuelta:

```bash
git reset --hard HEAD@{1}
node src/peso.js
```

```text
HEAD is now at 8ca64f9 feat: registro de peso semanal
Cambio en 4 semanas: -1.6 kg
```

- **Sirve para todo lo reciente:** una rama borrada con `-D`, un `--amend` o un _merge_ que salió mal. Busca el último momento bueno y vuelve con `git reset --hard <id>`, o crea una rama ahí: `git branch rescate <id>`.

<Callout type="risk">

- **El reflog es local y caduca:** no se sube a GitHub, un clon lo tiene vacío y Git limpia las entradas sin rama tras unos 30 días.
- **No recupera lo que nunca fue _commit_:** lo descartado con `restore` o con un `reset --hard` sin confirmar. **Un _commit_ es un punto de guardado.**
- **`HEAD@{n}` cambia con cada movimiento:** lo que era `HEAD@{1}` pasa a `HEAD@{2}`. Mira el reflog de nuevo o usa el identificador, que no cambia.

</Callout>

## Qué comando usar para deshacer

| Quiero…                                        | Comando                                 | ¿Se puede deshacer?          |
| ---------------------------------------------- | --------------------------------------- | ---------------------------- |
| Descartar cambios de un archivo sin confirmar  | `git restore archivo`                   | No                           |
| Sacar un archivo de _staging_                  | `git restore --staged archivo`          | Sí (no pierde nada)          |
| Corregir el último commit (no subido)          | `git commit --amend`                    | Sí, con `reflog`             |
| Deshacer un commit ya subido                   | `git revert <id>`                       | Sí, con otro `revert`        |
| Quitar commits locales y conservar los cambios | `git reset --soft` o `git reset HEAD~1` | Sí, con `reflog`             |
| Quitar commits locales y sus cambios           | `git reset --hard HEAD~1`               | Los commits sí, con `reflog` |
| Apartar trabajo a medias                       | `git stash push -u -m "…"`              | Sí, con `stash pop`          |
| Cancelar un merge con conflictos               | `git merge --abort`                     | Sí                           |

## Ejercicio práctico

<Callout type="exercise">

1. Desde `main`, crea dos ramas que cambien **la misma línea** de `src/tema.js`: en `feat/tema-oscuro-defecto`, la línea `const TEMAS = ["light", "dark"];` pasa a `["dark", "light"]` con el comentario `// oscuro primero`; en `feat/tema-sepia`, pasa a `["light", "dark", "sepia"]`.
2. Mezcla las dos en `main`, lee el conflicto (con `zdiff3`) y resuélvelo combinando las dos intenciones: oscuro primero **y** sepia disponible.
3. Comprueba con `git diff --cached --check` que no quedan marcadores, ejecuta `node src/tema.js` y termina el merge.
4. Haz un `git reset --hard HEAD~1` "por error" (perderás el merge) y recupéralo con `git reflog`.
5. Explica con tus palabras por qué en el paso 4 no debes usar `reset` si ya hubieras subido el merge a GitHub, y qué usarías en su lugar.

</Callout>

Solución. Primero, aparca el trabajo de `feat/peso-objetivo` y vuelve a `main`:

```bash
git switch feat/peso-objetivo
git add src/peso.js src/notas.js
git commit -m "wip: peso objetivo"
git switch main
```

Las dos ramas (`sed -i ''` edita desde la terminal en macOS; también vale a mano):

```bash
git switch -c feat/tema-oscuro-defecto
sed -i '' 's/const TEMAS = \["light", "dark"\];/const TEMAS = ["dark", "light"]; \/\/ oscuro primero/' src/tema.js
git commit -am "feat: el tema oscuro pasa a ser el primero"
git switch main
git switch -c feat/tema-sepia
sed -i '' 's/const TEMAS = \["light", "dark"\];/const TEMAS = ["light", "dark", "sepia"];/' src/tema.js
git commit -am "feat: añade el tema sepia"
git switch main
git merge feat/tema-oscuro-defecto
git merge feat/tema-sepia
```

El conflicto:

```text
<<<<<<< HEAD
const TEMAS = ["dark", "light"]; // oscuro primero
||||||| b2e155f
const TEMAS = ["light", "dark"];
=======
const TEMAS = ["light", "dark", "sepia"];
>>>>>>> feat/tema-sepia
```

`src/tema.js` resuelto:

```js
// Tema de color del Planificador: claro u oscuro
const TEMAS = ["dark", "light", "sepia"]; // oscuro primero

function siguienteTema(actual) {
  return actual === "light" ? "dark" : "light";
}

function esTemaValido(valor) {
  return TEMAS.includes(valor);
}

console.log(`Tema inicial: light → tras pulsar el botón: ${siguienteTema("light")}`);
console.log(`¿"sepia" es un tema válido? ${esTemaValido("sepia")}`);
```

```bash
git add src/tema.js
git diff --cached --check
node src/tema.js
git commit --no-edit
git branch -d feat/tema-oscuro-defecto feat/tema-sepia
```

```text
Tema inicial: light → tras pulsar el botón: dark
¿"sepia" es un tema válido? true
```

El "error" y la recuperación:

```bash
git reset --hard HEAD~1
git reflog -3
git reset --hard HEAD@{1}
git log --oneline --graph -4
```

- **En el reflog** verás `HEAD@{0}: reset: moving to HEAD~1` y, debajo, `HEAD@{1}: commit (merge): Merge branch 'feat/tema-sepia'`. Tras el último `reset`, el _merge_ vuelve a `main`.
- **Si ya estuviera en GitHub,** `reset` haría divergir tu `main` del remoto, y subirlo exigiría forzar el _push_ y borrar el _commit_ para todos. Lo correcto: `git revert -m 1 <id-del-merge>`.

<Callout type="risk">

- **`HEAD~1` en un _merge commit_ es su primer padre,** la línea de `main`. Por eso el `reset` solo pierde el _merge_ y la rama de sepia.

<Callout type="mastery">

Un conflicto ya no te produce ansiedad: lo lees con `zdiff3`, combinas las intenciones de las dos ramas y compruebas que no quedan marcadores. Sabes cuándo usar `revert` (lo compartido) y cuándo `reset` (lo local), y recuperas un commit perdido con `git reflog`.

</Callout>

## Resumen

- Un conflicto es un _merge_ en pausa: edita, quita marcadores, `git add` y `git commit`, o `--abort`.
- `zdiff3` muestra el original y ayuda a combinar intenciones.
- `restore` descarta sin vuelta atrás; `--amend` rehace el último _commit_ local.
- `revert` para lo compartido; `reset` solo para lo local.
- `stash -u` aparta trabajo a medias; `reflog` recupera _commits_ "perdidos".
