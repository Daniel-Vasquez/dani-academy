Hasta ahora, si necesitabas `Ejercicio` en dos archivos, lo copiabas. Aquí reorganizas el playground como un proyecto real: tipos en `src/tipos/`, `import type`, librerías con sus tipos, el alias `@/` y el `tsconfig.json` de esta plataforma explicado.

**Requisitos:** el `ts-playground` con el `tsconfig.json` de B1.1 (`verbatimModuleSyntax` activado).

## Paso 1: mover los tipos a un módulo propio

**Qué es:** un **módulo** es un archivo que exporta cosas (`export`) para que otros las importen (`import`).

**Cómo se usa:** crea `src/tipos/entreno.ts`.

```ts
// Archivo: src/tipos/entreno.ts
// Tipos (desaparecen al compilar)
export type Momento = "desayuno" | "comida" | "cena" | "snack";

export interface Ejercicio {
  readonly nombre: string;
  series: number;
  repeticiones: number;
  pesoKg: number;
}

export interface DiaEntreno {
  readonly fecha: string; // formato AAAA-MM-DD
  ejercicios: Ejercicio[];
  aguaMl: number;
}

// Valores (existen en ejecución)
export const OBJETIVO_AGUA_ML = 2000;

export function volumenTotal(dia: DiaEntreno): number {
  return dia.ejercicios.reduce((total, e) => total + e.series * e.repeticiones * e.pesoKg, 0);
}
```

- **Tipos y valores:** `type` e `interface` desaparecen al compilar; `const` y `function` siguen en ejecución. Esa diferencia es la clave del Paso 2.

<Callout type="risk">

- **Un archivo de tipos por dominio** (`tipos/entreno.ts`, `tipos/usuario.ts`), no un `tipos.ts` gigante que choque en cada _merge_.
- **Nada de lógica pesada junto a los tipos:** si el archivo empieza a importar librerías o a hablar con la base de datos, separa esa lógica (la capa de servicios, I3).

</Callout>

## Paso 2: importar con `import type`

**Qué es:** con `verbatimModuleSyntax`, TypeScript compila cada `import` **tal cual lo escribes**, quitando solo los marcados como tipos. Un tipo en un `import` normal quedaría en el JavaScript final, y fallaría en ejecución porque no existe.

**Cómo se usa:** crea `src/07-app.ts` con este error a propósito:

```ts
// Archivo: src/07-app.ts
import { DiaEntreno, OBJETIVO_AGUA_ML, volumenTotal } from "./tipos/entreno";

const hoy: DiaEntreno = {
  fecha: "2026-10-09",
  ejercicios: [
    { nombre: "peso muerto", series: 3, repeticiones: 5, pesoKg: 100 },
    { nombre: "dominadas", series: 4, repeticiones: 8, pesoKg: 0 },
  ],
  aguaMl: 1500,
};

console.log(`Volumen: ${volumenTotal(hoy)} kg`);
console.log(`Agua: ${hoy.aguaMl}/${OBJETIVO_AGUA_ML} ml`);
```

```bash
npm run typecheck
```

```text
error TS1484: 'DiaEntreno' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

Corrígelo de una de estas dos formas:

```ts
// Opción A: dos imports separados
import type { DiaEntreno } from "./tipos/entreno";
import { OBJETIVO_AGUA_ML, volumenTotal } from "./tipos/entreno";
```

```ts
// Opción B: un solo import, marcando el tipo con "type" en línea
import { type DiaEntreno, OBJETIVO_AGUA_ML, volumenTotal } from "./tipos/entreno";
```

El archivo completo, con la opción B:

```ts
// Archivo: src/07-app.ts
import { type DiaEntreno, OBJETIVO_AGUA_ML, volumenTotal } from "./tipos/entreno";

const hoy: DiaEntreno = {
  fecha: "2026-10-09",
  ejercicios: [
    { nombre: "peso muerto", series: 3, repeticiones: 5, pesoKg: 100 },
    { nombre: "dominadas", series: 4, repeticiones: 8, pesoKg: 0 },
  ],
  aguaMl: 1500,
};

console.log(`Volumen: ${volumenTotal(hoy)} kg`);
console.log(`Agua: ${hoy.aguaMl}/${OBJETIVO_AGUA_ML} ml`);
```

```bash
npm run typecheck
npm start -- src/07-app.ts
```

```text
Volumen: 1500 kg
Agua: 1500/2000 ml
```

- **En `dist/07-app.js`** (tras `npm run build`) queda `import { OBJETIVO_AGUA_ML, volumenTotal } from "./tipos/entreno";`: el tipo ha desaparecido.

<Callout type="risk">

- **`node dist/07-app.js` da `ERR_MODULE_NOT_FOUND`:** Node exige `.js` en los imports, y `moduleResolution: "Bundler"` asume que los resuelve un empaquetador. Aquí `dist/` solo sirve para inspeccionar. Para Node sin empaquetador: `"module": "NodeNext"` e imports con `.js`.
- **Dependencias circulares:** dos módulos que se importan entre sí pueden dar valores `undefined` según el orden de carga. Los `import type` no tienen ese problema.
- **Exporta solo lo necesario:** cada `export` es una promesa pública de la que otros acabarán dependiendo.

</Callout>

## Paso 3: librerías con tipos incluidos

**Qué es:** TypeScript conoce los tipos de una librería de JavaScript por sus archivos **`.d.ts`**, que solo contienen tipos. Las librerías modernas los incluyen.

**Cómo se usa:** instala `date-fns` y crea `src/07-fechas.ts`.

```bash
npm install date-fns
```

```ts
// Archivo: src/07-fechas.ts
import { addDays, differenceInCalendarDays, format } from "date-fns";
import { es } from "date-fns/locale";

const inicioPlan = new Date(2026, 9, 1); // 1 de octubre de 2026 (los meses empiezan en 0)
const finPlan = addDays(inicioPlan, 56); // 8 semanas

console.log(`Plan de entrenamiento: ${format(inicioPlan, "d 'de' MMMM", { locale: es })} → ${format(finPlan, "d 'de' MMMM", { locale: es })}`);
console.log(`Duración: ${differenceInCalendarDays(finPlan, inicioPlan)} días`);
```

```bash
npm run typecheck
npm start -- src/07-fechas.ts
```

```text
Plan de entrenamiento: 1 de octubre → 26 de noviembre
Duración: 56 días
```

Pon el cursor sobre `addDays` y pulsa `F12`: VS Code abre su `.d.ts` en `node_modules/date-fns/`.

```ts
export declare function addDays<DateType extends Date, ResultDate extends Date = DateType>(
  date: DateArg<DateType>,
  amount: number,
  options?: AddDaysOptions<ResultDate> | undefined,
): ResultDate;
```

- **Recibe una fecha, un `number` y unas opciones, y devuelve una fecha.** Los `<…>` son genéricos (I1). Esta es la documentación más fiable: la que usa el compilador.

<Callout type="risk">

- **Los meses empiezan en 0:** `new Date(2026, 9, 1)` es **octubre**. Los tipos no lo detectan, porque los dos son `number`.
- **`format` usa la zona del proceso:** México en tu Mac, UTC en Vercel. Para usuarios, fija la zona con `Intl.DateTimeFormat` y `timeZone`, o con `@date-fns/tz`.
- **Importa solo lo que usas:** en el navegador, cada kilobyte cuenta. Evita librerías que obliguen a importarlo todo.

</Callout>

## Paso 4: librerías sin tipos y los paquetes `@types`

**Qué es:** las librerías antiguas sin `.d.ts` tienen sus tipos aparte, en el proyecto DefinitelyTyped, publicados como `@types/nombre-de-la-libreria`.

**Cómo se usa:** instala `lodash`, que no trae tipos, y crea `src/07-lodash.ts`.

```bash
npm install lodash
```

```ts
// Archivo: src/07-lodash.ts
import groupBy from "lodash/groupBy.js";

interface Tarea {
  titulo: string;
  categoria: "trabajo" | "personal" | "salud";
}

const tareas: Tarea[] = [
  { titulo: "Revisar pull request", categoria: "trabajo" },
  { titulo: "Correr 5 km", categoria: "salud" },
  { titulo: "Preparar demo", categoria: "trabajo" },
  { titulo: "Llamar a mamá", categoria: "personal" },
];

const porCategoria = groupBy(tareas, (t) => t.categoria);
for (const [categoria, lista] of Object.entries(porCategoria)) {
  console.log(`${categoria}: ${lista.map((t) => t.titulo).join(", ")}`);
}
```

```bash
npm run typecheck
```

```text
error TS7016: Could not find a declaration file for module 'lodash/groupBy.js'. '…/node_modules/lodash/groupBy.js' implicitly has an 'any' type.
  Try `npm i --save-dev @types/lodash` if it exists or add a new declaration (.d.ts) file containing `declare module 'lodash/groupBy.js';`
```

Debajo salen otros dos errores, consecuencia del primero. El propio mensaje da la solución: instala los tipos como dependencia de desarrollo.

```bash
npm install --save-dev @types/lodash
npm run typecheck
npm start -- src/07-lodash.ts
```

```text
trabajo: Revisar pull request, Preparar demo
salud: Correr 5 km
personal: Llamar a mamá
```

- **Ahora `t` es `Tarea` y `lista` es `Tarea[]`.** `F12` sobre `groupBy` lleva a `node_modules/@types/lodash/`.
- **En npmjs.com,** un icono **TS** azul junto al nombre indica tipos incluidos; uno **DT** blanco, que hay que instalar `@types/...`.

<Callout type="risk">

- **Versiones desalineadas:** `@types/lodash` lo mantienen otras personas y puede ir por detrás de la librería. Comprueba que las versiones coinciden.
- **`@types` va en `devDependencies`:** en producción no sirven de nada.
- **No silencies el error con `declare module 'lodash/groupBy.js';`:** todo el módulo pasa a ser `any`. Y antes de instalar algo, mira si el lenguaje ya lo resuelve: `Object.groupBy` existe desde ES2024.

</Callout>

## Paso 5: alias de rutas con `paths`

**Qué es:** un **alias**: `@/` significa "desde `src/`", estés donde estés. Sustituye imports frágiles como `"../../../tipos/entreno"`.

**Cómo se usa:** añade `paths` a `compilerOptions`. El `tsconfig.json` completo:

```jsonc
// Archivo: tsconfig.json
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "moduleDetection": "force",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "rootDir": "src",
    "outDir": "dist",
    // "@/algo" se resuelve como "./src/algo", relativo a este tsconfig.json
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src"]
}
```

Compruébalo desde una carpeta profunda, `src/informes/semanal/resumen.ts`:

```ts
// Archivo: src/informes/semanal/resumen.ts
import { type DiaEntreno, volumenTotal } from "@/tipos/entreno";

const semana: DiaEntreno[] = [
  { fecha: "2026-10-05", ejercicios: [{ nombre: "sentadilla", series: 4, repeticiones: 8, pesoKg: 70 }], aguaMl: 2000 },
  { fecha: "2026-10-07", ejercicios: [{ nombre: "press banca", series: 4, repeticiones: 10, pesoKg: 50 }], aguaMl: 1800 },
  { fecha: "2026-10-09", ejercicios: [], aguaMl: 2200 },
];

const volumenSemana = semana.reduce((total, dia) => total + volumenTotal(dia), 0);
const diasConEntreno = semana.filter((dia) => dia.ejercicios.length > 0).length;

console.log(`Volumen de la semana: ${volumenSemana} kg en ${diasConEntreno} días`);
```

```bash
npm run typecheck
npm start -- src/informes/semanal/resumen.ts
```

```text
Volumen de la semana: 4240 kg en 2 días
```

- **`tsx` y Vite leen `paths`,** así que el alias funciona al ejecutar y en Astro.

<Callout type="risk">

- **`baseUrl` ya no existe en TypeScript 7:** da `error TS5102: Option 'baseUrl' has been removed`, y sin él, `"src/*"` da `error TS5090: Non-relative paths are not allowed`. Las rutas empiezan por `./`. TypeScript 6 aún lo acepta con un aviso.
- **`paths` no reescribe los imports al compilar:** en `dist/` sigue `"@/tipos/entreno"`. Funciona porque lo resuelve un empaquetador; con `tsc` a solas para publicar una librería, no sirve.
- **Alias que chocan con paquetes:** `utils/*` podría confundirse con un paquete de npm. Empieza por `@/` o `~/`.

</Callout>

## Paso 6: el `tsconfig.json` de un proyecto Astro

**Qué es:** el `tsconfig.json` de **esta plataforma**, tal cual. Es corto porque **hereda** casi todo con `extends`:

```json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist", "node_modules"],
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] },
    "jsx": "react-jsx",
    "jsxImportSource": "react",
    "noUncheckedIndexedAccess": true
  }
}
```

`astro/tsconfigs/strict` añade `"strict": true` y hereda de `base.json`, en `node_modules/astro/tsconfigs/`. Lo que activa `base.json` en Astro 7:

| Opción                             | Valor      | Para qué sirve                                                                   |
| ---------------------------------- | ---------- | -------------------------------------------------------------------------------- |
| `target`                           | `ESNext`   | Permite toda la sintaxis moderna; Vite se encarga de adaptarla a los navegadores |
| `module`                           | `ESNext`   | Imports y exports estándar, _top-level await_                                    |
| `moduleResolution`                 | `Bundler`  | Resuelve imports como Vite: sin extensiones obligatorias                         |
| `allowImportingTsExtensions`       | `true`     | Permite `import x from "./a.ts"` con la extensión                                |
| `resolveJsonModule`                | `true`     | Permite importar archivos `.json` con tipos                                      |
| `verbatimModuleSyntax`             | `true`     | Obliga a usar `import type` (Paso 2)                                             |
| `isolatedModules`                  | `true`     | Cada archivo se puede compilar por separado, como hace Vite                      |
| `noEmit`                           | `true`     | `tsc` no genera archivos: Astro compila, TypeScript solo comprueba               |
| `forceConsistentCasingInFileNames` | `true`     | Error si importas `./Tarjeta` y el archivo es `tarjeta.astro`                    |
| `esModuleInterop`                  | `true`     | Permite importar librerías antiguas (CommonJS) con `import x from`               |
| `skipLibCheck`                     | `true`     | No revisa los `.d.ts` de `node_modules` (más rápido)                             |
| `allowJs`                          | `true`     | Permite importar archivos `.js`                                                  |
| `jsx`                              | `preserve` | Deja el JSX para que lo transforme otro (aquí se sustituye por `react-jsx`)      |

Lo que añade el proyecto encima:

| Opción                                 | Para qué                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------- |
| `include` con `.astro/types.d.ts`      | Los tipos que **genera** Astro: colecciones, variables de entorno, _actions_ |
| `exclude`                              | No revisa la compilación ni las dependencias                                 |
| `paths`                                | El alias `@/` del Paso 5                                                     |
| `jsx: "react-jsx"` y `jsxImportSource` | Los `.tsx` usan React (B6)                                                   |
| `noUncheckedIndexedAccess`             | La protección de índices de B1.3, que `strict` no activa                     |

**`strict` es la opción más importante:** enciende a la vez `noImplicitAny` (B1.2), `strictNullChecks` (sin ella, `null` y `undefined` encajarían en cualquier tipo), `strictFunctionTypes`, `strictPropertyInitialization` y `useUnknownInCatchVariables` (el `catch (error)` de tipo `unknown`).

<Callout type="risk">

- **El editor no recarga `tsconfig.json`:** si los errores no cambian, `Cmd` + `Shift` + `P` → _TypeScript: Restart TS Server_.
- **`include` sin `.astro/types.d.ts`,** típico al copiar un `tsconfig.json`, da `Cannot find module 'astro:content'`. Ejecuta `npx astro sync` y revisa `include`.
- **`"strict": false` no arregla 200 errores:** los esconde. En un proyecto heredado, activa las comprobaciones una a una.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. En tu app de entrenamiento (el proyecto Astro), abre `node_modules/astro/tsconfigs/strict.json` y `base.json`, y compara su contenido con la tabla del Paso 6 (puede variar ligeramente según tu versión de Astro).
2. Copia el `tsconfig.json` de abajo, adaptado a tu proyecto, con un comentario en cada opción. Si tu proyecto usa `baseUrl`, elimínalo y añade `./` a las rutas de `paths`.
3. Busca en tu proyecto tres imports con `../../` y cámbialos por `@/`.
4. Ejecuta `npx astro check` y comprueba que no hay errores nuevos.

</Callout>

Solución: un `tsconfig.json` comentado para un proyecto Astro con React.

```jsonc
// Archivo: tsconfig.json (proyecto Astro, no el playground)
{
  // Hereda base.json (módulos, Bundler, noEmit, verbatimModuleSyntax…) más "strict": true
  "extends": "astro/tsconfigs/strict",
  // Revisa todo el proyecto más los tipos que genera Astro (astro:content, astro:env…)
  "include": [".astro/types.d.ts", "**/*"],
  // No revisa la carpeta de compilación ni las dependencias
  "exclude": ["dist", "node_modules"],
  "compilerOptions": {
    // Alias: "@/components/Tarjeta.astro" → "./src/components/Tarjeta.astro"
    "paths": { "@/*": ["./src/*"] },
    // Los .tsx usan el runtime JSX automático de React (sin import React en cada archivo)
    "jsx": "react-jsx",
    // De dónde salen las funciones de JSX: del paquete react
    "jsxImportSource": "react",
    // array[i] y objeto[clave] devuelven "T | undefined": obliga a comprobar antes de usar
    "noUncheckedIndexedAccess": true
  }
}
```

Una migración de imports típica, en un componente:

```astro
---
// Archivo: src/components/entrenos/detalle/TarjetaEjercicio.astro
// Antes:
// import type { Ejercicio } from "../../../tipos/entreno";
// import { formatearPeso } from "../../../lib/formato";
// Después:
import type { Ejercicio } from "@/tipos/entreno";
import { formatearPeso } from "@/lib/formato";

interface Props {
  ejercicio: Ejercicio;
}
const { ejercicio } = Astro.props;
---

<article>
  <h3>{ejercicio.nombre}</h3>
  <p>{ejercicio.series}×{ejercicio.repeticiones} · {formatearPeso(ejercicio.pesoKg)}</p>
</article>
```

Los dos archivos que importa, si tu proyecto no los tiene:

```ts
// Archivo: src/tipos/entreno.ts (proyecto Astro)
export interface Ejercicio {
  readonly nombre: string;
  series: number;
  repeticiones: number;
  pesoKg: number;
}
```

```ts
// Archivo: src/lib/formato.ts (proyecto Astro)
const formatoKg = new Intl.NumberFormat("es-MX", { style: "unit", unit: "kilogram", maximumFractionDigits: 1 });

export function formatearPeso(kg: number): string {
  return kg === 0 ? "peso corporal" : formatoKg.format(kg);
}
```

<Callout type="risk">

- **Migra los imports en un _commit_ aparte,** sin otros cambios: la revisión es trivial y deshacerlo, fácil.
- **Mayúsculas:** macOS no distingue `Tarjeta.astro` de `tarjeta.astro`; el Linux de Vercel, sí. Un import mal escrito funciona en tu Mac y falla al desplegar, y `forceConsistentCasingInFileNames` no lo detecta en todos los casos.
- **`Intl.NumberFormat` a nivel de módulo:** crearlo una vez es mucho más rápido que en cada llamada, y se nota en listas largas.

</Callout>

<Callout type="mastery">

Puedes crear un `tsconfig.json` desde cero y explicar cada línea, sabes cuándo usar `import type`, instalas `@types/...` solo cuando una librería no trae sus tipos y lees un `.d.ts` con `F12` en lugar de buscar en internet.

</Callout>

## Resumen

- Los tipos viven en módulos propios; los tipos desaparecen al compilar y los valores no.
- Con `verbatimModuleSyntax`, los tipos se importan con `import type`.
- Librerías modernas: `.d.ts` incluidos. Antiguas: `@types/...` en `devDependencies`.
- `"@/*": ["./src/*"]` crea el alias `@/`; en TypeScript 7 no hay `baseUrl`.
- En Astro, `extends: "astro/tsconfigs/strict"` hereda casi todo; `strict` es imprescindible.
