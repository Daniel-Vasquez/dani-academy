Todo el curso se junta aquí: un proyecto **Astro** tipado de punta a punta, con _props_, endpoints que validan datos y variables de entorno. Provocarás el `EnvInvalidVariables` que sale al desplegar en Vercel sin configurar una variable.

**Requisitos:** Node.js 22.12 o superior, y las secciones B1.1 a B1.7.

## Paso 1: crear el proyecto y activar la comprobación de tipos

**Qué es:** un proyecto Astro vacío con `astro check`, el comando que comprueba los tipos de los `.astro` y los `.ts`.

**Cómo se usa:** fuera de `ts-playground`, ejecuta:

```bash
npm create astro@latest mi-entreno -- --template minimal --install --no-git --yes
cd mi-entreno
npm install --save-dev @astrojs/check typescript
code .
```

- **`--install --no-git --yes`:** instala las dependencias, no crea repositorio y no pregunta nada.
- **`@astrojs/check` y `typescript`** son lo que usa `astro check`. Sin ellas, Astro pregunta si instalarlas la primera vez.

`package.json` completo, con el _script_ `check` (tus versiones pueden ser más nuevas):

```json
{
  "name": "mi-entreno",
  "type": "module",
  "version": "0.0.1",
  "engines": {
    "node": ">=22.12.0"
  },
  "scripts": {
    "dev": "astro dev",
    "build": "astro build",
    "preview": "astro preview",
    "astro": "astro",
    "check": "astro check"
  },
  "dependencies": {
    "astro": "^7.3.8"
  },
  "devDependencies": {
    "@astrojs/check": "^0.9.10",
    "typescript": "^6.0.3"
  }
}
```

El `tsconfig.json` que crea Astro, el de B1.7:

```json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"]
}
```

Añade la protección de índices de B1.3:

```json
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"],
  "compilerOptions": {
    "noUncheckedIndexedAccess": true
  }
}
```

<Callout type="risk">

- **`astro dev` no comprueba tipos:** como `tsx` en B1.1, borra los tipos y ejecuta. Una página con errores **se ve perfectamente**. La red de seguridad es `npm run check`, antes de cada _commit_ y en el CI.
- **TypeScript 6 aquí, 7 en el playground:** `@astrojs/check` todavía requiere la 6. Cada proyecto tiene la suya; las diferencias que te afectan (`baseUrl`) están en B1.7.
- **`npm create astro@latest` descarga siempre la última versión.** Si un tutorial usa otra versión mayor, revisa el _changelog_.

</Callout>

## Paso 2: un layout con `Props` tipadas

**Qué es:** lo que va entre las dos líneas `---` de un `.astro` (el _frontmatter_) es **TypeScript que se ejecuta en el servidor**. Una `interface Props` tipa `Astro.props`, y Astro la detecta por su nombre.

**Cómo se usa:** primero, los tipos del dominio en `src/tipos/entreno.ts`.

```ts
// Archivo: src/tipos/entreno.ts
export type Nivel = "basico" | "intermedio" | "avanzado";

export interface Entreno {
  id: number;
  titulo: string;
  minutos: number;
  nivel: Nivel;
}
```

Después, el layout `src/layouts/Base.astro`:

```astro
---
// Archivo: src/layouts/Base.astro
import { APP_NOMBRE } from "astro:env/client";

interface Props {
  titulo: string;
  descripcion?: string;
}

const { titulo, descripcion = "Registro de entrenamientos" } = Astro.props;
---

<html lang="es">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width" />
    <meta name="description" content={descripcion} />
    <title>{`${titulo} · ${APP_NOMBRE}`}</title>
  </head>
  <body>
    <slot />
  </body>
</html>
```

- **`descripcion`** es opcional y tiene un valor por defecto en la desestructuración (B1.5). **`<slot />`** inserta lo que pongas entre `<Base>` y `</Base>`.
- **`APP_NOMBRE`** viene de `astro:env/client`, que configurarás en el Paso 6. Hasta entonces, el editor lo marca en rojo, y es esperado.

<Callout type="risk">

- **El nombre `Props` es obligatorio:** con `interface PropsTarjeta`, `Astro.props` pasa a ser `Record<string, any>` y todo compila sin comprobar nada. `type Props = {…}` también vale.
- **Sin `interface Props`, nada avisa:** `const { titulo } = Astro.props` pasa `astro check` porque `titulo` es `any`. Revisa que **todos** tus componentes la declaren.
- **El _frontmatter_ se ejecuta en el servidor:** ahí no existen `window` ni `document`. El código del navegador va en `<script>`.

</Callout>

## Paso 3: un componente tipado y la página que lo usa

**Qué es:** las _props_ de un componente se comprueban en cada uso: un valor fuera de la unión, un texto donde va un número o una _prop_ que falta son errores de `astro check`.

**Cómo se usa:** crea `src/components/Tarjeta.astro`.

```astro
---
// Archivo: src/components/Tarjeta.astro
import type { Nivel } from "../tipos/entreno";

interface Props {
  titulo: string;
  minutos: number;
  nivel: Nivel;
  descripcion?: string;
}

const { titulo, minutos, nivel, descripcion } = Astro.props;

const ETIQUETAS: Record<Nivel, string> = {
  basico: "Básico",
  intermedio: "Intermedio",
  avanzado: "Avanzado",
};
---

<article data-nivel={nivel}>
  <h2>{titulo}</h2>
  <p>{minutos} min · {ETIQUETAS[nivel]}</p>
  {descripcion && <p>{descripcion}</p>}
</article>
```

Sustituye `src/pages/index.astro`:

```astro
---
// Archivo: src/pages/index.astro
import Base from "../layouts/Base.astro";
import Tarjeta from "../components/Tarjeta.astro";
import type { Entreno } from "../tipos/entreno";

const entrenos: Entreno[] = [
  { id: 1, titulo: "Rodaje suave", minutos: 30, nivel: "basico" },
  { id: 2, titulo: "Fuerza de pierna", minutos: 50, nivel: "intermedio" },
  { id: 3, titulo: "Series de 400 m", minutos: 45, nivel: "avanzado" },
];
---

<Base titulo="Entrenos">
  <h1>Mis entrenos</h1>
  {entrenos.map((e) => (
    <Tarjeta titulo={e.titulo} minutos={e.minutos} nivel={e.nivel} />
  ))}
</Base>
```

- **`Record<Nivel, string>`** (B1.4) obliga a tener una etiqueta por nivel: si añades `"elite"` a `Nivel`, `ETIQUETAS` da error.
- **`ETIQUETAS[nivel]` es `string`,** sin `undefined`, pese a `noUncheckedIndexedAccess`: la clave es un `Nivel` y el `Record` las tiene todas.

Provoca tres errores: sustituye lo que hay entre `<Base>` y `</Base>` por estas tarjetas.

```astro
<Base titulo="Entrenos">
  <Tarjeta titulo="Rodaje suave" minutos={30} />
  <Tarjeta titulo="Fuerza" minutos="50" nivel="intermedio" />
  <Tarjeta titulo="Series" minutos={45} nivel="experto" />
</Base>
```

```bash
npm run check
```

```text
src/pages/index.astro:10:41 - error ts(2322): Type '"experto"' is not assignable to type 'Nivel'.
src/pages/index.astro:9:28 - error ts(2322): Type 'string' is not assignable to type 'number'.
src/pages/index.astro:8:4 - error ts(2322): Type '{ titulo: string; minutos: number; }' is not assignable to type 'IntrinsicAttributes & Props'.
  Property 'nivel' is missing in type '{ titulo: string; minutos: number; }' but required in type 'Props'.

Result (8 files):
- 3 errors
```

Los números de línea dependen de tu _frontmatter_. Los mensajes:

- **`'"experto"' is not assignable to type 'Nivel'`:** un valor fuera de la unión.
- **`'string' is not assignable to type 'number'`:** las comillas siempre son texto. Para un número, llaves: `minutos={50}`.
- **`Property 'nivel' is missing`:** falta una _prop_. Lee la **segunda línea** del mensaje; `IntrinsicAttributes & Props` es la forma interna de Astro.

Con `npm run dev`, **la página se ve igual**, errores incluidos. Restaura `index.astro` antes de seguir.

<Callout type="risk">

- **`minutos="50"` es el error más común** viniendo de HTML. Sin _props_ tipadas, `minutos + 10` daría `"5010"`, el bug de B1.1.
- **`<Tarjeta entreno={e} />` acopla el componente** a la forma completa de `Entreno`. Las _props_ sueltas lo hacen reutilizable con datos de otras fuentes.
- **Astro no necesita `key` en `.map()`,** porque genera el HTML una vez. Una isla de React (B6), sí.

</Callout>

## Paso 4: los tipos que genera Astro

**Qué es:** la carpeta `.astro/`, que Astro **genera** a partir de tu configuración. `tsconfig.json` incluye `.astro/types.d.ts`, y por eso `astro:env/client` tiene tipos.

**Cómo se usa:** ejecuta `npm run check` o `npm run dev` y mírala.

```text
.astro/
├── types.d.ts       → punto de entrada: incluye los tipos de astro/client y los demás
├── env.d.ts         → tipos de tus variables de entorno (Paso 6)
├── content.d.ts     → tipos de las colecciones de contenido
└── …
```

Si el editor no se entera de un cambio de configuración, regénerala:

```bash
npx astro sync
```

- **Esta plataforma la usa con las colecciones de contenido:** el _frontmatter_ de cada lección (`sectionId`, `title`, `minutes`…) está tipado gracias a ella.

<Callout type="risk">

- **No edites ni subas `.astro/`:** se regenera en cada `dev`, `build`, `check` o `sync`, y la plantilla ya lo excluye de Git.
- **`Cannot find module 'astro:env/client'`:** tipos sin generar (proyecto recién clonado) o un `include` incompleto. `npx astro sync`, y si persiste, _TypeScript: Restart TS Server_.

</Callout>

## Paso 5: endpoints tipados con `APIRoute`

**Qué es:** un `.ts` dentro de `src/pages/` es un **endpoint**: devuelve datos en lugar de HTML. Cada método HTTP se exporta como una función de tipo `APIRoute`.

**Cómo se usa:** el más sencillo, `src/pages/api/hola.ts`.

```ts
// Archivo: src/pages/api/hola.ts
import type { APIRoute } from "astro";

// Esta ruta se ejecuta en cada petición (no se genera al compilar)
export const prerender = false;

export const GET: APIRoute = ({ url }) => {
  const nombre = url.searchParams.get("nombre") ?? "mundo";
  return Response.json({ mensaje: `Hola, ${nombre}` });
};
```

- **`APIRoute`** tipa el contexto (`url`, `request`, `params`, `cookies`…) y el retorno (`Response`). `{ url }` no se anota: es tipado contextual (B1.5).
- **`url.searchParams.get("nombre")`** es `string | null`, y `?? "mundo"` lo resuelve.
- **`prerender = false`:** Astro genera las páginas al compilar. Un endpoint que lee cada petición se ejecuta en cada petición.

Uno real, que recibe datos del exterior. El cuerpo es `unknown` hasta validarlo (B1.2), con los _guards_ de B1.6. Crea `src/pages/api/entrenos.ts`:

```ts
// Archivo: src/pages/api/entrenos.ts
import type { APIRoute } from "astro";
import { API_TOKEN, LIMITE_ENTRENOS } from "astro:env/server";
import type { Entreno, Nivel } from "../../tipos/entreno";

export const prerender = false;

const NIVELES: readonly string[] = ["basico", "intermedio", "avanzado"];

// En memoria para el ejemplo: se pierde al reiniciar el servidor
const entrenos: Entreno[] = [{ id: 1, titulo: "Rodaje suave", minutos: 30, nivel: "basico" }];

type EntradaEntreno = Omit<Entreno, "id">;

function esNivel(valor: unknown): valor is Nivel {
  return typeof valor === "string" && NIVELES.includes(valor);
}

function leerEntrada(cuerpo: unknown): EntradaEntreno | null {
  if (typeof cuerpo !== "object" || cuerpo === null) return null;
  const titulo = "titulo" in cuerpo ? cuerpo.titulo : undefined;
  const minutos = "minutos" in cuerpo ? cuerpo.minutos : undefined;
  const nivel = "nivel" in cuerpo ? cuerpo.nivel : undefined;

  if (typeof titulo !== "string" || titulo.trim().length < 3) return null;
  if (typeof minutos !== "number" || !Number.isInteger(minutos) || minutos <= 0 || minutos > 600) return null;
  if (!esNivel(nivel)) return null;

  return { titulo: titulo.trim(), minutos, nivel };
}

export const GET: APIRoute = () => {
  return Response.json({ entrenos: entrenos.slice(0, LIMITE_ENTRENOS) });
};

export const POST: APIRoute = async ({ request }) => {
  if (request.headers.get("authorization") !== `Bearer ${API_TOKEN}`) {
    return Response.json({ error: "No autorizado" }, { status: 401 });
  }

  let cuerpo: unknown;
  try {
    cuerpo = await request.json();
  } catch {
    return Response.json({ error: "El cuerpo debe ser JSON" }, { status: 400 });
  }

  const entrada = leerEntrada(cuerpo);
  if (entrada === null) {
    return Response.json({ error: "Datos inválidos" }, { status: 400 });
  }

  const nuevo: Entreno = { id: entrenos.length + 1, ...entrada };
  entrenos.push(nuevo);
  return Response.json(nuevo, { status: 201 });
};
```

- **El orden de `POST` importa:** autorización primero (`401`, sin leer el cuerpo); `request.json()` en un `try/catch` (`400` en lugar de `500`); y `leerEntrada`, que comprueba el tipo **y** el rango de cada campo.
- **`Omit<Entreno, "id">` más un `id`:** el cliente no elige el `id`, lo asigna el servidor.

Importa `API_TOKEN` y `LIMITE_ENTRENOS`, del Paso 6: no lo pruebes todavía.

<Callout type="risk">

- **`npm run build` falla con `prerender = false` sin adaptador:** `[NoAdapterInstalled] Cannot use server-rendered pages without an adapter.` Para desplegar, `npx astro add vercel` (A4).
- **Comparar tokens con `!==`** vale para aprender. En seguridad real: `crypto.timingSafeEqual`, y sesiones de usuario (I5) en lugar de un token compartido.
- **El array en memoria se pierde al reiniciar,** y en Vercel cada instancia tiene el suyo. Además, `entrenos.length + 1` repite `id` si borras. Los datos van en una base de datos (B5).

</Callout>

## Paso 6: variables de entorno tipadas con `astro:env`

**Qué es:** las variables de entorno llegan **como texto** y pueden faltar. `astro:env` declara un **esquema** con el tipo de cada una, y Astro las valida y las tipa.

**Cómo se usa:** sustituye `astro.config.mjs`.

```js
// Archivo: astro.config.mjs
// @ts-check
import { defineConfig, envField } from "astro/config";

export default defineConfig({
  env: {
    schema: {
      // Pública: se puede usar también en el navegador
      APP_NOMBRE: envField.string({ context: "client", access: "public", default: "Mi Entreno" }),
      // Secreta: solo existe en el servidor, nunca llega al navegador
      API_TOKEN: envField.string({ context: "server", access: "secret", min: 16 }),
      // Numérica: Astro la convierte de texto a number por ti
      LIMITE_ENTRENOS: envField.number({ context: "server", access: "public", default: 50 }),
    },
  },
});
```

Crea `.env` en la raíz (Astro lo lee en desarrollo):

```bash
API_TOKEN="token-de-desarrollo-1234567890"
```

Reinicia `npm run dev` (lo exige un cambio en `astro.config.mjs`) y abre `.astro/env.d.ts`:

```ts
declare module 'astro:env/client' {
	export const APP_NOMBRE: string;
}
declare module 'astro:env/server' {
	export const API_TOKEN: string;
	export const LIMITE_ENTRENOS: number;
}
```

- **`LIMITE_ENTRENOS` es `number`, no `string`:** Astro convierte y valida.

Prueba la API desde otra terminal:

```bash
curl "http://localhost:4321/api/hola?nombre=Dani"
curl http://localhost:4321/api/entrenos
curl -i -X POST http://localhost:4321/api/entrenos \
  -H "content-type: application/json" \
  -d '{"titulo":"Remo","minutos":20,"nivel":"basico"}'
curl -i -X POST http://localhost:4321/api/entrenos \
  -H "authorization: Bearer token-de-desarrollo-1234567890" \
  -H "content-type: application/json" \
  -d '{"titulo":"  Remo ","minutos":20,"nivel":"basico"}'
curl -i -X POST http://localhost:4321/api/entrenos \
  -H "authorization: Bearer token-de-desarrollo-1234567890" \
  -H "content-type: application/json" \
  -d '{"titulo":"Remo","minutos":"20","nivel":"experto"}'
```

De `curl -i` solo se muestran la línea de estado y el cuerpo:

```text
{"mensaje":"Hola, Dani"}
{"entrenos":[{"id":1,"titulo":"Rodaje suave","minutos":30,"nivel":"basico"}]}
HTTP/1.1 401 Unauthorized
{"error":"No autorizado"}
HTTP/1.1 201 Created
{"id":2,"titulo":"Remo","minutos":20,"nivel":"basico"}
HTTP/1.1 400 Bad Request
{"error":"Datos inválidos"}
```

- **Cuarta petición:** `"  Remo "` se guardó limpio, como `"Remo"`. **Quinta:** `minutos` llegó como texto (`"20"`), típico de un formulario, y se rechazó.

Ahora renombra `.env` a `.env.bak` y reinicia. La portada funciona, pero `http://localhost:4321/api/entrenos` da un 500:

```text
[EnvInvalidVariables] The following environment variables defined in `env.schema` are invalid:

- API_TOKEN is missing
```

- **Es el error de desplegar en Vercel sin configurar la variable:** tu `.env` no se sube, y no debe subirse.
- **Solo falla la ruta que la usa,** así que se descubre tarde, cuando alguien abre esa parte de la app. Vuelve a renombrar `.env.bak` a `.env`.

<Callout type="risk">

- **Nunca subas `.env` a Git** (compruébalo con `git status`). Documenta las variables en `.env.example`, sin valores reales. Si un secreto llega a GitHub, genera otro: borrar el _commit_ no basta.
- **En Vercel,** van en _Settings_ → _Environment Variables_ y solo se aplican a los despliegues **nuevos**.
- **`context: "client"` publica el valor** en el JavaScript del navegador. Nunca declares así un secreto. Y `import.meta.env.NOMBRE` no valida nada: para tus variables, `astro:env`.

</Callout>

## Paso 7: errores comunes en `.astro` y cómo leerlos

**Qué es:** una referencia de los errores que más verás, todos de `npm run check` salvo los dos que salen en `dev` o en `build`.

| Mensaje (resumido)                                               | Causa habitual                           | Solución                                 |
| ---------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| `Property 'x' is missing in type … but required in type 'Props'` | Falta una prop obligatoria               | Pásala, o hazla opcional con `?`         |
| `Type 'string' is not assignable to type 'number'` en una prop   | `prop="50"` en lugar de `prop={50}`      | Usa llaves para todo lo que no sea texto |
| `Type '"x"' is not assignable to type 'Nivel'`                   | Valor fuera de una unión                 | Corrige el valor o amplía la unión       |
| `Cannot find module 'astro:env/server'`                          | Tipos sin generar o `include` incompleto | `npx astro sync`; revisa `tsconfig.json` |
| `'X' is a type and must be imported using a type-only import`    | Falta `import type`                      | `import type { X }` (B1.7)               |
| `[EnvInvalidVariables] … is missing` (en `dev` o en producción)  | Variable de entorno no definida          | Añádela a `.env` o al panel de Vercel    |
| `[NoAdapterInstalled]` (en `build`)                              | `prerender = false` sin adaptador        | `npx astro add vercel`                   |

Para cualquier error nuevo: **archivo y línea** (dónde), **código** `ts(XXXX)` (qué clase de error) y **la última línea del mensaje** (qué falta o qué sobra).

```astro
---
// Archivo: src/components/ResumenSemana.astro
import type { Entreno } from "../tipos/entreno";
import Insignia from "./Insignia.astro";

interface Props {
  entrenos: Entreno[];
  objetivoMinutos?: number;
}

const { entrenos, objetivoMinutos = 150 } = Astro.props;

const totalMinutos = entrenos.reduce((total, e) => total + e.minutos, 0);
const porcentaje = objetivoMinutos > 0 ? Math.min(100, Math.round((totalMinutos / objetivoMinutos) * 100)) : 0;

<section>

  {entrenos.length === 0 ? (
    <p>Todavía no hay entrenos esta semana.</p>

    <ul>
      {entrenos.map((e) => (
        <li>
          {e.titulo} · {e.minutos} min <Insignia nivel={e.nivel} />
        </li>

</section>
```

<Callout type="risk">

- **División por cero:** con `objetivoMinutos={0}`, el porcentaje sería `Infinity`. `objetivoMinutos > 0` lo evita: los tipos dicen que es un `number`, no que sea razonable.
- **Estilos construidos con datos:** con un objeto tuyo (`ESTILOS`) es seguro. Nunca construyas estilos, HTML o URLs con texto de un usuario sin validarlo.
- **Colores fijos en el componente:** en un proyecto real van en variables CSS o en el tema de Tailwind (B7), para el modo oscuro.

</Callout>

<Callout type="mastery">

`astro check` pasa sin errores en uno de tus proyectos, todos tus componentes declaran `interface Props`, tus endpoints tratan el cuerpo de la petición como `unknown` hasta validarlo y tus variables de entorno están declaradas en `astro:env`, de modo que sabes leer un `EnvInvalidVariables` y arreglarlo en Vercel.

</Callout>

## Resumen

- `astro dev` no comprueba tipos; `npm run check` sí, antes de cada _commit_.
- Sin `interface Props`, `Astro.props` es `any` y nada avisa.
- Astro genera sus tipos en `.astro/`; `npx astro sync` los regenera.
- El cuerpo de una petición es `unknown` hasta validarlo; `prerender = false` necesita adaptador.
- `astro:env` valida las variables; si falta una, `EnvInvalidVariables` solo en las rutas que la usan.
