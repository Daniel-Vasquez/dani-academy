En B1.3 escribiste `EjercicioDelDia` dos veces, en dos archivos. La solución es **darle un nombre al tipo** y reutilizarlo, con `type` o con `interface`. Aquí ves sus diferencias reales con experimentos y fijas una convención.

**Requisitos:** el `ts-playground` con los archivos de B1.3.

## Paso 1: dar nombre a un tipo con `type`

**Qué es:** un **alias de tipo** es un nombre para un tipo. No crea nada nuevo.

**Cómo se usa:** crea `src/04-alias.ts`.

```ts
// Archivo: src/04-alias.ts
type Kilos = number;
type Fecha = string; // formato AAAA-MM-DD
type Tema = "light" | "dark";

type Ejercicio = {
  nombre: string;
  series: number;
  repeticiones: number;
  pesoKg: Kilos;
};

const sentadilla: Ejercicio = { nombre: "sentadilla", series: 4, repeticiones: 8, pesoKg: 70 };
const hoy: Fecha = "2026-10-09";
const tema: Tema = "dark";

const pesoComoNumero: number = sentadilla.pesoKg; // Kilos y number son el mismo tipo
console.log(`${hoy} · ${sentadilla.nombre}: ${pesoComoNumero} kg · tema ${tema}`);
```

```bash
npm start -- src/04-alias.ts
```

```text
2026-10-09 · sentadilla: 70 kg · tema dark
```

- **PascalCase** para los tipos (`Ejercicio`, `DiaEntreno`), como las clases y los componentes de React.
- **`Kilos` y `number` son intercambiables:** `const pesoComoNumero: number = sentadilla.pesoKg` compila. El alias solo documenta.

<Callout type="risk">

- **Los alias no protegen de mezclas:** puedes asignar minutos a un campo `Kilos` sin error. Pon la unidad en el nombre (`pesoKg`, `aguaMl`); los _branded types_ son la técnica avanzada.
- **No crees alias para todo:** `type Texto = string` obliga a buscar su definición sin aportar nada.

</Callout>

## Paso 2: describir objetos con `interface`

**Qué es:** una **interfaz** describe la forma de un objeto. Para objetos sencillos, el resultado es el mismo que con `type`.

**Cómo se usa:** crea `src/04-interfaces.ts`.

```ts
// Archivo: src/04-interfaces.ts
interface Usuario {
  readonly id: string;
  nombre: string;
  email: string;
  pesoObjetivoKg?: number;
}

type UsuarioComoType = {
  readonly id: string;
  nombre: string;
  email: string;
  pesoObjetivoKg?: number;
};

const dani: Usuario = { id: "u_1", nombre: "Dani", email: "dani@example.com" };
const mismoDani: UsuarioComoType = dani; // misma forma = mismo tipo, aunque los nombres sean distintos
const deVuelta: Usuario = mismoDani;

console.log(`${deVuelta.nombre} <${deVuelta.email}>`);
console.log(`Peso objetivo: ${deVuelta.pesoObjetivoKg ?? "sin definir"}`);
```

```bash
npm start -- src/04-interfaces.ts
```

```text
Dani <dani@example.com>
Peso objetivo: sin definir
```

- **Sintaxis:** `interface Usuario { … }` va **sin `=`**; `type Usuario = { … };`, **con `=`**.
- **`Usuario` y `UsuarioComoType` son intercambiables:** es el tipado estructural de B1.3. Importa la forma, no el nombre.

<Callout type="risk">

- **Las interfaces no existen en ejecución:** `valor instanceof Usuario` da `error TS2693: 'Usuario' only refers to a type, but is being used as a value here.` Para comprobar en ejecución, valida (B1.6 e I1).
- **Dos tipos con la misma forma son intercambiables:** si `Entreno` y `Comida` coincidieran, pasarías una comida como entreno sin error. Usa nombres de campo específicos.

</Callout>

## Paso 3: extender tipos con `extends` y `&`

**Qué es:** reutilizar los campos de un tipo en otro. `interface Admin extends Usuario` es "todo lo de `Usuario`, más algo"; `Usuario & { tema: Tema }` es "un objeto que cumple los dos a la vez".

**Cómo se usa:** crea `src/04-extender.ts`.

```ts
// Archivo: src/04-extender.ts
interface Usuario {
  readonly id: string;
  nombre: string;
  email: string;
}

// Con interface: extends
interface Admin extends Usuario {
  permisos: string[];
}

// Con type: intersección (&) = "todo lo de A y todo lo de B"
type Tema = "light" | "dark";
type UsuarioConTema = Usuario & { tema: Tema };

const admin: Admin = {
  id: "u_0",
  nombre: "Dani",
  email: "dani@example.com",
  permisos: ["publicar-cursos", "ver-estadisticas"],
};

const conTema: UsuarioConTema = {
  id: "u_1",
  nombre: "Ana",
  email: "ana@example.com",
  tema: "dark",
};

function saludar(usuario: Usuario): string {
  return `Hola, ${usuario.nombre}`;
}

console.log(saludar(admin)); // un Admin es un Usuario
console.log(saludar(conTema)); // un UsuarioConTema también
console.log(`Permisos de ${admin.nombre}: ${admin.permisos.join(", ")}`);
```

```bash
npm start -- src/04-extender.ts
```

```text
Hola, Dani
Hola, Ana
Permisos de Dani: publicar-cursos, ver-estadisticas
```

`saludar` acepta los dos tipos extendidos. Ahora la diferencia real: añade este intento de redefinir `email`, ejecuta `npm run typecheck` y bórralo.

```ts
interface AdminRoto extends Usuario {
  email: number;
}

type AdminRotoType = Usuario & { email: number };
const imposible: AdminRotoType = { id: "x", nombre: "x", email: "x" };
```

```text
error TS2430: Interface 'AdminRoto' incorrectly extends interface 'Usuario'.
  Types of property 'email' are incompatible.
    Type 'number' is not assignable to type 'string'.
error TS2322: Type 'string' is not assignable to type 'never'.
```

- **`extends` avisa en la declaración,** con un mensaje claro.
- **`&` no avisa al declarar:** `email` tendría que ser `string` **y** `number`, así que pasa a ser `never`. El error sale al crear un objeto, y dice `not assignable to type 'never'`.

<Callout type="risk">

- **`&` con conflictos produce `never` en silencio.** Para modelar objetos, prefiere `extends`.
- **En proyectos enormes, `extends` es más rápido:** TypeScript guarda en caché las relaciones entre interfaces; las intersecciones se recalculan.
- **Herencia profunda:** más de dos niveles de `extends` es señal de revisar el diseño.

</Callout>

## Paso 4: lo que solo puede hacer `type`

**Qué es:** una interfaz siempre describe un objeto. Las uniones, las tuplas y los tipos calculados solo se pueden nombrar con `type`.

**Cómo se usa:** crea `src/04-solo-type.ts`.

```ts
// Archivo: src/04-solo-type.ts
// 1. Uniones de valores literales
type Categoria = "trabajo" | "personal" | "salud" | "estudio";

// 2. Uniones de objetos (las verás a fondo en B1.6)
type Resultado = { ok: true; datos: string[] } | { ok: false; error: string };

// 3. Tuplas con nombre
type Coordenada = [latitud: number, longitud: number];

// 4. Tipos calculados a partir de otros
interface Ejercicio {
  nombre: string;
  series: number;
  repeticiones: number;
  pesoKg: number;
}
type CampoDeEjercicio = keyof Ejercicio; // "nombre" | "series" | "repeticiones" | "pesoKg"
type EjercicioSinPeso = Omit<Ejercicio, "pesoKg">;

const categoria: Categoria = "salud";
const respuesta: Resultado = { ok: false, error: "Sin conexión" };
const parque: Coordenada = [19.42, -99.18];
const campo: CampoDeEjercicio = "series";
const flexiones: EjercicioSinPeso = { nombre: "flexiones", series: 3, repeticiones: 15 };

console.log(categoria, respuesta.ok, parque[0], campo, flexiones.nombre);
```

```bash
npm start -- src/04-solo-type.ts
```

```text
salud false 19.42 series flexiones
```

- **`keyof Ejercicio`:** la unión de los nombres de sus propiedades. Sirve para que `ordenarPor(lista, "pesoKg")` solo acepte campos válidos.
- **`Omit<Ejercicio, "pesoKg">`:** un tipo sin esa propiedad. Hay más (`Pick`, `Partial`, `Required`): curso I1.
- **`interface Categoria = "trabajo" | "personal"`** es un error de sintaxis.

<Callout type="risk">

- **`Omit` no comprueba que la propiedad exista:** `Omit<Ejercicio, "pesoKgg">` compila y no quita nada. Revisa el resultado con el hover.
- **`Omit<Partial<Pick<…>>>` es ilegible:** con más de una utilidad, da nombre a un tipo intermedio.

</Callout>

## Paso 5: lo que solo puede hacer `interface`: la fusión de declaraciones

**Qué es:** dos interfaces con el mismo nombre **se fusionan** en una. Sirve para **ampliar tipos de librerías** sin tocar su código: Astro declara `App.Locals` vacía, y esta plataforma le añade `user` y `session` en `src/env.d.ts` (B1.8 e I5).

**Cómo se usa:** crea `src/04-fusion.ts`.

```ts
// Archivo: src/04-fusion.ts
interface Preferencias {
  tema: "light" | "dark";
}

interface Preferencias {
  objetivoVasos: number;
}

// Las dos declaraciones se han fusionado: ahora Preferencias exige ambos campos
const misPreferencias: Preferencias = { tema: "dark", objetivoVasos: 8 };
console.log(misPreferencias);
```

```bash
npm start -- src/04-fusion.ts
```

```text
{ tema: 'dark', objetivoVasos: 8 }
```

Con `type` es un error. Añade estas líneas, comprueba con `npm run typecheck` y bórralas:

```ts
type Tema = "light";
type Tema = "dark";
```

```text
src/04-fusion.ts:14:6 - error TS2300: Duplicate identifier 'Tema'.
src/04-fusion.ts:15:6 - error TS2300: Duplicate identifier 'Tema'.
```

- **TypeScript marca las dos declaraciones,** porque no sabe cuál sobra.

<Callout type="risk">

- **La fusión puede ser accidental:** dos archivos globales con `interface Config` se fusionan en silencio. Con `moduleDetection: "force"`, o un `import`/`export`, cada interfaz vive en su módulo.
- **La misma propiedad con tipos distintos** da `error TS2717: Subsequent property declarations must have the same type.`

</Callout>

## Paso 6: fijar una convención y aplicarla

**Qué es:** con los experimentos anteriores, una regla para elegir:

| Necesitas…                                  | `interface`                       | `type`                        |
| ------------------------------------------- | --------------------------------- | ----------------------------- |
| Describir la forma de un objeto             | ✅                                | ✅                            |
| Extender otro tipo de objeto                | ✅ `extends` (con errores claros) | ✅ `&` (con errores confusos) |
| Uniones de literales y de objetos           | ❌                                | ✅                            |
| Tuplas y tipos calculados (`keyof`, `Omit`) | ❌                                | ✅                            |
| Ampliar tipos de una librería (fusión)      | ✅                                | ❌                            |

La convención de este curso: **`interface` para formas de objetos** (entidades) y **`type` para todo lo demás**. Usar `type` para todo también es válido; mezclarlos sin criterio, no.

**Cómo se usa:** el modelo de tu app de entrenamiento, en `src/04-modelo.ts`.

```ts
// Archivo: src/04-modelo.ts
type Momento = "desayuno" | "comida" | "cena" | "snack";

interface Usuario {
  readonly id: string;
  nombre: string;
  email: string;
}

interface Ejercicio {
  readonly nombre: string;
  series: number;
  repeticiones: number;
  pesoKg: number;
  notas?: string;
}

interface Comida {
  nombre: string;
  kcal: number;
  momento: Momento;
}

interface DiaEntreno {
  readonly fecha: string; // formato AAAA-MM-DD
  readonly usuarioId: Usuario["id"];
  ejercicios: Ejercicio[];
  comidas?: Comida[];
  aguaMl: number;
}

function volumenTotal(dia: DiaEntreno): number {
  return dia.ejercicios.reduce((total, e) => total + e.series * e.repeticiones * e.pesoKg, 0);
}

function kcalPorMomento(dia: DiaEntreno, momento: Momento): number {
  return (dia.comidas ?? [])
    .filter((comida) => comida.momento === momento)
    .reduce((total, comida) => total + comida.kcal, 0);
}

const usuario: Usuario = { id: "u_1", nombre: "Dani", email: "dani@example.com" };

const jueves: DiaEntreno = {
  fecha: "2026-10-08",
  usuarioId: usuario.id,
  ejercicios: [
    { nombre: "sentadilla", series: 4, repeticiones: 8, pesoKg: 70 },
    { nombre: "press banca", series: 4, repeticiones: 10, pesoKg: 50 },
  ],
  comidas: [
    { nombre: "Avena con plátano", kcal: 420, momento: "desayuno" },
    { nombre: "Pollo con arroz", kcal: 650, momento: "comida" },
    { nombre: "Fruta", kcal: 120, momento: "snack" },
    { nombre: "Frutos secos", kcal: 180, momento: "snack" },
  ],
  aguaMl: 2250,
};

console.log(`${usuario.nombre} · ${jueves.fecha}`);
console.log(`Volumen: ${volumenTotal(jueves)} kg`);
console.log(`Snacks: ${kcalPorMomento(jueves, "snack")} kcal`);
console.log(`Cena: ${kcalPorMomento(jueves, "cena")} kcal`);
```

```bash
npm run typecheck
npm start -- src/04-modelo.ts
```

```text
Dani · 2026-10-08
Volumen: 4240 kg
Snacks: 300 kcal
Cena: 0 kcal
```

- **`usuarioId: Usuario["id"]`:** un _tipo de acceso indexado_. Si los `id` cambian de tipo, `DiaEntreno` se actualiza solo.

<Callout type="risk">

- **Un solo lugar para cada tipo:** copiar `Ejercicio` en otro archivo deshace lo ganado. En B1.7 lo moverás a `src/tipos/`.
- **El modelo de la app no es el de la base de datos:** en MongoDB, `id` será un `ObjectId` llamado `_id`. Los separarás en B5.
- **No añadas campos "por si acaso":** cada opcional es un caso más que manejar en todo el código.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Crea `src/04-ejercicio.ts` con un `type Categoria` para las categorías de color de tu Planificador 2026: `"trabajo" | "personal" | "salud" | "estudio"`.
2. Crea una `interface Tarea` con `id` (solo lectura), `titulo`, `categoria`, `hecha` y `fechaLimite` opcional.
3. Crea una `interface TareaRecurrente extends Tarea` con `cadaDias: number`.
4. Escribe `contarPorCategoria(tareas)` que devuelva un objeto con el número de tareas pendientes de cada categoría (todas las categorías deben aparecer, aunque sea con 0).
5. Usa un array que mezcle tareas normales y recurrentes, y ejecuta `npm run typecheck`.

</Callout>

Solución completa:

```ts
// Archivo: src/04-ejercicio.ts
type Categoria = "trabajo" | "personal" | "salud" | "estudio";

const CATEGORIAS: readonly Categoria[] = ["trabajo", "personal", "salud", "estudio"];

interface Tarea {
  readonly id: string;
  titulo: string;
  categoria: Categoria;
  hecha: boolean;
  fechaLimite?: string;
}

interface TareaRecurrente extends Tarea {
  cadaDias: number;
}

type ConteoPorCategoria = Record<Categoria, number>;

function contarPorCategoria(tareas: Tarea[]): ConteoPorCategoria {
  const conteo: ConteoPorCategoria = { trabajo: 0, personal: 0, salud: 0, estudio: 0 };
  for (const tarea of tareas) {
    if (!tarea.hecha) {
      conteo[tarea.categoria] += 1;
    }
  }
  return conteo;
}

const regarPlantas: TareaRecurrente = {
  id: "t_3",
  titulo: "Regar plantas",
  categoria: "personal",
  hecha: false,
  cadaDias: 3,
};

const tareas: Tarea[] = [
  { id: "t_1", titulo: "Revisar pull request", categoria: "trabajo", hecha: false, fechaLimite: "2026-10-10" },
  { id: "t_2", titulo: "Leer sección B1.4", categoria: "estudio", hecha: true },
  regarPlantas,
  { id: "t_4", titulo: "Correr 5 km", categoria: "salud", hecha: false },
  { id: "t_5", titulo: "Preparar demo", categoria: "trabajo", hecha: false },
];

const conteo = contarPorCategoria(tareas);
for (const categoria of CATEGORIAS) {
  console.log(`${categoria}: ${conteo[categoria]} pendientes`);
}
```

```text
trabajo: 2 pendientes
personal: 1 pendientes
salud: 1 pendientes
estudio: 0 pendientes
```

- **`Categoria` es `type` y `Tarea` es `interface`:** la convención del Paso 6.
- **`Record<Categoria, number>`** obliga a tener **las cuatro** categorías: sin `estudio: 0`, da `Property 'estudio' is missing`.
- **`regarPlantas` entra en `Tarea[]`** porque una `TareaRecurrente` tiene todo lo que pide `Tarea`.

<Callout type="risk">

- **`regarPlantas` se declara aparte a propósito:** escrito dentro del array, el _excess property checking_ rechaza `cadaDias`. Alternativa: `(Tarea | TareaRecurrente)[]`.
- **Dentro del array pierdes `cadaDias`:** cada elemento es `Tarea`. Para distinguirlos hace falta _narrowing_ (B1.6).
- **"1 pendientes" está mal a propósito:** arréglalo con `${n} ${n === 1 ? "pendiente" : "pendientes"}`, o con `Intl.PluralRules` en casos complejos.

</Callout>

<Callout type="mastery">

Puedes justificar por qué elegiste `type` o `interface` en cada caso: `interface` para formas de objetos (con `extends` y fusión), `type` para uniones, tuplas y tipos calculados, y sabes por qué una intersección con propiedades incompatibles acaba en `never`.

</Callout>

## Resumen

- `type` nombra cualquier tipo; `interface` describe objetos. Para objetos simples, son intercambiables.
- `extends` avisa de conflictos; `&` los convierte en `never` sin avisar.
- Solo `type` expresa uniones, tuplas y tipos calculados.
- Solo `interface` se fusiona: así se amplía `App.Locals` en Astro.
- `interface` para entidades, `type` para lo demás, y consistencia.
