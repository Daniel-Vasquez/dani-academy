Los datos reales son "una cosa **u** otra": una fecha como `Date` o como texto, un éxito o un error. Aquí los modelas con **uniones**, los estrechas con **_narrowing_** y haces que el compilador avise cuando olvidas un caso.

**Requisitos:** el `ts-playground`, con lo visto en B1.2 (`unknown`, literales) y en B1.5 (`fetch`).

## Paso 1: el problema de una unión sin estrechar

**Qué es:** una unión `string | Date` significa "cualquiera de los dos". Con ella, TypeScript solo te deja hacer lo que es válido **para ambos**.

**Cómo se usa:** crea `src/06-union.ts`.

```ts
// Archivo: src/06-union.ts
function formatearFecha(fecha: string | Date): string {
  return fecha.toLocaleDateString("es-MX", { timeZone: "America/Mexico_City" });
}

console.log(formatearFecha(new Date("2026-10-09T12:00:00Z")));
```

```bash
npm run typecheck
```

```text
error TS2551: Property 'toLocaleDateString' does not exist on type 'string | Date'. Did you mean 'toLocaleString'?
  Property 'toLocaleDateString' does not exist on type 'string'.
```

- **La segunda línea lo explica:** `toLocaleDateString` existe en `Date`, no en `string`. Ignora la sugerencia de `toLocaleString`. En JavaScript, esto habría explotado con un texto.

<Callout type="risk">

- **No lo arregles con `as`:** `(fecha as Date).toLocaleDateString()` compila y explota con un texto: `fecha.toLocaleDateString is not a function`.
- **Lo común sí funciona sin comprobar:** `fecha.toString()` compila, porque los dos tipos lo tienen.

</Callout>

## Paso 2: estrechar con `typeof` e `instanceof`

**Qué es:** el _narrowing_: tras una comprobación, el compilador **sabe** qué miembro de la unión tienes. `typeof` sirve para los primitivos y `instanceof`, para las clases (`Date`, `Error`, `Map`, `URL`).

**Cómo se usa:** sustituye `src/06-union.ts` por la versión corregida.

```ts
// Archivo: src/06-union.ts
function formatearFecha(fecha: string | Date): string {
  if (typeof fecha === "string") {
    // Aquí dentro TypeScript sabe que fecha es string
    return formatearFecha(new Date(fecha));
  }
  // Aquí, por descarte, fecha es Date
  return fecha.toLocaleDateString("es-MX", { timeZone: "America/Mexico_City", dateStyle: "long" });
}

function describirError(error: unknown): string {
  if (error instanceof Error) {
    return `${error.name}: ${error.message}`;
  }
  if (typeof error === "string") {
    return error;
  }
  return "Error desconocido";
}

console.log(formatearFecha(new Date("2026-10-09T12:00:00Z")));
console.log(formatearFecha("2026-10-09T12:00:00Z"));
console.log(describirError(new TypeError("fetch failed")));
console.log(describirError("Algo salió mal"));
console.log(describirError(42));
```

```bash
npm run typecheck
npm start -- src/06-union.ts
```

```text
9 de octubre de 2026
9 de octubre de 2026
TypeError: fetch failed
Algo salió mal
Error desconocido
```

- **La misma variable, tres tipos:** pasa el ratón por `fecha` en la firma (`string | Date`), dentro del `if` (`string`) y en el último `return` (`Date`). TypeScript sigue el flujo: si el `if` hizo `return`, solo queda `Date`.

<Callout type="risk">

- **`typeof null === "object"`:** si la unión incluye `null`, añade `x !== null`.
- **Fechas inválidas:** `new Date("ayer")` no lanza nada, y `formatearFecha("ayer")` devuelve `"Invalid Date"`. El _narrowing_ comprueba el tipo, no la validez: usa `Number.isNaN(fecha.getTime())`.
- **Zona horaria:** sin `timeZone`, se usa la del servidor. En Vercel es UTC, y un registro de las 21:00 en México saldría al día siguiente.

</Callout>

## Paso 3: estrechar con `in`, igualdad y comprobaciones de verdad

**Qué es:** si los miembros son objetos, `typeof` no los distingue: todos son `"object"`. Entonces se estrecha comprobando una propiedad (`in`) o un valor (`===`).

**Cómo se usa:** crea `src/06-in.ts`.

```ts
// Archivo: src/06-in.ts
interface Running {
  km: number;
  minutos: number;
}

interface Fuerza {
  series: number;
  repeticiones: number;
  pesoKg: number;
}

function resumen(actividad: Running | Fuerza): string {
  if ("km" in actividad) {
    const ritmo = actividad.minutos / actividad.km;
    return `${actividad.km} km a ${ritmo.toFixed(1)} min/km`;
  }
  return `${actividad.series}×${actividad.repeticiones} con ${actividad.pesoKg} kg`;
}

function saludo(nombre: string | null | undefined): string {
  if (nombre == null) {
    // == null atrapa null y undefined a la vez
    return "Hola, invitado";
  }
  return `Hola, ${nombre.trim()}`;
}

function etiquetaVasos(vasos: number | null): string {
  if (vasos === null) return "Sin registrar";
  if (vasos === 0) return "Nada de agua todavía";
  return `${vasos} ${vasos === 1 ? "vaso" : "vasos"}`;
}

console.log(resumen({ km: 5, minutos: 28 }));
console.log(resumen({ series: 4, repeticiones: 8, pesoKg: 70 }));
console.log(saludo(null), "|", saludo(undefined), "|", saludo("  Dani "));
console.log(etiquetaVasos(null), "|", etiquetaVasos(0), "|", etiquetaVasos(1), "|", etiquetaVasos(6));
```

```bash
npm start -- src/06-in.ts
```

```text
5 km a 5.6 min/km
4×8 con 70 kg
Hola, invitado | Hola, invitado | Hola, Dani
Sin registrar | Nada de agua todavía | 1 vaso | 6 vasos
```

- **`"km" in actividad`** estrecha a los miembros que tienen `km` (`Running`).
- **`nombre == null`,** con dos `=`, es la única comparación suelta recomendable: es `true` para `null` **y** `undefined`.
- **`vasos === null`** también estrecha: después, `vasos` es `number`.

<Callout type="risk">

- **`if (vasos)` trata 0 vasos como "sin dato",** porque `0` es falso. Es el problema de `||` frente a `??` (B1.3): compara con `null`.
- **`in` con propiedades opcionales:** si `Fuerza` tuviera `km?: number`, `"km" in actividad` dejaría de distinguirlas. El Paso 5 lo resuelve.

</Callout>

## Paso 4: tus propios _type guards_

**Qué es:** una función que devuelve `valor is Tipo`: "si devuelve `true`, `valor` es un `Tipo`". Encapsula comprobaciones complejas o repetidas.

**Cómo se usa:** crea `src/06-guards.ts`.

```ts
// Archivo: src/06-guards.ts
type Categoria = "trabajo" | "personal" | "salud" | "estudio";

const CATEGORIAS: readonly string[] = ["trabajo", "personal", "salud", "estudio"];

function esCategoria(valor: string): valor is Categoria {
  return CATEGORIAS.includes(valor);
}

interface Tarea {
  titulo: string;
  categoria: Categoria;
}

function crearTarea(titulo: string, categoriaDelFormulario: string): Tarea | null {
  if (!esCategoria(categoriaDelFormulario)) {
    return null;
  }
  // Aquí categoriaDelFormulario ya es Categoria
  return { titulo, categoria: categoriaDelFormulario };
}

// Simula lo que llega de un <select> de un formulario: siempre string
console.log(crearTarea("Correr 5 km", "salud"));
console.log(crearTarea("Hackear la NASA", "ocio"));

// Los guards también sirven en filter: el resultado queda estrechado
const entradas = ["trabajo", "ocio", "salud", "SALUD"];
const validas: Categoria[] = entradas.filter(esCategoria);
console.log(validas);
```

```bash
npm start -- src/06-guards.ts
```

```text
{ titulo: 'Correr 5 km', categoria: 'salud' }
null
[ 'trabajo', 'salud' ]
```

- **Después del `if (esCategoria(…))`,** el texto ya se puede asignar a un campo `Categoria`.
- **`entradas.filter(esCategoria)` devuelve `Categoria[]`.** Con `(c) => CATEGORIAS.includes(c)` sería `string[]`.

<Callout type="risk">

- **TypeScript confía en tu guard sin revisarlo:** si devolviera `true` siempre, "ocio" pasaría como `Categoria`. Mantenlo pequeño y pruébalo.
- **El tipo y el array repiten los valores:** si añades una categoría a uno solo, el guard la rechaza. Se deriva el tipo del array con `as const` (I1).
- **`"SALUD"` se rechaza:** normaliza con `.toLowerCase()` antes de validar, si tu caso lo necesita.

</Callout>

## Paso 5: uniones discriminadas

**Qué es:** una unión de objetos en la que **todos comparten un campo con un literal distinto**, el _discriminante_ (`tipo`, `kind`, `status`). Comprobando ese campo, TypeScript sabe qué objeto tienes.

**Cómo se usa:** crea `src/06-actividades.ts`.

```ts
// Archivo: src/06-actividades.ts
interface Fuerza {
  tipo: "fuerza";
  ejercicio: string;
  series: number;
  repeticiones: number;
  pesoKg: number;
}

interface Running {
  tipo: "running";
  km: number;
  minutos: number;
}

interface Hidratacion {
  tipo: "hidratacion";
  ml: number;
}

type Actividad = Fuerza | Running | Hidratacion;

function resumen(actividad: Actividad): string {
  switch (actividad.tipo) {
    case "fuerza":
      return `${actividad.ejercicio}: ${actividad.series}×${actividad.repeticiones} con ${actividad.pesoKg} kg`;
    case "running":
      return `Running: ${actividad.km} km en ${actividad.minutos} min`;
    case "hidratacion":
      return `Agua: ${actividad.ml} ml`;
    default: {
      const casoNoManejado: never = actividad;
      throw new Error(`Actividad desconocida: ${JSON.stringify(casoNoManejado)}`);
    }
  }
}

const hoy: Actividad[] = [
  { tipo: "running", km: 5, minutos: 28 },
  { tipo: "fuerza", ejercicio: "sentadilla", series: 4, repeticiones: 8, pesoKg: 70 },
  { tipo: "hidratacion", ml: 500 },
  { tipo: "hidratacion", ml: 750 },
];

for (const actividad of hoy) {
  console.log(`- ${resumen(actividad)}`);
}

const aguaTotal = hoy
  .filter((a): a is Hidratacion => a.tipo === "hidratacion")
  .reduce((total, a) => total + a.ml, 0);
console.log(`Agua total: ${aguaTotal} ml`);
```

```bash
npm run typecheck
npm start -- src/06-actividades.ts
```

```text
- Running: 5 km en 28 min
- sentadilla: 4×8 con 70 kg
- Agua: 500 ml
- Agua: 750 ml
Agua total: 1250 ml
```

- **`tipo: "fuerza"`** es el literal `"fuerza"`, no un `string` cualquiera.
- **En cada `case`, `actividad` se estrecha:** dentro de `case "running"`, el autocompletado solo ofrece `tipo`, `km` y `minutos`.
- **El `default` con `never`:** si manejas todos los casos, en el `default` no queda ninguno posible, y `actividad` es `never`.

<Callout type="risk">

- **El discriminante debe ser un literal en todos los miembros:** con un `tipo: string`, el estrechamiento deja de funcionar.
- **Lo que llega de MongoDB o de una API no es literal:** un `tipo: "natacion"` desconocido llega al `default` en ejecución. Por eso el `default` lanza un error con el valor recibido.
- **No metas objetos grandes en los mensajes de error:** `JSON.stringify` puede llenar los registros o filtrar datos personales. Registra solo `tipo`.

</Callout>

## Paso 6: que el compilador te obligue a manejar casos nuevos

**Qué es:** la **comprobación exhaustiva**: con el `default` de `never`, un miembro nuevo de la unión es un error de compilación en cada `switch` que no lo maneje.

**Cómo se usa:** añade un miembro nuevo en `src/06-actividades.ts`, sin tocar nada más. Sustituye la línea `type Actividad = ...` y pon la interfaz justo encima:

```ts
interface Nutricion {
  tipo: "nutricion";
  comida: string;
  kcal: number;
}

type Actividad = Fuerza | Running | Hidratacion | Nutricion;
```

```bash
npm run typecheck
```

```text
error TS2322: Type 'Nutricion' is not assignable to type 'never'.
```

El error te lleva al `default` de la función que olvidaste. Añade el caso que falta, antes del `default`:

```ts
    case "nutricion":
      return `${actividad.comida}: ${actividad.kcal} kcal`;
```

Y una comida a la lista `hoy`:

```ts
  { tipo: "nutricion", comida: "Avena con plátano", kcal: 420 },
```

Con `npm run typecheck` ya no hay errores, y `npm start -- src/06-actividades.ts` da:

```text
- Running: 5 km en 28 min
- sentadilla: 4×8 con 70 kg
- Agua: 500 ml
- Agua: 750 ml
- Avena con plátano: 420 kcal
Agua total: 1250 ml
```

- **Sin ese `default`,** la actividad nueva caería en un caso por defecto y verías textos vacíos en la interfaz.

<Callout type="risk">

- **`if/else` no protege igual:** el último `else` se traga cualquier tipo nuevo sin avisar. Usa `switch` con `default: never`.
- **Un `default: return ""` "por si acaso"** desactiva la comprobación exhaustiva.
- **Muchos `switch` sobre lo mismo:** agrupa la lógica en un objeto con una función por tipo. Habrá menos sitios que tocar.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Crea `src/06-ejercicio.ts` y modela el estado de una petición a una API como una unión discriminada por `estado`: `"idle"`, `"loading"`, `"success"` (con `datos`) y `"error"` (con `mensaje`).
2. Escribe `renderizar(estado)`, que devuelva un texto distinto para cada estado, con comprobación exhaustiva.
3. Escribe `cargarUsuario(id)`, que llame a `https://jsonplaceholder.typicode.com/users/:id` y devuelva el estado final (`success` o `error`), sin lanzar nunca errores.
4. Simula el ciclo completo para el id `1` y para el `999`, imprimiendo cada estado por el que pasa.

</Callout>

Solución completa:

```ts
// Archivo: src/06-ejercicio.ts
interface Usuario {
  id: number;
  name: string;
  email: string;
}

type EstadoPeticion<T> =
  | { estado: "idle" }
  | { estado: "loading" }
  | { estado: "success"; datos: T }
  | { estado: "error"; mensaje: string };

function renderizar(e: EstadoPeticion<Usuario>): string {
  switch (e.estado) {
    case "idle":
      return "Pulsa el botón para cargar el usuario";
    case "loading":
      return "Cargando…";
    case "success":
      return `${e.datos.name} <${e.datos.email}>`;
    case "error":
      return `Error: ${e.mensaje}`;
    default: {
      const casoNoManejado: never = e;
      throw new Error(`Estado desconocido: ${JSON.stringify(casoNoManejado)}`);
    }
  }
}

async function cargarUsuario(id: number): Promise<EstadoPeticion<Usuario>> {
  try {
    const res = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`, {
      signal: AbortSignal.timeout(5000),
    });
    if (!res.ok) {
      return { estado: "error", mensaje: `HTTP ${res.status}` };
    }
    const datos = (await res.json()) as Usuario;
    return { estado: "success", datos };
  } catch (error) {
    return { estado: "error", mensaje: error instanceof Error ? error.message : "Error de red" };
  }
}

for (const id of [1, 999]) {
  let estado: EstadoPeticion<Usuario> = { estado: "idle" };
  console.log(`[${id}] ${renderizar(estado)}`);

  estado = { estado: "loading" };
  console.log(`[${id}] ${renderizar(estado)}`);

  estado = await cargarUsuario(id);
  console.log(`[${id}] ${renderizar(estado)}`);
}
```

```bash
npm run typecheck
npm start -- src/06-ejercicio.ts
```

```text
[1] Pulsa el botón para cargar el usuario
[1] Cargando…
[1] Leanne Graham <Sincere@april.biz>
[999] Pulsa el botón para cargar el usuario
[999] Cargando…
[999] Error: HTTP 404
```

Compárala con la alternativa ingenua, muy habitual:

```ts
interface EstadoIngenuo {
  cargando: boolean;
  datos?: Usuario;
  error?: string;
}
```

- **Con el tipo ingenuo,** `{ cargando: true, datos: usuario, error: "falló" }` es válido, aunque no tiene sentido. La unión discriminada hace **imposibles los estados imposibles**, y en `case "success"`, `e.datos` existe sin `?.`.

<Callout type="risk">

- **`EstadoPeticion<T>` es un genérico:** `T` es un hueco que rellenas al usarlo (`EstadoPeticion<Usuario>`). Se ven a fondo en I1.
- **Peticiones que se pisan:** si se pulsa dos veces, la respuesta más lenta puede sobrescribir a la más reciente. En React se resuelve con `AbortController` (B6).
- **`cargarUsuario` nunca lanza:** quien la llama **debe** mirar el estado, o el error desaparece en silencio.

</Callout>

<Callout type="mastery">

Usas uniones discriminadas en lugar de objetos con muchos campos opcionales, sabes qué comprobación estrecha cada tipo de unión (`typeof`, `instanceof`, `in`, igualdad o un guard propio) y cada `switch` sobre un discriminante tiene un `default` con `never` que te avisa cuando aparece un caso nuevo.

</Callout>

## Resumen

- Una unión solo permite lo común a todos sus miembros hasta que la estrechas.
- `typeof` para primitivos, `instanceof` para clases, `in` para objetos y `== null` para vacíos.
- Un guard `valor is Tipo` sirve en `filter`, pero el compilador no lo revisa.
- Las uniones discriminadas hacen imposibles los estados imposibles.
- `default` con `never`: cada caso olvidado es un error de compilación.
