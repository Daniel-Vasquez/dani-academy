Hasta ahora has hablado con PostgreSQL desde `psql`. Una aplicación lo hace desde su código, y ahí aparecen problemas que `psql` no tiene: cómo pasar los datos de la petición sin abrir la puerta a una inyección SQL, qué tipo de JavaScript llega por cada tipo de PostgreSQL, cómo mantener el esquema de la base de datos al día con el código y cuántas conexiones abre cada instancia de tu app. En esta sección vas a conectar con el _driver_ `pg`, después vas a usar **Drizzle ORM**, que describe las tablas en TypeScript y genera las migraciones, y terminarás con el repositorio de evaluaciones de esta plataforma funcionando sobre PostgreSQL con la misma interfaz que el de MongoDB (I3.5).

**Lo que tendrás al terminar:** un proyecto `pg-ts` con un _pool_ de conexiones, el esquema de las evaluaciones en Drizzle con dos migraciones aplicadas, y el repositorio de evaluaciones en MongoDB y en PostgreSQL pasando los mismos 5 tests.

**Requisitos:** las secciones A3.1–A3.3 (PostgreSQL 18), I3.5 (repositorios inyectados) y Node 24 o superior, que ejecuta TypeScript sin compilar.

## Paso 1: conectar con `pg` y no concatenar SQL nunca

La aplicación no debe conectarse como `postgres`, que puede hacerlo todo. Crea un rol propio, con contraseña, y una base para esta sección (cambia la clave):

```bash
sudo -u postgres psql -c "CREATE ROLE academy_app LOGIN PASSWORD 'cambia-esta-clave'"
sudo -u postgres psql -c "CREATE DATABASE academia_ts OWNER academy_app"
```

La conexión llega por TCP (`localhost:5432`), con contraseña, y PostgreSQL 18 la comprueba con `scram-sha-256` sin tocar nada. Si PostgreSQL está en Docker, publica el puerto con `-p 5432:5432` (A3.1). Si está en una VM, reenvía el 5432 a tu equipo: Lima, por ejemplo, lo hace solo.

Crea el proyecto, en tu equipo:

`src/01-conectar.ts` conecta y busca un usuario por correo de dos formas: pegando el texto en el SQL y pasándolo como parámetro:

```ts
// Archivo: src/01-conectar.ts
// Conectar con node-postgres y consultar con parámetros, y por qué nunca se concatena SQL
import { pool } from "./db.ts";

const { rows: [info] } = await pool.query("SELECT current_user AS usuario, current_database() AS base, version()");
console.log(info);

await pool.query(`
  DROP TABLE IF EXISTS usuarios;
  CREATE TABLE usuarios (email text PRIMARY KEY, nombre text NOT NULL);
  INSERT INTO usuarios VALUES ('ana@ejemplo.com', 'Ana'), ('luis@ejemplo.com', 'Luis'), ('marta@ejemplo.com', 'Marta');
`);

// MAL: el texto de la petición se pega dentro del SQL
async function buscarConcatenando(email: string) {
  const { rows } = await pool.query(`SELECT nombre FROM usuarios WHERE email = '${email}'`);
  return rows.map((r) => r.nombre);
}

// BIEN: el SQL va por un lado y los valores por otro ($1)
async function buscarConParametro(email: string) {
  const { rows } = await pool.query("SELECT nombre FROM usuarios WHERE email = $1", [email]);
  return rows.map((r) => r.nombre);
}

for (const entrada of ["ana@ejemplo.com", "x' OR '1'='1", "x'; DROP TABLE usuarios; --"]) {
  console.log(`\nentrada: ${entrada}`);
  console.log("  con parámetro: ", await buscarConParametro(entrada));
  try {
    console.log("  concatenando:  ", await buscarConcatenando(entrada));
  } catch (error) {
    console.log("  concatenando:   error:", (error as Error).message);
  }
}

const { rows: tablas } = await pool.query("SELECT to_regclass('usuarios') AS existe");
console.log("\n¿Sigue existiendo la tabla usuarios?", tablas[0]?.existe ?? null);

await pool.end();
```

```text
$ node --env-file=.env src/01-conectar.ts
{
  usuario: 'academy_app',
  base: 'academia_ts',
  version: 'PostgreSQL 18.6 (Ubuntu 18.6-0ubuntu0.26.04.1) on aarch64-unknown-linux-gnu, compiled by gcc (Ubuntu 15.2.0-16ubuntu1) 15.2.0, 64-bit'
}

entrada: ana@ejemplo.com
  con parámetro:  [ 'Ana' ]
  concatenando:   [ 'Ana' ]

entrada: x' OR '1'='1
  con parámetro:  []
  concatenando:   [ 'Ana', 'Luis', 'Marta' ]

entrada: x'; DROP TABLE usuarios; --
  con parámetro:  []
  concatenando:   error: Cannot read properties of undefined (reading 'map')

¿Sigue existiendo la tabla usuarios? null
```

- **Con `$1`, el SQL y los datos viajan por separado:** PostgreSQL recibe la consulta ya analizada y el valor aparte, así que `x' OR '1'='1` es solo un correo que no existe. No hay forma de que un dato se convierta en SQL.
- **Concatenando, el dato se convierte en SQL:** `x' OR '1'='1` cierra la comilla y añade una condición que siempre se cumple, y devuelve los tres usuarios.
- **Y puede ejecutar más de una sentencia:** sin parámetros, `pg` usa el protocolo simple de PostgreSQL, que acepta varias sentencias separadas por `;`. La tercera entrada borró la tabla `usuarios` (`to_regclass` devuelve `null`). El error que se ve llega **después** del daño: con dos sentencias, `pg` devuelve un _array_ de resultados sin `rows`.

<Callout type="risk">

- **Ningún dato de la petición va dentro del texto del SQL:** ni del formulario, ni de la URL, ni de la cabecera, ni de la base de datos. Ni siquiera "ya validado": el día que cambie la validación, el agujero aparece. Si necesitas variar algo que no es un valor (el nombre de una columna para ordenar), elige entre una lista cerrada en tu código, nunca el texto tal cual.
- **El rol de la aplicación, con lo justo:** `academy_app` es dueño solo de su base. Si una inyección se cuela, el daño se limita a lo que ese rol puede hacer. Con el usuario `postgres`, podría borrar cualquier base del servidor.

</Callout>

## Paso 2: los tipos que llegan mal a JavaScript

`pg` convierte cada valor según su tipo de PostgreSQL. `src/02-tipos.ts` consulta un valor de cada tipo y lo ejecuta en dos zonas horarias:

```ts
// Archivo: src/02-tipos.ts
// Qué tipo de JavaScript llega por cada tipo de PostgreSQL
import { pool } from "./db.ts";

const { rows: [fila] } = await pool.query(`
  SELECT count(*)                          AS count_bigint,
         9007199254740993::bigint          AS bigint_grande,
         4.5::numeric(3,1)                 AS numeric,
         42::integer                       AS integer,
         0.1::float8 + 0.2::float8         AS float8,
         true                              AS boolean,
         timestamptz '2026-10-01 10:00:00+00' AS timestamptz,
         date '2026-10-01'                 AS date,
         '{"tema": "dark", "avisos": [1, 2]}'::jsonb AS jsonb,
         ARRAY['B1', 'I3']                 AS text_array
  FROM generate_series(1, 3)
`);

for (const [columna, valor] of Object.entries(fila ?? {})) {
  const tipo = valor instanceof Date ? "Date" : Array.isArray(valor) ? "array" : typeof valor;
  console.log(columna.padEnd(13), tipo.padEnd(7), valor instanceof Date ? valor.toISOString() : JSON.stringify(valor));
}

// La trampa del tipo date: por defecto llega como medianoche en la zona horaria de Node
const dia: unknown = fila?.date;
const enIso = dia instanceof Date ? dia.toISOString().slice(0, 10) : dia;
console.log(`\nTZ=${process.env.TZ}: date '2026-10-01' llega como el día ${enIso}`);

await pool.end();
```

- **`count(*)` llega como _string_ (`"3"`):** `count` devuelve `bigint`, que puede superar el entero exacto más grande de JavaScript (2^53), y `pg` no se arriesga. `"3" + 1` da `"31"`.
- **`numeric` también llega como _string_ (`"4.5"`):** a propósito, para no perder decimales. Es el tipo del dinero (A3.1).
- **`date` llega como un `Date` a medianoche de la zona horaria de Node:** en Ciudad de México, medianoche son las 06:00 UTC y el día no cambia; en Madrid, medianoche son las 22:00 UTC **del día anterior**, y `toISOString()` dice 30 de septiembre. El mismo código da días distintos según dónde corra el servidor.
- **`timestamptz` sí es fiable:** es un instante, y llega como el `Date` de ese instante en cualquier zona.

Los dos primeros se arreglan una vez, al crear el _pool_. Sustituye `src/db.ts`:

```ts
// Archivo: src/db.ts
// Un único pool de conexiones para todo el proceso, y los tipos que node-postgres convierte mal
import pg from "pg";

// date (OID 1082): se queda como "2026-10-01". Por defecto sería un Date a medianoche LOCAL,
// que en una zona por delante de UTC cambia de día al pasarlo a ISO
pg.types.setTypeParser(pg.types.builtins.DATE, (valor) => valor);
// bigint (OID 20), el tipo de count(*): a number. Seguro para contadores; no para valores
// por encima de 2^53 (los id de una tabla enorme), que perderían precisión
pg.types.setTypeParser(pg.types.builtins.INT8, (valor) => Number(valor));
// numeric se queda como string a propósito: convertirlo a number perdería decimales

const url = process.env.DATABASE_URL;
if (!url) throw new Error("Falta DATABASE_URL (¿has creado el .env?)");

export const pool = new pg.Pool({ connectionString: url, max: 10 });
```

El día ya es el mismo en las dos zonas, y `count(*)` es un número. Fíjate en `bigint_grande`: `9007199254740993` se ha convertido en `9007199254740992`, porque supera 2^53. Por eso el _parser_ de `bigint` sirve para contadores, pero no para cualquier columna `bigint`.

<Callout type="risk">

- **Los _parsers_ son globales:** `pg.types.setTypeParser` cambia la conversión para todo el proceso, también para otras librerías que usen `pg`. Regístralos en un solo sitio (`db.ts`) y antes de la primera consulta.
- **Con un `bigint` de verdad, usa `BigInt` o déjalo como texto:** un `id` de una tabla con miles de millones de filas no cabe en un `number`. Drizzle (Paso 3) declara cada columna `bigint` con `mode: "number"` o `mode: "bigint"`, y tienes que elegir.
- **`float8` tiene los errores de siempre:** `0.1 + 0.2` da `0.30000000000000004`, igual que en JavaScript. Para cantidades exactas, `numeric`.

</Callout>

## Paso 3: el esquema en TypeScript con Drizzle

Escribir SQL a mano en cada consulta tiene dos problemas: nada comprueba que `user_id` exista o sea un texto, y los tipos de las filas hay que escribirlos aparte. **Drizzle ORM** describe las tablas en TypeScript, y de ese esquema salen los tipos de las filas, las consultas tipadas y las migraciones. A diferencia de otros ORM, sus consultas se parecen mucho al SQL que generan.

El esquema de las evaluaciones, con la misma forma que la colección `quiz_attempts` de la plataforma y las restricciones que en MongoDB vivían en el validador (`db-setup.ts`). `src/schema.ts`:

```ts
// Archivo: src/schema.ts
// El esquema de las evaluaciones, en TypeScript: de aquí salen los tipos y las migraciones
import { sql } from "drizzle-orm";
import {
  bigint,
  boolean,
  check,
  index,
  pgTable,
  smallint,
  text,
  timestamp,
} from "drizzle-orm/pg-core";

export const quizAttempts = pgTable(
  "quiz_attempts",
  {
    id: bigint("id", { mode: "number" }).primaryKey().generatedAlwaysAsIdentity(),
    userId: text("user_id").notNull(),
    courseId: text("course_id").notNull(),
    answers: smallint("answers").array().notNull(),
    results: boolean("results").array().notNull(),
    score: smallint("score").notNull(),
    total: smallint("total").notNull(),
    passed: boolean("passed").notNull(),
    submittedAt: timestamp("submitted_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    check("course_id_valido", sql`${t.courseId} ~ '^([BIA][1-8]|P1)$'`),
    check("score_en_rango", sql`${t.score} BETWEEN 0 AND ${t.total}`),
    check("cinco_respuestas", sql`cardinality(${t.answers}) = 5 AND cardinality(${t.results}) = 5`),
    // Las consultas del repositorio: por usuario y curso, y por usuario, de la más reciente
    index("quiz_attempts_user_course_submitted").on(t.userId, t.courseId, t.submittedAt.desc()),
    index("quiz_attempts_user_submitted").on(t.userId, t.submittedAt.desc()),
  ],
);

// Los tipos salen del esquema: nunca se desincronizan de la tabla
export type QuizAttemptRow = typeof quizAttempts.$inferSelect;
export type NewQuizAttempt = typeof quizAttempts.$inferInsert;
```

`drizzle-kit` es la herramienta de línea de comandos que compara el esquema con las migraciones anteriores y escribe el SQL que falta. `drizzle.config.ts`:

<Callout type="risk">

- **El esquema de TypeScript no es la base de datos:** lo que manda es lo que hay en PostgreSQL. Si alguien cambia una tabla a mano, el esquema miente y Drizzle no se entera. Todos los cambios, por migraciones.
- **`drizzle-kit push` aplica el esquema sin migración:** es cómodo en un prototipo, pero no deja rastro ni se puede revisar, y en una base con datos puede proponer borrar una columna para crear otra. En cualquier base que importe, `generate` y `migrate`.
- **Un `CHECK` escrito con `` sql`…` `` no lo comprueba TypeScript:** la expresión regular de `course_id_valido` es texto. Si tiene un error, lo verás al aplicar la migración, no al compilar.

</Callout>

## Paso 4: consultas con Drizzle, y el SQL que generan

`src/orm.ts` crea Drizzle sobre el mismo _pool_ de `pg`:

```ts
// Archivo: src/orm.ts
// Drizzle sobre el mismo pool de node-postgres
import { drizzle } from "drizzle-orm/node-postgres";
import { pool } from "./db.ts";
import * as schema from "./schema.ts";

export const db = drizzle(pool, { schema });
export type Database = typeof db;
```

`src/04-consultas.ts` inserta, consulta, agrega y prueba los límites:

```ts
// Archivo: src/04-consultas.ts
// Insertar y consultar con Drizzle, y ver el SQL que genera
import { and, count, desc, eq, sql } from "drizzle-orm";
import { PgDialect } from "drizzle-orm/pg-core";
import { db } from "./orm.ts";
import { pool } from "./db.ts";
import { quizAttempts, type NewQuizAttempt } from "./schema.ts";

await db.delete(quizAttempts);

// 1. Insertar: el tipo NewQuizAttempt sale del esquema (id y submittedAt son opcionales)
const intento: NewQuizAttempt = {
  userId: "u_00042",
  courseId: "A3",
  answers: [1, 2, 0, 3, 1],
  results: [true, true, true, false, true],
  score: 4,
  total: 5,
  passed: true,
};
const [creado] = await db.insert(quizAttempts).values(intento).returning();
console.log("insertado:", creado);

// 2. Consultar: los nombres son los de TypeScript (userId), el SQL usa los de la tabla (user_id)
const consulta = db
  .select({ courseId: quizAttempts.courseId, score: quizAttempts.score, submittedAt: quizAttempts.submittedAt })
  .from(quizAttempts)
  .where(and(eq(quizAttempts.userId, "u_00042"), eq(quizAttempts.courseId, "A3")))
  .orderBy(desc(quizAttempts.submittedAt))
  .limit(5);
console.log("\nSQL generado:", consulta.toSQL());
console.log("filas:", await consulta);

// 3. sql`…` para lo que Drizzle no expresa: los valores ${…} también van como parámetros
const entrada = "x' OR '1'='1";
const peligrosa = sql`SELECT count(*) FROM quiz_attempts WHERE user_id = ${entrada}`;
console.log("\nsql`…` con una inyección:", new PgDialect().sqlToQuery(peligrosa), (await db.execute(peligrosa)).rows);

// 4. Agregaciones con las funciones de Drizzle
const porCurso = await db
```

- **El índice está en `DESC NULLS LAST`:** Drizzle añade `NULLS LAST` a todas las columnas de un índice si no le dices otra cosa.

- **Comprueba con `EXPLAIN` las consultas que genera el ORM:** el SQL de Drizzle es correcto y legible, pero los detalles (como el orden de los nulos) se ven en el plan, no en el código TypeScript. Haz con `toSQL()` y `EXPLAIN ANALYZE` lo que hiciste en A3.3.
- **Con pocas filas, el fallo no se nota:** con 8 intentos por usuario y curso, ordenar no cuesta nada, y este problema habría pasado todas las pruebas. Mide con el volumen que tendrá la tabla en producción, o con el peor usuario.
- **`select()` sin columnas trae todas:** como `SELECT *`. Para listados, pide solo lo que vas a mostrar, como la consulta del punto 2.

</Callout>

## Paso 5: una migración para arreglarlo

El arreglo es declarar el índice con el mismo orden que la consulta. En `src/schema.ts`, cambia los dos índices (el resto del archivo no cambia):

```ts
  bigint,

  pgTable,
  smallint,

  timestamp,

export const quizAttempts = pgTable(
  "quiz_attempts",
  {
    id: bigint("id", { mode: "number" }).primaryKey().generatedAlwaysAsIdentity(),
    userId: text("user_id").notNull(),
    courseId: text("course_id").notNull(),
    answers: smallint("answers").array().notNull(),
    results: boolean("results").array().notNull(),
    score: smallint("score").notNull(),
    total: smallint("total").notNull(),
    passed: boolean("passed").notNull(),

    index("quiz_attempts_user_course_submitted").on(t.userId, t.courseId, t.submittedAt.desc().nullsFirst()),
```

## Paso 6: el _pool_ de conexiones en _serverless_

Cada conexión a PostgreSQL es un proceso del servidor, y el servidor admite un número limitado (`max_connections`, 100 por defecto, con 3 reservadas para superusuarios). Un _pool_ abre unas pocas conexiones y las reutiliza entre peticiones. El error típico en _serverless_ es crear el _pool_ dentro del _handler_: cada invocación abre los suyos y no los cierra. `src/06-pool.ts` lanza 120 peticiones a la vez de las dos formas:

```ts
// Archivo: src/06-pool.ts
// 120 peticiones a la vez: un Pool nuevo por petición frente a un Pool compartido
import pg from "pg";

const url = process.env.DATABASE_URL!;
// La conexión que mide: se abre al principio y no se cierra, para tener sitio cuando el servidor se llene
const admin = new pg.Pool({ connectionString: url, max: 1, idleTimeoutMillis: 0 });

/** Conexiones de la aplicación abiertas ahora mismo en el servidor */
async function conexiones() {
  const { rows } = await admin.query(
    "SELECT count(*)::int AS n FROM pg_stat_activity WHERE usename = current_user AND pid <> pg_backend_pid()",
  );
  return rows[0].n as number;
}

/** Espera a que el servidor registre las desconexiones (pool.end() no espera a que termine) */
async function hastaQueSeCierren() {
  for (let i = 0; i < 100 && (await conexiones()) > 0; i++) await new Promise((r) => setTimeout(r, 50));
}

console.log(`Conexiones de la app al empezar: ${await conexiones()}\n`);

// MAL: cada "invocación" crea su propio Pool (como si estuviera dentro del handler) y no lo cierra
const abandonados: pg.Pool[] = [];
async function invocacionConPoolPropio() {
  const pool = new pg.Pool({ connectionString: url });
  abandonados.push(pool);
  await pool.query("SELECT pg_sleep(0.2)");
}

/** Las peticiones que fallaron, de un lote de Promise.allSettled */
const fallos = (r: PromiseSettledResult<unknown>[]) => r.filter((x): x is PromiseRejectedResult => x.status === "rejected");

let fallidas = fallos(await Promise.allSettled(Array.from({ length: 120 }, invocacionConPoolPropio)));
console.log("Pool por petición:");
console.log(`  ${120 - fallidas.length} bien, ${fallidas.length} con error`);
console.log(`  primer error: ${fallidas[0]?.reason.message}`);
console.log(`  conexiones que siguen abiertas al terminar: ${await conexiones()}`);
await Promise.all(abandonados.map((p) => p.end()));
await hastaQueSeCierren();
console.log(`  tras cerrar los pools a mano: ${await conexiones()}`);

// BIEN: un único Pool compartido por todas las peticiones del proceso
const pool = new pg.Pool({ connectionString: url, max: 10 });
let pico = 0;
const vigia = setInterval(async () => (pico = Math.max(pico, await conexiones())), 20);
const inicio = performance.now();
fallidas = fallos(await Promise.allSettled(Array.from({ length: 120 }, () => pool.query("SELECT pg_sleep(0.2)"))));
clearInterval(vigia);
console.log("\nPool compartido (max: 10):");
console.log(`  ${120 - fallidas.length} bien, ${fallidas.length} con error, en ${Math.round(performance.now() - inicio)} ms`);
console.log(`  pico de conexiones: ${pico}`);

await pool.end();
await admin.end();
```

- **Un _pool_ por petición:** las primeras 96 consiguen conexión y las 24 siguientes reciben `remaining connection slots are reserved for roles with the SUPERUSER attribute`: el servidor está lleno. Y las 96 conexiones **siguen abiertas** al terminar, hasta que cada _pool_ se cierre. En _serverless_ eso no pasa nunca de forma explícita: se quedan hasta que la plataforma congela o destruye la instancia.
- **Un _pool_ compartido de 10:** las 120 terminan bien, con un pico de exactamente 10 conexiones. Las peticiones que no tienen conexión libre esperan su turno: 12 tandas de 0,2 s, unos 2,4 s.

En una app de Astro en Vercel, como esta plataforma, el _pool_ se crea **fuera** del _handler_, en un módulo (como `src/db.ts`), y cada instancia de la función lo reutiliza entre invocaciones. Es lo mismo que hace `src/lib/mongo.ts` con MongoDB. Dos ajustes más:

- **`attachDatabasePool(pool)` de `@vercel/functions`:** admite el _pool_ de `pg` (sus tipos lo listan, junto con MongoDB y otros) y mantiene viva la instancia hasta que el _pool_ cierra las conexiones inactivas, según su `idleTimeoutMillis`. Es lo que la plataforma hace con MongoDB desde la Tanda 10.
- **Un _pooler_ delante de PostgreSQL:** con muchas instancias a la vez, ni un _pool_ por instancia basta (100 instancias × 10 conexiones). Los servicios gestionados (Neon, Supabase) ofrecen una URL "pooled" con PgBouncer delante, que reparte pocas conexiones reales entre muchas instancias.

<Callout type="risk">

- **Nunca `new Pool()` dentro de una función que se ejecuta por petición:** ni en un _endpoint_, ni en una Action, ni en un servicio. Un único módulo lo crea, y todo lo demás lo importa.
- **Ajusta `max` a lo que tu servidor aguanta:** con `max: 10` y 10 instancias, son 100 conexiones, todo el servidor. Calcula `max` × instancias posibles y deja margen para las migraciones y para ti.
- **Con un _pooler_ en modo transacción, cuidado con el estado de la sesión:** cada transacción puede ir por una conexión distinta, así que `SET` de sesión, las tablas temporales o las sentencias preparadas con nombre (`.prepare()` de Drizzle) pueden fallar o mezclarse entre clientes, salvo que el _pooler_ las admita. Las consultas normales de Drizzle con `pg` usan sentencias sin nombre y funcionan.

</Callout>

```ts
// Archivo: src/repositories/quiz-attempts.mongo.ts
// El repositorio de la plataforma (src/server/repositories/quiz-attempts.repo.ts), contra el contrato común
import type { Db } from "mongodb";
import type { CourseQuizSummary, QuizAttempt, QuizAttemptsRepo } from "./tipos.ts";

export function createQuizAttemptsRepo(db: Db): QuizAttemptsRepo {
  const col = db.collection<QuizAttempt>("quiz_attempts");
  const sinId = { projection: { _id: 0 } } as const; // el dominio no conoce el _id de MongoDB

  return {
    async insert(attempt) {
      await col.insertOne({ ...attempt }); // copia: insertOne añade _id al objeto que recibe
    },

    async listByCourse(userId, courseId, limit = 5) {
      return col.find({ userId, courseId }, sinId).sort({ submittedAt: -1 }).limit(limit).toArray();
    },

    async recent(userId, limit = 20) {
      return col.find({ userId }, sinId).sort({ submittedAt: -1 }).limit(limit).toArray();
    },

    async summaryByCourse(userId) {
      const rows = await col
        .aggregate<Omit<CourseQuizSummary, "courseId"> & { _id: string }>([
          { $match: { userId } },
          { $sort: { submittedAt: -1 } },
          {
            $group: {
              _id: "$courseId",
              attempts: { $sum: 1 },
              best: { $max: "$score" },
              passed: { $max: "$passed" }, // true > false en el orden BSON
              lastScore: { $first: "$score" },
              lastAt: { $first: "$submittedAt" },
            },
          },
        ])
        .toArray();
      return Object.fromEntries(rows.map(({ _id, ...r }) => [_id, { ...r, courseId: _id }]));
    },
  };
}
```

```ts
  results: quizAttempts.results,
  score: quizAttempts.score,
  total: quizAttempts.total,
  passed: quizAttempts.passed,
  submittedAt: quizAttempts.submittedAt,
};

export function createQuizAttemptsRepo(db: Database): QuizAttemptsRepo {
  return {
    async insert(attempt) {
      await db.insert(quizAttempts).values(attempt);
    },

    async listByCourse(userId, courseId, limit = 5) {
      return db
        .select(columnas)
        .from(quizAttempts)
        .where(and(eq(quizAttempts.userId, userId), eq(quizAttempts.courseId, courseId)))
        .orderBy(desc(quizAttempts.submittedAt))
        .limit(limit);
    },

    async recent(userId, limit = 20) {
      return db
        .select(columnas)
        .from(quizAttempts)
        .where(eq(quizAttempts.userId, userId))
        .orderBy(desc(quizAttempts.submittedAt))
        .limit(limit);
    },

    async summaryByCourse(userId) {
      const rows = await db
        .select({
          courseId: quizAttempts.courseId,
          attempts: count(),
          best: max(quizAttempts.score),
          passed: sql<boolean>`bool_or(${quizAttempts.passed})`,
          // La nota del intento más reciente: el primero del array ordenado por fecha
          lastScore: sql<number>`(array_agg(${quizAttempts.score} ORDER BY ${quizAttempts.submittedAt} DESC))[1]`,
          lastAt: max(quizAttempts.submittedAt),
        })
        .from(quizAttempts)
        .where(eq(quizAttempts.userId, userId))
        .groupBy(quizAttempts.courseId);

      // max() puede devolver null en un grupo vacío; aquí cada grupo tiene al menos un intento
      return Object.fromEntries(rows.map((r) => [r.courseId, { ...r, best: r.best!, lastAt: r.lastAt! }]));
    },
  };
}
```

```ts
  courseId,
  answers: [0, 0, 0, 0, 0],
  results: Array.from({ length: 5 }, (_, i) => i < score),
  score,
  total: 5,
  passed: score >= 4,
  submittedAt: new Date(submittedAt),
});

export function contratoQuizAttempts(nombre: string, preparar: () => Promise<QuizAttemptsRepo>) {
  describe(`quiz-attempts (${nombre})`, () => {
    let repo: QuizAttemptsRepo;
    beforeEach(async () => {
      repo = await preparar(); // cada test empieza con la tabla o la colección vacía
    });

    it("summaryByCourse: intentos, mejor nota, aprobado alguna vez y último intento", async () => {
      await repo.insert(attempt("B1", 3, "2026-10-01T10:00:00Z"));
      await repo.insert(attempt("B1", 5, "2026-10-02T10:00:00Z"));
      await repo.insert(attempt("B1", 2, "2026-10-03T10:00:00Z"));
      await repo.insert(attempt("B2", 1, "2026-10-04T10:00:00Z"));

      expect(summary.B1).toEqual({
        courseId: "B1",
        attempts: 3,
        best: 5,
        passed: true, // aprobó una vez, aunque el último intento suspendiera
        lastScore: 2,
        lastAt: new Date("2026-10-03T10:00:00Z"),
      });
      expect(summary.B2).toMatchObject({ attempts: 1, best: 1, passed: false });
      expect(await repo.summaryByCourse("u2")).toEqual({});
    });

    it("listByCourse ordena del más reciente al más antiguo y respeta el límite", async () => {
      for (let day = 1; day <= 7; day++) {
        await repo.insert(attempt("B1", day % 6, `2026-10-0${day}T10:00:00Z`));
      }
      const list = await repo.listByCourse("u1", "B1");
      expect(list).toHaveLength(5);
      expect(list[0]!.submittedAt).toEqual(new Date("2026-10-07T10:00:00Z"));
      expect((await repo.recent("u1", 2)).map((a) => a.submittedAt.getUTCDate())).toEqual([7, 6]);

      await repo.insert(original);
      expect(await repo.recent("u1")).toEqual([original]);
    });

    it("recent devuelve como mucho 20 por defecto, de todos los cursos", async () => {

      }
      const list = await repo.recent("u1");
      expect(list).toHaveLength(20);
      expect(new Set(list.map((a) => a.courseId))).toEqual(new Set(["B1", "I3"]));

      expect((await repo.summaryByCourse("u2")).B1).toMatchObject({ best: 1, passed: false });
    });
```

<Callout type="risk">

- **El contrato es tan bueno como sus tests:** con solo los dos tests originales, un repositorio de PostgreSQL que devolviera también el `id` de la fila habría pasado. Por eso hay un test que exige exactamente los campos del dominio.
- **Las dos bases ordenan distinto en los empates:** si dos intentos tienen la misma fecha, MongoDB y PostgreSQL pueden devolverlos en un orden diferente, y ningún test de este contrato lo vería. Si importa, añade un segundo criterio de orden (`id`) en los dos.
- **`TRUNCATE` en `beforeEach` necesita una base propia para los tests:** nunca apuntes los tests a la base de desarrollo, ni mucho menos a la de producción. Aquí es `academia_ts`, que solo existe para esto.

</Callout>

Y cambias de base de datos sustituyendo solo el repositorio, con los mismos tests como prueba.

</Callout>

## Resumen

- Los datos de la petición van siempre como parámetros (`$1`). Concatenados, una entrada puede leer todo o borrar una tabla.
- `pg` entrega `bigint` y `numeric` como texto, y `date` como medianoche local: corrígelo una vez en `db.ts`.
- Drizzle describe las tablas en TypeScript: de ahí salen los tipos, las consultas y las migraciones, que se generan, se revisan y se aplican.
- Comprueba con `EXPLAIN` el SQL del ORM: el orden de los nulos de un índice de Drizzle no coincidía con su propio `orderBy`.
- En _serverless_, un único _pool_ por instancia, creado fuera del _handler_, y un _pooler_ cuando hay muchas instancias.
- Un repositorio con un contrato sin base de datos se puede cambiar de MongoDB a PostgreSQL con los mismos tests.
