En A3.1 llevaste a PostgreSQL el esquema de Dani Academy, normalizado: cada dato en un solo sitio, con claves ajenas que lo unen. Es el punto de partida correcto, pero no la última palabra. Una app real necesita relaciones de muchos a muchos con datos propios, consultas de panel que agregan miles de filas en cada visita, una forma de borrar que no destruya lo que no debe y, si varias personas comparten la base de datos, que cada una vea solo lo suyo. Cada una de esas decisiones tiene un coste, y en esta sección vas a medirlo sobre el temario real de esta plataforma: cuándo **normalizar**, cuándo **desnormalizar**, y cómo hacerlo sin que los datos se contradigan.

**Lo que tendrás al terminar:** el temario de Dani Academy con sus prerrequisitos como relación N:M y consultas recursivas, un contador mantenido por un _trigger_ (y la razón para quitarlo), vistas materializadas para el panel de administración, borrado lógico con índices parciales, y RLS en las lecturas.

**Requisitos:** las secciones A3.1 (el esquema de la base `academia`, de su ejercicio) y A3.3 (índices). Todos los archivos se ejecutan desde `pg-lab` con `sudo -u postgres psql -X -d academia -f archivo.sql`.

## Paso 1: el temario real, en el esquema de A3.1

`exportar-temario.mjs` saca de esta plataforma los cursos (con sus prerrequisitos, de `courses.json`) y las secciones (de los `.mdx`). Ejecútalo donde tengas el repositorio y deja los dos CSV en `pg-lab/datos/`:

```js
// Archivo: exportar-temario.mjs
// Exporta el temario de Dani Academy: datos/cursos.csv (con sus prerrequisitos) y datos/secciones.csv
// Uso: node exportar-temario.mjs ../dani-academy/src/content
import { mkdirSync, readFileSync, readdirSync, writeFileSync } from "node:fs";
import { join } from "node:path";

const raiz = process.argv[2];
if (!raiz) throw new Error("Falta la ruta de src/content");

const csv = (valor) => `"${String(valor).replaceAll('"', '""')}"`;
const pgArray = (lista) => `{${lista.map((x) => `"${x.replaceAll('"', '\\"')}"`).join(",")}}`;
const nivel = { basic: "basico", intermediate: "intermedio", advanced: "avanzado", final: "proyecto" };

const cursos = JSON.parse(readFileSync(join(raiz, "courses.json"), "utf8"));
const filasCursos = [["id", "titulo", "nivel", "orden", "prerrequisitos"]];
for (const c of cursos) filasCursos.push([c.id, c.title, nivel[c.level], c.order, pgArray(c.prerequisites)]);

const campo = (fm, nombre) => fm.match(new RegExp(`^${nombre}: "?(.*?)"?$`, "m"))?.[1] ?? "";
const filasSecciones = [["id", "curso_id", "titulo", "orden", "minutos"]];
for (const carpeta of readdirSync(join(raiz, "sections")).sort()) {
  for (const archivo of readdirSync(join(raiz, "sections", carpeta)).sort()) {
    if (!archivo.endsWith(".mdx") || archivo.startsWith("_")) continue;
    const fm = readFileSync(join(raiz, "sections", carpeta, archivo), "utf8").split(/^---$/m)[1];
    filasSecciones.push([campo(fm, "sectionId"), campo(fm, "course"), campo(fm, "title"), campo(fm, "order"), campo(fm, "minutes")]);
  }
}

mkdirSync("datos", { recursive: true });
writeFileSync("datos/cursos.csv", filasCursos.map((f) => f.map(csv).join(",")).join("\n") + "\n");
writeFileSync("datos/secciones.csv", filasSecciones.map((f) => f.map(csv).join(",")).join("\n") + "\n");
console.log(`${filasCursos.length - 1} cursos y ${filasSecciones.length - 1} secciones exportados a datos/`);
```

## Paso 2: relaciones N:M, con una tabla intermedia

Cada curso tiene prerrequisitos, y cada curso puede ser prerrequisito de varios: es una relación de muchos a muchos, y además de una tabla **consigo misma**. Hay dos formas de guardarla: un _array_ en la propia fila de cada curso, o una tabla intermedia con una fila por cada "curso requiere curso". `51-prerrequisitos.sql` prueba las dos:

```sql
-- Archivo: 51-prerrequisitos.sql
-- Prerrequisitos de cada curso: primero como array, después como tabla intermedia N:M
CREATE TEMP TABLE temario (id text, titulo text, nivel text, orden integer, prerrequisitos text[]);
\copy temario FROM 'datos/cursos.csv' WITH (FORMAT csv, HEADER true)

-- (para poder repetirlo: deshace lo que crea este archivo)
DROP TABLE IF EXISTS curso_prerrequisitos;
ALTER TABLE cursos DROP COLUMN IF EXISTS prerrequisitos, DROP COLUMN IF EXISTS conocimientos_previos;

-- 1. Un array en la propia tabla: cómodo, y acepta cualquier cosa
ALTER TABLE cursos ADD COLUMN prerrequisitos text[] NOT NULL DEFAULT '{}';
UPDATE cursos c SET prerrequisitos = t.prerrequisitos FROM temario t WHERE t.id = c.id;

SELECT id, prerrequisitos FROM cursos WHERE id IN ('B1', 'B7', 'I3', 'P1') ORDER BY orden;
SELECT string_agg(id, ', ' ORDER BY orden) AS cursos_que_piden_I1 FROM cursos WHERE 'I1' = ANY (prerrequisitos);
UPDATE cursos SET prerrequisitos = array_append(prerrequisitos, 'I9') WHERE id = 'A1'; -- I9 no existe
SELECT id, prerrequisitos FROM cursos WHERE id = 'A1';
UPDATE cursos SET prerrequisitos = array_remove(prerrequisitos, 'I9') WHERE id = 'A1';

-- 2. Una tabla intermedia: cada fila es un "curso requiere curso", con claves ajenas a los dos lados
CREATE TABLE curso_prerrequisitos (
  curso_id    text NOT NULL REFERENCES cursos(id) ON DELETE CASCADE,
  requiere_id text NOT NULL REFERENCES cursos(id),
  PRIMARY KEY (curso_id, requiere_id),
  CHECK (curso_id <> requiere_id)
);
CREATE INDEX ON curso_prerrequisitos (requiere_id); -- para la dirección contraria: "¿quién depende de I1?"

-- Solo entran los prerrequisitos que son cursos; el resto es texto libre y se queda en otra columna
INSERT INTO curso_prerrequisitos (curso_id, requiere_id)
SELECT c.id, p.requiere FROM cursos c CROSS JOIN unnest(c.prerrequisitos) AS p(requiere)
WHERE p.requiere IN (SELECT id FROM cursos);
ALTER TABLE cursos RENAME COLUMN prerrequisitos TO conocimientos_previos;
UPDATE cursos SET conocimientos_previos = ARRAY(
  SELECT x FROM unnest(conocimientos_previos) AS x WHERE x NOT IN (SELECT id FROM cursos));

SELECT (SELECT count(*) FROM curso_prerrequisitos) AS relaciones,
       (SELECT string_agg(id || ': ' || array_to_string(conocimientos_previos, ', '), ' · ' ORDER BY orden)
          FROM cursos WHERE conocimientos_previos <> '{}') AS texto_libre;

-- Ahora la base de datos sí protege la relación
INSERT INTO curso_prerrequisitos VALUES ('A1', 'I9');
INSERT INTO curso_prerrequisitos VALUES ('A1', 'A1');
INSERT INTO curso_prerrequisitos VALUES ('A1', 'I1');
DELETE FROM cursos WHERE id = 'A4'; -- A6 lo necesita: RESTRICT por defecto
BEGIN;
DELETE FROM cursos WHERE id = 'A6'; -- nadie lo necesita: se borra, y sus prerrequisitos con él (CASCADE)
SELECT count(*) AS relaciones_tras_borrar_A6 FROM curso_prerrequisitos;
ROLLBACK;

-- 3. Todos los prerrequisitos de A8, también los indirectos: una consulta recursiva
WITH RECURSIVE cadena AS (
  SELECT requiere_id AS id, 1 AS nivel, ARRAY['A8', requiere_id] AS camino
  FROM curso_prerrequisitos WHERE curso_id = 'A8'
  UNION ALL
  SELECT p.requiere_id, c.nivel + 1, c.camino || p.requiere_id
  FROM cadena c JOIN curso_prerrequisitos p ON p.curso_id = c.id
)
SELECT id, max(nivel) AS distancia, count(*) AS caminos, (array_agg(array_to_string(camino, ' → ') ORDER BY nivel DESC))[1] AS camino_mas_largo
FROM cadena GROUP BY id ORDER BY distancia DESC, id;
```

- **El _array_ acepta cualquier cosa:** `I9` no existe y entra sin protestar, como `"JavaScript"` o `"Todo el temario"`. Para una lista que solo se lee con su fila (las etiquetas de un artículo, los tipos de entreno de un usuario), un _array_ con un índice GIN basta.
- **La tabla intermedia protege la relación:** la clave ajena rechaza `I9`, el `CHECK` rechaza que un curso se requiera a sí mismo, y la clave primaria rechaza repetir un prerrequisito. Ninguna de las tres es posible con un _array_: PostgreSQL no tiene claves ajenas sobre los elementos de un _array_.
- **Y decide qué pasa al borrar:** `A4` no se puede borrar porque `A6` lo necesita (`requiere_id` no tiene `ON DELETE`, así que es `NO ACTION`, que actúa como una restricción). Borrar `A6`, que nadie necesita, se lleva sus dos prerrequisitos (`ON DELETE CASCADE` en `curso_id`): de 35 relaciones a 33.
- **El texto libre no es una relación:** "JavaScript" no es un curso de la plataforma, así que no puede ir en una tabla con clave ajena. Se queda en otra columna, `conocimientos_previos`. Mezclar los dos en el mismo _array_ era el problema de fondo.
- **`WITH RECURSIVE` recorre la relación entera:** la primera parte (los prerrequisitos directos de `A8`) se une con la segunda, que sigue cada prerrequisito hacia atrás hasta que no quedan más. A8 depende de 9 cursos, y B1 está a 4 saltos por el camino más largo, al que se llega por 6 caminos distintos.

La clave primaria `(usuario_id, seccion_id)` responde "qué ha leído este usuario" (_Index Only Scan_, 0,07 ms), pero no "quién ha leído esta sección", que lee las 59 304 lecturas (1,6 ms). Con un índice sobre `seccion_id`, 0,23 ms. Por eso `curso_prerrequisitos` tiene un índice en `requiere_id`.

<Callout type="risk">

- **Un índice de expresión solo se usa con la misma expresión:** el índice único de A3.1 es sobre `lower(email)`. Con `WHERE email = …`, PostgreSQL lee los 2000 usuarios; con `WHERE lower(email) = …`, usa el índice. Es la regla de las funciones de A3.3.
- **Una consulta recursiva sin final no termina nunca:** si alguien crea un ciclo (A requiere B y B requiere A), `WITH RECURSIVE` da vueltas hasta agotar la memoria. Añade `CYCLE id SET hay_ciclo USING camino` (PostgreSQL 14+) o limita la profundidad (`WHERE c.nivel < 20`) en cualquier recursión sobre datos que escriben usuarios.
- **`array || 'texto'` no añade un elemento:** PostgreSQL interpreta `'I9'` como un _array_ literal y responde `malformed array literal`. Para añadir un elemento, `array_append`.

</Callout>

## Paso 3: desnormalizar un contador con un _trigger_

El panel enseña, de cada curso, cuántas secciones lleva leídas el usuario. Normalizado, eso es contar sus lecturas en cada visita. **Desnormalizar** es guardar el número ya contado y mantenerlo al día cada vez que cambian las lecturas. La forma de que no se desincronice es un _trigger_: una función que PostgreSQL ejecuta en cada `INSERT` o `DELETE`, dentro de la misma transacción. `53-contador.sql` lo construye y mide lo que gana y lo que cuesta:

```sql
-- Archivo: 53-contador.sql
-- Desnormalizar: guardar "secciones leídas por curso" en vez de contarlas en cada consulta, con un trigger
DROP TABLE IF EXISTS progreso_cursos;
CREATE TABLE progreso_cursos (
  usuario_id uuid NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
  curso_id   text NOT NULL REFERENCES cursos(id),
  leidas     integer NOT NULL CHECK (leidas >= 0),
  PRIMARY KEY (usuario_id, curso_id)
);
INSERT INTO progreso_cursos
SELECT usuario_id, split_part(seccion_id, '.', 1), count(*) FROM lecturas GROUP BY 1, 2;

-- El trigger: cada lectura que entra o sale suma o resta en el contador, en la misma transacción
CREATE OR REPLACE FUNCTION contar_lectura() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    INSERT INTO progreso_cursos VALUES (NEW.usuario_id, split_part(NEW.seccion_id, '.', 1), 1)
    ON CONFLICT (usuario_id, curso_id) DO UPDATE SET leidas = progreso_cursos.leidas + 1;
    RETURN NEW;
  ELSE
    UPDATE progreso_cursos SET leidas = leidas - 1
    WHERE usuario_id = OLD.usuario_id AND curso_id = split_part(OLD.seccion_id, '.', 1);
    RETURN OLD;
  END IF;
END $$;
CREATE TRIGGER lecturas_contador AFTER INSERT OR DELETE ON lecturas
FOR EACH ROW EXECUTE FUNCTION contar_lectura();

-- ¿Coincide con contar de verdad? Debe dar 0 diferencias
\set comprobar 'SELECT count(*) AS diferencias FROM (SELECT usuario_id, split_part(seccion_id, ''.'', 1) AS curso_id, count(*) AS leidas FROM lecturas GROUP BY 1, 2) AS real FULL JOIN (SELECT * FROM progreso_cursos WHERE leidas > 0) AS guardado USING (usuario_id, curso_id) WHERE real.leidas IS DISTINCT FROM guardado.leidas'
:comprobar;

-- Lo que gana: el panel de un usuario, contando frente a leyendo el contador
\set usuario '(SELECT id FROM usuarios WHERE lower(email) = ''u42@example.com'')'
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF)
SELECT split_part(seccion_id, '.', 1) AS curso_id, count(*) FROM lecturas WHERE usuario_id = :usuario GROUP BY 1;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF)
SELECT curso_id, leidas FROM progreso_cursos WHERE usuario_id = :usuario;

-- Lo que cuesta: 400 usuarios × 50 secciones, con el trigger y sin él (las que ya existían se saltan; se deshacen)
```

<Callout type="risk">

- **Un _trigger_ hace más lenta cada escritura, también las que no ves:** cada `INSERT` en `lecturas` hace ahora otro `INSERT … ON CONFLICT` en `progreso_cursos`. Si desnormalizas, ten una consulta que compruebe la coherencia (como `:comprobar`) y ejecútala de vez en cuando.
- **El _trigger_ no se ve en el código de la aplicación:** quien lea `INSERT INTO lecturas` en TypeScript no sabe que también se escribe otra tabla. Documéntalo junto al esquema, y en las migraciones (A3.4).

</Callout>

## Paso 4: vistas y vistas materializadas

Hay consultas que sí son caras: las del panel de administración, que agregan las lecturas e intentos de **todos** los usuarios. `54-vistas.sql` define las estadísticas de cada curso como vista y como vista materializada:

```sql
-- Archivo: 54-vistas.sql
-- Las estadísticas de cada curso para un panel de administración: vista frente a vista materializada
DROP MATERIALIZED VIEW IF EXISTS estadisticas_cursos_mv;
DROP VIEW IF EXISTS estadisticas_cursos;

-- 1. Una vista: un nombre para una consulta. No guarda nada: se calcula cada vez que se lee
CREATE VIEW estadisticas_cursos AS
SELECT c.id AS curso_id,
       count(DISTINCT l.usuario_id)                                   AS lectores,
       count(l.*)                                                     AS lecturas,
       (SELECT count(*) FROM intentos i WHERE i.curso_id = c.id)      AS intentos,
       (SELECT round(avg(nota), 2) FROM intentos i WHERE i.curso_id = c.id) AS nota_media,
       (SELECT round(100.0 * count(*) FILTER (WHERE nota >= 4) / nullif(count(*), 0), 1)
          FROM intentos i WHERE i.curso_id = c.id)                   AS pct_aprobados
FROM cursos c
LEFT JOIN secciones s ON s.curso_id = c.id
LEFT JOIN lecturas l ON l.seccion_id = s.id
GROUP BY c.id;

-- 2. Una vista materializada: la misma consulta, con el resultado GUARDADO en disco
CREATE MATERIALIZED VIEW estadisticas_cursos_mv AS SELECT * FROM estadisticas_cursos;

\timing on

\timing off
```

- **Una vista materializada guarda el resultado:** leerla cuesta lo que leer 24 filas (0,13 ms), unas 35 veces menos.

Cuándo refrescar depende de cuánto desfase admite quien la lee: un panel de administración puede ir con datos de hace una hora (un `REFRESH` programado, por ejemplo con la extensión `pg_cron` o con una tarea de la app); el progreso que ve cada usuario después de marcar una sección, no.

<Callout type="risk">

- **Una vista materializada desfasada no avisa:** responde con los datos del último `REFRESH`, sin indicar de cuándo son. Si el desfase importa, guarda en otra tabla la hora del último refresco y muéstrala junto al dato.
- **`REFRESH` recalcula entera la consulta:** con millones de filas puede tardar minutos y cargar la base de datos. No lo ejecutes en cada petición ni en cada escritura: entonces tendrías el coste de la consulta en cada escritura, que es peor que no materializar.
- **`CONCURRENTLY` hace más trabajo:** además de calcular el resultado, lo compara fila a fila con el anterior. Con 24 filas tardó lo mismo (32 ms), pero con vistas grandes se nota. Úsalo cuando la vista se lee mientras se refresca; si no, el normal basta.

</Callout>

## Paso 5: borrar en cascada, prohibirlo o marcarlo como borrado

Qué pasa con los datos de alguien cuando se borra es una decisión de diseño, no un detalle. `55-borrado.sql` prueba las tres opciones:

```sql
-- Archivo: 55-borrado.sql
-- Tres formas de "borrar": en cascada, prohibirlo, o marcarlo como borrado
\set ana '(SELECT id FROM usuarios WHERE lower(email) = ''u42@example.com'')'
\set luis '(SELECT id FROM usuarios WHERE lower(email) = ''u43@example.com'')'

-- 1. En cascada (ON DELETE CASCADE, de A3.1): borrar al usuario se lleva sus lecturas e intentos
SELECT (SELECT count(*) FROM lecturas WHERE usuario_id = :ana) AS lecturas_de_u42,
       (SELECT count(*) FROM intentos WHERE usuario_id = :ana) AS intentos_de_u42;
BEGIN;
DELETE FROM usuarios WHERE id = :ana;
SELECT count(*) AS lecturas_tras_borrar FROM lecturas WHERE usuario_id NOT IN (SELECT id FROM usuarios);
ROLLBACK;

-- 2. Prohibido (sin CASCADE, como secciones → cursos): un DELETE mal escrito no se lleva un curso entero
DELETE FROM cursos WHERE id = 'B1';

-- 3. Borrado lógico: una fecha de borrado en lugar de borrar la fila
ALTER TABLE usuarios ADD COLUMN borrado_en timestamptz;
UPDATE usuarios SET borrado_en = now() WHERE id = :luis;

-- La trampa del correo único: la persona no puede volver a registrarse con su correo
INSERT INTO usuarios (nombre, email) VALUES ('Usuario 43 de nuevo', 'u43@example.com');
-- Un índice único PARCIAL: el correo solo tiene que ser único entre los usuarios no borrados
DROP INDEX usuarios_email_unico;
CREATE UNIQUE INDEX usuarios_email_unico ON usuarios (lower(email)) WHERE borrado_en IS NULL;
INSERT INTO usuarios (nombre, email) VALUES ('Usuario 43 de nuevo', 'u43@example.com');
SELECT nombre, borrado_en IS NOT NULL AS borrado FROM usuarios WHERE lower(email) = 'u43@example.com' ORDER BY borrado;

-- La otra trampa: cada consulta tiene que acordarse de filtrar. Una vista con el filtro ayuda
CREATE VIEW usuarios_activos AS SELECT id, nombre, email, creado FROM usuarios WHERE borrado_en IS NULL;
SELECT (SELECT count(*) FROM usuarios) AS en_la_tabla, (SELECT count(*) FROM usuarios_activos) AS activos;
-- ...pero las lecturas del usuario borrado siguen contando en las estadísticas que no pasan por la vista
SELECT count(*) AS lecturas_de_usuarios_borrados FROM lecturas WHERE usuario_id IN (SELECT id FROM usuarios WHERE borrado_en IS NOT NULL);
```

- **Borrado lógico:** `borrado_en` marca la fila en lugar de borrarla, y se puede deshacer. Pero rompe dos cosas que antes funcionaban solas:
  - **El correo único:** la persona no puede volver a registrarse con su correo, porque la fila borrada sigue ahí. El arreglo es un índice único **parcial**, solo para las filas no borradas.
  - **Cada consulta tiene que acordarse de filtrar:** la tabla tiene 2000 filas y una está borrada. La vista `usuarios_activos` ayuda, pero las 34 lecturas del usuario borrado siguen contando en cualquier estadística que no pase por ella.

| `ON DELETE`                            | Al borrar la fila referenciada        | Para qué                                                                   |
| -------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------- |
| `CASCADE`                              | Borra las filas que la referencian    | Datos que no tienen sentido sin su dueño (lecturas, intentos)              |
| `RESTRICT` / `NO ACTION` (por defecto) | Da error si alguna fila la referencia | Datos que no deben desaparecer en cadena (las secciones de un curso)       |
| `SET NULL`                             | Deja la columna a `NULL`              | Conservar la fila sin su referencia (un intento anónimo para estadísticas) |

<Callout type="risk">

- **El índice parcial solo se usa si la consulta repite su condición:** desde este paso, el índice del correo es `WHERE borrado_en IS NULL`, y buscar con `WHERE lower(email) = …` a secas ya no lo usa. Lo verás en el ejercicio: un _Seq Scan_ sobre los 2000 usuarios. Las consultas por correo tienen que añadir `AND borrado_en IS NULL`, o ir por la vista.
- **Un borrado lógico no es un borrado:** el nombre y el correo siguen en la base de datos, en las copias de seguridad y en cualquier exportación. Si la persona pide que borres sus datos, márcala y además anonimiza lo personal (`nombre`, `email`), o bórrala de verdad.
- **`CASCADE` también borra en cadena lo que no esperabas:** si `lecturas` tuviera a su vez tablas con `CASCADE`, un solo `DELETE` de un usuario podría vaciar media base de datos. Antes de añadir un `CASCADE`, mira qué tablas cuelgan de la que borras.

</Callout>

## Paso 6: Row Level Security, la autorización en la base de datos

En esta plataforma, cada servicio filtra por el `userId` de la sesión: `setSectionRead` y `submitQuiz` lo reciben de `locals.user`, nunca de la petición. Si un día alguien escribe una consulta sin ese filtro, se ven los datos de todos. **Row Level Security** (RLS) pone la regla en la propia tabla: una política decide qué filas puede ver y escribir cada conexión, y se aplica a todas las consultas, se acuerde el código o no. `56-rls.sql` la prueba con un rol de aplicación que no es superusuario ni dueño de las tablas:

```sql
-- Archivo: 56-rls.sql
-- Row Level Security: que la base de datos solo deje a cada usuario ver y escribir SUS lecturas
-- El rol con el que se conecta la aplicación: sin superusuario y sin ser dueño de las tablas
DO $$ BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'app_web') THEN CREATE ROLE app_web; END IF;
END $$;
GRANT SELECT, INSERT, DELETE ON lecturas TO app_web;
GRANT SELECT ON usuarios TO app_web;

\set ana 'SELECT id FROM usuarios WHERE lower(email) = ''u42@example.com'''
\set luis 'SELECT id FROM usuarios WHERE lower(email) = ''u44@example.com'''

-- 1. Sin RLS, la aplicación ve todas las lecturas de todos
SET ROLE app_web;
SELECT count(*) AS sin_rls FROM lecturas;
RESET ROLE;

-- 2. La política: cada fila es visible (USING) y escribible (WITH CHECK) solo para su usuario.
--    El usuario lo dice la aplicación en cada transacción, con la variable app.usuario_id
ALTER TABLE lecturas ENABLE ROW LEVEL SECURITY;
DROP POLICY IF EXISTS lecturas_propias ON lecturas;
CREATE POLICY lecturas_propias ON lecturas
  USING (usuario_id = current_setting('app.usuario_id', true)::uuid)
  WITH CHECK (usuario_id = current_setting('app.usuario_id', true)::uuid);

SET ROLE app_web;
-- Sin decir quién es: current_setting(…, true) devuelve NULL y no se ve nada (falla cerrado)
SELECT count(*) AS sin_identificar FROM lecturas;

-- Una petición de u42: SET LOCAL dura solo hasta el final de la transacción
BEGIN;
SELECT set_config('app.usuario_id', (:ana)::text, true) IS NOT NULL AS peticion_de_u42; -- true = LOCAL
SELECT count(*) AS visibles_para_u42, count(*) FILTER (WHERE usuario_id = (:ana)) AS suyas FROM lecturas;
INSERT INTO lecturas (usuario_id, seccion_id) VALUES ((:luis), 'B1.2'); -- una lectura a nombre de otro
ROLLBACK;

-- La siguiente petición sin usuario, en la misma conexión: la variable ya no es NULL, sino ''
SELECT quote_literal(current_setting('app.usuario_id', true)) AS app_usuario_id;
SELECT count(*) AS sin_identificar_otra_vez FROM lecturas;
RESET ROLE;
-- La política corregida: '' cuenta como "sin usuario"
DROP POLICY lecturas_propias ON lecturas;
CREATE POLICY lecturas_propias ON lecturas
  USING (usuario_id = nullif(current_setting('app.usuario_id', true), '')::uuid)
  WITH CHECK (usuario_id = nullif(current_setting('app.usuario_id', true), '')::uuid);
SET ROLE app_web;
SELECT count(*) AS sin_identificar_corregida FROM lecturas;

-- 3. El fallo con un pool: SET (sin LOCAL) se queda en la conexión, y la siguiente petición lo hereda
BEGIN;
SELECT set_config('app.usuario_id', (:ana)::text, false) IS NOT NULL AS peticion_de_u42; -- false = toda la sesión
COMMIT;
-- ...la conexión vuelve al pool, y otra petición, sin usuario, la reutiliza:
SELECT count(*) AS la_siguiente_peticion_ve FROM lecturas;
RESET app.usuario_id;
RESET ROLE;

-- 4. Los superusuarios (y el dueño de la tabla, salvo FORCE ROW LEVEL SECURITY) se saltan la política
SELECT count(*) AS como_postgres FROM lecturas;

-- 5. Con el índice de la clave primaria, la política no hace la consulta más lenta
SET ROLE app_web;
BEGIN;
SELECT set_config('app.usuario_id', (:ana)::text, true) IS NOT NULL AS listo;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF) SELECT seccion_id FROM lecturas;
ROLLBACK;
RESET ROLE;

-- 6. Una vista se ejecuta con los permisos de su DUEÑO (aquí postgres, que se salta RLS)...
DROP VIEW IF EXISTS mis_lecturas;
CREATE VIEW mis_lecturas AS SELECT usuario_id, seccion_id, leida_en FROM lecturas;
GRANT SELECT ON mis_lecturas TO app_web;
SET ROLE app_web;
BEGIN;
SELECT set_config('app.usuario_id', (:ana)::text, true) IS NOT NULL AS peticion_de_u42;
SELECT count(*) AS u42_por_la_vista FROM mis_lecturas;
ROLLBACK;
RESET ROLE;
-- ...salvo con security_invoker (PostgreSQL 15+): entonces usa los permisos de quien la consulta
ALTER VIEW mis_lecturas SET (security_invoker = true);
SET ROLE app_web;
BEGIN;
```

- **La aplicación dice quién es el usuario:** RLS no conoce las sesiones de Better Auth. En cada transacción, la app guarda el id en una variable propia (`app.usuario_id`) con `set_config(…, true)`, que es `SET LOCAL`: dura hasta el `COMMIT` o el `ROLLBACK`.
- **`USING` filtra lo que se ve y `WITH CHECK` lo que se escribe:** `u42` ve sus 38 lecturas de las 60 114, y una lectura a nombre de otro usuario da `new row violates row-level security policy`.
- **Falla cerrado:** sin identificar a nadie, la política compara con `NULL` y no se ve ninguna fila.
- **Pero hay que tratar la cadena vacía:** cuando la variable ya se usó en la conexión, al terminar la transacción no vuelve a `NULL`, sino a `''`, y `''::uuid` da `invalid input syntax for type uuid`. Cada petición sin usuario fallaría. `nullif(…, '')` lo convierte en `NULL`.
- **Sin coste:** la política se convierte en una condición más, y la clave primaria la resuelve (_Index Only Scan_, 0,014 ms).

<Callout type="risk">

- **`SET` sin `LOCAL` se queda en la conexión:** tras la petición de `u42`, la siguiente que reutiliza la misma conexión del _pool_ (A3.4) ve sus 38 lecturas sin haber dicho quién es. Con un _pool_ o un _pooler_, usa siempre `set_config(…, true)` dentro de una transacción, nunca `SET` de sesión.
- **Las vistas se saltan RLS por defecto:** una vista se ejecuta con los permisos de su dueño. Aquí el dueño es `postgres`, que se salta las políticas, y a través de la vista `u42` vio las 60 114 lecturas. Crea las vistas sobre tablas con RLS con `security_invoker = true` (PostgreSQL 15+), que usa los permisos de quien consulta. Las vistas materializadas no tienen esa opción (lo verás en el ejercicio).
- **El dueño de la tabla y los superusuarios no pasan por la política:** si la aplicación se conecta como `postgres` o como dueña de la tabla, RLS no hace nada. Para que también se aplique al dueño, `ALTER TABLE … FORCE ROW LEVEL SECURITY`. Y la aplicación, siempre con su propio rol (A3.4).

</Callout>

- **Etiquetas como tabla N:M, no como _array_:** el nombre de una etiqueta cambia una vez en `etiquetas` y lo ven todos los cursos, una etiqueta mal escrita no entra (clave ajena) y borrar una etiqueta se lleva sus asignaciones (`CASCADE` en los dos lados: sin curso o sin etiqueta, la asignación no tiene sentido).
- **"Todas las etiquetas" es una división relacional:** se filtran las asignaciones de las etiquetas pedidas, se agrupan por curso y se quedan los cursos que tienen tantas como etiquetas había en la lista (`HAVING count(*) = 2`). Solo A8 tiene React y Astro a la vez.
- **El panel de un usuario no compensa materializarlo:** 0,38 ms en vivo frente a 0,33 ms desde la vista, casi todo en buscar al usuario por correo (el _Seq Scan_ del índice parcial del Paso 5). A cambio, la vista estaría desfasada: quien marca una sección como leída no lo vería hasta el siguiente `REFRESH`, que cuesta 251 ms.
- **El panel de administración, sí:** el progreso medio por etiqueta, sobre todos los usuarios, cuesta 167 ms en vivo y 0,18 ms desde la vista materializada, unas 900 veces menos, y nadie necesita ese dato al segundo. Refrescarla después de `panel_progreso` cuesta 21 ms.

<Callout type="risk">

- **Una vista materializada no aplica RLS:** guarda el resultado calculado por su dueño, con los datos de todos. Si la aplicación pudiera leer `panel_progreso`, `u42` vería a 1999 usuarios. Nunca des `SELECT` sobre una vista materializada con datos de usuarios al rol de la aplicación. Si la app la necesita, consúltala desde una función que filtre, o materializa solo datos agregados sin usuarios, como `progreso_por_etiqueta`.
- **Una vista materializada que lee de otra hereda su desfase:** `progreso_por_etiqueta` lee de `panel_progreso`, así que hay que refrescarlas en orden. Al revés, la segunda calcularía sobre los datos viejos de la primera.
- **La división relacional depende de que no haya duplicados:** `HAVING count(*) = 2` funciona porque la clave primaria impide asignar dos veces la misma etiqueta a un curso. Sin esa clave, una etiqueta repetida contaría dos veces.

</Callout>

<Callout type="mastery">

Decides cómo guardar cada relación (un _array_ si solo se lee con su fila, una tabla intermedia si necesita integridad o se consulta al revés) y si desnormalizar, según cómo se lee y se escribe cada dato: mides lo que gana y lo que cuesta un _trigger_ o una vista materializada antes de quedártelo. Eliges entre cascada, restricción y borrado lógico, y proteges los datos de cada usuario con RLS sin dejar que se escapen por una vista.

</Callout>

## Resumen

- Una relación N:M con integridad va en una tabla intermedia, con una clave primaria compuesta y un índice para cada dirección. Un _array_ basta para listas que no necesitan claves ajenas.
- `WITH RECURSIVE` recorre relaciones de una tabla consigo misma, como los prerrequisitos.
- Desnormalizar con un _trigger_ mantiene un dato coherente, pero encarece cada escritura y `TRUNCATE` lo desincroniza: solo compensa si la cuenta es cara y se lee mucho.
- Una vista no guarda nada; una vista materializada guarda el resultado, se lee muy rápido y se queda desfasada hasta el `REFRESH`.
- El borrado lógico necesita índices únicos parciales y que cada consulta filtre; `CASCADE` borra lo que depende de la fila.
- RLS filtra cada consulta por usuario con una variable de transacción (`SET LOCAL`), pero las vistas y las vistas materializadas pueden saltársela.
