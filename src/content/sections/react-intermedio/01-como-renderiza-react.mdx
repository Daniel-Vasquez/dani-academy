"Cuando cambia el estado, React vuelve a pintar" se queda corto: ¿se pintan los hijos?, ¿toca el DOM cada vez?, ¿por qué `memo` no evita un render?, ¿por qué todo sale dos veces en desarrollo? Aquí mides en el navegador qué provoca cada render y usas el _Profiler_ para saber qué se renderizó y por qué.

**Requisitos:** el proyecto `react-lab` de B6, con la hidratación de B6.3 y las islas compartidas de B6.7. Todo I2 se hace ahí:

```bash
cd react-lab
mkdir -p src/components/render
```

## Paso 1: render y commit no son lo mismo

**Qué es:** **render** es llamar a tu componente para obtener el JSX nuevo: solo JavaScript, calcula qué **debería** verse. **_Commit_** es comparar con el anterior, aplicar al DOM **solo las diferencias** y ejecutar los efectos. Calcular es barato; tocar el DOM, caro.

**Cómo se usa:** crea `src/components/render/RenderBasico.tsx`.

```tsx
// Archivo: src/components/render/RenderBasico.tsx
import { useEffect, useState } from "react";

function Hijo() {
  console.log("[render] Hijo");
  return <p id="hijo">Soy el hijo: no uso el contador</p>;
}

export function Padre() {
  const [n, setN] = useState(0);
  console.log(`[render] Padre (n = ${n})`);

  useEffect(() => {
    console.log(`[commit] Padre: el DOM ya muestra n = ${n}`);
  });

  return (
    <div className="tarjeta">
      <button id="sumar" onClick={() => setN(n + 1)}>
        Pulsado {n} veces
      </button>
      <button id="mismo" onClick={() => setN(n)}>
        Guardar el mismo valor
      </button>
      <Hijo />
    </div>
  );
}
```

Y `src/pages/render.astro`:

```astro
---
// Archivo: src/pages/render.astro
import Base from "../layouts/Base.astro";
import { Padre } from "../components/render/RenderBasico";
---

<Base titulo="Cómo renderiza React">
  <h1>Render y commit</h1>
  <Padre client:load />
</Base>
```

Con `npm run dev`, abre `http://localhost:4321/render` con la consola y pulsa los botones. Medido en Chrome, con un `MutationObserver` sobre el DOM del hijo:

```text
— al cargar (hidratación):
  [render] Padre (n = 0)
  [render] Hijo
  [commit] Padre: el DOM ya muestra n = 0
— Pulsar +1:
  [render] Padre (n = 1)
  [render] Hijo
  [commit] Padre: el DOM ya muestra n = 1
— Pulsar +1:
  [render] Padre (n = 2)
  [render] Hijo
  [commit] Padre: el DOM ya muestra n = 2
— Guardar el mismo valor:
  [render] Padre (n = 2)
— Guardar el mismo valor:
  (nada)
cambios en el DOM del hijo: 0
```

- **Si un componente se renderiza, se renderizan sus hijos:** `Hijo` no usa `n` y se ejecuta igual.
- **Renderizar no es tocar el DOM:** `Hijo` se renderizó 3 veces y su DOM cambió **0**. Casi siempre, un render "de más" no es un problema.
- **Guardar el mismo valor casi no renderiza:** la primera vez, React llama a `Padre` una vez más (sin hijos ni _commit_) para confirmarlo; la segunda, ni eso. Compara con `Object.is`: solo primitivos o **el mismo** objeto.

<Callout type="risk">

- **El cuerpo de un componente debe ser puro:** React puede llamarlo cuando quiera. Peticiones, `localStorage.setItem` o variables de fuera, en eventos o `useEffect`.
- **Un `console.log` en el cuerpo es para medir,** no para producción. Para medir en serio, el _Profiler_ (Paso 5).
- **"Se renderiza mucho" no es un bug por sí mismo:** comprueba antes si algo es lento (Paso 5 e I2.6).

</Callout>

## Paso 2: qué dispara un re-render

**Qué es:** un componente se vuelve a renderizar por **cuatro motivos**, y solo por ellos.

**Cómo se usa:**

| Disparador                                       | Ejemplo                                                   |
| ------------------------------------------------ | --------------------------------------------------------- |
| Su **estado** cambia                             | `setN(n + 1)`                                             |
| Su **padre** se renderiza                        | `Hijo` en el Paso 1                                       |
| Un **contexto** que lee cambia                   | `useContext(TemaCtx)` y el `Provider` recibe otro `value` |
| Un **store externo** al que está suscrito cambia | `useStore($vasos)` de nanostores (B6.7)                   |

- **Las _props_ no están, a propósito:** un componente no se renderiza "porque cambien sus props", sino porque su padre se renderizó. `memo` (Paso 3) permite saltarse el render si no cambiaron.

<Callout type="risk">

- **`setN(n + 1)` no cambia `n` "ya":** sigue con el valor antiguo hasta el próximo render (B6.3), y React agrupa las actualizaciones de un evento en un render.
- **Un efecto que actualiza el estado provoca otro render:** con dependencias mal puestas, un bucle. Lo calculable, calcúlalo en el render.

</Callout>

## Paso 3: identidad de objetos y funciones

**Qué es:** `memo(Componente)` se salta el render si las props son **iguales**, comparadas con `Object.is`: por **identidad**, no por contenido. Un objeto o una función escritos en el componente son **nuevos en cada render**.

**Cómo se usa:** crea `src/components/render/Identidad.tsx`.

```tsx
// Archivo: src/components/render/Identidad.tsx
import { createContext, memo, useCallback, useContext, useEffect, useMemo, useState } from "react";

interface TarjetaProps {
  etiqueta: string;
  estilo: { color: string };
  onElegir: () => void;
}

// memo: React se salta el render si TODAS las props son iguales (Object.is) que la vez anterior
const Tarjeta = memo(function Tarjeta({ etiqueta, estilo, onElegir }: TarjetaProps) {
  console.log(`[render] Tarjeta ${etiqueta}`);
  return (
    <button style={estilo} onClick={onElegir}>
      {etiqueta}
    </button>
  );
});

const TemaCtx = createContext("claro");

// También con memo: el contexto se salta memo y lo re-renderiza cuando cambia el valor
const LectorTema = memo(function LectorTema() {
  const tema = useContext(TemaCtx);
  console.log(`[render] LectorTema (${tema})`);
  return <p>Tema: {tema}</p>;
});

const ESTILO_FIJO = { color: "teal" }; // fuera del componente: el mismo objeto siempre

export function Identidad() {
  const [n, setN] = useState(0);
  const [tema, setTema] = useState("claro");

  // Se crean de nuevo en CADA render: mismo contenido, otra identidad
  const estiloNuevo = { color: "teal" };
  const elegirNuevo = () => console.log("elegido");

  // Se conservan entre renders mientras sus dependencias no cambien
  const estiloMemo = useMemo(() => ({ color: "teal" }), []);
  const elegirMemo = useCallback(() => console.log("elegido"), []);

  useEffect(() => {
    console.log("[efecto] depende de estiloNuevo");
  }, [estiloNuevo]);

  console.log(`[render] Identidad (n = ${n})`);
  return (
    <TemaCtx.Provider value={tema}>
      <div className="tarjeta">
        <button id="otro-render" onClick={() => setN((x) => x + 1)}>
          Re-renderizar el padre ({n})
        </button>
        <button id="cambiar-tema" onClick={() => setTema((t) => (t === "claro" ? "oscuro" : "claro"))}>
          Cambiar tema
        </button>
        <Tarjeta etiqueta="A (objetos nuevos)" estilo={estiloNuevo} onElegir={elegirNuevo} />
        <Tarjeta etiqueta="B (useMemo/useCallback)" estilo={estiloMemo} onElegir={elegirMemo} />
        <Tarjeta etiqueta="C (constante de módulo)" estilo={ESTILO_FIJO} onElegir={elegirMemo} />
        <LectorTema />
      </div>
    </TemaCtx.Provider>
  );
}
```

Y `src/pages/identidad.astro`:

```astro
---

import { Identidad } from "../components/render/Identidad";
---

<Base titulo="Identidad entre renders">
  <h1>Identidad de objetos y funciones</h1>

</Base>
```

En `/identidad`:

```text
— al cargar:
  [render] Identidad (n = 0)
  [render] Tarjeta A (objetos nuevos)
  [render] Tarjeta B (useMemo/useCallback)
  [render] Tarjeta C (constante de módulo)
  [render] LectorTema (claro)
  [efecto] depende de estiloNuevo
— Re-renderizar el padre:
  [render] Identidad (n = 1)
  [render] Tarjeta A (objetos nuevos)
  [efecto] depende de estiloNuevo
— Cambiar tema:
  [render] Identidad (n = 1)
  [render] Tarjeta A (objetos nuevos)
  [render] LectorTema (oscuro)
  [efecto] depende de estiloNuevo
```

- **Tarjeta A tiene `memo` y no sirve:** `{ color: "teal" }` y `() => …` son nuevos cada vez. **Tarjeta B** recibe `useMemo` y `useCallback`, que **conservan la identidad** mientras no cambien sus dependencias. **Tarjeta C** usa una constante **fuera** del componente: la solución más simple si no depende de nada.
- **El efecto con `[estiloNuevo]` se ejecuta en cada render,** por lo mismo: una causa habitual de efectos sin fin.
- **`LectorTema` tiene `memo` y se renderiza igual:** **el contexto se salta `memo`**.

<Callout type="risk">

- **El `value` de un `Provider` es una prop:** `value={{ usuario, salir }}` es nuevo en cada render y renderiza a **todos** los consumidores. Memorízalo con `useMemo` (I2.4).
- **`useMemo` y `useCallback` no son gratis:** úsalos con motivo medible (una prop de un `memo`, una dependencia de efecto), no "por si acaso" (I2.6).
- **Una dependencia que falta da datos viejos:** `useCallback(() => guardar(n), [])` usa siempre el primer `n`. No silencies `react-hooks/exhaustive-deps`.

</Callout>

## Paso 4: `StrictMode`, y lo que hace en una isla de Astro

**Qué es:** una herramienta de **desarrollo** que **renderiza dos veces** (para destapar cuerpos impuros) y **monta, desmonta y vuelve a montar los efectos** (para destapar efectos sin limpieza).

**Cómo se usa:** crea `src/components/render/Estricto.tsx`.

```tsx
// Archivo: src/components/render/Estricto.tsx
import { StrictMode, useEffect, useState } from "react";

function Reloj() {
  const [segundos, setSegundos] = useState(0);
  console.log("[render] Reloj");

  useEffect(() => {
    console.log("[efecto] Reloj: arranco el intervalo");
    const id = setInterval(() => setSegundos((s) => s + 1), 1000);
    return () => {
      console.log("[limpieza] Reloj: paro el intervalo");
      clearInterval(id);
    };
  }, []);

  return <p id="segundos">Llevas {segundos} s en la página</p>;
}

// StrictMode solo actúa en desarrollo: en producción no hace nada
export function RelojEstricto() {
  return (
    <StrictMode>
      <Reloj />
    </StrictMode>
  );
}
```

Y `src/pages/estricto.astro`:

```astro
---
// Archivo: src/pages/estricto.astro
import Base from "../layouts/Base.astro";
import { RelojEstricto } from "../components/render/Estricto";
---

<Base titulo="StrictMode">
  <h1>StrictMode</h1>
  <RelojEstricto client:load />
</Base>
```

Abre `/estricto` en desarrollo. Para comparar con producción hace falta un adaptador (la ruta de API de B6.6 da `NoAdapterInstalled` sin él):

```bash
npx astro add node --yes
npm run build
PORT=4322 node dist/server/entry.mjs
```

Abre `http://localhost:4322/estricto`:

```text
Desarrollo (npm run dev):
  [render] Reloj
  [render] Reloj
  [efecto] Reloj: arranco el intervalo
  [render] Reloj
  [render] Reloj
  [render] Reloj
  [render] Reloj
  [render] Reloj
  [render] Reloj
  → Llevas 3 s en la página
Producción (npm run build):
  [render] Reloj
  [efecto] Reloj: arranco el intervalo
  [render] Reloj
  [render] Reloj
  [render] Reloj
  → Llevas 3 s en la página
```

- **En desarrollo, cada render ocurre dos veces;** en producción, una. El contador avanza igual: el segundo render se descarta.
- **El doble efecto no aparece:** con React 19, solo ocurre si `StrictMode` envuelve **la raíz**. En una isla, la raíz la crea la integración de Astro (sin opción para `StrictMode`); en Vite o Next.js sí está en la raíz, y de ahí que los tutoriales digan "los efectos se ejecutan dos veces". Medido con React 19.3:

| Dónde está `<StrictMode>`                           | Render | Efectos                    |
| --------------------------------------------------- | ------ | -------------------------- |
| En la raíz (`createRoot(el).render(<StrictMode>…)`) | doble  | efecto → limpieza → efecto |
| Anidado dentro del árbol, como en una isla          | doble  | uno solo                   |

<Callout type="risk">

- **No "arregles" el doble efecto con `let yaMontado = false`:** esconde el bug que `StrictMode` señala. Si falla al ejecutarse dos veces, le falta la limpieza (B6.6).
- **En las islas, la limpieza la pruebas tú:** un efecto sin limpieza no se nota hasta el desmontaje (con `<ClientRouter />`, al navegar).
- **Con el puerto 4321 ocupado, `node dist/server/entry.mjs` se cierra sin avisar:** por eso `PORT=4322`. Sin `Server listening on…`, el puerto está ocupado.

</Callout>

## Paso 5: medir con React DevTools y con `<Profiler>`

**Qué es:** dos herramientas mejores que los `console.log`. **React DevTools** (extensión "React Developer Tools") añade **⚛️ Components** (árbol, props, estado y hooks) y **⚛️ Profiler** (cada _commit_, qué se renderizó y cuánto tardó). **`<Profiler>`** hace lo mismo desde el código: llama a `onRender` en cada _commit_ con el identificador, la fase (`mount` o `update`) y el tiempo.

**Cómo se usa:** en el engranaje de Components, **_Highlight updates when components render_** recuadra cada componente que se renderiza. En el Profiler, graba, interactúa y para; con **_Record why each component rendered while profiling_**, dice el motivo ("Hook 1 changed", "The parent component rendered"…). `<Profiler>` lo usarás en el ejercicio.

<Callout type="risk">

- **Los tiempos, en producción:** en desarrollo hay comprobaciones extra y `StrictMode`. El _Profiler_ en desarrollo dice **qué**; el _build_, **cuánto**.
- **`<Profiler>` tiene un coste** y en producción está desactivado salvo con un _build_ especial: investiga y quítalo.
- **Cada isla es una raíz independiente en DevTools:** son aplicaciones separadas (I2.4).

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Instala React DevTools, activa _Highlight updates when components render_ y abre `/estado` (el panel de hidratación de B6.3) y `/compartido` (las islas de B6.7).
2. **Antes de pulsar nada**, escribe tu predicción: ¿qué componentes se renderizan al pulsar "+" en el panel de hidratación, al cambiar el objetivo, al elegir el **mismo** objetivo y al pulsar "+ 1 vaso" en la página de islas compartidas?
3. Comprueba la predicción con los recuadros de DevTools.
4. Para dejarlo medido, envuelve esos componentes en `<Profiler>` en `src/components/render/Medidos.tsx` y móntalos todos en `src/pages/ejercicio-i21.astro`.

</Callout>

Solución. `src/components/render/Medidos.tsx`:

```tsx
// Archivo: src/components/render/Medidos.tsx
// Los componentes de B6 envueltos en <Profiler>: cada commit escribe qué se renderizó y cuánto tardó
import { Profiler, type ProfilerOnRenderCallback, type ReactNode } from "react";
import { Hidratacion } from "../estado/Hidratacion";
import { BotonVaso } from "../islas/BotonVaso";
import { MarcadorAgua } from "../islas/MarcadorAgua";

const registrar: ProfilerOnRenderCallback = (id, fase, duracion) => {
  console.log(`[profiler] ${id}: ${fase} (${duracion.toFixed(1)} ms)`);
};

function Medir({ id, children }: { id: string; children: ReactNode }) {
  return (
    <Profiler id={id} onRender={registrar}>
      {children}
    </Profiler>
  );
}

export const HidratacionMedida = () => (
  <Medir id="Hidratacion">
    <Hidratacion />
  </Medir>
);

export const MarcadorMedido = () => (
  <Medir id="MarcadorAgua">
    <MarcadorAgua />
  </Medir>
);

export const BotonMedido = () => (
  <Medir id="BotonVaso">
    <BotonVaso />
  </Medir>
);
```

`src/pages/ejercicio-i21.astro`:

```astro
---

---

<Base titulo="Ejercicio I2.1">
  <h1>¿Qué se re-renderiza?</h1>
  <HidratacionMedida client:load />
  <header class="tarjeta"><MarcadorMedido client:load /></header>
  <p>Este párrafo es HTML estático.</p>
  <BotonMedido client:load />
</Base>
```

Medido en Chrome (los milisegundos varían):

```text
— al cargar:
  [profiler] MarcadorAgua: mount (… ms)
  [profiler] BotonVaso: mount (… ms)
  [profiler] Hidratacion: mount (… ms)
— Hidratación: pulsar +:
  [profiler] Hidratacion: update (… ms)
— Hidratación: cambiar el objetivo:
  [profiler] Hidratacion: update (… ms)
— Hidratación: elegir el mismo objetivo:
  [profiler] Hidratacion: update (… ms)
— Pulsar + 1 vaso (islas compartidas):
  [profiler] MarcadorAgua: update (… ms)
```

- **Cada isla se monta por separado,** en el orden en que carga su código. **El panel de hidratación es un solo componente:** cualquier cambio lo renderiza entero, bien para una tarjeta, no para una página.
- **El mismo objetivo aún da un `update`:** el render de confirmación del Paso 1. Repítelo y desaparece.
- **"+ 1 vaso" solo renderiza `MarcadorAgua`:** `BotonVaso` no lee el _store_ y no se suscribe. `<Medir>` va **dentro** de cada componente de React: en el `.astro`, sus hijos llegarían como HTML estático.

<Callout type="risk">

- **Predecir antes de medir es lo importante:** si fallaste, busca en el Paso 2 qué disparador explica cada render.
- **No dejes `<Profiler>` en la app:** cuesta y ensucia la consola. Es de laboratorio.
- **Un recuadro de _Highlight updates_ es "se ejecutó",** no "cambió el DOM" (Paso 1).

</Callout>

<Callout type="mastery">

Predices qué componentes se volverán a renderizar ante un cambio: sabes que un componente se renderiza por su estado, por su padre, por un contexto o por un _store_ externo; distingues render (calcular) de _commit_ (tocar el DOM); sabes por qué un objeto o una función nuevos anulan `memo` y disparan efectos; y compruebas tus predicciones con React DevTools y `<Profiler>`.

</Callout>

## Resumen

- Render calcula el JSX; _commit_ aplica solo las diferencias y ejecuta efectos.
- Cuatro disparadores: estado, padre, contexto y _store_ externo.
- `Object.is` compara por identidad: `useMemo`, `useCallback` o una constante de módulo la conservan.
- `StrictMode` duplica renders en desarrollo; el doble efecto solo con `StrictMode` en la raíz, que en una isla no está.
- React DevTools y `<Profiler>` dicen qué se renderizó y por qué: mide antes de optimizar.
