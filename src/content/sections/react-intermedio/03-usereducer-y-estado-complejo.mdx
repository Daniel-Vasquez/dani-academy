Un cuestionario parece sencillo: la pregunta actual, las respuestas, si ya se envió y cuántos aciertos hubo. Con `useState` son cuatro variables, y cada botón tiene que actualizar **la combinación correcta** de ellas. El problema llega el día que una función olvida una: la pantalla muestra un resultado con todas las respuestas vacías, o un botón que "no hace nada". Son **estados contradictorios**, combinaciones de valores que nunca deberían existir a la vez. `useReducer` resuelve esto concentrando todas las transiciones en una sola función pura, y una **unión discriminada** (B1.6) hace que esas combinaciones imposibles ni siquiera se puedan escribir. En esta sección vas a provocar el bug, vas a hacerlo imposible y vas a probar la lógica sin abrir el navegador.

**Lo que tendrás al terminar:** un _reducer_ de cuestionario puro y probado con `node --test`, y un componente de cuestionario de 5 preguntas con navegación, respuestas y una pantalla de resultado con explicaciones.

**Requisitos:** las secciones I2.1 e I2.2 y uniones discriminadas (B1.6). Crea las carpetas:

```tsx
// Archivo: src/components/cuestionario/ConUseState.tsx
// ❌ Cuatro useState que deben cambiar a la vez… y un día uno se olvida
import { useState } from "react";
import { PREGUNTAS_DEMO as PREGUNTAS } from "../../lib/preguntas";

export function CuestionarioConUseState() {
  const [paso, setPaso] = useState(0);
  const [respuestas, setRespuestas] = useState<(number | null)[]>(PREGUNTAS.map(() => null));
  const [enviado, setEnviado] = useState(false);
  const [aciertos, setAciertos] = useState(0);

  function elegir(opcion: number) {
    setRespuestas(respuestas.map((r, i) => (i === paso ? opcion : r)));
  }

  function enviar() {
    setAciertos(respuestas.filter((r, i) => r === PREGUNTAS[i]!.correcta).length);
    setEnviado(true);
  }

  function repetir() {
    setPaso(0);
    setRespuestas(PREGUNTAS.map(() => null));
    // ← olvido: setEnviado(false) y setAciertos(0)

  if (enviado) {
    return (
      <div className="tarjeta" id="usestate">
        <p className="resultado">
          Resultado: {aciertos}/{PREGUNTAS.length} · respuestas: {JSON.stringify(respuestas)}
        </p>
        <button onClick={repetir}>Repetir</button>
      </div>
    );
  }

  const pregunta = PREGUNTAS[paso]!;
  return (
    <div className="tarjeta" id="usestate">
      <p>
        {paso + 1}/{PREGUNTAS.length} · {pregunta.enunciado}
      </p>
      {pregunta.opciones.map((o, i) => (
        <button key={o} aria-pressed={respuestas[paso] === i} onClick={() => elegir(i)}>
          {o}
        </button>
      ))}
      {paso < PREGUNTAS.length - 1 ? (
        <button onClick={() => setPaso(paso + 1)}>Siguiente</button>
      ) : (
        <button onClick={enviar}>Enviar</button>
      )}
    </div>
  );
}
```

```text

```

"Repetir" vació las respuestas y volvió al paso 0, pero **olvidó** `enviado` y `aciertos`. El resultado es una pantalla imposible: un 2/3 sin ninguna respuesta, y un botón que, a ojos del usuario, no hace nada. Nada en el código impide este estado: las cuatro variables son independientes, y TypeScript acepta cualquier combinación de sus valores (`enviado: true` con `respuestas: [null, null, null]` es perfectamente válido para él).

<Callout type="risk">

- **Cada `useState` nuevo multiplica las combinaciones:** con 4 variables, cada función que cambia el flujo tiene que acordarse de las 4. Con 6 (añade `cargando` y `error` para enviar a un servidor), los olvidos son casi seguros.
- **Los estados "derivados" no van en el estado:** `aciertos` se puede calcular a partir de `respuestas` y las preguntas. Guardarlo aparte es una de las causas del bug: dos fuentes de verdad que se desincronizan.

</Callout>

## Paso 2: un reducer y estados como unión discriminada

Un **_reducer_** es una función pura con esta forma: **(estado actual, acción) → estado nuevo**. Las **acciones** describen _qué ha pasado_ ("el usuario eligió la opción 2", "pulsó enviar"), y el _reducer_ decide _cómo cambia el estado_. Todas las transiciones viven en un solo sitio. Crea `src/lib/cuestionario.ts`:

```ts
// Archivo: src/lib/cuestionario.ts
// El flujo del cuestionario como una función pura: (estado, acción) → estado nuevo
import type { Pregunta } from "./preguntas.ts";

// Unión discriminada (B1.6): cada fase tiene SOLO los datos que tienen sentido en ella
export type EstadoCuestionario =
  | { fase: "respondiendo"; paso: number; respuestas: (number | null)[] }
  | { fase: "resultado"; respuestas: number[]; aciertos: number };

export type AccionCuestionario =
  | { type: "elegir"; opcion: number }
  | { type: "ir"; paso: number }
  | { type: "enviar"; preguntas: Pregunta[] }
  | { type: "repetir"; total: number };

export const estadoInicial = (total: number): EstadoCuestionario => ({
  fase: "respondiendo",
  paso: 0,
  respuestas: Array<number | null>(total).fill(null),
});

export function cuestionarioReducer(
  estado: EstadoCuestionario,
  accion: AccionCuestionario,
): EstadoCuestionario {
  switch (accion.type) {
    case "elegir":
      if (estado.fase !== "respondiendo") return estado;
      return {
        ...estado,
        respuestas: estado.respuestas.map((r, i) => (i === estado.paso ? accion.opcion : r)),
      };

    case "ir":
      if (estado.fase !== "respondiendo") return estado;
      return { ...estado, paso: Math.max(0, Math.min(accion.paso, estado.respuestas.length - 1)) };

    case "enviar": {
      if (estado.fase !== "respondiendo") return estado;
      const { respuestas } = estado;
      if (respuestas.some((r) => r === null)) return estado; // no se envía con huecos
      const completas = respuestas as number[];
      const aciertos = completas.filter((r, i) => r === accion.preguntas[i]?.correcta).length;
      return { fase: "resultado", respuestas: completas, aciertos };
    }

    case "repetir":
      return estadoInicial(accion.total); // UNA transición: imposible olvidar una variable
  }
}
```

Las dos ideas clave:

- **El estado es una unión discriminada por `fase`:** en `"respondiendo"` existen `paso` y unas respuestas que pueden ser `null`; en `"resultado"` existen `aciertos` y unas respuestas completas. No hay forma de escribir "resultado con respuestas vacías": el tipo no lo permite. Es la idea de "hacer imposibles los estados imposibles".
- **Las acciones también son una unión discriminada, por `type`:** dentro de cada `case`, TypeScript sabe qué datos trae la acción (`accion.opcion`, `accion.preguntas`…).

`"repetir"` es ahora **una sola transición**, `estadoInicial(total)`, y no hay variables que olvidar. Y cada `case` comprueba la fase: en la pantalla de resultado, `"elegir"` simplemente no hace nada.

Ahora el componente, que solo pinta el estado y envía acciones con `dispatch`. `src/components/cuestionario/ConReducer.tsx`:

```tsx
// Archivo: src/components/cuestionario/ConReducer.tsx
// ✅ El mismo cuestionario: el componente solo pinta el estado y envía acciones
import { useReducer } from "react";
import { cuestionarioReducer, estadoInicial } from "../../lib/cuestionario";
import { PREGUNTAS_DEMO as PREGUNTAS } from "../../lib/preguntas";

export function CuestionarioConReducer() {
  const [estado, dispatch] = useReducer(cuestionarioReducer, PREGUNTAS.length, estadoInicial);

  if (estado.fase === "resultado") {
    return (
      <div className="tarjeta" id="reducer">
        <p className="resultado">
          Resultado: {estado.aciertos}/{PREGUNTAS.length} · respuestas: {JSON.stringify(estado.respuestas)}
        </p>
        <button onClick={() => dispatch({ type: "repetir", total: PREGUNTAS.length })}>Repetir</button>
      </div>
    );
  }

  const { paso, respuestas } = estado; // aquí TypeScript sabe que la fase es "respondiendo"
  const pregunta = PREGUNTAS[paso]!;
  return (
    <div className="tarjeta" id="reducer">
      <p>
        {paso + 1}/{PREGUNTAS.length} · {pregunta.enunciado}
      </p>
      {pregunta.opciones.map((o, i) => (
        <button key={o} aria-pressed={respuestas[paso] === i} onClick={() => dispatch({ type: "elegir", opcion: i })}>
          {o}
        </button>
      ))}
      {paso < PREGUNTAS.length - 1 ? (
        <button onClick={() => dispatch({ type: "ir", paso: paso + 1 })}>Siguiente</button>
      ) : (
        <button onClick={() => dispatch({ type: "enviar", preguntas: PREGUNTAS })}>Enviar</button>
      )}
    </div>
  );
}
```

`useReducer(cuestionarioReducer, PREGUNTAS.length, estadoInicial)` usa la forma de tres argumentos: React llama a `estadoInicial(PREGUNTAS.length)` una sola vez para crear el estado de partida. Sustituye la página para comparar los dos:

**El compilador también vigila las acciones.** Añade una acción nueva a la unión, `| { type: "salir" }`, sin tratarla en el `switch`, y ejecuta `npx astro check`:

```text
src/lib/cuestionario.ts:26:4 - error ts(2366): Function lacks ending return statement and return type does not include 'undefined'.
```

Como el _reducer_ declara que devuelve `EstadoCuestionario` y el `switch` no cubre `"salir"`, TypeScript sabe que hay un camino que no devuelve nada. Cada acción nueva te obliga a decidir qué hace. Quita la acción añadida.

<Callout type="risk">

- **Un reducer nunca modifica el estado que recibe:** `estado.respuestas[paso] = opcion; return estado;` devuelve **el mismo objeto**, React lo compara con `Object.is` (I2.1), ve que no ha cambiado y **no vuelve a renderizar**. Crea siempre objetos y arrays nuevos (`{ ...estado, … }`, `.map`).
- **Nada de efectos dentro del reducer:** ni `fetch`, ni `localStorage`, ni `Math.random()` ni `Date.now()`. En desarrollo, `StrictMode` puede llamar al reducer dos veces, y una petición dentro se enviaría dos veces. Lo que no es puro va en el manejador del evento, antes o después del `dispatch`.
- **No añadas `default:` "por si acaso":** un `default: return estado;` silencia el error de las acciones sin tratar. Deja que el compilador te avise.

</Callout>

## Paso 3: probar el reducer sin montar React

Como el _reducer_ es una función pura, se prueba como cualquier función: le das un estado y una acción y compruebas lo que devuelve. No hace falta navegador, ni React, ni librerías de pruebas; basta con el _test runner_ que trae Node. Crea `src/lib/cuestionario.test.ts`:

```ts
// Archivo: src/lib/cuestionario.test.ts
// Uso: node --test src/lib/cuestionario.test.ts (Node 23.6+ ejecuta TypeScript directamente)
import assert from "node:assert/strict";
import { test } from "node:test";
import { cuestionarioReducer as reducer, estadoInicial } from "./cuestionario.ts";
import { PREGUNTAS_DEMO as PREGUNTAS } from "./preguntas.ts";

/** Responde las primeras preguntas de un cuestionario de `total` preguntas */
const responder = (total: number, opciones: number[]) =>
  opciones.reduce(
    (s, opcion, paso) => reducer(reducer(s, { type: "ir", paso }), { type: "elegir", opcion }),
    estadoInicial(total),
  );

test("no se puede enviar con preguntas sin responder", () => {
  const s = responder(3, [1, 1]); // falta la tercera
  assert.equal(reducer(s, { type: "enviar", preguntas: PREGUNTAS }), s);
});

test("enviar calcula los aciertos y pasa a resultado", () => {
  const s = reducer(responder(3, [1, 1, 0]), { type: "enviar", preguntas: PREGUNTAS });
  assert.deepEqual(s, { fase: "resultado", respuestas: [1, 1, 0], aciertos: 2 });
});

test("en la pantalla de resultado no se puede cambiar una respuesta", () => {
  const s = reducer(responder(3, [1, 1, 1]), { type: "enviar", preguntas: PREGUNTAS });
  assert.equal(reducer(s, { type: "elegir", opcion: 0 }), s);
});

test("repetir vuelve al estado inicial completo", () => {
  const s = reducer(responder(3, [1, 1, 0]), { type: "enviar", preguntas: PREGUNTAS });
  assert.deepEqual(reducer(s, { type: "repetir", total: 3 }), estadoInicial(3));
});

test("ir no se sale de los límites", () => {
  const s = reducer(estadoInicial(3), { type: "ir", paso: 99 });
  assert.deepEqual(s, { fase: "respondiendo", paso: 2, respuestas: [null, null, null] });
});
```

<Callout type="risk">

- **Prueba transiciones, no implementaciones:** "enviar con huecos no cambia nada" seguirá siendo cierto aunque reescribas el reducer; "el reducer llama a `.some()`" no. Las buenas pruebas describen comportamiento.
- **`node --test` no entiende los alias de Astro:** si el reducer importara `@/lib/…`, Node no sabría resolverlo. Mantén los _reducers_ con _imports_ relativos (o usa Vitest, que lee la configuración de Vite, como en la plataforma).
- **El tipo no sustituye a la prueba:** la unión discriminada impide "resultado sin respuestas", pero no impide que calcules mal los aciertos. Para eso está el segundo test.

</Callout>

```tsx
// Archivo: src/components/cuestionario/Cuestionario.tsx
import { useReducer } from "react";
import { cuestionarioReducer, estadoInicial } from "../../lib/cuestionario";
import type { PreguntaConExplicacion } from "../../lib/preguntas-react";

const LETRAS = ["A", "B", "C", "D"];

export function Cuestionario({ preguntas }: { preguntas: PreguntaConExplicacion[] }) {
  const [estado, dispatch] = useReducer(cuestionarioReducer, preguntas.length, estadoInicial);
  const total = preguntas.length;

  // ── Pantalla de resultado ──────────────────────────────────────────
  if (estado.fase === "resultado") {
    return (
      <section className="tarjeta" id="cuestionario" aria-live="polite">
        <h2>
          {estado.aciertos >= Math.ceil(total * 0.8) ? "¡Aprobado!" : "Aún no"} · {estado.aciertos}/{total}
        </h2>
        <ol>
          {preguntas.map((p, i) => {
            const elegida = estado.respuestas[i]!;
            const bien = elegida === p.correcta;
            return (
              <li key={p.enunciado} className={bien ? "bien" : "mal"}>
                {bien ? "✓" : "✗"} {p.enunciado}
                {!bien && (
                  <p>
                    Elegiste «{p.opciones[elegida]}»; la correcta es «{p.opciones[p.correcta]}».
                  </p>
                )}
                <p>{p.explicacion}</p>
              </li>
            );
          })}
        </ol>
        <button onClick={() => dispatch({ type: "repetir", total })}>Repetir</button>
      </section>
    );
  }

  // ── Respondiendo ───────────────────────────────────────────────────
  const { paso, respuestas } = estado;
  const pregunta = preguntas[paso]!;
  const pendientes = respuestas.filter((r) => r === null).length;

  return (
    <section className="tarjeta" id="cuestionario">
      <nav aria-label="Preguntas">
        {preguntas.map((p, i) => (
          <button
            key={p.enunciado}
            aria-current={i === paso ? "step" : undefined}
            aria-label={`Pregunta ${i + 1}${respuestas[i] === null ? ", sin responder" : ", respondida"}`}
            onClick={() => dispatch({ type: "ir", paso: i })}
          >
            {i + 1}
            {respuestas[i] !== null && "•"}
          </button>
        ))}
      </nav>

      <fieldset>
        <legend>
          Pregunta {paso + 1} de {total}: {pregunta.enunciado}
        </legend>
        {pregunta.opciones.map((opcion, i) => (
          <label key={opcion} style={{ display: "block" }}>
            <input
              type="radio"
              name={`pregunta-${paso}`}
              checked={respuestas[paso] === i}
              onChange={() => dispatch({ type: "elegir", opcion: i })}
            />{" "}
            {LETRAS[i]}. {opcion}
          </label>
        ))}
      </fieldset>

      <p>
        <button disabled={paso === 0} onClick={() => dispatch({ type: "ir", paso: paso - 1 })}>
          ← Anterior
        </button>{" "}
        {paso < total - 1 ? (
          <button onClick={() => dispatch({ type: "ir", paso: paso + 1 })}>Siguiente →</button>
        ) : (
          <button disabled={pendientes > 0} onClick={() => dispatch({ type: "enviar", preguntas })}>
            Enviar respuestas
          </button>
        )}
      </p>
      {paso === total - 1 && pendientes > 0 && (
        <p className="aviso">Te faltan {pendientes} pregunta(s) por responder.</p>
      )}
    </section>
  );
}
```

## Resumen

- Varios `useState` que cambian juntos acaban en estados contradictorios cuando una función olvida uno.
- `useReducer(reducer, arg, init)`: un _reducer_ puro `(estado, acción) → estado` concentra todas las transiciones; los componentes solo hacen `dispatch`.
- Estado y acciones como uniones discriminadas: las combinaciones imposibles no se pueden escribir y el compilador avisa de las acciones sin tratar.
- Nunca modifiques el estado recibido ni hagas efectos en el _reducer_; nada de `default` que silencie errores.
- Un _reducer_ se prueba con `node --test` (o Vitest) en milisegundos, sin navegador.
