## Paso 1: `memo`, `useMemo` y `useCallback`, cuándo sirven

**Qué es:** tres herramientas que evitan trabajo repetido entre renders.

| Herramienta                  | Qué memoriza                                        | Sirve cuando…                                                                            |
| ---------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `memo(Componente)`           | El render del componente, si sus _props_ no cambian | El componente es caro y su padre se renderiza a menudo por motivos que no le afectan     |
| `useMemo(() => valor, deps)` | Un valor calculado                                  | El cálculo es caro, o el valor es una _prop_ de un `memo` o una dependencia de un efecto |
| `useCallback(fn, deps)`      | Una función                                         | La función es una _prop_ de un `memo` o una dependencia de un efecto                     |

**Cómo se usa:** el uso por identidad ya lo mediste en I2.1; ahora, un cálculo caro. Crea `src/components/rendimiento/Estadisticas.tsx`.

```tsx
// Archivo: src/components/rendimiento/Estadisticas.tsx
// Un cálculo caro y un estado que no tiene nada que ver con él: con y sin useMemo
import { useMemo, useState, type ReactNode } from "react";

const ENTRENOS = Array.from({ length: 200_000 }, (_, i) => ({ minutos: 20 + (i % 70), km: (i % 13) + 0.5 }));

function calcularResumen(entrenos: typeof ENTRENOS) {
  let minutos = 0;
  let km = 0;
  for (const e of entrenos) {
    minutos += e.minutos;
    km += Math.sqrt(e.km * e.km); // trabajo de más, a propósito
  }
  return { minutos, km: Math.round(km) };
}

function Tarjeta({ id, resumen, children }: { id: string; resumen: { minutos: number; km: number }; children: ReactNode }) {
  return (
    <div className="tarjeta" id={id}>
      <p>
        {resumen.minutos} min · {resumen.km} km
      </p>
      {children}
    </div>
  );
}

export function EstadisticasSinMemo() {
  const [abierto, setAbierto] = useState(false); // estado que NO afecta al cálculo
  const inicio = performance.now();
  const resumen = calcularResumen(ENTRENOS); // se recalcula en CADA render
  console.log(`[medida] sin useMemo: ${(performance.now() - inicio).toFixed(1)} ms`);
  return (
    <Tarjeta id="sin-memo" resumen={resumen}>
      <button onClick={() => setAbierto(!abierto)}>{abierto ? "Ocultar" : "Ver"} detalles</button>
    </Tarjeta>
  );
}

export function EstadisticasConMemo() {
  const [abierto, setAbierto] = useState(false);
  const inicio = performance.now();
  const resumen = useMemo(() => calcularResumen(ENTRENOS), []); // solo la primera vez
  console.log(`[medida] con useMemo: ${(performance.now() - inicio).toFixed(1)} ms`);
  return (
    <Tarjeta id="con-memo" resumen={resumen}>
      <button onClick={() => setAbierto(!abierto)}>{abierto ? "Ocultar" : "Ver"} detalles</button>
    </Tarjeta>
  );
}
```

Pulsa tres veces "Ver detalles" en cada tarjeta, un estado ajeno al cálculo. En desarrollo:

```text
al hidratar: sin useMemo: 1.7 ms · con useMemo: 1.7 ms
3 clics en "Ver detalles" (sin-memo): sin useMemo: 2.8 ms · sin useMemo: 4.7 ms · sin useMemo: 1.4 ms
3 clics en "Ver detalles" (con-memo): con useMemo: 0.1 ms · con useMemo: 0.0 ms · con useMemo: 0.0 ms
```

- **`useMemo` funciona:** tras el primer render, 0 ms. Pero recorrer **200 000 entrenos** cuesta 1,4–4,7 ms, y un fotograma dura 16: sin `useMemo`, nadie notaría nada.
- **La regla práctica de React:** memorizar compensa si un cálculo tarda más de **1 ms** de forma constante. Se sabe midiendo (`console.time`, el _Profiler_ de I2.1).

<Callout type="risk">

- **La memorización cuesta:** guarda el valor y compara dependencias en cada render. Envolver un `a + b` es más lento y menos legible.
- **`memo` sin _props_ estables no hace nada** (I2.1): estabilízalas o quita el `memo`.
- **Dependencias incompletas dan valores viejos:** `useMemo(() => calcular(datos), [])` devuelve siempre el primero. Que lo revise `react-hooks/exhaustive-deps`.

</Callout>

## Paso 2: el React Compiler y su estado actual en Astro

**Qué es:** el **React Compiler** analiza tus componentes al compilar y añade la memorización exacta, sin escribirla. Su versión 1.0 es estable y React lo recomienda en proyectos nuevos. En Astro 7 se activa con una opción de la integración.

**Cómo se usa:**

```js
// @ts-check
import { defineConfig } from 'astro/config';

import react from '@astrojs/react';

import node from '@astrojs/node';

// https://astro.build/config
export default defineConfig({
  // compiler: true activa el React Compiler (necesita babel-plugin-react-compiler)
  integrations: [react({ compiler: true })],

  adapter: node({
    mode: 'standalone'
  })
});
```

Solo con `compiler: true`, al arrancar:

```text
React Compiler requires the optional `oxc-transform-react` package. Install it in your project before enabling `react({ compiler: true })`.
```

- **Aquí lo ejecuta `oxc-transform-react`,** no el `babel-plugin-react-compiler` de los tutoriales. Al instalarlo, npm encuentra un conflicto (fragmento):


- **`@astrojs/react` 7.0.1 pide `^0.145.0` y su _plugin_ de Vite, `^0.152.0`:** en versiones `0.x` no hay ninguna que valga para los dos. Para **probarlo**, no para producción:

```bash

```

Repitiendo `/identidad` (I2.1) y `/rendimiento` **sin tocar los componentes** (solo lo que cambia):

```text

  [render] Identidad (n = 1)
```

- **La Tarjeta A ya no se renderiza** con el padre, el efecto no se repite y `EstadisticasSinMemo` deja de recalcular: el compilador memorizó todo lo que hacías a mano.
- **En Astro 7.3 con `@astrojs/react` 7.0.1 solo se instala forzando dependencias:** experiméntalo en una rama y deshazlo (quita `compiler: true` y `npm uninstall oxc-transform-react --legacy-peer-deps`).

<Callout type="risk">

- **`--legacy-peer-deps` instala combinaciones no probadas juntas:** en producción, espera una combinación oficial.
- **Tras activarlo o desactivarlo, Vite puede quedar incoherente:** en el laboratorio, `_jsxDEV is not a function`. `npm run dev -- --force` regenera la caché.
- **No arregla un componente lento:** evita lo **repetido**, no el primer render de 10 000 filas (paginación, virtualización o `useTransition`, I2.5). Y asume componentes puros y estado sin mutar (I2.1, I2.2).

</Callout>

## Paso 3: patrones para organizar componentes

**Qué es:** **_render props_** (el componente pone la lógica y una función decide cómo se pinta), **_lifting state up_** (el estado compartido sube al padre común) y **componentes compuestos** (varios que solo tienen sentido juntos, con un contexto interno). Y **`lazy`** con **`Suspense`**, que cargan una parte bajo demanda y muestran un _fallback_ mientras llega.

**Cómo se usa:** crea `src/components/rendimiento/Patrones.tsx`.

```tsx
// Archivo: src/components/rendimiento/Patrones.tsx
import { useState, type ReactNode } from "react";

// ── Render props: el componente gestiona la lógica (filtrar) y QUIEN LO USA decide cómo pintar
interface ListaFiltrableProps<T> {
  elementos: T[];
  texto: (elemento: T) => string; // por qué campo se filtra
  renderElemento: (elemento: T) => ReactNode; // cómo se pinta cada uno
}

export function ListaFiltrable<T>({ elementos, texto, renderElemento }: ListaFiltrableProps<T>) {
  const [filtro, setFiltro] = useState("");
  const visibles = elementos.filter((e) => texto(e).toLowerCase().includes(filtro.toLowerCase()));
  return (
    <div>
      <input aria-label="Filtrar" value={filtro} onChange={(e) => setFiltro(e.target.value)} />
      <ul>{visibles.map((e) => <li key={texto(e)}>{renderElemento(e)}</li>)}</ul>
    </div>
  );
}

// ── Lifting state up: dos componentes hermanos que necesitan el mismo dato
function SelectorSemana({ semana, onCambiar }: { semana: number; onCambiar: (s: number) => void }) {
  return (
    <p>
      <button onClick={() => onCambiar(semana - 1)}>←</button> Semana {semana}{" "}
      <button onClick={() => onCambiar(semana + 1)}>→</button>
    </p>
  );
}

function ResumenSemana({ semana }: { semana: number }) {
  return <p id="resumen-semana">Resumen de la semana {semana}: {(semana * 37) % 300} min</p>;
}

export function PanelSemanal() {
  const [semana, setSemana] = useState(41); // el estado vive en el padre común
  return (
    <div className="tarjeta">
      <SelectorSemana semana={semana} onCambiar={setSemana} />
      <ResumenSemana semana={semana} />
    </div>
  );
}

const ENTRENOS = [
  { nombre: "Rodaje suave", minutos: 40 },
  { nombre: "Series 6x400", minutos: 35 },
  { nombre: "Fuerza tren inferior", minutos: 50 },
];

export function DemoPatrones() {
  return (
    <>
      <div className="tarjeta" id="render-props">
        <ListaFiltrable
          elementos={ENTRENOS}
          texto={(e) => e.nombre}
          renderElemento={(e) => (
            <>
              <strong>{e.nombre}</strong> · {e.minutos} min
            </>
          )}
        />
      </div>
      <PanelSemanal />
    </>
  );
}
```

- **`ListaFiltrable<T>`** (I1.1) lleva el filtro y recibe `renderElemento`. Hoy, casi siempre lo resuelve un _custom hook_ (I2.2), salvo cuando lo variable es JSX.
- **`PanelSemanal`** sube la semana que comparten `SelectorSemana` y `ResumenSemana`: lo primero que probar antes que contexto o un _store_ (I2.4). Los componentes compuestos son el ejercicio.

```tsx
const GraficoPesado = lazy(() => import("./GraficoPesado"));

        </Suspense>
      )}
    </div>
  );
}
```

<Callout type="risk">

- **En Astro, primero las directivas:** `client:visible` o `client:idle` (B6.7) retrasan toda la isla; `lazy` es para una parte **dentro** de ella (una pestaña, un modal).
- **`lazy` necesita `export default`:** con uno con nombre, `lazy(() => import("./X").then((m) => ({ default: m.X })))`. Y se declara **fuera** del componente, o cada render crea uno nuevo y pierde el estado.
- **Un _fallback_ de otro tamaño hace saltar la página (CLS):** dale el alto del contenido final.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Implementa el componente compuesto `Tabs` en `src/components/tabs/Tabs.tsx`, con `<Tabs defaultValue>`, `<Tabs.List label>`, `<Tabs.Trigger value>` y `<Tabs.Panel value>`.
2. Debe ser accesible: roles `tablist`, `tab` y `tabpanel`, `aria-selected`, `aria-controls` y `aria-labelledby`, y que cada `<Tabs>` tenga identificadores únicos.
3. Teclado: Tab entra en la pestaña activa (solo en ella), las flechas izquierda y derecha cambian de pestaña (dando la vuelta), Inicio y Fin van a la primera y la última, y un segundo Tab lleva al panel.
4. Úsalo en un panel de actividad con tres pestañas (Progreso, Exámenes, Sesiones) y compruébalo con el teclado y con axe.

</Callout>

Solución. `src/components/tabs/Tabs.tsx`:

```tsx
// Archivo: src/components/tabs/Tabs.tsx
// Componente compuesto accesible: <Tabs> + <Tabs.List> + <Tabs.Trigger> + <Tabs.Panel>
import { createContext, useContext, useId, useState, type KeyboardEvent, type ReactNode } from "react";

interface TabsContexto {
  valor: string;
  seleccionar: (valor: string) => void;
  idBase: string;
}

const TabsCtx = createContext<TabsContexto | null>(null);

function useTabs(componente: string): TabsContexto {
  const ctx = useContext(TabsCtx);
  if (!ctx) throw new Error(`<${componente}> debe usarse dentro de <Tabs>`);
  return ctx;
}

// Los id se derivan del valor: así el botón y su panel se referencian entre sí
const idTab = (base: string, valor: string) => `${base}-tab-${valor}`;
const idPanel = (base: string, valor: string) => `${base}-panel-${valor}`;

function Tabs({ defaultValue, children }: { defaultValue: string; children: ReactNode }) {
  const [valor, seleccionar] = useState(defaultValue);
  const idBase = useId(); // único aunque haya varios <Tabs> en la página
  return (
    <TabsCtx.Provider value={{ valor, seleccionar, idBase }}>
      <div className="tabs">{children}</div>
    </TabsCtx.Provider>
  );
}

function List({ label, children }: { label: string; children: ReactNode }) {
  const { seleccionar } = useTabs("Tabs.List");

  // Flechas, Inicio y Fin mueven el foco entre pestañas y la activan (activación automática)
  function onKeyDown(e: KeyboardEvent<HTMLDivElement>) {
    const tabs = [...e.currentTarget.querySelectorAll<HTMLButtonElement>('[role="tab"]')];
    const actual = tabs.indexOf(document.activeElement as HTMLButtonElement);
    if (actual === -1) return;
    const destino = {
      ArrowRight: (actual + 1) % tabs.length,
      ArrowLeft: (actual - 1 + tabs.length) % tabs.length,
      Home: 0,
      End: tabs.length - 1,
    }[e.key];
    if (destino === undefined) return;
    e.preventDefault(); // Inicio/Fin no deben desplazar la página
    const tab = tabs[destino]!;
    tab.focus();
    seleccionar(tab.dataset.valor!);
  }

  return (
    <div role="tablist" aria-label={label} onKeyDown={onKeyDown}>
      {children}
    </div>
  );
}

function Trigger({ value, children }: { value: string; children: ReactNode }) {
  const { valor, seleccionar, idBase } = useTabs("Tabs.Trigger");
  const activa = valor === value;
  return (
    <button
      type="button"
      role="tab"
      id={idTab(idBase, value)}
      data-valor={value}
      aria-selected={activa}
      aria-controls={idPanel(idBase, value)}
      tabIndex={activa ? 0 : -1} // "roving tabindex": solo la pestaña activa está en el orden de Tab
      onClick={() => seleccionar(value)}
    >
      {children}
    </button>
  );
}

function Panel({ value, children }: { value: string; children: ReactNode }) {
  const { valor, idBase } = useTabs("Tabs.Panel");
  return (
    <div
      role="tabpanel"
      id={idPanel(idBase, value)}
      aria-labelledby={idTab(idBase, value)}
      hidden={valor !== value}
      tabIndex={0} // el panel recibe el foco con Tab desde la pestaña
    >
      {children}
    </div>
  );
}

// Los subcomponentes cuelgan del principal: <Tabs.List>, <Tabs.Trigger>…
Tabs.List = List;
Tabs.Trigger = Trigger;
Tabs.Panel = Panel;

export { Tabs };
```

- **Contexto interno y un hook que lo exige:** `useTabs("Tabs.Trigger")` dice qué subcomponente se usó fuera de `<Tabs>` (I2.4). `Tabs.List = List` da la sintaxis `<Tabs.List>`.
- **_Roving tabindex_:** solo la activa tiene `tabIndex={0}`, así Tab entra una vez y sale al panel; dentro, flechas. Mover el foco también selecciona: conviene con paneles instantáneos (si cargaran datos, solo con Intro o espacio).
- **`useId()`** evita choques entre dos `<Tabs>` y coincide entre servidor e hidratación. **`hidden`** saca los paneles inactivos de la vista, del tabulado y de la accesibilidad, pero los mantiene montados con su estado.

<Callout type="risk">

- **Unas pestañas no son navegación:** si cada una necesita URL e historial, enlaces y páginas, no `role="tab"`.
- **Un rol ARIA promete un teclado:** `role="tab"` sin flechas es peor que nada, porque el lector anuncia "pestaña 1 de 3". Implementa el patrón completo de la WAI-ARIA.
- **Con paneles pesados, `hidden` no basta:** todos se renderizan. Renderiza solo el activo (`{activa && …}`), perdiendo su estado, o cárgalo con `lazy`.

</Callout>

<Callout type="mastery">

Optimizas solo después de medir con el _Profiler_: sabes que la mayoría de los cálculos cuestan menos de un fotograma, usas `memo`, `useMemo` y `useCallback` solo cuando la medición o la identidad lo justifican, conoces el React Compiler y su estado real en Astro, organizas componentes con _render props_, _lifting state up_ y componentes compuestos accesibles, y difieres con `lazy` lo que no se necesita al cargar.

</Callout>

## Resumen

- `useMemo` ahorró un cálculo de 1,4–4,7 ms: memoriza lo que pasa de ~1 ms o necesita identidad.
- El React Compiler memoriza solo, pero en Astro 7.3 con `@astrojs/react` 7.0.1 exige forzar dependencias.
- _Render props_ separan lógica y presentación; _lifting state up_ sube el estado al padre común.
- `lazy` + `Suspense` piden una parte de la isla solo al necesitarla, con un _fallback_ mientras tanto.
- Componente compuesto accesible: contexto, roles ARIA, _roving tabindex_, flechas y `useId`.
