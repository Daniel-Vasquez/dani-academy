En Astro, el HTML de una página se genera **en el _build_** (estático, SSG: un archivo igual para todos, servido desde una CDN) o **en cada petición** (SSR: tu código se ejecuta en un servidor, con datos de ese momento y de ese usuario). Aquí compilas de las dos formas, mides la diferencia y combinas ambas con las _server islands_.

**Requisitos:** la app `entrenos-app` de I1.6, con su `.env` apuntando a tu MongoDB. Todo I3 se hace sobre ella.

## Paso 1: el build sin adaptador

**Qué es:** un **adaptador** traduce tu app a la plataforma donde se ejecutará su código de servidor: Node, Vercel, Netlify… `npm run dev` siempre tiene un servidor (el de Vite); producción necesita saber cuál.

**Cómo se usa:** la ruta de API de I1.6 tiene `prerender = false`. Compila:

```bash
npm run build
```

```text
[NoAdapterInstalled] Cannot use server-rendered pages without an adapter. Please install and configure the appropriate server adapter for your final deployment.
```

| Adaptador         | Para                                    | Resultado del build                                     |
| ----------------- | --------------------------------------- | ------------------------------------------------------- |
| `@astrojs/node`   | Tu propio servidor, Docker, un VPS (A4) | Un servidor Node: `node dist/server/entry.mjs`          |
| `@astrojs/vercel` | Vercel (esta plataforma)                | Funciones _serverless_ y archivos para la CDN de Vercel |
| (ninguno)         | Una web 100 % estática                  | Solo archivos HTML, CSS y JS                            |

Añade el de Node, que se ejecuta en local:

```bash
npx astro add node --yes
```

`astro.config.mjs` queda así:

```js
// @ts-check
import { defineConfig, envField } from "astro/config";
import react from "@astrojs/react";

import node from "@astrojs/node";

export default defineConfig({
  integrations: [react()],

  env: {
    schema: {
      MONGODB_URI: envField.string({ context: "server", access: "secret", startsWith: "mongodb" }),
      MONGODB_DB: envField.string({ context: "server", access: "secret", default: "entrenos_lab" }),
    },
  },

  adapter: node({
    mode: "standalone",
  }),
});
```

<Callout type="risk">

- **Desarrollo no es producción:** que funcione en `npm run dev` no garantiza que compile. `npm run build` siempre antes de desplegar (esta plataforma lo hace en su CI).
- **El adaptador decide el entorno:** `@astrojs/node` en `standalone` es un servidor de larga duración; en Vercel, cada función puede arrancar en frío y vivir poco. Lo que "funciona en Node" puede comportarse distinto en _serverless_ (I3.4).

</Callout>

## Paso 2: estático por defecto, servidor donde haga falta

**Qué es:** con `output: "static"` (por defecto), **todo se genera en el _build_** salvo lo marcado con `export const prerender = false`. Con `output: "server"`, al revés: todo en cada petición salvo `prerender = true`.

**Cómo se usa:** un layout común, `src/layouts/Base.astro`:

```astro
---
// Archivo: src/layouts/Base.astro
interface Props {
  titulo: string;
}
const { titulo } = Astro.props;
---

<html lang="es">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width" />
    <title>{titulo} · Mis entrenos</title>
    <style is:global>
      body { font-family: system-ui, sans-serif; max-width: 32rem; margin: 2rem auto; padding: 0 1rem; }
      nav { display: flex; gap: 1rem; margin-bottom: 1rem; }
    </style>
  </head>
  <body>
    <nav><a href="/">Entrenos</a><a href="/estadisticas">Estadísticas</a><a href="/acerca">Acerca de</a></nav>
    <slot />
  </body>
</html>
```

Una página que no depende de nada, `src/pages/acerca.astro`:

```astro
---
// Archivo: src/pages/acerca.astro
// Contenido que no depende de quién lo pide ni de cuándo: se genera una vez, en el build
import Base from "../layouts/Base.astro";
const generada = new Date().toISOString();
---

<Base titulo="Acerca de">
  <h1>Acerca de Mis entrenos</h1>
  <p>Una app para registrar entrenos de fuerza, running y movilidad.</p>
  <p id="generada">HTML generado: {generada}</p>
</Base>
```

Y una con datos del momento, `src/pages/estadisticas.astro`:

```astro
---
// Archivo: src/pages/estadisticas.astro
// Depende de los datos de ese momento: se renderiza en el servidor en CADA petición
import Base from "../layouts/Base.astro";
import { db } from "../lib/mongo";

export const prerender = false;

const [fila] = await db
  .collection("entrenos")
  .aggregate<{ total: number; minutos: number }>([
    { $match: { userId: "u_demo" } },
    { $group: { _id: null, total: { $sum: 1 }, minutos: { $sum: "$minutos" } } },
  ])
  .toArray();
const generada = new Date().toISOString();
---

<Base titulo="Estadísticas">
  <h1>Estadísticas</h1>
  <p id="totales">{fila?.total ?? 0} entrenos · {fila?.minutos ?? 0} minutos</p>
  <p id="generada">HTML generado: {generada}</p>
</Base>
```

```bash
npm run build
```

```text
[build] output: "static"
  ├─ /acerca/index.html (+4ms)
  ├─ /index.html (+6ms)
[build] Complete!
```

- **`index` y `acerca` son HTML** en `dist/client/`; `estadisticas` y la API, código de servidor.

Arranca producción y pide cada página dos veces, creando un entreno entre medias:

```bash
PORT=4322 node dist/server/entry.mjs
```

```text
petición 1 /acerca        → generada: HTML generado: 2026-10-16T02:51:40.250Z
petición 1 /estadisticas  → totales: 0 entrenos · 0 minutos generada: HTML generado: 2026-10-16T02:51:50.094Z
petición 2 /acerca        → generada: HTML generado: 2026-10-16T02:51:40.250Z
petición 2 /estadisticas  → totales: 0 entrenos · 0 minutos generada: HTML generado: 2026-10-16T02:51:51.140Z
POST entreno → 201
tras crear un entreno → 1 entrenos · 30 minutos
```

- **`/acerca` devuelve siempre la hora del _build_:** el mismo archivo para todos, con `Last-Modified` y `ETag` para la caché.
- **`/estadisticas` cambia en cada petición** y refleja el entreno nuevo **al instante**.

Con `output: "server"` en `astro.config.mjs`:

```text
— output: server, sin prerender:
[build] output: "server"
[build] Complete!
— output: server, acerca con prerender = true:
[build] output: "server"
  ├─ /acerca/index.html (+4ms)
[build] Complete!
```

- **Sin `prerender = true`, el _build_ no genera HTML.** Esta plataforma usa `output: "server"` porque casi todo depende del usuario; con mayoría de páginas públicas, mejor el valor por defecto.

| Pregunta                                     | Estático (en el build)                           | Servidor (en cada petición) |
| -------------------------------------------- | ------------------------------------------------ | --------------------------- |
| ¿Depende de quién la pide? (sesión, cookies) | No                                               | Sí                          |
| ¿Depende de datos que cambian a menudo?      | No (o se acepta que se actualice al redesplegar) | Sí                          |
| ¿Puede fallar por la base de datos?          | No: ya está generada                             | Sí                          |
| ¿Dónde se sirve en Vercel?                   | CDN, en todo el mundo                            | Una función, en una región  |

<Callout type="risk">

- **Una página estática con datos de usuario es un fallo de seguridad:** se genera en el _build_ sin usuario (o con el de quien compiló) y se sirve igual a todos. Cookies y sesión, siempre en servidor.
- **Los datos de una página estática se congelan en el _build_** hasta el siguiente despliegue.
- **`prerender = true` en una ruta dinámica** necesita `getStaticPaths`; con miles de elementos, el _build_ tarda minutos. Ahí, servidor y caché HTTP.

</Callout>

## Paso 3: el ciclo de vida de una petición en el servidor

**Qué es:** el recorrido de una petición a `/estadisticas` en producción.

**Cómo se usa:**

1. **El adaptador recibe la petición** y busca un archivo estático con esa ruta; si existe, lo envía y tu código ni se ejecuta.
2. **El _router_ de Astro** encuentra `src/pages/estadisticas.astro`.
3. **Se ejecuta el _middleware_** (I3.4): sesión, rutas protegidas, cabeceras.
4. **Se ejecuta el _frontmatter_,** con la consulta a MongoDB.
5. **Los componentes se renderizan y se envían en _streaming_.**
6. **El navegador pinta** y luego hidrata las islas `client:*`.

- **Los pasos 3 a 5 se repiten en cada petición:** la página es tan rápida como su consulta más lenta.

<Callout type="risk">

- **Un `await` lento en el _frontmatter_ retrasa toda la página:** nada llega al navegador hasta que se resuelve. Lo lento y secundario, a una _server island_ (Paso 4).
- **Una excepción en el _frontmatter_ es un 500** que tumba la página: captura lo esperable y deja el resto al manejador de errores (I1.5).

</Callout>

## Paso 4: server islands, una página estática con un trozo dinámico

**Qué es:** una página estática en la que un componente marcado con **`server:defer`** se pide al servidor **aparte**, después de cargar, mientras se ve su `fallback`.

**Cómo se usa:** crea `src/components/UltimoEntreno.astro`.

```astro
---
// Archivo: src/components/UltimoEntreno.astro
// Componente de servidor: consulta MongoDB cada vez que se pide
import { db } from "../lib/mongo";

const ultimo = await db
  .collection<{ tipo: string; minutos: number; fecha: Date }>("entrenos")
  .find({ userId: "u_demo" })
  .sort({ fecha: -1, creado: -1 })
  .limit(1)
  .next();
---

<p id="ultimo">
  {
    ultimo
      ? `Último entreno: ${ultimo.tipo}, ${ultimo.minutos} min (${ultimo.fecha.toISOString().slice(0, 10)})`
      : "Todavía no has registrado ningún entreno"
  }
</p>
```

Y sustituye `src/pages/index.astro`:

```astro
---
// Archivo: src/pages/index.astro
// La página se genera en el build; solo el último entreno se pide al servidor en cada visita
import Base from "../layouts/Base.astro";
import Entrenos from "../components/Entrenos";
import UltimoEntreno from "../components/UltimoEntreno.astro";
---

<Base titulo="Mis entrenos">
  <h1>Mis entrenos</h1>
  <UltimoEntreno server:defer>
    <p slot="fallback" id="ultimo-cargando">Cargando tu último entreno…</p>
  </UltimoEntreno>
  <Entrenos client:load />
</Base>
```

Compila:

```text
[build] output: "static"
  ├─ /acerca/index.html (+4ms)
  ├─ /index.html (+61ms)
— HTML de dist/client/index.html:
/_server-islands/UltimoEntreno
id="ultimo-cargando">Cargando tu último entreno…
```

- **`index.html` sigue siendo estático:** lleva el `fallback` ("Cargando…") y una referencia a `/_server-islands/UltimoEntreno`.

Medido en Chrome:

```text
al recibir el HTML: Cargando tu último entreno…
después: Último entreno: running, 30 min (2026-10-14)
peticiones: GET /_server-islands/UltimoEntreno · GET /api/entrenos
```

- **La página llega al instante** (desde la CDN, en producción) y el servidor solo ejecuta la consulta y devuelve ese trozo de HTML.

| Aspecto                                   | Isla de cliente (`client:load`, B6.7) | _Server island_ (`server:defer`) |
| ----------------------------------------- | ------------------------------------- | -------------------------------- |
| ¿Dónde se ejecuta su código?              | En el navegador (React)               | En el servidor (Astro)           |
| ¿Envía JavaScript al navegador?           | Sí, el del componente                 | No, solo HTML                    |
| ¿Puede leer la base de datos o la sesión? | No directamente (necesita una API)    | Sí                               |

<Callout type="risk">

- **Necesitan adaptador:** sin servidor, nadie responde a `/_server-islands/…`.
- **Sus _props_ viajan por la URL, cifradas:** nada grande ni secreto; lee lo necesario dentro del componente.
- **Un _fallback_ de otro tamaño mueve la página (CLS),** como con `Suspense` en I2.6: dale la altura final.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Clasifica cada ruta de tu app (`/`, `/acerca`, `/estadisticas`, `/api/entrenos`) como estática, de servidor o mixta, justificando cada una con la tabla del Paso 2.
2. Configúralas con el `output` por defecto y `prerender = false` donde haga falta (es como ha quedado la app tras los pasos anteriores).
3. Compara este _build_ con uno `output: "server"` sin ningún `prerender`: cuenta los HTML generados y mide el tiempo medio de respuesta de cada página con 50 peticiones.

</Callout>

| Ruta            | Modo                                         | Motivo                                                                                                                 |
| --------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `/acerca`       | Estática                                     | No depende de nada                                                                                                     |
| `/`             | Estática + _server island_ + isla de cliente | La estructura es fija; el último entreno se pide al servidor (`server:defer`) y el formulario es React (`client:load`) |
| `/estadisticas` | Servidor                                     | Depende de los datos de ese momento                                                                                    |
| `/api/entrenos` | Servidor                                     | Es una API: lee y escribe en la base de datos                                                                          |

Con producción en marcha, en otra terminal (50 peticiones por ruta y la media con `awk`):

```bash
for r in / /acerca /estadisticas; do
  t=$(for i in $(seq 1 50); do curl -s -o /dev/null -w "%{time_total}\n" http://localhost:4322$r; done | awk '{s+=$1} END {printf "%.2f", s/NR*1000}')
  echo "$r $t ms"
done
```

En un portátil, con MongoDB en la misma máquina:

```text
Mixto (output por defecto + prerender = false donde hace falta):
   HTML generados en el build: 2
   /              0.61 ms de media (50 peticiones)
   /acerca        0.43 ms de media (50 peticiones)
   /estadisticas  2.03 ms de media (50 peticiones)
Todo bajo demanda (output: "server"):
   HTML generados en el build: 0
   /              2.59 ms de media (50 peticiones)
   /acerca        0.58 ms de media (50 peticiones)
   /estadisticas  1.26 ms de media (50 peticiones)
```

- **La portada es unas 4 veces más lenta en servidor** (0,61 → 2,59 ms): renderiza React en cada petición, en vez de leer un archivo.
- **Lo demás es ruido:** `/estadisticas` es de servidor en los dos, y `/acerca` apenas cuesta renderizarla.
- **La diferencia real llega en producción:** Atlas con decenas de milisegundos por consulta, arranques en frío y una CDN cerca del usuario frente a una función en una región.

<Callout type="risk">

- **No concluyas con una medición:** una petición puede tardar el doble por cualquier motivo. Media o, mejor, mediana.
- **La primera petición tras arrancar es más lenta** (módulos, primera conexión). El arranque en frío de Vercel se mide en Vercel.
- **Tu red no es la de tus usuarios:** un móvil con 4G lejos del servidor nota mucho más la diferencia (A6).

</Callout>

<Callout type="mastery">

Sabes qué páginas deben renderizarse en el servidor y por qué: añades el adaptador que corresponde a tu plataforma, generas en el _build_ todo lo que no depende del usuario ni de datos cambiantes, marcas con `prerender` las excepciones según el `output`, entiendes qué ocurre en cada paso de una petición en el servidor y usas _server islands_ para el trozo dinámico de una página estática.

</Callout>

## Resumen

- Con una ruta de servidor, el adaptador es obligatorio; sin él, `NoAdapterInstalled`.
- `output: "static"`: todo en el _build_ salvo `prerender = false`; `output: "server"`, al revés.
- Lo estático es igual para todos; lo de servidor se ejecuta cada vez.
- En servidor, la página es tan rápida como su consulta más lenta.
- `server:defer`: un trozo de servidor en una página estática, con `fallback`.
