Tras meses, un proyecto funciona, pero ya no sabes por qué es como es: partes que dan miedo, otras que no sabes si se usan, y todo parece urgente. Una **revisión de arquitectura** mira el conjunto con método (qué está bien, qué estorba, qué arreglar primero), para no acabar en una lista de gustos. Aquí escribes un _script_ de revisión, separas las falsas alarmas, ordenas la deuda y dejas tus decisiones por escrito.

**Requisitos:** todo este curso, además de rendimiento (A6), seguridad (A5) y CI (A7). Se revisó esta plataforma: 94 archivos y 4700 líneas en `src/`, 114 _commits_ en cinco semanas. Proyecto personal y joven: sus cifras son ejemplo, no referencia.

## Paso 1: el método

**Qué es:** tres preguntas, en orden: **¿qué va a cambiar?** (revisar lo que nadie tocará es entretenimiento), **¿qué dicen los datos?** (cada hallazgo, algo que se pueda señalar) y **¿qué significa?** (un número es una pregunta, no una conclusión).

**Cómo se usa:**

- **Cinco miradas:** acoplamiento, duplicación, límites, rendimiento y seguridad.
- **Un tiempo fijo,** por ejemplo dos horas: si tarda más, dejará de hacerse.

## Paso 2: un _script_ que mide

**Qué es:** `scripts/revisar.mjs` lee `src/` y el historial de Git, sin instalar nada.

**Cómo se usa:**

```js
// Archivo: scripts/revisar.mjs
// Revisión rápida de src/: dependencias, ciclos, duplicación y puntos calientes, sin instalar nada.
// Uso, desde la raíz del proyecto: node scripts/revisar.mjs
import { execSync } from "node:child_process";
import { existsSync, readFileSync, readdirSync, statSync } from "node:fs";
import { dirname, join, normalize, relative } from "node:path";

const RAIZ = "src";
const EXTENSIONES = [".ts", ".tsx", ".astro", ".js", ".mjs"];
const IMPORT = /(?:from\s+|import\s+|import\(\s*)["']([^"']+)["']/g;
const VENTANA = 8; // líneas seguidas iguales para contar como duplicado

function archivos(carpeta) {
  return readdirSync(carpeta).flatMap((nombre) => {
    const ruta = join(carpeta, nombre);
    if (statSync(ruta).isDirectory()) return nombre === "content" ? [] : archivos(ruta);
    return EXTENSIONES.some((e) => ruta.endsWith(e)) ? [ruta] : [];
  });
}

function resolver(desde, destino) {
  const base = destino.startsWith("@/")
    ? join(RAIZ, destino.slice(2))
    : destino.startsWith(".")
      ? normalize(join(dirname(desde), destino))
      : null;
  if (!base) return null; // una dependencia de npm
  const candidatos = ["", ...EXTENSIONES, ...EXTENSIONES.map((e) => `/index${e}`)];
  return candidatos.map((e) => base + e).find((r) => existsSync(r) && statSync(r).isFile()) ?? null;
}

const lista = archivos(RAIZ);
const codigo = new Map(lista.map((a) => [a, readFileSync(a, "utf8")]));
const ver = (ruta) => relative(RAIZ, ruta);
const top = (filas, n = 8) => filas.sort((a, b) => b[1] - a[1]).slice(0, n);
const imprimir = (filas) => {
  for (const [nombre, valor] of filas) console.log(`  ${String(valor).padStart(4)}  ${nombre}`);
};

// 1. Quién importa a quién
const grafo = new Map();
for (const [archivo, texto] of codigo) {
  const destinos = [...texto.matchAll(IMPORT)].map((m) => resolver(archivo, m[1]));
  grafo.set(archivo, new Set(destinos.filter(Boolean)));
}
const entrantes = new Map(lista.map((a) => [a, 0]));
for (const destinos of grafo.values()) {
  for (const d of destinos) entrantes.set(d, (entrantes.get(d) ?? 0) + 1);
}

console.log(`${lista.length} archivos, ${[...codigo.values()].join("").split("\n").length} líneas`);
console.log("\nMás importados: si cambian, afectan a más sitios");
imprimir(top([...entrantes].map(([a, n]) => [ver(a), n])));
console.log("\nImportan más cosas: saben demasiado");
imprimir(top([...grafo].map(([a, d]) => [ver(a), d.size])));

// 2. Ciclos: recorrido en profundidad guardando el camino actual
const ciclos = new Set();
const visto = new Set();
function visitar(archivo, camino) {
  const i = camino.indexOf(archivo);
  if (i >= 0) return void ciclos.add(camino.slice(i).map(ver).join(" → "));
  if (visto.has(archivo)) return;
  visto.add(archivo);
  for (const d of grafo.get(archivo) ?? []) visitar(d, [...camino, archivo]);
}
for (const archivo of lista) visitar(archivo, []);
console.log(`\nCiclos: ${ciclos.size}`);
for (const ciclo of ciclos) console.log(`  ${ciclo}`);

// 3. Duplicación: bloques de VENTANA líneas iguales, sin contar espacios ni líneas triviales
const bloques = new Map();
for (const [archivo, texto] of codigo) {
  const lineas = texto.split("\n").map((l) => l.trim());
  for (let i = 0; i + VENTANA <= lineas.length; i++) {
    const bloque = lineas.slice(i, i + VENTANA);
    if (bloque.filter((l) => l.length > 8).length < VENTANA - 2) continue;
    const clave = bloque.join("\n");
    bloques.set(clave, [...(bloques.get(clave) ?? []), `${ver(archivo)}:${i + 1}`]);
  }
}
const repetidos = [...bloques.values()].filter((sitios) => sitios.length > 1);
console.log(`\nBloques de ${VENTANA} líneas repetidos: ${repetidos.length}`);
for (const sitios of repetidos.slice(0, 6)) console.log(`  ${sitios.slice(0, 3).join("  =  ")}`);

// 4. Puntos calientes: lo que más cambia y además es grande
const historial = execSync("git log --name-only --format=", { encoding: "utf8" }).split("\n");
const cambios = new Map();
for (const ruta of historial) {
  if (codigo.has(ruta)) cambios.set(ruta, (cambios.get(ruta) ?? 0) + 1);
}
console.log("\nPuntos calientes: cambios × líneas");
imprimir(
  top(
    [...cambios].map(([a, n]) => {
      const lineas = codigo.get(a).split("\n").length;
      return [`${ver(a)} (${n} cambios, ${lineas} líneas)`, n * lineas];
    }),
  ),
);
```

<Callout type="risk">

- **Comprueba tu detector:** un «0 ciclos» solo vale si sabe encontrar uno. Se provocó un ciclo en otra app y lo encontró.
- **Lee con expresiones regulares, no como un compilador:** no ve rutas construidas en tiempo de ejecución, cuenta los `import type`, encuentra un ciclo por grupo y la duplicación es literal.
- **Para un proyecto grande,** `madge`, `jscpd` y `knip` (no usados aquí).

</Callout>

## Paso 3: acoplamiento y límites

**Qué es:** quién depende de quién, y si se respetan las reglas de capas.

**Cómo se usa:**

- **Muy importado no es malo:** `lib/constants.ts` lo usan 20 archivos, pero son 44 líneas que casi no cambian, un cimiento. Lo peligroso es muy importado **y** cambiante.
- **Lo que más importa suele ser una página:** `[section].astro` importa 14 archivos, el punto donde todo se une; en un servicio sería un problema.
- **Los puntos calientes indican dónde invertir:** la portada de un curso tiene 207 líneas y 4 cambios, y las páginas debían ser delgadas (A8.4). Hallazgo real.

Los límites se comprueban buscando lo que no debería ocurrir:

```bash
grep -rlE 'from "@/server/repositories' src/pages | wc -l    # páginas que saltan los servicios
grep -rlE 'from "@/server/' src/components | wc -l           # componentes que tocan el servidor
```

```text
3
7
```

Siete componentes tocando el servidor suena grave. Primera falsa alarma:

```text
import type { CourseOverview } from "@/server/services/overview.service";
import type { PublicQuestion, SubmitQuizResult } from "@/server/services/quiz.service";
```

- **Todos eran `import type`,** que desaparece al compilar: nada llega al navegador. Un olor menor, no un fallo.
- **Los otros 3 sí son reales:** la portada de un curso, el temario y la evaluación llaman a `repos.…` sin servicio. Razonable para leer, pero rompe la regla D6 del proyecto (ruta, servicio y repositorio).

<Callout type="risk">

- **Un `grep` cuenta coincidencias, no fallos:** mira cada resultado antes de concluir.
- **Una regla solo existe si está escrita:** sin la D6, los 3 atajos serían una opinión (Paso 9).

</Callout>

## Paso 4: duplicación

**Qué es:** código repetido, que importa cuando una corrección debe hacerse en varios sitios **y es fácil olvidar uno**.

**Cómo se usa:** cinco bloques, de los que cuatro son solapes de un mismo fragmento: **dos** casos reales. Uno, el formulario:

```tsx
<TextField
  label="Correo"
  type="email"
  autoComplete="email"
  inputMode="email"
  error={errors.email?.message}
  {...register("email")}
/>
```

- **Está en `LoginForm` y `RegisterForm`, y no se une:** es código parecido, no el mismo conocimiento (cambian por motivos distintos, como `autoComplete`) y ya comparten `TextField`. Una abstracción costaría más que 8 líneas.
- **La tabla de intentos de `QuizHistoryTable` y `evaluacion.astro`** sí cumple la regla en parte: candidata, pero menor.

<Callout type="risk">

- **Unir lo parecido acopla lo que cambia por separado:** cada cambio de un formulario obligaría a pensar en el otro.
- **El detector solo ve duplicación literal:** dos bloques iguales con otros nombres pasan.

</Callout>

## Paso 5: rendimiento

**Qué es:** sin medir producción, el _build_ ya da pistas sobre el JavaScript.

**Cómo se usa:**

```bash
npm run build
for f in dist/client/_astro/*.js; do echo "$(gzip -c "$f" | wc -c) $(basename "$f")"; done | sort -rn | head -4
```

```text
102417 NotesEditor.BVhQSCeV.js
 64983 client.Dda4loRL.js
 33726 TextField.WhAAFl1S.js
 11179 auth-client.B90wgs1i.js
```

- **102 KB para un editor de notas parece el primer objetivo,** y es la segunda falsa alarma. El código lo explica:

```tsx
// TipTap y ProseMirror (unos 100 KB gzip) van en un trozo aparte que solo se pide si hace falta
const NotesEditor = lazy(() => import("./NotesEditor"));
```

- **Un archivo grande en `dist/` no es lo que descarga cada visita:** la pregunta es **cuándo se carga**, con la pestaña Network (A6).

<Callout type="risk">

- **El tamaño del _build_ no dice cuándo se descarga:** confírmalo en el navegador antes de optimizar.
- **Un `lazy` que alguien quita sin saberlo** devuelve los 100 KB a todas las páginas: el comentario del código lo protege.

</Callout>

## Paso 6: pruebas

**Qué es:** la cobertura de Vitest, que dice qué líneas recorren los tests unitarios.

**Cómo se usa:**

```bash
npx vitest run --coverage
```

```text
Líneas 51 %  ·  Ramas 41 %  ·  Funciones 40 %

src/server/services        0 de 90 líneas      0 %
src/server/repositories   62 de 66 líneas     94 %
src/lib/domain            44 de 44 líneas    100 %
```

- **Ninguna línea de los servicios probada:** tercera falsa alarma, o casi. Vitest solo mide sus tests, y los servicios los recorren los 64 E2E de Playwright. Aun así, un E2E no prueba cada rama de una regla.
- **Buena señal:** lo más delicado, las reglas puras de `lib/domain`, está al 100 %.

<Callout type="risk">

- **La cobertura mide líneas recorridas, no comprobadas:** un 100 % sin aserciones no prueba nada.
- **Sumar E2E y unitarios exige otra herramienta:** no confundas «0 % en Vitest» con «sin probar».

</Callout>

## Paso 7: seguridad

**Qué es:** esta mirada no se mide con un _script_, sino con la lista de A5.

**Cómo se usa:**

- ¿Las dependencias tienen fallos conocidos? `npm audit --omit=dev`.
- ¿Hay secretos en el historial o en el cliente?
- ¿Cada ruta comprueba la sesión y **a quién pertenece** el dato?
- ¿Las entradas se validan en el servidor?
- ¿Hay límites en lo que se puede abusar?
- ¿Las cabeceras son las de A5?

- **Esta lección no incluye resultados de esta parte, a propósito:** un informe de seguridad de un sistema en producción no va en una lección pública. Guárdalo en privado; se puede publicar que la revisión existe, no sus hallazgos, hasta resolverlos.

## Paso 8: la deuda técnica

**Qué es:** lo que te frena al cambiar el código, como un préstamo que cobra intereses. **El código feo que nadie toca no es deuda,** ni lo decidido a conciencia.

**Cómo se usa:** tras separar las falsas alarmas, `docs/deuda.md`:

| Hallazgo                               | Impacto | Esfuerzo | Decisión    |
| -------------------------------------- | ------- | -------- | ----------- |
| E2E de CI en rojo desde octubre        | Alto    | Bajo     | Ya          |
| `README` y `AGENTS.md` de plantilla    | Medio   | Bajo     | Ya          |
| Portada de curso: 207 líneas           | Medio   | Medio    | Al tocarla  |
| 3 páginas sin capa de servicio         | Bajo    | Bajo     | Al tocarlas |
| Estructura por tipo, no por _features_ | Medio   | Alto     | Proyecto A8 |
| Tabla de intentos repetida             | Bajo    | Bajo     | Al tocarla  |

- **Fuera, con su motivo:** los campos repetidos de los formularios, el `import type` de los componentes y la pestaña que no se sincroniza (A8.3, decisión consciente).
- **La primera fila:** comprobado en A7, el CI fallaba desde octubre en el paso de MongoDB y se seguía publicando, porque lo que frena un `push` es un _hook_ local. **Una alarma siempre en rojo no avisa de nada.** En A7 se reprodujo, y fijar `mongo:8.2` debería bastar; el cambio sigue sin aplicarse ni probarse en el propio CI.
- **Tres reglas para ordenar:** alto impacto y poco esfuerzo, ya; lo demás, al pasar por allí, en una PR propia antes de la funcionalidad; y lo grande, con fecha o nunca, escribiendo por qué.

<Callout type="risk">

- **Revisar sin decidir no sirve:** cada fila termina con una decisión, aunque sea «no lo haremos».
- **El impacto es criterio, no medida:** escríbelo para que otra persona lo discuta.
- **Vuelve a medir dentro de unos meses:** importa la tendencia. En la app de A8.4, lo más importado pasó a ser `features/auth/server.ts` (14), una puerta de entrada, lo buscado.

</Callout>

## Paso 9: decisiones para tu yo futuro, y para una IA

**Qué es:** las decisiones escritas convierten una preferencia en algo comprobable.

**Cómo se usa:**

- **La plataforma no tiene `docs/adr/`,** sino una tabla de 11 decisiones con su motivo en `planificacion.md`: por eso la revisión pudo decir que tres páginas rompen la «regla D6». Le faltan las alternativas descartadas, lo primero que se olvida; el formato de A8.4 las añade.
- **Una IA tiene tu mismo problema dentro de un año:** lee qué se hizo, no por qué. `AGENTS.md`, que esas herramientas leen al empezar, aquí solo tiene las instrucciones genéricas de Astro. Debería contar lo que no se deduce del código:

```markdown
# Dani Academy

Plataforma personal de cursos: Astro + React + MongoDB, en Vercel.

## Comprobar

npm run lint && npm run check && npm run test:run

## Reglas

- Capas: ruta → servicio → repositorio. La lógica pura va en `src/lib/domain/`.
- El contenido vive en `src/content`, nunca en MongoDB (ver planificacion.md, D1).
- Las respuestas de las evaluaciones nunca llegan al cliente (D9).
- Se trabaja directamente en `main`.

## No hacer

- No imprimir el contenido de `.env`.
- No renombrar los IDs de curso ni de sección: son claves del progreso (D3).
```

- **Pequeño y concreto.** No se ha medido cuánto ayuda: es una recomendación.

<Callout type="risk">

- **`README`, ADR y `AGENTS.md` envejecen:** incluye «revisar la documentación» en cada revisión.
- **Un `AGENTS.md` con información falsa es peor que uno vacío:** la IA la seguirá. Solo lo que sigue siendo cierto.

</Callout>

Solución. La revisión la haces tú con los Pasos 1 a 8 sobre tu Planificador: el resultado es tu lista de deuda. Como ejemplo, los 3 ADR de la plataforma, de sus decisiones reales.

`docs/adr/0001-contenido-en-el-repositorio.md`:

```markdown
# ADR-0001 · El contenido vive en el repositorio

Estado: aceptado

## Contexto

El temario son más de cien lecciones que cambian con cada revisión. Debe
poder revisarse como el código, y un error no debe llegar a publicarse.

## Decisión

Las lecciones son MDX en Content Collections, validadas con Zod en el build.
MongoDB guarda solo lo que pertenece a cada persona.

## Alternativas

- CMS o MongoDB: edición sin desplegar, pero sin validación en el build, sin
  historial en Git y con un servicio más que mantener.

## Consecuencias

- Publicar exige un despliegue.
- Un frontmatter mal escrito rompe el build, que es lo que se busca.
```

`docs/adr/0002-progreso-una-fila-por-seccion.md`:

```markdown
# ADR-0002 · El progreso es una fila por sección leída

Estado: aceptado

## Contexto

La consulta más frecuente es "secciones leídas de este curso". Marcar dos
veces, o desde dos pestañas, no debe duplicar nada.

## Decisión

Colección `section_progress` con un documento por sección, e índice único
`{ userId, sectionId }`. `markRead` hace `upsert` con `$setOnInsert`.

## Alternativas

- Un documento por curso con un array `seccionesLeidas`: lectura en una
  consulta y tamaño acotado, pero se pierde la fecha de cada sección
  (`readAt`), que usa "continuar donde lo dejaste".

## Consecuencias

- Marcar es idempotente, también con dos peticiones a la vez.
- Leer un curso devuelve varias filas: se cubre con un índice `{ userId, courseId }`.
```

`docs/adr/0003-trabajar-en-main.md`:

```markdown
# ADR-0003 · Trabajo directo en `main`, con un hook local

Estado: en revisión

## Contexto

Hay una sola persona, así que nadie más revisaría una PR.

## Decisión

Commits directos a `main`. Un hook `pre-push` en `.githooks/` ejecuta las
comprobaciones antes de subir, y Vercel despliega desde `main`.

## Alternativas

- PR y regla de protección (A7): garantía en el servidor, a cambio de un
  paso más en cada cambio.

## Consecuencias

- Publicar es muy rápido.
- Nada obliga a que el CI esté en verde: el E2E lleva roto desde octubre
  sin frenar ninguna publicación. Por eso este ADR está en revisión.
```

- **Fíjate en el tercero:** escribir sus consecuencias sacó a la luz un problema que la decisión original no contaba. Ese es el valor del ejercicio.
- **Elige las tres decisiones más caras de cambiar,** no las más interesantes, y si no recuerdas el motivo, escribe «no consta».
- **El Planificador no se ha revisado aquí:** el resultado depende de tu código.

<Callout type="mastery">

Puedes explicar el porqué de cada decisión estructural de tus proyectos y señalar dónde está escrito. Sabes medir, descartar las falsas alarmas y ordenar lo que queda. Y una revisión tuya termina con decisiones, no con una lista de quejas.

</Callout>

## Resumen

- **Qué va a cambiar, qué dicen los datos y qué significan,** con cinco miradas y tiempo fijo.
- **Prueba tu detector:** un «0 ciclos» solo vale si sabe encontrar uno.
- **Falsas alarmas:** 7 `import type`, un editor de 102 KB con carga diferida y 0 % en servicios que cubre el E2E.
- **Muy importado no es malo** si no cambia; código parecido no es el mismo conocimiento.
- **La seguridad se revisa, pero sus hallazgos no se publican.**
- **Deuda es lo que te frena:** lo urgente y fácil ya, lo demás al pasar, lo grande con fecha o nunca.
- **Una alarma siempre en rojo no avisa;** ADR y `AGENTS.md` cuentan lo que el código no.
