Un proyecto pequeño se ordena solo por tipo (`components/`, `services/`, `schemas/`), hasta que añadir «mis marcas» obliga a abrir siete carpetas y editar archivos de otras funcionalidades. Organizar por **_features_** es que lo que cambia junto viva junto. Aquí reorganizas la app así, proteges sus límites con una regla y dejas escrito por qué.

**Requisitos:** capas (I3.5), ESLint (A7.2) y las lecciones anteriores de este curso. Medido sobre la app de entrenamiento real (60 archivos en `src/`, 71 tests de Vitest) en un Mac con Node 26; el monorepo es una maqueta aparte.

## Paso 1: el síntoma

**Qué es:** con la estructura por tipo, una funcionalidad nueva se reparte por muchas carpetas y toca archivos ajenos.

**Cómo se usa:** «Mis marcas» por tipo son 10 archivos en 7 carpetas:

```text
A  src/components/TablaMarcas.astro
A  src/pages/api/marcas.ts
A  src/pages/marcas.astro
M  src/repositories/index.ts       ← ajeno
A  src/repositories/marcas.repo.ts
A  src/schemas/marca.ts
M  src/services/index.ts           ← ajeno
A  src/services/marcas.service.ts
A  tests/unit/marcas.test.ts
M  tests/unit/servicios.test.ts    ← ajeno
```

- **Las tres `M` son lo preocupante:** para añadir algo has editado archivos existentes, donde chocarán dos personas.
- **Esta plataforma, organizada por tipo, muestra lo mismo:** las notas están en 5 carpetas, un _commit_ típico suyo toca 6 y uno de progreso 10. Con 4 _commits_ de cada una, es una pista, no una estadística.

<Callout type="risk">

- **Un archivo común que todos editan** (`services/index.ts`) es el primer sitio de conflictos entre ramas.
- **Contar carpetas no basta:** mira cuántos archivos ajenos hay que editar, como en el Paso 4.

</Callout>

## Paso 2: la estructura

**Qué es:** cada funcionalidad en su carpeta, y lo compartido aparte.

**Cómo se usa:**

```text
src/
├── features/
│   ├── auth/
│   ├── entrenos/
│   ├── marcas/
│   │   ├── components/TablaMarcas.astro
│   │   ├── marca.schema.ts
│   │   ├── marcas.repo.ts
│   │   ├── marcas.service.ts
│   │   └── server.ts          ← lo que ofrece al resto
│   ├── notas/
│   └── resumen/
├── components/ui/             ← sin lógica de negocio
├── lib/                       ← mongo, log, errores: lo usan varias
├── layouts/
├── actions/
└── pages/                     ← solo rutas: delgadas
```

1. **¿Pertenece a una funcionalidad?** Va a su _feature_.
2. **¿Lo usan varias, y no sabe nada del negocio?** Va a `lib/` o a `components/ui/`.
3. **¿Es una URL?** Va a `pages/`, porque Astro enruta por archivos. Ahí solo llamas a la _feature_.

- **No muevas algo a `lib/` para no decidir:** `tipos.ts` tenía una lista de entrenos y otra de notas, y se partió en dos, cada una a su _feature_.

<Callout type="risk">

- **`lib/` como cajón de sastre** recrea el problema: solo lo que no sabe del negocio.
- **`pages/` sigue siendo de Astro:** no metas lógica ahí, solo llamadas a la _feature_.

</Callout>

## Paso 3: una _feature_ completa

**Qué es:** las capas de I3.5 (esquema, repositorio, servicio), dentro de la carpeta, con un `server.ts` como puerta de entrada.

**Cómo se usa:** el contrato:

```ts
// Archivo: src/features/marcas/marca.schema.ts
export interface MarcaDTO {
  tipo: string;
  minutos: number;
  entrenos: number;
}
```

El repositorio:

```ts
// Archivo: src/features/marcas/marcas.repo.ts
import type { Db } from "mongodb";
import type { MarcaDTO } from "./marca.schema";

export function crearMarcasRepo(db: Db) {
  const col = db.collection("entrenos");

  return {
    async porTipo(userId: string): Promise<MarcaDTO[]> {
      return col
        .aggregate<MarcaDTO>([
          { $match: { userId } },
          { $group: { _id: "$tipo", minutos: { $max: "$minutos" }, entrenos: { $sum: 1 } } },
          { $project: { _id: 0, tipo: "$_id", minutos: 1, entrenos: 1 } },
        ])
        .toArray();
    },
  };
}

export type MarcasRepo = ReturnType<typeof crearMarcasRepo>;
```

El servicio:

```ts
// Archivo: src/features/marcas/marcas.service.ts
import type { MarcasRepo } from "./marcas.repo";

export function crearServicioMarcas(repo: Pick<MarcasRepo, "porTipo">) {
  return {
    async listar(userId: string) {
      const marcas = await repo.porTipo(userId);
      return marcas.sort((a, b) => b.minutos - a.minutos);
    },
  };
}
```

- **`server.ts` conecta la _feature_ con la base real** y es su puerta. Antes lo hacía un `services/index.ts` común, que había que editar cada vez:

```ts
// Archivo: src/features/marcas/server.ts
import { db } from "@/lib/mongo";
import { crearMarcasRepo } from "./marcas.repo";
import { crearServicioMarcas } from "./marcas.service";

export const servicioMarcas = crearServicioMarcas(crearMarcasRepo(db));
```

El componente:

```astro
---
// Archivo: src/features/marcas/components/TablaMarcas.astro
import type { MarcaDTO } from "../marca.schema";

const { marcas } = Astro.props as { marcas: MarcaDTO[] };
---

<ul>
  {marcas.map((m) => (
    <li>
      {m.tipo}: {m.minutos} min en {m.entrenos} entrenos
    </li>
  ))}
</ul>
```

Las rutas, delgadas:

```ts
// Archivo: src/pages/api/marcas.ts
import type { APIRoute } from "astro";
import { usuarioDe } from "@/features/auth/server";
import { servicioMarcas } from "@/features/marcas/server";
import { aRespuesta } from "@/lib/errores";

export const prerender = false;

export const GET: APIRoute = async ({ locals }) => {
  try {
    return Response.json({ marcas: await servicioMarcas.listar(usuarioDe(locals).id) });
  } catch (e) {
    return aRespuesta(e);
  }
};
```

```astro
---
// Archivo: src/pages/marcas.astro
import TablaMarcas from "@/features/marcas/components/TablaMarcas.astro";
import { usuarioDe } from "@/features/auth/server";
import { servicioMarcas } from "@/features/marcas/server";
import Base from "@/layouts/Base.astro";

export const prerender = false;

const marcas = await servicioMarcas.listar(usuarioDe(Astro.locals).id);
---

<Base titulo="Mis marcas">
  <h1>Mis marcas</h1>
  <TablaMarcas marcas={marcas} />
</Base>
```

Y su test:

```ts
// Archivo: tests/unit/marcas.test.ts
import { describe, expect, it } from "vitest";
import { crearServicioMarcas } from "@/features/marcas/marcas.service";

describe("marcas", () => {
  it("ordena de mayor a menor", async () => {
    const porTipo = async () => [
      { tipo: "fuerza", minutos: 30, entrenos: 2 },
      { tipo: "running", minutos: 60, entrenos: 1 },
    ];
    const marcas = await crearServicioMarcas({ porTipo }).listar("ana");
    expect(marcas.map((m) => m.tipo)).toEqual(["running", "fuerza"]);

```

<Callout type="risk">

- **`server.ts` solo lo importa el servidor:** si una isla lo importa, arrastra MongoDB al navegador (Paso 6).
- **El test importa el servicio interno a propósito:** la regla del Paso 5 deja fuera `tests/`.

</Callout>

## Paso 4: la medida

**Qué es:** la misma funcionalidad en las dos estructuras, con `astro check` sin errores y el _build_ y los 72 tests en verde en ambas.

**Cómo se usa:**

| Aspecto                  | Por tipo | Por _features_ |
| ------------------------ | -------- | -------------- |
| Archivos                 | 10       | 8              |
| Carpetas                 | 7        | 5              |
| Archivos ajenos editados | 3        | **0**          |

- **La diferencia de carpetas es modesta** (`pages/`, `pages/api/` y `tests/` siguen por necesidad); lo que cambia es la última fila. Al quitar la funcionalidad:

```text
Por features: borrar la carpeta, las 2 rutas y el test  →  build y 71 tests en verde
Por tipo:     borrar los 7 archivos nuevos              →  build 1
  Could not resolve './marcas.service' in src/services/index.ts
```

- **Por tipo, además, hay que recordar qué tres archivos editaste.** Si puedes borrar una funcionalidad borrando una carpeta, sus límites son reales.

<Callout type="risk">

- **Una _feature_ puede depender de otra:** `resumen` usa los entrenos, la única dependencia de esta app. Bien si va en una dirección y pasa por `server.ts`.
- **`features/` no se paga solo:** con pocas páginas, por tipo es más simple; cámbialo cuando una funcionalidad toque muchas carpetas.

</Callout>

## Paso 5: que los límites se cumplan

**Qué es:** sin una regla, una carpeta es una costumbre. `no-restricted-imports` de ESLint impide entrar por la puerta de atrás.

**Cómo se usa:** en `eslint.config.js`, antes de `prettier`:

```js
{
  // Una feature solo ofrece lo público: server.ts, sus esquemas y sus componentes
  files: ["src/**/*.{ts,tsx,astro}"],
  rules: {
    "no-restricted-imports": [
      "error",
      {
        patterns: [
          {
            group: [
              "@/features/*/*",
              "!@/features/*/server",
              "!@/features/*/*.schema",
              "!@/features/*/components",
              "!@/features/*/components/*",
              "../*/*",
              "!../components/*",
              "../../*/*",
            ],
            message: "Eso es interno de la feature: usa server.ts, su esquema o sus componentes.",
          },
        ],
      },
    ],
  },
},
```

- **Encontró 15 importaciones en 13 archivos** que entraban por detrás (`@/features/auth/sesion`); se resolvieron ampliando cada `server.ts`. Ahora un atajo no pasa:

```text
'@/features/entrenos/entrenos.repo' import is restricted from being used by a pattern.
Eso es interno de la feature: usa server.ts, su esquema o sus componentes.
```

- **Los patrones `../*/*` hacen falta:** solo con los de `@/`, `../entrenos/entrenos.repo` dio código 0; con ellos, 1.

<Callout type="risk">

- **Una regla solo protege si se ejecuta:** ponla en el CI (A7).
- **Los tests quedan fuera a propósito** (`files: ["src/**"]`): pueden importar lo interno para probarlo.
- **`dependency-cruiser`** es más estricto (no probado aquí): esta regla bastó.

</Callout>

## Paso 6: _barrel files_, con cuidado

**Qué es:** un _barrel_ es un `index.ts` que reexporta una carpeta. Cómodo, y peligroso.

**Cómo se usa:**

```ts
// src/features/entrenos/index.ts
export * from "./entreno.schema";
export * from "./entrenos.repo";
export * from "./entrenos.service";
export * from "./ritmo";
export * from "./server";
export * from "./tipos";
```

Importando solo `TIPOS_ENTRENO` desde una isla de React:

| El _barrel_ incluye       | Build | JS del cliente (gzip) | MongoDB en el cliente |
| ------------------------- | ----- | --------------------- | --------------------- |
| Sin _barrel_              | 0     | 126 KB                | No                    |
| Todo, con `server.ts`     | 1     | —                     | —                     |
| Todo, sin `server.ts`     | **0** | **343 KB**            | **Sí**                |
| Esquema y funciones puras | 0     | 126 KB                | No                    |

- **La tercera fila:** el _build_ pasó en verde con el controlador de MongoDB en el navegador, y nada avisa salvo vigilar el tamaño (A6). La segunda falló gracias a `astro:env`, no por casualidad:

```text
[ServerOnlyModule] The "astro:env/server" module is only available server-side.
```

**El servidor de desarrollo no descarta nada:** 300 módulos con _barrel_, usando uno:

```text
              peticiones en dev   de esa carpeta   build final
con barrel    331                 301              134 bytes
directo       31                  1                134 bytes
```

- **En producción, idéntico; en desarrollo, 300 peticiones más** (625–846 ms frente a 572–639 en un Mac), y crece con el proyecto.

**Los ciclos:** un archivo que importa del _barrel_ de su carpeta:

```ts
// a.mjs
import { LIMITE } from "./index.mjs"; // su propio barrel, que reexporta a.mjs y b.mjs
export const DOBLE = LIMITE * 2;
```

```text
ReferenceError: Cannot access 'LIMITE' before initialization
```

- **Desde `./b.mjs`, dio `20`.** Por eso tres reglas: `server.ts` nombra lo que exporta, sin `export *` (`export { crearNota, listarNotas } from "./notas.server"`); nada de servidor en lo que importa el cliente; y dentro de una _feature_, rutas relativas directas.

<Callout type="risk">

- **`export *` puede meter el servidor en el navegador sin romper el _build_:** vigila el tamaño del JavaScript del cliente.
- **Un ciclo da `ReferenceError` en tiempo de ejecución,** no al compilar: nunca importes de tu propia puerta.

</Callout>

## Paso 7: nombres y documentación

**Qué es:** nombres coherentes, un `README` que dice cómo se usa y **ADR** que dicen por qué es así.

**Cómo se usa:** en esta app, componentes en `PascalCase` y el resto en minúsculas con guiones y sufijo (`marcas.repo.ts`, `marcas.service.ts`, `marca.schema.ts`): el sufijo permite buscar y escribir reglas como la del Paso 5. Y las mayúsculas: `Ritmo` en vez de `ritmo` en un `import`:

```text
Mac (sistema sin distinguir mayúsculas):  build 0
Linux, como tu CI y tu servidor:          build 1
  Could not resolve '../lib/Ritmo'
astro check, en el Mac:                   error ts(1149)
```

- **Funciona en tu equipo y se rompe al desplegar;** `astro check` lo detecta en local.
- **El `README`** responde qué es, cómo se arranca, cómo se prueba y dónde está cada cosa, para ti dentro de seis meses y para cualquier IA. El de esta plataforma sigue siendo el de la plantilla de Astro: deuda real, que A8.5 enseña a priorizar.
- **Un ADR** (_Architecture Decision Record_) guarda en `docs/adr/` una decisión y su motivo, incluido lo descartado:

```markdown
# ADR-0001 · Título en forma de decisión

Estado: aceptado · Fecha: AAAA-MM-DD

## Contexto

Qué problema había y qué limitaciones existen.

## Decisión

Qué se hace, en una o dos frases.

## Alternativas

Qué se descartó, y por qué.

## Consecuencias

Qué mejora, qué empeora y qué hay que vigilar.
```

- **Un ADR aceptado no se edita:** si cambias de idea, otro lo sustituye.

<Callout type="risk">

- **macOS no distingue mayúsculas en los nombres; Linux, sí:** un `import` mal escrito pasa en local y rompe el CI o el servidor.
- **Un `README` de plantilla es peor que ninguno:** parece documentación y no explica nada.

</Callout>

## Paso 8: monorepo, solo cuando hace falta

**Qué es:** un monorepo con **pnpm workspaces** guarda varios paquetes en un repositorio. Aquí, dos apps de Astro que comparten un paquete de esquemas.

**Cómo se usa:**

```text
apps/web/  apps/panel/  packages/esquemas/  pnpm-workspace.yaml
```

`pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

- **El paquete se exporta sin compilar** (`"exports": "./src/index.ts"`) y las apps lo declaran con `"@entrenos/esquemas": "workspace:*"`. Funcionó a la primera:

```bash
pnpm --filter web build    # una app
pnpm -r build              # todas
```

`web` importó `zod` sin declararlo, una **dependencia fantasma**:

```text
pnpm:  código 1 · failed to resolve import "zod"
npm:   código 0 · funciona por casualidad
```

- **Con npm funcionaba por casualidad** (otro paquete la traía) y se rompería si la quitara; pnpm lo detecta a tiempo.
- **Cuándo:** dos cosas que se despliegan por separado y comparten código. Con una sola app, las _features_ dan casi todo sin ceremonia; esta app no lo necesita.

<Callout type="risk">

- **No se ha probado con Docker ni en Vercel,** donde está buena parte de su coste.
- **Exportar `.ts` sin compilar** obliga a que cada app sepa compilarlo: funciona con Vite, no con cualquier herramienta.

</Callout>

Después, a mano:

1. Divide `lib/tipos.ts` en `entrenos/tipos.ts` y `notas/categorias.ts`.
2. Crea un `server.ts` por _feature_, como este, y borra `src/composicion/`. Sus usos cambian: `servicios.entrenos` pasa a ser `servicioEntrenos`.

```ts
// Archivo: src/features/entrenos/server.ts
// Lo que esta feature ofrece al resto de la app en el servidor, conectado a la base de datos real
import { cacheDatos } from "@/lib/cache-memoria";
import { repoLimites } from "@/lib/limites";
import { db } from "@/lib/mongo";
import { crearEntrenosRepo } from "./entrenos.repo";
import { crearServicioEntrenos } from "./entrenos.service";

export type { EntrenosRepo } from "./entrenos.repo";

export const servicioEntrenos = crearServicioEntrenos({
  entrenos: repoEntrenos,
  limites: repoLimites,
  alCambiar: () => cacheDatos.borrar("comunidad"), // todos los cambios pasan por aquí
});
```

3. Saca el límite compartido a `src/lib/limites.ts`, y en el test de la API cambia el `vi.mock` a `@/features/resumen/server`.
4. Activa la regla del Paso 5, y amplía cada `server.ts` hasta que no quede ningún error.
5. Corrige las cabeceras `// Archivo:`, que siguen con la ruta antigua.
6. Escribe `docs/adr/0001-organizar-por-features.md`:

```markdown
# ADR-0001 · Organizar `src` por features

Estado: aceptado · Fecha: 2026-11-07

## Contexto

Añadir "Mis marcas" tocó 10 archivos en 7 carpetas, y 3 eran de otras
funcionalidades. Las conexiones comunes (`services/index.ts`) se editaban
en cada cambio. No había nada que impidiera saltarse las capas.

## Decisión

Cada funcionalidad vive en `src/features/<nombre>/`. Fuera de ella solo se
usan `server.ts`, sus esquemas y sus componentes. Lo impide ESLint
(`no-restricted-imports`). `pages/` solo contiene rutas.

## Alternativas

- Seguir por tipo: simple, pero cada funcionalidad nueva edita archivos ajenos.
- Monorepo con paquetes: solo hay una app que desplegar; no compensa.
- Un `index.ts` con `export *` por feature: metió MongoDB en el navegador,
  con el build en verde (126 → 343 KB). Descartado.

## Consecuencias

- Mis marcas pasa a 8 archivos, y ninguno ajeno. Borrar una funcionalidad
  es borrar su carpeta, sus rutas y sus tests.
- Cada `server.ts` debe mantenerse a mano.
- Las rutas de `pages/` y los tests siguen fuera de la carpeta.
- Vigilar: que `lib/` no se convierta en un cajón de sastre.
```

- **Al terminar, `astro check`, ESLint, el _build_ y los tests en verde.** Los E2E y un servidor no se probaron: hazlo antes de desplegar.
- **Si tu app es distinta,** cambia la tabla `M`: es lo único específico.
- **El resto es criterio** (`CampoTexto` a `components/ui/`, `limites` a `lib/`): otra persona podría defender otra cosa, y para eso está el ADR.

<Callout type="mastery">

Una funcionalidad nueva cabe en una carpeta, más sus rutas y sus tests, sin tocar nada ajeno. Puedes demostrarlo borrándola. Una regla de ESLint protege los límites, y un ADR explica por qué existen.

</Callout>

## Resumen

- **Por _features_:** lo que cambia junto, vive junto.
- **Mis marcas:** de 10 archivos a 8, y de 3 ajenos editados a 0; se borra quitando una carpeta.
- **`server.ts`** es la puerta de cada _feature_; `no-restricted-imports` encontró 15 atajos, también relativos.
- **_Barrels_:** con `export *`, MongoDB llegó al navegador con el _build_ en verde, y 331 peticiones en dev frente a 31.
- **Mayúsculas:** Mac 0, Linux 1; `astro check` lo ve.
- **`README`** para cómo se usa, **ADR** para por qué.
- **Monorepo** solo con despliegues separados; pnpm ve dependencias fantasma.
- **Migra con _script_ y todas las comprobaciones.**
