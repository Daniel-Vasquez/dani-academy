Un proyecto pequeño se organiza solo: `components/`, `services/`, `schemas/`. Funciona hasta que añadir algo tan simple como "mis marcas" te obliga a abrir siete carpetas y a editar archivos de otras funcionalidades. Lo que pertenece a la misma idea está repartido por tipo de archivo, y lo que no tiene nada que ver está junto.

Una analogía: un almacén frente a una cocina. En un almacén ordenas por tipo, todos los cuchillos juntos y todas las sartenes juntas. Pero nadie cocina así: en una cocina, cada puesto tiene a mano lo que necesita para su plato. Organizar por **_features_** es montar puestos: lo que cambia junto, vive junto.

**Lo que tendrás al terminar:** una app reorganizada por _features_, una regla que impide saltarse sus límites y un registro escrito de por qué.

**Requisitos:** capas (I3.5), ESLint (A7.2) y las lecciones anteriores de este curso.

Todo se midió sobre la app de entrenamiento del curso, real, con 60 archivos en `src/` y 71 tests de Vitest, en un Mac con Node 26. El monorepo es una maqueta aparte.

## Paso 1: el síntoma

Se añadió la misma funcionalidad a la app, "Mis marcas", con la estructura por tipo. Son 10 archivos en 7 carpetas:

```text
A  src/components/TablaMarcas.astro
A  src/pages/api/marcas.ts
A  src/pages/marcas.astro
M  src/repositories/index.ts       ← ajeno
A  src/repositories/marcas.repo.ts
A  src/schemas/marca.ts
M  src/services/index.ts           ← ajeno
A  src/services/marcas.service.ts
A  tests/unit/marcas.test.ts
M  tests/unit/servicios.test.ts    ← ajeno
```

Lo preocupante son las tres `M`: **para añadir algo nuevo has editado archivos que ya existían.** Dos personas que añadan una funcionalidad cada una chocarán ahí.

Se ve igual en la plataforma donde lees esto, organizada por tipo. Las notas están en 5 carpetas de `src/`, y un _commit_ típico de esa funcionalidad toca 6 carpetas. Uno de progreso, 10. Son pocos _commits_, 4 de cada una, así que tómalo como una pista y no como una estadística.

## Paso 2: la estructura

```text
src/
├── features/
│   ├── auth/
│   ├── entrenos/
│   ├── marcas/
│   │   ├── components/TablaMarcas.astro
│   │   ├── marca.schema.ts
│   │   ├── marcas.repo.ts
│   │   ├── marcas.service.ts
│   │   └── server.ts          ← lo que ofrece al resto
│   ├── notas/
│   └── resumen/
├── components/ui/             ← sin lógica de negocio
├── lib/                       ← mongo, log, errores: lo usan varias
├── layouts/
├── actions/
└── pages/                     ← solo rutas: delgadas
```

Tres preguntas deciden dónde va cada archivo:

1. **¿Pertenece a una funcionalidad?** Va a su _feature_.
2. **¿Lo usan varias, y no sabe nada del negocio?** Va a `lib/` o a `components/ui/`.
3. **¿Es una URL?** Va a `pages/`, porque Astro enruta por archivos. Ahí solo llamas a la _feature_.

No muevas algo a `lib/` para no decidir. Un archivo `tipos.ts` tenía dos listas, una de entrenos y otra de notas. En `lib/` sería un cajón de sastre, así que se partió en dos, y cada lista se fue a su _feature_.

## Paso 3: una _feature_ completa

Las capas de I3.5 siguen ahí, pero dentro de la carpeta. El contrato:

```ts
// Archivo: src/features/marcas/marca.schema.ts
export interface MarcaDTO {
  tipo: string;
  minutos: number;
  entrenos: number;
}
```

El repositorio:

```ts
// Archivo: src/features/marcas/marcas.repo.ts
import type { Db } from "mongodb";
import type { MarcaDTO } from "./marca.schema";

export function crearMarcasRepo(db: Db) {
  const col = db.collection("entrenos");

  return {
    async porTipo(userId: string): Promise<MarcaDTO[]> {
      return col
        .aggregate<MarcaDTO>([
          { $match: { userId } },
          { $group: { _id: "$tipo", minutos: { $max: "$minutos" }, entrenos: { $sum: 1 } } },
          { $project: { _id: 0, tipo: "$_id", minutos: 1, entrenos: 1 } },
        ])
        .toArray();
    },
  };
}

export type MarcasRepo = ReturnType<typeof crearMarcasRepo>;
```

El servicio:

```ts
// Archivo: src/features/marcas/marcas.service.ts
import type { MarcasRepo } from "./marcas.repo";

export function crearServicioMarcas(repo: Pick<MarcasRepo, "porTipo">) {
  return {
    async listar(userId: string) {
      const marcas = await repo.porTipo(userId);
      return marcas.sort((a, b) => b.minutos - a.minutos);
    },
  };
}
```

La pieza nueva es `server.ts`. Conecta la _feature_ con la base de datos real y es su puerta de entrada. Antes, eso lo hacía un `services/index.ts` común a todas, y por eso había que editarlo cada vez:

```ts
// Archivo: src/features/marcas/server.ts
import { db } from "@/lib/mongo";
import { crearMarcasRepo } from "./marcas.repo";
import { crearServicioMarcas } from "./marcas.service";

export const servicioMarcas = crearServicioMarcas(crearMarcasRepo(db));
```

El componente:

```astro

import type { MarcaDTO } from "../marca.schema";

const { marcas } = Astro.props as { marcas: MarcaDTO[] };

```

Las rutas, delgadas:

## Paso 4: la medida

La misma funcionalidad, en las dos estructuras. En ambas, `astro check` dio 0 errores, y el build y los 72 tests pasaron:

|                          | Por tipo | Por _features_ |
| ------------------------ | -------- | -------------- |
| Archivos                 | 10       | 8              |
| Carpetas                 | 7        | 5              |
| Archivos ajenos editados | 3        | **0**          |

La diferencia de carpetas es modesta, y tres de ellas siguen ahí por necesidad: `pages/`, `pages/api/` y `tests/`. Lo que cambia de verdad es esa última fila. Y se nota al quitar la funcionalidad:

```text
Por features: borrar la carpeta, las 2 rutas y el test  →  build y 71 tests en verde
Por tipo:     borrar los 7 archivos nuevos              →  build 1
  Could not resolve './marcas.service' in src/services/index.ts
```

Por tipo, además tienes que recordar qué tres archivos editaste. **Si puedes borrar una funcionalidad borrando una carpeta, sus límites son reales.** Es una prueba difícil de engañar.

<Callout type="risk">

- **Una _feature_ no significa "sin dependencias".** `resumen` usa los entrenos de `entrenos`, y eso está bien. En esta app es la única dependencia entre _features_. Mientras vaya en una dirección y pase por `server.ts`, no hay problema.
- **La carpeta `features/` no se paga sola.** En un proyecto con unas pocas páginas, ordenar por tipo es más simple. Plantéatelo cuando una funcionalidad empiece a tocar muchas carpetas.

</Callout>

## Paso 5: que los límites se cumplan

Sin una regla, una carpeta es solo una costumbre. Añade esto a `eslint.config.js`, antes de `prettier`:

```js
{
  // Una feature solo ofrece lo público: server.ts, sus esquemas y sus componentes
  files: ["src/**/*.{ts,tsx,astro}"],
  rules: {
    "no-restricted-imports": [
      "error",
      {
        patterns: [
          {
            group: [
              "@/features/*/*",
              "!@/features/*/server",
              "!@/features/*/*.schema",
              "!@/features/*/components",
              "!@/features/*/components/*",
              "../*/*",
              "!../components/*",
              "../../*/*",
            ],
            message: "Eso es interno de la feature: usa server.ts, su esquema o sus componentes.",
          },
        ],
      },
    ],
  },
},
```

Al activarla sobre la app recién migrada, encontró **15 importaciones en 13 archivos** que entraban por la puerta de atrás, como `@/features/auth/sesion`. Se resolvieron ampliando el `server.ts` de cada _feature_. Y ahora un atajo no pasa:

```text
'@/features/entrenos/entrenos.repo' import is restricted from being used by a pattern.
Eso es interno de la feature: usa server.ts, su esquema o sus componentes.
```

Los patrones `../*/*` están ahí por una razón. Con solo los de `@/`, una ruta relativa como `../entrenos/entrenos.repo` se saltaba la regla: dio código 0. Con ellos, dio código 1.

<Callout type="risk">

- **Una regla solo protege si se ejecuta.** Ponla en tu CI (A7), o seguirá siendo una costumbre.
- **Los tests quedan fuera a propósito** (`files: ["src/**"]`): un test sí puede importar un servicio interno para probarlo.
- **Si lo necesitas más estricto,** existen herramientas dedicadas a las dependencias, como `dependency-cruiser`. No se han probado aquí: esta regla cubrió lo que hacía falta.

</Callout>

## Paso 6: _barrel files_, con cuidado

Un _barrel_ es un `index.ts` que reexporta una carpeta. Es cómodo:

```ts
// src/features/entrenos/index.ts
export * from "./entreno.schema";
export * from "./entrenos.repo";
export * from "./entrenos.service";
export * from "./ritmo";
export * from "./server";
export * from "./tipos";
```

Se probó importando una sola constante, `TIPOS_ENTRENO`, desde una isla de React:

| El _barrel_ incluye       | Build | JS del cliente (gzip) | MongoDB en el cliente |
| ------------------------- | ----- | --------------------- | --------------------- |
| Sin _barrel_              | 0     | 126 KB                | No                    |
| Todo, con `server.ts`     | 1     | —                     | —                     |
| Todo, sin `server.ts`     | **0** | **343 KB**            | **Sí**                |
| Esquema y funciones puras | 0     | 126 KB                | No                    |

Lee la tercera fila dos veces. **El build pasó en verde con el controlador de MongoDB en el navegador,** por una línea que parecía inofensiva. Es el caso más peligroso: nada avisa, salvo que vigiles el tamaño (A6).

La segunda fila falló gracias a `astro:env`, no por casualidad:

```text
[ServerOnlyModule] The "astro:env/server" module is only available server-side.
```

Hay otros dos problemas:

**El servidor de desarrollo no descarta nada.** Una carpeta de 300 módulos con _barrel_, usando uno solo:

```text
              peticiones en dev   de esa carpeta   build final
con barrel    331                 301              134 bytes
directo       31                  1                134 bytes
```

En producción, el resultado fue idéntico. En desarrollo, 300 peticiones más. En un Mac tardó entre 625 y 846 ms, frente a 572 y 639 ms: se nota poco aquí, pero crece con el proyecto.

**Los ciclos.** Si un archivo importa desde el _barrel_ de su propia carpeta:

```ts
// a.mjs
import { LIMITE } from "./index.mjs"; // su propio barrel, que reexporta a.mjs y b.mjs
export const DOBLE = LIMITE * 2;
```

```text
ReferenceError: Cannot access 'LIMITE' before initialization
```

Importando desde `./b.mjs`, dio `20`.

Por eso, este proyecto sigue tres reglas:

- **`server.ts` nombra lo que exporta,** sin `export *`. Se lee como una lista de lo público. Por ejemplo, `export { crearNota, listarNotas } from "./notas.server"`.
- **Nada que use el servidor en un archivo que importe el cliente.** `server.ts` no lo importa ninguna isla.
- **Dentro de una _feature_, rutas relativas directas.** Nunca a través de su propia puerta.

## Paso 7: nombres y documentación

**Los nombres son una decisión de equipo, y lo importante es que sean coherentes.** En esta app: componentes en `PascalCase`, y el resto en minúsculas con guiones y un sufijo que dice qué es: `marcas.repo.ts`, `marcas.service.ts` y `marca.schema.ts`. Un sufijo permite buscar y escribir reglas, como la del Paso 5.

Y cuidado con las mayúsculas. Se escribió `Ritmo` en lugar de `ritmo` en un `import`:

```text
Mac (sistema sin distinguir mayúsculas):  build 0
Linux, como tu CI y tu servidor:          build 1
  Could not resolve '../lib/Ritmo'
astro check, en el Mac:                   error ts(1149)
```

Funciona en tu equipo y se rompe al desplegar. `astro check` lo detecta en local: otra razón para tenerlo en tu CI.

**`README`: cómo se usa.** Debe responder a qué es esto, cómo se arranca, cómo se prueba y dónde está cada cosa. Es la puerta de entrada para ti, dentro de seis meses, y para cualquier IA que trabaje en tu código. El de la plataforma donde lees esto sigue siendo el de la plantilla de Astro, y no explica nada del proyecto. Es deuda real, y A8.5 trata de cómo verla y priorizarla.

**ADR: por qué es así.** Un _Architecture Decision Record_ es un archivo corto que guarda una decisión y su motivo, en `docs/adr/`. El código te dice qué se hizo, pero no qué se descartó. Esta es una plantilla:

```markdown
# ADR-0001 · Título en forma de decisión

Estado: aceptado · Fecha: AAAA-MM-DD

## Contexto

Qué problema había y qué limitaciones existen.

## Decisión

Qué se hace, en una o dos frases.

## Alternativas

Qué se descartó, y por qué.

## Consecuencias

Qué mejora, qué empeora y qué hay que vigilar.
```

No se edita un ADR aceptado. Si cambias de idea, escribes otro que lo sustituye: el historial de decisiones es lo valioso.

## Paso 8: monorepo, solo cuando hace falta

Un monorepo con **pnpm workspaces** guarda varios paquetes en un repositorio. Se montó uno con dos apps de Astro que comparten un paquete de esquemas:

```text
apps/web/  apps/panel/  packages/esquemas/  pnpm-workspace.yaml
```

`pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

El paquete se exporta sin compilar, con `"exports": "./src/index.ts"`, y las apps lo declaran con `"@entrenos/esquemas": "workspace:*"`. Funcionó a la primera:

```bash
pnpm --filter web build    # una app
pnpm -r build              # todas
```

La diferencia clara con npm es esta. `web` importó `zod` sin declararlo, una **dependencia fantasma**:

```text
pnpm:  código 1 · failed to resolve import "zod"
npm:   código 0 · funciona por casualidad
```

Con npm, `zod` estaba disponible por ser dependencia de otro paquete. Si ese paquete la quita, tu app se rompe sin haber cambiado. pnpm lo detecta a tiempo.

**¿Cuándo?** Cuando tengas dos cosas que se despliegan por separado y comparten código. Con una sola app, los paquetes solo añaden ceremonia: las _features_ dan casi toda la organización sin coste. Para esta app de entrenamiento, no hace falta.

No se ha probado un monorepo con Docker ni en Vercel, que es donde está buena parte de su coste.

6. Escribe `docs/adr/0001-organizar-por-features.md`:

```markdown
# ADR-0001 · Organizar `src` por features

Estado: aceptado · Fecha: 2026-11-07

## Contexto

Añadir "Mis marcas" tocó 10 archivos en 7 carpetas, y 3 eran de otras
funcionalidades. Las conexiones comunes (`services/index.ts`) se editaban
en cada cambio. No había nada que impidiera saltarse las capas.

## Decisión

Cada funcionalidad vive en `src/features/<nombre>/`. Fuera de ella solo se
usan `server.ts`, sus esquemas y sus componentes. Lo impide ESLint
(`no-restricted-imports`). `pages/` solo contiene rutas.

## Alternativas

- Seguir por tipo: simple, pero cada funcionalidad nueva edita archivos ajenos.
- Monorepo con paquetes: solo hay una app que desplegar; no compensa.
- Un `index.ts` con `export *` por feature: metió MongoDB en el navegador,
  con el build en verde (126 → 343 KB). Descartado.

## Consecuencias

- Mis marcas pasa a 8 archivos, y ninguno ajeno. Borrar una funcionalidad
  es borrar su carpeta, sus rutas y sus tests.
- Cada `server.ts` debe mantenerse a mano.
- Las rutas de `pages/` y los tests siguen fuera de la carpeta.
- Vigilar: que `lib/` no se convierta en un cajón de sastre.
```

Al terminar: `astro check`, ESLint, el build y los tests, todos en verde.

- **Los E2E no se ejecutaron en esta migración,** ni se probó en un servidor. Hazlo tú antes de desplegar.
- **Si tu app es distinta,** cambia la tabla `M`: es lo único específico.
- **Lo que sigue es tu criterio.** `CampoTexto` fue a `components/ui/`, y `limites` a `lib/`. Otra persona podría defender otra cosa, y para eso está el ADR.

<Callout type="mastery">

Una funcionalidad nueva cabe en una carpeta, más sus rutas y sus tests, sin tocar nada ajeno. Puedes demostrarlo borrándola. Una regla de ESLint protege los límites, y un ADR explica por qué existen.

</Callout>

## Resumen

- **Por _features_:** lo que cambia junto, vive junto.
- **Mis marcas:** de 10 archivos a 8, y de 3 archivos ajenos editados a 0.
- **La prueba:** borrar una carpeta y que todo siga en verde.
- **`server.ts`** es la puerta de cada _feature_ y conecta sus piezas.
- **`no-restricted-imports`** encontró 15 atajos, y también debe cubrir las rutas relativas.
- **_Barrels_:** con `export *`, MongoDB llegó al navegador con el build en verde. Y 331 peticiones en dev frente a 31.
- **Mayúsculas:** Mac 0, Linux 1. `astro check` lo detecta.
- **`README`** dice cómo se usa, y un **ADR** dice por qué es así.
- **Monorepo:** para dos cosas que se despliegan por separado. pnpm detecta dependencias fantasma.
- **Migrar con _script_, en una PR aparte,** y con todas las comprobaciones: los tests no vieron el error en `scripts/`.
