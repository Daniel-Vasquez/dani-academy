Marcas una sección como leída: el botón cambia, pero el contador sigue en 0 y el índice tampoco se entera, porque cada isla de React vive aparte con lo que recuerda. Con otra pestaña, un fallo de red u otro dispositivo, empeora. Aquí haces que botón, índice y contador nunca se contradigan: un _store_ que obedece al servidor y un aviso entre pestañas.

**Requisitos:** Nanostores básico (B6.7), actualizaciones optimistas (I2.5), _View Transitions_ (A6) y A8.2. Medido en Chromium con dos pestañas reales, Astro 7.4.7, `nanostores` 1.5.5 y `@nanostores/react` 2.0.1; servidor en el mismo Mac y base **simulada** (un `Map` con esperas fijas). Solo Chromium.

## Paso 1: el problema

**Qué es:** dos islas, cada una con su `useState`, que no saben nada la una de la otra.

**Cómo se usa:**

```bash
mkdir estado && cd estado
npm init -y
npm pkg set type=module scripts.build="astro build" scripts.start="node ./dist/server/entry.mjs"
npm i astro @astrojs/node @astrojs/react react react-dom nanostores @nanostores/react
npm i -D @astrojs/check typescript @types/react
```

`astro.config.mjs`:

```js
import node from "@astrojs/node";
import react from "@astrojs/react";
import { defineConfig } from "astro/config";

export default defineConfig({
  output: "server",
  integrations: [react()],
  adapter: node({ mode: "standalone" }),
});
```

Tras pulsar el botón, la página mostraba:

```text
0 de 3 leídas | ✓ Leída
```

- **Las dos tienen razón según lo que saben:** el dato debe vivir fuera de las islas.

<Callout type="risk">

- **`useState` y `Context` no se cruzan entre islas:** cada isla es un árbol de React aparte.
- **El fallo no se ve con una sola isla:** prueba siempre con dos que muestren el mismo dato.

</Callout>

## Paso 2: el _store_

**Qué es:** Nanostores guarda estado fuera de los componentes. **`atom`** guarda un valor (`.set()`), **`map`** un objeto (`.setKey()`) y **`computed`** deriva un valor de otro _store_.

**Cómo se usa:** lo esencial, en `src/stores/progreso.ts`:

```ts
import { atom, computed, map } from "nanostores";

export const $leidas = map<Record<string, boolean>>({});
export const $totalLeidas = computed($leidas, (l) => Object.values(l).filter(Boolean).length);
export const $aviso = atom("");
```

- **El total no se guarda, se calcula:** dos números que no existen por separado no pueden contradecirse. Con `@nanostores/react`, 1,5 KB con gzip.

Las secciones y la «base de datos», que hará de registro central:

```ts
// Archivo: src/lib/secciones.ts
export const secciones = [
  { id: "B1-1", titulo: "Qué es TypeScript" },
  { id: "B1-2", titulo: "Tipos básicos" },
  { id: "B1-3", titulo: "Funciones" },
];
```

```ts
// Archivo: src/lib/datos.ts
// Simula una base de datos: es la fuente de verdad, y vive en el servidor
export const ajustes = { lectura: 20, escrituraPut: 20, escrituraDelete: 20, fallo: false };

const espera = (ms: number) => new Promise((resuelve) => setTimeout(resuelve, ms));
const leidas = new Map<string, Set<string>>();

export async function leerProgreso(usuario: string) {
  await espera(ajustes.lectura);
  return Object.fromEntries([...(leidas.get(usuario) ?? [])].map((id) => [id, true]));
}

export async function guardar(usuario: string, seccionId: string, leida: boolean) {
  await espera(leida ? ajustes.escrituraPut : ajustes.escrituraDelete);
  if (ajustes.fallo) throw new Error("No se pudo guardar");
  const conjunto = leidas.get(usuario) ?? new Set<string>();
  if (leida) conjunto.add(seccionId);
  else conjunto.delete(seccionId);
  leidas.set(usuario, conjunto);
}
```

La API. `src/pages/api/progreso/index.ts`:

```ts
// Archivo: src/pages/api/progreso/index.ts
import type { APIRoute } from "astro";
import { leerProgreso } from "../../../lib/datos";

export const GET: APIRoute = async ({ cookies }) => {
  const usuario = cookies.get("sesion")?.value;
  if (!usuario) return new Response(null, { status: 401 });
  const cabeceras = { "Content-Type": "application/json", "Cache-Control": "private, no-store" };
  return new Response(JSON.stringify(await leerProgreso(usuario)), { headers: cabeceras });
};
```

`src/pages/api/progreso/[id].ts`:

```ts
// Archivo: src/pages/api/progreso/[id].ts
import type { APIRoute } from "astro";
import { guardar } from "../../../lib/datos";

const cambiar =
  (leida: boolean): APIRoute =>
  async ({ params, cookies }) => {
    const usuario = cookies.get("sesion")?.value;
    if (!usuario) return new Response(null, { status: 401 });
    try {
      await guardar(usuario, params.id!, leida);
      return new Response(null, { status: 204 });
    } catch {
      return new Response(null, { status: 503 });
    }
  };

export const PUT = cambiar(true);
export const DELETE = cambiar(false);
```

<Callout type="risk">

- **El servidor es la fuente de verdad, el _store_ una copia de trabajo:** nunca al revés.
- **Guardar un total aparte invita a la contradicción:** lo que se puede calcular, con `computed`.

</Callout>

## Paso 3: el primer render

**Qué es:** las islas se renderizan primero en el servidor, donde el _store_ está vacío.

**Cómo se usa:** sin más cuidado, con una sección leída:

```text
HTML:       0 de 3 leídas
navegador:  1 de 3 leídas
consola:    Minified React error #418
```

- **Error de hidratación:** el HTML dice una cosa y React otra. Cada isla recibe del servidor su valor inicial y `useStore` lo usa con `ssr`. El botón importa `cambiar` (Paso 4), así que aún no compila:

```tsx
// Archivo: src/components/ContadorLeidas.tsx
import { useStore } from "@nanostores/react";
import { $totalLeidas } from "../stores/progreso";

export default function ContadorLeidas({ inicial, total }: { inicial: number; total: number }) {
  const leidas = useStore($totalLeidas, { ssr: () => inicial });
  return (
    <p id="contador">
      {leidas} de {total} leídas
    </p>
  );
}
```

<Callout type="risk">

- **Nunca escribas en un _store_ desde el servidor:** es un módulo compartido por todas las peticiones. Con `$leidas.set(leidas)` en la página, **Bob recibió el contador de Ana en 3 de 20 intentos** con dos peticiones casi a la vez. A solas no se ve. Pasa los datos por _props_.
- **`<script type="application/json">` con `set:html` no se escapa:** aquí hay claves propias y booleanos; con texto de usuarios, un `</script>` rompería la página. Sustituye `<` por `\u003c` antes (no medido).
- **`BroadcastChannel` también existe en Node:** sin `enNavegador`, se crearía uno en el servidor.

</Callout>

## Paso 4: el servidor manda

**Qué es:** cada cambio en cuatro pasos: pintar, enviar, volver a preguntar y avisar. La pantalla responde al momento, pero queda lo que dice el servidor.

**Cómo se usa:** sustituye `src/stores/progreso.ts`:

```ts
// Archivo: src/stores/progreso.ts
import { atom, computed, map } from "nanostores";

export type Leidas = Record<string, boolean>;

export const $leidas = map<Leidas>({});
export const $totalLeidas = computed($leidas, (l) => Object.values(l).filter(Boolean).length);
export const $aviso = atom("");

// Este módulo también se carga en el servidor, donde no hay pestañas ni documento
const enNavegador = typeof document !== "undefined";
const canal = enNavegador ? new BroadcastChannel("progreso") : null;

let confirmado: Leidas = {}; // lo último que ha dicho el servidor
let pendientes = 0;
let cola: Promise<unknown> = Promise.resolve();

/** Trae la verdad del servidor, y solo la pinta si no quedan cambios por confirmar */
export async function recargar() {
  try {
    const r = await fetch("/api/progreso");
    if (r.ok) confirmado = await r.json();
  } catch {
    // Sin red: se conserva lo último confirmado
  }
  if (pendientes === 0) $leidas.set(confirmado);
}

/** Copia en el store el estado que el servidor puso en el HTML de esta página */
function sembrar() {
  const nodo = document.getElementById("leidas-iniciales");
  if (!nodo?.textContent) return;
  confirmado = JSON.parse(nodo.textContent);
  $leidas.set(confirmado);
}

export function cambiar(seccionId: string, leida: boolean) {
  $aviso.set("");
  $leidas.setKey(seccionId, leida); // se pinta ya
  pendientes += 1;
  // Uno detrás de otro: si no, un DELETE rápido puede adelantar a un PUT lento
  cola = cola.then(async () => {
    const metodo = leida ? "PUT" : "DELETE";
    const r = await fetch(`/api/progreso/${seccionId}`, { method: metodo }).catch(() => null);
    pendientes -= 1;
    if (!r?.ok) $aviso.set("No se pudo guardar");
    await recargar(); // si ha fallado, esto deshace el cambio
    if (r?.ok) canal?.postMessage("cambio"); // nunca se avisa de algo sin confirmar
  });
  return cola;
}

if (enNavegador) {
  sembrar();
  canal?.addEventListener("message", recargar);
  document.addEventListener("astro:after-swap", sembrar);
  document.addEventListener("visibilitychange", () => {
    if (document.visibilityState === "visible") recargar();
  });
}
```

Con la base fallando, el botón pasó por:

```text
✓ Leída  →  Marcar como leída  +  "No se pudo guardar"
```

- **Sin red, igual:** se deshizo y avisó, y el siguiente clic con red se guardó.

**La cola no es un adorno.** Con un `PUT` de 600 ms y un `DELETE` de 10 ms, dos clics seguidos («marcar» y «desmarcar»); el `DELETE` adelantó al `PUT`:

| Versión                 | Pantalla | Servidor | Resultado                    |
| ----------------------- | -------- | -------- | ---------------------------- |
| Sin cola y sin recargar | Sin leer | Leída    | ✗ Se contradicen             |
| Sin cola, con recargar  | Leída    | Leída    | ✗ Coinciden, pero no era eso |
| Con cola                | Sin leer | Sin leer | ✓                            |

- **Volver a preguntar arregla la contradicción, no el dato:** solo la cola respeta lo pedido. Con cinco clics, `10101`, y pantalla y servidor iguales.

<Callout type="risk">

- **`pendientes` evita un parpadeo:** la respuesta de `recargar` aún no refleja un cambio en camino y lo pisaría.
- **El `catch` dentro de la cola es obligatorio:** una promesa rota detiene `cola.then` y ningún clic posterior llega. Por eso `fetch` lleva `.catch` y `recargar`, `try`.
- **Cada cambio cuesta un `GET` más:** con un solo campo, usa la respuesta del `PUT`.

</Callout>

## Paso 5: otra pestaña

**Qué es:** `BroadcastChannel` envía mensajes entre pestañas del mismo origen.

**Cómo se usa:** dos líneas de `progreso.ts`:

```ts
canal?.postMessage("cambio"); // en la pestaña que cambia
canal?.addEventListener("message", recargar); // en las demás
```

- **El mensaje solo avisa:** cada pestaña pregunta al servidor. La segunda se actualizó a los 71 ms del clic con un `GET`; el canal tardó 1 ms.

| Aspecto                         | `BroadcastChannel` | Evento `storage` |
| ------------------------------- | ------------------ | ---------------- |
| Latencia medida                 | 1 ms o menos       | 1 ms o menos     |
| Llega a la propia pestaña       | No                 | No               |
| Mismo valor dos veces           | Se reciben las dos | Solo la primera  |
| Puede enviar objetos            | Sí                 | Solo texto       |
| Deja algo guardado              | No                 | Sí               |
| Llega a otro perfil o navegador | No                 | No               |

- **`BroadcastChannel` para avisar, `storage` para guardar un valor:** aquí el dato está en el servidor.

**Avisar antes de confirmar,** con el mensaje antes del `PUT` y el servidor fallando:

```text
pestaña A: 0 de 3 leídas
pestaña B: 1 de 3 leídas    ← se quedó con algo que nunca ocurrió
servidor:  {}
```

- **Por eso el aviso va tras `if (r?.ok)`.**

**Avisar cada vez que cambia el _store_:**

```ts
$leidas.listen(() => canal?.postMessage("cambio")); // NO
```

- **43 mensajes por segundo sin final:** aviso, `recargar`, cambio, aviso. La pantalla se veía bien; solo lo descubre la pestaña Network.

<Callout type="risk">

- **El canal no llega a pestañas cerradas ni a otros dispositivos:** las nuevas leen del servidor.
- **Mismo origen es protocolo, dominio y puerto:** `www.` y sin `www` son canales distintos.
- **Una isla `client:visible` sin hidratar muestra HTML antiguo,** fuera de la pantalla; al llegar, salió correcta.

</Callout>

## Paso 6: otro dispositivo

**Qué es:** ningún canal avisa en el portátil de un cambio hecho en el móvil. Lo barato es preguntar al volver.

**Cómo se usa:**

```ts
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "visible") recargar();
});
```

Un cambio simulado desde fuera, y después el evento:

```text
al abrir:           0 de 3 leídas
tras el cambio:     0 de 3 leídas    ← aún sin enterarse
al volver a la pestaña: 1 de 3 leídas
```

- **El evento se disparó a mano** (el navegador automatizado no cambió de pestaña de verdad). Sin _WebSockets_, una pantalla va por detrás un rato: aceptable, siempre que no se quede así.

<Callout type="risk">

- **`visibilitychange` no avisa con la pestaña visible:** si dos personas trabajan a la vez sobre lo mismo, necesitarás _WebSockets_ o sondeo.
- **Cada vuelta a la pestaña es un `GET`:** barato aquí; con datos pesados, limita su frecuencia.

</Callout>

## Paso 7: con _View Transitions_

**Qué es:** con `<ClientRouter />`, navegar no recarga la página y **el módulo del _store_ no vuelve a ejecutarse:** sigue vivo, con una trampa.

**Cómo se usa:** cada página trae datos nuevos, pero `sembrar()` solo corría al inicio. Sin `astro:after-swap` y con un cambio desde fuera:

```text
tras navegar: 0 de 3 leídas    ← HTML nuevo, store antiguo
al recargar:  1 de 3 leídas
```

Con este _listener_, correcto desde la navegación:

```ts
document.addEventListener("astro:after-swap", sembrar);
```

`transition:persist` conserva una isla entre páginas, con su estado:

| Isla                                            | Tras navegar                        |
| ----------------------------------------------- | ----------------------------------- |
| `<NotaRapida client:load />`                    | Texto perdido                       |
| `<NotaRapida client:load transition:persist />` | Conserva `hola`                     |
| `<BotonLeida transition:persist />`             | Correcto: recibe las _props_ nuevas |
| `<BotonLeida … transition:persist-props />`     | ✗ Sigue siendo el de la sección 1   |

- **La última fila es una contradicción real:** en la sección 2 decía `✓ Leída` y al pulsarlo **desmarcó la sección 1**. `persist-props` conserva las _props_ antiguas: solo para lo que no depende de la página, como un reproductor.

<Callout type="risk">

- **Sin `astro:after-swap`, el HTML es nuevo y el _store_ viejo:** vuelve a sembrar en cada navegación.
- **`transition:persist-props` mezcla páginas:** pruébalo navegando y pulsando, no solo mirando.

</Callout>

## Paso 8: la plataforma donde lees esto

**Qué es:** esta plataforma comparte estado sin Nanostores: `MarkAsReadButton` lanza `da:section-read` en `document` y un `<script>` del índice lateral lo escucha. Para un solo aviso es buena solución: sin dependencias y sin React en el índice.

**Cómo se usa:** un `CustomEvent` no sale de la pestaña. En local, dos pestañas en la misma sección:

```text
tras marcar en A:  A: Leído, 1/2    B: Marcar como leído, 0/2
```

- **B queda atrás hasta navegar o recargar,** sin romperse: pulsar otra vez repite un `PUT` sin efecto y acaba en `Leído, 1/2`. Es una contradicción consciente; si importase, bastaría un `BroadcastChannel` en ese evento.

<Callout type="risk">

- **Un evento en `document` acopla por un nombre de texto:** una errata en `da:section-read` no da error, simplemente nadie escucha.
- **Lo que vale para un aviso no escala:** con varios datos compartidos, un _store_ es más fácil de seguir.

</Callout>

| -------------------------- | ------------------------------------------- |

<Callout type="mastery">

Dos islas nunca muestran estados contradictorios, porque ninguna guarda su propia versión del dato: todas leen un _store_, y el _store_ obedece al servidor. Sabes qué ocurre con un fallo, con dos clics, con otra pestaña y tras navegar, porque lo has provocado.

</Callout>

## Resumen

- **`atom`, `map` y `computed`:** lo derivado se calcula.
- **`useStore` con `ssr`** evita el error #418; **nunca `.set()` en el servidor** (Bob vio a Ana 3 de 20 veces).
- **Pintar, enviar, volver a preguntar y avisar,** con una cola: sin ella, un `DELETE` adelantó a un `PUT`.
- **`BroadcastChannel` avisa** solo lo confirmado, nunca desde `.listen()` (43 por segundo).
- **`visibilitychange`** para otros dispositivos.
- **`ClientRouter`:** vuelve a sembrar en `astro:after-swap`; `persist-props` desmarcó la sección equivocada.
