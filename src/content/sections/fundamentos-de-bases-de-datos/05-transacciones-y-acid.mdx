Una transferencia resta de una cuenta y suma en otra: si el servidor se cae entre las dos, el dinero desaparece. Aquí lo provocas con un banco de juguete en SQLite, lo arreglas con **transacciones** y compruebas cada letra de **ACID** con un experimento.

**Requisitos:** el proyecto `db-lab` de las secciones anteriores.

## Paso 1: una transferencia que se queda a medias

**Qué es:** una **transacción** agrupa varias operaciones: o se confirman **todas** con `COMMIT`, o se descartan **todas**, con `ROLLBACK` o si la conexión se corta antes del `COMMIT`.

**Cómo se usa:** crea `banco.sql` en `db-lab`.

```sql
-- Archivo: banco.sql
-- Dos cuentas con 100 cada una (se puede ejecutar varias veces)
DROP TABLE IF EXISTS cuentas;
CREATE TABLE cuentas (
  id INTEGER PRIMARY KEY,
  titular TEXT NOT NULL,
  saldo INTEGER NOT NULL CHECK (saldo >= 0)
);
INSERT INTO cuentas (id, titular, saldo) VALUES (1, 'Dani', 100), (2, 'Ana', 100);
```

Simula una transferencia de 30 de Dani a Ana que se corta tras el primer `UPDATE`: ejecuta solo la resta y cierra la sesión.

```bash
sqlite3 banco.db < banco.sql
sqlite3 banco.db
```

```sql
UPDATE cuentas SET saldo = saldo - 30 WHERE id = 1;
.quit
```

```bash
sqlite3 -box banco.db "SELECT titular, saldo FROM cuentas; SELECT SUM(saldo) AS total FROM cuentas;"
```

```text
┌─────────┬───────┐
│ titular │ saldo │
├─────────┼───────┤
│ Dani    │ 70    │
│ Ana     │ 100   │
└─────────┴───────┘
┌───────┐
│ total │
├───────┤
│ 170   │
└───────┘
```

- **Han desaparecido 30:** cada `UPDATE` se confirmó por separado, y el segundo nunca llegó.

Ahora dentro de una transacción:

```bash
sqlite3 banco.db < banco.sql
sqlite3 banco.db
```

```sql
BEGIN;
UPDATE cuentas SET saldo = saldo - 30 WHERE id = 1;
SELECT saldo FROM cuentas WHERE id = 1;
.quit
```

```text
70
```

Dentro, Dani ya tiene 70. Cierra la sesión **sin `COMMIT`** y míralo desde fuera:

```bash
sqlite3 -box banco.db "SELECT titular, saldo FROM cuentas; SELECT SUM(saldo) AS total FROM cuentas;"
```

```text
┌─────────┬───────┐
│ titular │ saldo │
├─────────┼───────┤
│ Dani    │ 100   │
│ Ana     │ 100   │
└─────────┴───────┘
┌───────┐
│ total │
├───────┤
│ 200   │
└───────┘
```

- **Como si nada hubiera pasado.** La transferencia completa se escribe así:

```sql
BEGIN;
UPDATE cuentas SET saldo = saldo - 30 WHERE id = 1;
UPDATE cuentas SET saldo = saldo + 30 WHERE id = 2;
COMMIT;
```

<Callout type="risk">

- **Un error dentro de una transacción no la deshace sola.** Recrea las cuentas y transfiere 500 que Dani no tiene, sumando primero a Ana:

  ```sql
    .mode box
    BEGIN;
    UPDATE cuentas SET saldo = saldo + 500 WHERE id = 2;
    UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1;
    SELECT titular, saldo FROM cuentas;
    ROLLBACK;
  ```

  ```text
    Runtime error near line 4: CHECK constraint failed: saldo >= 0 (19)
    ┌─────────┬───────┐
    │ titular │ saldo │
    ├─────────┼───────┤
    │ Dani    │ 100   │
    │ Ana     │ 600   │
    └─────────┴───────┘
  ```

  El segundo `UPDATE` falló, pero **el primero sigue aplicado**: Ana tiene 600. Con `COMMIT` habrías **creado 500 de la nada**. Ante un error, `ROLLBACK`, en el `catch` (Paso 2).

- **Una transacción de escritura abierta bloquea a los demás** (Paso 3). Nunca la dejes abierta esperando algo lento, como una API o al usuario.

</Callout>

## Paso 2: los experimentos de ACID en código

**Qué es:** cuatro experimentos en Node, uno por garantía, con el patrón de cualquier transacción: `BEGIN`, las operaciones, `COMMIT`, y `ROLLBACK` en el `catch`.

**Cómo se usa:** crea `transacciones.js` en `db-lab`.

```js
// Archivo: transacciones.js
// Atomicidad, aislamiento y durabilidad con una transferencia entre dos cuentas
import { rmSync } from "node:fs";
import { spawnSync } from "node:child_process";
import { DatabaseSync } from "node:sqlite";

const ARCHIVO = "banco.db";

function crearBanco() {
  rmSync(ARCHIVO, { force: true });
  const db = new DatabaseSync(ARCHIVO);
  db.exec(`
    CREATE TABLE cuentas (
      id INTEGER PRIMARY KEY,
      titular TEXT NOT NULL,
      saldo INTEGER NOT NULL CHECK (saldo >= 0)
    );
    INSERT INTO cuentas (id, titular, saldo) VALUES (1, 'Dani', 100), (2, 'Ana', 100);
  `);
  return db;
}

const estado = (db) =>
  db.prepare("SELECT titular, saldo FROM cuentas ORDER BY id").all().map((c) => `${c.titular} ${c.saldo}`).join(" · ") +
  ` · total ${db.prepare("SELECT SUM(saldo) AS t FROM cuentas").get().t}`;

// ─── 1. ATOMICIDAD: un fallo entre los dos UPDATE ───
function transferir(db, origen, destino, cantidad, { fallarAMitad }) {
  db.prepare("UPDATE cuentas SET saldo = saldo - ? WHERE id = ?").run(cantidad, origen);
  if (fallarAMitad) throw new Error("El servidor se cayó entre los dos UPDATE");
  db.prepare("UPDATE cuentas SET saldo = saldo + ? WHERE id = ?").run(cantidad, destino);
}

let db = crearBanco();
try {
  transferir(db, 1, 2, 30, { fallarAMitad: true });
} catch (error) {
  console.log(`Sin transacción: ${error.message}`);
}
console.log(`  → ${estado(db)}`);
db.close();

db = crearBanco();
try {
  db.exec("BEGIN");
  transferir(db, 1, 2, 30, { fallarAMitad: true });
  db.exec("COMMIT");
} catch (error) {
  db.exec("ROLLBACK");
  console.log(`Con transacción: ${error.message} → ROLLBACK`);
}
console.log(`  → ${estado(db)}`);

// La consistencia también la protegen las restricciones: no se puede quedar en negativo
try {
  db.exec("BEGIN");
  transferir(db, 1, 2, 500, { fallarAMitad: false });
  db.exec("COMMIT");
} catch (error) {
  db.exec("ROLLBACK");
  console.log(`Transferencia de 500: ${error.message} → ROLLBACK`);
}
console.log(`  → ${estado(db)}`);
db.close();

// ─── 2. AISLAMIENTO: dos conexiones que leen, calculan y escriben a la vez ───
db = crearBanco();
const cajeroA = new DatabaseSync(ARCHIVO);
const cajeroB = new DatabaseSync(ARCHIVO);
const leerSaldo = (conexion) => conexion.prepare("SELECT saldo FROM cuentas WHERE id = 1").get().saldo;
const escribirSaldo = (conexion, saldo) => conexion.prepare("UPDATE cuentas SET saldo = ? WHERE id = 1").run(saldo);

const saldoVistoPorA = leerSaldo(cajeroA); // A lee 100
const saldoVistoPorB = leerSaldo(cajeroB); // B lee 100, antes de que A escriba
escribirSaldo(cajeroA, saldoVistoPorA - 30); // A retira 30 → 70
escribirSaldo(cajeroB, saldoVistoPorB - 50); // B retira 50 → 50, ¡pisando a A!
console.log(`Dos retiradas (30 y 50) leyendo y escribiendo: saldo de Dani = ${leerSaldo(db)} (debería ser 20)`);

escribirSaldo(db, 100);
const retirar = (conexion, cantidad) =>
  conexion.prepare("UPDATE cuentas SET saldo = saldo - ? WHERE id = 1 AND saldo >= ?").run(cantidad, cantidad).changes;
retirar(cajeroA, 30);
retirar(cajeroB, 50);
const tercera = retirar(cajeroA, 50); // ya no hay saldo suficiente
console.log(`Tres retiradas atómicas (30, 50 y 50): saldo = ${leerSaldo(db)}, la tercera ${tercera ? "se aplicó" : "se rechazó"}`);

// Mientras una conexión tiene una transacción de escritura abierta, la otra no puede escribir
cajeroA.exec("BEGIN IMMEDIATE");
try {
  retirar(cajeroB, 10);
} catch (error) {
  console.log(`El cajero B intenta escribir durante la transacción de A: ${error.message}`);
}
cajeroA.exec("ROLLBACK");
cajeroA.close();
cajeroB.close();
db.close();

// ─── 3. DURABILIDAD: el proceso muere de golpe, antes y después del COMMIT ───
db = crearBanco();
db.close();
for (const confirmar of [false, true]) {
  const hijo = `
    import { DatabaseSync } from "node:sqlite";
    const db = new DatabaseSync("${ARCHIVO}");
    db.exec("BEGIN");
    db.exec("INSERT INTO cuentas (titular, saldo) VALUES ('Luis', 50)");
    ${confirmar ? 'db.exec("COMMIT");' : ""}
    process.kill(process.pid, "SIGKILL"); // muerte súbita: sin cerrar nada
  `;
  spawnSync(process.execPath, ["--input-type=module", "-e", hijo]);
  db = new DatabaseSync(ARCHIVO);
  const luis = db.prepare("SELECT COUNT(*) AS n FROM cuentas WHERE titular = 'Luis'").get().n;
  console.log(`Proceso matado ${confirmar ? "después" : "antes"} del COMMIT: ¿existe la cuenta de Luis? ${luis ? "sí" : "no"}`);
  db.close();
}

// ─── 4. Rendimiento: 10 000 inserciones con y sin transacción ───
db = crearBanco();
const insertar = db.prepare("INSERT INTO cuentas (titular, saldo) VALUES (?, ?)");
let inicio = performance.now();
for (let i = 0; i < 10_000; i++) insertar.run(`Cliente ${i}`, 10);
const sinTransaccion = performance.now() - inicio;
inicio = performance.now();
db.exec("BEGIN");
for (let i = 0; i < 10_000; i++) insertar.run(`Cliente ${i}`, 10);
db.exec("COMMIT");
const conTransaccion = performance.now() - inicio;
console.log(`10 000 inserciones: ${Math.round(sinTransaccion)} ms sin transacción · ${Math.round(conTransaccion)} ms con transacción`);
db.close();
rmSync(ARCHIVO, { force: true });
```

```bash
node transacciones.js
```

```text
Sin transacción: El servidor se cayó entre los dos UPDATE
  → Dani 70 · Ana 100 · total 170
Con transacción: El servidor se cayó entre los dos UPDATE → ROLLBACK
  → Dani 100 · Ana 100 · total 200
Transferencia de 500: CHECK constraint failed: saldo >= 0 → ROLLBACK
  → Dani 100 · Ana 100 · total 200
Dos retiradas (30 y 50) leyendo y escribiendo: saldo de Dani = 50 (debería ser 20)
Tres retiradas atómicas (30, 50 y 50): saldo = 20, la tercera se rechazó
El cajero B intenta escribir durante la transacción de A: database is locked
Proceso matado antes del COMMIT: ¿existe la cuenta de Luis? no
Proceso matado después del COMMIT: ¿existe la cuenta de Luis? sí
10 000 inserciones: 2695 ms sin transacción · 3 ms con transacción
```

El patrón del bloque 1:

```js
try {
  db.exec("BEGIN");
  transferir(db, 1, 2, 30, { fallarAMitad: false }); // las operaciones que van juntas
  db.exec("COMMIT");
} catch (error) {
  db.exec("ROLLBACK"); // ante cualquier error, se descarta todo
}
```

<Callout type="risk">

- **El `ROLLBACK` va en el `catch`, siempre.** Sin él, la transacción queda abierta, la siguiente operación entra en ella y la base de datos queda bloqueada para los demás.
- **Los tiempos dependen de tu disco:** las 10 000 inserciones sin transacción tardan entre uno y varios segundos. La proporción no cambia.

</Callout>

## Paso 3: las cuatro letras de ACID

**Qué es:** las cuatro garantías de una transacción. Cada una se ve en un bloque del resultado.

- **A, atomicidad: todo o nada** (bloque 1). Sin transacción, el fallo dejó el total en 170; con ella, el `ROLLBACK` lo dejó en 200.
- **C, consistencia: solo estados válidos** (tercer resultado). La transferencia de 500 violaba `CHECK (saldo >= 0)` y se rechazó. La consistencia la definen **tus reglas**; la transacción impide confirmar un estado que las incumpla.
- **D, durabilidad: lo confirmado sobrevive** (bloque 3). Un proceso hijo se mata con `SIGKILL`: antes del `COMMIT`, Luis no existe; después, sí. Un `COMMIT` promete que el dato ya está en disco.

**I, aislamiento: las transacciones simultáneas no se pisan** (bloque 2), el más importante a diario:

- **Leer y escribir desde dos cajeros:** los dos leen 100, calculan en JavaScript y escriben. El segundo **pisa** al primero: 50 en vez de 20. Es la escritura perdida de B4.1 con una base de datos de verdad, porque el error está en **calcular fuera** de ella.
- **Retiradas atómicas:** `UPDATE cuentas SET saldo = saldo - ? WHERE id = 1 AND saldo >= ?` lee, comprueba y escribe **en una sola operación**. La tercera retirada no encuentra fila que cumpla `saldo >= 50`, `changes` es 0 y se rechaza.
- **`database is locked`:** con una transacción de escritura abierta (`BEGIN IMMEDIATE`), nadie más escribe. SQLite aísla con un solo escritor; PostgreSQL y MongoDB permiten varios, con el mismo principio.

**El bloque 4:** 10 000 inserciones tardan unos 2700 ms sin transacción y **3 ms** con ella. Sin transacción, cada `INSERT` es la suya, y la durabilidad obliga a llegar al disco **cada vez**. Por eso `indices.js` (B4.4) insertaba entre `BEGIN` y `COMMIT`.

<Callout type="risk">

- **Leer → calcular en JavaScript → escribir es la primera fuente de errores de concurrencia,** en SQL y en MongoDB. Calcula en la base de datos (`saldo - ?`, `{ $inc: { saldo: -30 } }`), con la condición en el filtro (`AND saldo >= ?`).
- **`database is locked` en producción** suele ser una transacción larga o sin `ROLLBACK`. `PRAGMA busy_timeout = 5000` espera hasta 5 segundos, pero no arregla la causa.
- **La durabilidad tiene matices:** depende del disco y de `PRAGMA synchronous`. Atlas, además, copia el dato a varios servidores antes de confirmar.

</Callout>

## Paso 4: transacciones en MongoDB y en esta plataforma

**Qué es:** en MongoDB, **una operación sobre un solo documento siempre es atómica**: `updateOne` con `$set`, `$inc` y `$push` se aplica entera o no se aplica. Las transacciones multidocumento existen (requieren un _replica set_, como Atlas), pero son más lentas y tienen límites: se usan cuando no hay otra opción.

Esta plataforma **no usa transacciones multidocumento**. Cada operación toca un solo documento:

- **Marcar una sección** es un _upsert_ sobre `section_progress`, con el índice único `{ userId, sectionId }`: dos clics simultáneos no crean dos lecturas (el `ON CONFLICT DO NOTHING` de B4.3).
- **Enviar una evaluación** inserta **un** documento en `quiz_attempts` con todo el resultado dentro.
- **Los límites de peticiones** (`rate_limits`) suman con `$inc` en un _upsert_, sin leer antes.

Que cada operación importante sea **atómica por sí misma** es más simple y más rápido que coordinar transacciones.

## Paso 5: el teorema CAP, sin humo

**Qué es:** con la base de datos en **varios servidores**, como tu clúster de Atlas, durante un fallo de red solo puedes garantizar dos de estas tres:

- **C (_Consistency_):** todas las lecturas ven el último dato escrito. No es la "C" de ACID.
- **A (_Availability_):** todo servidor que funciona responde siempre.
- **P (_Partition tolerance_):** sigue funcionando aunque se corte la red entre servidores.

**P no es opcional,** porque las redes fallan. La elección real es qué hacer **cuando** se corta:

- **CP:** el servidor aislado deja de aceptar escrituras. Algunos ven errores, pero nadie lee datos viejos. Es MongoDB por defecto: solo el **primario** escribe, y deja de serlo si queda aislado.
- **AP:** todos responden, algunos con datos desactualizados un tiempo. Lo eligen DynamoDB o Cassandra en ciertos modos, aceptable para un contador de "me gusta".

En el día a día: **leer de una réplica secundaria, o de una caché, puede dar un dato algo antiguo.** El _driver_ de MongoDB lee del primario por defecto.

<Callout type="risk">

- **CAP no dice que NoSQL no sea consistente:** MongoDB por defecto es CP. Habla de lo que pasa durante un fallo de red.
- **La caché es una réplica más:** cuando la CDN de Vercel sirve una página de hace 60 segundos (B3.5), eliges disponibilidad frente a consistencia.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Reproduce en `sqlite3` el Paso 1 completo: la transferencia que se queda a medias **sin** transacción y **con** transacción, y comprueba el total después de cada una.
2. Modifica el bloque 2 de `transacciones.js` para que las dos retiradas que leen y escriben lo hagan **dentro de una transacción** (`BEGIN IMMEDIATE` … `COMMIT`) en cada cajero, una detrás de otra. ¿Sigue perdiéndose una retirada? ¿Por qué?
3. Revisa una de tus apps (el Planificador 2026 o la de entrenamiento) y escribe qué operaciones deberían ser atómicas y cómo lo conseguirías en MongoDB.

</Callout>

Solución del punto 2. Sustituye las cuatro líneas de las "dos retiradas leyendo y escribiendo" por:

```js
cajeroA.exec("BEGIN IMMEDIATE");
const saldoVistoPorA = leerSaldo(cajeroA); // A lee 100 dentro de su transacción
escribirSaldo(cajeroA, saldoVistoPorA - 30); // A escribe 70
cajeroA.exec("COMMIT");

cajeroB.exec("BEGIN IMMEDIATE"); // B no puede empezar hasta que A termine
const saldoVistoPorB = leerSaldo(cajeroB); // B lee 70, el valor ya confirmado por A
escribirSaldo(cajeroB, saldoVistoPorB - 50); // B escribe 20
cajeroB.exec("COMMIT");
console.log(`Dos retiradas (30 y 50) con transacciones: saldo de Dani = ${leerSaldo(db)} (debería ser 20)`);
```

```text
Dos retiradas (30 y 50) con transacciones: saldo de Dani = 20 (debería ser 20)
```

- **Ya no se pierde nada:** `BEGIN IMMEDIATE` reserva la escritura desde el principio, así que B lee **después** de que A confirme. Si lo intentara a la vez, recibiría `database is locked`.
- **Aun así, `UPDATE … WHERE saldo >= ?` es mejor:** no necesita transacción, no bloquea y no permite saldos negativos.

Solución del punto 3, para el Planificador 2026:

| Operación                                                    | ¿Atómica?                         | Cómo en MongoDB                                                                                                                                  |
| ------------------------------------------------------------ | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Marcar una tarea como hecha                                  | Sí, pero es un solo documento     | `updateOne({ _id }, { $set: { hecha: true, hechaEn: new Date() } })`                                                                             |
| Completar una subtarea y recalcular el progreso de la tarea  | Sí: las dos cosas juntas          | Subtareas anidadas en la tarea: un solo `updateOne` con `$set` sobre la subtarea (`subtareas.$.hecha`) y `$inc` sobre el contador de completadas |
| Mover una tarea de una lista a otra con contadores por lista | Sí: restar en una y sumar en otra | Dos documentos: transacción de MongoDB (`session.withTransaction`), o mejor, no guardar contadores y calcularlos al leer                         |
| Crear un usuario con sus categorías por defecto              | Sí                                | Categorías dentro del documento del usuario: un solo `insertOne`                                                                                 |
| Registrar cuántas veces se abre la app                       | No hace falta transacción         | `$inc` atómico sobre un contador                                                                                                                 |

<Callout type="risk">

- **Con un `BEGIN` normal, las dos conexiones leen a la vez,** y al escribir se bloquean mutuamente: ninguna puede confirmar. Para leer → escribir en SQLite, `BEGIN IMMEDIATE`.
- **Un contador guardado es una promesa de mantenerlo al día** en cada operación. Calcularlo al leer, con un buen índice, suele ser más seguro.

</Callout>

<Callout type="mastery">

Reconoces en tus apps qué operaciones deberían ser atómicas: las que hacen varias escrituras que solo tienen sentido juntas. Sabes protegerlas con `BEGIN`/`COMMIT`/`ROLLBACK` (con el `ROLLBACK` en el `catch`), evitas el patrón leer → calcular → escribir con operaciones atómicas (`saldo - ?`, `$inc`) y explicas qué garantiza cada letra de ACID.

</Callout>

## Resumen

- `COMMIT` confirma todo; `ROLLBACK` o un corte lo descartan todo. Un error no la deshace solo.
- ACID: atomicidad, consistencia, aislamiento y durabilidad.
- Calcula en la base de datos (`saldo - ?`, `$inc`) con la condición en el filtro.
- Una transacción acelera las inserciones en lote: de 2,7 s a 3 ms.
- En MongoDB, un documento es atómico: diseña para tocar uno. CAP: consistencia o disponibilidad ante un fallo de red.
