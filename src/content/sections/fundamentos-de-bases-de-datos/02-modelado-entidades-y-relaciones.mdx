Antes de escribir SQL o MongoDB hay que decidir **qué** se guarda y **cómo se relaciona**. El código se refactoriza en una tarde; los datos de miles de usuarios, no. Aquí modelas esta misma plataforma, desde una hoja de cálculo ingenua hasta un diagrama entidad-relación limpio.

**Requisitos:** el proyecto `db-lab` de B4.1.

## Paso 1: entidades, atributos y claves

**Qué es:** una **entidad** es una "cosa" con identidad propia (usuario, curso, sección); un **atributo**, un dato suyo (`nombre`, `minutos`); la **clave primaria**, lo que identifica **una única** instancia sin repetirse nunca. Una **clave foránea** guarda la clave primaria **de otra entidad**: así se expresa una relación, como el `userId` y el `sectionId` del progreso de esta plataforma.

| Tipo                       | Qué es                                      | Ejemplo en esta plataforma                                   | Ventaja                                 | Riesgo                                                               |
| -------------------------- | ------------------------------------------- | ------------------------------------------------------------ | --------------------------------------- | -------------------------------------------------------------------- |
| **Natural**                | Un dato que ya existe en el mundo real      | `"B1.3"` para una sección; el `email` de un usuario          | Tiene significado: se lee y se entiende | Puede cambiar (el usuario cambia de correo, renumeras las secciones) |
| **Artificial** (subrogada) | Un identificador inventado, sin significado | El `_id` (un `ObjectId`) de MongoDB; un `id` autoincremental | No cambia nunca                         | No dice nada por sí mismo                                            |

- **Esta plataforma usa las dos:** el usuario tiene un `id` artificial de Better Auth, porque su correo puede cambiar; las secciones, el código natural `"B1.3"`, estable y presente en URLs y temario.

<Callout type="risk">

- **El email como clave primaria es una trampa:** al cambiarlo, hay que actualizarlo en todas las tablas que lo usan. `id` artificial como clave, y el email como atributo **único** (B4.4).
- **Las claves naturales "estables" a veces cambian:** si `B1.3` pasara a ser `B1.4`, el progreso guardado apuntaría a la sección equivocada. Úsalas solo con plan de migración.

</Callout>

## Paso 2: la hoja de cálculo y sus anomalías

**Qué es:** guardar todo en una tabla plana, como haría alguien que empieza: una fila por usuario y curso, con las secciones leídas en una celda.

| usuario | email            | curso | tituloCurso            | leidas           |
| ------- | ---------------- | ----- | ---------------------- | ---------------- |
| Dani    | dani@ejemplo.com | B1    | TypeScript desde cero  | B1.1, B1.2, B1.3 |
| Dani    | dani@ejemplo.com | B2    | Git y flujo de trabajo | B2.1             |
| Ana     | ana@ejemplo.com  | B1    | TypeScript desde cero  | B1.1,B1.2        |

**Cómo se usa:** crea `normalizar.js` en `db-lab`, que muestra sus problemas y los corrige.

```js
// Archivo: normalizar.js
// De una "hoja de cálculo" plana a tablas normalizadas, con las anomalías que lo justifican

// ─── 1. La hoja de cálculo: una fila por usuario y curso ───
const hoja = [
  { usuario: "Dani", email: "dani@ejemplo.com", curso: "B1", tituloCurso: "TypeScript desde cero", leidas: "B1.1, B1.2, B1.3" },
  { usuario: "Dani", email: "dani@ejemplo.com", curso: "B2", tituloCurso: "Git y flujo de trabajo", leidas: "B2.1" },
  { usuario: "Ana", email: "ana@ejemplo.com", curso: "B1", tituloCurso: "TypeScript desde cero", leidas: "B1.1,B1.2" },
];

// Problema de 1FN: varias secciones en una celda. Contar lecturas obliga a "trocear" texto
const lecturasDeB12 = hoja.filter((fila) => fila.leidas.split(", ").includes("B1.2")).length;
console.log(`¿Cuántas personas leyeron B1.2? ${lecturasDeB12} (la respuesta correcta es 2)`);

// Anomalía de actualización: Dani cambia de correo, pero solo se corrige una de sus filas
hoja[0].email = "dani@nuevo.com";
const correosDeDani = new Set(hoja.filter((f) => f.usuario === "Dani").map((f) => f.email));
console.log(`Correos de Dani en la hoja: ${[...correosDeDani].join(" y ")}`);

// Anomalía de inserción: un curso nuevo sin lectores no tiene dónde guardarse
// (cada fila exige un usuario: habría que inventar uno o dejar huecos)

// Anomalía de borrado: si Ana deja de tener lecturas y se borra su fila, desaparece Ana
const sinAna = hoja.filter((f) => f.usuario !== "Ana");
console.log(`¿Sigue existiendo Ana tras borrar su única fila? ${sinAna.some((f) => f.usuario === "Ana")}`);

// ─── 2. El modelo normalizado: cada dato en un solo sitio ───
const usuarios = [
  { id: 1, nombre: "Dani", email: "dani@ejemplo.com" },
  { id: 2, nombre: "Ana", email: "ana@ejemplo.com" },
];
const cursos = [
  { id: "B1", titulo: "TypeScript desde cero" },
  { id: "B2", titulo: "Git y flujo de trabajo" },
  { id: "B3", titulo: "Cómo funciona la web" }, // un curso sin lectores: sin problema
];
const secciones = [
  { id: "B1.1", cursoId: "B1" },
  { id: "B1.2", cursoId: "B1" },
  { id: "B1.3", cursoId: "B1" },
  { id: "B2.1", cursoId: "B2" },
];
// Tabla intermedia N:M: una fila por cada par usuario–sección
const lecturas = [
  { usuarioId: 1, seccionId: "B1.1" },
  { usuarioId: 1, seccionId: "B1.2" },
  { usuarioId: 1, seccionId: "B1.3" },
  { usuarioId: 1, seccionId: "B2.1" },
  { usuarioId: 2, seccionId: "B1.1" },
  { usuarioId: 2, seccionId: "B1.2" },
];

console.log("─── Modelo normalizado ───");
console.log(`¿Cuántas personas leyeron B1.2? ${lecturas.filter((l) => l.seccionId === "B1.2").length}`);

usuarios[0].email = "dani@nuevo.com"; // un solo sitio que cambiar
console.log(`Correo de Dani: ${usuarios.find((u) => u.id === 1).email}`);

const progreso = (usuarioId, cursoId) => {
  const delCurso = secciones.filter((s) => s.cursoId === cursoId).map((s) => s.id);
  const leidas = lecturas.filter((l) => l.usuarioId === usuarioId && delCurso.includes(l.seccionId));
  return `${leidas.length}/${delCurso.length}`;
};
for (const usuario of usuarios) {
  console.log(`${usuario.nombre}: B1 ${progreso(usuario.id, "B1")} · B2 ${progreso(usuario.id, "B2")}`);
}
```

```bash
node normalizar.js
```

```text
¿Cuántas personas leyeron B1.2? 1 (la respuesta correcta es 2)
Correos de Dani en la hoja: dani@nuevo.com y dani@ejemplo.com
¿Sigue existiendo Ana tras borrar su única fila? false
─── Modelo normalizado ───
¿Cuántas personas leyeron B1.2? 2
Correo de Dani: dani@nuevo.com
Dani: B1 3/3 · B2 1/1
Ana: B1 2/3 · B2 0/1
```

- **Varios valores en una celda:** Ana tiene `"B1.1,B1.2"` sin espacio, `split(", ")` no la encuentra, y la respuesta es **1** en lugar de **2**.
- **Actualización:** el correo de Dani está en dos filas; cambiado en una, tiene dos correos. **Inserción:** el curso B3 no se puede guardar hasta que alguien lo lea. **Borrado:** borrar la única fila de Ana **borra a Ana**.
- **La segunda mitad** reparte los datos en `usuarios`, `cursos`, `secciones` y `lecturas`, con **cada dato en un solo sitio**. Eso es la **normalización**.

<Callout type="risk">

- **Una hoja compartida es una base de datos sin protección:** columnas repetidas y celdas con listas son una base de datos pidiendo salir.
- **Datos repetidos acaban divergiendo:** pregúntate "si este dato cambia, ¿en cuántos sitios lo cambio?". Lo ideal es uno.

</Callout>

## Paso 3: los tipos de relación

**Qué es:** entre dos entidades solo hay tres relaciones. Se averigua con **dos preguntas**, una en cada sentido.

| Relación | Pregunta 1                                    | Pregunta 2                                        | Ejemplo              | Cómo se guarda                                                      |
| -------- | --------------------------------------------- | ------------------------------------------------- | -------------------- | ------------------------------------------------------------------- |
| **1:1**  | ¿Un usuario tiene cuántos perfiles? **Uno**   | ¿Un perfil es de cuántos usuarios? **Uno**        | Usuario ↔ perfil     | Clave foránea única en cualquiera de las dos (o fusionarlas en una) |
| **1:N**  | ¿Un curso tiene cuántas secciones? **Muchas** | ¿Una sección es de cuántos cursos? **Uno**        | Curso → secciones    | Clave foránea en el lado "N" (`secciones.cursoId`)                  |
| **N:M**  | ¿Un usuario lee cuántas secciones? **Muchas** | ¿Una sección la leen cuántos usuarios? **Muchos** | Usuarios ↔ secciones | **Tabla intermedia** con las dos claves foráneas (`lecturas`)       |

- **En una 1:N, la clave foránea va en el lado de los muchos:** cada sección dice su curso (`cursoId: "B1"`); el curso no guarda la lista.
- **Una N:M necesita una tabla intermedia,** que puede tener atributos propios: aquí, **cuándo** se leyó (`readAt`).

<Callout type="risk">

- **Una 1:1 esconde a menudo una 1:N futura:** "una dirección" hasta que hay una de envío y otra de facturación. Piénsalo antes de fusionar.
- **Una lista de identificadores en una columna no es una N:M:** es el problema del Paso 2. En MongoDB se usan arrays de verdad, con límites (I4).

</Callout>

## Paso 4: normalizar paso a paso (1FN, 2FN y 3FN)

**Qué es:** la normalización se hace por niveles, las **formas normales**. En una frase: **cada atributo depende de la clave, de toda la clave y de nada más que de la clave.**

**Cómo se usa:** aplícalas a la hoja del Paso 2.

**1FN, un solo valor por celda:** la columna `leidas` se separa en una fila por lectura.

| usuario | email            | curso | tituloCurso            | seccion |
| ------- | ---------------- | ----- | ---------------------- | ------- |
| Dani    | dani@ejemplo.com | B1    | TypeScript desde cero  | B1.1    |
| Dani    | dani@ejemplo.com | B1    | TypeScript desde cero  | B1.2    |
| Dani    | dani@ejemplo.com | B1    | TypeScript desde cero  | B1.3    |
| Dani    | dani@ejemplo.com | B2    | Git y flujo de trabajo | B2.1    |
| Ana     | ana@ejemplo.com  | B1    | TypeScript desde cero  | B1.1    |
| Ana     | ana@ejemplo.com  | B1    | TypeScript desde cero  | B1.2    |

Contar quién leyó `B1.2` ya es contar filas, pero el correo de Dani está cuatro veces.

**2FN, todo depende de la clave completa:** la clave es **(usuario, sección)**, pero `email` depende solo del usuario, y `curso` y `tituloCurso`, solo de la sección. Se separan:

```text
usuarios (id, nombre, email)
secciones (id, curso, tituloCurso)
lecturas (usuarioId, seccionId)        ← clave: la pareja completa
```

**3FN, nada depende de otro atributo:** `tituloCurso` depende del **curso**, no de la sección (una dependencia **transitiva**), y se repite en cada sección de B1. Se separa:

```text
usuarios  (id, nombre, email)
cursos    (id, titulo)
secciones (id, cursoId → cursos.id)
lecturas  (usuarioId → usuarios.id, seccionId → secciones.id)
```

- **Son las cuatro tablas** de la segunda mitad de `normalizar.js`.

<Callout type="risk">

- **Normalizar no es gratis:** mostrar "Dani leyó B1.2 de TypeScript desde cero" exige combinar tablas en cada consulta (el `JOIN` de B4.3). Casi siempre compensa.
- **Desnormalizar a propósito es válido:** el progreso de esta plataforma guarda `courseId` además de `sectionId`, aunque se deduce, para contar por curso con una consulta sencilla y un índice.
- **No guardes lo que se calcula,** como un porcentaje de progreso: habría que actualizarlo en cada cambio. Si es caro, guárdalo como caché y con una fuente de verdad clara.

</Callout>

## Paso 5: el diagrama entidad-relación

**Qué es:** un **diagrama entidad-relación** (E-R) dibuja las entidades como cajas, sus atributos dentro y las relaciones como líneas con su cardinalidad.

**Cómo se usa:** el modelo de esta plataforma, tal como está construida.

```text
┌──────────────┐ 1        N ┌──────────────────┐ N        1 ┌──────────────┐
│ usuario      │────────────│ lectura          │────────────│ seccion      │
│──────────────│            │──────────────────│            │──────────────│
│ id (PK)      │            │ usuarioId (FK)   │            │ id (PK) B1.3 │
│ nombre       │            │ seccionId (FK)   │            │ cursoId (FK) │
│ email (único)│            │ cursoId (FK)     │            │ titulo       │
└──────┬───────┘            │ leidaEn          │            │ orden        │
       │ 1                  └──────────────────┘            │ minutos      │
       │                                                    └──────┬───────┘
       │ N                                                         │ N
┌──────┴─────────────┐ N                                  1 ┌──────┴───────┐
│ intento_evaluacion │──────────────────────────────────────│ curso        │
│────────────────────│                                      │──────────────│
│ id (PK)            │                                      │ id (PK) B1   │
│ usuarioId (FK)     │                                      │ slug         │
│ cursoId (FK)       │                                      │ titulo       │
│ nota, total        │                                      │ nivel, orden │
│ aprobado           │                                      └──────────────┘
│ enviadoEn          │
└────────────────────┘
```

- **Se lee así:** un usuario tiene muchas lecturas y muchos intentos; una sección es de un curso y tiene muchas lecturas. La N:M entre usuarios y secciones se resuelve con **`lectura`**.
- **Cursos y secciones no están en la base de datos:** viven en archivos (`courses.json` y las `.mdx`, con su esquema en `src/content.config.ts`), porque los escribe el autor. En MongoDB solo está lo que generan los usuarios: `section_progress`, `quiz_attempts`, `study_sessions` y lo de Better Auth.

Para dibujarlo con una herramienta, pega esto en [mermaid.live](https://mermaid.live):

```text
erDiagram
  USUARIO ||--o{ LECTURA : "lee"
  SECCION ||--o{ LECTURA : "es leída en"
  CURSO ||--|{ SECCION : "tiene"
  USUARIO ||--o{ INTENTO_EVALUACION : "hace"
  CURSO ||--o{ INTENTO_EVALUACION : "se evalúa en"
  USUARIO {
    string id PK
    string nombre
    string email UK
  }
  CURSO {
    string id PK
    string titulo
  }
  SECCION {
    string id PK
    string cursoId FK
    string titulo
  }
  LECTURA {
    string usuarioId FK
    string seccionId FK
    datetime leidaEn
  }
  INTENTO_EVALUACION {
    string id PK
    string usuarioId FK
    string cursoId FK
    int nota
    boolean aprobado
  }
```

- **`||` es "exactamente uno", `o{` "cero o muchos" y `|{` "uno o muchos".** `CURSO ||--|{ SECCION`: un curso tiene una o más secciones, y cada sección es de exactamente un curso.

<Callout type="risk">

- **Falta una restricción:** un usuario no debe leer **dos veces** la misma sección, así que `(usuarioId, seccionId)` debe ser **única**. Esta plataforma lo garantiza con el índice único `user_section_unique`; en B4.4 crearás el equivalente. Sin él, un doble clic pasaría el progreso del 100 %.
- **Modela lo que la app necesita hoy:** cada entidad "por si acaso" es código, consultas y migraciones.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Sin mirar el Paso 5, dibuja en papel el diagrama entidad-relación de esta plataforma: usuarios, cursos, secciones, progreso (lecturas) y evaluaciones. Marca las claves primarias, las foráneas y la cardinalidad de cada relación.
2. Añade dos entidades que la plataforma tiene y que no están en el diagrama del Paso 5: las **sesiones de estudio** (cada visita a una lección con su duración y las secciones que viste) y las **preguntas** de cada evaluación.
3. Para cada relación nueva, justifica su tipo con las dos preguntas del Paso 3.
4. Busca en tu diagrama un dato que se pueda calcular a partir de otros y decide si lo guardarías o no.

</Callout>

Solución. Las dos entidades nuevas y sus relaciones:

| Relación                    | Pregunta 1                               | Pregunta 2                                      | Tipo | Cómo se guarda                                                                |
| --------------------------- | ---------------------------------------- | ----------------------------------------------- | ---- | ----------------------------------------------------------------------------- |
| Usuario – sesión de estudio | Un usuario tiene **muchas** sesiones     | Una sesión es de **un** usuario                 | 1:N  | `sesion_estudio.usuarioId`                                                    |
| Sesión de estudio – sección | En una sesión ves **muchas** secciones   | Una sección se ve en **muchas** sesiones        | N:M  | Tabla intermedia `sesion_seccion (sesionId, seccionId)`                       |
| Curso – pregunta            | Un curso tiene **muchas** (5) preguntas  | Una pregunta es de **un** curso                 | 1:N  | `pregunta.cursoId`                                                            |
| Intento – pregunta          | Un intento responde **muchas** preguntas | Una pregunta se responde en **muchos** intentos | N:M  | Tabla intermedia `respuesta (intentoId, preguntaId, opcionElegida, correcta)` |

Las nuevas cajas:

```text
sesion_estudio (id PK, usuarioId FK, inicio, ultimaActividad)
sesion_seccion (sesionId FK, seccionId FK)                       ← N:M
pregunta       (id PK, cursoId FK, enunciado, opciones, correcta, explicacion)
respuesta      (intentoId FK, preguntaId FK, opcionElegida, correcta)   ← N:M con atributos
```

- **Cómo lo resuelve la plataforma:** en MongoDB, `study_sessions` guarda las secciones vistas como un **array** (`sectionIds: ["B1.1", "B1.2"]`), y `quiz_attempts`, las respuestas y los aciertos en dos arrays (`answers` y `results`). Es la forma documental de una N:M pequeña y acotada. Las preguntas viven en `b1.yaml`, `b2.yaml`…
- **El dato calculable:** la nota (`score`) se deduce de `results`, pero se guarda, porque un intento **no cambia nunca**. El porcentaje de progreso, en cambio, cambia con cada lectura y se calcula al vuelo.

<Callout type="risk">

- **Un array solo sustituye a una tabla intermedia si es pequeño y acotado:** todas las lecturas de un usuario en toda su vida harían crecer el documento sin control (I4).
- **Editar una pregunta ya respondida** hace que el intento antiguo apunte a otra. Muchos sistemas guardan una copia en el intento, o versionan las preguntas.

</Callout>

<Callout type="mastery">

Identificas el tipo de relación entre dos entidades al primer vistazo con las dos preguntas, sabes que la clave foránea va en el lado de los muchos y que una N:M necesita una tabla intermedia, reconoces las anomalías de una tabla sin normalizar y aplicas 1FN, 2FN y 3FN para que cada dato viva en un solo sitio.

</Callout>

## Resumen

- Entidad, atributo, clave primaria (natural o artificial) y clave foránea.
- Una tabla sin normalizar sufre anomalías de actualización, inserción y borrado.
- 1:1, 1:N (foránea en el lado N) y N:M (tabla intermedia).
- 1FN, 2FN y 3FN: cada dato, en un solo sitio.
- Desnormalizar vale si es consciente y las copias se mantienen.
