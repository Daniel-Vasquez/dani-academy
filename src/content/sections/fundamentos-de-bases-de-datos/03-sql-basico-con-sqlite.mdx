Aunque tus proyectos usen MongoDB, vas a encontrarte SQL en entrevistas, en herramientas de analítica, en Supabase y PostgreSQL, en los paneles de Vercel… y, sobre todo, te enseña a **pensar en conjuntos de datos** en lugar de en bucles, que es justo lo que necesitarás con las agregaciones de MongoDB. En esta sección vas a convertir el diagrama de B4.2 en una base de datos real, vas a provocar cada error que protege tus datos, vas a responder preguntas cada vez más difíciles hasta calcular el **porcentaje de progreso por curso** (lo que hace la página de progreso de esta plataforma) y, al final, vas a usarla desde Node.

## Paso 1: crear las tablas con `CREATE TABLE`

Crea `esquema.sql` en `db-lab`. Es la traducción directa del diagrama de B4.2, con cada regla del modelo escrita como una **restricción** que la base de datos hará cumplir:

```sql
-- Archivo: esquema.sql
-- Modelo de datos de Dani Academy (B4.2) en SQLite
PRAGMA foreign_keys = ON;

DROP TABLE IF EXISTS intentos;
DROP TABLE IF EXISTS lecturas;
DROP TABLE IF EXISTS secciones;
DROP TABLE IF EXISTS cursos;
DROP TABLE IF EXISTS usuarios;

CREATE TABLE usuarios (
  id     INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  email  TEXT NOT NULL UNIQUE
);

CREATE TABLE cursos (
  id     TEXT PRIMARY KEY,                -- clave natural: 'B1'
  titulo TEXT NOT NULL,
  nivel  TEXT NOT NULL CHECK (nivel IN ('basico', 'intermedio', 'avanzado')),
  orden  INTEGER NOT NULL
);

CREATE TABLE secciones (
  id       TEXT PRIMARY KEY,              -- clave natural: 'B1.3'
  curso_id TEXT NOT NULL REFERENCES cursos(id),
  titulo   TEXT NOT NULL,
  orden    INTEGER NOT NULL,
  minutos  INTEGER NOT NULL DEFAULT 60
);

-- Tabla intermedia N:M entre usuarios y secciones
CREATE TABLE lecturas (
  usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
  seccion_id TEXT NOT NULL REFERENCES secciones(id),
  leida_en   TEXT NOT NULL,               -- fecha ISO 8601 en UTC
  PRIMARY KEY (usuario_id, seccion_id)    -- una sección no se lee dos veces
);

CREATE TABLE intentos (
  id         INTEGER PRIMARY KEY,
  usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
  curso_id   TEXT NOT NULL REFERENCES cursos(id),
  nota       INTEGER NOT NULL CHECK (nota BETWEEN 0 AND 5),
  enviado_en TEXT NOT NULL
);
```

Lo que dice cada pieza:

- **`INTEGER PRIMARY KEY`**: clave primaria numérica. Si no indicas el `id` al insertar, SQLite asigna el siguiente número automáticamente.
- **`TEXT PRIMARY KEY`**: una clave natural (`'B1'`, `'B1.3'`), como decidiste en B4.2.
- **`NOT NULL`**: la columna es obligatoria.
- **`UNIQUE`**: no puede haber dos filas con el mismo valor (dos usuarios con el mismo correo).
- **`CHECK (…)`**: una condición que toda fila debe cumplir (el nivel solo puede ser uno de tres; la nota, entre 0 y 5).
- **`DEFAULT 60`**: valor si no se indica otro.
- **`REFERENCES cursos(id)`**: una **clave foránea**: el valor debe existir en esa otra tabla.
- **`ON DELETE CASCADE`**: si se borra el usuario, se borran también sus lecturas e intentos.
- **`PRIMARY KEY (usuario_id, seccion_id)`**: una clave primaria **compuesta**: la pareja no se puede repetir. Es la restricción que impide leer dos veces la misma sección.
- **`DROP TABLE IF EXISTS`**: borra las tablas si ya existían, para poder ejecutar el script tantas veces como quieras. Se borran en orden inverso a como dependen unas de otras.

Crea `datos.sql` con datos de prueba:

Crea la base de datos ejecutando los dos scripts (el `<` le pasa el contenido del archivo a `sqlite3`):

```bash

sqlite3 academia.db ".tables"
```

```text
cursos     intentos   lecturas   secciones  usuarios
```

<Callout type="risk">

- **`DROP TABLE` borra los datos para siempre.** En este script de laboratorio es lo que quieres; en una base de datos con datos reales, ejecutarlo por error es una catástrofe. Nunca ejecutes un `esquema.sql` con `DROP` contra producción.
- **Los tipos de SQLite son flexibles:** a diferencia de PostgreSQL, SQLite acepta guardar `'hola'` en una columna `INTEGER`. Las restricciones `CHECK` y `NOT NULL` son las que de verdad protegen los datos. (Si quieres tipos estrictos, SQLite tiene tablas `STRICT`: `CREATE TABLE … ( … ) STRICT;`).
- **Las fechas son texto:** SQLite no tiene un tipo fecha. Se guardan como texto ISO 8601 en UTC (`'2026-10-01T15:00:00Z'`), que se ordena correctamente como texto. Nunca guardes fechas como `'01/10/2026'`: no se ordenan bien y son ambiguas (¿1 de octubre o 10 de enero?).

</Callout>

## Paso 2: consultar con `SELECT`, `WHERE`, `ORDER BY` y `LIMIT`

Abre una sesión interactiva y configura la salida para que sea legible:

```bash
sqlite3 academia.db
```

```text
SQLite version 3.51.0 2025-06-12 13:14:41
Enter ".help" for usage hints.
sqlite>
```

```sql
.mode box
PRAGMA foreign_keys = ON;
```

`.mode box` dibuja las tablas con bordes (los comandos que empiezan por punto son de la herramienta `sqlite3`, no de SQL). El `PRAGMA` lo explicarás en el Paso 3. Ahora, tu primera consulta, todo de la tabla de cursos:

```sql
SELECT * FROM cursos;
```

```text
┌────┬────────────────────────┬────────┬───────┐
│ id │         titulo         │ nivel  │ orden │
├────┼────────────────────────┼────────┼───────┤
│ B1 │ TypeScript desde cero  │ basico │ 1     │
│ B2 │ Git y flujo de trabajo │ basico │ 2     │
│ B3 │ Cómo funciona la web   │ basico │ 3     │
└────┴────────────────────────┴────────┴───────┘
```

Elige columnas, filtra, ordena y limita:

```sql
SELECT id, titulo FROM secciones WHERE curso_id = 'B1' ORDER BY orden DESC LIMIT 2;
```

```text
┌──────┬──────────────────────────┐
│  id  │          titulo          │
├──────┼──────────────────────────┤
│ B1.4 │ type vs interface        │
│ B1.3 │ Arrays, tuplas y objetos │
└──────┴──────────────────────────┘
```

Se lee casi como una frase: "selecciona el id y el título **de** secciones **donde** el curso sea B1, **ordenadas** por orden descendente, **solo 2**". Condiciones combinadas:

```sql
SELECT id, titulo, minutos FROM secciones
WHERE curso_id IN ('B2', 'B3') AND titulo LIKE '%Git%';
```

```text
┌──────┬─────────────────────────┬─────────┐
│  id  │         titulo          │ minutos │
├──────┼─────────────────────────┼─────────┤
│ B2.1 │ El modelo mental de Git │ 60      │
└──────┴─────────────────────────┴─────────┘
```

- **`IN (…)`**: el valor está en la lista.
- **`LIKE '%Git%'`**: el texto contiene "Git". `%` es "cualquier cosa" (cero o más caracteres) y `_`, "exactamente un carácter".
- **`AND` / `OR`**: combinan condiciones. Usa paréntesis cuando mezcles los dos.
- **Una consulta puede ocupar varias líneas**: termina cuando escribes `;`. Si pulsas Enter sin `;`, el _prompt_ cambia a `...>` y espera más texto.

<Callout type="risk">

- **El orden de las filas no está garantizado sin `ORDER BY`.** Hoy SQLite te las devuelve en el orden de inserción; mañana, tras un índice nuevo o un cambio de versión, puede que no. Si el orden importa, escríbelo.
- **`SELECT *` en el código de una app es frágil:** si mañana añades una columna enorme (o sensible, como un _hash_ de contraseña), todas las consultas la arrastrarán. En el código, enumera las columnas que necesitas.
- **Comillas:** en SQL, los textos van entre comillas **simples** (`'B1'`). Las dobles son para nombres de columnas o tablas. `WHERE curso_id = "B1"` funciona en SQLite por compatibilidad, pero falla en otras bases de datos.

</Callout>

## Paso 3: insertar y comprobar que las restricciones protegen tus datos

Sigue en la sesión de `sqlite3`. Intenta guardar datos incorrectos, uno por uno:

```sql
INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B9.9', '2026-10-08T10:00:00Z');
INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B1.1', '2026-10-08T10:00:00Z');
INSERT INTO usuarios (nombre, email) VALUES ('Otra Dani', 'dani@ejemplo.com');
INSERT INTO cursos (id, titulo, nivel, orden) VALUES ('X1', 'Prueba', 'experto', 9);
```

```text
Runtime error: FOREIGN KEY constraint failed (19)
Runtime error: UNIQUE constraint failed: lecturas.usuario_id, lecturas.seccion_id (19)
Runtime error: UNIQUE constraint failed: usuarios.email (19)
Runtime error: CHECK constraint failed: nivel IN ('basico', 'intermedio', 'avanzado') (19)
```

Cuatro errores, cuatro bugs que **no llegarán a tus datos**:

1. **`FOREIGN KEY`**: la sección `B9.9` no existe.
2. **`UNIQUE` en `lecturas`**: Ana ya había leído `B1.1`. Es la clave primaria compuesta en acción, la protección contra el doble clic.
3. **`UNIQUE` en `usuarios.email`**: ese correo ya está registrado.
4. **`CHECK`**: `'experto'` no es un nivel válido.

Ahora el experimento más importante. Sal de la sesión (`.quit`) y repite el primer `INSERT` **sin** el `PRAGMA`, en una sola orden desde la terminal:

```bash
sqlite3 academia.db "INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B9.9', '2026-10-08T10:00:00Z'); SELECT changes();"
```

```text
1
```

**Se insertó.** `changes()` devuelve cuántas filas cambió la última operación: 1. Ana tiene ahora una lectura de una sección que no existe. Bórrala y vuelve a la sesión interactiva:

```bash
sqlite3 academia.db "DELETE FROM lecturas WHERE seccion_id = 'B9.9';"
sqlite3 academia.db
```

```sql
.mode box
PRAGMA foreign_keys = ON;
```

<Callout type="risk">

- **En SQLite, las claves foráneas están desactivadas por defecto** (por compatibilidad con bases de datos antiguas) y `PRAGMA foreign_keys = ON` hay que ejecutarlo en **cada conexión nueva**: cada vez que abres `sqlite3`, cada vez que tu programa abre la base de datos. Es el error más común con SQLite: crees que tus `REFERENCES` te protegen y no lo hacen. (PostgreSQL y MySQL las aplican siempre).
- **La base de datos es tu última línea de defensa, no la única:** valida también en tu código para dar mensajes claros al usuario ("ese correo ya está registrado"). La restricción garantiza que, aunque tu validación falle, el dato incorrecto no entre.

</Callout>

## Paso 4: modificar y borrar, y el peligro de olvidar el `WHERE`

`UPDATE` cambia filas existentes y `DELETE` las borra. Los dos usan `WHERE` para elegir **qué** filas:

```sql
UPDATE usuarios SET email = 'dani@nuevo.com' WHERE id = 1;
SELECT changes() AS filas_cambiadas;
SELECT * FROM usuarios WHERE id = 1;
```

```text
┌─────────────────┐
│ filas_cambiadas │
├─────────────────┤
│ 1               │
└─────────────────┘
┌────┬────────┬────────────────┐
│ id │ nombre │     email      │
├────┼────────┼────────────────┤
│ 1  │ Dani   │ dani@nuevo.com │
└────┴────────┴────────────────┘
```

Gracias a la normalización de B4.2, el correo de Dani se cambia en **un solo sitio**. Ahora, lo que **no** debes hacer nunca. Sal de la sesión (`.quit`), haz una **copia** de la base de datos y practica el error sobre la copia:

```bash
cp academia.db copia.db
sqlite3 -box copia.db "UPDATE secciones SET minutos = 45; SELECT changes() AS filas_cambiadas;"
sqlite3 -box copia.db "DELETE FROM lecturas; SELECT changes() AS filas_borradas;"
rm copia.db
```

```text
┌─────────────────┐
│ filas_cambiadas │
├─────────────────┤
│ 7               │
└─────────────────┘
┌────────────────┐
│ filas_borradas │
├────────────────┤
│ 7              │
└────────────────┘
```

Sin `WHERE`, `UPDATE` cambió **todas** las secciones y `DELETE` borró **todas** las lecturas. Sin confirmación, sin papelera, sin `Ctrl+Z`. Ahora, el borrado en cascada y la protección de las claves foráneas, también sobre una copia:

```bash
cp academia.db prueba.db
sqlite3 prueba.db
```

```sql
.mode box
PRAGMA foreign_keys = ON;
SELECT COUNT(*) AS lecturas_de_ana FROM lecturas WHERE usuario_id = 2;
DELETE FROM usuarios WHERE id = 2;
SELECT COUNT(*) AS lecturas_de_ana FROM lecturas WHERE usuario_id = 2;
DELETE FROM secciones WHERE id = 'B1.1';
.quit
```

```text
┌─────────────────┐
│ lecturas_de_ana │
├─────────────────┤
│ 2               │
└─────────────────┘
┌─────────────────┐
│ lecturas_de_ana │
├─────────────────┤
│ 0               │
└─────────────────┘
Runtime error: FOREIGN KEY constraint failed (19)
```

```bash
rm prueba.db
```

- Al borrar a Ana, **`ON DELETE CASCADE`** borró sus dos lecturas: no quedan lecturas "huérfanas" de un usuario que no existe.
- La sección `B1.1` **no se pudo borrar**: tiene lecturas que la referencian y su clave foránea no tiene `ON DELETE CASCADE`. La base de datos impide dejar lecturas apuntando a la nada.

<Callout type="risk">

- **Antes de un `UPDATE` o un `DELETE`, ejecuta el mismo `WHERE` con un `SELECT`:** `SELECT * FROM lecturas WHERE usuario_id = 2;`. Si ves las filas que esperas, cambia `SELECT *` por `DELETE`. Es la costumbre que más desastres evita.
- **`ON DELETE CASCADE` es potente y peligroso:** borrar un usuario borra todo su historial sin preguntar. Úsalo solo donde los datos hijos no tienen sentido sin el padre (lecturas sin usuario). Para datos que deben conservarse (facturas), mejor impedir el borrado o marcar el registro como borrado (`borrado_en`).
- **Haz copias de seguridad antes de operaciones masivas:** `sqlite3 academia.db ".backup antes-de-limpiar.db"`. En MongoDB Atlas, el plan gratuito no incluye copias automáticas.

</Callout>

## Paso 5: combinar tablas con `JOIN`

Los datos están repartidos en varias tablas (normalización). `JOIN` los **vuelve a unir** en una consulta, emparejando filas por sus claves. Abre de nuevo la sesión (`sqlite3 academia.db`, `.mode box` y el `PRAGMA`) y pregunta qué secciones ha leído Ana, con sus títulos:

```sql
SELECT u.nombre, s.id AS seccion, s.titulo, l.leida_en
FROM lecturas l
JOIN usuarios u ON u.id = l.usuario_id
JOIN secciones s ON s.id = l.seccion_id
WHERE u.nombre = 'Ana'
ORDER BY l.leida_en;
```

```text
┌────────┬─────────┬────────────────────────────────────┬──────────────────────┐
│ nombre │ seccion │               titulo               │       leida_en       │
├────────┼─────────┼────────────────────────────────────┼──────────────────────┤
│ Ana    │ B1.1    │ Qué es TypeScript y por qué existe │ 2026-10-04T09:30:00Z │
│ Ana    │ B1.2    │ Tipos primitivos e inferencia      │ 2026-10-06T10:00:00Z │
└────────┴─────────┴────────────────────────────────────┴──────────────────────┘
```

- **`FROM lecturas l`**: la tabla de partida, con un alias corto (`l`).
- **`JOIN usuarios u ON u.id = l.usuario_id`**: por cada lectura, busca el usuario cuyo `id` coincide con su `usuario_id`.
- **`s.id AS seccion`**: renombra la columna en el resultado.

Un `JOIN` normal (`INNER JOIN`) solo devuelve las filas que **tienen pareja** en las dos tablas. Pero la página de un curso necesita **todas** las secciones, leídas o no, para pintar las marcas. Para eso existe **`LEFT JOIN`**: conserva todas las filas de la tabla de la izquierda, y rellena con vacío (`NULL`) cuando no hay pareja:

```sql
SELECT s.id, s.titulo, l.leida_en
FROM secciones s
LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = 2
WHERE s.curso_id = 'B1'
ORDER BY s.orden;
```

```text
┌──────┬────────────────────────────────────┬──────────────────────┐
│  id  │               titulo               │       leida_en       │
├──────┼────────────────────────────────────┼──────────────────────┤
│ B1.1 │ Qué es TypeScript y por qué existe │ 2026-10-04T09:30:00Z │
│ B1.2 │ Tipos primitivos e inferencia      │ 2026-10-06T10:00:00Z │
│ B1.3 │ Arrays, tuplas y objetos           │                      │
│ B1.4 │ type vs interface                  │                      │
└──────┴────────────────────────────────────┴──────────────────────┘
```

Es exactamente la información que necesita la barra lateral de un curso. Y para responder "¿qué le queda por leer a Ana?", filtra las que no tienen pareja:

```sql
SELECT s.id, s.titulo
FROM secciones s
LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = 2
WHERE s.curso_id = 'B1' AND l.seccion_id IS NULL
ORDER BY s.orden;
```

```text
┌──────┬──────────────────────────┐
│  id  │          titulo          │
├──────┼──────────────────────────┤
│ B1.3 │ Arrays, tuplas y objetos │
│ B1.4 │ type vs interface        │
└──────┴──────────────────────────┘
```

<Callout type="risk">

- **La condición del usuario va en el `ON`, no en el `WHERE`:** si escribes `LEFT JOIN lecturas l ON l.seccion_id = s.id WHERE l.usuario_id = 2`, el `WHERE` descarta las filas donde `l.usuario_id` es `NULL`… que son justo las secciones no leídas. El `LEFT JOIN` se convierte en un `JOIN` normal sin avisar. Las condiciones sobre la tabla de la derecha de un `LEFT JOIN` van en el `ON`.
- **`= NULL` no funciona nunca:** en SQL, `NULL` significa "desconocido", y cualquier comparación con él da "desconocido", no "verdadero". Se compara con `IS NULL` o `IS NOT NULL`.
- **Un `JOIN` sin condición multiplica filas:** olvidar el `ON` (o escribir una condición que no relaciona bien las tablas) produce todas las combinaciones posibles. Con 1000 usuarios y 134 secciones, 134 000 filas. Si un resultado tiene sospechosamente muchas filas, revisa los `ON`.

</Callout>

## Paso 6: resumir con `GROUP BY` y funciones de agregado

Las preguntas de una página de progreso son resúmenes: cuántas, cuánto de media, el máximo. `GROUP BY` agrupa filas y las **funciones de agregado** (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) calculan un valor por grupo:

```sql
SELECT u.nombre, COUNT(l.seccion_id) AS leidas
FROM usuarios u
LEFT JOIN lecturas l ON l.usuario_id = u.id
GROUP BY u.id
ORDER BY leidas DESC;
```

```text
┌────────┬────────┐
│ nombre │ leidas │
├────────┼────────┤
│ Dani   │ 5      │
│ Ana    │ 2      │
│ Luis   │ 0      │
└────────┴────────┘
```

La media de las evaluaciones por curso:

```sql
SELECT c.id AS curso, COUNT(*) AS intentos, ROUND(AVG(i.nota), 2) AS media, MAX(i.nota) AS mejor
FROM intentos i
JOIN cursos c ON c.id = i.curso_id
GROUP BY c.id;
```

```text
┌───────┬──────────┬───────┬───────┐
│ curso │ intentos │ media │ mejor │
├───────┼──────────┼───────┼───────┤
│ B1    │ 3        │ 4.0   │ 5     │
└───────┴──────────┴───────┴───────┘
```

Y para filtrar **grupos** (no filas) se usa **`HAVING`**: los usuarios con al menos 2 secciones leídas:

```sql
SELECT u.nombre, COUNT(l.seccion_id) AS leidas
FROM usuarios u
LEFT JOIN lecturas l ON l.usuario_id = u.id
GROUP BY u.id
HAVING COUNT(l.seccion_id) >= 2;
```

```text
┌────────┬────────┐
│ nombre │ leidas │
├────────┼────────┤
│ Dani   │ 5      │
│ Ana    │ 2      │
└────────┴────────┘
```

La diferencia: `WHERE` filtra filas **antes** de agrupar; `HAVING` filtra grupos **después**.

<Callout type="risk">

- **`COUNT(*)` frente a `COUNT(columna)`:** cambia la primera consulta por `COUNT(*)` y verás que **Luis aparece con 1** lectura en lugar de 0. Con `LEFT JOIN`, Luis tiene una fila con la lectura vacía (`NULL`): `COUNT(*)` cuenta filas (1), mientras que `COUNT(l.seccion_id)` cuenta solo los valores no nulos (0). Con `LEFT JOIN`, cuenta siempre una columna de la tabla de la derecha.
- **La división entera:** en SQLite, `2 / 4` es `0`, no `0.5`, porque dividir dos enteros da un entero. Por eso las consultas de porcentaje multiplican primero por `100.0` (un número decimal): `100.0 * leidas / total`.
- **Columnas fuera del `GROUP BY`:** SQLite te deja seleccionar una columna que no está agrupada ni agregada y te devuelve el valor de una fila cualquiera del grupo. PostgreSQL da error. No te fíes de ese valor.

</Callout>

## Paso 7: consultar desde Node, sin inyección SQL

En una app, las consultas las lanza tu código con valores que vienen del usuario. Crea `consultas.js` en `db-lab`:

```js
// Archivo: consultas.js
// Consultar academia.db desde Node, de forma segura e insegura
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync("academia.db");
db.exec("PRAGMA foreign_keys = ON");

// ✅ Consulta preparada: el valor viaja aparte del SQL y nunca se interpreta como código
const progresoPorCurso = db.prepare(`
  SELECT s.curso_id AS curso,
         COUNT(l.seccion_id) AS leidas,
         COUNT(*) AS total,
         ROUND(100.0 * COUNT(l.seccion_id) / COUNT(*), 1) AS porcentaje
  FROM secciones s
  LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = ?
  GROUP BY s.curso_id
  ORDER BY s.curso_id
`);

console.log("Progreso de Dani (id 1):");
console.table(progresoPorCurso.all(1));

// ❌ SQL construido concatenando texto que viene del usuario
function buscarUsuarioInseguro(email) {
  return db.prepare(`SELECT id, nombre, email FROM usuarios WHERE email = '${email}'`).all();
}

// ✅ La misma búsqueda con un parámetro
const buscarUsuario = db.prepare("SELECT id, nombre, email FROM usuarios WHERE email = ?");

const ataque = "x' OR '1'='1";
console.log(`Búsqueda insegura con "${ataque}":`, buscarUsuarioInseguro(ataque).map((u) => u.email));
console.log(`Búsqueda segura con "${ataque}":`, buscarUsuario.all(ataque).map((u) => u.email));
console.log("Búsqueda segura de un correo real:", { ...buscarUsuario.get("ana@ejemplo.com") });

db.close();
```

```bash
node consultas.js
```

```text
Progreso de Dani (id 1):
┌─────────┬───────┬────────┬───────┬────────────┐
│ (index) │ curso │ leidas │ total │ porcentaje │
├─────────┼───────┼────────┼───────┼────────────┤
│ 0       │ 'B1'  │ 4      │ 4     │ 100        │
│ 1       │ 'B2'  │ 1      │ 2     │ 50         │
│ 2       │ 'B3'  │ 0      │ 1     │ 0          │
└─────────┴───────┴────────┴───────┴────────────┘
Búsqueda insegura con "x' OR '1'='1": [ 'dani@nuevo.com', 'ana@ejemplo.com', 'luis@ejemplo.com' ]
Búsqueda segura con "x' OR '1'='1": []
Búsqueda segura de un correo real: { id: 2, nombre: 'Ana', email: 'ana@ejemplo.com' }
```

La primera consulta usa **`?`**: un hueco que se rellena con `progresoPorCurso.all(1)`. Es una **consulta preparada**.

La segunda parte es la lección de seguridad más importante del curso. `buscarUsuarioInseguro` construye el SQL **pegando** el texto del usuario. Con un correo normal funciona. Pero con el texto `x' OR '1'='1`, el SQL resultante es:

```sql
SELECT id, nombre, email FROM usuarios WHERE email = 'x' OR '1'='1'
```

La comilla del usuario **cerró** el texto y lo que sigue se ejecutó **como SQL**: `'1'='1'` siempre es verdadero, así que devuelve **todos** los usuarios. Es una **inyección SQL**. En un formulario de login, eso es entrar sin contraseña; con otros textos, borrar tablas o leer datos ajenos. Con la consulta preparada, el mismo texto se busca **literalmente** como correo, y no encuentra nada.

<Callout type="risk">

- **Nunca construyas SQL concatenando valores del usuario**, ni con _template strings_ (`${email}`). Siempre parámetros (`?`). No hay excepciones: escapar comillas a mano tiene fallos conocidos. Lo que sí puede ir en el texto del SQL son valores que controla tu código (por ejemplo, elegir entre dos nombres de columna fijos para ordenar).
- **MongoDB tiene su propia versión del ataque:** si pasas a una consulta un objeto que viene del cuerpo de la petición sin validar, `{ "email": { "$ne": null } }` encuentra a cualquier usuario. Se llama inyección NoSQL, y se evita validando el tipo de cada valor (curso A5).
- **`DatabaseSync` es síncrona:** cada consulta bloquea Node hasta que termina. Para un script o una herramienta, perfecto; en un servidor con mucho tráfico, las consultas largas detendrían las demás peticiones.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Escribe una consulta que devuelva, **para un usuario**, el porcentaje de secciones leídas de **cada curso**, incluidos los cursos en los que no ha leído nada (con 0 %).
2. Escribe otra que devuelva la **última sección leída** por cada usuario, con su título y su fecha (los usuarios sin lecturas no aparecen).
3. Añade a `consultas.js` una función `marcarLeida(usuarioId, seccionId)` con una consulta preparada que no falle si la sección ya estaba leída.

</Callout>

Solución del punto 1. La clave es empezar desde **todas** las secciones combinadas con el usuario (`CROSS JOIN`, todas las combinaciones), y unir las lecturas con `LEFT JOIN`:

```sql
SELECT u.nombre,
       s.curso_id AS curso,
       COUNT(l.seccion_id) AS leidas,
       COUNT(*) AS total,
       ROUND(100.0 * COUNT(l.seccion_id) / COUNT(*), 1) AS porcentaje
FROM usuarios u
CROSS JOIN secciones s
LEFT JOIN lecturas l ON l.usuario_id = u.id AND l.seccion_id = s.id
WHERE u.id = 1
GROUP BY u.id, s.curso_id
ORDER BY s.curso_id;
```

│ nombre │ curso │ leidas │ total │ porcentaje │
├────────┼───────┼────────┼───────┼────────────┤
│ Dani   │ B1    │ 4      │ 4     │ 100.0      │
│ Dani   │ B2    │ 1      │ 2     │ 50.0       │

Solución del punto 2. Para cada usuario, la lectura cuya fecha coincide con la **máxima** de sus lecturas (una subconsulta):

```sql
SELECT u.nombre, s.id AS seccion, s.titulo, l.leida_en
FROM lecturas l
JOIN usuarios u ON u.id = l.usuario_id
JOIN secciones s ON s.id = l.seccion_id
WHERE l.leida_en = (
  SELECT MAX(l2.leida_en) FROM lecturas l2 WHERE l2.usuario_id = l.usuario_id
)
ORDER BY u.nombre;
```

```text
┌────────┬─────────┬───────────────────────────────┬──────────────────────┐
│ nombre │ seccion │            titulo             │       leida_en       │
├────────┼─────────┼───────────────────────────────┼──────────────────────┤
│ Ana    │ B1.2    │ Tipos primitivos e inferencia │ 2026-10-06T10:00:00Z │
│ Dani   │ B2.1    │ El modelo mental de Git       │ 2026-10-07T15:05:00Z │
└────────┴─────────┴───────────────────────────────┴──────────────────────┘
```

Es la consulta que alimenta el botón "Continuar donde lo dejaste" del temario.

Solución del punto 3. Añade esto al final de `consultas.js`, **antes** de `db.close();`:

```js
// Marca una sección como leída. Si ya lo estaba, no hace nada (idempotente, como un PUT)
const insertarLectura = db.prepare(`
  INSERT INTO lecturas (usuario_id, seccion_id, leida_en)
  VALUES (?, ?, ?)
  ON CONFLICT (usuario_id, seccion_id) DO NOTHING
`);

function marcarLeida(usuarioId, seccionId) {
  const { changes } = insertarLectura.run(usuarioId, seccionId, new Date().toISOString());
  return changes === 1 ? "marcada" : "ya estaba leída";
}

console.log("B1.3 para Ana:", marcarLeida(2, "B1.3"));
console.log("B1.3 para Ana, otra vez:", marcarLeida(2, "B1.3"));
```

```text
B1.3 para Ana: marcada
B1.3 para Ana, otra vez: ya estaba leída
```

`ON CONFLICT … DO NOTHING` convierte el error de `UNIQUE` en "no hagas nada". Es la versión SQL de lo que hace esta plataforma en MongoDB con un _upsert_ sobre su índice único: marcar dos veces deja una sola lectura.

<Callout type="risk">

- **Si dos lecturas de un usuario tienen exactamente la misma fecha**, la consulta del punto 2 devolverá las dos. Con fechas al segundo es improbable, pero posible. Las bases de datos modernas resuelven este tipo de consultas con funciones de ventana (`ROW_NUMBER() OVER (PARTITION BY …)`), que verás en cursos avanzados.
- **`new Date().toISOString()`** genera la fecha en UTC con milisegundos (`2026-10-09T15:42:10.123Z`), compatible con el formato de `datos.sql`. Si mezclaras fechas con y sin zona horaria en la misma columna, el orden alfabético dejaría de coincidir con el temporal.
- **Ejecutar `consultas.js` dos veces** deja la lectura de `B1.3` de Ana ya creada desde la primera vez. Para empezar de cero, vuelve a crear la base de datos con `esquema.sql` y `datos.sql`.

</Callout>

<Callout type="mastery">

Escribes un `SELECT` con `JOIN` y `GROUP BY` sin ayuda: sabes cuándo hace falta un `LEFT JOIN` y dónde poner sus condiciones, cuentas con `COUNT(columna)` en lugar de `COUNT(*)`, nunca lanzas un `UPDATE` o un `DELETE` sin comprobar antes su `WHERE`, y desde el código usas siempre consultas preparadas.

</Callout>

## Resumen

- `CREATE TABLE` define columnas y restricciones (`PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, `REFERENCES`) que la base de datos hace cumplir.
- En SQLite, `PRAGMA foreign_keys = ON` en cada conexión, o las claves foráneas no se comprueban.
- `SELECT … FROM … WHERE … ORDER BY … LIMIT` para leer; `UPDATE` y `DELETE` siempre con `WHERE` comprobado antes con un `SELECT`.
- `JOIN` une tablas por sus claves; `LEFT JOIN` conserva las filas sin pareja (`NULL`); `GROUP BY` + `COUNT`/`AVG`/`MAX` resume; `HAVING` filtra grupos.
- Desde el código, consultas preparadas con `?`: concatenar texto del usuario abre la puerta a la inyección SQL.
