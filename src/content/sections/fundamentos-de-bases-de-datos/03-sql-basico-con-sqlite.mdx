**SQL** es el lenguaje de las bases de datos relacionales: lo encontrarás en entrevistas, en analítica, en Supabase y en PostgreSQL, y te enseña a pensar en conjuntos en lugar de en bucles. Aquí conviertes el diagrama de B4.2 en una base de datos real y calculas el progreso por curso.

**Requisitos:** el proyecto `db-lab` de B4.1 y B4.2, y `sqlite3` (viene en macOS).

## Paso 1: crear las tablas con `CREATE TABLE`

**Qué es:** `CREATE TABLE` define las columnas de una tabla y sus **restricciones**, las reglas del modelo que la base de datos hará cumplir.

**Cómo se usa:** crea `esquema.sql` en `db-lab`, la traducción del diagrama de B4.2.

```sql
-- Archivo: esquema.sql
-- Modelo de datos de Dani Academy (B4.2) en SQLite
PRAGMA foreign_keys = ON;

DROP TABLE IF EXISTS intentos;
DROP TABLE IF EXISTS lecturas;
DROP TABLE IF EXISTS secciones;
DROP TABLE IF EXISTS cursos;
DROP TABLE IF EXISTS usuarios;

CREATE TABLE usuarios (
  id     INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  email  TEXT NOT NULL UNIQUE
);

CREATE TABLE cursos (
  id     TEXT PRIMARY KEY,                -- clave natural: 'B1'
  titulo TEXT NOT NULL,
  nivel  TEXT NOT NULL CHECK (nivel IN ('basico', 'intermedio', 'avanzado')),
  orden  INTEGER NOT NULL
);

CREATE TABLE secciones (
  id       TEXT PRIMARY KEY,              -- clave natural: 'B1.3'
  curso_id TEXT NOT NULL REFERENCES cursos(id),
  titulo   TEXT NOT NULL,
  orden    INTEGER NOT NULL,
  minutos  INTEGER NOT NULL DEFAULT 60
);

-- Tabla intermedia N:M entre usuarios y secciones
CREATE TABLE lecturas (
  usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
  seccion_id TEXT NOT NULL REFERENCES secciones(id),
  leida_en   TEXT NOT NULL,               -- fecha ISO 8601 en UTC
  PRIMARY KEY (usuario_id, seccion_id)    -- una sección no se lee dos veces
);

CREATE TABLE intentos (
  id         INTEGER PRIMARY KEY,
  usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
  curso_id   TEXT NOT NULL REFERENCES cursos(id),
  nota       INTEGER NOT NULL CHECK (nota BETWEEN 0 AND 5),
  enviado_en TEXT NOT NULL
);
```

- **`INTEGER PRIMARY KEY`** asigna el siguiente número si no indicas el `id`; **`TEXT PRIMARY KEY`** es una clave natural (`'B1.3'`).
- **`NOT NULL`**, obligatoria; **`UNIQUE`**, sin repetidos; **`CHECK (…)`**, una condición que toda fila cumple; **`REFERENCES`**, una clave foránea, y **`ON DELETE CASCADE`** borra los hijos con el padre.
- **`PRIMARY KEY (usuario_id, seccion_id)`** es compuesta: impide leer dos veces la misma sección. **`DROP TABLE IF EXISTS`**, en orden inverso a las dependencias, permite repetir el script.

Datos de prueba, en `datos.sql`:


Crea la base de datos (`<` pasa el archivo a `sqlite3`):

```bash

```

```text
cursos     intentos   lecturas   secciones  usuarios
```

<Callout type="risk">

- **`DROP TABLE` borra los datos para siempre.** Aquí es lo que quieres; nunca ejecutes un `esquema.sql` con `DROP` contra producción.
- **SQLite acepta `'hola'` en una columna `INTEGER`:** lo que protege son `CHECK` y `NOT NULL`. Para tipos estrictos, tablas `STRICT`.
- **Las fechas son texto** en ISO 8601 y UTC (`'2026-10-01T15:00:00Z'`), que se ordena bien. Nunca `'01/10/2026'`: ambiguo y mal ordenado.

</Callout>

## Paso 2: consultar con `SELECT`, `WHERE`, `ORDER BY` y `LIMIT`

**Qué es:** `SELECT` lee filas: elige columnas, las filtra (`WHERE`), las ordena (`ORDER BY`) y limita cuántas (`LIMIT`).

**Cómo se usa:** abre una sesión interactiva.

```bash
sqlite3 academia.db
```

```text
SQLite version 3.51.0 2025-06-12 13:14:41
Enter ".help" for usage hints.
sqlite>
```

`.mode box` dibuja bordes (los comandos con punto son de `sqlite3`, no de SQL), y el `PRAGMA` se explica en el Paso 3:

```sql
.mode box
PRAGMA foreign_keys = ON;
```

```sql
SELECT * FROM cursos;
```

```text
┌────┬────────────────────────┬────────┬───────┐
│ id │         titulo         │ nivel  │ orden │
├────┼────────────────────────┼────────┼───────┤
│ B1 │ TypeScript desde cero  │ basico │ 1     │
│ B2 │ Git y flujo de trabajo │ basico │ 2     │
│ B3 │ Cómo funciona la web   │ basico │ 3     │
└────┴────────────────────────┴────────┴───────┘
```

Filtra, ordena y limita:

```sql
SELECT id, titulo FROM secciones WHERE curso_id = 'B1' ORDER BY orden DESC LIMIT 2;
```

```text
┌──────┬──────────────────────────┐
│  id  │          titulo          │
├──────┼──────────────────────────┤
│ B1.4 │ type vs interface        │
│ B1.3 │ Arrays, tuplas y objetos │
└──────┴──────────────────────────┘
```

Condiciones combinadas:

```sql
SELECT id, titulo, minutos FROM secciones
WHERE curso_id IN ('B2', 'B3') AND titulo LIKE '%Git%';
```

```text
┌──────┬─────────────────────────┬─────────┐
│  id  │         titulo          │ minutos │
├──────┼─────────────────────────┼─────────┤
│ B2.1 │ El modelo mental de Git │ 60      │
└──────┴─────────────────────────┴─────────┘
```

- **`IN (…)`:** el valor está en la lista. **`LIKE '%Git%'`:** contiene "Git"; `%` es cualquier cosa y `_`, un carácter.
- **`AND` y `OR`,** con paréntesis si los mezclas. Una consulta termina en `;`: sin él, el _prompt_ cambia a `...>` y espera.

<Callout type="risk">

- **Sin `ORDER BY`, el orden no está garantizado:** hoy sale el de inserción; tras un índice nuevo, puede que no.
- **`SELECT *` en el código es frágil:** una columna nueva, enorme o sensible (un _hash_ de contraseña), viaja en todas las consultas. Enumera las columnas.
- **Textos entre comillas simples** (`'B1'`). Las dobles son para nombres; `"B1"` funciona en SQLite por compatibilidad y falla en otras bases.

</Callout>

## Paso 3: las restricciones protegen tus datos

**Qué es:** cada restricción rechaza un dato incorrecto **antes** de que entre.

**Cómo se usa:** en la sesión, intenta guardar datos incorrectos.

```sql
INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B9.9', '2026-10-08T10:00:00Z');
INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B1.1', '2026-10-08T10:00:00Z');
INSERT INTO usuarios (nombre, email) VALUES ('Otra Dani', 'dani@ejemplo.com');
INSERT INTO cursos (id, titulo, nivel, orden) VALUES ('X1', 'Prueba', 'experto', 9);
```

```text
Runtime error: FOREIGN KEY constraint failed (19)
Runtime error: UNIQUE constraint failed: lecturas.usuario_id, lecturas.seccion_id (19)
Runtime error: UNIQUE constraint failed: usuarios.email (19)
Runtime error: CHECK constraint failed: nivel IN ('basico', 'intermedio', 'avanzado') (19)
```

- **`FOREIGN KEY`:** la sección `B9.9` no existe. **`UNIQUE` en `lecturas`:** Ana ya leyó `B1.1`, la protección contra el doble clic. **`UNIQUE` en `email`:** correo repetido. **`CHECK`:** `'experto'` no es un nivel.

Ahora, sal (`.quit`) y repite el primer `INSERT` **sin** el `PRAGMA`:

```bash
sqlite3 academia.db "INSERT INTO lecturas (usuario_id, seccion_id, leida_en) VALUES (2, 'B9.9', '2026-10-08T10:00:00Z'); SELECT changes();"
```

```text
1
```

- **Se insertó:** `changes()` dice que cambió 1 fila. Ana tiene una lectura de una sección inexistente. Bórrala y vuelve a la sesión:

```bash
sqlite3 academia.db "DELETE FROM lecturas WHERE seccion_id = 'B9.9';"
sqlite3 academia.db
```

```sql
.mode box
PRAGMA foreign_keys = ON;
```

<Callout type="risk">

- **En SQLite, las claves foráneas están desactivadas por defecto,** y `PRAGMA foreign_keys = ON` va en **cada conexión nueva**. Es el error más común: crees que `REFERENCES` te protege y no. PostgreSQL y MySQL las aplican siempre.
- **La base de datos es la última línea de defensa:** valida también en tu código para dar mensajes claros ("ese correo ya está registrado").

</Callout>

## Paso 4: modificar, borrar y el peligro de olvidar el `WHERE`

**Qué es:** `UPDATE` cambia filas y `DELETE` las borra. El `WHERE` decide **cuáles**.

**Cómo se usa:**

```sql
UPDATE usuarios SET email = 'dani@nuevo.com' WHERE id = 1;
SELECT changes() AS filas_cambiadas;
SELECT * FROM usuarios WHERE id = 1;
```

```text
┌─────────────────┐
│ filas_cambiadas │
├─────────────────┤
│ 1               │
└─────────────────┘
┌────┬────────┬────────────────┐
│ id │ nombre │     email      │
├────┼────────┼────────────────┤
│ 1  │ Dani   │ dani@nuevo.com │
└────┴────────┴────────────────┘
```

- **El correo de Dani cambia en un solo sitio,** gracias a la normalización de B4.2.

Lo que no debes hacer nunca, practicado sobre una **copia**:

```bash
cp academia.db copia.db
sqlite3 -box copia.db "UPDATE secciones SET minutos = 45; SELECT changes() AS filas_cambiadas;"
sqlite3 -box copia.db "DELETE FROM lecturas; SELECT changes() AS filas_borradas;"
rm copia.db
```

```text
┌─────────────────┐
│ filas_cambiadas │
├─────────────────┤
│ 7               │
└─────────────────┘
┌────────────────┐
│ filas_borradas │
├────────────────┤
│ 7              │
└────────────────┘
```

- **Sin `WHERE`,** `UPDATE` cambió **todas** las secciones y `DELETE` borró **todas** las lecturas. Sin confirmación ni papelera.

El borrado en cascada, también sobre una copia:

```bash
cp academia.db prueba.db
sqlite3 prueba.db
```

```sql
.mode box
PRAGMA foreign_keys = ON;
SELECT COUNT(*) AS lecturas_de_ana FROM lecturas WHERE usuario_id = 2;
DELETE FROM usuarios WHERE id = 2;
SELECT COUNT(*) AS lecturas_de_ana FROM lecturas WHERE usuario_id = 2;
DELETE FROM secciones WHERE id = 'B1.1';
.quit
```

```text
┌─────────────────┐
│ lecturas_de_ana │
├─────────────────┤
│ 2               │
└─────────────────┘
┌─────────────────┐
│ lecturas_de_ana │
├─────────────────┤
│ 0               │
└─────────────────┘
Runtime error: FOREIGN KEY constraint failed (19)
```

```bash
rm prueba.db
```

- **Al borrar a Ana, `ON DELETE CASCADE` borró sus lecturas:** no quedan huérfanas.
- **`B1.1` no se pudo borrar:** tiene lecturas que la referencian, sin cascada.

<Callout type="risk">

- **Antes de un `UPDATE` o un `DELETE`, ejecuta el mismo `WHERE` con un `SELECT`.** Si salen las filas esperadas, cambia `SELECT *` por `DELETE`. Es la costumbre que más desastres evita.
- **`ON DELETE CASCADE` borra sin preguntar:** solo para hijos sin sentido sin el padre. Para lo que debe conservarse (facturas), impide el borrado o marca la fila (`borrado_en`).
- **Copia de seguridad antes de operaciones masivas:** `sqlite3 academia.db ".backup antes-de-limpiar.db"`. El plan gratuito de Atlas no las hace solo.

</Callout>

## Paso 5: combinar tablas con `JOIN`

**Qué es:** `JOIN` **vuelve a unir** en una consulta lo que la normalización separó, emparejando filas por sus claves. Un `JOIN` normal solo devuelve filas **con pareja**; **`LEFT JOIN`** conserva todas las de la izquierda y rellena con `NULL`.

**Cómo se usa:** abre la sesión (`sqlite3 academia.db`, `.mode box` y el `PRAGMA`). Las secciones que leyó Ana:

```sql
SELECT u.nombre, s.id AS seccion, s.titulo, l.leida_en
FROM lecturas l
JOIN usuarios u ON u.id = l.usuario_id
JOIN secciones s ON s.id = l.seccion_id
WHERE u.nombre = 'Ana'
ORDER BY l.leida_en;
```

```text
┌────────┬─────────┬────────────────────────────────────┬──────────────────────┐
│ nombre │ seccion │               titulo               │       leida_en       │
├────────┼─────────┼────────────────────────────────────┼──────────────────────┤
│ Ana    │ B1.1    │ Qué es TypeScript y por qué existe │ 2026-10-04T09:30:00Z │
│ Ana    │ B1.2    │ Tipos primitivos e inferencia      │ 2026-10-06T10:00:00Z │
└────────┴─────────┴────────────────────────────────────┴──────────────────────┘
```

- **`FROM lecturas l`:** la tabla de partida, con alias. **`JOIN usuarios u ON u.id = l.usuario_id`:** por cada lectura, su usuario. **`AS`** renombra una columna.

Todas las secciones, leídas o no, como necesita la barra lateral:

```sql
SELECT s.id, s.titulo, l.leida_en
FROM secciones s
LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = 2
WHERE s.curso_id = 'B1'
ORDER BY s.orden;
```

```text
┌──────┬────────────────────────────────────┬──────────────────────┐
│  id  │               titulo               │       leida_en       │
├──────┼────────────────────────────────────┼──────────────────────┤
│ B1.1 │ Qué es TypeScript y por qué existe │ 2026-10-04T09:30:00Z │
│ B1.2 │ Tipos primitivos e inferencia      │ 2026-10-06T10:00:00Z │
│ B1.3 │ Arrays, tuplas y objetos           │                      │
│ B1.4 │ type vs interface                  │                      │
└──────┴────────────────────────────────────┴──────────────────────┘
```

Las que le quedan por leer:

```sql
SELECT s.id, s.titulo
FROM secciones s
LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = 2
WHERE s.curso_id = 'B1' AND l.seccion_id IS NULL
ORDER BY s.orden;
```

```text
┌──────┬──────────────────────────┐
│  id  │          titulo          │
├──────┼──────────────────────────┤
│ B1.3 │ Arrays, tuplas y objetos │
│ B1.4 │ type vs interface        │
└──────┴──────────────────────────┘
```

<Callout type="risk">

- **La condición del usuario va en el `ON`, no en el `WHERE`:** en el `WHERE` descarta las filas con `NULL`, que son justo las no leídas, y el `LEFT JOIN` se vuelve un `JOIN` sin avisar.
- **`= NULL` no funciona nunca:** `NULL` es "desconocido". Se compara con `IS NULL` o `IS NOT NULL`.
- **Un `JOIN` sin condición multiplica filas:** con 1000 usuarios y 134 secciones, 134 000. Si salen demasiadas, revisa los `ON`.

</Callout>

## Paso 6: resumir con `GROUP BY`

**Qué es:** `GROUP BY` agrupa filas, y las **funciones de agregado** (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) calculan un valor por grupo. `WHERE` filtra filas **antes** de agrupar; **`HAVING`** filtra grupos **después**.

**Cómo se usa:** cuántas secciones leyó cada usuario.

```sql
SELECT u.nombre, COUNT(l.seccion_id) AS leidas
FROM usuarios u
LEFT JOIN lecturas l ON l.usuario_id = u.id
GROUP BY u.id
ORDER BY leidas DESC;
```

```text
┌────────┬────────┐
│ nombre │ leidas │
├────────┼────────┤
│ Dani   │ 5      │
│ Ana    │ 2      │
│ Luis   │ 0      │
└────────┴────────┘
```

La media de las evaluaciones por curso:

```sql
SELECT c.id AS curso, COUNT(*) AS intentos, ROUND(AVG(i.nota), 2) AS media, MAX(i.nota) AS mejor
FROM intentos i
JOIN cursos c ON c.id = i.curso_id
GROUP BY c.id;
```

```text
┌───────┬──────────┬───────┬───────┐
│ curso │ intentos │ media │ mejor │
├───────┼──────────┼───────┼───────┤
│ B1    │ 3        │ 4.0   │ 5     │
└───────┴──────────┴───────┴───────┘
```

Los usuarios con al menos 2 lecturas, con `HAVING`:

```sql
SELECT u.nombre, COUNT(l.seccion_id) AS leidas
FROM usuarios u
LEFT JOIN lecturas l ON l.usuario_id = u.id
GROUP BY u.id
HAVING COUNT(l.seccion_id) >= 2;
```

```text
┌────────┬────────┐
│ nombre │ leidas │
├────────┼────────┤
│ Dani   │ 5      │
│ Ana    │ 2      │
└────────┴────────┘
```

<Callout type="risk">

- **`COUNT(*)` frente a `COUNT(columna)`:** con `COUNT(*)`, Luis sale con 1 lectura, porque `LEFT JOIN` le da una fila con `NULL`. Con `LEFT JOIN`, cuenta una columna de la derecha.
- **`2 / 4` es `0` en SQLite:** dos enteros dan un entero. Multiplica primero por `100.0`: `100.0 * leidas / total`.
- **SQLite deja seleccionar una columna no agrupada** y devuelve la de una fila cualquiera. PostgreSQL da error. No te fíes de ese valor.

</Callout>

## Paso 7: consultar desde Node, sin inyección SQL

**Qué es:** una **consulta preparada** usa **`?`** como hueco para cada valor, que se rellena aparte. El valor nunca se interpreta como SQL.

**Cómo se usa:** crea `consultas.js` en `db-lab`.

```js
// Archivo: consultas.js
// Consultar academia.db desde Node, de forma segura e insegura
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync("academia.db");
db.exec("PRAGMA foreign_keys = ON");

// ✅ Consulta preparada: el valor viaja aparte del SQL y nunca se interpreta como código
const progresoPorCurso = db.prepare(`
  SELECT s.curso_id AS curso,
         COUNT(l.seccion_id) AS leidas,
         COUNT(*) AS total,
         ROUND(100.0 * COUNT(l.seccion_id) / COUNT(*), 1) AS porcentaje
  FROM secciones s
  LEFT JOIN lecturas l ON l.seccion_id = s.id AND l.usuario_id = ?
  GROUP BY s.curso_id
  ORDER BY s.curso_id
`);

console.log("Progreso de Dani (id 1):");
console.table(progresoPorCurso.all(1));

// ❌ SQL construido concatenando texto que viene del usuario
function buscarUsuarioInseguro(email) {
  return db.prepare(`SELECT id, nombre, email FROM usuarios WHERE email = '${email}'`).all();
}

// ✅ La misma búsqueda con un parámetro
const buscarUsuario = db.prepare("SELECT id, nombre, email FROM usuarios WHERE email = ?");

const ataque = "x' OR '1'='1";
console.log(`Búsqueda insegura con "${ataque}":`, buscarUsuarioInseguro(ataque).map((u) => u.email));
console.log(`Búsqueda segura con "${ataque}":`, buscarUsuario.all(ataque).map((u) => u.email));
console.log("Búsqueda segura de un correo real:", { ...buscarUsuario.get("ana@ejemplo.com") });

db.close();
```

```bash
node consultas.js
```

```text
Progreso de Dani (id 1):
┌─────────┬───────┬────────┬───────┬────────────┐
│ (index) │ curso │ leidas │ total │ porcentaje │
├─────────┼───────┼────────┼───────┼────────────┤
│ 0       │ 'B1'  │ 4      │ 4     │ 100        │
│ 1       │ 'B2'  │ 1      │ 2     │ 50         │
│ 2       │ 'B3'  │ 0      │ 1     │ 0          │
└─────────┴───────┴────────┴───────┴────────────┘
Búsqueda insegura con "x' OR '1'='1": [ 'dani@nuevo.com', 'ana@ejemplo.com', 'luis@ejemplo.com' ]
Búsqueda segura con "x' OR '1'='1": []
Búsqueda segura de un correo real: { id: 2, nombre: 'Ana', email: 'ana@ejemplo.com' }
```

- **`progresoPorCurso.all(1)`** rellena el `?` con el id de Dani.
- **`buscarUsuarioInseguro` pega el texto del usuario en el SQL.** Con `x' OR '1'='1`, la comilla cierra el texto y lo demás se ejecuta como SQL:

```sql
SELECT id, nombre, email FROM usuarios WHERE email = 'x' OR '1'='1'
```

- **`'1'='1'` siempre es verdadero, y devuelve todos los usuarios.** Es una **inyección SQL**: en un login, entrar sin contraseña. Con la consulta preparada, el texto se busca literalmente, y no encuentra nada.

<Callout type="risk">

- **Nunca construyas SQL concatenando valores del usuario,** tampoco con `${email}`. Siempre `?`. En el texto del SQL solo va lo que controla tu código, como elegir entre dos nombres de columna fijos.
- **MongoDB tiene su versión:** un objeto del cuerpo sin validar como `{ "email": { "$ne": null } }` encuentra a cualquiera. Se evita validando el tipo de cada valor (A5).
- **`DatabaseSync` es síncrona:** cada consulta bloquea Node. Bien para un script; en un servidor con tráfico, detendría las demás peticiones.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Escribe una consulta que devuelva, **para un usuario**, el porcentaje de secciones leídas de **cada curso**, incluidos los cursos en los que no ha leído nada (con 0 %).
2. Escribe otra que devuelva la **última sección leída** por cada usuario, con su título y su fecha (los usuarios sin lecturas no aparecen).
3. Añade a `consultas.js` una función `marcarLeida(usuarioId, seccionId)` con una consulta preparada que no falle si la sección ya estaba leída.

</Callout>

Solución del punto 1. Se parte de **todas** las secciones combinadas con el usuario (`CROSS JOIN`, todas las combinaciones) y se unen las lecturas con `LEFT JOIN`:

```sql
SELECT u.nombre,
       s.curso_id AS curso,
       COUNT(l.seccion_id) AS leidas,
       COUNT(*) AS total,
       ROUND(100.0 * COUNT(l.seccion_id) / COUNT(*), 1) AS porcentaje
FROM usuarios u
CROSS JOIN secciones s
LEFT JOIN lecturas l ON l.usuario_id = u.id AND l.seccion_id = s.id
WHERE u.id = 1
GROUP BY u.id, s.curso_id
ORDER BY s.curso_id;
```

```text
┌────────┬───────┬────────┬───────┬────────────┐
│ nombre │ curso │ leidas │ total │ porcentaje │
├────────┼───────┼────────┼───────┼────────────┤
│ Dani   │ B1    │ 4      │ 4     │ 100.0      │
│ Dani   │ B2    │ 1      │ 2     │ 50.0       │
│ Dani   │ B3    │ 0      │ 1     │ 0.0        │
└────────┴───────┴────────┴───────┴────────────┘
```

Solución del punto 2. Por cada usuario, la lectura con la fecha **máxima**, con una subconsulta:

```sql
SELECT u.nombre, s.id AS seccion, s.titulo, l.leida_en
FROM lecturas l
JOIN usuarios u ON u.id = l.usuario_id
JOIN secciones s ON s.id = l.seccion_id
WHERE l.leida_en = (
  SELECT MAX(l2.leida_en) FROM lecturas l2 WHERE l2.usuario_id = l.usuario_id
)
ORDER BY u.nombre;
```

```text
┌────────┬─────────┬───────────────────────────────┬──────────────────────┐
│ nombre │ seccion │            titulo             │       leida_en       │
├────────┼─────────┼───────────────────────────────┼──────────────────────┤
│ Ana    │ B1.2    │ Tipos primitivos e inferencia │ 2026-10-06T10:00:00Z │
│ Dani   │ B2.1    │ El modelo mental de Git       │ 2026-10-07T15:05:00Z │
└────────┴─────────┴───────────────────────────────┴──────────────────────┘
```

- **Es la consulta del botón "Continuar donde lo dejaste"** del temario.

Solución del punto 3. Añade esto al final de `consultas.js`, **antes** de `db.close();`:

```js
// Marca una sección como leída. Si ya lo estaba, no hace nada (idempotente, como un PUT)
const insertarLectura = db.prepare(`
  INSERT INTO lecturas (usuario_id, seccion_id, leida_en)
  VALUES (?, ?, ?)
  ON CONFLICT (usuario_id, seccion_id) DO NOTHING
`);

function marcarLeida(usuarioId, seccionId) {
  const { changes } = insertarLectura.run(usuarioId, seccionId, new Date().toISOString());
  return changes === 1 ? "marcada" : "ya estaba leída";
}

console.log("B1.3 para Ana:", marcarLeida(2, "B1.3"));
console.log("B1.3 para Ana, otra vez:", marcarLeida(2, "B1.3"));
```

```text
B1.3 para Ana: marcada
B1.3 para Ana, otra vez: ya estaba leída
```

- **`ON CONFLICT … DO NOTHING`** convierte el error de `UNIQUE` en "no hagas nada". Es lo que hace esta plataforma en MongoDB con un _upsert_ sobre su índice único.

<Callout type="risk">

- **Dos lecturas con la misma fecha exacta** salen las dos en el punto 2. Se resuelve con funciones de ventana (`ROW_NUMBER() OVER (PARTITION BY …)`), en cursos avanzados.
- **No mezcles fechas con y sin zona horaria** en una columna: el orden alfabético dejaría de ser el temporal. `toISOString()` da UTC con milisegundos.
- **Ejecutar `consultas.js` dos veces** deja la lectura de `B1.3` creada desde la primera. Para empezar de cero, vuelve a ejecutar `esquema.sql` y `datos.sql`.

</Callout>

<Callout type="mastery">

Escribes un `SELECT` con `JOIN` y `GROUP BY` sin ayuda: sabes cuándo hace falta un `LEFT JOIN` y dónde poner sus condiciones, cuentas con `COUNT(columna)` en lugar de `COUNT(*)`, nunca lanzas un `UPDATE` o un `DELETE` sin comprobar antes su `WHERE`, y desde el código usas siempre consultas preparadas.

</Callout>

## Resumen

- `CREATE TABLE` con restricciones que la base de datos hace cumplir.
- En SQLite, `PRAGMA foreign_keys = ON` en cada conexión.
- `UPDATE` y `DELETE`, siempre con un `WHERE` comprobado antes con `SELECT`.
- `JOIN` une; `LEFT JOIN` conserva lo que no tiene pareja; `GROUP BY` resume y `HAVING` filtra grupos.
- Desde el código, consultas preparadas con `?`: nunca concatenar texto del usuario.
