Con los datos de B4.3 todo es instantáneo, pero con 100 000 filas una consulta sin índice se nota, y con millones puede tumbar el servidor. El **índice** es lo que más rendimiento da… y lo que más se usa mal. Aquí lo mides todo: el antes, el después y lo que cuesta.

**Requisitos:** el proyecto `db-lab` con `academia.db` de B4.3.

## Paso 1: qué es un índice

**Qué es:** una estructura aparte, **ordenada** por una o varias columnas, que guarda dónde están las filas con cada valor. Es un árbol B (_B-tree_): encontrar un valor entre un millón cuesta unos 20 pasos, no un millón.

**Cómo se usa:** `EXPLAIN QUERY PLAN` dice **cómo** piensa ejecutar la base de datos una consulta. **`SCAN`** recorre la tabla entera; **`SEARCH … USING INDEX`** va directo a las filas.

```bash
sqlite3 academia.db ".indexes"
sqlite3 academia.db "EXPLAIN QUERY PLAN SELECT * FROM usuarios WHERE email = 'ana@ejemplo.com'"
sqlite3 academia.db "EXPLAIN QUERY PLAN SELECT * FROM lecturas WHERE seccion_id = 'B1.1'"
```

```text
sqlite_autoindex_cursos_1     sqlite_autoindex_secciones_1
sqlite_autoindex_lecturas_1   sqlite_autoindex_usuarios_1
QUERY PLAN
`--SEARCH usuarios USING INDEX sqlite_autoindex_usuarios_1 (email=?)
QUERY PLAN
`--SCAN lecturas
```

- **SQLite crea solo un índice por cada `UNIQUE` y cada clave primaria compuesta,** porque necesita buscar rápido para comprobar repetidos. Por eso buscar por `email` es un `SEARCH`.
- **Las lecturas de una sección son un `SCAN`:** nadie creó un índice por `seccion_id`.

<Callout type="risk">

- **Que exista un índice no garantiza que se use:** con la consulta mal escrita (Paso 4), sigue siendo un `SCAN`. Mira siempre el plan.
- **Con tablas diminutas, el tiempo no dice nada:** 7 filas son instantáneas con o sin índice. Por eso el resto trabaja con 100 000.

</Callout>

## Paso 2: el banco de pruebas con 100 000 filas

**Qué es:** un script que crea 1000 usuarios con 100 entrenos cada uno y mide la misma consulta en cinco escenarios.

**Cómo se usa:** crea `indices.js` en `db-lab`.

```js
// Archivo: indices.js
// 100 000 entrenos: cuánto ganan las lecturas con un índice y cuánto pierden las escrituras
import { rmSync, statSync } from "node:fs";
import { DatabaseSync } from "node:sqlite";

const ARCHIVO = "indices.db";
const FILAS = 100_000;
const USUARIOS = 1_000;

// Mide cuánto tarda una función, repitiéndola para que el resultado sea estable
function medir(fn, repeticiones = 50) {
  const inicio = performance.now();
  for (let i = 0; i < repeticiones; i++) fn();
  return (performance.now() - inicio) / repeticiones;
}

function crearBaseDeDatos(indices) {
  rmSync(ARCHIVO, { force: true });
  const db = new DatabaseSync(ARCHIVO);
  db.exec(`CREATE TABLE entrenos (
    id INTEGER PRIMARY KEY,
    usuario_id INTEGER NOT NULL,
    fecha TEXT NOT NULL,
    km REAL NOT NULL
  )`);
  for (const sql of indices) db.exec(sql);

  const insertar = db.prepare("INSERT INTO entrenos (usuario_id, fecha, km) VALUES (?, ?, ?)");
  const inicio = performance.now();
  db.exec("BEGIN"); // todas las inserciones en una transacción: mucho más rápido (B4.5)
  for (let i = 0; i < FILAS; i++) {
    const usuarioId = (i % USUARIOS) + 1;
    const dia = new Date(Date.UTC(2025, 0, 1) + (i % 365) * 86_400_000).toISOString().slice(0, 10);
    insertar.run(usuarioId, dia, Math.round(Math.random() * 150) / 10);
  }
  db.exec("COMMIT");
  const msInsertar = performance.now() - inicio;
  return { db, msInsertar, kb: Math.round(statSync(ARCHIVO).size / 1024) };
}

const plan = (db, sql) => db.prepare(`EXPLAIN QUERY PLAN ${sql}`).all().map((p) => p.detail).join(" + ");

// ─── 1. Sin índices ───
const { db } = crearBaseDeDatos([]);
const CONSULTA = "SELECT fecha, km FROM entrenos WHERE usuario_id = ? ORDER BY fecha DESC LIMIT 10";
const consulta = db.prepare(CONSULTA);

console.log("Sin índice:");
console.log(`  plan:   ${plan(db, CONSULTA.replace("?", "42"))}`);
console.log(`  tiempo: ${medir(() => consulta.all(42)).toFixed(3)} ms por consulta`);

// ─── 2. Índice simple en usuario_id ───
db.exec("CREATE INDEX idx_entrenos_usuario ON entrenos (usuario_id)");
const conIndice = db.prepare(CONSULTA);
console.log("Con índice en (usuario_id):");
console.log(`  plan:   ${plan(db, CONSULTA.replace("?", "42"))}`);
console.log(`  tiempo: ${medir(() => conIndice.all(42)).toFixed(3)} ms por consulta`);

// ─── 3. Índice compuesto en el orden correcto: (usuario_id, fecha) ───
db.exec("DROP INDEX idx_entrenos_usuario");
db.exec("CREATE INDEX idx_entrenos_usuario_fecha ON entrenos (usuario_id, fecha)");
const compuesto = db.prepare(CONSULTA);
console.log("Con índice compuesto (usuario_id, fecha):");
console.log(`  plan:   ${plan(db, CONSULTA.replace("?", "42"))}`);
console.log(`  tiempo: ${medir(() => compuesto.all(42)).toFixed(3)} ms por consulta`);

// ─── 4. El mismo índice compuesto, pero consultando solo por fecha ───
const SOLO_FECHA = "SELECT COUNT(*) FROM entrenos WHERE fecha = '2025-06-01'";
console.log("Consulta solo por fecha con el índice (usuario_id, fecha):");
console.log(`  plan:   ${plan(db, SOLO_FECHA)}`);
db.close();

// ─── 5. El coste: tiempo de inserción y tamaño del archivo ───
console.log("Coste de mantener índices al insertar 100 000 filas:");
for (const [nombre, indices] of [
  ["0 índices", []],
  ["1 índice ", ["CREATE INDEX i1 ON entrenos (usuario_id, fecha)"]],
  ["3 índices", ["CREATE INDEX i1 ON entrenos (usuario_id, fecha)", "CREATE INDEX i2 ON entrenos (fecha)", "CREATE INDEX i3 ON entrenos (km)"]],
]) {
  const resultado = crearBaseDeDatos(indices);
  resultado.db.close();
  console.log(`  ${nombre}: ${Math.round(resultado.msInsertar)} ms · ${resultado.kb} KB`);
}
rmSync(ARCHIVO, { force: true });
```

La consulta medida, "los 10 últimos entrenos de un usuario":

```sql
SELECT fecha, km FROM entrenos WHERE usuario_id = ? ORDER BY fecha DESC LIMIT 10
```

- **`medir`** repite 50 veces y saca la media: una sola medida varía demasiado. **`plan`** une las líneas de `EXPLAIN QUERY PLAN`.
- **Las 100 000 inserciones van en una transacción** (`BEGIN` y `COMMIT`): sin ella, SQLite confirmaría en disco cada fila por separado (B4.5).

```bash
node indices.js
```

```text
Sin índice:
  plan:   SCAN entrenos + USE TEMP B-TREE FOR ORDER BY
  tiempo: 1.837 ms por consulta
Con índice en (usuario_id):
  plan:   SEARCH entrenos USING INDEX idx_entrenos_usuario (usuario_id=?) + USE TEMP B-TREE FOR ORDER BY
  tiempo: 0.030 ms por consulta
Con índice compuesto (usuario_id, fecha):
  plan:   SEARCH entrenos USING INDEX idx_entrenos_usuario_fecha (usuario_id=?)
  tiempo: 0.008 ms por consulta
Consulta solo por fecha con el índice (usuario_id, fecha):
  plan:   SCAN entrenos USING COVERING INDEX idx_entrenos_usuario_fecha
Coste de mantener índices al insertar 100 000 filas:
  0 índices: 80 ms · 2964 KB
  1 índice : 126 ms · 5292 KB
  3 índices: 329 ms · 9104 KB
```

Tus tiempos serán otros, pero las proporciones se mantienen.

<Callout type="risk">

- **Tu Mac no es producción:** aquí todo cabe en memoria y en un SSD. Con millones de filas que no caben, la diferencia entre `SCAN` y `SEARCH` pasa de milisegundos a **segundos**.
- **`Math.random()` cambia los datos en cada ejecución:** no afecta a los tiempos, pero un test necesitaría datos deterministas.

</Callout>

## Paso 3: del recorrido completo a la búsqueda directa

**Qué es:** sin índice, el plan es `SCAN entrenos + USE TEMP B-TREE FOR ORDER BY`: lee las 100 000 filas para quedarse con 100, y luego las **ordena** en una estructura temporal.

**Cómo se usa:** un índice en `usuario_id` se crea con una línea.

```sql
CREATE INDEX idx_entrenos_usuario ON entrenos (usuario_id);
```

- **El plan pasa a `SEARCH … USING INDEX idx_entrenos_usuario (usuario_id=?)`,** y la consulta, de **1,837 ms** a **0,030 ms**: unas **60 veces más rápida**.
- **Sigue `USE TEMP B-TREE FOR ORDER BY`:** el índice encuentra las filas, pero no ordenadas por fecha.
- **El nombre `idx_tabla_columnas`** te dirá qué es cuando lo veas en un plan dentro de seis meses.

<Callout type="risk">

- **Crear un índice en una tabla grande de producción** puede tardar minutos y, en algunas bases de datos, bloquear las escrituras. Créalos al diseñar la tabla, o con poco tráfico.
- **Si la consulta devuelve casi toda la tabla,** el índice puede ser **más lento** que un `SCAN`, y la base de datos lo ignora. Brillan cuando se selecciona una parte pequeña.

</Callout>

## Paso 4: índices compuestos, el orden importa

**Qué es:** un índice compuesto se ordena **primero** por la primera columna y, **dentro de cada valor**, por la segunda. La regla: **primero las columnas con igualdad (`=`), después la de orden o rango (`>`, `<`, `BETWEEN`)**.

**Cómo se usa:** con `(usuario_id, fecha)`, las filas del usuario 42 están juntas y ya ordenadas por fecha.

```text
usuario_id │ fecha
───────────┼────────────
        41 │ 2025-12-25
        42 │ 2025-01-01   ← empiezan las filas del usuario 42…
        42 │ 2025-01-02
        42 │ …
        42 │ 2025-12-31   ← …ya ordenadas por fecha
        43 │ 2025-01-01
```

- **El plan queda sin `USE TEMP B-TREE`,** y la consulta baja a **0,008 ms**: lee las 10 últimas directamente.
- **La cara B, la cuarta línea del resultado:** con ese índice, buscar **solo por fecha** vuelve a ser un `SCAN`. `USING COVERING INDEX` significa que recorre el índice entero en lugar de la tabla, pero sigue siendo un recorrido completo.

<Callout type="risk">

- **`(a, b)` sirve para `a` y para `a` + `b`, no para `b` sola.** Por lo mismo, hace innecesario un índice solo en `a`.
- **Una función sobre la columna anula el índice:** `WHERE LOWER(email) = …` o `substr(fecha, 1, 7)` no lo usan. Normaliza al guardar (correos en minúsculas, como esta plataforma) y escribe rangos: `fecha >= '2025-06-01' AND fecha < '2025-07-01'`.
- **`LIKE '%texto%'` nunca usa un índice normal:** empezar por `%` obliga a mirarlo todo. Para eso hay índices de texto completo (_full-text search_).

</Callout>

## Paso 5: el coste de los índices

**Qué es:** cada índice es una copia ordenada que hay que mantener al día. Acelera las lecturas a cambio de escrituras más lentas y más espacio.

**Cómo se usa:** la última parte del resultado mide ese coste.

```text
Coste de mantener índices al insertar 100 000 filas:
  0 índices: 80 ms · 2964 KB
  1 índice : 126 ms · 5292 KB
  3 índices: 329 ms · 9104 KB
```

- **Con 3 índices, insertar es 4 veces más lento:** cada `INSERT`, `UPDATE` o `DELETE` actualiza la tabla **y cada índice**. Y el archivo ocupa **el triple**.
- **En una app típica compensa,** porque cada dato se lee muchas más veces de las que se escribe. Un índice que ninguna consulta usa es coste puro.

Un índice **único** además **impide duplicados**:

```sql
CREATE UNIQUE INDEX idx_usuarios_email ON usuarios (email);
```

- **Es lo que creó SQLite por el `UNIQUE` de `email`,** y lo que hace esta plataforma en MongoDB con `{ userId: 1, sectionId: 1 }, { unique: true }`: impide marcar dos veces la misma sección, aunque lleguen dos peticiones exactamente a la vez.

<Callout type="risk">

- **No indexes todas las columnas "por si acaso":** cada índice frena todas las escrituras para siempre. Indexa las consultas **frecuentes**, no las de un informe mensual.
- **Un índice único no se crea si ya hay duplicados:** primero hay que limpiarlos. Mejor definir las restricciones desde el principio.
- **En MongoDB la lógica es idéntica:** `explain()` muestra `COLLSCAN` (el `SCAN`) o `IXSCAN` (el `SEARCH`), y el orden de los campos importa igual (B5.6).

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Para cada una de estas consultas frecuentes de `academia.db`, mira su plan con `EXPLAIN QUERY PLAN` y decide si necesita un índice:
   - Cuántas personas han leído una sección: `SELECT * FROM lecturas WHERE seccion_id = 'B1.1'`.
   - Los intentos de un usuario en un curso, del más reciente al más antiguo: `SELECT * FROM intentos WHERE usuario_id = 1 AND curso_id = 'B1' ORDER BY enviado_en DESC`.
   - Las secciones de un curso en orden: `SELECT * FROM secciones WHERE curso_id = 'B1' ORDER BY orden`.
2. Escribe los índices en un archivo `indices-academia.sql`, aplícalos y comprueba que los planes pasan a `SEARCH` y que desaparece `USE TEMP B-TREE`.
3. Compara tus índices con los que crea esta plataforma en MongoDB (en `scripts/db-setup.ts`) para sus colecciones de progreso y evaluaciones.

</Callout>

Solución. Los planes de partida:

```text
SELECT * FROM lecturas WHERE seccion_id = 'B1.1'
`--SCAN lecturas

SELECT * FROM intentos WHERE usuario_id = 1 AND curso_id = 'B1' ORDER BY enviado_en DESC
|--SCAN intentos
`--USE TEMP B-TREE FOR ORDER BY

SELECT * FROM secciones WHERE curso_id = 'B1' ORDER BY orden
|--SCAN secciones
`--USE TEMP B-TREE FOR ORDER BY
```

- **Las lecturas de un usuario ya usan un índice:** el de la clave primaria `(usuario_id, seccion_id)`. Las de una sección no, porque `seccion_id` es la **segunda** columna (Paso 4).

`indices-academia.sql`:

```sql
-- Archivo: indices-academia.sql
-- Índices para las consultas frecuentes de academia.db
CREATE INDEX IF NOT EXISTS idx_lecturas_seccion ON lecturas (seccion_id);
CREATE INDEX IF NOT EXISTS idx_intentos_usuario_curso_fecha ON intentos (usuario_id, curso_id, enviado_en);
CREATE INDEX IF NOT EXISTS idx_secciones_curso_orden ON secciones (curso_id, orden);
```

```bash
sqlite3 academia.db < indices-academia.sql
sqlite3 academia.db "EXPLAIN QUERY PLAN SELECT * FROM lecturas WHERE seccion_id = 'B1.1'"
sqlite3 academia.db "EXPLAIN QUERY PLAN SELECT * FROM intentos WHERE usuario_id = 1 AND curso_id = 'B1' ORDER BY enviado_en DESC"
sqlite3 academia.db "EXPLAIN QUERY PLAN SELECT * FROM secciones WHERE curso_id = 'B1' ORDER BY orden"
```

```text
QUERY PLAN
`--SEARCH lecturas USING INDEX idx_lecturas_seccion (seccion_id=?)
QUERY PLAN
`--SEARCH intentos USING INDEX idx_intentos_usuario_curso_fecha (usuario_id=? AND curso_id=?)
QUERY PLAN
`--SEARCH secciones USING INDEX idx_secciones_curso_orden (curso_id=?)
```

- **Los tres pasan a `SEARCH`, sin `USE TEMP B-TREE`:** las igualdades (`usuario_id`, `curso_id`) van primero y el orden (`enviado_en`), al final.
- **La plataforma** crea en `scripts/db-setup.ts` `{ userId: 1, sectionId: 1 }` único, `{ userId: 1, courseId: 1 }` y `{ userId: 1, courseId: 1, submittedAt: -1 }`, **el mismo índice** de intentos que acabas de diseñar (`-1` es descendente). No tiene uno por sección porque nunca pregunta quién leyó una sección: los índices salen de las consultas que la app **realmente** hace.

<Callout type="risk">

- **`IF NOT EXISTS`** permite repetir el script. Sin él, falla con `index … already exists`.
- **Un índice solo para una consulta de administración** puede no compensar, porque frena cada lectura nueva. Compara cuánto se ejecuta la consulta con cuánto se escribe en la tabla.
- **`intentos WHERE curso_id = 'B1'` sola sigue siendo un `SCAN`:** `curso_id` no es la primera columna de ningún índice.

</Callout>

<Callout type="mastery">

Sabes qué campos de tus consultas necesitan índice: lees un `EXPLAIN QUERY PLAN` y distingues `SCAN` de `SEARCH`, ordenas los índices compuestos con las igualdades primero y el orden al final, sabes que un índice `(a, b)` no sirve para buscar por `b`, y no creas índices que ninguna consulta frecuente usa, porque cada uno frena las escrituras.

</Callout>

## Resumen

- Un índice ordenado permite ir directo a las filas (`SEARCH`) en lugar de recorrerlas (`SCAN`).
- `EXPLAIN QUERY PLAN` muestra el plan; `USE TEMP B-TREE` es ordenar en memoria.
- Compuesto: igualdades primero y el orden o rango al final. `(a, b)` no sirve para `b`.
- Cada índice frena las escrituras y ocupa espacio: aquí, 3 índices = 4 veces más lento y el triple.
- Los únicos impiden duplicados. Indexa las consultas frecuentes.
