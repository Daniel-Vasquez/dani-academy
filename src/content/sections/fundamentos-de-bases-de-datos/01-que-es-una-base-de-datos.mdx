¿Por qué no guardar los datos de una app en un `datos.json` y ya? Aquí lo pruebas: 50 escrituras simultáneas sobre un archivo JSON frente a las mismas sobre SQLite. El resultado explica qué hace una base de datos por ti.

**Requisitos:** Node.js 22.13 o superior (trae `node:sqlite`; `node -v`) y `sqlite3`, que viene con macOS (`sqlite3 --version`).

## Paso 1: crear el laboratorio

**Qué es:** `db-lab`, el proyecto que usarás en todo B4. Node trae SQLite integrado, así que no hay nada que instalar.

**Cómo se usa:**

```bash
mkdir db-lab

code .
```

`package.json`:

```json
{
  "name": "db-lab",
  "version": "1.0.0",
  "private": true,

```

</Callout>

## Paso 2: el experimento, JSON frente a SQLite

**Qué es:** la API de tareas de B3.3 guardando en un archivo: por cada tarea, **lee** el archivo, **añade** la tarea y lo **reescribe** entero. Con 50 personas pulsando "Guardar" a la vez, el patrón falla.

**Cómo se usa:** crea `json-vs-sqlite.js`.

```js
// Archivo: json-vs-sqlite.js
// Compara un archivo JSON con una base de datos SQLite ante 50 escrituras simultáneas
import { readFile, writeFile, rm } from "node:fs/promises";
import { DatabaseSync } from "node:sqlite";

const ESCRITURAS = 50;

// ─── 1. Un archivo JSON como "base de datos" ───
const ARCHIVO = "tareas.json";
await writeFile(ARCHIVO, "[]");

async function anadirTareaJson(titulo) {
  const tareas = JSON.parse(await readFile(ARCHIVO, "utf-8")); // leer todo
  tareas.push({ id: tareas.length + 1, titulo }); // modificar en memoria
  await writeFile(ARCHIVO, JSON.stringify(tareas, null, 2)); // reescribir todo
}

// 50 peticiones "a la vez", como 50 usuarios pulsando "Guardar" en el mismo segundo
await Promise.all(Array.from({ length: ESCRITURAS }, (_, i) => anadirTareaJson(`Tarea ${i + 1}`)));
const enJson = JSON.parse(await readFile(ARCHIVO, "utf-8"));
console.log(`JSON:   ${ESCRITURAS} escrituras → ${enJson.length} tareas guardadas`);

// ─── 2. La misma operación con SQLite ───
await rm("tareas.db", { force: true });
const db = new DatabaseSync("tareas.db");
db.exec("CREATE TABLE tareas (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL)");
const insertar = db.prepare("INSERT INTO tareas (titulo) VALUES (?)");

await Promise.all(Array.from({ length: ESCRITURAS }, async (_, i) => insertar.run(`Tarea ${i + 1}`)));
const { total } = db.prepare("SELECT COUNT(*) AS total FROM tareas").get();
console.log(`SQLite: ${ESCRITURAS} escrituras → ${total} tareas guardadas`);

// ─── 3. Un corte a mitad de escritura ───
const completo = JSON.stringify(enJson, null, 2);
await writeFile(ARCHIVO, completo.slice(0, completo.length / 2)); // el proceso "muere" a la mitad
try {
  JSON.parse(await readFile(ARCHIVO, "utf-8"));
} catch (error) {
  console.log(`JSON tras un corte: ${error.message}`);
}
db.close();
```

```bash
node json-vs-sqlite.js
```

```text
JSON:   50 escrituras → 1 tareas guardadas
SQLite: 50 escrituras → 50 tareas guardadas
JSON tras un corte: Unterminated string in JSON at position 24 (line 4 column 6)
```

- **De 50 tareas, el JSON conserva una:** las 50 llamadas leen el archivo cuando aún está vacío, cada una añade **su** tarea a **su** copia y la última en escribir borra a las otras 49. Es una **escritura perdida** (_lost update_), una **condición de carrera**.
- **A veces el archivo queda corrupto:** una escritura empieza antes de que termine otra, y el script se detiene con `SyntaxError: Unexpected end of JSON input`.
- **La tercera línea simula un corte a mitad de escribir** (un despliegue, falta de memoria): medio JSON, y **toda** la información ilegible. SQLite guardó las 50 sin cambiar tu lógica.

<Callout type="risk">

- **No hacen falta muchos usuarios:** un doble clic en "Guardar" o dos pestañas bastan para perder datos con un archivo JSON.
- **Tampoco funciona en Vercel:** el sistema de archivos de una función es de solo lectura (salvo `/tmp`, que se borra en cada arranque) y cada instancia tiene el suyo.

</Callout>

## Paso 3: qué hace un gestor de bases de datos por ti

**Qué es:** un **SGBD** (sistema gestor de bases de datos) es el programa que hay detrás: SQLite, PostgreSQL, MySQL o MongoDB. Tiene cuatro trabajos:

| Trabajo            | Qué significa                                                                         | Lo que hacía tu archivo JSON                              |
| ------------------ | ------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Almacenamiento** | Guarda los datos en disco en un formato eficiente, en páginas pequeñas                | Reescribía el archivo **entero** por cada cambio          |
| **Consultas**      | Encuentra datos sin leerlo todo: "las tareas pendientes de Dani, ordenadas por fecha" | Había que cargar todo en memoria y filtrar con JavaScript |
| **Concurrencia**   | Ordena las operaciones simultáneas para que ninguna pise a otra                       | Perdió 49 de 50 escrituras                                |
| **Durabilidad**    | Lo confirmado sobrevive a un corte: nunca deja un archivo a medias                    | Medio JSON ilegible                                       |

**Cómo se usa:** mira por dentro la base de datos creada.

```bash
ls -la tareas.db
sqlite3 tareas.db ".schema"
sqlite3 -header -column tareas.db "SELECT id, titulo FROM tareas ORDER BY id DESC LIMIT 3;"
sqlite3 tareas.db "SELECT COUNT(*) FROM tareas WHERE titulo LIKE 'Tarea 1%';"
```

```text
-rw-r--r--@ 1 tu-usuario  staff  8192  9 oct 15:33 tareas.db
CREATE TABLE tareas (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL);
id  titulo
--  --------
50  Tarea 50
49  Tarea 49
48  Tarea 48
11
```

- **`tareas.db` es un archivo de 8 KB** en páginas de 4 KB: al insertar, SQLite solo cambia las páginas afectadas.
- **`.schema`** muestra la tabla, sus columnas y sus restricciones (`NOT NULL`).
- **La última consulta** cuenta los títulos que empiezan por "Tarea 1" sin escribir un bucle. Ese lenguaje es **SQL** (B4.3).

<Callout type="risk">

- **Una base de datos no te salva de leer → modificar → escribir en tu código:** también ahí se pierden escrituras. Pide la operación a la base de datos (`UPDATE … SET contador = contador + 1`) o usa transacciones (B4.5).
- **El `.db` no se copia "en caliente":** con la app escribiendo, la copia puede salir corrupta. Usa `sqlite3 tareas.db ".backup copia.db"`.

</Callout>

## Paso 4: los tipos de bases de datos

**Qué es:** todas cumplen los cuatro trabajos, pero organizan los datos de forma distinta. **Relacional:** **tablas** con columnas fijas, relacionadas por identificadores. **Documental:** **documentos** JSON en colecciones, que pueden **anidar** datos relacionados.

**Cómo se usa:** los mismos datos, Dani y dos entrenos, en los dos modelos. Relacional:

```text
usuarios                         entrenos
| id | nombre | email         |  | id | usuario_id | fecha      | km  |
|----|--------|---------------|  |----|------------|------------|-----|
| 1  | Dani   | dani@ejem.com |  | 1  | 1          | 2026-10-01 | 5.2 |
                                 | 2  | 1          | 2026-10-03 | 8.0 |
```

Documental:

```json
{
  "_id": 1,
  "nombre": "Dani",
  "email": "dani@ejem.com",
  "entrenos": [
    { "fecha": "2026-10-01", "km": 5.2 },
    { "fecha": "2026-10-03", "km": 8.0 }
  ]
}
```

| Tipo            | Ejemplos                                                                                            | Cómo guarda                                        | Brilla en                                                                          | Sufre con                                                         |
| --------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **Relacional**  | PostgreSQL, MySQL, SQLite                                                                           | Tablas con columnas fijas, relacionadas por claves | Datos muy relacionados y consistencia estricta (pagos, inventario, reservas)       | Datos de forma muy variable; cambiar el esquema en tablas enormes |
| **Documental**  | MongoDB                                                                                             | Documentos JSON (BSON) en colecciones              | Datos que se leen juntos, esquema que evoluciona, desarrollo rápido con JavaScript | Muchas relaciones cruzadas que hay que combinar en cada consulta  |
| **Clave-valor** | Redis, Vercel KV                                                                                    | Una clave → un valor, normalmente en memoria       | Cachés, sesiones, contadores, límites de peticiones: lecturas en microsegundos     | Cualquier consulta que no sea "dame el valor de esta clave"       |
| **Otras**       | Elasticsearch (búsqueda), InfluxDB (series temporales), Neo4j (grafos), pgvector (vectores para IA) | Especializadas                                     | Un problema concreto                                                               | Todo lo demás                                                     |

- **La regla práctica:** relacional si las relaciones y la consistencia son el centro (en la duda, PostgreSQL); documental si los datos se leen como objetos completos y su forma evoluciona; clave-valor como complemento para velocidad. Muchas apps combinan varias.

<Callout type="risk">

- **"NoSQL no tiene esquema" es medio verdad:** tu código siempre espera una forma. Sin validación (esta plataforma usa `$jsonSchema`), acabas con documentos de cinco formas distintas.
- **Anidar sin límite rompe:** miles de entrenos dentro del usuario hacen crecer el documento hacia el máximo de 16 MB, y cada lectura los arrastra todos. Cuándo anidar es la gran decisión del modelado (I4).
- **Elegir por moda sale caro:** migrar de base de datos con datos en producción es de lo más arriesgado. Elige por la forma de tus datos y tus consultas.

</Callout>

## Paso 5: embebida frente a servidor

**Qué es:** **embebida** (SQLite): la base de datos es un archivo y el motor, una librería dentro de tu programa, sin red ni nada que arrancar. **Servidor** (PostgreSQL, MySQL, MongoDB): otro programa, normalmente en otra máquina, al que te conectas por red con usuario y contraseña, y que comparten muchas instancias de tu app.

**Cómo se usa:** tu clúster de **MongoDB Atlas** es un servidor, y conecta con todo lo de B3:

- **Vive en una región** de AWS, Google Cloud o Azure, la que elegiste al crearlo (_Overview_ del clúster).
- **Es un _replica set_:** tres servidores con copias de los datos; si uno cae, otro toma el relevo. `mongodb+srv://` es un registro DNS de tipo `SRV` (B3.2) que los lista.
- **Cada consulta viaja cifrada con TLS** (B3.5) desde tu función de Vercel, y solo se aceptan las IPs de _Network Access_. Vercel no tiene IPs fijas: hace falta `0.0.0.0/0`.

<Callout type="risk">

- **SQLite no sirve directamente en Vercel:** el `.db` viviría en el disco efímero de cada función. Hay servicios específicos (como Turso); para Vercel, lo natural es un servidor como Atlas.
- **Región de Atlas cerca de la de Vercel:** una función en Washington (`iad1`, la de por defecto) contra un clúster en São Paulo multiplica la latencia por cada consulta.
- **La cadena de conexión es un secreto,** con usuario y contraseña: en `.env` y en las variables de Vercel, nunca en Git.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Lista los datos que guarda (o guardaría) tu **Planificador 2026**: tareas, categorías, usuarios, preferencias, sesiones, eventos de calendario, adjuntos…
2. Para cada uno, decide en qué tipo de base de datos encajaría mejor y justifícalo con lo aprendido: forma de los datos, relaciones, cómo se consultan y con qué frecuencia cambian.
3. Modifica `json-vs-sqlite.js` para que, en lugar de crear 50 tareas, haga 50 veces "marcar la tarea 1 como hecha y sumar 1 a su contador de ediciones". ¿Cuántas ediciones registra el JSON? Explica por qué.

</Callout>

Solución del punto 2, una propuesta razonada:

| Dato                                                       | Tipo                                                                          | Por qué                                                                                            |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Usuarios (nombre, correo, _hash_ de contraseña)            | Documental (MongoDB) o relacional                                             | Forma estable y consultas por correo; cualquiera de los dos, y ya usas MongoDB                     |
| Tareas (título, categoría, hecha, fecha límite, subtareas) | Documental                                                                    | Se leen como objetos completos; las subtareas se anidan en la tarea                                |
| Categorías de color                                        | Ninguna: constante en el código                                               | Son cuatro valores fijos que no edita el usuario                                                   |
| Preferencias (tema, vista por defecto)                     | `localStorage` o un campo del usuario                                         | Pequeñas, de un solo usuario y no secretas                                                         |
| Sesiones de login                                          | Documental (como Better Auth en esta plataforma) o clave-valor (Redis)        | Lectura en cada petición por una clave única y caducidad automática                                |
| Eventos de calendario compartidos con otras personas       | Relacional                                                                    | Muchas relaciones N:M (eventos ↔ invitados) y consistencia (no reservar dos veces la misma franja) |
| Archivos adjuntos                                          | Almacenamiento de objetos (Vercel Blob, S3); en la base de datos, solo la URL | Las bases de datos no están hechas para guardar archivos grandes                                   |

Solución del punto 3. Sustituye la sección 1 de `json-vs-sqlite.js` por esta y ejecútalo:

```js
// ─── 1. Un archivo JSON como "base de datos" ───
const ARCHIVO = "tareas.json";
await writeFile(ARCHIVO, JSON.stringify([{ id: 1, titulo: "Correr 5 km", hecha: false, ediciones: 0 }]));

async function marcarHechaJson() {
  const tareas = JSON.parse(await readFile(ARCHIVO, "utf-8"));
  tareas[0].hecha = true;
  tareas[0].ediciones += 1;
  await writeFile(ARCHIVO, JSON.stringify(tareas, null, 2));
}

await Promise.all(Array.from({ length: ESCRITURAS }, () => marcarHechaJson()));
const enJson = JSON.parse(await readFile(ARCHIVO, "utf-8"));
console.log(`JSON:   ${ESCRITURAS} ediciones → contador = ${enJson[0].ediciones}`);
```

```text
JSON:   50 ediciones → contador = 1
SQLite: 50 escrituras → 50 tareas guardadas
JSON tras un corte: Unterminated string in JSON at position 45 (line 4 column 27)
```

- **El contador dice 1:** las 50 llamadas leen `ediciones: 0`, calculan `0 + 1`, y la última escritura gana. Es **leer → modificar → escribir** sin protección. La posición del corte cambia porque el contenido es otro, y a veces el archivo se corromperá.

<Callout type="risk">

- **El mismo error existe en MongoDB:** `findOne`, `tarea.ediciones += 1` y `replaceOne` pierden ediciones igual. Se pide en una sola operación: `updateOne({ _id }, { $inc: { ediciones: 1 } })` (B5).
- **Probar a mano no lo detecta:** en tu Mac nunca hay dos peticiones a la vez. Por eso el experimento lanza 50 con `Promise.all`.

</Callout>

<Callout type="mastery">

Puedes explicar cuándo elegirías SQL y cuándo NoSQL: qué hace un gestor de bases de datos que un archivo JSON no puede (almacenamiento, consultas, concurrencia y durabilidad), qué forma de datos favorece cada modelo, y la diferencia entre una base de datos embebida como SQLite y un servidor como tu clúster de Atlas.

</Callout>

## Resumen

- Un archivo JSON pierde escrituras simultáneas y se corrompe si el proceso muere al escribir.
- Un SGBD se encarga del almacenamiento, las consultas, la concurrencia y la durabilidad.
- Relacional: tablas y claves. Documental: documentos anidables. Clave-valor: acceso por clave.
- Embebida (SQLite, un archivo) frente a servidor (Atlas: réplicas, TLS y región).
- Elige por la forma de tus datos y tus consultas, no por moda.
