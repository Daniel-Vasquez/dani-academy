Una página accesible es una página que puede usar cualquiera: quien ve mal y necesita contraste, quien usa un lector de pantalla, quien no puede usar el ratón y navega con el teclado, quien se marea con las animaciones. No es un extra para unos pocos: es calidad, y en muchos países, una obligación legal. La buena noticia es que casi todo se resuelve con HTML bien escrito y unos pocos detalles de CSS. En esta sección vas a medir el contraste de tus _tokens_, a auditar `tw-lab` con dos herramientas que no siempre coinciden, a corregir lo que encuentren y a comprobar que la página se puede usar entera con el teclado.

**Lo que tendrás al terminar:** `scripts/contraste.ts`, que mide el contraste de cada par de _tokens_; un enlace para saltar al contenido; foco visible en todo; respeto a `prefers-reduced-motion`, y cinco páginas sin infracciones de axe en claro y en oscuro.

**Requisitos:** el proyecto `tw-lab` de I7.3, Chrome con la extensión axe DevTools (gratuita) y Lighthouse, que viene en las DevTools de Chrome.

## Paso 1: el contraste, medido

WCAG (_Web Content Accessibility Guidelines_) define el **contraste** entre dos colores como una relación que va de 1:1 (iguales) a 21:1 (negro sobre blanco), calculada a partir de su luminancia. Los mínimos del nivel AA, el que se exige normalmente:

| Contenido                                    | Mínimo AA | Mínimo AAA |
| -------------------------------------------- | --------- | ---------- |
| Texto normal                                 | 4,5:1     | 7:1        |
| Texto grande (24 px, o 18,7 px en negrita)   | 3:1       | 4,5:1      |
| Iconos, bordes de campos y otros componentes | 3:1       | —          |

No hace falta calcularlo a mano. Crea `scripts/contraste.ts`, que aplica la fórmula de WCAG a cada par de _tokens_ en los dos temas:

```ts
// Archivo: scripts/contraste.ts
// Relación de contraste WCAG 2.x entre pares de tokens, en claro y en oscuro
// Uso: node scripts/contraste.ts
type Hex = `#${string}`;

/** Luminancia relativa de un color (fórmula de WCAG 2.x) */
function luminancia(hex: Hex): number {
  const canales = [1, 3, 5].map((i) => parseInt(hex.slice(i, i + 2), 16) / 255);
  const lineal = canales.map((c) => (c <= 0.04045 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4));
  return 0.2126 * lineal[0]! + 0.7152 * lineal[1]! + 0.0722 * lineal[2]!;
}

/** De 1:1 (iguales) a 21:1 (negro sobre blanco) */
export function contraste(a: Hex, b: Hex): number {
  const [claro, oscuro] = [luminancia(a), luminancia(b)].sort((x, y) => y - x);
  return (claro! + 0.05) / (oscuro! + 0.05);
}

const TEMAS = {
  claro: { bg: "#fafafa", surface: "#eaedf2", fg: "#0f172a", muted: "#475569", accent: "#0d9488", "accent-strong": "#0f766e", "accent-contrast": "#ffffff", danger: "#f25c76", "danger-strong": "#be123c" },
  oscuro: { bg: "#0d1117", surface: "#161b22", fg: "#e6edf3", muted: "#9aa4b2", accent: "#2dd4bf", "accent-strong": "#5eead4", "accent-contrast": "#04201d", danger: "#f87191", "danger-strong": "#fda4af" },
} as const;

// [texto, fondo, uso]
const PARES = [
  ["fg", "bg", "texto normal"],
  ["muted", "bg", "texto secundario"],
  ["muted", "surface", "texto secundario en tarjeta"],
  ["accent", "bg", "acento como TEXTO"],
  ["accent-strong", "bg", "enlaces y texto de acento"],
  ["accent-contrast", "accent", "texto de un botón"],
  ["danger", "bg", "error como TEXTO"],
  ["danger-strong", "bg", "texto de error"],
] as const;

for (const [tema, t] of Object.entries(TEMAS)) {
  console.log(`${tema}:`);
  for (const [texto, fondo, uso] of PARES) {
    const r = contraste(t[texto] as Hex, t[fondo] as Hex);
    const nota = r >= 7 ? "AAA" : r >= 4.5 ? "AA" : r >= 3 ? "solo texto grande (AA ≥ 18,7 px negrita o 24 px)" : "✗ no pasa";
    console.log(`  ${`${texto} sobre ${fondo}`.padEnd(30)} ${r.toFixed(2).padStart(5)}:1  ${nota.padEnd(10)} ${uso}`);
  }
}
```

- **El acento de la plataforma, `#0d9488`, sobre el fondo `#fafafa` da 3,59:1:** no llega a 4,5. Sirve para fondos, bordes, iconos y texto grande, pero **no** para texto normal. Por eso existe `--accent-strong` (`#0f766e`, 5,24:1), y por eso los enlaces y el texto de acento lo usan.
- **El texto blanco sobre un botón de acento también falla** (3,74:1). Los botones con texto van sobre `accent-strong` (5,47:1, Paso 5).
- **En oscuro todo pasa con holgura:** el acento claro (`#2dd4bf`) sobre fondo oscuro da 10,17:1. Un color puede servir en un tema y no en el otro; mide los dos.

<Callout type="risk">

- **El contraste depende del fondo real, no del de la página:** el texto secundario da 7,26:1 sobre `bg`, pero 6,46:1 dentro de una tarjeta (`surface`). Mide cada combinación que uses.
- **La opacidad engaña:** `text-fg/60` es un color distinto, mezclado con el fondo, y su contraste es mucho menor. Para texto, usa un _token_ con su propio valor (`muted`), no una opacidad.
- **El contraste no es lo único:** un enlace que solo se distingue por el color (sin subrayado) no se ve para quien no distingue ese color. `prose` subraya los enlaces del texto; mantenlo.

</Callout>

## Paso 2: HTML semántico, _landmarks_ y títulos

Un lector de pantalla no "ve" la página: recorre su estructura. Usa los **landmarks** (las zonas de la página) para saltar entre ellas y los títulos para hacerse un índice:

| Elemento   | Zona (_landmark_)   | Uso                                                   |
| ---------- | ------------------- | ----------------------------------------------------- |
| `<header>` | Cabecera (`banner`) | La barra superior. **Una por página**                 |
| `<nav>`    | Navegación          | Los menús. Si hay varios, cada uno con `aria-label`   |
| `<main>`   | Contenido principal | **Una por página**. Lo que no se repite entre páginas |
| `<aside>`  | Complementario      | El índice lateral del curso                           |
| `<footer>` | Pie (`contentinfo`) | El pie de página                                      |

Y los títulos, en orden: un único `<h1>` por página y, debajo, `<h2>`, `<h3>`… sin saltar niveles. El nivel lo decide la estructura, no el tamaño: si quieres un `<h2>` pequeño, cambia su clase, no lo conviertas en `<h3>`.

<Callout type="risk">

- **Un `<div>` con un `onClick` no es un botón:** no se alcanza con Tab, no se activa con Enter ni con Espacio y el lector de pantalla no dice que es un botón. Usa `<button>` para acciones y `<a href>` para ir a otra página.
- **Las imágenes necesitan `alt`:** que describa lo que aporta la imagen, o `alt=""` si es decorativa (así el lector de pantalla la salta).

</Callout>

## Paso 3: foco visible, teclado y enlace para saltar

Quien navega con el teclado pulsa Tab para ir de un elemento al siguiente, y necesita **ver** dónde está. Y si cada página empieza con la misma barra de enlaces, tendrá que pasar por todos ellos antes de llegar al contenido, en cada página. Las dos soluciones son un **foco visible** en todo y un **enlace para saltar al contenido**, oculto hasta que recibe el foco. Crea `src/components/SaltarAlContenido.astro`:

```astro
---
// Archivo: src/components/SaltarAlContenido.astro
// El primer elemento con foco: oculto hasta que se llega con Tab, y salta al <main id="contenido">
---

<a
  href="#contenido"
  class="sr-only rounded-lg bg-accent-strong px-4 py-2 text-accent-contrast focus:not-sr-only focus:absolute focus:top-3 focus:left-3 focus:z-50"
>
  Saltar al contenido
</a>
```

Úsalo en el _layout_ como el primer elemento con foco, dentro de la cabecera. Para las páginas que tienen su propia cabecera (las de curso, de B7), el _layout_ ya no pone la suya: así nunca hay dos `<header>`. Sustituye `src/layouts/Layout.astro`:

```astro
---
// Archivo: src/layouts/Layout.astro
import "../styles/global.css";
import { ClientRouter } from "astro:transitions";
import BotonTema from "../components/BotonTema.astro";
import SaltarAlContenido from "../components/SaltarAlContenido.astro";

interface Props {
  titulo: string;
  /** Para las páginas que traen su propia cabecera (y ponen en ella el botón de tema) */
  sinCabecera?: boolean;
}
const { titulo, sinCabecera = false } = Astro.props;
---

<html lang="es">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width" />
    <title>{titulo} · Tailwind lab</title>
    <!-- 1. El tema, ANTES de que el navegador pinte nada. is:inline: Astro no lo aplaza ni lo empaqueta -->
    <script is:inline>
      (() => {
        const aplicarTema = () => {
          let guardado = null;
          try {
            guardado = localStorage.getItem("tema");
          } catch {
            // Almacenamiento bloqueado: se sigue la preferencia del sistema
          }
          const oscuro = guardado ? guardado === "dark" : matchMedia("(prefers-color-scheme: dark)").matches;
          document.documentElement.dataset.theme = oscuro ? "dark" : "light";
        };
        aplicarTema();
        // 2. View Transitions: al navegar, el <html> nuevo llega sin data-theme. Se reaplica antes de pintarlo
        if (!window.__temaEscuchando) {
          window.__temaEscuchando = true;
          document.addEventListener("astro:after-swap", aplicarTema);
        }
      })();
    </script>
    <ClientRouter />
    <slot name="head" />
  </head>
  <body class="bg-bg font-sans text-fg">
    {
      !sinCabecera && (
        <header class="flex justify-end p-3">
          <SaltarAlContenido />
          <BotonTema />
        </header>
      )
    }
    {sinCabecera && <SaltarAlContenido />}
    <slot />
  </body>
</html>
```

Y en las páginas:

- **Cada `<main>` lleva `id="contenido"`,** el destino del enlace.
- **`curso.astro` y `curso-responsive.astro`** pasan `sinCabecera` al _layout_, importan `BotonTema` y lo ponen dentro de su `<nav>`.

<Callout type="risk">

- **Nunca quites el contorno del foco** (`outline: none`) sin poner otro igual de visible: es la única forma de saber dónde estás con el teclado. `:focus-visible` (Paso 5) lo muestra al usar el teclado, pero no al hacer clic con el ratón.
- **`sr-only` oculta visualmente, no para el lector de pantalla:** el enlace de salto sigue en la página. `focus:not-sr-only` lo hace visible al recibir el foco. Con `display: none` o `hidden`, nadie podría usarlo.

</Callout>

## Paso 4: ARIA, solo cuando el HTML no basta

**ARIA** son atributos que dan a los lectores de pantalla información que el HTML no tiene. La primera regla de ARIA es **no usarlo** si un elemento HTML ya lo hace: un `<button>` ya es un botón; `role="button"` en un `<div>` es peor que un `<button>`.

| Necesitas…                                | HTML       | ARIA, solo si no hay HTML           |
| ----------------------------------------- | ---------- | ----------------------------------- |
| Un botón                                  | `<button>` | —                                   |
| Un botón que se activa y desactiva        | `<button>` | `aria-pressed="true"` / `"false"`   |
| Nombrar algo sin texto visible (un icono) | —          | `aria-label="Cerrar"`               |
| Enlazar un campo con su error             | —          | `aria-describedby` (I5.5)           |
| Avisar de un cambio                       | —          | `role="alert"` o `aria-live` (I5.5) |
| La página actual en un menú               | —          | `aria-current="page"` (B7.4)        |

`BotonTema` (I7.2) es el caso de `aria-pressed`: es un **interruptor**, y su texto ("Modo oscuro") no cambia, pero su estado sí. Con `aria-pressed`, el lector de pantalla dice "Modo oscuro, botón, activado" o "desactivado".

<Callout type="risk">

- **`aria-pressed` es para interruptores, no para cualquier botón:** "Guardar" no tiene estado, así que no lleva `aria-pressed`. Si el texto del botón cambia con el estado ("Ver más" / "Ver menos"), tampoco: el texto ya lo dice.
- **ARIA no añade comportamiento:** `role="button"` no hace que un `<div>` responda a Enter. Solo cambia lo que se anuncia.

</Callout>

## Paso 5: movimiento reducido y los cambios en `global.css`

Algunas personas sufren mareos o náuseas con las animaciones, y lo indican en su sistema operativo. CSS lo recibe como `prefers-reduced-motion: reduce`. Este paso y el foco visible del Paso 3 son las dos reglas nuevas de `src/styles/global.css`, junto con los ajustes de contraste del código del ejercicio. Sustituye el archivo:

- **`:focus-visible`** pone un contorno de 2 px con `--accent-strong` a cualquier elemento enfocado con el teclado, en toda la app.
- **Con movimiento reducido**, todas las transiciones y animaciones duran prácticamente cero. Medido en el primer botón de `/estados`: `transition-duration` pasa de `0.15s` a `1e-05s`. Las View Transitions de Astro ya respetan esta preferencia por su cuenta: su `viewtransitions.css` quita las animaciones con `@media (prefers-reduced-motion)`.

<Callout type="risk">

- **Reducir no es quitar la información:** si una animación comunica algo (una barra de progreso que avanza), con movimiento reducido el cambio tiene que seguir viéndose, aunque sea de golpe.
- **El `!important` es intencionado:** tiene que ganar a las clases `transition` y `duration-*` de cualquier componente, sin revisarlos uno a uno.

</Callout>

## Resumen

- AA exige 4,5:1 para texto normal y 3:1 para texto grande e iconos. El acento `#0d9488` sobre `#fafafa` da 3,59:1: para texto, `accent-strong` (5,24:1).
- Un `<header>`, un `<main>`, títulos en orden y un único `<h1>`. `<button>` para acciones, `<a>` para navegar.
- Foco visible con `:focus-visible` y un enlace "Saltar al contenido" como primer elemento con foco.
- ARIA solo si el HTML no basta: `aria-pressed` para los interruptores.
- `prefers-reduced-motion: reduce` quita las transiciones (de 0,15 s a casi cero).
- Lighthouse y axe no siempre coinciden (100 frente a un fallo): usa las dos y revisa a mano, en claro y en oscuro.
