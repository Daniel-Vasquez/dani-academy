«Me sale un error en estadísticas», y en tu equipo funciona, las pruebas pasan y el servidor responde. **Observabilidad** es poder responder desde fuera qué pasó, con lo que el propio sistema dejó escrito, sin reproducirlo. Aquí escribes logs consultables y un código que une al usuario con Nginx, Node y Sentry. También sacas métricas de errores y latencia y montas una alerta que avisa antes que tus usuarios.

**Requisitos:** la app con Nginx de A6.3 y el aviso de `scripts/vigilar.sh` de A4.

## Paso 1: logs que se pueden consultar

**Qué es:** un objeto JSON por línea, que una máquina puede filtrar y contar, en lugar de texto para personas.

**Cómo se usa:** hasta ahora, cada petición dejaba esto:

```text
GET /api/health → 200 (2.1 ms)
```

- **Para una persona vale,** pero no responde cuántos 500 hubo ayer en `/estadisticas` ni qué le pasó a un usuario.

```bash
npm install pino
```

`src/lib/contexto.ts` guarda los datos de la petición con `AsyncLocalStorage` de Node: una variable global propia de cada petición, aunque haya mil, sin pasar el `requestId` a mano:

```ts
// Archivo: src/lib/contexto.ts
// Lo que se sabe de la petición en curso, disponible en cualquier función sin pasarlo a mano
import { AsyncLocalStorage } from "node:async_hooks";

export interface ContextoPeticion {
  requestId: string;
  userId?: string;
}

export const contexto = new AsyncLocalStorage<ContextoPeticion>();
```

`src/lib/log.ts`:

```ts
// Archivo: src/lib/log.ts
// Logs en JSON, una línea por evento: los lee una máquina, no una persona
import pino from "pino";
import { contexto } from "./contexto";

export const log = pino({
  level: process.env.LOG_LEVEL ?? "info",
  messageKey: "mensaje",
  timestamp: pino.stdTimeFunctions.isoTime,
  formatters: { level: (nivel) => ({ nivel }) }, // "error" en lugar de 50
  base: { version: process.env.APP_VERSION ?? "dev" }, // qué versión lo escribió
  mixin: () => ({ ...contexto.getStore() }), // requestId y userId, en cada línea, sin pedirlos
  // Si llega a un log por error, se tapa. Los datos personales tampoco se escriben
  redact: {
    paths: ["password", "*.password", "email", "*.email", "cookie", "*.cookie", "authorization", "*.authorization"],
    censor: "[oculto]",
  },
});
```

- **`mixin` añade el contexto a cada línea.** Niveles: `error` si hay que mirarlo, `warn` si es raro, `info` para lo normal y `debug` para investigar.

```ts
log.info({ entrenoId: creado.id, tipo: creado.tipo }, "entreno creado");
```

Cambia los `console.error` que queden, como el de `aRespuesta` en `src/lib/errores.ts`:

```ts
log.error({ err: e }, "error no controlado en la API");
```

Eso rompe `tests/unit/api-resumen.test.ts`, que espiaba `console.error` (en A7.1 lo detectó el CI):

```ts
import { log } from "../../src/lib/log";

const registro = vi.spyOn(log, "error").mockImplementation(() => {}); // espiarlo y silenciarlo
// …
expect(registro).toHaveBeenCalledWith({ err: expect.any(Error) }, "error no controlado en la API");
registro.mockRestore();
```

- **4,6 µs por línea** con contexto y `redact`. `redact`, con datos falsos:

```text
{"password":"[oculto]","email":"[oculto]","mensaje":"nivel 1"}
{"usuario":{"email":"[oculto]","password":"[oculto]"},"mensaje":"nivel 2"}
{"peticion":{"usuario":{"email":"ana@correo.com"}},"mensaje":"nivel 3"}
{"correo":"ana@correo.com","mensaje":"otro nombre"}
{"mensaje":"texto con ana@correo.com dentro"}
```

<Callout type="risk">

- **`redact` es una red, no una solución:** `*.email` solo llega a un nivel, otros nombres y el texto libre pasan. **Registra campos que elijas, nunca objetos enteros** (`request.body`, `usuario`), y jamás _tokens_ ni contraseñas: un log se copia más y se protege peor.
- **Los logs son datos personales** (`userId`, IP), y un `warn` que nadie mira es ruido: una contraseña incorrecta es `info`. Astro escribe sus errores en texto, por eso `jq` usa `fromjson?`.
- **En Vercel,** los _Runtime Logs_ duran 1 hora en Hobby y 1 día en Pro, con 256 líneas por petición: para la semana pasada, envíalos fuera.

</Callout>

## Paso 2: un id para cada petición

**Qué es:** un `requestId` que une todas las líneas de una petición, desde Nginx hasta tu servicio.

**Cómo se usa:** en `src/middleware.ts`, en lugar del registro de I3:

```ts
import { contexto } from "./lib/contexto";
import { log } from "./lib/log";

/** 0. Registro: abre el contexto de la petición, y deja una línea por cada una */
const registrar = defineMiddleware((ctx, next) => {
  if (ctx.isPrerendered) return next(); // en el build no hay peticiones que registrar
  if (ctx.locals.requestId) return next(); // Astro repite el middleware al pintar 500.astro: ya está registrada

  const { pathname: ruta } = ctx.url;
  const metodo = ctx.request.method;
  const recibido = ctx.request.headers.get("x-request-id") ?? "";
  // El de Nginx, si lo hay. Viene de fuera: solo se acepta si tiene el formato esperado
  const requestId = /^[\w-]{16,64}$/.test(recibido) ? recibido : crypto.randomUUID();

  ctx.locals.requestId = requestId; // para src/pages/500.astro, que se pinta fuera del contexto

  return contexto.run({ requestId }, async () => {
    const inicio = performance.now();
    const ms = () => Math.round(performance.now() - inicio);
    try {
      const respuesta = await next();
      respuesta.headers.set("X-Request-Id", requestId);
      // Las sondas de salud llegan cada pocos segundos: se guardan solo en nivel debug
      const nivel = ruta === "/api/health" ? "debug" : "info";
      log[nivel]({ metodo, ruta, status: respuesta.status, ms: ms() }, "petición");
      return respuesta;
    } catch (error) {
      log.error({ metodo, ruta, status: 500, ms: ms(), err: error }, "petición fallida");
      throw error; // Astro responde con src/pages/500.astro
    }
  });
});
```

- **Se registra `pathname`,** no la URL entera: la _query_ puede llevar datos personales.

En `cargarSesion`, tras identificar al usuario:

```ts
const actual = contexto.getStore();
if (actual) actual.userId = datos.user.id; // desde aquí, cada línea lleva quién es
```

Añade `requestId?: string;` a `Locals` en `src/env.d.ts`. Dos líneas de una petición, del servicio y del _middleware_, quedan unidas:

```json
{"nivel":"info","version":"a64d","requestId":"24206cdc224cda92ca5bffa1344982c8","userId":"6aee818c64b7aca5709a6b51","entrenoId":"6aee818ea675a1c20bd746dc","tipo":"fuerza","mensaje":"entreno creado"}
{"nivel":"info","version":"a64d","requestId":"24206cdc224cda92ca5bffa1344982c8","userId":"6aee818c64b7aca5709a6b51","metodo":"POST","ruta":"/api/entrenos","status":201,"ms":52,"mensaje":"petición"}
```

Que el id nazca en **Nginx** registra también lo que nunca llega a Node. Junto a los `proxy_set_header`:

```nginx
proxy_set_header X-Request-Id $request_id; # el mismo id en Nginx y en Node
access_log /var/log/nginx/entrenos.json entrenos_json;
```

En `/etc/nginx/conf.d/registro.conf`:

```nginx
# $uri, no $request_uri: la query puede llevar datos personales
log_format entrenos_json escape=json '{"time":"$time_iso8601","requestId":"$request_id","metodo":"$request_method","ruta":"$uri","status":$status,"ms":$request_time,"cache":"$upstream_cache_status"}';
```

Y en `snippets/cdn.conf`, porque una copia de la caché guarda el id de quien la generó:

```nginx
proxy_hide_header X-Request-Id;
add_header X-Request-Id $request_id always; # el de ESTA petición, aunque venga de la caché
```

<Callout type="risk">

- **En un error, Astro pasa dos veces por el _middleware_** (la petición y `500.astro`): sin la línea de `ctx.locals.requestId`, cada error contaba doble y, sin Nginx, el código mostrado no era el del error. Se vio al comparar 6 errores con 12 en las métricas.
- **Un `X-Request-Id` de fuera no es de fiar:** se valida y Nginx lo sustituye, o cualquiera escribiría en tus logs. Las sondas de salud (17 000 líneas al día) van en `debug`.
- **`AsyncLocalStorage` se pierde con algunas API de _callbacks_,** no con `async/await`. Y el `access.log` por defecto de Nginx sigue guardando _query_ e IP.

</Callout>

## Paso 3: del usuario al error

**Qué es:** el usuario recibe un código que tú puedes buscar, y con él sigues la petición por cada capa.

**Cómo se usa:** `src/pages/500.astro`:

```astro
---
// Archivo: src/pages/500.astro
// Sin detalles del error: solo un código con el que encontrarlo en los logs
export const prerender = false; // si no, se genera en el build, sin petición ni código

const codigo = Astro.locals.requestId;
---

<!doctype html>
<html lang="es">
  <head>
    <meta charset="utf-8" />
    <title>Algo ha fallado</title>
  </head>
  <body>
    <h1>Algo ha fallado</h1>
    <p>Ya lo hemos registrado. Si necesitas ayuda, indica este código:</p>
    <p id="codigo"><code>{codigo}</code></p>
  </body>
</html>
```

- **`prerender = false` es imprescindible:** sin él la página se genera en el _build_, sin petición, y el código sale vacío (el segundo fallo de esta prueba).

Un error de verdad, en `src/pages/estadisticas.astro`:

```ts
const [ultimo] = await repos.entrenos.listar(usuario.id, { limite: 1 });
const ultimoDia = ultimo.fecha.toISOString().slice(0, 10); // ERROR A PROPÓSITO
```

- **En tu equipo funciona** (tienes entrenos); solo falla a quien acaba de registrarse. Ve «Algo ha fallado» y te manda:

```text
8804af6715b67cfc6b6822be9374f306
```

En Nginx, qué pasó por fuera:

```bash
sudo grep -F 8804af6715b67cfc6b6822be9374f306 /var/log/nginx/entrenos.json
```

```json
{"time":"2026-11-06T19:42:40-06:00","requestId":"8804af6715b67cfc6b6822be9374f306","metodo":"GET","ruta":"/estadisticas","status":500,"ms":0.005,"cache":"MISS"}
```

En Node, qué pasó por dentro:

```bash
sudo journalctl -t entrenos --since "-1h" -o cat | grep -F 8804af6715b67cfc6b6822be9374f306 |
  jq -c '{nivel, version, userId, ruta, status, err: {type: .err.type, message: .err.message}}'
```

```json
{"nivel":"error","version":"a64e","userId":"6aee821095a56e7ec54caf10","ruta":"/estadisticas","status":500,"err":{"type":"TypeError","message":"Cannot read properties of undefined (reading 'fecha')"}}
```

- **Ruta, versión, usuario y mensaje sin reproducir nada:** `undefined` al leer `fecha` y un `userId` sin entrenos. La causa:

```ts
const ultimoDia = ultimo?.fecha.toISOString().slice(0, 10) ?? "todavía ninguno";
```

- **El límite de los logs:** `err.stack` apunta a `estadisticas_Dko60Qmy.mjs:23`, un archivo compilado.

<Callout type="risk">

- **La página de error no da detalles:** solo el código. Una traza o un mensaje interno ayudarían a un atacante (A5.1).
- **Busca primero en el último tramo de tiempo** (`--since "-1h"`): `grep` sobre todo el diario es lento en un servidor con meses de logs.

</Callout>

## Paso 4: Sentry en el servidor

**Qué es:** **Sentry** agrupa los errores iguales, avisa de los nuevos y añade contexto. Su plan gratuito, al escribir esto, incluye 1 usuario y 5000 errores.

**Cómo se usa:**

```bash
npm install @sentry/astro
```

Crea un proyecto en sentry.io y pon su DSN en `.env` como `SENTRY_DSN`. En `astro.config.mjs`:

```js
import sentry from "@sentry/astro/integration";

export default defineConfig({
  integrations: [sentry({ sourcemaps: { disable: true }, telemetry: false })], // los source maps, en el Paso 5
  // …
});
```

`sentry.server.config.ts`, en la raíz:

```ts
// Archivo: sentry.server.config.ts
import * as Sentry from "@sentry/astro";
import { sinIp } from "./src/lib/sentry-limpiar";

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  release: process.env.APP_VERSION,
  tracesSampleRate: 0, // solo errores: sin trazas de rendimiento
  dataCollection: { cookies: false, httpHeaders: false, urlQueryParams: false },
  beforeSend: sinIp,
});
```

`src/lib/sentry-limpiar.ts`:

```ts
// Archivo: src/lib/sentry-limpiar.ts
// Lo último antes de salir de tu servidor: la IP es un dato personal y Sentry no la necesita
import type { ErrorEvent } from "@sentry/astro";

export function sinIp(evento: ErrorEvent) {
  if (evento.user) delete evento.user.ip_address;
  return evento;
}
```

Para unir Sentry con tus logs, en el _middleware_:

```ts
import * as Sentry from "@sentry/astro";

// en registrar, al principio de contexto.run
Sentry.getIsolationScope().setTag("requestId", requestId);

// en cargarSesion, junto a actual.userId
Sentry.setUser({ id: datos.user.id }); // solo el id: ni nombre ni correo
```

Los errores de la API los captura `aRespuesta` y no suben, así que Sentry no los ve. Allí:

```ts
log.error({ err: e }, "error no controlado en la API");
Sentry.captureException(e); // este error ya no sube: sin esto, Sentry no se entera
```

- **Se comprobó con el SDK real y un receptor propio,** sin cuenta de Sentry: se ve lo que sale del servidor, pero **no el panel**. Funcionó con Astro 7 y el adaptador de Node, aunque la documentación dice «4.0.0 o superior».

Por defecto, sin `dataCollection` ni `beforeSend`, con `/estadisticas?email=ana@correo.com&dni=12345678Z`:

```text
url:     https://academy.entrenos.test/estadisticas?email=ana@correo.com&dni=12345678Z&nombre=Ana
user:    {"id": "6aee7f6500afb73860a543d6", "ip_address": "127.0.0.1"}
cookies: "[Filtered]"
```

- **Tapó la _cookie_ y un `token`, pero salieron el correo, el DNI y la IP.** Con la configuración de arriba:

```text
request: {"method": "GET", "url": "https://academy.entrenos.test/estadisticas"}
tags:    {"requestId": "27610f1d4fa1db8cf72b57b88dd43630"}
user:    {"id": "6aee818c64b7aca5709a6b51"}
```

- **Lo útil:** `release`, el tipo de error, 10 marcos de pila y **la línea exacta** del archivo compilado:

```text
TypeError: Cannot read properties of undefined (reading 'fecha')
  estadisticas_tfNmj9vW.mjs:23
  const ultimoDia = ultimo.fecha.toISOString().slice(0, 10);
```

Con MongoDB parado, `/api/entrenos` dio 500 en 5 s, `/api/health` 503, y el evento llegó con su `requestId`:

```text
MongoServerSelectionError: interrupted at shutdown
```

<Callout type="risk">

- **Lo que envías sale de tu servidor** hacia otra empresa: decláralo en tu política de privacidad y revisa un evento real.
- **Sentry no cuenta:** 6 errores iguales seguidos fueron 1 evento; los logs tenían 6. Y si se agota la cuota, deja de avisar.
- **El DSN solo envía; `SENTRY_AUTH_TOKEN` da acceso a tu cuenta:** nunca en el repositorio ni la imagen. La imagen subió de 565 a 685 MB, y `tracesSampleRate: 1.0` es caro: aquí, 0.

</Callout>

## Paso 5: Sentry en el navegador

**Qué es:** un error de JavaScript en el móvil del usuario no llega a tus logs. Sentry lo captura, con dos costes.

**Cómo se usa:** el peso, JavaScript por página en un navegador:

```text
                                 /estadisticas   /
Sin Sentry en el navegador       2,8 KB          64,3 KB
Con sentry.client.config.ts      47,4 KB         108,9 KB
Sin ese archivo                  80,7 KB         142,2 KB
```

- **44 KB en cada página;** en `/estadisticas`, 17 veces más, buena parte de lo ganado en A6.2. **Borrar el archivo lo empeora** (el SDK arranca con sus valores por defecto) y `bundleSizeOptimizations` no cambió nada. Lo que funcionó:

```js
sentry({ enabled: { client: false, server: true }, sourcemaps: { disable: true }, telemetry: false });
```

- **Las páginas quedaron como en la primera fila.**

El segundo coste es la CSP de A5, que bloquea los envíos a otro dominio sin error visible:

```text
Connecting to 'http://…/api/1/envelope/…' violates the following Content Security Policy directive
```

Sin abrir la CSP, los eventos pasan por tu dominio. `sentry.client.config.ts`:

```ts
// Archivo: sentry.client.config.ts
import * as Sentry from "@sentry/astro";
import { sinIp } from "./src/lib/sentry-limpiar";

Sentry.init({
  dsn: "https://…@….ingest.sentry.io/…", // el de tu proyecto: es público
  tunnel: "/api/sentry-tunel", // por tu dominio: así lo permite la CSP de A5
  tracesSampleRate: 0,
  dataCollection: { cookies: false, urlQueryParams: false },
  beforeSend: sinIp,
});
```

`src/pages/api/sentry-tunel.ts`, con la ruta en `PUBLICAS`:

```ts
// Archivo: src/pages/api/sentry-tunel.ts
// Los errores del navegador pasan por aquí. Solo se reenvían a tu proyecto de Sentry
import { handleTunnelRequest } from "@sentry/astro";
import type { APIRoute } from "astro";
import { repos } from "../../repositories";

export const prerender = false;

export const POST: APIRoute = async ({ request, clientAddress }) => {
  const { permitido } = await repos.limites.contar(`sentry:${clientAddress}`, 30, 60);
  if (!permitido) return new Response(null, { status: 429 });

  return handleTunnelRequest(request); // solo reenvía al DSN de tu propio proyecto
};
```

- **Con un error real del navegador,** el túnel dio 200 y el evento llegó sin `?email=`.

<Callout type="risk">

- **Depende de tu app:** con mucho JavaScript propio, 44 KB se justifican; aquí no. Solo en el servidor, no verás los del navegador.
- **El servidor debe llegar a Sentry:** si no, cada envío tardó 10 s en dar 500, visible solo en los logs del túnel. El túnel es público (con límite por IP) y solo reenvía a tu DSN.
- **La pila del navegador va minificada** (`page.C0qHT4lz.js:21`): legible solo con _source maps_ y `SENTRY_AUTH_TOKEN`, no probado. Extensiones y bloqueadores meten ruido o impiden el envío.

</Callout>

## Paso 6: métricas y alertas

**Qué es:** un error dice qué pasó; una **métrica**, cómo va todo. Para empezar bastan tres: peticiones, fallos y latencia. Una **alerta** es una métrica con umbral y alguien que la recibe.

**Cómo se usa:** `scripts/metricas.sh`, desde los logs que ya tienes:

```bash
#!/usr/bin/env bash
# Archivo: scripts/metricas.sh
# Métricas de los últimos minutos, calculadas con los propios logs.
# Uso: bash scripts/metricas.sh [minutos]
MINUTOS="${1:-5}"

journalctl -t entrenos --since "-${MINUTOS}min" -o cat --no-pager |
  jq -Rrs '
    [split("\n")[] | fromjson? | select(.ruta and .status)] as $p
    | ($p | map(.ms) | sort) as $ms
    | ($p | map(select(.status >= 500))) as $e
    | "peticiones \($p | length)",
      "errores5xx \($e | length)",
      "porcentaje \(if ($p | length) > 0 then (($e | length) * 1000 / ($p | length) | round / 10) else 0 end)",
      "p50ms \($ms[($ms | length) / 2 | floor] // 0)",
      "p95ms \($ms[($ms | length) * 0.95 | floor] // 0)",
      ($e | group_by(.ruta) | map("ruta5xx \(.[0].ruta) \(length)") | .[])
  '
```

```bash
sudo bash scripts/metricas.sh 5
```

Con 7 errores provocados en `/estadisticas`:

```text
peticiones 17
errores5xx 7
porcentaje 41.2
p50ms 2
p95ms 65
ruta5xx /estadisticas 7
```

- **`p50ms` es lo normal y `p95ms` lo que sufren los peores** (A6.1).

`scripts/vigilar.sh` (A4) ya corre cada 5 minutos y avisa por Telegram si algo cambia. Antes de la comprobación de reinicio:

```bash
# Errores de la app en los últimos 5 minutos, según sus propios logs
read -r total errores < <(bash "$(dirname "$0")/metricas.sh" 5 | awk '$1 == "peticiones" { t = $2 } $1 == "errores5xx" { e = $2 } END { print t + 0, e + 0 }')
if [ "$errores" -ge 5 ] && [ $((errores * 100 / total)) -ge 5 ]; then
  problemas+=("$errores errores 5xx de $total peticiones en 5 minutos")
fi
```

Con un receptor de prueba en lugar de Telegram:

```text
⚠️ academy.entrenos.test
7 errores 5xx de 17 peticiones en 5 minutos
```

- **Al repetir no se reenvió:** no se repite mientras nada cambie.

<Callout type="risk">

- **Una alerta debe poder actuarse:** si avisa de lo que no arreglas, aprenderás a ignorarla, también la buena. Pocas, y provocadas al menos una vez.
- **Dos condiciones, no una:** `5 %` saltaría con 1 error de 2 de madrugada, y `5 errores` con mucho tráfico por nada. Ajústalas a tu tráfico.
- **Vive en el mismo servidor** (hace falta el monitor externo de A4), y calcular desde el diario no escala a millones de peticiones: Prometheus o un servicio dedicado.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

Integra Sentry en tu app, provoca un error a propósito y localízalo con su traza y su `requestId`.

</Callout>

Solución, con los Pasos 3 y 4:

1. Crea tu proyecto en Sentry y configura `SENTRY_DSN`.
2. Añade el `ultimo.fecha` del Paso 3 y despliega **con una etiqueta nueva** (A6.3).
3. Regístrate con un usuario de prueba sin entrenos y entra en `/estadisticas`.
4. Copia el código de la página.
5. Búscalo en Nginx y en Node con los comandos del Paso 3.
6. Búscalo en Sentry, en la etiqueta `requestId`, y comprueba que el evento **no** lleva correo, _cookies_ ni IP.
7. Escribe qué falló en tres líneas, sin abrir el código.
8. Corrige con `ultimo?.fecha`, despliega y comprueba que el usuario ve «todavía ninguno».

En este laboratorio:

```text
usuario nuevo: 500, código 8804af6715b67cfc6b6822be9374f306
Nginx:   GET /estadisticas 500
Node:    TypeError … reading 'fecha' · version a64e · userId 6aee8210…
Sentry:  tag requestId, línea 23 del archivo compilado
tras corregirlo: 200, «Último entreno: todavía ninguno»
```

- **Cada herramienta responde a una pregunta:** Nginx, si llegó; Node, qué pasó; Sentry, qué línea y si es nuevo.
- **Con Sentry solo en el servidor** funciona igual: el error es de servidor.
- **La etiqueta en el panel no se ha podido ver:** si no la encuentras, revisa `setTag`.

## Resumen

- **`pino` en JSON:** 4,6 µs por línea; `mixin` y `AsyncLocalStorage` añaden `requestId` y `userId`.
- **Campos elegidos:** `redact` no cubre niveles profundos, otros nombres ni texto libre.
- **`requestId`:** nace en Nginx, se valida en Node, sale en `500.astro` (con `prerender = false`) y se etiqueta en Sentry.
- **Sentry por defecto envió correo, DNI e IP;** con `dataCollection` y `beforeSend`, nada. Y no cuenta: 6 errores, 1 evento.
- **En el navegador, 44 KB por página;** `enabled: { client: false }` los quita. La CSP exige `tunnel`.
- **Métricas desde los logs** y una alerta con dos condiciones, probada.
