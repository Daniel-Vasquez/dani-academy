Puedes tener un código impecable y perderlo todo por una línea: una clave pegada en un archivo, subida a un repositorio y copiada por un bot en minutos. O por un paquete que llevas años usando y que un día publica una versión maliciosa. Los fallos de esta sección no están en tu lógica, sino **alrededor de ella**: en cómo guardas las llaves, en de quién te fías y en lo que dejas escrito.

Una analogía: las llaves de tu casa. Si pierdes una, no basta con buscarla: **cambias la cerradura**, porque no sabes quién la encontró. Borrar un secreto de Git es buscar la llave; rotarlo es cambiar la cerradura. Y las dependencias son los obreros que dejas entrar: seguramente son de fiar, pero conviene saber quiénes son, y quedarse mirando si llega uno nuevo.

**Lo que tendrás al terminar:** un gancho que impide subir secretos, un procedimiento para rotar uno en minutos, medido; un criterio para priorizar `npm audit`; y una lista de seguridad para cada lanzamiento.

**Requisitos:** las secciones anteriores de A5, y la app en tu servidor. Las pruebas con secretos usan valores falsos, en repositorios desechables.

## Paso 1: un secreto en Git no se borra

Se creó un repositorio de prueba con un _token_ falso en `config.js`. **gitleaks** busca secretos en la historia de Git. Se ejecuta con Docker, sin instalar nada, y `--redact` evita que los imprima:

```bash
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest git /repo --redact --no-banner
```

```text
con el token en un commit, git: exit 1 (0 limpio, 1 hay secretos)
```

Lo detecta. La reacción normal es borrar el archivo y hacer otro _commit_:

```bash
git rm config.js
git commit -m "quita el token"
```

```text
tras borrarlo, carpeta: exit 0 (0 limpio, 1 hay secretos)
tras borrarlo, historia: exit 1 (0 limpio, 1 hay secretos)
```

**La carpeta está limpia, y el secreto sigue ahí.** Git guarda todo lo que has confirmado. `git log -p` lo enseña, y cualquiera con un clon también. **`git filter-repo`** reescribe la historia sin ese archivo:

```bash
sudo apt-get install -y git-filter-repo
git filter-repo --force --invert-paths --path config.js
```

```text
tras filter-repo, historia: exit 0 (0 limpio, 1 hay secretos)
commits: 1
```

Pero mira lo que pasó con un clon hecho antes:

```text
una copia hecha antes (un clon, otro equipo): 2 líneas con el token
identificador del último commit:  c77140d (reescrito)  ·  feb6f39 (la copia)
```

Reescribir cambia los identificadores de los _commits_ y no alcanza a ninguna copia: clones, _forks_, cachés. **Si el repositorio fue público aunque sea un minuto, ese secreto está comprometido.** Por eso el orden no se negocia: **primero rotar, después limpiar**.

**Mejor que no entre.** Un gancho `pre-commit` lo comprueba antes de confirmar. Crea `.githooks/pre-commit`:

```bash
#!/usr/bin/env bash
# Archivo: .githooks/pre-commit
# Bloquea el commit si lo que está en el área de preparación contiene un secreto
exec docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest \
  git /repo --pre-commit --staged --redact --no-banner --no-color
```

```bash
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

```text
commit limpio: exit 0 · commits 2
commit con token: exit 1 · commits 2
```

El segundo _commit_ no existe: nunca llegó a la historia.

Y antes de todo eso, el `.gitignore` y `.env.example` (I3.6). Compruébalo:

```bash
git check-ignore .env .env.local
git ls-files | grep -E '(^|/)\.env'
```

La primera debe listar los dos, y la segunda, solo `.env.example`.

<Callout type="risk">

- **Un gancho local se puede saltar:** `git commit --no-verify`, o un equipo sin él. Añade `gitleaks` a CI, y activa la protección de GitHub (_push protection_).
- **Los falsos positivos existen:** al pasar `gitleaks` por el repositorio de este curso, 93 _commits_, dio 5 hallazgos, y los 5 eran ejemplos de las lecciones. Revísalos uno a uno. Los que sean falsos se anotan en `.gitleaksignore`, para que un hallazgo nuevo destaque.
- **`gitleaks` no lo ve todo:** busca patrones. Una contraseña inventada por ti en un `const clave = "…"` puede pasar. No sustituye a no escribirla.
- **`.env` en una imagen o una copia también es una filtración:** lo viste en A4.2. Y en la historia de un `Dockerfile` antiguo, también.
- **`git filter-repo` reescribe la historia de todos:** avisa antes, y cada persona debe volver a clonar.

</Callout>

## Paso 2: rotar en minutos

Si dudas, rota. Y para no dudar, debe ser barato. `scripts/rotar-secreto.sh` cambia `BETTER_AUTH_SECRET` usando lo que ya tienes: despliegue sin cortes (A4.5) y un _script_:

```bash
#!/usr/bin/env bash
# Archivo: scripts/rotar-secreto.sh
# BETTER_AUTH_SECRET filtrado: nuevo secreto, despliegue sin cortes y sesiones revocadas.
# Uso, en el servidor, desde la carpeta del proyecto: bash scripts/rotar-secreto.sh
set -euo pipefail

DOMINIO="$(grep '^APP_HOSTNAME=' .env | cut -d= -f2)"
VERSION="$(curl -s -m 5 "https://$DOMINIO/api/health" | sed -E 's/.*"version":"([^"]+)".*/\1/')"
[ -n "$VERSION" ] || { echo "✗ La app no responde: arréglalo primero"; exit 1; }

if grep -q ':4321;' /etc/nginx/entrenos-activo.conf; then FILTRADA=blue; else FILTRADA=green; fi

echo "== 1. Secreto nuevo en .env"
NUEVO="$(openssl rand -base64 32)"
sed -i "s|^BETTER_AUTH_SECRET=.*|BETTER_AUTH_SECRET=$NUEVO|" .env

echo "== 2. Desplegar la misma versión ($VERSION) con el secreto nuevo"
bash scripts/desplegar.sh "$VERSION" | grep -E '^(✓|✗)'

echo "== 3. Quitar la instancia con el secreto filtrado: volver.sh no debe poder arrancarla"
docker compose rm -f "$FILTRADA" >/dev/null 2>&1

echo "== 4. Revocar todas las sesiones"
docker compose exec -T mongo mongosh --quiet entrenos --eval \
  'print("sesiones borradas:", db.session.deleteMany({}).deletedCount)'

echo "✓ Rotado. Ahora: revisa los registros de la ventana de exposición y anota el incidente"
```

Medido con la carga de A4.5 en marcha, y una sesión abierta:

```text
sesión antes: /estadisticas -> 200
sesiones en la base: 49
== 1. Secreto nuevo en .env
== 2. Desplegar la misma versión (a54c) con el secreto nuevo
✓ a54c en producción (green). Para volver atrás: bash scripts/volver.sh
== 3. Quitar la instancia con el secreto filtrado: volver.sh no debe poder arrancarla
== 4. Revocar todas las sesiones
sesiones borradas: 49
✓ Rotado. Ahora: revisa los registros de la ventana de exposición y anota el incidente
tardó 17.60 s
```

```text
659 peticiones, 0 fallos
cookie antigua: /estadisticas -> 302
cookie antigua: /api/entrenos -> 401
volver a entrar -> 200
sesión nueva -> 200
```

**17,6 s, sin un solo error**, y todas las sesiones anteriores han dejado de valer. Docker recrea el contenedor porque cambió el `.env`, aunque la imagen sea la misma.

- **Etapa 3:** el contenedor parado aún lleva el secreto filtrado, y es el destino de `volver.sh`. Hay que quitarlo: medido, `volver.sh` responde `✗ No hay instancia anterior a la que volver`, y es lo correcto.
- **Etapa 4:** con el secreto nuevo, las _cookies_ antiguas ya no valen, pero borrar las sesiones elimina también los _tokens_ que seguían en la base (A5.1).

Cada secreto se rota distinto. Guarda el procedimiento en `docs/rotar-secreto.md`:

```markdown
# Se ha filtrado un secreto

**Primero rotar, después limpiar.** Un secreto publicado está comprometido para siempre.

1. **Anota la hora.** Cuándo se filtró y cuándo lo has sabido: es tu ventana de exposición.
2. **Rota:**
   - `BETTER_AUTH_SECRET`: `bash scripts/rotar-secreto.sh`. Cierra todas las sesiones.
   - Contraseña de MongoDB: Atlas → Database Access → Edit, cambia `MONGODB_URI` en `.env` y despliega.
   - Token de Vercel, GitHub o de un bot: revócalo en su panel y crea otro.
3. **Revisa la ventana de exposición:** registros de acceso, usuarios nuevos, datos cambiados.
4. **Limpia Git** solo después (`git filter-repo`), y avisa a quien tenga un clon.
5. **Busca la causa:** ¿por qué entró? Añade el control que faltaba.
6. **Apúntalo** aquí: qué pasó, cuánto tardaste y qué has cambiado.
```

**En Vercel,** las variables viven en _Settings_ → _Environment Variables_. Cambiarlas no afecta al despliegue en curso: hay que desplegar otra vez. Mantén un valor distinto por entorno (I3.6): un secreto filtrado de _preview_ no debe abrir producción.

<Callout type="risk">

- **Cerrar todas las sesiones afecta a todos los usuarios:** es el precio de rotar. Si tienes muchos, hazlo igualmente, pero avisa. Better Auth admite varias claves a la vez (`secrets`, versionadas) para rotar sin cerrarlas, pero no se ha medido aquí, y no sirve si ya se ha filtrado.
- **Un secreto filtrado y sin usar sigue siendo una emergencia:** no sabes quién lo tiene. No esperes a ver daños.
- **Revisa la ventana de exposición:** rotar corta el acceso, pero no deshace lo que alguien ya hizo.
- **`.env` tiene `chmod 600` antes y después:** `sed -i` conserva los permisos. Medido: sigue en 600.
- **El contenedor tiene el secreto a la vista:** `docker inspect` muestra las variables a cualquiera del grupo `docker` (A4.2, que equivale a `root`). Es lo normal; solo recuerda quién está en ese grupo.

</Callout>

## Paso 3: dependencias

Tu app ejecuta código de cientos de paquetes. **`npm audit`** los compara con una base de vulnerabilidades conocidas:

```bash
npm audit --omit=dev
```

La app de entrenos, instalada hace pocas semanas:

```text
found 0 vulnerabilities
```

Otro proyecto real, con dependencias de hace meses y sin cambios en ese código:

```text
con devDependencies:     26 (16 moderadas, 10 altas)
solo producción:         14 (5 moderadas, 9 altas)
```

**Una vulnerabilidad aparece en código que no has tocado.** Por eso esto se repite, no se hace una vez. Y 14 no significa 14 emergencias. Tres preguntas ordenan la lista:

1. **¿Se ejecuta en producción?** `--omit=dev` quita los tests. Pero una herramienta de _build_ también puede salir: un fallo en el empaquetador de un adaptador no se ejecuta cuando alguien visita tu web.
2. **¿Llega ahí un dato del atacante?** Tipos reales de esa lista:
   - Una biblioteca de validación que puede agotar la memoria con entradas enormes: **prioritaria**, porque valida justo lo que envían los usuarios.
   - Un fallo de `launch-editor` solo en Windows, en el servidor de desarrollo: no te afecta en producción.
   - Una expresión regular lenta en las rutas de una herramienta de _build_: solo la alimentas tú.
3. **¿Hay arreglo?** `npm audit fix` aplica lo compatible, y `npm audit fix --dry-run` enseña lo que haría. Lo que pide un cambio mayor necesita pruebas, no un `--force` a ciegas.

En CI, falla solo en lo que vas a atender:

```bash
npm audit --omit=dev --audit-level=high
```

**Automatiza las actualizaciones.** Dependabot abre un _pull request_ cuando hay una versión nueva, y tus tests la prueban. Crea `.github/dependabot.yml` y activa las actualizaciones en los ajustes de seguridad del repositorio:

```yaml
# Archivo: .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    cooldown:
      default-days: 7 # no propone versiones publicadas hace menos de 7 días
    open-pull-requests-limit: 5
    groups:
      menores:
        update-types: [minor, patch]
```

Renovate hace lo mismo, con más opciones.

### La cadena de suministro

`npm audit` solo ve lo que ya se conoce. Un paquete comprometido ayer no está en la lista. Tres defensas, medidas:

**El _lockfile_ y `npm ci`.** `package-lock.json` guarda el _hash_ de cada paquete. Si el archivo descargado no coincide:

```text
npm error code EINTEGRITY
npm ci exit 1
```

Instala exactamente lo que probaste, o nada.

**Los _scripts_ de instalación.** Un paquete puede ejecutar lo que quiera al instalarse, con tus permisos: justo en tu equipo, donde está tu `.env`. Con un paquete de prueba con `postinstall`:

```text
postinstall ejecutado (npm install): 1
postinstall ejecutado (npm ci --ignore-scripts): 0
```

Para hacerlo fijo, `ignore-scripts=true` en `.npmrc`. Algunos paquetes los necesitan para compilar; los que vayas a permitir, de uno en uno.

**Espera antes de instalar lo último.** Los paquetes maliciosos suelen descubrirse en horas o días. `min-release-age` ignora las versiones más recientes:

```bash
npm install zod --min-release-age=7
```

```text
con 7 días:        zod 4.6.7
con 36500 días:    npm error code ENOVERSIONS · No versions available for zod
```

Y `npm audit signatures` comprueba la firma del registro:

```text
audited 1 package in 1s
1 package has a verified registry signature
```

<Callout type="risk">

- **Revisa lo que instalas:** un nombre mal escrito puede ser un paquete malicioso que imita a otro (_typosquatting_). Mira quién lo publica, y sus descargas, antes de `npm install`.
- **Menos dependencias, menos riesgo:** `is-odd` existe, y tiene dependencias. Tres líneas tuyas no tienen cadena de suministro.
- **`npm audit fix --force` puede romper la app:** salta versiones mayores. Hazlo en una rama, con tests.
- **Dependabot no sustituye a tus tests:** un _pull request_ en verde solo vale tanto como lo que comprueban. Revisa antes de mezclar, y no actives la mezcla automática en dependencias de producción.
- **`.github/dependabot.yml` no se ha ejecutado aquí:** necesita un repositorio en GitHub. Comprueba que su primera ejecución aparece en GitHub.
- **Actualiza también la imagen:** una dependencia de Alpine o de Node no aparece en `npm audit` (A4.6).

</Callout>

## Paso 4: registros sin secretos

Un secreto en un registro es un secreto en texto plano, copiado a cada copia de seguridad y al servicio de registros. Mira lo que hay en el tuyo:

```bash
V="$(grep '^BETTER_AUTH_SECRET=' .env | cut -d= -f2-)"
sudo journalctl -t entrenos --no-pager | grep -cF "$V"
sudo journalctl -t entrenos --no-pager | grep -ciE 'mongodb(\+srv)?://|authorization|cookie:'
sudo grep -cE 'password|token=' /var/log/nginx/access.log
```

```text
0
0
0
```

Limpio, y no por suerte: tu _middleware_ registra método, ruta y código, y `aRespuesta` escribe el error, no la petición. Las reglas:

- **Nunca** cuerpos de petición, cabeceras enteras, _cookies_, contraseñas ni _tokens_.
- **Cuidado con `console.log(request)` o `console.log(usuario)`:** un objeto entero lleva lo que no ves.
- **Nada secreto en la URL:** acaba en el registro de Nginx y en historiales.
- **Un error puede llevar datos:** un fallo de conexión puede incluir una URI con contraseña. Comprueba lo que se escribe.

Tampoco deben salir en el navegador. Con el mismo valor, buscado en `dist` dentro de la imagen:

```text
archivos de dist con el secreto: 0
```

`astro:env` lo lee en el servidor, y solo `PUBLIC_` llega al cliente (I3.6).

<Callout type="risk">

- **Un error de terceros también escribe:** al añadir un servicio de errores como Sentry, revisa qué envía: por defecto puede incluir cabeceras o datos de la petición.
- **Los correos de los usuarios son datos personales:** por eso el límite por cuenta de A5.4 guarda un _hash_.
- **Repite la búsqueda tras cada funcionalidad nueva:** un `console.log` olvidado de una sesión de depuración es el origen típico.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Ejecuta `gitleaks` sobre tus repositorios y revisa cada hallazgo. Instala el gancho `pre-commit`.
2. Activa Dependabot y revisa `npm audit --omit=dev` con las tres preguntas del Paso 3.
3. Redacta tu lista de seguridad para cada lanzamiento.
4. Haz un simulacro: cronometra una rotación completa de `BETTER_AUTH_SECRET`. Debe bajar de 15 minutos.

</Callout>

Solución. Los puntos 1, 2 y 4 son los Pasos 1 a 3. Para el 4, cuenta desde que decides rotar hasta que has comprobado que la sesión antigua no vale y que puedes volver a entrar: el _script_ tardó 17,6 s, y el resto es tu tiempo, leyendo `docs/rotar-secreto.md`. La lista, en `docs/lanzamiento.md`, reúne lo que has construido en este curso:

Cada línea sale de una sección: `buscar-riesgos.sh` (A5.2), `auditar.sh` (A5.1), `comprobar-cabeceras.sh` (A5.3) y `comprobar-limites.sh` (A5.4). No es un documento nuevo, sino el resumen de lo que ya sabes comprobar.

<Callout type="risk">

- **Una lista que nadie usa no sirve:** mantenla corta. Si una línea siempre se marca sin mirar, automatízala o quítala.
- **Automatiza lo que puedas:** lo que un _script_ puede comprobar, va a CI. La lista es para lo que necesita criterio.
- **El simulacro cuenta como incidente:** apunta lo que no estaba escrito y corrígelo.

</Callout>

<Callout type="mastery">

Sabes rotar un secreto filtrado en menos de 15 minutos: primero cambias la cerradura, con un despliegue sin cortes y las sesiones revocadas; después revisas la ventana de exposición; y solo entonces limpias Git, sabiendo que eso no alcanza a ningún clon. Impides que entre con un gancho, priorizas `npm audit` por lo que de verdad se ejecuta y recibe datos del atacante, confías en el _lockfile_ y no en la suerte, y no escribes secretos en tus registros.

</Callout>

## Resumen

- Borrar un secreto en un _commit_ nuevo no lo elimina: `gitleaks` lo sigue viendo en la historia. `git filter-repo` limpia tu repositorio, no los clones.
- **Primero rotar, después limpiar.** Un secreto publicado está comprometido.
- Un gancho `pre-commit` con `gitleaks` impidió el _commit_. Se puede saltar: añádelo también a CI.
- Rotación de `BETTER_AUTH_SECRET`: **17,6 s, 0 errores** entre 659 peticiones. Cierra las sesiones, y hay que quitar la instancia antigua para que `volver.sh` no la arranque.
- `npm audit --omit=dev` aparece en código que no has tocado: 0 en un proyecto reciente, 14 en otro de hace meses. Prioriza: ¿se ejecuta en producción?, ¿llega un dato del atacante?, ¿hay arreglo?
- `npm ci` falló con `EINTEGRITY` ante un paquete alterado, `--ignore-scripts` evitó un `postinstall`, y `min-release-age` espera antes de instalar lo último.
- Registros sin secretos: 0 coincidencias, y 0 archivos de `dist` con el secreto. Nunca cuerpos, cabeceras ni _cookies_.
- Una lista de seguridad corta para cada lanzamiento, y lo demás, automatizado.
