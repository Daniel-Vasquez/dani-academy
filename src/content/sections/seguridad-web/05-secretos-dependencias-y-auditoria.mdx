Un código impecable se pierde por una clave subida a un repositorio y copiada por un bot en minutos, o por un paquete de años que publica una versión maliciosa. Los fallos de esta sección están **alrededor** de tu lógica: cómo guardas las llaves, de quién te fías y qué dejas escrito. Aquí impides subir secretos, rotas uno en segundos, priorizas `npm audit` y redactas una lista para cada lanzamiento.

**Requisitos:** las secciones anteriores de A5 y la app en tu servidor. Las pruebas con secretos usan valores falsos, en repositorios desechables.

## Paso 1: un secreto en Git no se borra

**Qué es:** Git guarda todo lo confirmado. **gitleaks** busca secretos en la historia; se ejecuta con Docker y `--redact` evita imprimirlos.

**Cómo se usa:** un repositorio de prueba con un _token_ falso en `config.js`:

```bash
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest git /repo --redact --no-banner
```

```text
con el token en un commit, git: exit 1 (0 limpio, 1 hay secretos)
```

Lo normal es borrar el archivo y confirmar:

```bash
git rm config.js
git commit -m "quita el token"
```

```text
tras borrarlo, carpeta: exit 0 (0 limpio, 1 hay secretos)
tras borrarlo, historia: exit 1 (0 limpio, 1 hay secretos)
```

- **La carpeta está limpia y el secreto sigue en la historia** (`git log -p`, y cualquier clon). **`git filter-repo`** la reescribe sin el archivo:

```bash
sudo apt-get install -y git-filter-repo
git filter-repo --force --invert-paths --path config.js
```

```text
tras filter-repo, historia: exit 0 (0 limpio, 1 hay secretos)
commits: 1
```

Con un clon hecho antes:

```text
una copia hecha antes (un clon, otro equipo): 2 líneas con el token
identificador del último commit:  c77140d (reescrito)  ·  feb6f39 (la copia)
```

- **Reescribir cambia los identificadores y no alcanza a clones, _forks_ ni cachés.** Si fue público un minuto, el secreto está comprometido: **primero rotar, después limpiar**.

Mejor que no entre. `.githooks/pre-commit`:

```bash
#!/usr/bin/env bash
# Archivo: .githooks/pre-commit
# Bloquea el commit si lo que está en el área de preparación contiene un secreto
exec docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest \
  git /repo --pre-commit --staged --redact --no-banner --no-color
```

```bash
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

```text
commit limpio: exit 0 · commits 2
commit con token: exit 1 · commits 2
```

- **El segundo _commit_ nunca llegó a la historia.** Y antes, `.gitignore` y `.env.example` (I3.6):

```bash
git check-ignore .env .env.local
git ls-files | grep -E '(^|/)\.env'
```

- **La primera debe listar los dos,** y la segunda solo `.env.example`.

<Callout type="risk">

- **Un gancho local se salta** (`--no-verify`, otro equipo): añade `gitleaks` a CI y la _push protection_ de GitHub.
- **Falsos positivos y huecos:** en el repositorio de este curso (93 _commits_) dio 5 hallazgos, todos ejemplos de lecciones; anótalos en `.gitleaksignore`. Y busca patrones: una contraseña inventada en un `const` puede pasar.
- **`git filter-repo` reescribe la historia de todos:** avisa y que cada persona vuelva a clonar. Un `.env` en una imagen o en un `Dockerfile` antiguo también es una filtración (A4.2).

</Callout>

## Paso 2: rotar en minutos

**Qué es:** si dudas, rota; y para no dudar, debe ser barato. `scripts/rotar-secreto.sh` cambia `BETTER_AUTH_SECRET` con el despliegue sin cortes de A4.5.

**Cómo se usa:**

```bash
#!/usr/bin/env bash
# Archivo: scripts/rotar-secreto.sh
# BETTER_AUTH_SECRET filtrado: nuevo secreto, despliegue sin cortes y sesiones revocadas.
# Uso, en el servidor, desde la carpeta del proyecto: bash scripts/rotar-secreto.sh
set -euo pipefail

DOMINIO="$(grep '^APP_HOSTNAME=' .env | cut -d= -f2)"
VERSION="$(curl -s -m 5 "https://$DOMINIO/api/health" | sed -E 's/.*"version":"([^"]+)".*/\1/')"
[ -n "$VERSION" ] || { echo "✗ La app no responde: arréglalo primero"; exit 1; }

if grep -q ':4321;' /etc/nginx/entrenos-activo.conf; then FILTRADA=blue; else FILTRADA=green; fi

echo "== 1. Secreto nuevo en .env"
NUEVO="$(openssl rand -base64 32)"
sed -i "s|^BETTER_AUTH_SECRET=.*|BETTER_AUTH_SECRET=$NUEVO|" .env

echo "== 2. Desplegar la misma versión ($VERSION) con el secreto nuevo"
bash scripts/desplegar.sh "$VERSION" | grep -E '^(✓|✗)'

echo "== 3. Quitar la instancia con el secreto filtrado: volver.sh no debe poder arrancarla"
docker compose rm -f "$FILTRADA" >/dev/null 2>&1

echo "== 4. Revocar todas las sesiones"
docker compose exec -T mongo mongosh --quiet entrenos --eval \
  'print("sesiones borradas:", db.session.deleteMany({}).deletedCount)'

echo "✓ Rotado. Ahora: revisa los registros de la ventana de exposición y anota el incidente"
```

Con la carga de A4.5 en marcha y una sesión abierta:

```text
sesión antes: /estadisticas -> 200
sesiones en la base: 49
== 1. Secreto nuevo en .env
== 2. Desplegar la misma versión (a54c) con el secreto nuevo
✓ a54c en producción (green). Para volver atrás: bash scripts/volver.sh
== 3. Quitar la instancia con el secreto filtrado: volver.sh no debe poder arrancarla
== 4. Revocar todas las sesiones
sesiones borradas: 49
✓ Rotado. Ahora: revisa los registros de la ventana de exposición y anota el incidente
tardó 17.60 s
```

```text
659 peticiones, 0 fallos
cookie antigua: /estadisticas -> 302
cookie antigua: /api/entrenos -> 401
volver a entrar -> 200
sesión nueva -> 200
```

- **17,6 s, sin errores, y todas las sesiones anteriores dejan de valer.** Docker recrea el contenedor porque cambió el `.env`.
- **Etapa 3:** el contenedor parado aún lleva el secreto filtrado y es el destino de `volver.sh`; se quita, y `volver.sh` responde `✗ No hay instancia anterior a la que volver`, lo correcto.
- **Etapa 4:** las _cookies_ antiguas ya no valen, y borrar las sesiones elimina los _tokens_ que seguían en la base (A5.1).

Cada secreto se rota distinto. `docs/rotar-secreto.md`:

```markdown
# Se ha filtrado un secreto

**Primero rotar, después limpiar.** Un secreto publicado está comprometido para siempre.

1. **Anota la hora.** Cuándo se filtró y cuándo lo has sabido: es tu ventana de exposición.
2. **Rota:**
   - `BETTER_AUTH_SECRET`: `bash scripts/rotar-secreto.sh`. Cierra todas las sesiones.
   - Contraseña de MongoDB: Atlas → Database Access → Edit, cambia `MONGODB_URI` en `.env` y despliega.
   - Token de Vercel, GitHub o de un bot: revócalo en su panel y crea otro.
3. **Revisa la ventana de exposición:** registros de acceso, usuarios nuevos, datos cambiados.
4. **Limpia Git** solo después (`git filter-repo`), y avisa a quien tenga un clon.
5. **Busca la causa:** ¿por qué entró? Añade el control que faltaba.
6. **Apúntalo** aquí: qué pasó, cuánto tardaste y qué has cambiado.
```

- **En Vercel,** _Settings_ → _Environment Variables_, y hay que desplegar otra vez. Un valor por entorno (I3.6): uno filtrado de _preview_ no debe abrir producción.

<Callout type="risk">

- **Rotar cierra las sesiones de todos:** avisa. Better Auth admite varias claves (`secrets`, versionadas) para rotar sin cerrarlas, no medido aquí y no válido si ya se filtró.
- **Filtrado y sin usar sigue siendo emergencia,** y rotar no deshace lo ya hecho: revisa la ventana de exposición.
- **`sed -i` conserva el `chmod 600`** del `.env` (medido), pero `docker inspect` enseña las variables a todo el grupo `docker` (equivale a `root`, A4.2).

</Callout>

## Paso 3: dependencias

**Qué es:** **`npm audit`** compara tus paquetes con una base de vulnerabilidades conocidas; el _lockfile_ y las opciones de npm protegen de las que aún no se conocen.

**Cómo se usa:**

```bash
npm audit --omit=dev
```

La app de entrenos, instalada hace pocas semanas:

```text
found 0 vulnerabilities
```

Otro proyecto real, con dependencias de hace meses y sin cambios en ese código:

```text
con devDependencies:     26 (16 moderadas, 10 altas)
solo producción:         14 (5 moderadas, 9 altas)
```

- **Las vulnerabilidades aparecen en código que no has tocado:** se repite, no se hace una vez. Y 14 no son 14 emergencias:
  1. **¿Se ejecuta en producción?** `--omit=dev` quita los tests, pero una herramienta de _build_ también sale y no se ejecuta al visitar tu web.
  2. **¿Llega un dato del atacante?** Un validador que agota la memoria con entradas enormes es **prioritario**; `launch-editor` solo en Windows en desarrollo, o una _regex_ lenta en una herramienta de _build_ que solo alimentas tú, no.
  3. **¿Hay arreglo?** `npm audit fix` aplica lo compatible (`--dry-run` lo enseña); un cambio mayor necesita pruebas, no `--force`.

En CI, falla solo en lo que vas a atender:

```bash
npm audit --omit=dev --audit-level=high
```

**Dependabot** abre un _pull request_ con cada versión nueva y tus tests la prueban. `.github/dependabot.yml`, y activa las actualizaciones en los ajustes de seguridad del repositorio (Renovate hace lo mismo, con más opciones):

```yaml
# Archivo: .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    cooldown:
      default-days: 7 # no propone versiones publicadas hace menos de 7 días
    open-pull-requests-limit: 5
    groups:
      menores:
        update-types: [minor, patch]
```

### La cadena de suministro

`npm audit` no ve un paquete comprometido ayer. **El _lockfile_ y `npm ci`:** `package-lock.json` guarda el _hash_ de cada paquete:

```text
npm error code EINTEGRITY
npm ci exit 1
```

- **Instala exactamente lo que probaste, o nada.**

**Los _scripts_ de instalación** ejecutan lo que quieran con tus permisos, en tu equipo, junto a tu `.env`. Con un paquete de prueba con `postinstall`:

```text
postinstall ejecutado (npm install): 1
postinstall ejecutado (npm ci --ignore-scripts): 0
```

- **Fijo con `ignore-scripts=true` en `.npmrc`,** permitiendo de uno en uno los que lo necesiten para compilar.

**Espera antes de instalar lo último:** los maliciosos se descubren en horas o días, y `min-release-age` ignora lo más reciente:

```bash
npm install zod --min-release-age=7
```

```text
con 7 días:        zod 4.6.7
con 36500 días:    npm error code ENOVERSIONS · No versions available for zod
```

Y `npm audit signatures` comprueba la firma del registro:

```text
audited 1 package in 1s
1 package has a verified registry signature
```

<Callout type="risk">

- **Revisa lo que instalas** (_typosquatting_: un nombre mal escrito que imita a otro): quién lo publica y sus descargas. Y menos dependencias, menos riesgo: `is-odd` existe y tiene dependencias.
- **`npm audit fix --force` salta versiones mayores:** en una rama, con tests. Dependabot vale lo que tus tests; sin mezcla automática en producción.
- **`dependabot.yml` no se ha ejecutado aquí** (necesita GitHub): comprueba su primera ejecución. Y la imagen (Alpine, Node) no aparece en `npm audit` (A4.6).

</Callout>

## Paso 4: registros sin secretos

**Qué es:** un secreto en un registro está en texto plano, en cada copia y en el servicio de registros.

**Cómo se usa:** busca el tuyo:

```bash
V="$(grep '^BETTER_AUTH_SECRET=' .env | cut -d= -f2-)"
sudo journalctl -t entrenos --no-pager | grep -cF "$V"
sudo journalctl -t entrenos --no-pager | grep -ciE 'mongodb(\+srv)?://|authorization|cookie:'
sudo grep -cE 'password|token=' /var/log/nginx/access.log
```

```text
0
0
0
```

- **Limpio, no por suerte:** el _middleware_ registra método, ruta y código, y `aRespuesta` escribe el error, no la petición.
- **Nunca** cuerpos, cabeceras enteras, _cookies_, contraseñas ni _tokens_; cuidado con `console.log(request)` o `console.log(usuario)`, que llevan lo que no ves.
- **Nada secreto en la URL** (registro de Nginx, historiales), y **un error puede llevar datos** (una URI con contraseña).

Ni en el navegador. El mismo valor, buscado en `dist` dentro de la imagen:

```text
archivos de dist con el secreto: 0
```

- **`astro:env` lo lee en el servidor;** solo `PUBLIC_` llega al cliente (I3.6).

<Callout type="risk">

- **Un servicio de errores como Sentry** puede enviar cabeceras o datos de la petición por defecto: revísalo.
- **Los correos son datos personales:** por eso el límite por cuenta de A5.4 guarda un _hash_.
- **Repite la búsqueda tras cada funcionalidad:** un `console.log` de depuración olvidado es el origen típico.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Ejecuta `gitleaks` sobre tus repositorios y revisa cada hallazgo. Instala el gancho `pre-commit`.
2. Activa Dependabot y revisa `npm audit --omit=dev` con las tres preguntas del Paso 3.
3. Redacta tu lista de seguridad para cada lanzamiento.
4. Haz un simulacro: cronometra una rotación completa de `BETTER_AUTH_SECRET`. Debe bajar de 15 minutos.

</Callout>

Solución. Los puntos 1, 2 y 4 son los Pasos 1 a 3. Para el 4, cuenta desde que decides rotar hasta comprobar que la sesión antigua no vale y que puedes volver a entrar: el _script_ tardó 17,6 s, y el resto es tu tiempo con `docs/rotar-secreto.md`. La lista, `docs/lanzamiento.md`:

```markdown
# Lista de seguridad antes de cada lanzamiento

## Secretos

- [ ] `gitleaks git .` sin hallazgos nuevos
- [ ] `.env` fuera de Git y con `chmod 600` en el servidor
- [ ] Ningún `PUBLIC_` contiene un secreto
- [ ] Sé dónde está cada secreto y cómo rotarlo (`docs/rotar-secreto.md`)

## Dependencias

- [ ] `npm audit --omit=dev --audit-level=high` revisado, con cada excepción anotada
- [ ] `package-lock.json` en el commit, y el servidor usa `npm ci`
- [ ] Sin paquetes nuevos que no haya leído

## Código

- [ ] `bash scripts/buscar-riesgos.sh src` revisado
- [ ] Cada ruta nueva filtra por `userId` y valida con Zod
- [ ] Ningún registro escribe contraseñas, tokens ni cookies
- [ ] Modelo de amenazas actualizado (`docs/amenazas.md`)

## Después de desplegar

- [ ] `bash scripts/auditar.sh <dominio> <ip>`
- [ ] `bash scripts/comprobar-cabeceras.sh <dominio>`
- [ ] `bash scripts/comprobar-limites.sh <dominio>`
- [ ] Copia reciente, restaurada (`docs/runbook.md`)
```

- **Cada línea sale de una sección:** `buscar-riesgos.sh` (A5.2), `auditar.sh` (A5.1), `comprobar-cabeceras.sh` (A5.3) y `comprobar-limites.sh` (A5.4). Es el resumen de lo que ya sabes comprobar.

<Callout type="risk">

- **Una lista que nadie usa no sirve:** corta; una línea que se marca sin mirar, automatízala o quítala.
- **Lo que un _script_ comprueba va a CI;** la lista, para lo que necesita criterio.
- **El simulacro cuenta como incidente:** apunta lo que no estaba escrito y corrígelo.

</Callout>

<Callout type="mastery">

Sabes rotar un secreto filtrado en menos de 15 minutos: primero cambias la cerradura, con un despliegue sin cortes y las sesiones revocadas; después revisas la ventana de exposición; y solo entonces limpias Git, sabiendo que eso no alcanza a ningún clon. Impides que entre con un gancho, priorizas `npm audit` por lo que de verdad se ejecuta y recibe datos del atacante, confías en el _lockfile_ y no en la suerte, y no escribes secretos en tus registros.

</Callout>

## Resumen

- Borrar en un _commit_ nuevo no elimina el secreto; `git filter-repo` limpia tu repositorio, no los clones.
- **Primero rotar, después limpiar.**
- Gancho `pre-commit` con `gitleaks`, y también en CI.
- Rotar `BETTER_AUTH_SECRET`: **17,6 s, 0 errores** en 659 peticiones; cierra sesiones y quita la instancia antigua.
- `npm audit --omit=dev`: 0 en un proyecto reciente, 14 en otro antiguo. Prioriza por producción, dato del atacante y arreglo.
- `EINTEGRITY`, `--ignore-scripts` y `min-release-age` frente a la cadena de suministro.
- Registros y `dist` sin secretos: 0 coincidencias.
- Una lista corta por lanzamiento; lo demás, automatizado.
