Casi todos los fallos de esta sección son uno: **tratar como instrucción algo que debía ser un dato**. El servidor espera un correo y recibe un trozo de consulta; el navegador espera un texto y recibe un `<script>`. Aquí reconoces inyección NoSQL y SQL, asignación masiva y los tres tipos de XSS, ves dónde tu _stack_ te protege y dónde no, y limpias HTML cuando hace falta.

**Requisitos:** `entrenos-app` y A5.1. Los ejemplos ❌ se midieron en rutas de laboratorio de un servidor de pruebas, borradas al terminar: **no los añadas a tu app** ni pruebes en webs ajenas.

## Paso 1: inyección NoSQL

**Qué es:** en MongoDB el filtro es un objeto, y el JSON de tu API también puede traer objetos, que MongoDB interpreta como operadores.

**Cómo se usa:** este inicio de sesión hecho a mano parece inofensivo:

```ts
// ❌ Vulnerable: el cuerpo llega a la consulta sin validar
const body = await request.json();
const cuenta = await cuentas.findOne({ email: body.email, clave: body.clave });
```

Con `clave` como objeto (`$ne` es «distinto de»):

```bash
curl -s -H "content-type: application/json" \
  -d '{"email":"ana@prueba.test","clave":{"$ne":null}}' http://localhost:4321/api/lab/nosql
```

```text
clave correcta                              {"cuenta":{"email":"ana@prueba.test"}}
clave equivocada                            {"cuenta":null}
clave {"$ne":null}                          {"cuenta":{"email":"ana@prueba.test"}}
email y clave {"$ne":null}                  {"cuenta":{"email":"ana@prueba.test"}}
email {"$gt":"b"}, clave {"$ne":null}       {"cuenta":{"email":"beto@prueba.test"}}
clave {"$regex":"^secreta"}                 {"cuenta":{"email":"ana@prueba.test"}}
clave {"$regex":"^xyz"}                     {"cuenta":null}
```

- **Entra sin conocer la contraseña:** «clave distinta de `null`» se cumple siempre. `$gt` elige a quién, y `$regex` deja adivinar la clave carácter a carácter.

La defensa, **comprobar el tipo antes de consultar**:

```ts
// ✅ Si no es un texto, ni llega a MongoDB
const r = z.object({ email: z.email(), clave: z.string() }).safeParse(body);
if (!r.success) return Response.json({ error: "Datos no válidos" }, { status: 400 });
const cuenta = await cuentas.findOne(r.data);
```

```text
clave correcta           {"cuenta":{"email":"ana@prueba.test"}} -> 200
clave {"$ne":null}       {"error":"Datos no válidos"} -> 400
```

Si no puedes validar, **`$eq`** compara literalmente:

```ts
await cuentas.findOne({ email: { $eq: body.email }, clave: { $eq: body.clave } });
```

```text
clave {"$ne":null}       {"cuenta":null} -> 200
```

**Validar no basta si el esquema admite objetos.** Tres trampas:

```ts
// ❌ Zod lo valida... y lo deja pasar: unknown y any aceptan un objeto
z.object({ email: z.unknown(), clave: z.any() }).parse(body);
```

```text
clave {"$ne":null}       {"cuenta":{"email":"ana@prueba.test"}} -> 200
```

```ts
// ❌ looseObject conserva los campos que no conoce, incluidos los operadores
z.looseObject({ email: z.string() }).safeParse(body);
```

```text
{"ok":true,"datos":{"email":"ana@prueba.test","$where":"true"}}
```

```ts
// ❌ El cuerpo entero como filtro: quien llama escribe la consulta
await cuentas.countDocuments(body);
```

```text
{"$or":[{"email":"x"},{"clave":{"$ne":null}}]}  ->  {"n":2}
```

**Asignación masiva** es lo mismo al escribir: con el cuerpo en `$set`, el cliente elige los campos:

```ts
// ❌ El cliente elige los campos
await entrenos.updateOne({ _id: id, userId }, { $set: body });
```

```text
{"minutos":46,"userId":"beto"}  ->  {"_id":"e1","userId":"beto","minutos":46}
```

- **El filtro por `userId` era correcto y el entreno cambió de dueño,** porque el campo llegó en el `$set`. Con un esquema estricto:

```ts
// ✅ Zod descarta lo que no está en el esquema
const cambios = z.object({ minutos: z.number().int().positive() }).parse(body);
await entrenos.updateOne({ _id: id, userId }, { $set: cambios });
```

```text
{"minutos":46,"userId":"beto"}  ->  {"_id":"e1","userId":"ana","minutos":46}
```

- **Es lo que hace tu app:** en A5.1 ese `userId` se ignoró.

<Callout type="risk">

- **Asume que el cuerpo es lo peor posible:** un formulario solo envía textos, pero `curl` manda JSON.
- **`?tipo[$ne]=x` no hace nada con `URLSearchParams`,** pero Express con `qs` lo convierte en objeto: valida también los parámetros, y antes de consultar.
- **`$regex` con datos del cliente consume CPU** (ReDoS): escapa la cadena o usa un índice de texto.

</Callout>

## Paso 2: inyección SQL

**Qué es:** lo de A3.4: con una plantilla `` `… '${email}'` ``, `x'; DROP TABLE usuarios; --` borró la tabla y `x' OR '1'='1` devolvió a todos.

**Cómo se usa:** separando la consulta de los valores:

```ts
// ❌ El valor forma parte del texto de la consulta
await pool.query(`SELECT nombre FROM usuarios WHERE email = '${email}'`);

// ✅ El valor viaja aparte y nunca se interpreta como SQL
await pool.query("SELECT nombre FROM usuarios WHERE email = $1", [email]);
```

- **Drizzle parametriza también dentro de `sql`;** `sql.raw()`, no: solo con texto que no venga del usuario.

<Callout type="risk">

- **Columnas y tablas no se parametrizan** (`ORDER BY $1` no funciona): compara con una lista cerrada (`z.enum(["fecha", "minutos"])`).
- **No escapes a mano:** quitar comillas falla en el caso que no pensaste.

</Callout>

## Paso 3: XSS

**Qué es:** **XSS** (_Cross-Site Scripting_) es inyección en el navegador de otro: tu web le entrega un _script_ del atacante y lo ejecuta como tuyo. **Reflejado** (viene en la URL de un enlace preparado), **almacenado** (en tu base, ataca a todo el que lo vea; el peor) y **de DOM** (tu JavaScript lee la URL y la escribe en la página).

**Cómo se usa:** cada variante, en Chromium, con una carga que solo incrementa un contador:

```text
EJECUTA  set:html con ?q=, <img onerror>         <img src="x" onerror="…">
EJECUTA  set:html con ?q=, <script>              <script>…</script>
no       {q} en Astro, <img onerror>             &lt;img src=x onerror="…"&gt;
no       {q} en Astro, <script>                  &lt;script&gt;…&lt;/script&gt;
EJECUTA  innerHTML con #hash, <img onerror>      <img src="x" onerror="…">
no       innerHTML con #hash, <script>           <script>…</script>
no       textContent con #hash, <img onerror>
EJECUTA  dangerouslySetInnerHTML, <img onerror>  <img src="x" onerror="…">
EJECUTA  dangerouslySetInnerHTML, <script>       <script>…</script>
no       {html} en React, <img onerror>          &lt;img src=x onerror="…"&gt;
```

- **`{q}` en Astro y `{html}` en React escapan:** `<` pasa a `&lt;` y se pinta como texto.
- **`set:html`, `dangerouslySetInnerHTML` e `innerHTML` son salidas de emergencia:** interpretan HTML. Con `innerHTML`, `<script>` no se ejecuta pero `<img onerror>` sí: bloquear `<script>` no protege.

```astro
---
const q = Astro.url.searchParams.get("q") ?? "";
---
<!-- ✅ Se escapa -->
<p>{q}</p>
<!-- ❌ Se interpreta como HTML -->
<p set:html={q} />
```

```js
// ❌ De DOM: lee de la URL y escribe HTML
document.querySelector("#m").innerHTML = decodeURIComponent(location.hash.slice(1));
// ✅ Texto, nunca HTML
document.querySelector("#t").textContent = decodeURIComponent(location.hash.slice(1));
```

**Almacenado:** el campo `notas` acepta cualquier texto de hasta 200 caracteres, y eso es correcto (`<img …>` es texto válido; 201). El peligro es cómo se muestra. Con `set:html` y una sesión real:

```text
guardar nota con HTML -> 201
EJECUTA  modo=mal (set:html)
   cookies que ve el script: "" · entrenos leídos con la sesión: 1
no       modo=bien ({notas})
```

- **El _script_ no leyó la _cookie_** (`document.cookie` vacío, por `HttpOnly`):

```text
__Secure-better-auth.session_token httpOnly=true secure=true sameSite=Lax
```

- **Pero pidió `/api/entrenos` con la sesión de la víctima y leyó sus datos:** el navegador adjunta la _cookie_ solo. `HttpOnly` limita el daño, no sustituye a escapar.

<Callout type="risk">

- **Validar la entrada no detiene el XSS:** la defensa es escapar la **salida** según el contexto. Quitar `<` al guardar rompe «3 < 5» y no protege. Bloquear palabras tampoco: hay decenas de formas sin `<script>`.
- **`set:html={JSON.stringify(datos)}` en un `<script>` es vulnerable:** `</script>` lo cierra. Pasa datos por `props` a las islas.
- **CSP es la segunda capa:** sin `unsafe-inline` en `script-src`, los manejadores en línea no se ejecutan (A5.3).

</Callout>

## Paso 4: un `href` también ejecuta código

**Qué es:** un enlace con datos del usuario (`<a href={usuario.web}>`) donde el peligro no son las comillas sino el protocolo.

**Cómo se usa:**

```astro
<a href={usuario.web}>Mi web</a>
```

Astro escapa las comillas: no se sale del atributo.

```text
href del enlace: "><img src=x onerror="…">   →  todo se queda dentro del atributo
```

Con `javascript:window.__xss=1`, al hacer clic:

```text
Astro:  href="javascript:window.__xss=1"                            EJECUTA
React:  href="javascript:throw new Error('React has blocked…')"     no
```

- **Astro escapa, pero no mira el protocolo:** no hay nada que escapar tras `javascript:`. React 19 lo bloquea. Y la validación habitual lo acepta:

```ts
z.url().safeParse("javascript:alert(1)").success; // true
```

```text
z.url()  true  javascript:alert(1)
z.url()  true  JaVaScRiPt:alert(1)
z.url()  true  data:text/html,hola
```

Hay que decir qué protocolos aceptas:

```ts
// ✅ Una lista de lo permitido
const Web = z.url({ protocol: /^https?$/ });
```

```text
false  "javascript:alert(1)"
false  "JaVaScRiPt:alert(1)"
false  "data:text/html,hola"
false  "ftp://example.com"
false  " javascript:alert(1)"
true   "https://example.com/ruta"
true   "http://example.com"
```

<Callout type="risk">

- **Lista de permitidos, no de prohibidos:** «no empieza por `javascript:`» falla con mayúsculas, espacios y `data:`.
- **Los datos guardados antes de la regla siguen en la base:** valida también al mostrar. Y `src`, `action` y `formaction` tienen el mismo problema.
- **El `href` de error de React** deja un enlace muerto, que es correcto, pero la entrada sigue mal.

</Callout>

## Paso 5: cuando de verdad necesitas HTML

**Qué es:** tres opciones, de mejor a peor: no necesitarlo, construirlo tú desde datos que no son HTML, o limpiar el del usuario.

**Cómo se usa:**

- **No necesitarlo:** para los saltos de línea de una nota, `white-space: pre-line` y `{notas}` tal cual.
- **Construirlo tú:** las notas personales de esta plataforma (negrita, cursiva, color) se guardan como JSON validado con Zod, y `renderNoteHtml` las convierte:

```ts
const escapeHtml = (s: string) =>
  s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;").replace(/"/g, "&quot;");

let html = escapeHtml(node.text); // el texto del usuario, siempre escapado
if (marks.some((m) => m.type === "bold")) html = `<strong>${html}</strong>`; // las etiquetas son tuyas
```

- **Es uno de los dos únicos sitios con HTML crudo de la plataforma:** las etiquetas las escribe el código y lo del usuario siempre se escapa.
- **Limpiarlo:** **DOMPurify** lo analiza con un parser real y quita lo que no esté en tu lista. En el servidor necesita `jsdom`:

```bash
npm install dompurify jsdom
```

```ts
// Archivo: src/lib/limpiar-html.ts
// Limpia HTML que escribe el usuario: solo pasan estas etiquetas y estos atributos
import createDOMPurify from "dompurify";
import { JSDOM } from "jsdom";

const DOMPurify = createDOMPurify(new JSDOM("").window);

export function limpiarHtml(sucio: string): string {
  return DOMPurify.sanitize(sucio, {
    ALLOWED_TAGS: ["p", "br", "strong", "em", "ul", "ol", "li", "a"],
    ALLOWED_ATTR: ["href"],
  });
}
```

```astro
<p set:html={limpiarHtml(notas)} />
```

```text
<img src=x onerror="…">                       => (vacío)
<script>…</script>                            => (vacío)
<svg onload="x()">                            => (vacío)
<a href="javascript:x()">a</a>                => <a>a</a>
<a href="https://example.com" onclick="x()">b</a>  => <a href="https://example.com">b</a>
<strong>hola</strong> <em>mundo</em>          => <strong>hola</strong> <em>mundo</em>
<iframe src="https://example.com"></iframe>   => (vacío)
<style>*{display:none}</style>                => (vacío)
```

La página de antes, con el mismo dato malicioso:

```text
no       modo=limpio (set:html con limpiarHtml)
```

- **`ALLOWED_TAGS` y `ALLOWED_ATTR`:** una lista corta de lo permitido.
- **Nada de _regex_:** los navegadores reparan el HTML mal formado de formas sorprendentes (mXSS); el caso `<math><mtext>…` también quedó vacío.

<Callout type="risk">

- **Limpia en la salida y conserva el original:** si DOMPurify corrige un fallo, lo guardado ya limpio no se beneficia. Y mantenlo al día (A5.5).
- **`jsdom` pasa a producción** (era `devDependency` desde I7.3): la imagen sube de 562 a 565 MB. En _serverless_, valora `sanitize-html`.
- **Permitir `a` deja enlazar a cualquier web,** aunque DOMPurify quite `javascript:`. Si no lo necesitas, quítalo.

</Callout>

<Callout type="mastery">

Ningún dato del cliente llega a una consulta o al HTML sin validar o escapar. Compruebas el tipo antes de consultar, sabiendo que `z.any()` y `looseObject` no protegen; nunca pasas el cuerpo a `$set`; dejas que Astro y React escapen; tratas `set:html`, `dangerouslySetInnerHTML` e `innerHTML` como excepciones que hay que justificar; y validas el protocolo de cada URL, porque ni `z.url()` ni el `href` de Astro lo hacen.

</Callout>

## Resumen

- La raíz: un dato tratado como instrucción.
- **NoSQL:** `{"$ne":null}` entró sin contraseña; `z.string()` o `$eq` lo paran, `z.any()`, `z.unknown()` y `looseObject` no.
- **Asignación masiva:** `$set: body` cambió el dueño de un entreno; solo campos validados.
- **SQL:** parámetros, nunca plantillas ni `sql.raw()` con datos.
- **XSS:** `set:html`, `dangerouslySetInnerHTML` e `innerHTML` ejecutaron `<img onerror>`; `HttpOnly` no impidió leer datos con la sesión.
- **`href` con `javascript:`:** Astro lo deja y `z.url()` lo acepta; `z.url({ protocol: /^https?$/ })`.
- **HTML del usuario:** evítalo, constrúyelo escapando o DOMPurify con lista corta.
