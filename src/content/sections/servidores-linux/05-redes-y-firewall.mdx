Tu app escucha en el puerto 3000, y la pregunta es: **¿quién más puede conectarse?** Cada programa que escucha en un puerto es una puerta abierta a Internet: una base de datos sin proteger, un panel de pruebas, la app sin el servidor web delante. Aquí haces el inventario de puertos, diagnosticas conexiones, cierras con un **_firewall_** todo salvo SSH y la web, y frenas a quien prueba credenciales contra SSH.

**Requisitos:** el servidor de I6.4 con `entrenos` en el puerto 3000. Los comandos van en el servidor (`ssh academy`), salvo los que indican el Mac.

## Paso 1: interfaces, IPs y puertos abiertos

**Qué es:** **`ip -brief address`** lista las **interfaces** de red y sus IPs, **`ip route`** dice por dónde sale el tráfico y **`ss -tlnp`** (TCP, a la escucha, en número, con el proceso; `-u` añade UDP) dice qué programa escucha y **en qué dirección**.

**Cómo se usa:**

```text
$ ip -brief address
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             192.168.5.15/24 metric 200 fe80::5055:55ff:fe88:6e63/64
lima0            UP             192.168.64.2/24 metric 100 fdd7:c1c8:f4c7:a5d0:5055:55ff:feae:de30/64 fe80::5055:55ff:feae:de30/64
$ ip route | head -n 3
default via 192.168.64.1 dev lima0 proto dhcp src 192.168.64.2 metric 100
default via 192.168.5.2 dev eth0 proto dhcp src 192.168.5.15 metric 200
192.168.5.0/24 dev eth0 proto kernel scope link src 192.168.5.15 metric 200
$ sudo ufw status
Status: inactive
```

- **`lo` es la propia máquina** (`127.0.0.1`); `lima0`, la red con tu Mac (`192.168.64.2`); `eth0`, la interna de Lima. En un VPS verás la IP pública.
- **`ufw` está inactivo:** todo lo que escucha está expuesto.

```text
$ sudo ss -tlnp
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      4096   127.0.0.53%lo:53         0.0.0.0:*    users:(("systemd-resolve",pid=633,fd=20))
LISTEN 0      4096       127.0.0.1:42565      0.0.0.0:*    users:(("containerd",pid=1318,fd=16))
LISTEN 0      4096         0.0.0.0:22         0.0.0.0:*    users:(("sshd",pid=1074,fd=3),("systemd",pid=1,fd=207))
LISTEN 0      4096      127.0.0.54:53         0.0.0.0:*    users:(("systemd-resolve",pid=633,fd=22))
LISTEN 0      511                *:3000             *:*    users:(("node",pid=1008,fd=21))
LISTEN 0      4096            [::]:22            [::]:*    users:(("sshd",pid=1074,fd=4),("systemd",pid=1,fd=208))
```

| Dirección                      | Quién puede conectarse                           | En este servidor                |
| ------------------------------ | ------------------------------------------------ | ------------------------------- |
| `127.0.0.1:…` o `127.0.0.53:…` | Solo la propia máquina                           | El DNS local (53), `containerd` |
| `0.0.0.0:…` o `[::]:…`         | Cualquiera, por cualquier interfaz (IPv4 o IPv6) | SSH (22)                        |
| `*:…`                          | Cualquiera, IPv4 e IPv6                          | **Tu app (3000)**               |

Desde tu Mac responden la app, SSH y `ping`:

```text
$ curl -s http://192.168.64.2:3000/   (desde el Mac)
{"pid":1008,"enMarchaSeg":118}
$ nc -z -G 3 192.168.64.2 22 && echo abierto
Connection to 192.168.64.2 port 22 [tcp/ssh] succeeded!
abierto
$ ping -c 2 192.168.64.2
2 packets transmitted, 2 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 0.182/0.506/0.830/0.324 ms
```

<Callout type="risk">

- **Escuchar en `127.0.0.1` es la primera defensa:** no se alcanza desde fuera ni sin _firewall_. Bases de datos y apps detrás de un servidor web (A4), así. Node escucha en todas si no se lo dices (`servidor.listen(PORT, "127.0.0.1")`).
- **Revisa `ss -tlnp` tras instalar algo:** muchos paquetes arrancan un servicio con puerto. Si no sabes qué es, averígualo.

</Callout>

## Paso 2: diagnosticar con `curl` y `ping`

**Qué es:** herramientas para saber **en qué capa falla** una conexión: sin `ping`, es la red (o el servidor está apagado); con `ping` pero sin puerto, el programa o el _firewall_; con puerto pero con error, la app.

**Cómo se usa:**

| Herramienta | Qué comprueba                                               | Ejemplo                                           |
| ----------- | ----------------------------------------------------------- | ------------------------------------------------- |
| `ping`      | Que la máquina responde en la red (ICMP)                    | `ping -c 2 192.168.64.2`                          |
| `nc -z`     | Que un puerto TCP acepta conexiones                         | `nc -z -G 3 192.168.64.2 22` (en Linux, `-w 3`)   |
| `curl -sS`  | Que una web responde, y qué responde                        | `curl -sS --max-time 5 http://192.168.64.2:3000/` |
| `curl -I`   | Solo las cabeceras de la respuesta                          | `curl -I https://academy.danielvasquez.lat`       |
| `ss -tlnp`  | En el servidor: que el programa escucha, y en qué dirección | Paso 1                                            |

<Callout type="risk">

- **Sin `ping` no siempre está caído:** muchos proveedores bloquean ICMP. Prueba también el puerto.
- **`curl -s` oculta los errores:** un fallo parece una respuesta vacía. Para diagnosticar, `curl -sS` o `curl -v`.

</Callout>

## Paso 3: un _firewall_ con `ufw`

**Qué es:** un **_firewall_** decide qué conexiones entran. **`ufw`** (_Uncomplicated Firewall_) lo configura en Ubuntu con la regla de oro: **denegar todo lo que entra y permitir solo lo necesario**, aquí SSH (22), HTTP y HTTPS (80 y 443). El 3000 no se expone: en producción, el servidor web lo sirve por el 443 (A4).

**Cómo se usa:** estas órdenes, en este orden, las aplicarás en el ejercicio:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable
```

- **`default deny incoming`** deja fuera lo que no tenga regla; **`default allow outgoing`** permite salir (para `apt`, MongoDB Atlas…).
- **`allow OpenSSH`** abre el 22 con el perfil de Ubuntu (`sudo ufw app list`), y **`enable`** lo activa ya y en cada arranque, preguntando antes porque podría cortar tu SSH.

<Callout type="risk">

- **SSH antes de `enable`:** con `deny incoming` y sin esa regla, en un VPS te dejas fuera; solo queda la consola del proveedor (en Lima, `limactl shell`).
- **Con Docker, `ufw` no basta:** `docker run -p 8080:80` abre reglas propias que `ufw` no controla. Publica solo en `127.0.0.1` (`-p 127.0.0.1:8080:80`).

</Callout>

## Paso 4: `fail2ban` contra los intentos de entrada

**Qué es:** con el 22 abierto llegan intentos automáticos sin parar; con SSH solo por clave (I6.3) no adivinan nada, pero llenan registros y gastan recursos. **`fail2ban`** lee los registros y bloquea un tiempo en el _firewall_ las IP que fallan demasiado.

**Cómo se usa:**

```bash
sudo apt install -y fail2ban
```

```text
$ sudo apt install -y fail2ban 2>&1 | grep -E "Installing:|Summary" | head -2
Installing:
Summary:
$ systemctl is-active fail2ban
active
$ cat /etc/fail2ban/jail.d/defaults-debian.conf
[DEFAULT]
banaction = nftables
banaction_allports = nftables[type=allports]

[sshd]
backend = systemd
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
enabled = true
$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed:	0
|  |- Total failed:	0
|  `- Journal matches:	_SYSTEMD_UNIT=ssh.service + _COMM=sshd
`- Actions
   |- Currently banned:	0
   |- Total banned:	0
   `- Banned IP list:
$ sudo fail2ban-client get sshd maxretry; sudo fail2ban-client get sshd findtime; sudo fail2ban-client get sshd bantime
5
600
600
```

- **En Ubuntu, `[sshd]` viene activado** (`/etc/fail2ban/jail.d/defaults-debian.conf`) y lee el diario de `systemd`.
- **Por defecto:** 5 fallos (`maxretry`) en 10 minutos (`findtime`) bloquean la IP 10 minutos (`bantime`).

Seis intentos fallidos desde tu Mac contra **tu** servidor de práctica, con un usuario inexistente:

```text
$ for i in 1 2 3 4 5 6; do ssh -o BatchMode=yes nadie@192.168.64.2 true; done   (desde el Mac)
nadie@192.168.64.2: Permission denied (publickey).
nadie@192.168.64.2: Permission denied (publickey).
nadie@192.168.64.2: Permission denied (publickey).
nadie@192.168.64.2: Permission denied (publickey).
nadie@192.168.64.2: Permission denied (publickey).
nadie@192.168.64.2: Permission denied (publickey).
$ sudo fail2ban-client status sshd   (en el servidor)
Status for the jail: sshd
|- Filter
|  |- Currently failed:	1
|  |- Total failed:	6
|  `- Journal matches:	_SYSTEMD_UNIT=ssh.service + _COMM=sshd
`- Actions
   |- Currently banned:	1
   |- Total banned:	1
   `- Banned IP list:	192.168.64.1
$ ssh academy whoami   (desde el Mac, con la clave buena)
ssh: connect to host 192.168.64.2 port 22: Connection refused
$ sudo fail2ban-client set sshd unbanip 192.168.64.1   (en el servidor, por la consola: limactl shell)
1
$ ssh academy whoami   (desde el Mac)
deploy
```

- **Tras 5 fallos, tu Mac (`192.168.64.1`) queda bloqueado,** y como es por IP, ni tu clave buena entra (`Connection refused`).
- **`unbanip`** lo levanta, por **otra** vía: `limactl shell` aquí; en un VPS, la consola del proveedor o esperar 10 minutos.

<Callout type="risk">

- **Puedes bloquearte a ti mismo:** un `ssh` probando claves equivocadas o una IP de oficina compartida. Tus IP fijas, en `ignoreip` de `/etc/fail2ban/jail.local` (nunca en `jail.conf`).
- **`fail2ban` frena, no protege:** con muchas IP, nadie llega al límite. La protección real es SSH solo con clave (I6.3).

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Configura `ufw` en tu servidor de práctica: denegar lo que entra por defecto, permitir SSH, 80 y 443, y activarlo.
2. Comprueba desde tu Mac que el puerto 22 sigue abierto y que el 3000 de la app, que no está permitido, está cerrado.
3. Explica la diferencia entre lo que responde el 3000 y lo que responde el 80, que está permitido pero no tiene ningún programa escuchando.

</Callout>

Solución, en el servidor (responde `y` en `enable`):

```text
$ sudo ufw default deny incoming
Default incoming policy changed to 'deny'
(be sure to update your rules accordingly)
$ sudo ufw default allow outgoing
Default outgoing policy changed to 'allow'
(be sure to update your rules accordingly)
$ sudo ufw allow OpenSSH
Rules updated
Rules updated (v6)
$ sudo ufw allow 80,443/tcp
Rules updated
Rules updated (v6)
$ yes | sudo ufw enable
Firewall is active and enabled on system startup
$ sudo ufw status verbose
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
22/tcp (OpenSSH)           ALLOW IN    Anywhere
80,443/tcp                 ALLOW IN    Anywhere
22/tcp (OpenSSH (v6))      ALLOW IN    Anywhere (v6)
80,443/tcp (v6)            ALLOW IN    Anywhere (v6)

$ sudo ufw status numbered
Status: active

     To                         Action      From
     --                         ------      ----
[ 1] OpenSSH                    ALLOW IN    Anywhere
[ 2] 80,443/tcp                 ALLOW IN    Anywhere
[ 3] OpenSSH (v6)               ALLOW IN    Anywhere (v6)
[ 4] 80,443/tcp (v6)            ALLOW IN    Anywhere (v6)

$ curl -s localhost:3000/; echo
{"pid":1008,"enMarchaSeg":135}
```

- **`status verbose`** da la política (`deny (incoming), allow (outgoing)`) y las reglas IPv4 e IPv6 (`v6`); **`status numbered`** las numera para `sudo ufw delete 2`.
- **Dentro del servidor, la app sigue respondiendo** (`curl localhost:3000`): `ufw` filtra lo que viene de fuera.

Desde el Mac:

```text
$ curl -sS --max-time 5 http://192.168.64.2:3000/   (desde el Mac)
curl: (28) Connection timed out after 5003 milliseconds (5.0 s)
$ nc -z -G 3 192.168.64.2 22 && echo abierto
Connection to 192.168.64.2 port 22 [tcp/ssh] succeeded!
abierto
$ curl -sS --max-time 5 http://192.168.64.2:80/
curl: (7) Failed to connect to 192.168.64.2 port 80 after 1002 ms: Couldn't connect to server (1.1 s)
$ ping -c 1 192.168.64.2 | tail -n 2
1 packets transmitted, 1 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 0.578/0.578/0.578/nan ms
```

- **El 3000 se rinde a los 5 segundos** (`Connection timed out`): `ufw` **descarta** en silencio, y quien explora puertos no recibe pistas.
- **El 80 rechaza al instante** (`Couldn't connect`): `ufw` lo deja pasar, pero nadie escucha.
- **El 22 sigue abierto y `ping` funciona:** `ufw` permite ICMP de serie.

<Callout type="risk">

- **Con Lima, no compruebes contra `localhost`:** Lima reenvía al Mac los puertos de la máquina **por dentro**, saltándose `ufw`. Medido: `http://localhost:3000` sigue respondiendo, y quien escucha en el Mac es `limactl`. Prueba contra `192.168.64.2`.
- **`ufw status` dice las reglas, no lo accesible:** la prueba real es conectarse desde otra máquina.

</Callout>

<Callout type="mastery">

Sabes qué puertos expone tu servidor y por qué: los lees con `ss -tlnp` y distingues lo que escucha solo en _localhost_ de lo que escucha para todos, diagnosticas por capas con `ping`, `nc` y `curl`, dejas abiertos con `ufw` solo SSH, 80 y 443, compruebas desde fuera que el resto no responde y tienes `fail2ban` frenando los intentos repetidos contra SSH.

</Callout>

## Resumen

- `ip -brief address` y `ss -tlnp`: `127.0.0.1` es solo local; `0.0.0.0` o `*`, para todos.
- Por capas: `ping` (red), `nc -z` (puerto), `curl -sS` (aplicación).
- `ufw default deny incoming`, SSH antes de activar, 80 y 443, y `ufw enable`.
- Bloqueado: _timeout_; permitido sin programa: rechazo inmediato.
- `fail2ban`: 5 fallos en 10 minutos, 10 minutos fuera; `unbanip` e `ignoreip`.
