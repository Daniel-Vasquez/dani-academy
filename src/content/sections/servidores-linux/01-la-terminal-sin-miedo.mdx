Un servidor no tiene Finder: no hay ventanas ni ratón, solo una terminal. Este curso te enseña a administrar uno, y todo empieza aquí. La terminal no es más difícil que el Finder, pero sí distinta: en lugar de hacer clic, escribes lo que quieres, y eso tiene una ventaja enorme. Lo que escribes se puede repetir, combinar y automatizar. En esta sección vas a moverte por carpetas, crear y borrar archivos, leer el registro de peticiones de tu app de entrenamiento y buscar en él, todo en el `zsh` de tu Mac. También verás la diferencia con `bash`, la terminal de casi todos los servidores, que te encontrarás en el resto del curso.

**Lo que tendrás al terminar:** soltura con los comandos de archivos, lectura y búsqueda, tuberías y redirecciones, y tus propios alias en `~/.zshrc`.

**Requisitos:** un Mac con iTerm2 o la app Terminal, y tu `entrenos-app` (I3) con un registro de peticiones en `logs/app.log`. Para crearlo, arranca la app en segundo plano, navega un rato (con y sin sesión) y guarda las líneas del _middleware_ de registro de I3.4:

```bash
cd ~/entrenos-app
npx astro dev --background
mkdir -p logs
npx astro dev logs | grep "→" > logs/app.log
```

## Paso 1: la _shell_ y las rutas

La **terminal** (iTerm2) es la ventana; la **_shell_** es el programa que lee lo que escribes y lo ejecuta. macOS usa **`zsh`** desde 2019; la mayoría de servidores Linux usan **`bash`**. Para el día a día son casi iguales, con alguna diferencia importante (al final de este paso). Cada comando se ejecuta en la **carpeta actual**, y las rutas indican dónde está un archivo:

- **Ruta absoluta:** empieza por `/`, desde la raíz del disco. `/usr/bin` es la misma carpeta estés donde estés.
- **Ruta relativa:** desde la carpeta actual. `proyecto/src` es "la carpeta `src` dentro de `proyecto`, aquí".
- **Atajos:** `.` es la carpeta actual, `..` la de arriba, `~` tu carpeta personal y `cd -` vuelve a la anterior.

Crea una carpeta de práctica y muévete por ella:

```bash
mkdir ~/practica-terminal
cd ~/practica-terminal
```

```text
$ echo $SHELL
/bin/zsh
$ pwd
/Users/tu-usuario/practica-terminal
$ cd .. && pwd
/Users/tu-usuario
$ cd ~ && pwd
/Users/tu-usuario
$ cd /usr/bin && pwd
/usr/bin
$ mkdir -p proyecto/src/components && cd proyecto/src && pwd
/Users/tu-usuario/practica-terminal/proyecto/src
$ cd proyecto/src && cd ../.. && pwd
/Users/tu-usuario/practica-terminal
```

- **`pwd`** (_print working directory_) dice dónde estás. Ante la duda, ejecútalo.
- **`mkdir -p`** crea las carpetas intermedias que falten (`proyecto` y `src` antes que `components`) y no da error si ya existen.
- **Cada línea de la salida** empieza con `$` y el comando (es la convención de este curso: el `$` no se escribe); debajo, lo que respondió.

La diferencia que más sorprende entre las dos _shells_: una variable con espacios, **sin comillas**.

```text
— en el Mac (zsh):
$ archivo="mi informe.txt"; touch $archivo; ls
mi informe.txt
— en el servidor (bash):
$ echo $SHELL
/bin/bash
$ archivo="mi informe.txt"; touch $archivo; ls
informe.txt
mi
$ archivo="mi informe.txt"; touch "$archivo"; ls
mi informe.txt
```

En `bash`, `$archivo` sin comillas se parte por los espacios, y `touch` recibe dos argumentos: `mi` e `informe.txt`. `zsh` no lo hace. Con comillas (`"$archivo"`), las dos funcionan igual. En el servidor, y en los _scripts_ de I6.6, **pon siempre las variables entre comillas**.

<Callout type="risk">

- **El tabulador es tu mejor amigo:** escribe el principio de un nombre y pulsa Tab, y la _shell_ lo completa. Evita erratas y te dice si un archivo existe, antes de que un comando falle.
- **Los nombres con espacios necesitan comillas:** `cd Mis documentos` intenta entrar en `Mis` y falla; `cd "Mis documentos"` funciona. En tus propios proyectos, evita espacios en los nombres de archivo.
- **Un comando pegado de Internet se ejecuta tal cual:** antes de pegarlo, léelo y entiende qué hace. Un `cd` que falla seguido de un `rm` borra en la carpeta equivocada (Paso 2).

</Callout>

## Paso 2: crear, copiar, mover y borrar

```text
$ touch notas.txt .oculto
$ ls
notas.txt
proyecto
$ ls -la
total 0
drwxr-xr-x@ 5 tu-usuario  wheel  160 16 oct 14:13 .
drwxr-xr-x@ 3 tu-usuario  wheel   96 16 oct 14:13 ..
-rw-r--r--@ 1 tu-usuario  wheel    0 16 oct 14:13 .oculto
-rw-r--r--@ 1 tu-usuario  wheel    0 16 oct 14:13 notas.txt
drwxr-xr-x@ 3 tu-usuario  wheel   96 16 oct 14:13 proyecto
$ cp notas.txt copia.txt && ls
copia.txt
notas.txt
proyecto
$ mv copia.txt renombrada.txt && ls
notas.txt
proyecto
renombrada.txt
$ mkdir docs && mv renombrada.txt docs/ && ls docs
renombrada.txt
$ cp -r docs docs-copia && ls
docs
docs-copia
notas.txt
proyecto
$ rm notas.txt && ls
docs
docs-copia
proyecto
$ rm docs-copia
rm: docs-copia: is a directory
$ rm -r docs-copia && ls
docs
proyecto
```

| Comando         | Qué hace                                            | Ejemplo                       |
| --------------- | --------------------------------------------------- | ----------------------------- |
| `touch`         | Crea un archivo vacío (o actualiza su fecha)        | `touch notas.txt`             |
| `ls` / `ls -la` | Lista la carpeta / con ocultos y detalles           | `ls -la`                      |
| `cp` / `cp -r`  | Copia un archivo / una carpeta con su contenido     | `cp -r docs docs-copia`       |
| `mv`            | Mueve **o** renombra (es lo mismo: cambiar la ruta) | `mv copia.txt renombrada.txt` |
| `rm` / `rm -r`  | Borra un archivo / una carpeta con su contenido     | `rm -r docs-copia`            |

- **Los archivos que empiezan por `.` están ocultos:** `ls` no enseña `.oculto`; `ls -la` sí. `.env`, `.gitignore` y `.zshrc` son ocultos por esto.
- **`ls -la` da los permisos, el dueño, el grupo, el tamaño y la fecha.** Los leerás en I6.2. En tu carpeta personal, el grupo será `staff`.
- **`rm` no borra carpetas sin `-r`:** `rm docs-copia` responde `is a directory`. Es una pequeña protección.

<Callout type="risk">

- **`rm` no tiene papelera:** lo borrado no se recupera. Si dudas, usa `rm -i` (pregunta por cada archivo), o mueve a una carpeta temporal en lugar de borrar.
- **Nunca combines un `cd` que puede fallar con un `rm` que usa rutas relativas:** si `cd carpeta-con-errata && rm -r *` falla el `cd`, el `&&` lo para; con `;` en lugar de `&&`, el `rm` se ejecutaría en la carpeta en la que estabas. Esta plataforma tiene esa regla en sus notas desde que un `cd` fallido sobrescribió un `.env`.
- **`cp` y `mv` pisan sin avisar:** si el destino existe, lo sustituyen. `cp -i` y `mv -i` preguntan antes.

</Callout>

## Paso 3: leer archivos

En la carpeta de tu app:

```bash
cd ~/entrenos-app
```

```text
$ head -n 3 logs/app.log
POST /api/auth/sign-in/email → 200 (65.5 ms)
GET /estadisticas → 200 (21.5 ms)
GET /api/entrenos → 200 (2.0 ms)
$ tail -n 2 logs/app.log
GET /estadisticas → 302 (0.1 ms)
GET /api/resumen → 200 (1.6 ms)
$ wc -l logs/app.log
      36 logs/app.log
```

- **`cat`** vuelca el archivo entero. Bien para archivos cortos; para uno de miles de líneas, inunda la pantalla.
- **`less`** lo abre para leerlo con calma: flechas o espacio para avanzar, `/texto` para buscar, `n` para el siguiente resultado y `q` para salir. Es lo que usarás para leer configuraciones en el servidor.
- **`head -n 3` y `tail -n 2`**, las primeras y las últimas líneas. `wc -l` cuenta las líneas: 36 peticiones.

**`tail -f`** (_follow_) se queda esperando y enseña cada línea nueva según llega. Es la forma de ver un registro en directo. Con la app escribiendo en el registro mientras lo sigues, filtrando solo los errores 4xx:

```bash
tail -n 0 -f logs/app.log | grep --line-buffered "→ 4"
```

```text
GET /api/entrenos/abc → 404 (0.3 ms)
POST /api/entrenos → 422 (0.8 ms)
```

Llegaron cuatro líneas nuevas; solo salen las dos con código 4xx. Para salir de `tail -f`, Ctrl+C.

<Callout type="risk">

- **`--line-buffered` es necesario detrás de `tail -f`:** sin él, `grep` acumula su salida y la enseña a trozos, así que parece que no llega nada.
- **`tail -f` no muestra las líneas antiguas con `-n 0`:** sin esa opción, empieza enseñando las 10 últimas.

</Callout>

## Paso 4: buscar, tuberías y redirecciones

```text
$ grep -rn "MONGODB_URI" src/
src/lib/mongo.ts:3:import { MONGODB_DB, MONGODB_URI } from "astro:env/server";
src/lib/mongo.ts:11:  new MongoClient(MONGODB_URI, {
$ grep -c "→ 401" logs/app.log
3
$ grep "→ 4" logs/app.log | head -n 3
GET /api/entrenos → 401 (0.1 ms)
GET /api/entrenos/no-existe → 404 (0.4 ms)
GET /api/entrenos → 422 (0.7 ms)
$ grep -v "→ 200" logs/app.log | wc -l
      10
$ find . -name "*.astro" -not -path "./node_modules/*" | wc -l
      11
$ find src -name "*.tsx" | head -n 3
src/components/Objetivo.tsx
src/components/Entrenos.tsx
src/components/NuevaNota.tsx
$ cut -d " " -f 4 logs/app.log | sort | uniq -c | sort -rn
  26 200
   3 422
   3 404
   3 401
   1 302
```

- **`grep`** busca texto: `-r` en todas las subcarpetas, `-n` con el número de línea, `-c` cuenta las líneas, `-v` invierte (las que **no** coinciden) y `-l` solo da los nombres de archivo.
- **`find`** busca archivos por nombre (`-name "*.astro"`), tipo o fecha. `-not -path "./node_modules/*"` excluye una carpeta. En un proyecto de JavaScript, olvidarlo es buscar entre miles de archivos ajenos.
- **La tubería `|`** conecta la salida de un comando con la entrada del siguiente. La última línea es una cadena de cuatro: `cut` saca la cuarta columna (el código), `sort` la ordena, `uniq -c` cuenta los repetidos y `sort -rn` ordena por número. En una línea, el resumen de errores de tu app.

Las **redirecciones** mandan la salida a un archivo en lugar de a la pantalla:

```text
$ echo "primera línea" > salida.txt && cat salida.txt
primera línea
$ echo "segunda línea" >> salida.txt && cat salida.txt
primera línea
segunda línea
$ echo "lo pisa todo" > salida.txt && cat salida.txt
lo pisa todo
$ ls archivo-que-no-existe > lista.txt
ls: archivo-que-no-existe: No such file or directory
$ cat lista.txt | wc -c
       0
$ ls archivo-que-no-existe 2> errores.txt; cat errores.txt
ls: archivo-que-no-existe: No such file or directory
$ ls archivo-que-no-existe . > todo.txt 2>&1; cat todo.txt
ls: archivo-que-no-existe: No such file or directory
.:
docs
errores.txt
lista.txt
proyecto
salida.txt
todo.txt
$ ls archivo-que-no-existe 2> /dev/null; echo "código de salida: $?"
código de salida: 1
```

| Símbolo          | Qué hace                                                                         |
| ---------------- | -------------------------------------------------------------------------------- |
| `>`              | Escribe la salida en un archivo, **sustituyendo** lo que tuviera                 |
| `>>`             | La **añade** al final                                                            |
| `2>`             | Redirige los **errores** (los programas escriben los errores en un canal aparte) |
| `> archivo 2>&1` | Las dos cosas al mismo archivo                                                   |
| `2> /dev/null`   | Descarta los errores (`/dev/null` es un "agujero negro")                         |

- **Los errores no pasan por `>`:** `ls archivo-que-no-existe > lista.txt` sigue mostrando el error en pantalla, y `lista.txt` queda vacío (0 bytes). Hace falta `2>`.
- **`$?`** es el código de salida del último comando: 0 si fue bien, otro número si falló. Los _scripts_ de I6.6 lo usan para decidir.

<Callout type="risk">

- **`>` sobre un archivo importante lo vacía al instante:** `echo algo > .env` borra todo el `.env` y deja solo `algo`. Si querías añadir, era `>>`. En el servidor, haz una copia (`cp .env .env.bak`) antes de tocar un archivo de configuración.
- **`grep` interpreta algunos caracteres como patrones:** `.` significa "cualquier carácter" y `*`, "repetido". Para buscar texto literal con esos caracteres, usa `grep -F`.

</Callout>

## Paso 5: alias y `~/.zshrc`

Un **alias** es un nombre corto para un comando largo. Se escriben en **`~/.zshrc`**, el archivo que `zsh` lee al abrir cada terminal. Ábrelo con tu editor:

```bash
code ~/.zshrc
```

Y añade al final:

```bash
# Archivo: ~/.zshrc (añade esto al final)
alias gs="git status -sb"
alias dev="npm run dev"
alias ll="ls -lah"
alias ..="cd .."
alias errores='grep -v "→ 200" logs/app.log'

# Una función: como un alias, pero con argumentos
buscar() {
  grep -rn "$1" src/
}
```

Guarda y recarga la configuración en la terminal abierta (las nuevas ya la leerán solas):

```bash
source ~/.zshrc
```

```text
ll='ls -lah'
gs='git status -sb'
errores='grep -v "→ 200" logs/app.log'
buscar is a shell function from /Users/tu-usuario/.zshrc
GET /api/entrenos → 401 (0.1 ms)
GET /api/entrenos/no-existe → 404 (0.4 ms)
src/lib/mongo.ts:3:import { MONGODB_DB, MONGODB_URI } from "astro:env/server";
src/lib/auth.ts:5:import { BETTER_AUTH_SECRET, BETTER_AUTH_URL } from "astro:env/server";
src/services/index.ts:3:import { OBJETIVO_SEMANAL_MINUTOS } from "astro:env/server";
```

- **`alias` sin argumentos** lista los alias definidos; con un nombre, enseña ese.
- **Una función** (`buscar`) es como un alias, pero con argumentos: `$1` es el primero.
- **`errores`** funciona en cualquier proyecto que tenga `logs/app.log`, porque la ruta es relativa a la carpeta en la que estás.

<Callout type="risk">

- **No uses el nombre de un comando que ya existe:** un alias `ls="ls -la"` cambia `ls` en todas partes, incluidos los _scripts_ que lo esperan normal. Por eso `ll` es un nombre nuevo.
- **Un error en `~/.zshrc` afecta a todas las terminales:** si al abrir una ves un error, revisa lo último que añadiste. Antes de editarlo, cópialo: `cp ~/.zshrc ~/.zshrc.bak`.
- **En el servidor, el archivo es otro:** `bash` lee `~/.bashrc`. Tus alias del Mac no existen allí.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. Crea 5 alias útiles en tu `~/.zshrc` (por ejemplo, `gs` para `git status` y `dev` para `npm run dev`) y comprueba que funcionan en una terminal nueva.
2. Cuenta, con una sola línea de comandos, cuántos componentes de React tiene tu app.
3. Comprueba si todos los archivos `.tsx` son componentes con `export default function`, y averigua cuál no lo es.

</Callout>

Solución. Los alias son los del Paso 5 (`gs`, `dev`, `ll`, `..` y `errores`), más la función `buscar`. Para contar los componentes:

```text
$ find src -name "*.tsx" | wc -l
       9
$ grep -rl "export default function" src --include="*.tsx" | wc -l
       8
$ grep -rL "export default function" src --include="*.tsx"
src/components/CampoTexto.tsx
```

- **`find src -name "*.tsx" | wc -l`** cuenta los archivos de React: 9. Basta con `src` para no entrar en `node_modules`; si buscaras desde la raíz del proyecto, añade `-not -path "./node_modules/*"`.
- **Pero no todos son iguales:** `grep -rl` lista los archivos que **contienen** el texto (8) y `grep -rL`, los que **no** lo contienen. `CampoTexto.tsx` (I5.5) se exporta con nombre y con `forwardRef`, no con `export default function`. "Contar componentes" depende de cómo definas componente, y la terminal te deja comprobarlo en segundos.

<Callout type="risk">

- **`wc -l` cuenta líneas, no archivos:** funciona porque `find` escribe un archivo por línea. Con nombres de archivo que contienen saltos de línea (raro, pero posible), el recuento sería incorrecto.
- **`--include="*.tsx"` necesita comillas:** sin ellas, `zsh` intenta expandir el `*` antes de pasárselo a `grep` y, si no encuentra nada en la carpeta actual, da el error `no matches found`.

</Callout>

<Callout type="mastery">

Usas la terminal para tareas que antes hacías en Finder: te mueves con rutas absolutas y relativas, creas, copias, mueves y borras sabiendo que no hay papelera, lees y sigues registros con `less` y `tail -f`, buscas con `grep` y `find`, encadenas comandos con tuberías, guardas resultados con redirecciones y tienes tus propios alias.

</Callout>

## Resumen

- La _shell_ (`zsh` en el Mac, `bash` en los servidores) ejecuta cada comando en la carpeta actual; `pwd` dice cuál es.
- `cp`, `mv` y `rm` actúan sin avisar ni papelera; `-i` pide confirmación.
- `cat`, `less`, `head`, `tail` y `tail -f` para leer; `grep` y `find` para buscar.
- `|` encadena comandos; `>` sustituye, `>>` añade, `2>` redirige los errores.
- En `bash`, las variables siempre entre comillas: `"$archivo"`.
