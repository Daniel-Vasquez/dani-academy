Un servidor lo comparten varios usuarios y programas, y Linux decide qué puede hacer cada uno con **usuarios, grupos y permisos**. Casi todo "no funciona en el servidor" (y mucho de seguridad) viene de ahí: un `.env` que lee cualquiera, una app que no puede escribir, un _script_ que no se ejecuta. Aquí creas tu servidor de práctica y un usuario para desplegar, y lees y cambias permisos hasta entender `-rw-r--r--` de un vistazo.

**Requisitos:** I6.1, un Mac con Apple Silicon o Intel, unos 3 GB libres y [Homebrew](https://brew.sh).

## Paso 1: tu servidor de práctica con Lima

**Qué es:** **Lima** crea una máquina virtual con Ubuntu dentro de tu Mac, gratis y desde la terminal: un Linux de verdad para romper sin miedo. Un contenedor de Docker no sirve: no tiene `systemd` (I6.4) ni _firewall_ (I6.5).

**Cómo se usa:**

```bash
brew install lima
limactl create --name=academy --cpus=2 --memory=2 --disk=10 --tty=false \
  --set '.mounts=[] | .networks=[{"vzNAT":true}]' template:ubuntu-lts
limactl start academy
limactl shell academy
```

- **`--set '.mounts=[]'`** no comparte tu carpeta del Mac: nada del servidor puede tocar tus archivos.
- **`.networks=[{"vzNAT":true}]`** da al servidor una IP propia (`192.168.64.x`), que usarás en I6.5.
- **`limactl shell academy`** abre una terminal **dentro**: hasta `exit`, todo se ejecuta en Ubuntu (26.04 LTS en la medición). Lima crea un usuario como el tuyo con `sudo` sin contraseña (`tu-usuario` en las salidas); un VPS suele empezar como `root`, y lo primero es lo del Paso 2.

<Callout type="risk">

- **Bórralo al acabar el curso:** `limactl stop academy` lo apaga y `limactl delete academy` lo elimina; encendido usa 2 GB de RAM.
- **Mira en qué terminal estás:** un `sudo` en el sitio equivocado es el error más fácil de este curso.

</Callout>

## Paso 2: usuarios, grupos, `root` y `sudo`

**Qué es:** cada usuario tiene un número (UID), un grupo principal y otros grupos. **`root`** (UID 0) puede todo sin comprobaciones, así que no se trabaja con él: se usa un usuario normal con **`sudo`**, una tarea cada vez y con registro.

**Cómo se usa:** crea el usuario para desplegar.

```bash
sudo adduser --disabled-password --comment "" deploy
sudo passwd deploy
```

- **`--disabled-password`** lo crea sin contraseña para entrar (en I6.3, por SSH con clave), y **`passwd`** le pone la que pedirá `sudo`: larga y distinta de cualquier otra.

Comprobado en el servidor:

```text
$ whoami
tu-usuario
$ id
uid=501(tu-usuario) gid=1000(tu-usuario) groups=1000(tu-usuario),999(systemd-journal)
$ sudo adduser --disabled-password --comment "" deploy
usermod: no changes
$ groups deploy
deploy : deploy users
$ sudo usermod -aG sudo deploy
$ groups deploy
deploy : deploy sudo users
$ getent passwd deploy
deploy:x:1001:1001::/home/deploy:/bin/bash
$ sudo -l -U deploy
User deploy may run the following commands on lima-academy:
    (ALL : ALL) ALL
$ ls /root
ls: cannot open directory '/root': Permission denied
$ sudo ls -a /root
.
..
.bashrc
.profile
.ssh
```

- **`id`** da UID, grupo y grupos (`systemd-journal` deja leer los registros, I6.4). **`usermod -aG sudo deploy`** añade el grupo `sudo`; sin la `-a`, `-G` **sustituye** todos los grupos.
- **`sudo -l -U deploy`** muestra `(ALL : ALL) ALL`; **`/root`** no se puede ni listar sin `sudo`.
- **`/etc/passwd`** guarda nombre, UID 1001, GID 1001, carpeta y _shell_; la contraseña, cifrada, está en `/etc/shadow`, que solo lee `root`.

<Callout type="risk">

- **`usermod -G` sin `-a` es un clásico:** `-G docker deploy` lo deja **solo** en `docker`, sin `sudo`; si era tu único administrador, te quedas fuera.
- **Los grupos nuevos se aplican en la siguiente sesión:** `groups` no los muestra hasta volver a entrar.
- **Ubuntu 26.04 usa `sudo-rs`** (`sudo-rs 0.2.13`): cambian algunos mensajes, no los comandos ni `/etc/sudoers`.

</Callout>

## Paso 3: leer y cambiar permisos

**Qué es:** cada archivo tiene **dueño**, **grupo** y tres juegos de permisos (dueño, grupo y los demás), de tres letras cada uno.

| Letra | En un archivo            | En una carpeta                                 | Valor |
| ----- | ------------------------ | ---------------------------------------------- | ----- |
| `r`   | Leer el contenido        | Listar lo que contiene                         | 4     |
| `w`   | Modificarlo              | Crear, borrar o renombrar lo que contiene      | 2     |
| `x`   | Ejecutarlo como programa | **Entrar** en ella y acceder a lo que contiene | 1     |

`-rw-r--r--`: tipo (`-` archivo, `d` carpeta, `l` enlace), `rw-` dueño, `r--` grupo, `r--` otros. En **octal** se suma cada juego: `rw-` = 6, `r--` = 4, así que es **644**.

| Octal | Letras      | Uso típico                                           |
| ----- | ----------- | ---------------------------------------------------- |
| `644` | `rw-r--r--` | Archivos normales: todos leen, solo el dueño escribe |
| `600` | `rw-------` | Secretos: `.env`, claves SSH. Solo el dueño          |
| `640` | `rw-r-----` | Configuración que el grupo necesita leer             |
| `755` | `rwxr-xr-x` | Programas y carpetas públicas                        |
| `750` | `rwxr-x---` | Carpetas para el dueño y su grupo                    |
| `700` | `rwx------` | Carpetas privadas                                    |

**Cómo se usa:** como `deploy` (`sudo -iu deploy` abre su sesión), con tu usuario intentando leer sus archivos:

```text
$ sudo -iu deploy bash -c 'umask; touch nota.txt; mkdir privado; echo "echo hola desde el script" > saluda.sh; ls -l'
0022
total 8
-rw-r--r-- 1 deploy deploy    0 Oct 16 14:18 nota.txt
drwxr-xr-x 2 deploy deploy 4096 Oct 16 14:18 privado
-rw-r--r-- 1 deploy deploy   26 Oct 16 14:18 saluda.sh
$ sudo -iu deploy bash -c './saluda.sh'
bash: line 1: ./saluda.sh: Permission denied
$ sudo -iu deploy bash -c 'chmod u+x saluda.sh && ./saluda.sh && ls -l saluda.sh'
hola desde el script
-rwxr--r-- 1 deploy deploy 26 Oct 16 14:18 saluda.sh
$ sudo -iu deploy bash -c 'echo "MONGODB_URI=secreto" > .env && chmod 600 .env && chmod 700 privado && chmod 644 nota.txt && ls -la'
total 32
drwxr-x--- 3 deploy deploy 4096 Oct 16 14:18 .
drwxr-xr-x 4 root   root   4096 Oct 16 14:18 ..
-rw-r--r-- 1 deploy deploy  220 Oct 16 14:18 .bash_logout
-rw-r--r-- 1 deploy deploy 3771 Oct 16 14:18 .bashrc
-rw------- 1 deploy deploy   20 Oct 16 14:18 .env
-rw-r--r-- 1 deploy deploy  807 Oct 16 14:18 .profile
-rw-r--r-- 1 deploy deploy    0 Oct 16 14:18 nota.txt
drwx------ 2 deploy deploy 4096 Oct 16 14:18 privado
-rwxr--r-- 1 deploy deploy   26 Oct 16 14:18 saluda.sh
$ ls -ld /home/deploy
drwxr-x--- 3 deploy deploy 4096 Oct 16 14:18 /home/deploy
$ cat /home/deploy/nota.txt
cat: /home/deploy/nota.txt: Permission denied
$ sudo chmod 755 /home/deploy && cat /home/deploy/nota.txt && echo "(nota.txt es 644: se puede leer)"
(nota.txt es 644: se puede leer)
$ cat /home/deploy/.env
cat: /home/deploy/.env: Permission denied
$ ls /home/deploy/privado
ls: cannot open directory '/home/deploy/privado': Permission denied
$ sudo chmod 750 /home/deploy && ls -ld /home/deploy
drwxr-x--- 3 deploy deploy 4096 Oct 16 14:18 /home/deploy
$ sudo touch /home/deploy/config.json && sudo ls -l /home/deploy/config.json
-rw-r--r-- 1 root root 0 Oct 16 14:19 /home/deploy/config.json
$ sudo -iu deploy bash -c 'echo "{}" > config.json'
bash: line 1: config.json: Permission denied
$ sudo chown deploy:deploy /home/deploy/config.json && sudo ls -l /home/deploy/config.json
-rw-r--r-- 1 deploy deploy 0 Oct 16 14:19 /home/deploy/config.json
$ sudo -iu deploy bash -c 'echo "{}" > config.json && echo "escrito"'
escrito
```

- **Lo nuevo nace con `644` y `755`:** la **`umask`** (`0022`) resta a `666` y `777`.
- **Un _script_ nuevo no se ejecuta** (`Permission denied`) hasta `chmod u+x` (`u` dueño, `g` grupo, `o` otros, `a` todos; `+` añade, `-` quita).
- **La carpeta de `deploy` es `750`:** nadie más entra, aunque `nota.txt` sea `644`. Hace falta permiso en el archivo **y** `x` en todo el camino. Con `755`, `nota.txt` se lee; `.env` (600) y `privado` (700), no.
- **`chown dueño:grupo`** cambia el dueño: lo creado con `sudo` es de `root` y `deploy` no lo puede escribir hasta entonces.

<Callout type="risk">

- **`chmod 777` no arregla nada, lo rompe:** cualquiera puede modificar el archivo o vaciar la carpeta. Averigua **qué** usuario necesita **qué** permiso.
- **Lo creado con `sudo` es de `root`:** `sudo nano /opt/app/.env` o `sudo git clone` dejan archivos que la app no lee. Trabaja como su usuario o `chown` después.
- **`chmod -R 644` quita la `x` a las subcarpetas** y nadie entra. Por tipo: `find carpeta -type d -exec chmod 755 {} +` y `find carpeta -type f -exec chmod 644 {} +`.

</Callout>

## Paso 4: instalar programas con `apt`

**Qué es:** **`apt`** instala desde los **repositorios** de Ubuntu: el paquete, sus dependencias y todo en su sitio. Siempre en dos pasos: actualizar la lista e instalar.

**Cómo se usa:**

```text
$ sudo apt update 2>&1 | tail -n 2
Reading state information...
41 packages can be upgraded. Run 'apt list --upgradable' to see them.
$ apt list --upgradable 2>/dev/null | wc -l
42
$ tree --version
bash: line 1: tree: command not found
$ sudo apt install -y tree 2>&1 | grep -E "^(Installing|Summary|  Download|Setting up)|Upgrading:|Installing:" | head -n 6
Installing:
Summary:
  Upgrading: 0, Installing: 1, Removing: 0, Not Upgrading: 41
  Download size: 52.7 kB
Setting up tree (2.3.1-1) ...
$ tree --version
tree v2.3.1 © 1996 - 2026 by Steve Baker, Thomas Moore, Francesc Rocher, Florian Sesser, Kyosuke Tokoro
$ which tree
/usr/bin/tree
$ dpkg -L tree | grep -E "bin|man1"
/usr/bin
/usr/bin/tree
/usr/share/man/man1
/usr/share/man/man1/tree.1.gz
$ apt show tree 2>/dev/null | grep -E "^(Package|Version|Installed-Size|Description)"
Package: tree
Version: 2.3.1-1
Installed-Size: 162 kB
Description: displays an indented directory tree, in color
$ sudo apt remove -y tree 2>&1 | grep -E "^(Removing|REMOVING|Summary)" | head -n 3
REMOVING:
Summary:
Removing tree (2.3.1-1) ...
$ tree --version
bash: line 1: tree: command not found
```

- **`apt update`** solo descarga la lista y dice cuántas actualizaciones hay; **`apt install -y`** instala sin preguntar (`tree`, 52,7 kB).
- **`dpkg -L`** dice dónde quedó cada archivo: el programa en `/usr/bin`, el manual en `/usr/share/man`.
- **`apt remove`** desinstala, `purge` borra también la configuración y `autoremove` las dependencias huérfanas. **`sudo apt upgrade`** instala las pendientes (41): hazlo con regularidad, muchas son de seguridad.

<Callout type="risk">

- **No instales a mano si hay paquete:** algo copiado en `/usr/local/bin` no se actualiza y nadie lo recuerda. Para Node.js, el repositorio de NodeSource o `nvm`.
- **`apt upgrade` en producción, con calma:** algunas actualizaciones reinician servicios. En un momento tranquilo y antes en un servidor de pruebas como este.

</Callout>

## Paso 5: dónde está cada cosa

**Qué es:** las carpetas del sistema y lo que contiene cada una.

**Cómo se usa:**

```text
$ ls /

dev
etc
home

lost+found
media
mnt
opt

root
run
sbin
snap
srv

$ ls /etc | wc -l
195
$ ls -l /etc/ssh/sshd_config /etc/hostname /etc/passwd /etc/shadow
-rw-r--r-- 1 root root     13 Oct 16 14:11 /etc/hostname
-rw-r--r-- 1 root root   1694 Oct 16 14:18 /etc/passwd
-rw-r----- 1 root shadow  906 Oct 16 14:18 /etc/shadow
-rw-r--r-- 1 root root   4307 Aug 31 12:36 /etc/ssh/sshd_config
$ ls /var/log | head -n 8

$ ls /opt
$ sudo du -sh /usr /var /etc 2>/dev/null
2.8G	/usr
323M	/var
6.2M	/etc
```

| Carpeta | Qué contiene                                                        | Ejemplo                                      |
| ------- | ------------------------------------------------------------------- | -------------------------------------------- |
| `/etc`  | Configuración del sistema y de los servicios (195 entradas, 6,2 MB) | `/etc/ssh/sshd_config` (I6.3)                |
| `/var`  | Datos que cambian: registros, cachés, bases de datos                | `/var/log/auth.log`, los accesos al servidor |
| `/home` | Las carpetas personales de los usuarios                             | `/home/deploy`                               |
| `/opt`  | Programas y apps que no vienen en paquetes (vacía de serie)         | `/opt/entrenos`, tu app (I6.4)               |
| `/usr`  | Los programas instalados (2,8 GB, lo más grande)                    | `/usr/bin/tree`                              |
| `/tmp`  | Archivos temporales, que se borran al reiniciar                     | —                                            |
| `/root` | La carpeta personal de `root`                                       | —                                            |

- **`/etc/shadow` es `640` del grupo `shadow`:** nadie más lee los _hashes_ (I5.1). `/etc/passwd` es `644`.

<Callout type="risk">

- **Antes de editar `/etc`, una copia:** `sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak`. Un error en SSH puede dejarte fuera (I6.3).
- **`/tmp` se vacía al reiniciar:** los _backups_ de I6.6 van en `/var/backups`.

</Callout>

## Ejercicio práctico

<Callout type="exercise">

1. En tu servidor de práctica, con el usuario `deploy` del Paso 2, crea la carpeta `/opt/entrenos` para la app, de `deploy` y con permisos `750`.
2. Como `deploy`, crea dentro un `config.env` que el grupo pueda leer y un `.env` que solo pueda leer `deploy`.
3. Crea un usuario `lector` sin `sudo`, dale acceso de lectura a la configuración a través del grupo `deploy` y comprueba qué puede y qué no puede hacer.

</Callout>

Solución, comprobada en el servidor:

```text
$ sudo mkdir -p /opt/entrenos && sudo chown deploy:deploy /opt/entrenos && sudo chmod 750 /opt/entrenos && ls -ld /opt/entrenos
drwxr-x--- 2 deploy deploy 4096 Oct 16 14:19 /opt/entrenos
$ sudo -iu deploy bash -c 'cd /opt/entrenos && echo "PORT=4321" > config.env && echo "MONGODB_URI=secreto" > .env && chmod 640 config.env && chmod 600 .env && ls -la /opt/entrenos'
total 16
drwxr-x--- 2 deploy deploy 4096 Oct 16 14:19 .
drwxr-xr-x 3 root   root   4096 Oct 16 14:19 ..
-rw------- 1 deploy deploy   20 Oct 16 14:19 .env
-rw-r----- 1 deploy deploy   10 Oct 16 14:19 config.env
$ sudo adduser --disabled-password --comment "" lector >/dev/null 2>&1 && groups lector
lector : lector users
$ sudo -iu lector bash -c 'ls /opt/entrenos'
ls: cannot open directory '/opt/entrenos': Permission denied
$ sudo usermod -aG deploy lector && groups lector
lector : lector users deploy
$ sudo -iu lector bash -c 'ls /opt/entrenos && cat /opt/entrenos/config.env'
config.env
PORT=4321
$ sudo -iu lector bash -c 'cat /opt/entrenos/.env'
cat: /opt/entrenos/.env: Permission denied
$ sudo -iu lector bash -c 'echo "PORT=80" > /opt/entrenos/config.env'
bash: line 1: /opt/entrenos/config.env: Permission denied
$ sudo -iu lector bash -c 'sudo whoami'
sudo: I'm sorry lector. I'm afraid I can't do that
```

- **Sin el grupo, `lector` no lista `/opt/entrenos`:** con `750`, es "otros".
- **Con `usermod -aG deploy lector`** es "grupo": lista y lee `config.env` (`640`), pero ni `.env` (`600`) ni modificar `config.env` (sin `w`). Y sin `sudo`, con el mensaje de `sudo-rs`.
- **Es el patrón de un servidor real:** la app y sus archivos de un usuario, y quien lee registros o configuración en su grupo, sin tocar los secretos.

<Callout type="risk">

- **El grupo da todo lo que el grupo lee:** `lector` lee cualquier `640` o `750` de `deploy`, no solo `/opt/entrenos`. Para separar, un grupo propio (`sudo addgroup entrenos-lectura`).
- **Borra los usuarios de práctica:** `sudo deluser --remove-home lector`.

</Callout>

<Callout type="mastery">

Lees `-rw-r--r--` y sabes quién puede hacer qué: el dueño lee y escribe, el grupo y los demás solo leen (644). Creas usuarios con `sudo` sin trabajar como `root`, das los permisos justos con `chmod` en octal o simbólico y con `chown`, compartes por grupo sin exponer los secretos (600), instalas con `apt` y sabes en qué carpeta del sistema buscar cada cosa.

</Callout>

## Resumen

- Lima da un Ubuntu de práctica que no puede tocar tus archivos.
- Nada como `root`: un usuario con `sudo` (`usermod -aG`, con la `-a`).
- `r=4`, `w=2`, `x=1`: 644 archivos, 600 secretos, 755 y 750 carpetas.
- En una carpeta, `x` es entrar, y hace falta en todo el camino.
- `apt update`, después `apt install`; `dpkg -L` dice dónde quedó cada archivo.
